MAP 全体地図 — キャッシュは1個ではない

「キャッシュ」と一言で言うが、1リクエストの経路上には最低7層のキャッシュがある。どの層で解くかを間違えると、いくら Redis をチューニングしても速くならない。まずこの地図を頭に入れる。

⑦ この表から読み取るべき法則

  • 速さと無効化のしやすさは反比例する。 ブラウザキャッシュは0msだが、世界中の端末に散らばったコピーを消す手段は存在しない。Redisは2msかかるが DEL 一発で全員に効く。

01 Cacheとは / なぜ必要なのか

キャッシュ＝「取得や計算にコストがかかる結果を、速い場所に置いた複製」。定義はこれだけ。難しいのは定義ではなく、複製を持った瞬間に生まれる「原本とのズレ」をどう扱うか。この章はその出発点。

🏛 図書館の例え。 あなたは論文を書いていて、同じ辞書を1日に200回引く。毎回地下書庫まで往復（片道5分）していたら、それだけで1日が終わる。だから机の上に辞書を置く。これがキャッシュ。
ただし置いた瞬間、こういう問題が生まれる: ①机は狭い（どれを置くか＝追い出し）②書庫の辞書が改訂されても机の上は古い版のまま（整合性）③隣の席の人も同じ辞書を欲しがる（共有）。この3つが本書の全て。

① この技術は何を解決するために生まれたのか

解決するのは 「速度差」 そのものではなく、「速度差 × 繰り返し回数」という掛け算。コンピュータの記憶階層は、速いものほど小さく高価という物理的な制約を持つ。この階層差は数桁ある。

図1-1 レイテンシ階層。数字の暗記より「桁がいくつ違うか」を体で覚える。面接では「メモリとディスクで5〜6桁、同一DCと大陸間で3桁」と言えれば十分。

⑥ メリット

  • レイテンシ短縮: 40ms → 0.6ms のような1〜2桁の改善。ユーザー体験に直結する。
  • スループット向上: DBの接続数というハードな上限を回避できる。
  • コスト削減: DBのスケールアップ（高価・上限あり）より、Redis追加（安価）のほうが桁違いに安い。db.r6g.4xlarge を1台減らせるなら cache.r6g.large を数台置いてもお釣りが来る。
  • スパイク耐性: TVで紹介された・バズった瞬間に耐えられるかは、ほぼキャッシュ設計で決まる。
  • 依存先の保護: 外部API（決済・地図・翻訳）のレート制限と課金を守る。これは速度ではなくお金と信頼性の話。

⑦ デメリット・トレードオフ

  • 整合性が壊れる: 原本と複製がズレる。これは「バグ」ではなく「仕様として選んだ結果」でなければならない。
  • デバッグが難しくなる: 「自分の環境では直っているのに本番で古い」の原因調査は、キャッシュが多層だと地獄。
  • 新しい障害モードが増える: Stampede / Hot Key / Avalanche / Penetration（12〜15章）。全部キャッシュを入れなければ存在しない障害。
  • 運用対象が増える: Redisのフェイルオーバー・メモリ監視・バージョンアップ。
  • 「遅い理由」を隠す: N+1クエリをキャッシュで塞ぐと、cold start や cache flush の瞬間に必ず牙をむく。

⑨ Googleレベルではどう設計されるか

  • キャッシュを「性能最適化」ではなく「容量計画の一部」として扱う。 設計ドキュメントに必ず「想定ヒット率」と「ヒット率が0%になった時にバックエンドが耐えられるか」の2つを書く。後者を cache-loss survivability と呼ぶ。これに答えられない設計はレビューを通らない。
  • 「キャッシュが落ちてもサービスは落ちない」を必ず設計する。 具体的には ①バックエンドへの流量を load shedding / adaptive throttling で制限し ②溢れた分は degrade（古い値を返す・簡易版を返す・503を返す）させる。Google SRE Book の「Handling Overload」の章がそのまま該当。
  • ヒット率ではなく「バックエンドQPSの p99」を SLI にする。 ヒット率99%でも、Hot Key が1本あればバックエンドの特定シャードは死ぬ。平均値ではなく分布を見る。
  • キャッシュ層を専用サービスとして切り出す。 Google なら Memcache/Slicer、Facebook なら mcrouter + memcached、Netflix なら EVCache。アプリごとに Redis クライアントの設定を書かせない。一貫性ポリシーをライブラリで強制するのが要点。

02 ヒット率と局所性 — キャッシュの算数

キャッシュ設計で唯一「計算できる」部分。ヒット率が数%変わるとバックエンド負荷が何倍変わるかを暗算できると、面接でも実務でも桁違いに強い。式は2本だけ。

🏛 図書館の例え。 蔵書100万冊のうち、実際に借りられるのはごく一部の人気本に集中する。上位1000冊（0.1%）が貸出全体の半分を占める、というのはあらゆる図書館で観測される現象。
だから「机に何冊置くか」ではなく「どの本を置くか」が効く。ランダムに1000冊置いてもヒット率は0.1%だが、人気上位1000冊を置けば50%になる。500倍の差。これが局所性（locality）。

① 何を解決するために生まれたのか（この章の問い）

「キャッシュを入れました。効果はどれくらいですか?」に定量的に答えるための道具。「速くなりました」では設計にならない。「ヒット率95%で、DB到達QPSは 10,000 → 500、平均レイテンシは 40ms → 2.6ms になります」と言えるのが設計。

③ 基本概念 — 2本の式

// 式1: 実効レイテンシ（Average Memory Access Time の考え方） 実効レイテンシ = H × T_cache + (1 - H) × (T_cache + T_backend) = T_cache + (1 - H) × T_backend H : ヒット率（0〜1） T_cache : キャッシュのレイテンシ（Redis: 0.5ms） T_backend : バックエンドのレイテンシ（DB: 40ms） // 重要: MISS したときは「キャッシュを見る時間 + DBへ行く時間」の両方かかる。 // つまりキャッシュは MISS 時に必ず少し遅くする。それでも H が高ければ勝つ。 // 式2: バックエンドに到達する QPS Backend QPS = Total QPS × (1 - H) // この (1 - H) を「ミス率」と呼ぶ。設計で見るべきはヒット率ではなくミス率。 // 99% → 95% は「4ポイント下がった」ではなく「ミス率が 1% → 5% = 5倍になった」。

ここが最重要: ヒット率は線形に効かない。95%→99% は「4%の改善」ではなく「バックエンド負荷が1/5になる」。逆に 99%→95% は「わずかな悪化」ではなく「DB負荷が5倍になる障害」。ヒット率のグラフを見るときは、常に 1 - H を対数で見る癖をつける。

④ 内部でどう動くのか — なぜヒット率が高くなるのか（局所性）

ヒット率が高くなる理由は運ではなく、アクセスに偏り（局所性）があるから。偏りには2種類ある。

  • 時間的局所性（Temporal locality）: 一度アクセスされたものは、すぐまたアクセスされる。→ LRU が効く根拠（17章）
  • 空間的局所性（Spatial locality）: 近くのものが一緒にアクセスされる。→ DBのページ読み・CDNのプリフェッチの根拠

そしてWebサービスのアクセス分布は経験的に Zipf 分布（べき乗則）に従う。「n番目に人気のアイテムのアクセス数は 1/n に比例する」。

図2-2 Zipf分布と容量-ヒット率カーブ。「キャッシュ容量を2倍にしてもヒット率は数%しか上がらない」のはこのカーブの形が理由。

⑩ 面接での問われ方

Q. 「1億件の商品があります。キャッシュには何を入れますか?」

悪い答え: 「全部入れます」「LRUで自動的に決まります」
良い答え: 「アクセスはZipf分布に従うので、全件入れる必要はありません。上位1%（100万件）を入れれば約50%、上位10%で約80%のヒット率が見込めます。1件1KBとして100万件で1GB、1000万件で10GB。まず1%から始めてヒット率を計測し、カーブが寝るところで止めます。同時に、載らないロングテールがDBに落ちる分をキャパシティとして確保します。」

Q. 「ヒット率を上げるにはどうしますか?」（答えは4方向あることを示せると良い）

  1. TTLを伸ばす → 鮮度とのトレードオフ。明示的無効化とセットにすれば伸ばせる（10章）
  2. 容量を増やす → evicted_keys が出ている時だけ有効。カーブが寝ていたら金の無駄
  3. キー空間を小さくする → パラメータ正規化。最も費用対効果が高いのに見落とされがち
  4. 載せ方を変える → 事前計算して常駐させる（Refresh Ahead / warm up）。8章

03 TTL — 鮮度の設計

TTL は「N秒後に自動で消える」という時限装置。実装は1行だが、TTLの数字を決める行為はビジネス判断そのもの。「なんとなく300秒」で設定された値が、後の障害の原因になる。

🏛 図書館の例え。 机に置いた辞書に「◯月◯日まで有効」と付箋を貼る。期限が来たら机から下げて、次に必要になったとき書庫から改訂版を取ってくる。
ここで大事なのは、期限が切れるまでは改訂版が出ていても気づかないということ。TTLは「最大でこれだけ古い可能性がある」という上限の宣言であって、鮮度の保証ではない。

① 何を解決するために生まれたのか

「無効化を実装しなくても、いつかは正しくなる」という保険。全ての更新パスから確実にキャッシュを消すのは現実には難しい（バッチ・管理画面・DB直修正・他チームのサービス）。TTLはそれらの漏れを時間で回収する仕組み。

同時に、メモリの自動回収機構でもある。 TTLがなければキャッシュは単調増加し、いつか必ずメモリを食い潰す。

② TTLがないと何が問題になるのか

TTLなし（永続キャッシュ）で起きること結果
無効化の実装漏れが1箇所でもあると、そのキーは永遠に古い「なぜか1人だけ古い名前で表示される」が半年続く
キー数が単調増加するmaxmemory 到達 → 予期しない eviction で全体のヒット率が突然崩れる
アクセスされなくなったキーが残り続けるメモリの大半が「二度と使われないデータ」で埋まる
スキーマ変更時に古い構造のJSONが残るデプロイ後にデコードエラーが多発（→ キーにバージョンを入れる、後述）

図3-1 TTLが作る「ズレの窓」。TTLは鮮度の保証ではなく、古さの上限値。

④ 内部でどう動くのか — Redis はどうやって期限切れを消しているか

ここは面接で稀に刺さる。Redis は TTL 満了の瞬間にキーを消していない。 タイマーで全キーを監視するのは O(n) で不可能だから、2つの戦略を組み合わせている。

図3-2 Redisの期限切れ削除。「TTLは即座には消えない」「消える瞬間にCPUを食う」の2点が実務の要点。

  • 実装が1引数で済む。最も安いキャッシュ整合性戦略
  • 無効化の実装漏れを時間で回収できる（保険として機能する）
  • メモリが自動的に回収される
  • 「最大でTTL秒古い」という説明可能な保証が得られる。SLAに書ける

⑦ トレードオフ

  • 短くするとヒット率が落ちる。TTL 5秒はほぼキャッシュしていないのと同じになることがある
  • 長くすると古さが目立つ
  • TTL満了は「全員同時」に起きる。同じタイミングで作られたキーは同じタイミングで死ぬ（14章 Avalanche）
  • TTL単体では「更新した瞬間に反映」ができない。→ 明示的無効化（10章）と組み合わせるのが実務

⑨ Googleレベルの設計 — 「TTLを2つ持つ」という発想

上級テクニック。物理TTLと論理TTLを分ける。これは12章（Stampede）と14章（Avalanche）の両方を同時に解く強力なパターンなので、ここで概念だけ入れておく。

// 値の中に「論理的な期限」を埋め込み、Redis の TTL（物理）はその 2〜3 倍にする type Entry[T any] struct { Value T `json:"v"` ExpiresAt time.Time `json:"exp"` // ← 論理TTL（例: 300秒後） } rdb.Set(ctx, key, entry, 900*time.Second) // ← 物理TTL は 3倍 // 読み取り時: // now < ExpiresAt → そのまま返す（HIT） // ExpiresAt <= now → 「古いが値はある」状態 // → 1本だけ非同期で更新を走らせ、他は古い値を即返す // キー自体が無い（物理TTL切れ） → 本当のMISS。同期で取りに行く

効果: ①TTL満了時に全員がDBに殺到しない（古い値を返せるから）②DBが遅い・落ちている間も古い値でサービスが継続する（graceful degradation）。これは HTTP の stale-while-revalidate と全く同じ思想で、CDN・ブラウザ・Redis の3層で同じパターンが使える（24章で再登場）。

⑩ 面接での問われ方

Q. 「TTLは何秒にしますか?」 — この質問に「300秒です」と即答すると落ちる。正解は逆算のプロセスを見せること。

  1. 「このデータが古かった場合、誰がどう困りますか?」を先に確認する（ビジネス要件の確認）
  2. 許容遅延が決まったら、それをTTLの上限にする
  3. 下限は「ヒット率が要件を満たす最小値」。更新頻度が1時間に1回なら、TTL 60秒でもヒット率はほぼ落ちない
  4. 更新時に明示DELできるパスがあるなら、TTLは長めにして保険に徹させる
  5. 最後にジッターを必ず付けると言う。ここまで言えれば満点

04 Cache Aside（Lazy Loading）

実務で使われるキャッシュの9割はこれ。「アプリがキャッシュを見て、無ければDBから取って、自分で書き戻す」という最も素朴なパターン。素朴だが、正しく書くのは意外に難しい。この章で落とし穴まで潰す。

🏛 図書館の例え。 あなた自身が机を見て、無ければ書庫に取りに行き、戻ってきたら机に置く。司書は何もしてくれない。「キャッシュはただの箱で、賢いのはアプリ側」という構造。
次章の Read Through は「司書に頼めば、司書が書庫まで行って机に置いてくれる」構造。この違いが両者の全て。

① 何を解決するために生まれたのか

特別な仕組みを何も要求しないこと。キャッシュ側に「DBの読み方」を教える必要がないので、Redis / Memcached / メモリ内Map のどれでも同じコードで動く。任意のクエリ・任意の計算結果・外部API のレスポンスまで、何でもキャッシュできる汎用性が最大の価値。

  • 何でもキャッシュできる。テーブル1行でも、10テーブルJOINの集計でも、外部APIのレスポンスでも同じコード

  • 実際に要求されたものだけが載る = メモリ効率が良い（Lazy Loading の名の由来）
  • Redis / Memcached / メモリMap を差し替え可能

⑦ トレードオフ

  • キャッシュのロジックがアプリ全体に散らばる。100箇所に同じ if 文が書かれ、1箇所だけ TTL を忘れる
  • 初回アクセスは必ず遅い（cold start）。デプロイ直後・スケールアウト直後に p99 が跳ねる

  • 整合性は結果整合。DB更新とDELの間に必ず隙間がある

  • ほぼ全てのWebサービスの読み取りパス。 「Redisを使っています」と言う場合、9割はこれ
  • AWS ElastiCache のドキュメントでも第一の推奨パターン。 AWS は "Lazy Loading" と呼ぶ
  • 外部API のレート制限対策。 為替レート・地図のジオコーディング・翻訳など、1回の呼び出しが有料なもの
  • 重い集計。 「今月の売上ランキング」を毎回計算せず、10分キャッシュ

質問答えの骨子
「更新時、キャッシュは削除しますか更新しますか?」削除。理由は①並行更新で古い値が固定化するのを防げる ②DELは冪等 ③更新後すぐ読まれないキーを無駄に温めない。ただし超Hotなキーは例外的にSETもあり（DELすると全員がMISSして殺到するため）と付け加えられると強い
「DB更新とキャッシュ削除、どちらが先ですか?」DB更新が先。DELが先だと隙間で古い値が載り直す。ただし「DB更新後にDELが失敗する」ケースは残るので、TTLを保険にする／CDCで確実に消す（10章）
「Redisが落ちたらどうしますか?」キャッシュのエラーはMISS扱いにしてDBにフォールバック。ただし全量が流れると死ぬので、サーキットブレーカで同時実行数を制限し、超過分は劣化レスポンスを返す
「Cache Aside の弱点は?」①コールドスタート ②Stampede ③ロジックの散在。①はwarm up、②はsingleflight、③はライブラリ化で対処。ここまで即答できると Cache Aside の理解は合格

05 Read Through

Cache Aside の「アプリがDBに行く」部分を、キャッシュ層に代行させるパターン。アプリから見ると「キャッシュに聞けば必ず値が返ってくる」ように見える。Cache Aside との違いは責務の置き場所だけで、動作の本質は同じ。

🏛 図書館の例え。 Cache Aside ではあなたが書庫まで走る。Read Through では司書に頼むと、司書が「机にありますよ」あるいは「無いので取ってきますね」と対応して、必ず本を手渡してくれる。
あなたは書庫の場所も、本の並べ方も知らなくていい。知識が司書（キャッシュ層）に集約されるのが利点であり、同時に「司書が知らないものは頼めない」という制約でもある。

  • アプリのコードが1行になる。読み取り側にキャッシュの知識が要らない
  • 規律を強制できる: TTL必須・singleflight・メトリクス・シリアライズ形式・キー命名を1箇所で担保
  • キャッシュ戦略を後から差し替えられる（Redis→2層、TTL→論理TTLなど、呼び出し側の変更ゼロで）
  • 大規模組織・マイクロサービス多数の環境で真価を発揮

⑦ トレードオフ

  • キーごとに loader を登録する必要がある。アドホックな集計・検索クエリには向かない
  • 抽象化のコスト。「なぜこのクエリが飛んだのか」がコードから見えにくくなる
  • 性能は Cache Aside と同じ。速度目的で導入しても意味がない
  • Redis 自体は Read Through をサポートしない（DBを読む機能が無い）。必ずアプリ側にライブラリを作ることになる

⑧⑨ 実務例と Google レベル

  • Java の Ehcache / Caffeine / Guava LoadingCache: CacheLoader を登録する形。Read Through の最も有名な実装。Caffeine の LoadingCache は singleflight 相当も内蔵する
  • Facebook の TAO: ソーシャルグラフ専用の Read Through キャッシュ層。アプリは「このIDのフレンド一覧」と聞くだけで、キャッシュ層がMySQLへの読み方を全部知っている
  • Netflix EVCache: クライアントライブラリがレプリカ選択・タイムアウト・フォールバックを全部内蔵。アプリは規律を意識しない
  • DynamoDB Accelerator (DAX): AWS で唯一「本物の Read Through」が使えるマネージドサービス。DynamoDB の API と互換なので、SDKのエンドポイントを差し替えるだけでキャッシュが入る。アプリのコード変更が事実上ゼロという点で例外的に強力

Googleレベルの判断基準: チームが5人なら Cache Aside で十分。50人を超えたら Read Through 型のライブラリを作る。理由は性能ではなく、「レビューで防げないミス（TTL忘れ・singleflight忘れ・キー命名の不統一）を構造的に不可能にする」ため。

⑩ 面接での問われ方

Q. 「Cache Aside と Read Through、どちらを選びますか?」

満点の答え: 「性能は同じなので、性能で選ぶ問題ではありません。 判断軸は2つ。①アクセスパターンが固定的（IDで1件引く）なら Read Through にして規律を集約します。アドホックな検索や集計が多いなら Cache Aside の柔軟性が要ります。②チーム規模。人数が多いほど、ライブラリで強制できる Read Through の価値が上がります。実際にはホットパスだけ Read Through 型のヘルパーを用意し、それ以外は Cache Asideというハイブリッドが現実的です。」

06 Write Through

書き込みのときにキャッシュとDBを両方、同期的に更新するパターン。「キャッシュは常に最新」という強い性質が得られる代わりに、書き込みが遅くなり、2箇所を更新することによる新しい失敗モードが生まれる。

🏦 銀行の例え。 窓口で入金すると、行員は元帳（DB）に記入すると同時に、手元の残高メモ（キャッシュ）も書き換える。次に残高を聞かれたらメモを見れば済むので即答できる。
問題は「元帳に書いた直後、メモを書く前に行員が倒れたら?」。元帳は正しく、メモは古い。この不整合をどう扱うかが Write Through の全て。

① 何を解決するために生まれたのか

Cache Aside の2つの弱点を消すため。

  • 「更新直後の読み取りが必ずMISSになる」問題。 Cache Aside は更新時にDELするので、更新直後のアクセスは全部DBへ行く。更新が多く、かつ更新直後に読まれるデータ（自分のプロフィール・カート・スコア）ではこれが痛い
  • 「キャッシュに古い値が乗り続ける窓」を無くす。 Write Through なら書いた瞬間にキャッシュも新しい

図6-1 Write Through のシーケンスと3つの失敗モード。「2つのストアに書く」＝分散トランザクション、という認識が出発点。

④ 内部処理 — バージョン付き Write Through（実務で使える形）

失敗パターンCを塞ぐには、キャッシュに「いつの値か」を持たせて、古い書き込みを拒否する。Redis の Lua スクリプトで原子的に判定する。

// Lua: 保存されている version より新しい時だけ上書きする（Compare-And-Set） var setIfNewer = redis.NewScript(` local cur = redis.call('GET', KEYS[1]) if cur then local ok, decoded = pcall(cjson.decode, cur) if ok and tonumber(decoded.ver) >= tonumber(ARGV[2]) then return 0 end -- 古い書き込みは捨てる end redis.call('SET', KEYS[1], ARGV[1], 'EX', ARGV[3]) return 1 `) func (s *Service) UpdateProfile(ctx context.Context, u *User) error { // ① 必ず DB が先。ここで version（updated_at や楽観ロックの版番号）が確定する if err := s.repo.UpdateReturningVersion(ctx, u); err != nil { return err } // ② キャッシュへ。古いバージョンなら書き込まれない b, _ := json.Marshal(cacheEntry{Val: u, Ver: u.Version}) if err := setIfNewer.Run(ctx, s.rdb, []string{key(u.ID)}, b, u.Version, 300).Err(); err != nil { // ③ SET に失敗したら DEL にフォールバック（古い値を残すよりは MISS のほうがマシ） s.rdb.Del(ctx, key(u.ID)) metrics.WriteThroughFallback() } return nil }

判断のポイント: ここまでやる価値があるのは「更新直後に高頻度で読まれるHotなキー」だけ。大半のデータは Cache Aside の DEL で十分。Write Through はピンポイントで使う最適化と考える。

⑥ メリット

  • Read-your-writes が成立する: 自分が更新した直後に自分で読んで、古い値が見えることがない。UXに直結
  • 更新直後のMISSが発生しない: Hotなキーを DEL すると全員が殺到する（Cache Breakdown）が、SET なら起きない
  • キャッシュが常に「最新である」という前提でコードが書ける（TTLを保険としてしか使わなくてよい）
  • 読み取りが極端に多く、書き込みが少ないワークロードでは事実上ノーコスト

⑦ トレードオフ

  • 書き込みレイテンシが増える（DB + Cache の直列）
  • 2ストア更新の不整合が構造的に残る。完全な解は存在しない（分散トランザクションの問題）
  • 読まれないデータもキャッシュに載る。「1回書いて二度と読まれない」データが多いとメモリの無駄（ログ・イベント系は最悪）
  • 並行更新の順序逆転にはバージョン管理が必須になり、実装が重くなる
  • 複数のキーに影響する更新（一覧キャッシュなど）を全部 SET し直すのは非現実的。結局 DEL が混ざる

⑧ 実務での利用例 — 「一部のキーだけ Write Through」が現実解

ユースケース方式理由
ユーザーのセッションWrite Through（というより Redis が本体）そもそもDBに書かない。書けば即最新
自分のプロフィールWrite Through更新直後に必ず自分が見る。古いと「保存されてない」と誤解される
いいね数・閲覧数のカウンタWrite Through（Redis INCR）+ 非同期でDBへ厳密な値が不要。7章の Write Behind に近い
商品マスタ（管理画面から更新）Cache Aside（DEL）更新頻度が低く、直後に読まれるとも限らない。SETする価値が薄い
一覧・検索結果Write Through 不可1件の更新が影響する一覧キーを列挙できない。DEL かタグ無効化（10章）
口座残高Write Through かつ厳密にそもそも「読みはキャッシュ、書きはDBトランザクション」。キャッシュは表示専用と割り切る

⑨ Googleレベルではどう設計されるか

  • 「2ストア更新」を避ける設計に持っていく。 最も強い解は CDC（Change Data Capture）: アプリはDBだけ更新し、DBのログ（binlog / WAL）を購読する別プロセスがキャッシュを更新/削除する。アプリのコードから2ストア更新が消えるので、失敗パターンA/B/Cが構造的に発生しなくなる（10章で図解）
  • Facebook の memcache 論文（"Scaling Memcache at Facebook", NSDI 2013）の結論も同じ。 彼らは「更新時は SET せず DELETE する」を原則にし、さらに leases という仕組みで「古い値を書き戻す競合」を防いでいる（12章で再登場）
  • 整合性の要求を「データ種別ごとに」文書化する。 「セッションは strong、プロフィールは read-your-writes、一覧は eventual（最大60秒）」のように階層を定義し、それぞれに方式を割り当てる。全部を同じ方式にしない

⑩ 面接での問われ方

順序途中で落ちた場合評価

07 Write Behind（Write Back）

書き込みをキャッシュだけで完了させ、DBへの反映は非同期でまとめて行うパターン。書き込みが桁違いに速くなる代わりに、キャッシュが落ちるとデータが消える。使いどころが極端に限定される、諸刃の剣。

📮 宅配便の例え。 Write Through は「1個の荷物を1回ずつトラックで運ぶ」。Write Behind は「営業所にいったん預かって、集荷トラックが1時間に1回まとめて運ぶ」。
荷物を預けた時点で「受け付けました」と言われるので、あなたは速いと感じる。しかし営業所が火事になったら、まだ運ばれていない荷物は消える。この「消えてもいいか?」がこのパターンの採否を決める唯一の問い。

①② 何を解決するか / これがないと何が問題か

解決するのは「書き込みが多すぎてDBが持たない」という問題。特に以下の形。

  • 同じ行への高頻度更新: 動画の再生回数。1本の動画に秒間5,000回の UPDATE videos SET views = views + 1 が来ると、その1行のロック競合でDBが死ぬ（行ロックの直列化）
  • 書き込み量そのものが多い: ログ・イベント・既読フラグ・センサーデータ
  • 1件ずつ書くとオーバーヘッドが支配的: 1件INSERTのコストの大半はネットワーク往復とトランザクション開始/コミット。1000件まとめれば1件あたりのコストが1/100以下になる

図7-1 Write Behind のフローと write coalescing の効果。「同じ行への大量更新を1回に畳む」のが本質的な価値。

④ 内部処理 — Go 実装（カウンタのバッチフラッシュ）

// ===== 書き込み側: Redis だけで完結。0.6ms で返る ===== func (s *Service) IncrView(ctx context.Context, videoID int64) error { pipe := s.rdb.Pipeline() pipe.Incr(ctx, fmt.Sprintf("cnt:view:%d", videoID)) pipe.SAdd(ctx, "dirty:view", videoID) // ← 変更されたIDを記録（これが無いと全件走査になる） _, err := pipe.Exec(ctx) return err } // ===== フラッシャー: 30秒ごとに別 goroutine / 別Pod で走る ===== func (s *Service) Flush(ctx context.Context) error { // ① dirty集合から最大1000件を取り出す。SPOP は原子的なので複数Podで走っても重複しない ids, err := s.rdb.SPopN(ctx, "dirty:view", 1000).Result() if err != nil || len(ids) == 0 { return err } // ② 現在値をまとめて取得（MGET = 1往復） keys := make([]string, len(ids)) for i, id := range ids { keys[i] = "cnt:view:" + id } vals, err := s.rdb.MGet(ctx, keys...).Result() if err != nil { s.rdb.SAdd(ctx, "dirty:view", toAny(ids)...) // ← 失敗したら必ず戻す（でないと消失する） return err } // ③ 1本のバッチUPDATE。PostgreSQL なら VALUES リストで一括 // UPDATE videos v SET views = t.n FROM (VALUES (1,100),(2,250)) AS t(id,n) WHERE v.id = t.id if err := s.repo.BulkUpdateViews(ctx, pairs(ids, vals)); err != nil { s.rdb.SAdd(ctx, "dirty:view", toAny(ids)...) // ← ここも同様 return err } return nil }

実装で最も間違えるポイント: SPOP して DB 書き込みに失敗した時に dirty集合へ戻し忘れること。これをやると静かにデータが消える。「取り出したら、成功するまで責任を持つ」——キューの at-least-once 処理と全く同じ規律が要る。ここまで気を配るくらいなら、最初から Kafka / SQS を使うほうが早いことが多い。

⑥ メリット

  • 書き込みレイテンシが劇的に下がる（12ms → 0.6ms）
  • DBへの書き込み回数が桁違いに減る。write coalescing（同一行への複数更新を1回に畳む）が最大の効果
  • スパイクを吸収できる。バズって書き込みが10倍になっても、DBに届く量はほぼ一定
  • 同一行のロック競合が消える。これは回数削減より重要なことが多い

⑦ トレードオフ

  • データが消える可能性がある。これに尽きる
  • DBが Source of Truth でなくなる時間帯がある。DBを直接見る他システム（BI・バッチ・別チームのサービス）が古い値を見る
  • フラッシュ処理という新しい運用対象。止まっていても表向きは正常に見えるので、監視が難しい（dirty集合のサイズを必ず監視する）
  • 順序保証がない。「削除してから更新」がフラッシュ時に逆転しうる
  • デバッグが極めて困難。「DBの値が合わない」の調査が地獄

⑧ 実務での利用例

  • YouTube の再生回数: 「301回で止まる」の都市伝説の正体。正確なカウントのために非同期集計と不正検知を挟んでいる（28章）
  • Instagram / X の いいね数・表示回数: 表示は Redis の値、DBへは非同期
  • 既読フラグ・最終アクセス時刻: 1秒古くても誰も困らない典型
  • レートリミッタのカウンタ: そもそもDBに書かないこともある
  • ゲームのスコア・ランキング: Redis の Sorted Set がそのまま本体。定期的にDBへスナップショット
  • 使ってはいけない例: 決済・注文・在庫引当・ユーザー登録・投稿本文。「消えたら謝罪では済まないもの」は全部NG

⑨ Googleレベルではどう設計されるか

  • 「Write Behind」という名前ではなく、ストリーム処理として設計する。 クライアント → Kafka/PubSub → ストリーム集計（Flink / Beam / Dataflow）→ DB。耐久性はキューが保証し、集計はストリームエンジンが保証する。Redis を書き込みバッファにするのは、キューを持てない小規模構成での代替手段という位置づけ
  • 「正確な値」と「表示用の値」を分ける。 表示は Redis の概算値（速い・多少ズレる）、課金や分析に使う値はストリーム処理の結果（遅い・正確）。1つの数字を両方に使おうとするのが設計ミス
  • 近似データ構造を使う。 ユニークユーザー数なら HyperLogLog（Redis の PFADD / PFCOUNT）。12KBで誤差0.81%。正確な集合を持つよりメモリが数千分の1

⑩ 面接での問われ方

Q. 「YouTube の再生回数のように、秒間数万の更新が来るカウンタをどう設計しますか?」（頻出）

  1. まず問題を特定する: 「1行に更新が集中するので、DBの行ロックで直列化して詰まります。回数の問題ではなくロック競合の問題です」← ここを言えるかで差がつく
  2. Redis の INCR で受ける: 原子的で高速。同一キーへの集中は13章（Hot Key）の対策も併用
  3. 非同期でDBへ畳んで書く: dirty集合 + バッチUPDATE。「5,000回の +1」が「+150,000」1回になる
  4. 耐久性を明言する: 「フラッシュ間隔ぶんの損失を許容します。再生回数なので許容できます。課金に使う値なら Kafka を挟んで at-least-once にします」
  5. 読み取り: 表示は Redis の値をそのまま。DBの値は使わない（そちらが遅れているため）

08 Refresh Ahead（予測リフレッシュ）

TTLが切れる前に、先回りしてキャッシュを更新しておくパターン。ユーザーに MISS を一度も体験させないのが目的。12章の Stampede 対策と表裏一体。

🍽 レストランの例え。 人気メニューのソースを、なくなってから作り始めるとその間の注文が全部待たされる。だから残り2割になった時点で仕込みを始める。客は一度も待たない。
ただし「その日は誰も頼まなかった」場合、仕込んだソースは廃棄になる。これが Refresh Ahead のコスト。人気メニューにだけ使う技術。

図8-1 素朴なTTL vs Refresh Ahead。「古い値を返しながら裏で更新する」は層を超えて再利用できる最重要パターン。

④ 内部処理 — 2つの実装方式

方式いつ更新するか長所短所向くケース
A. リクエスト駆動
（stale-while-revalidate）		アクセスがあった時に「残り時間が閾値以下」なら裏で更新アクセスが無いキーは更新されない = 無駄がない。実装が単純アクセスが完全に途切れると物理TTLで消えるほぼ全ての場合。既定はこれ
B. スケジュール駆動
（事前計算 / warm）		cron / ワーカーが定期的に、アクセスと無関係に更新アクセスがゼロでも常に温かい。デプロイ直後も速い読まれないキーも更新するので無駄。対象リストの管理が必要トップページ・ランキング・ホーム画面など「必ず見られる少数のキー」
// 方式A: リクエスト駆動の Refresh Ahead（実務ではこれが基本） type entry[T any] struct { V T `json:"v"` Exp time.Time `json:"exp"` // 論理TTL } func (c *Cache[T]) Get(ctx context.Context, key string) (T, error) { var zero T b, err := c.rdb.Get(ctx, key).Bytes() if err != nil { return c.loadAndSet(ctx, key) // 物理TTL切れ = 本当のMISS。同期で取る } var e entry[T] if json.Unmarshal(b, &e) != nil { return c.loadAndSet(ctx, key) } if time.Now().Before(e.Exp) { return e.V, nil // まだ新鮮。そのまま返す } // ここが Refresh Ahead の核: 論理TTLは切れているが、値はある // → 「更新中」の印を SET NX で1本だけ立て、勝った1本だけが裏で更新する if ok, _ := c.rdb.SetNX(ctx, key+":refreshing", 1, 30*time.Second).Result(); ok { go func() { // ★ リクエストの ctx は使わない。呼び出し元が返ると同時にキャンセルされるため bg, cancel := context.WithTimeout(context.Background(), 10*time.Second) defer cancel() defer c.rdb.Del(bg, key+":refreshing") _, _ = c.loadAndSet(bg, key) }() } return e.V, nil // ← 古い値を即返す。ユーザーは待たされない }

実装の最頻バグ: go func() の中でリクエストの ctx をそのまま使うこと。HTTPハンドラが return した瞬間に ctx がキャンセルされ、更新が毎回失敗して永遠に古い値のままになる。しかもエラーはログにしか出ないので気づきにくい。必ず context.Background() から作り直す。

⑥ メリット

  • ユーザーがMISSを体験しない。p99レイテンシが安定する。これが最大の価値
  • Cache Stampede が構造的に起きない（TTL満了時に殺到する対象が存在しない）
  • DBが遅い/落ちている間も古い値でサービスが続く（graceful degradation）
  • TTLを短くしても実質的なDB負荷が増えない

⑦ トレードオフ

  • 誰も読まないキーを更新する無駄（方式Bで顕著）
  • 古い値を返すことを明示的に許容する必要がある。在庫や権限では使えない
  • 実装が複雑になる。論理TTL・更新中フラグ・バックグラウンドcontext の3点セット
  • 更新が失敗し続けても表面上は正常に見える。「refresh失敗回数」と「返した値の古さ（age）」を必ず監視する

⑧⑨ 実務例と Google レベル

  • Netflix: ホーム画面の各行（"あなたにおすすめ"）は事前計算してEVCacheに常駐させる。ユーザーがアプリを開いた時に計算していたら間に合わない → 方式B（28章）
  • Twitter(X): ホームタイムラインは投稿時に事前計算してキャッシュへ push（fan-out on write）。これも究極の Refresh Ahead（28章）
  • Fastly / CloudFront: stale-while-revalidate と stale-if-error をエッジで実装。後者は「オリジンが5xxを返したら古いキャッシュを返す」という、可用性のための機能（25章）
  • Googleの発想: 「Refresh Ahead は性能最適化ではなく可用性設計」。バックエンドが落ちても、古い値を返し続けられる時間だけサービスは生き延びる。stale-if-error の許容時間を長め（数時間）に設定しておくのは、障害時の最後の砦になる

⑩ 面接での問われ方

Q. 「TTL満了の瞬間にDBへのアクセスが集中します。どう防ぎますか?」

3つの答えを持っておく（重ねて使える）:

  1. TTLにジッターを入れる（満了時刻を分散させる。最も安い）
  2. singleflight / 分散ロック（同時MISSを1本に束ねる。12章）
  3. Refresh Ahead（そもそも MISS を発生させない。最も強いが実装コストが高い）

「Hotなキーには3、それ以外には1と2」と使い分けを示せると、実務感覚があると評価される。

10 Cache Invalidation — 難しいのはここ

Phil Karlton の有名な言葉「コンピュータサイエンスで難しいことは2つ。キャッシュの無効化と、名前付け」。この章はその1つ目。「いつ・何を・どうやって消すか」の3つが全部難しい。

🏛 図書館の例え。 書庫の本が改訂されたとき、机の上の旧版を回収したい。だが問題は3つ。
① いつ回収する? 改訂の瞬間に気づけるか（更新の検知）
② 何を回収する? その本のコピーは、あなたの机だけでなく隣の部屋の机にも、分館にも、来館者のカバンの中にもある（キーの列挙）

⑨ Googleレベル / Facebook の "leases"

Facebook の memcache 論文で導入された仕組み。レース①（古い値の書き戻し）と Stampede を同時に解く、非常に美しい設計。

  1. MISS したクライアントに、キャッシュが「lease token（64bitの数字）」を1つだけ発行する
  2. クライアントはDBから読んだ値を、token を添えて書き戻す
  3. DEL が発生すると、そのキーの token は無効化される
  4. 無効な token を持った書き戻しは拒否される → 古い値が復活しない
  5. さらに、token を持っていない2本目以降のクライアントは「少し待って再試行してね」と言われる → Stampede も防げる

Redis には lease 機能は無いが、6章のバージョン付きSET（CAS）+ 12章の SETNX ロックを組み合わせると、ほぼ同じ効果が得られる。面接でこの名前を出せると強い: 「Facebook の memcache 論文の leases と同じ発想で、CAS とロックを組み合わせます」。

12 Cache Stampede / Breakdown

1本のキーが消えた瞬間に、そのキーを待っていた数千のリクエストが一斉にDBへなだれ込む現象。別名 thundering herd / dog-piling。中国語圏では「缓存击穿（Cache Breakdown）」と呼ばれる。キャッシュ障害で最も頻繁に起きる。

🍽 レストランの例え。 人気の日替わりランチが売り切れた瞬間、厨房に20人分の注文が同時に飛ぶ。厨房は1人分ずつしか作れないので全員が待たされ、しかも同じ料理を20回作る。
正しいのは「最初の1人の注文だけ厨房に通し、残り19人はその1皿ができるのを待って分ける」。これが singleflight。

13 Hot Key

特定の1キーにアクセスが集中し、そのキーを持つ Redis ノード1台だけが飽和する問題。クラスタを組んでいても1つのキーは1つのシャードにしか無いので、シャードを増やしても解決しない。

🏦 銀行の例え。 窓口を10個に増やしても、「山田さんの口座」を扱えるのが3番窓口だけなら、山田さんに用がある客は全員3番に並ぶ。他の9窓口は暇なのに3番だけパンクする。
解決策は2つ。①山田さんの口座情報のコピーを10窓口すべてに配る（＝キーの複製）②各窓口に山田さんのメモを持たせる（＝ローカルキャッシュ）。窓口を増やす（＝シャード追加）のは無意味。

図13-1 Hot Key の構造と3対策。「シャードを増やす」が効かないことの理解が出発点。

④ 実装 — L1 + L2 の2層キャッシュ（対策A）

// Hot Key 対策の本命。Pod内メモリ(L1) → Redis(L2) → DB の3段 import "github.com/dgraph-io/ristretto" type TwoTier struct { l1 *ristretto.Cache // プロセス内。TinyLFU ベース（17章） rdb *redis.Client sf singleflight.Group } func (c *TwoTier) Get(ctx context.Context, key string) ([]byte, error) { // ① L1: ネットワークすら発生しない（~100ns） if v, ok := c.l1.Get(key); ok { metrics.L1Hit(); return v.([]byte), nil } // ② L2: Redis。ここも singleflight で束ねる v, err, _ := c.sf.Do(key, func() (any, error) { if b, err := c.rdb.Get(ctx, key).Bytes(); err == nil { c.l1.SetWithTTL(key, b, int64(len(b)), 3*time.Second) // L1は短命に return b, nil } // ③ DB b, err := c.loadFromDB(ctx, key) if err != nil { return nil, err } c.rdb.Set(ctx, key, b, jitter(5*time.Minute)) c.l1.SetWithTTL(key, b, int64(len(b)), 3*time.Second) return b, nil }) if err != nil { return nil, err } return v.([]byte), nil }

L1 の TTL は「許容できる不整合の秒数」そのもの。 3秒なら「最大3秒、Podごとに違う値が見える」。ここを 60秒にすると Redis の負荷はさらに減るが、「更新したのに一部のユーザーだけ古い」という現象が1分続く。迷ったら短く（1〜5秒）。それでも Hot Key 対策としては十分すぎる効果がある（150,000 → 13 QPS）。

より厳密にしたい場合は Redis Pub/Sub で無効化をブロードキャストして L1 を消す（23章）。ただし「全Podに届く保証が無い」ので、TTLとの併用は必須。

⑧⑨ 実務例と Google レベル

  • X（Twitter）の有名人ツイート: 1つのツイートに数百万アクセス。エッジ + アプリ内キャッシュで吸収（28章）
  • ECのタイムセール: 開始の瞬間に1商品へ全流量。開始前にL1へwarm upしておくのが定石
  • 設定・フィーチャーフラグ: 全リクエストが読むので構造的にHot。そもそもRedisに置かず、起動時ロード + Pub/Subで更新通知が正解
  • Google の考え方: Hot Key は「バグではなく人気の証」。だから自動で検知して自動で複製する層を作る。Slicer（Googleの負荷分散システム）は、キーの負荷を観測して動的にシャードを分割・再配置する。「人間がHotキーを特定して手で対処する」のは規模が小さいうちだけという前提に立つ

14 Cache Avalanche（雪崩）

大量のキーが同時に消え、全流量がDBへなだれ込む障害。Stampede が「1本のキー」の問題なのに対し、Avalanche は「キャッシュ全体」の問題。サービス全断につながる、最も被害が大きいパターン。

🛣 高速道路の例え。 全ての車が高速道路（キャッシュ）を使って快適に走っている。ある瞬間に高速が全面通行止めになると、全車が一斉に一般道（DB）へ降りる。一般道は高速の1/100の容量しかないので、即座に大渋滞。
さらに悪いことに、渋滞で遅くなった車がイライラして何度も経路を変える（リトライ）ので、事態が加速度的に悪化する。

Q. 「Redisが全部落ちたらどうなりますか?」

この質問はキャッシュ設計の理解度を測る最も有効な質問として広く使われている。答えの構成:

  1. まず数字で答える: 「ヒット率99%なので、DBへの流量は100 QPS から 10,000 QPS になります。DBの限界は1,500 QPS なので6.7倍のオーバー、つまり落ちます」
  2. だから設計で守る: L1で吸収 → DBへの同時実行数を制限 → 溢れは劣化応答 → サーキットブレーカ
  3. 「守る対象はDB」だと明言する: 「全リクエストを成功させることは諦めます。DBを生かして部分的にサービスを続けるほうが、全部を巻き込んで死ぬより良いので」
  4. 復旧時の二次災害に言及する: 「復旧後も冷たいキャッシュで再度殺到するので、段階的に流量を戻します」
  5. そもそも落ちにくくする: Multi-AZ・レプリカ昇格・Cluster（21〜22章）

Q. 「Stampede と Avalanche の違いは?」 — 「Stampede は1本のキーに対する同時MISS（垂直方向）、Avalanche は大量のキーが同時に消える（水平方向）。対策も違い、前者は singleflight、後者は TTLジッターと流量制限」と即答できるようにしておく。

15 Cache Penetration（貫通）

存在しないデータへのアクセスは、キャッシュを素通りして毎回DBに届く。キャッシュは「あるもの」しか覚えないから。攻撃者に悪用されると、キャッシュがあっても無意味にDBを殴れる。

🏛 図書館の例え。 「存在しない本」を毎回リクエストされると、司書は毎回書庫まで探しに行き、毎回「ありません」と戻ってくる。机には何も置かれない（無いものは置けない）。
だから次も、その次も探しに行く。解決策は「その本はありません」という札を机に置くこと。「無い」という事実もキャッシュする。

④ 実装 — 空値キャッシュの正しい書き方

const nullSentinel = "\x00__NULL__" // 通常の値と絶対に衝突しない文字列にする func (s *Service) GetProduct(ctx context.Context, id int64) (*Product, error) { // ★ まず入力を検証する。これだけで攻撃の大半は止まる if id <= 0 || id > maxKnownID { return nil, ErrNotFound } key := fmt.Sprintf("app:v3:product:%d", id) switch b, err := s.rdb.Get(ctx, key).Result(); { case err == nil && b == nullSentinel: return nil, ErrNotFound // ← 「無い」がHITした。DBに行かない case err == nil: var p Product if json.Unmarshal([]byte(b), &p) == nil { return &p, nil } } p, err := s.repo.Find(ctx, id) if errors.Is(err, sql.ErrNoRows) { // 「無い」を短命でキャッシュする。長くすると、後から作られた時に見えない s.rdb.Set(ctx, key, nullSentinel, 60*time.Second) return nil, ErrNotFound } if err != nil { return nil, err } b, _ := json.Marshal(p) s.rdb.Set(ctx, key, b, jitter(5*time.Minute)) return p, nil } // ★ 作成時に必ず空値キャッシュを消す。これを忘れると「作ったのに404」が60秒続く func (s *Service) CreateProduct(ctx context.Context, p *Product) error { if err := s.repo.Insert(ctx, p); err != nil { return err } s.rdb.Del(ctx, fmt.Sprintf("app:v3:product:%d", p.ID)) // ← 見落としやすい return nil }

最頻バグ: 空値と「値が JSON の null」を区別できないコード。json.Unmarshal("null") はエラーにならないので、「存在しない」と「値がnull」が混ざって静かに壊れる。だからセンチネルは JSONとして絶対にパースできない文字列（先頭に \x00 を入れるなど）にする。

⑩ 面接での問われ方

17 追い出しアルゴリズム — LRU / LFU / TinyLFU

メモリが満杯になったとき、どのキーを捨てるか。TTL切れ（鮮度）とは別の、容量の問題。選択を誤るとヒット率が数十%変わる。

🏛 図書館の例え。 机に10冊しか置けない。11冊目を置くには1冊を書庫へ戻さないといけない。どれを戻すか?
LRU: 一番長く触っていない本を戻す（「最近使っていない＝もう使わないだろう」）
LFU: 一番参照回数が少ない本を戻す（「めったに使わない＝もう使わないだろう」）

18 Distributed Cache と Consistent Hashing

1台のメモリに収まらなくなったら、複数台に分ける。問題は「どのキーをどのノードに置くか」。素朴な hash % N はノードを1台増やすだけでほぼ全キーが移動する。

🚚 物流倉庫の例え。 商品を「商品番号 ÷ 倉庫数の余り」で振り分けている。倉庫が3→4に増えると、ほぼ全ての商品の配置先が変わるので、全在庫を運び直すことになる。
Consistent Hashing は「円形の地図の上に倉庫と商品を配置し、商品は時計回りで最初に出会った倉庫に入れる」方式。倉庫を1つ足しても、移動するのはその倉庫の担当区間だけ。

20 Redis Persistence — RDB と AOF

「キャッシュなのに永続化が必要?」という疑問がまず来る。答えは「速く復旧するため」。空のキャッシュで起動すると14章の二次災害が起きるので、永続化は耐久性の話ではなく可用性の話として理解する。

🏦 銀行の例え。 RDB は「毎日夜に金庫の中身を全部写真に撮る」方式。復元は写真を見るだけで速いが、写真を撮ってから停電までの取引は失われる。
AOF は「取引を1件ずつ台帳に書き足す」方式。ほぼ何も失わないが、復元は台帳を最初から全部読み直すので遅い。
実務では両方やる。台帳で直近を守り、写真で高速復元する。

21 Redis Sentinel — 自動フェイルオーバー

プライマリが落ちた時に、レプリカを自動で昇格させる監視システム。シャーディングはしない（データは全ノードで同じ）。Cluster を使わない中規模構成の標準解。

🏦 銀行の例え。 Sentinel は「支店長が倒れていないか見張る監査役が3人いる」状態。1人が「倒れてる!」と言っても動かない（誤報かもしれない）。過半数（2人以上）が同意したら、副支店長を支店長に昇格させる。
監査役が2人だと、片方がネットワーク的に孤立した時に「過半数」が成立せず動けない。だから3人以上の奇数にする。

図21-1 Sentinelの構成とフェイルオーバー。「15秒書き込めない」「非同期なので少し失う」の2点を設計に織り込む。

22 Redis Cluster — 水平分割

データを複数ノードに分割して、メモリ容量とスループットを水平にスケールさせる仕組み。16384個の hash slot という固定分割を使う（Consistent Hashing ではない）。

🚚 物流倉庫の例え。 商品を16384個の「棚番号」に割り当て、棚番号の範囲ごとに倉庫を担当させる。倉庫を増やす時は「棚番号 0〜1000 をこの新倉庫に移す」と決めて、その棚の商品だけ運ぶ。
棚番号は絶対に変わらないので、倉庫の増減が「棚の担当替え」に還元される。これが Consistent Hashing との違い（円周上の位置を計算しなおす必要がない）。

23 Redis Pub/Sub — ローカルキャッシュの無効化

Pub/Sub の最も実用的な使い道は「メッセージング」ではなく、「全Podのプロセス内キャッシュ（L1）を一斉に消す」こと。13章のHot Key対策で作ったL1の、唯一の無効化手段。

📮 館内放送の例え。 各職員が手元に名簿のコピーを持っている（L1）。名簿が更新されたら「◯◯さんのページは破棄してください」と館内放送する。
ただし館内放送は「その瞬間に館内にいた人にしか届かない」。トイレに行っていた人・後から出勤した人には届かない。だから放送に頼りきらず、コピーには短い有効期限も付ける。これがPub/SubとTTLを併用する理由。

24 Browser Cache

最も速く（0ms）、最も消せないキャッシュ。HTTPヘッダで制御するという点で、バックエンドエンジニアも必ず理解しておく必要がある。「HTMLは短命、アセットは不変」が全ての基本。

📮 郵便の例え。 max-age は「この手紙は◯日間有効」という賞味期限。期限内は郵便局に問い合わせず、手元の手紙を読む。
ETag は「この手紙の版番号」。期限が切れたら郵便局に「版番号 abc の手紙、まだ最新?」と聞く。最新なら「はい」（304）だけ返ってくるので、手紙の中身を再送してもらわなくて済む。封筒代（帯域）が節約できる。

図24-1 ブラウザキャッシュの判断フロー。「304」と「通信ゼロ」は別物。

ディレクティブ意味使う場面
max-age=NN秒間は再検証せず使うすべての基本。これが無いとブラウザが独自ヒューリスティックで判断する（危険）
s-maxage=NCDN等の共有キャッシュ専用の max-age「ブラウザは60秒、CDNは1時間」のように層ごとに違うTTLを設定できる。実務で非常に有用
public共有キャッシュ（CDN）に保存してよい誰に見せても同じ内容のもの
privateブラウザだけ。CDNには保存させないログインユーザー向けのHTML/APIには必須。これを忘れてpublicにすると他人の個人情報がCDNから配信される（31章の実例）
no-cache保存はするが、使う前に必ず再検証する「no-store」と混同されやすい。キャッシュしないわけではない
no-store一切保存しない決済情報・個人情報を含むレスポンス。これが本当の「キャッシュ禁止」
immutable期限内はリロードしても再検証しないハッシュ付きアセット。これがないと Cmd+R で全部304の往復が発生する
stale-while-revalidate=N期限切れ後N秒は古い値を返し、裏で更新APIのGET。8章 Refresh Ahead と同じ効果をブラウザ/CDNで得る
stale-if-error=Nオリジンがエラーの時、N秒は古い値を返す可用性のための切り札。オリジン障害時にサイトが生き残る
must-revalidate期限切れ後は必ず再検証（staleを使わない）金額表示など、古い値を出してはいけないもの
Vary: Accept-Encoding, Accept-Language指定ヘッダごとに別キャッシュを持つVary: Cookie は事実上キャッシュ無効化（Cookieは全員違う）。Vary: User-Agent も同様に危険（無数のUAがある）

質問答え
「no-cache と no-store の違いは?」no-cache は「保存するが使う前に必ず確認する」、no-store は「保存しない」。 名前が紛らわしいが逆の意味に近い。「キャッシュを無効にしたい」なら no-store
「max-age=0 と no-cache の違いは?」実質ほぼ同じ（どちらも毎回再検証する）。厳密には no-cache のほうが強く、stale の使用を明示的に禁じる
「JSファイルの更新が反映されません」「ハッシュ付きファイル名にして immutable にします。HTMLは no-cache にして、新しいファイル名を必ず伝えられるようにします」= 11章と同じ答え
「ETag はどう生成しますか?」「コンテンツのハッシュ（strong ETag）か、更新時刻+サイズ（weak ETag）。複数サーバで違うETagを返すと毎回200になるので、内容から決定的に生成する必要があります」

25 CDN Cache

世界中に分散したキャッシュサーバ（PoP）で、「光の速さ」という物理法則に対処する。Redisでは絶対に解決できない問題を解く唯一の層。

🚚 物流倉庫の例え。 中央倉庫（オリジン）が東京にあり、注文が世界中から来る。ブラジルからの注文に東京から発送すると1週間かかる。
だから各地域に地域倉庫（PoP）を置き、よく売れる商品を前もって配っておく。ブラジルの客はサンパウロ倉庫から翌日受け取れる。
新商品は最初の1件だけ東京から取り寄せる（初回MISS）。そして全世界の倉庫が同時に東京へ注文すると中央倉庫が潰れるので、地域統括倉庫（Origin Shield）を1段挟む。

両方「キャッシュ」だが、解いている問題が根本的に違う。CDN は距離（物理）を、Redis は計算コストを解く。どちらかで代替できるものではない。

⑩ 面接での問われ方

Q. 「CDNがあるのに、なぜRedisも必要なのですか?」

満点の答え: 「解いている問題が違います。CDNは『距離』を解きます——東京とサンパウロの往復185msは物理法則なので、データを近くに置く以外の手段がありません。Redisは『計算コスト』を解きます——800msかかる集計クエリを0.5msにするのは、距離の問題ではありません。

またCDNはユーザー別データが苦手です。Cookieでキャッシュを分けるとキーが人数分になってヒット率がゼロになるので。逆にRedisは地理的分散が苦手です。

だから『全員に同じものを返す静的・準静的コンテンツはCDN、ユーザーごとに違うデータや重い計算結果はRedis』と切り分けて、両方を層として重ねます。」

Q. 「APIレスポンスをCDNに載せられますか?」 — 「認証不要で全員同じ結果のGETなら載せられます。public, s-maxage=300, stale-while-revalidate を付けて、クエリパラメータを正規化します。認証付きのAPIは private / no-store にして絶対にCDNに載せません——他人のデータが配信される事故になるので。」

29 理解度チェック

クリックすると答えが開きます。答えを見る前に、自分の言葉で30秒説明できるかを試してください。言葉にできないものは、まだ理解していません。

Q1 キャッシュを入れると必ず速くなる? 遅くなるケースはある?
遅くなるケースは3つある。①MISS時: キャッシュを見る時間が上乗せされるので、必ず少し遅い（1章③の式）。②ヒット率が低い場合: MISSばかりなら、オーバーヘッドだけ増える。検索クエリをそのままキーにするとこうなる。③値が巨大な場合: 1MBのJSONをRedisから取ってデシリアライズするより、indexの効いたDBクエリのほうが速いことがある。

「キャッシュが有効な3条件」を思い出す: 取得コストが本質的に高い / 同じ結果が繰り返し要求される / 多少古くても許される。
Q2 ヒット率 90% と 99% では、DBの負荷は何倍違う?
10倍。 見るべきは「ヒット率の差（9ポイント）」ではなくミス率の比（10% ÷ 1% = 10倍）。

ヒット率は線形に効かない。95%→99% は「4%の改善」ではなく「バックエンド負荷が1/5」。逆に 99%→95% は「わずかな悪化」ではなく「DB負荷が5倍になる障害」。ダッシュボードでは常に 1 - H を見る癖をつける（2章）。
Q3 更新時、キャッシュは「削除」と「更新」のどちらが正しい? なぜ?
原則は削除（DEL）。 理由は3つ。①並行更新に強い: 2つの更新が交錯した時、SETだと「遅れて到着した古い値」が固定化するが、DELなら結果は必ず「空」になり、次の読みで正しい値が載る。②DELは冪等: 何度実行しても壊れない（CDCのat-least-onceと相性が良い）。③読まれないデータを温めない。

例外: 超Hotなキーは、DELすると全員が同時にMISSして殺到する（Cache Breakdown）。この場合はバージョン付きCASでSETする（6章）。
Q4 DB更新とキャッシュ削除、どちらを先にする? 完全に安全か?
DB更新が先。 逆（DEL→DB更新）だと、その隙間に読まれて古い値が載り直す。

ただしDB→DELでも完全ではない。「MISSしてDBを読んだリクエスト」が遅延し、その後にDB更新+DELが走り、最後にその遅延したリクエストがSETすると、古い値が載る（10章 図10-1）。

完全な解は存在しない。 だから ①TTLで古さの上限を保証し ②バージョン付きCASで確率を下げ ③重要ならCDCで経路を一本化する。面接では「防げます」と断言せず、この3層で管理すると答える。
Q5 Cache Stampede と Cache Avalanche の違いを1文で。
Stampede は「1本のキーへの同時MISS」（垂直）、Avalanche は「大量のキーが同時に消える」（水平）。

対策も違う: Stampede は singleflight / 論理TTL、Avalanche は TTLジッター / 流量制限 / L1 / Multi-AZ。

ついでに Hot Key（1キーへのアクセス集中 → Redisが死ぬ）と Penetration（存在しないデータ → 素通り）も区別する。Hot Key だけが「Redisが死ぬ」、他3つは「DBが死ぬ」のが覚え方（16章）。
Q6 Redisが全部落ちたら何が起きる? 具体的な数字で答えて。
「ヒット率99%・全体10,000 QPS」なら、DBへの流量が 100 QPS → 10,000 QPS（100倍）になる。DBの限界が1,500 QPSなら6.7倍のオーバーで落ちる。

だから4段の防御を設計する: ①L1で吸収 ②DBへの同時実行数をセマフォで制限 ③溢れは劣化応答（古い値/簡易版/503）④サーキットブレーカ。

さらに重要: Redisが復旧しても中身は空なので、全MISSで再びDBが死ぬ（二次災害）。復旧時は流量を段階的に戻す。Multi-AZでレプリカ昇格させれば、そもそも冷たくならない（14章）。
Q7 1つのキーに秒間15万アクセス。シャードを増やせば解決する?
解決しない。 Redis Cluster では slot = CRC16(key) mod 16384 なので、1つのキーは必ず1つのシャード（=1コア）にしか存在しない。シャードを8個にしても、そのキーの負荷は1台に集中し続ける。

正しい対策は3つ: ①アプリ内L1キャッシュ（TTL 1〜3秒）——40Pod × 3秒なら Redis へは13 QPS。4桁の削減。②キー複製（key#0〜#9）——鮮度が要る場合。③レプリカへの読み分散——3〜5倍にしかならないので補助（13章）。
Q8 存在しないIDを1秒に1万件叩かれたら?
Cache Penetration。 キャッシュは「あるもの」しか覚えないので、毎回MISSしてDBに届く。ヒット率が実質0%になり、キャッシュがあっても無いのと同じ。

対策を段階で: ①入力バリデーション（id≤0、範囲外は即400）——コストゼロで最大の効果 ②空値キャッシュ（TTL 60秒）——3行で実装できる ③Bloom Filter——ランダムIDで空値がメモリを圧迫する場合 ④レートリミット。

実装の注意: センチネルはJSONとしてパースできない文字列にする（「存在しない」と「値がnull」を区別するため）。作成時に必ずDELする（15章）。
Q9 プロフィール画像を更新したのに古い画像が表示される。CDNをpurgeすれば直る?
直らない。 ブラウザキャッシュには purge が効かない（世界中の端末にコピーがあり、運営から手が届かない）。

正解は「消す設計をやめて、URLを変える設計にする」。画像を上書きせず、内容のハッシュをパスに含めて新しいオブジェクトとして保存する（/avatars/42/a3f9c1d8.jpg）。ヘッダは public, max-age=31536000, immutable。

これで無効化が必要なのは「そのURLを含むAPIレスポンスのキャッシュ（Redis）」だけになり、DEL一発で済む。難しい層（ブラウザ・CDN）から問題を追い出して、簡単な層（Redis）に閉じ込めたのがこの設計の本質（11章）。
Q10 no-cache と no-store の違いは?
no-cache =「保存はするが、使う前に必ずサーバへ確認する」。no-store =「一切保存しない」。 名前から受ける印象が逆なので注意。

「キャッシュを無効にしたい」なら no-store。no-cache は ETag と組み合わせて304 Not Modified で帯域を節約する用途（HTMLに使うのが典型）。

関連して private の忘れは重大事故につながる: 認証付きAPIに public を付けるとCDNが他人の個人情報を配信する（24章 / 31章）。
Q11 Redis の maxmemory-policy を設定しないとどうなる?
既定は noeviction。メモリが満杯になると追い出さずに書き込みをエラーにする（OOM command not allowed）。キャッシュとして使っている場合、突然「SETが全部失敗する」障害になる。読みはできるので気づきにくい。

キャッシュ用途なら allkeys-lru（既定の選択）または allkeys-lfu（アクセス偏りが強く、夜間バッチのスキャンがある場合）。

また maxmemory はインスタンスメモリの60〜75%にする。RDB保存時の fork によるCopy-on-Writeで一時的にメモリが増えるため（17章 / 20章）。
Q12 LRU と LFU、どちらが優れている?
一概には言えない。壊れ方が正反対。

LRUは「最近性」だけを見るので、夜間バッチが全件スキャンすると人気データが全部追い出される（scan pollution）。
LFUは「頻度」だけを見るので、去年バズった記事が永遠に居座り、新着が入れない（cache pollution）。

実務の答えは減衰付きLFU（Redis の allkeys-lfu）またはW-TinyLFU（ristretto / Caffeine）。後者は「入場審査」で一度きりのスキャンを弾き、Sketchの減衰で古い人気を忘れる（17章）。
Q13 hash % N でシャーディングしてはいけない理由は?
ノードを N→N+1 にすると、約 1-1/N（3台なら75%）のキーが別ノードに移動する。移動したキーは全部MISSになり、増設した瞬間にヒット率が25%まで落ちて全MISSがDBへ流れる（＝Avalanche）。

Consistent Hashing なら移動は約 1/N のみ。さらに仮想ノード（1物理ノードを円上の150〜200箇所に配置）で①担当量の偏りを±5%以内にし ②1台落ちた時の負荷が「隣1台」ではなく残り全台に分散する（障害の連鎖を防ぐ）。後者が実は最大の利点（18章）。
Q14 なぜキャッシュに永続化（RDB/AOF）が必要?
データを守るためではなく、復旧時に「温かい状態」で起動するため。 空のキャッシュで起動すると全リクエストがMISSしてDBが死ぬ（14章の二次災害）。

つまり永続化は耐久性の話ではなく可用性の話。

ただし永続化にはコストがある（fork時のレイテンシスパイク・CoWでメモリ2倍・fsyncのIO）。だから実務ではプライマリでは永続化を切り、レプリカ側でRDBを取る。Multi-AZでレプリカ昇格させる構成なら、レプリカはデータを持っているのでそもそも冷たくならない（20章）。
Q15 Redis Pub/Sub でキャッシュ無効化を通知すれば、L1キャッシュの整合性は保証される?
保証されない。 Pub/Sub は at-most-once（fire-and-forget）で、購読していない間の配信は永久に失われる。Podの再起動中・ネットワークの瞬断中・Redisのフェイルオーバー中の通知は届かない。

正しい設計は「Pub/Sub は最適化、TTL は保証」の二重化。L1のTTLを3〜5秒にした上でPub/Subを足す。通常は即座に無効化され、漏れた時でも最大5秒で回復する。

確実性が必要なら Redis Streams（永続化される）か Kafka を使う（23章）。
Q16 CDNがあるのに Redis も必要な理由は?
解いている問題が違う。

CDN は「距離」を解く: 東京⇄サンパウロの往復185msは光の速さによる物理的下限で、サーバをどれだけ速くしても消えない。データを近くに置く以外の手段がない。
Redis は「計算コスト」を解く: 800msかかる集計クエリを0.5msにする。これは距離の問題ではない。

加えてCDNはユーザー別データが苦手（Cookieで分けるとキーが人数分になりヒット率0%）、Redisは地理的分散が苦手。だから両方を層として重ねる（26章）。
Q17 在庫（残り2室）はキャッシュしていい?
「表示」はしてよい。「引当の判断」はしてはいけない。

基準は「読んだ値で世界を変えるか」。
・「残り2室」の表示 → キャッシュ可（多少古くても、次の画面で正しくなればよい）
・在庫を -1 する判断 → 必ずDBのトランザクション（SELECT ... FOR UPDATE または楽観ロック）

予約時に「満室になりました」と出るのはバグではなく仕様。UIで正直に扱う。同じ原則が、クーポン利用可否・権限チェック・決済金額にも当てはまる（28章）。
Q18 キャッシュを全部消したい。FLUSHALL してよい?
絶対にダメ。 全キーが消えて全流量がDBへ行く（Avalanche）。しかも復旧に時間がかかる。

正解はキーのバージョンprefixを上げる: app:v3:... → app:v4:...。
・新しいキーは徐々に温まる（段階的にDBへ流れるので急激なスパイクにならない）
・古いキーはTTLで自然消滅する
・ロールバックも簡単（v3に戻せば元のキャッシュがまだ生きている）

これはスキーマ変更時（JSONの構造が変わった時）にも使える。だからキーには最初からバージョンを入れておく（3章 / 10章）。

  • Redis層: short_code → long_url のマップ。データが小さく（100バイト程度）不変なのでヒット率99.9%が狙える理想的なキャッシュ対象。TTL長め（1日）
  • Write Through: 作成時にRedisへも書く（作成直後にアクセスされるので）
  • 不変性の活用: 短縮URLは基本的に変更されないので、無効化の心配がほぼない。「TTLは長く、無効化は考えない」でよい

Q2 Twitterのタイムラインを設計してください。

Q3 ECサイトの商品ページが遅いです。どう改善しますか?

  1. 計測する: 「どこが遅いか分解します。TTFB / DB / 外部API / レンダリング」
  2. キャッシュ以外の可能性を先に潰す: N+1クエリ / index不足 / 不要なJOIN / 過剰なデータ取得。これらが原因ならキャッシュは問題を隠して悪化させます
  3. それでも本質的に重いなら、要素ごとに分ける:
    • 画像・JS/CSS → CDN + immutable
    • 商品基本情報 → Redis（TTL 5分 + 更新時DEL）
    • 「この商品を見た人はこれも」→ 事前計算してRedisに常駐（TTL 1時間）
    • 在庫表示 → TTL 5秒。引当はDB
    • 価格 → キャッシュしてよいが、カート投入時と決済時に必ずDBで再検証
    • レビュー一覧 → TTL 10分。ページネーションはキーに含める
  4. セール開始に備える: 人気商品はL1キャッシュ + 事前warm up（13章 / 8章）

この問題の評価軸は「キャッシュを知っているか」ではなく「キャッシュを使わない判断ができるか」。

リクエストごとに要素が増えるのでメモリを食う
トークンバケットHash に tokens と last_refill。Luaで原子的に補充+消費バースト許容を制御できる。実務の本命

加点ポイント: ①必ずLuaで原子的に（GET→判定→SET を分けると競合で通り抜ける）②Cluster ではキーに {user_id} のハッシュタグを付ける ③Redisが落ちた時にどうするか——「fail open（全部通す）」か「fail closed（全部拒否）」を明示する。DDoS対策ならfail closed、UX優先ならfail open。この判断を聞かれることが多い ④分散環境では「ローカルで粗く数えて、定期的にRedisと同期」する近似方式もある（精度を落として性能を取る）

Q5 ニュースフィードのランキングを1分ごとに更新したい。どう設計しますか?
  1. 計算はリクエストパスから外す: バッチ/ストリームワーカーが1分ごとに計算し、結果をRedisへ書く。リクエスト時は「読むだけ」（8章 方式B = スケジュール駆動のRefresh Ahead）
  2. Sorted Set を使う: ZADD ranking:tokyo score member → ZREVRANGE 0 49 で上位50件が O(log n + 50)
  3. 切り替えは原子的に: 新しいランキングを別キー（ranking:tokyo:v{n+1}）に作り、完成したらポインタキーを1回 SET して切り替える。ZADDで既存キーを更新すると、途中の中途半端な状態が読まれる
  4. TTLは物理的な保険として長めに（10分）。ワーカーが止まっても即座に空にならない
  5. 監視: 「ランキングの最終更新時刻」をキーに含めて記録し、5分以上更新されていなければアラート。ワーカーが静かに止まる事故が最も多い

加点: 「パーソナライズが入る場合は、共通のランキング（キャッシュ可）とユーザー別の重み付け（リクエスト時に軽く計算）に分けます。全ユーザーぶんのパーソナライズ結果をキャッシュするのは、キー数が爆発して現実的ではありません」

Q6 セッション管理を設計してください。Redisが落ちたら全員ログアウトしますか?

まず方式を2つ提示する:

サーバサイドセッション（Redis）JWT（ステートレス）
Redis障害時全員ログアウト影響なし
即時失効DELで即座できない（有効期限まで生きる）
権限変更の反映即座トークン再発行まで反映されない
スケールRedisがボトルネックになりうる検証はローカルで完結

実務の答えはハイブリッド: 短命なアクセストークン（JWT、5〜15分）+ 長命なリフレッシュトークン（Redisで管理）。「即時失効」はリフレッシュトークンをDELすることで実現し、最大でアクセストークンの寿命だけ遅延する。

Redis障害への備え: ①MemoryDBを使う（複数AZへ同期複製、データ損失なし）②Multi-AZ + 自動フェイルオーバー ③AOF everysec。ただし「非同期レプリケーションなのでフェイルオーバー時に数十msぶん失う=一部ユーザーが再ログイン」ことを許容範囲として明示するのが誠実な設計。

Q7 「いいね」ボタンを設計してください。秒間10万クリックに耐えられますか?
  1. 問題を特定する: 「同じ投稿への UPDATE posts SET likes = likes + 1 が集中すると、行ロックで直列化してDBが詰まります。回数ではなくロック競合の問題です」
  2. カウントは Redis INCR: 原子的で高速。表示もRedisの値をそのまま使う（DBの値は使わない——遅れているため）
  3. 「誰が押したか」は別管理: 冪等性のため必要。SADD likes:post:{id} {user_id} で重複を防ぐ。ただし人気投稿でSetが巨大化するので、Bitmap（user_idをオフセットに）や「自分が押したかだけ分かればよい」なら liked:{user}:{post} の個別キーにする
  4. DBへは Write Behind: dirty集合 + 30秒ごとのバッチUPDATE。5,000回の+1が「+150,000」1回に畳まれる（write coalescing）
  5. Hot Key対策: 特定の投稿に集中するので、読みはL1キャッシュ（TTL 1秒）。書きは INCR なのでL1で吸収できない → キー複製（cnt:post:{id}#0〜#9 にランダムINCRし、読み時に合計する）
  6. 耐久性を明言: 「フラッシュ間隔ぶんの損失を許容します。いいね数なので許容できます」

5番のキー複製まで言えると、Hot Keyの「書き込み側」も理解していると評価される。

Q8 全世界にサービスを展開します。キャッシュはどう配置しますか?
  1. まずデータを分類する:
    • 全世界で同じ・不変（画像・JS・公開記事）→ CDN。これが最も効く
    • 地域ごとに違う（現地の商品・価格・言語）→ 各リージョンにRedisを置き、キーに地域を含める
    • ユーザー固有（セッション・カート）→ ユーザーを地域にピン留めする（データレジデンシー要件とも合致）
    • グローバルで整合が必要（在庫・残高）→ キャッシュしない。単一リージョンのDBで処理する
  2. クロスリージョンのキャッシュ同期はしない: 「東京とバージニアのRedisを同期させる」設計は、レイテンシと整合性の両方で破綻する。各リージョンが独立してDBから読み、独立してキャッシュを持つ
  3. 無効化はグローバルに伝える: リージョン間はKafka/SNSでイベントを配り、各リージョンが自分のRedisをDELする。伝播に数秒かかることを許容範囲として明記
  4. DBレプリカを各リージョンに置く: 読みはローカルレプリカから。書きは単一リージョンに集約（マルチマスタは整合性が破綻する）

法規制の観点も加点: 「GDPR等で個人データを地域外に出せない場合があるので、『何を地理的に分散させてよいか』は技術判断だけでは決まりません」

Q9 あなたが設計したキャッシュ層に、障害が起きました。どう調査しますか?

運用経験を測る問題。 手順を層で切る:

  1. 症状を分類する: 「遅い」のか「古い値が出る」のか「エラーになる」のか。原因が全く違う
  2. 「古い値」なら層を切り分ける: ①ブラウザ（シークレットウィンドウで確認）②CDN（curl -I で X-Cache: HIT を確認）③L1（Pod単位で確認する——特定Podだけ古いことがある）④Redis（redis-cli GET と TTL）⑤DB（直接SELECT）。上から順に、実際の値を目で見る
  3. 「遅い」なら: ①SLOWLOG GET 25 ②--bigkeys / --hotkeys ③RedisのCPU（1コア100%なら飽和）④ネットワーク帯域 ⑤アプリ側のヒット率の急変
  4. 「エラー」なら: OOM（maxmemory-policy が noeviction）／接続数上限／フェイルオーバー中／CROSSSLOT
  5. 事前に用意しておくべきもの: ①キー種別ごとのヒット率ダッシュボード ②evicted_keys / expired_keys の推移 ③DB到達QPS ④「返した値の古さ（age）」のヒストグラム ⑤キャッシュを緊急でバイパスするフィーチャーフラグ

最後の5番目が最も評価される: 「キャッシュが原因かどうかを切り分けるために、実行時にキャッシュを無効化できるフラグを用意しておきます。ただし有効化するとDBに全量が流れるので、流量制限と併用します」

Q10 「キャッシュを入れないほうがいい」のはどんな場合ですか?

この質問は判断力を測る最上級の問題。答えられる候補者は少ない。

  1. 同じデータが繰り返し読まれない: 検索クエリが毎回ユニーク、時系列データの追記読み、レポートの1回だけの生成。ヒット率が上がらないのでオーバーヘッドだけが残る
  2. 1秒のズレも許されない: 残高・決済結果・在庫の引当判定・OTP。キャッシュしないのが正しい設計
  3. 元のクエリを直せば済む: index不足・N+1・不要なJOIN。キャッシュで塞ぐと、cold start時に必ず牙をむく
  4. データが巨大で、取得より転送が支配的: 1MBのJSONなら、Redisからの転送+デシリアライズがDBクエリより遅いことがある
  5. セキュリティ上、複製を持てない: 規制で「特定のストレージ以外に置けない」データ
  6. 運用できる体制がない: Redisの監視・フェイルオーバー・容量管理を誰も見ないなら、キャッシュは可用性を下げるだけ。これは技術ではなく組織の判断

締めの一言: 「キャッシュは複雑さという負債を払って速度を買う取引です。負債を返せる体制があり、かつ買った速度に見合う価値がある時だけ入れます。」

付録 チートシート

1. キャッシュを入れる判断

①取得/計算コストが本質的に高い ②同じ結果が繰り返し要求される ③多少古くても許される。3つ揃わないなら入れない。「遅いから Redis」は減点。

2. ヒット率の算数

実効レイテンシ = T_cache + (1-H) × T_backend
Backend QPS = Total QPS × (1-H)
見るのは H ではなく 1-H。90%→99% で負荷は1/10。

3. TTLの決め方

「このデータが古い時、誰がどう困るか」を文章で書く → 許容遅延がTTLの上限。必ず ±10% のジッターを付ける。

4. キー設計の4原則

①名前空間 ②スキーマバージョン（v3）③レスポンスを分岐させる要素を全部（ユーザー・言語・通貨・権限）④可変長はハッシュ化。

5. 更新時の鉄則

DBを先に、キャッシュはDEL。SETではない（並行更新で古い値が固定化する）。DELは冪等だから失敗にも強い。

6. 5つのパターン

読み: Cache Aside（既定）/ Read Through（規律の統一）/ Refresh Ahead（Hotキー）
書き: DEL（既定）/ Write Through（read-your-writes）/ Write Behind（消えてよいカウンタ）

7. 4大障害

Stampede=1キー同時MISS→singleflight / Hot Key=1キー集中→L1 / Penetration=存在しない→空値キャッシュ / Avalanche=大量同時消失→ジッター+流量制限

8. eviction

キャッシュ用途なら allkeys-lru（既定の選択）か allkeys-lfu（偏りが強い/バッチがある）。既定の noeviction は事故る。maxmemory は実メモリの60〜75%。

9. Redis で使うな

KEYS * / FLUSHALL / MONITOR。代わりに SCAN / キーのバージョン上げ / SLOWLOG。巨大キーは UNLINK。

10. HTTPヘッダ

アセット: public, max-age=31536000, immutable
HTML: no-cache
公開API: public, s-maxage=300, stale-while-revalidate=600
認証API: private, no-store

11. CDN と Redis

CDN=距離（物理）を解く・全員同じもの向き。Redis=計算コストを解く・ユーザー別向き。両方を層として重ねる。競合しない。

12. 消せないものは名前を変える

ブラウザキャッシュは消せない → ハッシュ付きURL + immutable。難しい層から問題を追い出して簡単な層に閉じ込める。

13. 表示 vs 確定

「読むだけ」ならキャッシュ可。「その値で世界を変える」（在庫引当・決済・権限判定）なら必ずDBのトランザクション。

14. 監視すべき5つ

①キー種別ごとのヒット率 ②evicted_keys ③DB到達QPS ④Redis p99 ⑤DBSIZE の推移（単調増加＝TTL忘れ）。加えて非同期処理の最終成功時刻。

15. cache-loss survivability

設計書に必ず書く: 「ヒット率が0%になった時、バックエンドは耐えられるか」。答えがNoなら、L1・流量制限・劣化応答・サーキットブレーカを設計する。

16. 実装チェックリスト

TTL必須 / ジッター / singleflight / 空値キャッシュ / Hotキー判定 / Redis障害時の挙動 / 更新時のDEL経路 / キーのバージョン / メトリクス。最初の3つとメトリクスは必須。

この本を1文にまとめると

キャッシュとは「速度を買い、鮮度と複雑さを支払う取引」である。
だから設計とは「どのデータに、いくらまで支払うか」を決めることであり、実装とは「支払いすぎないように歯止めをかけること」（TTL・ジッター・singleflight・流量制限）である。
