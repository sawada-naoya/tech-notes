Web API Design · Contract between Client and Server

図解Web API設計
ClientとServerのContractをどう決めるか

RESTのURL命名規則を覚える教材ではない。
APIはContract（契約）であり、設計するのは「変更可能で、安全で、理解しやすく、障害時にも正しく振る舞う境界」。
この4つの性質を、どの設計判断が支えているのかを一つずつ繋げていく。

変更可能

Clientを壊さずに進化できる。「Serverだけ直せばいい」は成立しない（11・12章）

安全

他人のデータを触れない。内部を漏らさない。認可はエンドポイントではなくオブジェクト単位（10・19章）

理解しやすい

ドキュメントを読まずに8割わかる。結果をClientがコードで分岐できる（5・6章）

障害時に正しい

タイムアウト・再送・同時実行で壊れない。ここが設計の本体（8・9・16章）

00 この教材が扱う範囲

結論から言うと、API設計の難所は「正常系のURL設計」ではなく「異常系の振る舞い」にある。前者は1日で学べるが、後者は事故を起こすまで気づけない。

軽く触れるだけ — 命名と作法

複数形にするか単数形か / スネークケースかキャメルケースか / 末尾スラッシュ。
重要だが、決めて統一すれば終わる。議論の価値が低い

深く扱う — 契約と障害時の振る舞い

同じリクエストが2回届いたら / 2人が同時に更新したら / Clientが古いバージョンのままだったら / Webhookが3回配送されたら / 一部だけ失敗したら。

なぜ異常系が本体なのか

■ 実際に起きること

  • モバイルアプリが電波の悪い場所で注文ボタンを押した → タイムアウト → アプリが自動リトライ → 二重注文・二重課金
  • 管理画面2枚で同じ商品を編集した → 後から保存した方が勝つ → 先に保存した変更が消える（Lost Update）
  • レスポンスにフィールドを1つ追加した → 古いiOSアプリがJSONパースに失敗 → アプリ全体がクラッシュ
  • 決済サービスのWebhookが2回届いた → 在庫が2回減る
  • URLのIDを書き換えた → 他人の注文が見える（BOLA）

どれもURL設計が正しくても起きる。そしてどれも、設計時に1つ判断を足しておけば防げた。

▸ 全章を貫く4つの問い

  1. このリクエストが2回届いたらどうなるか（冪等性 → 8章）
  2. 2つのリクエストが同時に来たらどうなるか（並行性 → 9章）
  3. この変更で、更新していないClientは壊れるか（進化 → 11・12章）
  4. この結果を受け取ったClientは、次に何をすべきか判断できるか（Status・Error → 5・6章）

設計レビューでこの4つを聞けるようになることが、この教材の到達点。

▸ 前提と表記

  • 題材はEC（Product / Cart / Order / Payment）で統一。章をまたいで同じAPIが育っていく
  • コード例は Go（標準ライブラリ + 最小限の補助）と JSON。フレームワーク固有の書き方は避ける
  • 章末には これだけ覚える Trade-off よくある失敗 自問する質問 の4枚を置いた。辞書として引くときはここだけ読めばいい

図0.1 — Contract層が厚いほど、Client と Server は独立して変更できる

Part 1

契約としてのAPI — 入口の形を決める

APIは関数呼び出しではない。相手のコードを自分では直せない、更新タイミングも制御できない、という前提の上に立つ契約である。この非対称性を理解すると、命名の議論より先に決めるべきことが見えてくる。

01 APIとは何か

結論: APIは「Serverが一方的に守ると約束したもの」。約束していないものに依存されると壊れ、約束しすぎると何も変えられなくなる。設計とは、何を約束し、何を約束しないかを決めること。

コンセントの比喩。 壁のコンセントは「100V・50/60Hz・この形状の穴」だけを約束している。配線の材質も発電所の種類も約束していないので、電力会社は自由に変えられる。もし「壁の中の銅線の太さ」に依存する家電を作ったら、それは契約外のものに依存している。APIで漏れたImplementation Detailは、この銅線にあたる。

1-1. Contractに含まれるもの / 含まれないもの

要素契約か変更するとどうなるか
URL・HTTP Method契約Clientが404を受け取る。即座に壊れる
Requestのフィールドと型契約必須追加・型変更は既存Clientを壊す
Responseのフィールドと型契約削除・型変更・リネームは壊す（追加は多くの場合安全）
Status Code契約200→202 の変更でClientの分岐が狂う
エラーコード体系契約Clientが分岐に使っている。リネームは壊す
冪等性の保証契約明示しないとClientは安全にリトライできない
並び順のデフォルト暗黙の契約になりがち明示していなくても、Clientは現在の順序に依存する
レスポンスの速度暗黙遅くなるとClient側がタイムアウトする
内部のテーブル構造契約ではない漏らしていなければ自由に変えられる
使用ミドルウェア・言語契約ではない同上。エラーメッセージから漏れることがある

▲ 暗黙の契約が最も危険

ドキュメントに書いていなくても、Clientが観測できるものはすべて依存される。
「並び順は保証していない」と書いてあっても、実際に常にID順で返っていれば、Clientはソートせずに表示する。ある日DBの実行計画が変わって順序が変わった瞬間、Client側のバグとして顕在化する。
対策は「保証しないものは、あえてランダムにする」か「保証して明記する」のどちらか。中途半端に安定させるのが一番悪い。

1-2. Implementation Detailが漏れる典型

✕ DB Modelをそのまま返す

  • status_cd: 3 の意味はドキュメントを見ないと分からない
  • is_deleted deleted_at は内部の論理削除。Clientには無意味
  • internal_memo は社内メモの漏洩
  • 連番IDが外部に出て、他人のIDを推測できる
  • カラム名を変えた瞬間にClientが壊れる

✓ 表現を設計して返す

  • status は意味が読める文字列
  • 金額は amount + currency の構造体。単位が自明
  • 内部IDではなく公開ID。内部の連番は漏れない
  • テーブルを分割・統合しても、この形は維持できる

▸ 金額を文字列で返すか数値で返すか

  • 最小単位の整数（6000 = 6000円、または600000 = 6000.00円）が最も安全。JSONの number は倍精度浮動小数点なので、小数で金額を扱うと丸め誤差が出る
  • 必ず通貨と単位をセットで返す。"total": 6000 だけだと「円か銭か」がドキュメント依存になる
  • 大きな整数（ID）も注意 — JavaScriptの Number は 253 を超えると精度を失う。IDは文字列で返すのが安全

1-3. 契約の非対称性

図1.1 — 「Serverだけ直せばいい」が成立するのは、Clientも自分たちが全部握っている場合だけ

▸ ここから導かれる原則

  • 最も古いClientが生きている限り、契約は生き続ける。2年前のアプリが使われているなら、2年前の契約を守る必要がある
  • 「内部APIだから雑でよい」は半分だけ正しい — Client も自分たちが握っていて、同時デプロイできるなら互換性の負荷は下がる。ただしモバイルアプリが混じった瞬間に外部APIと同じ制約になる
  • 約束を減らすほど自由が増える。返すフィールドを最小にし、保証を明記する

✓ これだけ覚える

  • APIは「守ると約束したもの」の集合。約束していないものを漏らさない
  • Clientが観測できるものは、書いていなくても依存される
  • Server と Client の変更コストは非対称。古いClientが契約の寿命を決める
  • DB Modelをそのまま返すのは、内部構造を契約にしてしまう行為

⇄ Trade-off

  • 返すフィールドを多くする → Clientが追加リクエスト不要 / 全部が契約になり、消せなくなる
  • 最小限にする → 変更の自由が残る / Clientのリクエスト回数が増える
  • 内部モデルと表現を分ける → リファクタが自由 / 変換コードとテストが必要

✕ よくある失敗

  • ORMの構造体をそのままJSONにする — カラム名変更がAPIの破壊的変更になる
  • 内部の数値コードを返す — 意味が読めず、ドキュメントなしでは使えない
  • デバッグ用フィールドを本番で返し続ける — 消そうとした時には依存されている
  • 並び順を保証せずに安定して返す — 暗黙の依存が育つ

? 設計時に自問する質問

  • このフィールドを来年削除したくなったら削除できるか
  • 内部のテーブル構造を変えたとき、このレスポンスは変わるか
  • 最も古いClientはいつのバージョンか。それはいつまで生きるか
  • ドキュメントに書いていないが、Clientが依存しそうな挙動はないか

02 Resource Modeling

結論: リソースとは「名前を付けて指し示す価値があるもの」。DBのテーブルでもなく、画面でもない。指し示す必要がないものにURLを与えると、使われないエンドポイントが増える。

2-1. ECからリソースを導く

● 要件から候補を出す

要件: 顧客が商品を探し、カートに入れ、注文し、支払い、配送状況を確認する 名詞を拾う: 顧客 / 商品 / カート / 注文 / 支払い / 配送 動詞を拾う: 探す / 入れる / 注文する / 支払う / 確認する / キャンセルする

基本のリソース

GET/v1/products商品コレクション（検索・絞り込みの入口）
GET/v1/products/{id}商品1件
GET/v1/cart自分のカート（シングルトンリソース）
POST/v1/cart/itemsカートに商品を追加
PATCH/v1/cart/items/{id}数量変更
DELETE/v1/cart/items/{id}カートから削除
POST/v1/orders注文を作る
GET/v1/orders自分の注文一覧
GET/v1/orders/{id}注文詳細
GET/v1/orders/{id}/shipments配送状況（1注文にN配送）

▲ 「カート」はなぜシングルトンか

  • ユーザーごとに1つしかなく、IDで指定する意味がない。/cart は「認証されたユーザーのカート」を意味する
  • /carts/{id} にすると、他人のカートIDを指定できてしまう形になる。認可バグの温床
  • 同じ理由で /me /v1/account もシングルトン。「自分のもの」はIDを取らないのが安全

2-2. RPC的APIとの違い

✕ 動詞をエンドポイントにする

POST/api/getOrderList
POST/api/createOrder
POST/api/updateOrderStatus
POST/api/deleteOrderById
POST/api/getOrderListForAdminScreen
  • 操作が増えるたびにエンドポイントが増え続ける
  • HTTPのキャッシュ・冪等性・条件付きリクエストが一切使えない
  • 命名規則が人によってぶれ、一貫性が失われる
  • ForAdminScreen — 画面がAPIに漏れている

✓ 名詞 + Methodで表す

GET/v1/orders
POST/v1/orders
PATCH/v1/orders/{id}
DELETE/v1/orders/{id}
GET/v1/orders?status=pending
  • 操作の種類が5つに固定される。覚えることが減る
  • GETはキャッシュでき、DELETEは冪等、という共通理解が働く
  • 管理画面用のフィルタはクエリパラメータで表現できる

▸ RPCが悪いわけではない

gRPCは完全にRPCだが、大規模なマイクロサービス間通信では最適な選択になる（→ 17章）。
問題なのは「HTTPを使いながらHTTPの利点を捨てている」状態。RPCを選ぶなら、gRPCのようにスキーマとコード生成が揃った仕組みで一貫させるほうがよい。中途半端な POST /api/doSomething が最悪。

2-3. POST /orders/{id}/cancel はRESTでは間違いか

? Thinking Point

「キャンセル」をどう表現するか。以下の4案のうち、どれを選ぶか決めてから読み進めること。

案A: POST /v1/orders/{id}/cancel 案B: PATCH /v1/orders/{id} { "status": "cancelled" } 案C: POST /v1/orders/{id}/cancellation 案D: DELETE /v1/orders/{id}
案評価理由
A. POST /cancel実務では十分正解厳密なRESTではないが、意図が明確で、誤用しようがない。多くの大手APIが採用している
B. PATCH status避けるべき詳細は下記。最も一般的な誤り
C. POST /cancellation最も筋が良い「キャンセルという出来事」をリソース化。理由・実行者・日時を持てる。GETで参照もできる
D. DELETE誤り注文は消えない。キャンセルは状態遷移であって削除ではない

■ 案B（PATCHでstatusを書き換える）が危険な理由

  • Clientに状態遷移の知識を要求する — 「次にどの状態へ行けるか」を知らないとリクエストできない。それはServerの責務
  • 不正な遷移を弾く処理が肥大する — shipped → cancelled cancelled → paid ... すべてのパターンを1つのハンドラで検証することになる
  • キャンセルに付随する情報を渡せない — キャンセル理由、返金するか、在庫を戻すか。statusフィールド1つでは表現できない
  • 認可が粗くなる — 「statusを変更できる権限」という曖昧な単位になる。実際には「キャンセルできる人」と「発送できる人」は別
  • 副作用が見えない — statusを書き換えるだけに見えて、裏で返金APIが走る。契約から副作用が読み取れない

✓ 判断の指針

  • その操作が「記録に残る出来事」なら、リソース化する（cancellation / refund / shipment / approval）
  • 記録に残らない単なる操作なら、動詞のままでよい（POST /v1/emails/{id}/resend）
  • 迷ったら「その操作の結果をGETしたくなるか」で判断する。したくなるならリソース
  • RESTの原理主義に付き合う必要はない。判断基準は「Clientが誤用できないか」「後から情報を足せるか」

2-4. 画面単位のエンドポイントを作るべきか

⇄ リソース指向 vs 画面指向（BFF）

  • リソース指向で通す → API がシンプルで再利用可能 / 1画面で5回リクエストが必要になる（Chatty API → 21章）
  • 画面用エンドポイントを作る → 1リクエストで完結、モバイルの通信効率が良い / 画面が変わるとAPIが変わる。APIが画面の数だけ増える
  • 折衷: コアAPIはリソース指向で作り、必要な画面だけ ?include=items,shipments や専用のBFF層で束ねる。「束ねる層」と「真実の層」を分けるのが要点

2-5. 命名の最低限のルール

項目推奨理由
コレクション/orders（複数形）一覧であることが明確。単複混在が最も読みにくい
単語の区切り/order-items または /order_itemsどちらでもよいが統一する。キャメルケースは避ける
JSONのキーsnake_case か camelCase を統一混在が最悪。既存のClient言語に合わせる
階層の深さ2階層まで/a/{id}/b/{id}/c/{id} は長すぎる。子リソースは単体でも引けるようにする
日時RFC 3339 / ISO 8601（UTC）2026-09-23T10:00:00Z。独自フォーマットを作らない
真偽値のフィールドis_ や has_ を付ける意味が読める。ただし状態はbooleanで表さない

✓ これだけ覚える

  • リソースは「名前を付けて指し示す価値があるもの」。テーブルでも画面でもない
  • PATCHでstatusを書き換えさせない。状態遷移の知識をClientに持たせないこと
  • 記録に残る操作は出来事としてリソース化する（cancellation / refund）
  • 「自分のもの」はIDを取らない（/cart /me）。認可事故が構造的に減る

⇄ Trade-off

  • POST /{id}/verb → 意図が明確・実装が単純 / RESTの統一性からは外れ、増えると雑然とする
  • サブリソース化 → 情報を足せる・参照できる / エンドポイントが増え、設計コストがかかる
  • リソース指向で統一 → 再利用・理解しやすさ / 1画面あたりのリクエスト回数が増える
  • 画面単位のAPI → 通信効率 / 画面変更がAPI変更になり、数が増え続ける

✕ よくある失敗

  • /api/getXxx を量産 — HTTPの機能を全部捨てている
  • PATCH で status を自由に書き換えさせる — 不正遷移と認可漏れの温床
  • DELETEで論理削除する — 「消えた」のか「消せない状態」なのかが曖昧になる
  • /users/{id}/cart で自分のカートを取る — 他人のIDを入れられる構造を作っている

? 設計時に自問する質問

  • このURLは何を指しているか、1文で言えるか
  • この操作の結果を、後からGETしたくなるか
  • Clientはこのリクエストを送るために、内部の状態遷移を知る必要があるか
  • URLに他人のIDを入れたら、何が起きるか

03 HTTP Method — SafetyとIdempotency

結論: Methodの選択は好みではなく「Clientとネットワークに与える許可」の宣言。GETと言った時点で「勝手にキャッシュしてよい」「勝手に再送してよい」と言っている。

3-1. 2つの性質

Safety（安全性）

サーバーの状態を変えないこと。安全なMethodは、何回呼んでも、呼ばなくても、結果に差がない。
→ ブラウザ・プロキシ・クローラが勝手に呼んでよい

Idempotency（冪等性）

1回実行しても N回実行しても、最終的な状態が同じであること。
→ タイムアウト時に安全にリトライできる（レスポンスが同じである必要はない）

MethodSafeIdempotentBody用途リトライ
GETYESYESなし取得常に安全
POSTNONOあり作成・処理の実行危険（→ 8章で対策）
PUTNOYESあり指定IDへの全体置換安全
PATCHNO設計次第あり部分更新設計次第
DELETENOYES通常なし削除安全
HEADYESYESなし存在確認・メタ情報常に安全
OPTIONSYESYESなしCORSプリフライト常に安全

▲ 「冪等 = 同じレスポンス」ではない

  • DELETE /v1/orders/123 の1回目は 204、2回目は 404 を返すかもしれない。レスポンスは違うが、最終状態（消えている）は同じ。よって冪等
  • 冪等性が保証するのは「副作用が重複しないこと」であって、レスポンスの一致ではない
  • ただしClientの実装を楽にしたいなら、DELETEの2回目も 204 を返す設計は有効（「消えている」という要求は満たされているため）。どちらでもよいが、ドキュメントで明示する

3-2. Safetyを破るとどうなるか

■ GETで状態を変える実例

GET /api/orders/123/cancel ← リンクとして実装してしまった 起きること: 1. ブラウザのプリフェッチが、ユーザーがクリックする前にキャンセルを実行 2. Chrome の先読み、リンクプレビュー、メールクライアントのURL検査で発火 3. クローラが管理画面のリンクを辿って全注文をキャンセル 4. プロキシがレスポンスをキャッシュし、2回目以降は実行されずに成功を返す 5. ブラウザの「戻る」で再実行される
  • 実際に起きた事例として有名なのが、社内ツールのリンクをクローラが辿って全データを削除したケース
  • GETは「誰が何回呼んでもよい」という宣言。この約束を破ると、自分の預かり知らぬところで実行される

3-3. POST / PUT / PATCH の使い分け

リソースを作る／変えるとき、どのMethodか？ ├─ 新規作成で、IDをServerが決めるか？ │ └─ YES → POST /orders → 201 + Location ヘッダ（冪等でない → Idempotency-Key を検討） ├─ 新規作成だが、IDをClientが決めるか？ │ └─ YES → PUT /orders/{client-generated-id} → 冪等になる。オフライン対応アプリで有効 ├─ 既存リソースの全フィールドを送って置き換えるか？ │ └─ YES → PUT /orders/{id} → 送らなかった項目は消える、が契約 ├─ 一部のフィールドだけ変えるか？ │ └─ YES → PATCH /orders/{id} → 「送らない = 変更しない」を明記する └─ 状態遷移・処理の実行か？ └─ YES → POST /orders/{id}/cancellation （→ 2章）

■ PATCHの落とし穴 — 「null」と「未指定」の区別

▸ PATCHを冪等にできるか

  • 値を代入する形（{"quantity": 3}）→ 何回送っても3になる。冪等
  • 相対的な変更（{"quantity_delta": +1}）→ 送るたびに増える。冪等でない
  • PATCHは「代入」で設計する。加算・追記が必要なら、それは専用のサブリソースへのPOSTにする

3-4. 迷いやすいケース

やりたいことMethod理由
複雑な条件での検索（条件が長大でURLに収まらない）POST /products/searchやむを得ない妥協。Safetyを失うのでキャッシュできない。まずGET + クエリで収まらないか検討する
ログインPOST /sessionsセッションというリソースを作ると考える。GETは論外（認証情報がURLに残る）
ファイルアップロードPOST または PUTIDをClientが決めるならPUT。PUTなら再送で重複しない
並び替え（ドラッグ&ドロップ）PUT /lists/{id}/item-order順序全体を1つのリソースとして置換する。冪等になる
一括削除POST /orders/bulk-deleteDELETEにbodyを付けるのは仕様上曖昧。プロキシに落とされることがある
いいね / いいね解除PUT / DELETE /posts/{id}/likeトグル（POST /toggle）にしない。トグルは冪等でなく、連打で状態が読めなくなる

✓ これだけ覚える

  • MethodはClientとネットワークへの許可の宣言。GETは「勝手に呼んでよい」の意味
  • 冪等性は「最終状態が同じ」であり、レスポンスの一致ではない
  • PATCHは代入で設計する。加算・トグルは冪等性を壊す
  • PATCHの null と「未指定」を区別するか、区別しない契約にするかを最初に決める

⇄ Trade-off

  • PUT（全体置換） → 冪等・単純 / Clientが全フィールドを送る必要があり、競合で他人の変更を消す
  • PATCH（部分更新） → 通信量が少なく競合が減る / nullの解釈が難しく、冪等性の設計が要る
  • POST /search → 複雑な条件を送れる / キャッシュ不可、ブックマーク不可、ログから条件が追いにくい

✕ よくある失敗

  • GETで更新する — プリフェッチ・クローラ・キャッシュで事故る
  • 何でもPOST — 冪等性もキャッシュも失い、リトライ設計ができなくなる
  • POST /toggle-like — 連打やリトライで状態が不定になる
  • DELETEにリクエストボディを付ける — 中間機器に落とされることがある

? 設計時に自問する質問

  • このリクエストがタイムアウト後に自動リトライされたらどうなるか
  • GETと宣言したこの処理は、本当に状態を変えていないか（ログ以外に）
  • このPATCHを2回送ったら、結果は同じか
  • Clientはこの更新で、送らなかったフィールドがどうなるか分かるか

04 Request / Response設計

結論: Path / Query / Header / Body の使い分けは「何を識別し、何を絞り込み、何を運び、何を送るか」で決まる。判断を間違えるとキャッシュ・ログ・セキュリティに波及する。

4-1. 4つの置き場所

置き場所置くもの置いてはいけないもの理由
Pathリソースの識別子。階層構造絞り込み条件、任意パラメータPathは「どれ」を指す。任意項目を入れると組み合わせ爆発する
Query絞り込み・並び替え・ページング・表示制御秘密情報（token, password）URLはアクセスログ・ブラウザ履歴・Refererに残る
Header認証、コンテンツ交渉、Idempotency-Key、Request-ID、ETag業務データHeaderは「通信の制御情報」。業務データを入れると発見されない
Body作成・更新するデータ本体GETでの送信GETのbodyは仕様上意味を持たず、中間機器に落とされる

■ URLに秘密情報を置いたときに漏れる経路

GET /v1/orders?api_key=sk_live_abc123 漏れる先: ・Webサーバ / ロードバランサ / CDN のアクセスログ（長期保管される） ・APMツール・エラー監視サービス（外部SaaSに送信される） ・ブラウザの履歴・オートコンプリート ・Referer ヘッダ（外部サイトへのリンクをクリックした瞬間に送信） ・プロキシのキャッシュキー → 認証情報は必ず Authorization ヘッダ。これは通常ログに残らない

4-2. 一覧APIの4点セット

▸ 設計上の決めごと

  • フィルタと検索を分ける — status=published（構造化・完全一致）と q=...（曖昧・スコア順）は別物。混ぜると実装も仕様も曖昧になる
  • ソートの記法を1つに決める — sort=-created_at か sort_by=created_at&order=desc。複数キーを扱うなら前者
  • ソート可能なフィールドをホワイトリスト化 — 任意のカラム名を受け付けると、索引のないカラムで全件ソートされて落ちる。SQLインジェクションの経路にもなる
  • limitに上限を設ける — limit=1000000 を防ぐ。上限を超えたら 400 で返すか、上限に丸めて返すかを決めて明記する
  • 未知のクエリパラメータをどうするか決める — 無視する（寛容）か 400 にする（厳格）。タイポを検出できるのは後者だが、将来のパラメータ追加時にClientが壊れにくいのは前者

4-3. レスポンスの形

✕ 独自エンベロープで全部包む

  • HTTPが既に持っている情報（成否・状態）を二重に表現している
  • success を見ないと判断できない形にすると、200 + error=true への道が開く（→ 21章）
  • すべてのClientが .data を剥がす処理を書く必要がある

✓ リソースをそのまま返す

  • 成否はStatus Codeで表す（→ 5章）
  • コレクションは配列を直接返さず、オブジェクトで包む。後からページ情報やメタ情報を足せる

▲ 配列をトップレベルで返してはいけない理由

  • [ {...}, {...} ] を返すと、後から総件数や次ページ情報を足す場所がない。足すには破壊的変更になる
  • 過去にはJSON配列を直接返すことによるセキュリティ上の問題も指摘されていた（古いブラウザでのJSONハイジャック）
  • 常にオブジェクトで返す。中身が1件でもコレクションでも同じ方針にする

4-4. nullを返すか、キーごと省くか

方針形長所短所
常にキーを返す（null許容）{"note": null}スキーマが安定。Clientが存在チェック不要レスポンスサイズが増える
nullならキーを省く{}サイズが小さい「値がない」と「フィールドが存在しない」が区別できない。型付き言語で扱いにくい
空配列は必ず返す{"items": []}Clientがnullチェックとループを両方書かずに済む—

▸ 推奨

「キーは常に返す。配列はnullではなく空配列」を原則にする。
例外は、権限によって見せられないフィールド。この場合はnullではなくキーごと省くほうがよい（nullだと「値が無い」のか「見せてもらえない」のか区別できないため）。省いたうえで、必要なら "_permissions" のような形で理由を示す。

  • 認証情報をURLに置かない。ログ・履歴・Refererに残る
  • レスポンスは常にオブジェクト。配列を直接返すと後から拡張できない
  • ソート可能フィールドはホワイトリスト。limitには上限を設ける

⇄ Trade-off

✕ よくある失敗

  • APIキーをクエリパラメータで受ける — アクセスログに平文で残り続ける
  • sortにカラム名をそのまま渡す — 索引なしソートで全件走査、injectionの入口
  • limitに上限がない — 1リクエストでメモリを食い尽くす
  • 空配列の代わりにnullを返す — Client側で必ずnull起因のバグが出る

  • このパラメータはアクセスログに残ってよい情報か
  • limitの最大値はいくつか。指定されなかったときのデフォルトは
  • このレスポンスに後からメタ情報を足せる構造になっているか
  • ソートとフィルタの対象フィールドに索引はあるか

05 Status Code

結論: Status Codeは「Clientの取るべき行動のカテゴリ」を表す。細かい理由はエラーコードで伝える（→ 6章）。だから覚えるべきは番号の意味ではなく、その番号を見たClientが何をするか。

5-3. 迷いやすい境界

▲ 400 と 422 の使い分け

  • 400 = {"quantity": "abc"} — パースできない・スキーマに合わない。Clientの実装バグ
  • 422 = {"quantity": -1} — 形式は正しいが業務ルールに反する。ユーザーの入力ミス
  • 分ける実利: Clientは400なら「バグとして記録」、422なら「フォームにエラー表示」と処理を変えられる
  • 400に統一する流派もある。統一する場合も、エラーコードで区別できるようにしておく。重要なのは「Clientが処理を分けられること」

▲ 403 と 404 の使い分け — 情報漏洩とのトレードオフ

GET /v1/orders/OTHER_USERS_ORDER_ID 403 を返す → 「そのIDの注文は存在する。あなたには見えないだけ」と教えてしまう 攻撃者はIDの有効性を総当たりで確認できる（存在推測） 404 を返す → 「無い」としか分からない。情報を与えない ただし正規ユーザーが権限の問題に気づきにくい
  • 推奨: 他人のリソースには404（存在を隠す）。自分のリソースだが操作権限がない場合は403（理由を伝える）
  • 管理画面など、内部の信頼できる利用者向けには403で理由を伝えるほうが親切

▲ 409 が最も使われず、最も必要なコード

  • 重複作成: 同じメールアドレスで登録 → 409 + EMAIL_ALREADY_EXISTS
  • 楽観ロックの衝突: If-Match が一致しない → 412 または 409（→ 9章）
  • 不正な状態遷移: 発送済みの注文をキャンセル → 409 + ORDER_ALREADY_SHIPPED
  • 409の本質は「今の状態では無理。状態が変われば可能かもしれない」。422（入力を直せ）とも403（永久に無理）とも違う

■ 在庫切れは 409 か 422 か

  • 422の論: 「数量10に対し在庫3」は入力値の問題。ユーザーが数量を直せば通る
  • 409の論: 在庫はサーバー側の状態。入力は正しく、状態と矛盾している。時間が経てば入荷して通るかもしれない
  • 結論: どちらでもよいが、チームで決めて統一する。重要なのは code: "INSUFFICIENT_STOCK" と details: {"available": 3} を返すこと。Clientが分岐に使うのはStatusではなくエラーコード

5-4. Statusの選び方（Decision Tree）

処理は成功したか？ ├─ YES │ ├─ 新しいリソースを作ったか？ → YES → 201 + Location + 作成物をボディに │ ├─ 受け付けただけで、処理はこれからか？ → YES → 202 + ジョブURL │ ├─ 返すボディがあるか？ → YES → 200 / NO → 204 │ └─ NO ├─ サーバー側の問題か？ │ ├─ YES → 一時的で、回復が見込めるか？ │ │ ├─ YES → 503 + Retry-After │ │ └─ NO → 500 （詳細は返さない。ログにrequest_idを残す） │ └─ NO → 次へ ├─ 認証されているか？ → NO → 401 （WWW-Authenticate を付ける） ├─ 権限があるか？ │ ├─ NO・他人のリソース → 404 （存在を隠す） │ └─ NO・自分のだが操作不可 → 403 ├─ リクエストの形式は正しいか？ → NO → 400 ├─ レート制限に達したか？ → YES → 429 + Retry-After ├─ 現在のリソース状態と矛盾するか？ → YES → 409 （重複・状態遷移・競合） └─ 422 （業務ルール違反。フィールド単位の詳細を返す）

5-5. 201 / 202 / 204 の実装

▸ 204を使うべきでない場面

  • PATCH / PUT の後 — 更新後の値（updated_at、サーバーが補正した値、計算された合計）をClientが知りたい。200 + 更新後リソースが親切
  • POST の後 — 作成されたIDを返さないと、Clientは作ったものを参照できない
  • 204が適切なのはDELETEと、本当に返すものがない操作だけ

✓ これだけ覚える

  • Statusは「Clientが次に取る行動のカテゴリ」。細かい理由はエラーコードで
  • 401=認証し直せ / 403=諦めろ / 404=隠す / 409=状態を取り直せ / 422=入力を直せ
  • 202は「完了していない」の宣言。200と混同するとClientが誤動作する
  • 5xxは「成功したか不明」。だから冪等性が必要になる

⇄ Trade-off

  • 403で理由を返す → 利用者に親切 / リソースの存在を教えてしまう
  • 404で隠す → 情報を与えない / 正規ユーザーが原因を特定できない
  • 400と422を分ける → Clientが処理を分けられる / 境界の判断でチーム内が揺れる
  • 400に統一 → 迷わない / フォーム表示とバグ検知を区別できない

✕ よくある失敗

  • 200 + {"success": false} — 監視もリトライも壊れる（→ 21章）
  • 業務エラーで500を返す — 監視アラートが鳴り続け、本物の障害が埋もれる
  • 401と403を取り違える — Clientが無限にトークン更新を試みるループに入る
  • 429にRetry-Afterを付けない — Clientが即座に再送し、さらに負荷が上がる

? 設計時に自問する質問

  • このStatusを受け取ったClientは、リトライすべきか否かを判断できるか
  • この5xxは本当にサーバーの不具合か。業務エラーを混ぜていないか
  • 404を返すべき場面で403を返して、存在を教えていないか
  • 202を返しているのに、Clientは完了したと思っていないか

06 Error Design

結論: エラーレスポンスは「人間が読むメッセージ」ではなく「プログラムが分岐するためのデータ」。messageだけ返すAPIは、Clientに文字列マッチを強制している。

6-1. Error Contract

✕ メッセージだけ

  • Clientが分岐するには日本語の文字列マッチしかない
  • 文言を変えた瞬間にClientが壊れる。メッセージが契約になってしまう
  • 多言語対応ができない（サーバーが言語を知らない）
  • 「どの商品が」「あと何個なら買えるか」が分からず、UIを作れない

  • code: 機械が分岐する。不変の識別子（大文字スネーク）
  • message: 人間向け。いつでも変えてよい
  • details: UIを作るための構造化データ
  • request_id: 問い合わせ時にログと突き合わせる鍵

結論: バリデーションは3層ある。Syntax（形が正しいか）→ Semantic（値として妥当か）→ Business Rule（今の状態で許されるか）。混ぜると、置き場所も返すStatusも決まらなくなる。

  • ③はDBを見ないと判定できない → 判定した瞬間と実行する瞬間で状態が変わりうる。ここが最大の論点（7-3）
  • ①②はフレームワークに任せてよい。③は絶対に任せてはいけない — 業務ルールがバリデーションタグに散ると、ドメインの知識が消える

▸ 設計上の決めごと

  • 最初の1件で止めるか、全件返すか → 全件返す。1件ずつ直させるフォームは最悪のUX
  • fieldの表記を決める → items[0].quantity のようなパス形式。Clientが入力欄と対応付けられる形にする
  • messageは国際化を考える → サーバーで日本語を返すか、codeだけ返してClientが文言を持つか。多言語対応するなら code + パラメータだけ返し、文言はClient側に持たせる

■ 在庫チェックが破れる瞬間

  • 正しさは実行時の原子的な操作で担保する — 条件付きUPDATE、UNIQUE制約、予約テーブル

⇄ それでも事前チェックを残す理由

  • 残す → カート画面で「在庫切れ」を先に出せる。無駄な決済処理を減らせる / 正しさの担保だと誤解される
  • 消す → 責務が明確 / UXが悪化し、決済直前まで失敗が分からない

  • 業務ルールをバリデーションタグに書く — ドメイン知識が分散し、テストもできない
  • Clientのバリデーションだけに頼る — APIを直接叩かれたら無防備

壊れない境界 — 再送・同時実行・権限

ここからがAPI設計の本体。ネットワークは必ず失敗し、Clientは必ずリトライし、ユーザーは必ず同時に操作し、攻撃者は必ずIDを書き換えてくる。この3つに対する設計が無いAPIは、動いているのではなく、まだ事故に遭っていないだけ。

08 Idempotency — 2回届いても壊れない

結論: ネットワーク越しの「1回だけ実行」は原理的に保証できない。保証できるのは「何回届いても、結果が1回分になる」こと。冪等性とは、Exactly-Onceを諦めて At-Least-Once + 重複排除で実現する現実解。

8-2. 冪等性を得る3つの手段

手段やり方向いている場面限界
① 構造的に冪等にするPUT（置換）、DELETE、「代入」型のPATCH更新系。IDがすでに決まっている操作新規作成には使えない（IDをClientが決められるなら可）
② 自然キーのUNIQUE制約業務的に一意な値にDB制約を張り、違反を「既にある」として扱うメール登録、注文番号、外部システムのイベントID自然キーが存在しない操作には使えない
③ Idempotency-KeyClientが生成した鍵で、リクエストと結果を記録する決済・注文など、自然キーが無く副作用が重い操作実装コストが高い。保存期間の設計が必要

▸ 選択の順序

  1. まず①を検討する — 「IDをClientに生成させてPUT」にできないか。最も安く、最も壊れない
  2. 次に② — 業務的な一意キーがあるなら、UNIQUE制約で十分なことが多い

8-4. ③ Idempotency-Key の設計

▲ 「同じキー・違う内容」を弾く理由

  • キーを使い回されると、別の注文が前の注文のレスポンスを受け取ることになる。Client側のバグを静かに隠してしまう
  • だからリクエストボディのハッシュを保存して照合する。一致しなければエラーにする
  • ハッシュ対象はボディだけでなくメソッド + パス + ボディにする。同じキーで別エンドポイントを叩かれるのも防ぐ

■ scope を付けない実装が危険な理由

  • キーはClientが自由に決める文字列。悪意あるユーザーが他人と同じキーを送れる
  • グローバルに一意にしていると、他人のリクエストの記録済みレスポンスが返ってくる（他人の注文情報の漏洩）
  • 必ず「認証された主体」でスコープを切る。テナント分離があるならテナントIDも含める（→ 10章）

8-5. 状態遷移と、同時に来たときの扱い

▲ 5xxのときにキーを解放する理由

  • 500を記録してしまうと、Clientが再送しても永遠に500が再生される
  • 一時的な障害なら、再送で成功するべき。だから「確定した結果（2xx/4xx）だけを記録し、不確定な失敗は記録しない」
  • ただし「500を返したが副作用は起きていた」ケースがある。これを防ぐには、副作用と記録を同一トランザクションに入れるのが理想（下記）

✓ より強い実装 — 副作用と記録を同一トランザクションに

09 Concurrency — 同時更新で消えない

結論: Lost Updateは「エラーが出ないバグ」。両方のリクエストが200を返し、片方の変更だけが静かに消える。誰も気づかないまま運用され、「なぜか元に戻っている」という問い合わせだけが残る。

9-1. Lost Update をAPI視点で見る

図9.1 — PUT（全体置換）は、送っていないつもりの項目も上書きする

9-2. 4つの対処

方法やり方効果限界
① PATCHにする変更した項目だけ送る別項目を編集している限り衝突しない。最も安く効く同じ項目を同時に編集したら、やはり後勝ちになる
② version フィールドボディに version を含めて送り返す衝突を検出できる。実装が単純APIのボディに技術的な項目が混ざる
③ ETag + If-MatchHTTPの条件付きリクエストを使う標準的。キャッシュとも統合されるETagの生成・比較の設計が要る

9-3. ETag + If-Match の設計

▸ ETagに何を入れるか

  • version列をそのまま — ETag: "7"。単純で計算コストゼロ。最も実務的
  • updated_at — 精度が秒だと同一秒内の更新を検出できない。使うならミリ秒以上
  • 内容のハッシュ — 厳密だが計算コストがかかる。表現（レスポンス）が変わるとETagも変わってしまう点に注意
  • 推奨は version 列。DBのUPDATE文にそのまま条件として使える

412 Precondition Failed送られた事前条件（If-Match）が満たされなかったETag / If-Match を使っている場合。HTTPの意味に忠実
409 Conflict現在の状態と矛盾するボディのversionで検出した場合、重複作成、不正な状態遷移
428 Precondition Required条件付きリクエストが必須なのに付いていない楽観ロックを強制したい場合

▸ どちらでもよい、が混ぜない

412と409のどちらを返すかで実害が出ることは少ない。重要なのは、Clientが「最新を取り直して再試行すればよい」と判断できること。
そのためにエラーコード（RESOURCE_MODIFIED）を必ず添え、detailsに現在のバージョンや更新者を入れると、Client側でUIを作れる。

9-5. 衝突したときのClient側の選択肢

A. 再取得して上書き

最新を取得し、自分の変更を再適用して再送。自動でやると結局Lost Updateと同じになるので、単純な項目にのみ。

B. ユーザーに提示して選ばせる

「他のユーザーが更新しました。あなたの変更: 2800円 / 現在の値: 3000円」。業務システムで最も安全。

C. 自動マージ

項目が重ならなければ自動で統合。PATCHで送っていれば、そもそもサーバー側で衝突しないことが多い。

D. 最後の書き込みを勝たせる

明示的にこれを選ぶなら問題ない。無自覚にこうなっているのが問題。ドキュメントに「後勝ち」と明記する。

? Thinking Point

在庫の増減（stock を 10 → 9 にする）に楽観ロックは必要か？

考えてから開く

不要。というより、楽観ロックは適切な解ではない。

  • 在庫の減算は「9にする」ではなく「1減らす」という相対的な操作。絶対値を送る時点で設計が誤っている
  • UPDATE inventories SET quantity = quantity - 1 WHERE product_id = ? AND quantity >= 1 なら、競合しても両方正しく処理される（片方が0行になるのは在庫が尽きた時だけ）
  • 楽観ロックを付けると、同時に10人が買おうとしたとき9人が412で弾かれる。在庫は十分あるのに
  • 使い分け: 「人間が値を決める編集」＝楽観ロック / 「機械的な増減」＝条件付きUPDATE（相対演算）。競合を検出したいのか、競合しても正しく処理したいのかで分かれる

✓ これだけ覚える

  • Lost Updateはエラーが出ないバグ。両方が200を返す
  • まずPATCHにするだけで大半の衝突は消える
  • 検出が必要なら ETag + If-Match（または version）。412/409 + RESOURCE_MODIFIED
  • 人間が決める値は楽観ロック、機械的な増減は相対演算で解く

⇄ Trade-off

  • 楽観ロック → 衝突を検出でき、ロックを保持しない / Clientに再試行の実装が必要
  • 悲観ロック → 衝突が起きない・編集中を可視化できる / 解放漏れ、タイムアウト、API設計の複雑化
  • If-Match を必須化（428） → 事故が構造的に防げる / 既存Clientが壊れる。段階的移行が必要
  • 後勝ちを許容 → 実装が最も単純 / 変更が静かに消える。明示的に選ぶなら可

✕ よくある失敗

  • PUTで全項目を送らせる — 触っていない項目まで上書きされる
  • 衝突時に自動で再取得＆再送 — 結局Lost Updateになる。人間の判断が要る場面がある
  • 在庫減算に楽観ロック — 在庫があるのに大量に弾かれる
  • ETagを返すが If-Match を無視する — 使われていない防御は無いのと同じ

? 設計時に自問する質問

  • 2人が同時にこれを更新したら、どちらかの変更が消えるか
  • 消えたとき、それに気づく人はいるか
  • この値は「人が決める値」か「機械的に増減する値」か
  • 衝突を返したとき、Clientは何をすればよいか分かるか

10 Authentication / Authorization

結論: AuthN（誰か）とAuthZ（何ができるか）は、実装の層も、失敗時のStatusも、変更の頻度も違う。混同すると「ログインできているのに他人のデータが見える」という最も多い脆弱性になる。

10-1. 用語の整理 — 何がどの役割か

用語レイヤ役割よくある誤解
Cookie運搬手段ブラウザが自動で付けてくれる入れ物「Cookie認証」という認証方式があるわけではない。中身がセッションIDかトークンかが本質
Session状態管理サーバー側に状態を持ち、IDだけをClientに渡すCookieとセットで語られるが、別概念。ヘッダで運んでもよい
JWTデータ形式署名付きのJSON。改ざん検知ができる「JWT = 認証方式」ではない。単なる入れ物の形式。暗号化もされていない（誰でも中身を読める）
Bearer Token運搬規約Authorization: Bearer xxx という送り方中身はJWTでもランダム文字列でもよい。「持っている人が使える」という意味
OAuth 2.0認可の委譲「AさんのデータへのアクセスをBアプリに許可する」仕組み認証のプロトコルではない。ユーザーが誰かは規定していない
OIDC認証OAuth 2.0の上に「誰か」を乗せた仕様（ID Token）「OAuthでログイン」と言われるものは、実質これ

▲ 混同が生む具体的な事故

  • 「JWTを使っているから安全」 — JWTは改ざんを防ぐだけ。盗まれたら終わりで、しかもサーバー側で失効させられない
  • 「OAuthでログインしているから本人確認済み」 — OAuth単体ではユーザーの同一性を保証しない。Implicit Flowでのトークン差し替え攻撃の原因になった
  • 「認証を通っているから、このデータは見せてよい」 — これがBOLA（→ 19章）。認証は入館証、認可は各部屋の鍵

10-2. Session vs JWT の選択

観点Session（サーバー状態あり）JWT（自己完結）
失効即座にできる（サーバーで消すだけ）できない。有効期限が切れるまで有効
権限変更の反映次のリクエストから反映トークン更新まで古い権限のまま
スケール共有ストア（Redis等）が必要検証にI/O不要
サイズIDのみ（数十バイト）数百バイト〜。全リクエストに乗る
マイクロサービス各サービスがストアを見る必要各サービスが独立に検証できる
漏洩時の被害サーバーで即無効化有効期限まで悪用され続ける

✓ 実務での落とし所

  • 単一のWebアプリ + モバイル → セッション（Cookie: HttpOnly + Secure + SameSite）が最も安全で単純。「モダンだからJWT」という理由で選ばない
  • JWTを使うなら短命に — アクセストークンは5〜15分、リフレッシュトークンはサーバー側で失効管理する。これで両者の利点を組み合わせる
  • JWTに権限を詰め込みすぎない — ロールが変わっても反映されない。権限はリクエスト時に引く
  • ブラウザではトークンをlocalStorageに置かない — XSSで即座に盗まれる。HttpOnly Cookieに入れる（CSRF対策とセットで）

10-3. 認可の3つの軸

図10.1 — ①は「入口」、②③は「データ1件ごと」。層が違う

▸ 「忘れられない構造」にする

  • チェックを書き忘れられる設計をやめる — FindByID(id) が存在する限り、誰かが必ず使う
  • テナントIDはコンテキストから自動注入 — ORMのフック、DBのRow Level Security、専用のクエリビルダで強制する
  • デフォルト拒否 — ルーティングに認可の指定がないエンドポイントは、起動時にエラーにする。新規追加時の漏れを構造的に防げる
  • テストで担保する — 「他人のIDでアクセスして404になる」テストを、全リソースに対して機械的に書く

10-4. どこで認可を判定するか

場所向いている判定限界
ミドルウェア認証、ロールによる粗い制御個別オブジェクトの所有者は分からない（まだDBを見ていない）
Handlerリクエスト単位の権限チェック書き忘れる。ユースケースが増えるたびに重複する
UseCase業務ルールと結びついた判定（「発送済みは本人でもキャンセル不可」）最も表現力が高い。ここが主戦場
Repository / SQLテナント境界、所有者による絞り込み構造的に漏れない。一覧系は必ずここで

■ 一覧APIの認可漏れは詳細APIより見つかりにくい

  • GET /v1/orders で、うっかり WHERE customer_id = ? を外すと全ユーザーの注文が返る
  • 詳細APIは「他人のIDを入れる」テストをしやすいが、一覧は「自分のデータが返っている」ことしか確認しないため見逃される
  • 対策: テストで「別ユーザーのデータを作り、一覧に含まれないこと」を必ず検証する。自分のデータだけのテストは、この穴を発見できない

✓ これだけ覚える

  • AuthN=入館証、AuthZ=各部屋の鍵。401と403が違うのはこのため
  • JWTはデータ形式であって認証方式ではない。失効できない点が最大の制約
  • 認可はRBAC / Ownership / Tenant の3軸すべてを通す
  • 「チェックを書き忘れられない構造」にする。規律ではなく構造で守る

⇄ Trade-off

  • Session → 即時失効・権限変更が反映される / 共有ストアが必要で、サービス間で共有しづらい
  • JWT → 検証にI/O不要・分散に強い / 失効できず、権限変更が遅れる
  • 認可をSQLで強制 → 漏れない / 業務的な条件を表現しづらい
  • 認可をUseCaseで判定 → 表現力が高い / 書き忘れる余地が残る

✕ よくある失敗

  • 認証だけして所有者チェックを忘れる — API脆弱性の第1位（BOLA）
  • 一覧APIでテナント条件を落とす — 他社のデータが全件返る
  • JWTをlocalStorageに保存 — XSSで一発で盗まれる
  • JWTに権限を詰めて長命にする — 権限剥奪しても有効期限まで操作できる

? 設計時に自問する質問

  • このエンドポイントに他人のIDを入れたら何が返るか
  • 一覧APIのSQLに、テナントと所有者の条件は必ず入るか
  • ユーザーを即座にログアウトさせたいとき、それは可能か
  • 新しいエンドポイントを追加したとき、認可の指定漏れは検出されるか

Part 4

変化に耐える — 契約を壊さずに進化させる

APIは一度公開したら終わりではなく、そこから数年運用される。問題は「変更すること」ではなく「変更がClientに何をするか」を予測できないこと。どの変更が安全でどれが破壊的かを、型として覚える。

11 Versioning

結論: バージョニングは「破壊的変更を許すための仕組み」ではなく、「破壊的変更を避けきれなかったときの最後の手段」。v2を作るということは、v1とv2を両方保守し続けるということ。

11-1. バージョンの置き場所

方式形長所短所
URLパス/v1/orders一目で分かる。ブラウザで叩ける。ルーティングで分離しやすい厳密にはリソースのURIが変わってしまう（同じリソースに2つのURL）
ヘッダAccept: application/vnd.example.v2+jsonURIが安定。細かい粒度で指定できる見えにくい。デバッグ・キャッシュ・ドキュメント化が面倒

クエリ?version=2導入が簡単キャッシュキーが分散。付け忘れやすい

▸ 実務の選択

  • 社内・自社アプリ向け → /v1 で十分。わかりやすさが最大の価値
  • 多数の外部開発者向け → 日付バージョンを検討する価値がある。「Clientは契約日のまま動き続け、任意のタイミングで上げる」が実現できる
  • 避けるべき — /v1.2.3 のようなセマンティックバージョン。APIのバージョンは「互換性の世代」であって、リリース番号ではない

11-2. v2を作る前に考えること

■ v2のコストは「作ること」ではない

v2をリリースした後に必要になるもの: ・v1 と v2 の両方のコードを保守する（バグ修正は両方に適用） ・v1 と v2 の両方のドキュメント ・v1 と v2 の両方のテスト ・新機能を v1 にも入れるのか、v2 だけなのかの判断が毎回発生 ・v1 の利用者を移行させる交渉・告知・猶予期間の設定 ・v1 を落とす日の決定と、落とした後の問い合わせ対応 実際に起きること: v1 が永久に消えず、v3 が作られ、3世代を保守する
  • 「v2を作る」は最終手段。まず後方互換な形で実現できないかを徹底的に考える（→ 12章）
  • それでもv2が必要になる典型は、リソースモデルそのものが変わるとき。フィールドの追加削除レベルなら、v2は不要

▲ 「レスポンスへのフィールド追加」が安全でない場合

  • Clientが厳格なスキーマ検証をしている — 未知フィールドでバリデーションエラーにする実装（一部のOpenAPIバリデータのデフォルト設定）
  • Clientが構造体に全フィールドをマッピングし、未知を許さない — 一部の言語・ライブラリの設定次第
  • レスポンスサイズが跳ね上がる — 巨大なフィールドを足すと、帯域とパース時間でモバイルが遅くなる
  • 対策: ドキュメントとSDKで「未知のフィールドは無視すること」を契約として明記する。これを最初に宣言していないと、追加すらできないAPIになる

11-4. 破壊的変更を避ける技法

✕ リネームする

✓ 両方返して、段階的に消す

✓ 互換を保つパターン集

  • フィールドを増やして、古いものを残す — 最も基本。消すのは利用がゼロになってから
  • 新しい挙動をオプトインにする — ?expand=items のように、指定した場合だけ新しい形にする
  • デフォルト値で旧挙動を維持する — 新しいパラメータを追加し、未指定時は従来通りにする
  • 新しいエンドポイントを作る — /v1/orders を残しつつ /v1/orders/search を追加。v2を切るよりはるかに安い
  • サンセット予告をヘッダで出す — Deprecation: true / Sunset: Sat, 31 Dec 2026 23:59:59 GMT / Link: <...>; rel="deprecation"

11-5. 廃止のプロセス

1. 新しい形を追加し、両方を並行提供する 2. ドキュメントで旧方式を「非推奨」と明記し、移行手順を書く 3. レスポンスに Deprecation / Sunset ヘッダを付ける 4. 利用状況を計測する（誰が・どのくらい使っているか。これが無いと止められない） 5. 主要な利用者に個別に連絡する 6. 猶予期間を置く（外部公開APIなら最低6ヶ月〜1年が一般的） 7. 一時的な停止テスト（Brownout）を短時間実施し、影響を可視化する 8. 廃止する

▸ 4番が最も重要

「誰が使っているか分からない機能は、永久に消せない」。
エンドポイント・フィールド単位の利用計測を最初から入れておくこと。Client識別子（User-Agent / API Key / Client-Version）をログに必ず残すと、廃止の判断が事実ベースでできるようになる。

✓ これだけ覚える

  • v2を作るコストは「作ること」ではなく「両方を保守し続けること」
  • 追加は概ね安全、削除・リネーム・型変更・必須化は破壊的
  • 「未知のフィールドは無視する」を最初に契約として明記する
  • 廃止には利用計測が必須。使用者が分からない機能は消せない

⇄ Trade-off

  • URLパスバージョン → 明快・デバッグしやすい / 同じリソースに複数URL、全体を丸ごと複製しがち
  • 日付バージョン → 段階移行が容易・Clientが固定できる / 変換層が蓄積し、実装が重くなる
  • v2を切る → 設計を刷新できる / 保守コストが倍増し、v1が消えない
  • 互換を維持し続ける → Clientが壊れない / 古い設計を引きずり、フィールドが増え続ける

✕ よくある失敗

  • 「誰も使っていないはず」で削除 — 必ず誰かが使っている
  • バリデーションをこっそり厳しくする — 昨日まで通っていたリクエストが落ちる。破壊的変更だと認識されにくい
  • v2を作って、v1にバグ修正を入れ忘れる — 古い利用者だけ壊れたままになる
  • Enum値を黙って追加する — Clientのswitchが未知の値で落ちる（→ 12章）

? 設計時に自問する質問

  • この変更で、更新していないClientは壊れるか
  • v2を作らずに、追加だけで実現できないか
  • このフィールド/エンドポイントを誰がどれだけ使っているか、今すぐ分かるか
  • 廃止の告知先リストはあるか

12 API Evolution — 変更がClientに何をするか

結論: 「Serverだけ変更すればよい」変更は、ほとんど存在しない。Clientのコードがどう書かれているかを想像できないと、安全な変更と危険な変更を区別できない。

12-1. Enum追加が壊す瞬間

✕ Clientの実装（よくある形）

✓ 未知の値に耐える実装

  • だがこれはClient側の実装の話。Server側から強制はできない

✓ Server側でできること

  • 契約に明記する — 「statusの値は将来追加されうる。未知の値は汎用として扱うこと」をドキュメントの冒頭に書く
  • 最初からその他の値を混ぜておく — リリース時点から未知の値がありうると分かる状態にすると、Clientが最初からフォールバックを書く
  • 表示用テキストを一緒に返す — {"status": "partially_shipped", "status_label": "一部発送済み"}。Clientがマッピングを持たなくて済むので、追加が安全になる
  • グルーピングを併せて返す — {"status": "partially_shipped", "status_group": "in_progress"}。粗い分類でClientが分岐できる

12-2. 変更の種類と、Clientに起きること

変更Clientで起きること安全にする方法
Responseにフィールド追加通常は無視される。厳格なパーサだとエラー契約に「未知は無視」と明記。大きなデータはオプトインに
Responseからフィールド削除nullアクセスでクラッシュ、または空表示両方返す期間を置き、利用ゼロを確認してから削除

12-3. 最初に宣言しておくべき「進化の契約」

▲ このポリシーが無いと何が起きるか

  • フィールド1つ追加するのに関係者全員の確認が必要になる — 壊れるかどうかが誰にも分からないため
  • 結果としてAPIが凍結される。改善が止まり、新機能は別エンドポイントとして雑に増殖する
  • ポリシーは制約ではなく、変更する自由を確保するための宣言

  • 互換性ポリシーを先に宣言する。変更の自由はそれで得られる
  • 並び順・デフォルト値・レイテンシも暗黙の契約になっている

  • status だけ返す → APIが表示に関与しない / 値の追加でClientが壊れうる

✕ よくある失敗

  • Enum値を黙って追加 — Clientのswitchが落ちる。最も多い「悪意のない破壊」
  • レスポンスを「整理」してフィールド名を統一する — 善意のリファクタで全Clientを壊す
  • パフォーマンス改善でレスポンス構造を変える — 改善のつもりが破壊的変更
  • 互換性ポリシーを書かないまま数年運用 — 何も変えられないAPIになる

  • 「整理・統一」を理由に変えようとしていないか

▸ カーソルを不透明（Base64）にする理由

  • 中身を後から変更できる — ソートキーを変えても、Clientの実装に影響しない
  • Clientが勝手に生成するのを防ぐ — 「id=1000から取得」のような改ざんで、想定外のクエリを投げられない
  • 暗号化ではないので秘密情報は入れない。改ざん防止が必要なら署名を付ける
  • 期限や検索条件のハッシュを含めると、「古いカーソル」「条件が変わったカーソル」を検出して400にできる

13-3. 総件数をどうするか

⇄ COUNT は意外と高価

  • 毎回COUNTする → 正確 / 条件付きCOUNTは全件走査になりうる。一覧表示より重いことがある
  • 返さない → 高速 / 「全100件中1-20件」が表示できない
  • 概算を返す → 実用的（「約1,200件」）/ 正確な数が必要な業務では使えない
  • 上限付きCOUNT → COUNT(*) FROM (SELECT 1 ... LIMIT 1000) で「1000件以上」と表示。検索結果の表示では最も実務的

13-4. 選択の指針

どちらのページングにするか？ ├─ 無限スクロール / フィード / 新着が頻繁に入るか？ │ └─ YES → Cursor （Offsetは重複・欠落が必ず起きる） ├─ データ量が数万件を超えるか？ │ └─ YES → Cursor （深いOFFSETは線形に遅くなる） ├─ 「5ページ目へ」のようなジャンプが業務要件か？ │ └─ YES → Offset （管理画面の一覧など。件数上限とセットで） ├─ 外部公開APIか？ │ └─ YES → Cursor （後から仕様を変えやすい。不透明カーソルが効く） └─ Offset で十分 （管理画面・件数が少ない・静的） ※ 迷ったら Cursor。Offset → Cursor への移行は破壊的変更になる

✓ これだけ覚える

  • Offsetは「並びが変わらない」前提の仕組み。追加・削除で重複と欠落が起きる
  • Cursorは一意キーとの複合で順序を完全に決める。同値での取りこぼしを防ぐ
  • カーソルは不透明（Base64）にして、後から中身を変えられるようにする
  • limitには必ず上限。COUNTは想像より高価

⇄ Trade-off

  • Offset → ページジャンプ・総件数が自然 / 重複欠落、深いページで遅い
  • Cursor → 一貫性・一定の性能 / ジャンプ不可、実装が複雑、総件数が別途
  • 総件数を返す → UIが作りやすい / COUNTのコストが一覧取得を上回ることがある
  • 上限付きCOUNT → 高速で実用的 / 「1000件以上」という曖昧な表示になる

✕ よくある失敗

  • created_at だけをカーソルにする — 同時刻の行で重複・欠落する
  • ソート順が不定のままページング — ORDER BYが一意でないと、ページ間で順序が入れ替わる
  • limitに上限を設けない — limit=999999 でメモリを食い潰す
  • カーソルを生のIDにする — Clientが生成・改ざんでき、仕様変更もできなくなる

? 設計時に自問する質問

  • 1ページ目を見ている間にデータが追加されたら、2ページ目で何が起きるか
  • ORDER BY は一意に順序が決まる組み合わせになっているか
  • 3年後のデータ量で、最後のページを開いたら何秒かかるか
  • 総件数は本当に必要か。概算で足りないか

14 Bulk API

結論: 一括APIの設計は「全部成功か、全部失敗か」を選ぶことから始まる。ここを曖昧にしたまま作ると、「3件目で失敗したが1・2件目は登録された」という状態をClientが知る手段が無くなる。

14-1. 2つのモデル

観点Atomic Bulk（全か無か）Best Effort Bulk（部分成功）
意味1件でも失敗したら全件ロールバック成功したものは反映し、失敗したものを報告する
Status200/201 または 4xx/5xx（明快）207 Multi-Status、または200 + 各件の結果
Clientの後処理単純（全部やり直す）どれが成功したかを解析し、失敗分だけ再送する
向いている場面会計仕訳、在庫の一括振替、関連するデータ群CSVインポート、大量の独立したレコード
件数の上限トランザクションが長くなるので小さめ（〜100件）大きめでも可（〜1000件）
冪等性まとめて1つのIdempotency-Keyでよい件ごとに冪等キーが要ることが多い

▸ 選ぶ基準

  • 各要素が業務的に独立しているか — 独立していれば Best Effort。相互に依存する（合計が一致する必要がある等）なら Atomic
  • 部分的に成功した状態が、業務的に意味を持つか — 持たないなら Atomic 一択
  • Clientが失敗分だけ再送できるか — できないなら Best Effort にする意味がない

14-2. Best Effort の返し方

✕ 成否が分からない

  • どの1件が失敗したのか分からない
  • 再送しようがない。全部再送すると成功した2件が重複する
  • 理由も分からないので、ユーザーに何も伝えられない

✓ 件ごとに結果を返す

  • index でリクエストの何番目かが分かる
  • 各件に個別のStatusとエラー。単体APIと同じ構造にする
  • Clientは失敗分だけを抽出して再送できる

▸ index ではなく client_reference_id を推奨

Clientが送る各要素にClient側の識別子を持たせると、結果の突き合わせが確実になる。

14-3. 207 を使うべきか

⇄ 207 Multi-Status vs 200

  • 207を使う → 「部分成功がありうる」ことがStatusから分かる / WebDAV由来で馴染みが薄く、一部のHTTPクライアントやミドルウェアが素直に扱わないことがある
  • 常に200を返す → 扱いやすい / 監視上「成功」に見え、失敗が可視化されない
  • 折衷: 全件成功なら200、1件でも失敗があれば207。これで監視の成功率指標に部分失敗が現れる
  • 全件失敗でも200を返すのは避ける。この場合は 400/422 で返してよい

14-4. Atomic Bulk の実装

? Thinking Point

CSVで1万件の商品を登録したい。Atomic / Best Effort / それ以外、どれを選ぶか。

考えてから開く

答え: どちらでもなく、非同期ジョブにする（→ 15章）。

  • Atomicは不可能 — 1万件を1トランザクションに入れると、ロック時間が長すぎて他の処理を止める。タイムアウトもする
  • 同期のBest Effortも無理 — レスポンスが返るまで数分かかり、HTTPのタイムアウトに引っかかる。途中で切れたら結果が分からない
  • 正解の形: POST /v1/product-imports → 202 Accepted + ジョブID → 進捗を GET /v1/product-imports/{id} で確認 → 完了後にエラー一覧のCSVをダウンロード
  • 判断の線引き: 「同期で返せる件数」を先に決める（例: 100件）。それを超えるなら形が変わる。件数で設計が変わることを、最初に認識しておく

✓ これだけ覚える

  • Atomic か Best Effort かを最初に決める。曖昧なまま作らない
  • Best Effortは件ごとのStatusとエラーを返す。要約だけでは再送できない
  • client_ref で対応付けると確実
  • 件数の上限を設ける。上限を超える規模は非同期ジョブに形を変える

⇄ Trade-off

  • Atomic → Clientの処理が単純・整合性が保てる / 1件の不備で全件やり直し、大量件数に不向き
  • Best Effort → 大量処理に強い / Clientに再送ロジックが必要。部分状態の扱いが複雑
  • 207を返す → 部分失敗が可視化される / 扱いに慣れていないClientがある
  • 200で統一 → 扱いやすい / 監視上で失敗が見えなくなる

✕ よくある失敗

  • 「N件中M件成功」だけ返す — どれが失敗したか分からず再送できない
  • 部分失敗でも常に200 — 監視の成功率が100%のまま、データが欠ける
  • 件数の上限がない — 1万件のリクエストでタイムアウト・メモリ枯渇
  • 全体に1つの冪等キーだけ — 部分成功後の再送で、成功済みの分が重複する

? 設計時に自問する質問

  • 3件目で失敗したとき、1・2件目はどうなるべきか
  • Clientは失敗した分だけを再送できるか
  • 最大何件を想定しているか。その件数で何秒かかるか
  • 部分失敗は監視のダッシュボードに現れるか

15 Async API

結論: 「重いから非同期にする」のではなく、「レスポンス時間を保証できないから非同期にする」。処理時間が入力に依存する操作は、いつか必ずタイムアウトする。

15-1. 非同期にすべき判断

この処理を同期で返してよいか？ ├─ 処理時間は入力サイズに比例して増えるか？ │ └─ YES → 非同期を検討 （CSVインポート、一括更新、レポート生成） ├─ 外部サービスの応答を待つか？ │ └─ YES → 非同期を検討 （相手の遅延が自分のレイテンシになる） ├─ 最悪ケースで何秒かかるか？ │ ├─ 〜1秒 → 同期 │ ├─ 1〜10秒 → 同期でも可 （ただしタイムアウト設定とUXを設計する） │ ├─ 10〜30秒 → 非同期を強く推奨 （LBやプロキシの既定タイムアウトに近い） │ └─ 30秒〜 → 非同期一択 └─ 失敗したときに再実行が必要か？ └─ YES → 非同期 （ジョブなら再試行・状態管理ができる）

15-2. 標準形

▸ 設計上の要点

  • ジョブ取得APIは、ジョブが失敗しても200を返す — 「ジョブの状態を取得する」ことには成功している。ジョブの失敗を500で返すと、Clientがリトライループに入る
  • Retry-After でポーリング間隔を指示する — Clientが1秒ごとに叩くのを防ぐ。状態に応じて値を変える（queued中は長め、running後半は短め）
  • 受付時にもIdempotency-Keyを効かせる — 二重送信で同じジョブが2つ起動しないように（→ 8章）
  • 結果は別リソースにする — ジョブの状態と、生成された成果物（CSV・レポート）は別。成果物には有効期限を設ける
  • キャンセルを用意するか決める — DELETE /v1/jobs/{id} または POST /v1/jobs/{id}/cancellation。実行中の中断が可能かは実装次第なので、契約で明示する

15-3. ポーリング以外の通知手段

方式仕組み向いている場面注意
ポーリングClientがGETを繰り返す最も単純。外部公開APIの標準間隔の指示が無いと過剰アクセスになる
Webhook完了時にServerがClientへPOSTサーバー間連携受信エンドポイントが必要。署名・再送の設計が要る（→ 16章）
SSEサーバーからの一方向ストリーム進捗のリアルタイム表示接続を保持する。プロキシのバッファリングに注意
WebSocket双方向の常時接続チャット・協調編集ジョブ通知だけのために導入するのは重い
Long Polling結果が出るまでレスポンスを保留準リアルタイムが欲しいが実装を増やしたくない接続を長時間占有する。タイムアウト設計が要る

▸ 迷ったらポーリング

SSE・WebSocketは接続の維持・再接続・スケール（どのサーバーに繋がっているか）という運用課題を持ち込む。
「Retry-Afterに従ったポーリング」で要件が満たせるなら、それが最も安い。UXのために数秒の即時性が要るなら、進捗だけSSEにして結果はGETで取る、という分離も有効。

15-4. 非同期化で生まれる新しい責務

■ 「202を返して終わり」ではない

  • ジョブが永久にqueuedのまま — ワーカーが落ちていることを検知する仕組みが要る。created_at から一定時間経過したジョブをアラートする
  • Clientがポーリングをやめない — 完了後もポーリングし続ける実装。終端状態を明示し、Cache-Control で完了ジョブをキャッシュ可能にする
  • ジョブレコードが無限に増える — 保持期間（例: 30日）を決めて削除する
  • 成果物ファイルが残り続ける — ストレージコスト。有効期限付きの署名URLにする
  • ジョブの結果を誰が見てよいか — ジョブIDを知っていれば誰でも取得できる実装になりがち。ジョブにも所有者の認可が必要（→ 10章）

✓ これだけ覚える

  • 非同期化の基準は「重いか」ではなく「所要時間を保証できるか」
  • 202 + Location + status_url が標準形。202は「完了していない」の宣言
  • ジョブが失敗しても、ジョブ取得APIは200。500にするとリトライループになる
  • Retry-After でポーリング間隔を指示する

⇄ Trade-off

  • 非同期化する → タイムアウトしない・再試行できる / ジョブ管理・保持期間・認可・監視という新しい責務が生まれる
  • 同期のまま → 単純・即座に結果が分かる / 入力次第でタイムアウトし、失敗時の状態が不明になる
  • ポーリング → 単純・スケールしやすい / 無駄なリクエストと数秒の遅延
  • Webhook通知 → 即座・無駄がない / 受信側の実装が必要で、再送・署名の設計が要る

✕ よくある失敗

  • 202なのにClientが完了扱い — 契約とドキュメントで明示しないと必ず起きる
  • ジョブ失敗を500で返す — Clientが無限にリトライする
  • Retry-Afterを返さない — Clientが100ms間隔で叩き、自分でDoSを受ける
  • ジョブに認可をかけ忘れる — 他人のインポート結果が見える

? 設計時に自問する質問

  • この処理の最悪ケースは何秒か。入力サイズに比例するか
  • ワーカーが落ちてジョブが滞留したら、誰が気づくか
  • Clientはどの間隔でポーリングすればよいと分かるか
  • ジョブIDを知っている他人が結果を取得できてしまわないか

16 Webhook

結論: Webhookは「相手のサーバーの可用性に依存する、認証を逆転させたAPI」。通常のAPIで効いていた前提（相手が起きている・自分が認証する側・失敗したらClientが再送する）がすべて反転するため、専用の設計が要る。

16-1. 何が反転するのか

観点通常のAPI（Pull）Webhook（Push）
接続の向きClient → ServerServer → Client（立場が逆転）
認証する側Serverが Client を認証受信側が送信元を検証する必要がある
失敗時の責任Clientが再送を判断送信側が再送の責任を持つ
相手の可用性Serverは自分で管理できる相手のエンドポイントが落ちていることを前提にする
順序Clientが順に呼ぶので自明並行配送・再送により順序が入れ替わる
重複Clientのリトライのみ送信側の再送により必ず重複する

▸ Webhookの3原則

  1. At-Least-Once である — 少なくとも1回は届く。つまり2回以上届くことがある
  2. 順序は保証されない — created の後に updated が来るとは限らない
  3. いつ届くか分からない — 即座かもしれないし、相手の障害復旧後に数時間分まとめて届くかもしれない

この3つを受信側が知らないと、必ず事故が起きる。だから送信側はドキュメントの最初にこれを書く。

16-2. Producer（送信側）の設計

要素なぜ必要か
イベントID受信側が重複を排除する唯一の手段。再送時も同じIDを使うことが絶対条件
イベント種別（type）受信側が処理を分岐する。resource.action の形式が読みやすい
タイムスタンプリプレイ攻撃の防止（古すぎるリクエストを拒否）。署名対象に含める
署名送信元の検証。これが無いと誰でも偽のイベントを送れる
api_versionペイロードの形式を固定できる。受信側が追随できないまま形が変わるのを防ぐ
revision / version順序が入れ替わったときに、受信側が古い更新を捨てられる
occurred_at実際に起きた時刻。配送時刻とは別。集計のずれを防ぐ

16-3. 署名の作り方と検証

■ 署名検証でよくある誤り

  • パース後のJSONを再シリアライズして検証 — キーの順序や空白が変わり、絶対に一致しない。生のバイト列で検証する
  • タイムスタンプを見ていない — 過去の正当なリクエストをそのまま再送されると通ってしまう（リプレイ）
  • == で文字列比較 — タイミング攻撃の対象になる。定数時間比較を使う
  • 署名の検証自体を実装していない — エンドポイントのURLを知っていれば誰でも「決済成功」を送れる。実害の大きい脆弱性
  • ボディのサイズ制限がない — 巨大なボディでメモリを枯渇させられる

16-4. 再送と Dead Letter

図16.1 — 4xx（400/422）は再送しない。相手の実装が悪いので、何度送っても同じ

✓ Producerが用意すべきもの

  • 再送ポリシーの明記 — 何回・どの間隔・いつ諦めるか。受信側が復旧計画を立てられる
  • タイムアウトの明記 — 「5秒以内に応答しない場合は失敗とみなす」。受信側が重い処理を同期でやらない根拠になる
  • 配送ログの提供 — 管理画面で「いつ・何を送り・何が返ってきたか」を見せる。これが無いと受信側は調査できない
  • 手動再送の手段 — Dead Letterになったイベントを、受信側が復旧後に再送できるボタン or API
  • イベント一覧API — GET /v1/events?since=...。Webhookを取りこぼしても、Pullで復元できる経路を残す。これが最も重要な救済策
  • 送信元IPの固定 or 明示 — 受信側がファイアウォールで絞れるようにする

16-5. Consumer（受信側）の設計

▲ 「受信 → 記録 → 即200 → 非同期処理」にする理由

  • 送信側のタイムアウトは通常5〜30秒。同期で重い処理をすると、成功しているのにタイムアウト扱いで再送される
  • 再送されると同じ重い処理が並行して走る。負荷が雪だるま式に増える
  • 「受け取った」と「処理した」を分離すると、自分のペースで処理でき、失敗時も自分で再試行できる
  • ただし ③ の前に ② を確実に永続化すること。記録前に200を返すと、イベントを失う

16-6. 順序の問題

■ 順序が入れ替わると何が起きるか

送信された順: ① order.updated (status: "paid", revision: 2) 10:00:00 ② order.updated (status: "shipped", revision: 3) 10:00:01 ①が一時的に失敗して再送 → 到着順が逆転: ② を先に処理 → status = shipped ① を後で処理 → status = paid ← 発送済みが支払い済みに巻き戻る

✓ 3つの対処

  • revisionで古い更新を捨てる（推奨） — 受信側が現在のrevisionを保持し、if event.revision <= current.revision { skip }。最も単純で確実
  • イベントを「通知」として扱い、値はAPIで取り直す — ペイロードの値を信じず、GET /v1/orders/{id} で最新を取得する。順序問題が構造的に消える。ただしAPI呼び出しが増える
  • キー単位で順序を保証する — 送信側が同一リソースのイベントを直列化する。実装コストが高く、スループットが落ちる

? Thinking Point

「Webhookのペイロードに全データを入れる」か「IDだけ送ってAPIで取り直させる」か。

考えてから開く
観点Fat（全データ）Thin（IDのみ）
API呼び出し不要イベントごとに発生
順序問題影響を受ける（revisionが必要）常に最新を取るので影響なし
認可ペイロードに機微情報が乗る取得時に認可が効く
ペイロードの進化フィールド追加が受信側に影響しうるイベント形式が安定
相手の負荷低い通知のたびにAPIを叩かれる

実務の答え: 両方入れる。

  • ペイロードに現在の値 + revisionを入れつつ、「最新性が重要な処理ではAPIで取り直すこと」をドキュメントに書く
  • 受信側は、軽い処理（通知の表示）はペイロードで済ませ、お金や在庫が動く処理はAPIで取り直すという使い分けができる
  • 機微情報（カード番号・個人情報）はペイロードに含めない。Webhookのログは相手のサーバーに残る

16-7. Producer / Consumer チェックリスト

Producer（送る側）

  • イベントIDを付与し、再送時も同じIDを使う
  • HMAC署名 + タイムスタンプを付ける
  • 指数バックオフ + jitter で再送する
  • 4xxは再送しない、5xx/タイムアウトは再送する
  • 再送上限と Dead Letter を持つ
  • 配送ログを受信側に見せる
  • 手動再送の手段を用意する
  • イベント一覧APIで取りこぼしを復元できる
  • タイムアウト秒数を明記する
  • ペイロードのバージョンを持つ
  • 連続失敗が続く宛先は自動で停止し、通知する

Consumer（受け取る側）

  • 署名を必ず検証する（生ボディで、定数時間比較で）
  • タイムスタンプの鮮度を確認する
  • event_id で重複を排除する（UNIQUE制約）
  • 記録と副作用を同一トランザクションに入れる
  • 即座に2xxを返し、重い処理は非同期にする
  • 順序の入れ替わりを前提にする（revision比較）
  • 未知のイベント種別は無視して200を返す
  • ペイロードの未知フィールドを無視する
  • エンドポイントを推測されにくいURLにする
  • ボディサイズの上限を設ける
  • 処理失敗をログに残し、再処理できるようにする

✓ これだけ覚える

  • WebhookはAt-Least-Once・順序保証なし・到着時刻不定
  • 受信側は署名検証 → event_idで重複排除 → 即200 → 非同期処理
  • 署名は生ボディ + タイムスタンプ + 定数時間比較
  • 順序はrevisionで解決するか、APIで取り直す
  • 送信側はイベント一覧APIで取りこぼしを復元できる経路を必ず残す

⇄ Trade-off

  • Fatペイロード → API呼び出し不要で高速 / 順序問題と情報漏洩リスク、形式の進化が難しい
  • Thinペイロード → 常に最新・認可が効く / 通知のたびにAPI呼び出しが発生
  • 同期で処理する → 実装が単純 / タイムアウトで再送され、並行実行で負荷が増える
  • 受信して非同期処理 → 堅牢 / Inboxテーブルとワーカーが必要

✕ よくある失敗

  • 署名検証をしない — URLを知る誰もが「決済成功」を送れる
  • パース後のJSONで署名検証 — 一致せず、検証を諦めることになる
  • 重複排除をしない — 在庫が2回減る、メールが2回届く、二重に課金される
  • 同期で重い処理をして200が遅れる — 成功しているのに再送され、負荷が増幅する
  • 4xxを返して再送を期待する — 4xxは「送り直しても無駄」の意味。5xxを返すべき場面

? 設計時に自問する質問

  • 同じイベントが3回届いたら、何が3回起きるか
  • updated が created より先に届いたら、どうなるか
  • 受信側が3時間落ちていたら、そのイベントはどうなるか。復旧後に取り戻せるか
  • 署名検証を外したら、誰でも偽イベントを送れる状態になっていないか
  • 処理に10秒かかるとき、送信側のタイムアウトは何秒か

結論: 3つは「誰が誰と、どういう関係で通信するか」で選ぶ。技術的な優劣ではなく、Clientの数・変更速度・型の共有可能性が判断軸。

17-2. それぞれが解く問題

REST が解く問題

「誰が使うか分からない相手に、長期間安定した契約を提供する」。
HTTPの共通理解（キャッシュ・冪等性・Status）に乗れるため、Clientが既存の道具をそのまま使える。外部公開APIの既定値。

GraphQL が解く問題

「1つのバックエンドに対して、要求する形が画面ごとにバラバラ」。
画面追加のたびにAPIを作る、あるいは巨大なレスポンスを返す、という二択を回避できる。Client数が少なく形が安定しているなら、メリットは小さい。

gRPC が解く問題

「自社内のサービス間で、大量の通信を型安全かつ高速に行う」。
protoから両側のコードが生成されるため、契約のズレが起きない。相手も自分たちが管理している場合に最も効く。

併用が普通

外部公開はREST、社内サービス間はgRPC、フロント向けはGraphQLのBFF、という構成は一般的。「どれか1つを選ぶ」問題ではない。

17-3. 選択のDecision Tree

この通信の相手は誰か？ ├─ 不特定多数の外部開発者・パートナー企業 │ └─ REST （学習コスト・ツール・キャッシュ・安定性。GraphQLは相手に学習を強いる） ├─ 自社のフロントエンド（Web / モバイル） │ ├─ 画面ごとの要求データが大きく異なり、画面追加が頻繁か？ │ │ ├─ YES → GraphQL（またはBFF + REST） │ │ └─ NO → REST （多くの場合こちらで足りる） │ └─ モバイルで通信量が深刻な制約か？ │ └─ YES → GraphQL か fields パラメータ付きREST ├─ 自社内のサービス間通信 │ ├─ 高頻度・低レイテンシが要求されるか？ │ │ ├─ YES → gRPC │ │ └─ NO → REST でよい （運用の単純さが勝つ） │ └─ 双方向ストリーミングが必要か？ → YES → gRPC └─ 迷っている └─ REST （最も情報が多く、後から部分的に置き換えられる）

17-4. GraphQL を選ぶ前に知っておくこと

■ GraphQLで新たに発生する設計課題

  • N+1問題 — posts { author { name } } が投稿数だけクエリを発行する。DataLoaderによるバッチ化が必須
  • クエリの複雑さの制限 — 深くネストしたクエリでサーバーを落とせる。深さ制限・複雑度スコア・タイムアウトが必要
  • 認可がフィールド単位になる — 「このフィールドはこのロールだけ」を型定義に埋め込む必要がある。RESTのエンドポイント単位より難しい
  • キャッシュが効かない — POST一本なので、CDNもブラウザキャッシュも使えない。Persisted Queryなどの対策が要る
  • レート制限が難しい — 「リクエスト数」では制限にならない。クエリのコストで計算する必要がある
  • これらを解ける体制があるかで判断する。「Over-fetchが嫌だから」だけで選ぶと、運用で詰まる

✓ これだけ覚える

  • 選択軸は「相手が誰か」「型を共有できるか」「変更速度」
  • 外部公開はREST。HTTPの共通理解に乗れることが最大の価値
  • 社内サービス間はgRPCが効く。両側を自分たちが管理しているため
  • GraphQLはOver-fetchを解く代わりに、N+1・複雑度制限・認可・キャッシュという課題を持ち込む

⇄ Trade-off

  • REST → 単純・キャッシュ可・誰でも使える / Over/Under-fetch、画面ごとの最適化がしにくい
  • GraphQL → Clientが必要な形を取れる / 運用課題が多く、キャッシュとレート制限が難しい
  • gRPC → 高速・型安全・コード生成 / ブラウザ非対応、デバッグにツールが要る
  • 複数併用 → 適材適所 / 運用対象と学習コストが増える

✕ よくある失敗

  • 流行を理由に選ぶ — 解こうとしている問題が無いまま導入すると、複雑さだけ残る
  • GraphQLでN+1対策をしない — 1クエリで数百のDBアクセスが発生する
  • 外部公開APIをgRPCだけで提供 — 利用者が使えない。RESTのゲートウェイが要る
  • RESTでGraphQLの真似をする — ?fields= の無制限な実装でキャッシュもテストも破綻する

? 設計時に自問する質問

  • このAPIのClientは自分たちが管理しているか、他人か
  • 解こうとしている問題は何か。それは今あるRESTで解けないか
  • GraphQLを選ぶなら、N+1・複雑度制限・フィールド認可を誰が設計するか
  • キャッシュを捨ててよいか

Part 6

運用品質 — 契約を守り続けるための仕組み

設計したものが実装とズレていないか、攻撃に耐えるか、壊れたときに原因を追えるか。ここが無いと、良い設計も1年で崩れる。

18 OpenAPI

結論: OpenAPIの価値は「ドキュメントが自動生成されること」ではなく「契約が機械検証可能になること」。人が読む資料としてだけ使うなら、費用対効果は低い。

18-1. Contract First と Code First

観点Contract First（スキーマ先行）Code First（コード先行）
流れYAMLを書く → サーバー/Clientのコードを生成実装を書く → アノテーションからYAMLを生成
設計の議論実装前にレビューできる実装後なので、指摘が手戻りになる
並行開発フロントとバックが同時に始められる（モックが作れる）バックエンドの実装待ちになる
ズレの発生実装がスキーマから外れる可能性（検証で防ぐ）コードが真実なのでズレない
YAMLの保守巨大なYAMLの管理コスト不要
向いている場面複数チーム・外部公開・API設計が主戦場小規模・単一チーム・素早く作る

▸ 実務での折衷

  • Code Firstで生成しつつ、CIでスキーマの破壊的変更を検出する — 生成されたYAMLをリポジトリにコミットし、差分をレビュー対象にする。保守コストが低く、変更に気づける
  • 重要なAPIだけContract First — 外部公開する部分、複数チームが関わる部分だけ先に契約を決める
  • どちらでもよいが、「スキーマがCIで検証されているか」だけは満たす。手書きのドキュメントは必ず腐る

18-2. スキーマから得られるもの

用途得られる価値注意
ドキュメント生成常に最新。手書きドキュメントの腐敗を防ぐ生成しただけでは読みやすくない。説明・例は手で書く
Client SDK生成型付きクライアント。手書きのHTTP呼び出しが消える生成コードの品質は言語・ツールによる差が大きい
モックサーバーフロントが実装を待たずに開発できるモックの挙動と実装がズレることがある
リクエスト/レスポンス検証テストで「契約通りか」を自動検証できる本番でのレスポンス検証は性能に影響する
破壊的変更の検出CIで差分を検査し、Breakingならビルドを落とす専用ツール（oasdiff等）が必要
Lint命名規則・必須項目・例の有無を自動チェックルールの合意が先に必要

✓ 最も投資対効果が高いのは「破壊的変更の検出」

CIのパイプライン例: 1. コードからOpenAPIを生成 2. main ブランチのスキーマと比較（oasdiff --fail-on-diff breaking） 3. 破壊的変更を検出したら: ・PRにコメントで「この変更はBreakingです」と表示 ・意図的な場合はラベル（breaking-change-approved）で通す 4. マージ時にスキーマをコミット 効果: 11・12章で挙げた「悪意のない破壊」を、レビュー前に機械が発見する

18-3. 書くべきこと・書かれないこと

✕ 型だけのスキーマ

  • いつ何のエラーが返るか分からない
  • Idempotency-Key が必要かどうか書かれていない
  • 例が無く、実際のリクエストが想像できない

✓ 契約として使えるスキーマ

■ スキーマに書けないので、別途書く必要があるもの

  • 冪等性の保証範囲 — どのエンドポイントが冪等か、キーの有効期間は何時間か
  • 互換性ポリシー — 何が予告なく変わり、何が事前告知されるか（→ 12章）
  • レート制限 — 単位・上限・超過時の挙動
  • 並び順の保証 — デフォルトの順序を保証するのか否か
  • 結果整合性 — 「作成直後に一覧に出ないことがある」といった遅延の有無
  • これらは「APIガイド」として、スキーマとは別のドキュメントに書く。ここが抜けているAPIは、型が正しくても使いにくい

✓ これだけ覚える

  • OpenAPIの価値は「契約が機械検証可能になること」
  • 最も効くのはCIでの破壊的変更検出
  • Contract / Code どちらでもよいが、スキーマをリポジトリで管理し差分をレビューする
  • 冪等性・互換性ポリシー・レート制限はスキーマに書けない。別途ガイドを書く

⇄ Trade-off

  • Contract First → 設計を先にレビューでき、並行開発できる / YAMLの保守と実装とのズレ
  • Code First → ズレない・保守が楽 / 設計レビューが実装後になる
  • SDKを生成する → Clientの実装が楽・型安全 / 生成物の品質差、生成の運用が必要
  • 本番でレスポンス検証 → 契約違反を確実に検出 / レイテンシとCPUのコスト

✕ よくある失敗

  • スキーマを作ったが誰も見ない — 生成して満足し、CIに組み込まない
  • エラーレスポンスを定義しない — 正常系だけのスキーマは契約として不完全
  • 例を書かない — 型だけでは使い方が分からない
  • 手書きドキュメントと二重管理 — 必ず片方が古くなる

? 設計時に自問する質問

  • このスキーマはCIで検証されているか。ただの資料になっていないか
  • エラーレスポンスとエラーコードは全部定義されているか
  • 冪等性・レート制限・互換性ポリシーはどこに書いてあるか
  • 初めて使う人が、例を見て最初のリクエストを送れるか

19 Security

結論: API特有の脆弱性は「認証は通っているが、認可が足りない」ものが大半。画面が無いぶん、UIで隠していたものがそのまま露出する。

19-1. BOLA（Broken Object Level Authorization）

✕ 認証だけして所有者を見ない

  • UIにはリンクが無いので、開発中は気づかない
  • 連番IDだと全件を順に取得できる

✓ 所有者を条件に含める

  • SQLの WHERE に条件が入るので構造的に漏れない
  • 404を返して存在を隠す（→ 5章）

▸ 検出方法

  • テストで機械的に潰す — 「ユーザーAのリソースに、ユーザーBのトークンでアクセスして404/403になる」テストを全エンドポイントに書く
  • 一覧APIも必ずテストする — 他人のデータが含まれないこと（→ 10章）
  • IDを推測しにくくするのは補助的な対策 — ULID化は有効だが、認可の代わりにはならない

19-2. Mass Assignment

✕ リクエストをそのままモデルに流す

✓ 受け取る項目を明示する

  • 許可リスト方式。禁止リストは必ず漏れる
  • 権限変更は別エンドポイント + 別の認可にする

19-3. その他の主要リスク

リスク起きること対策
Sensitive Data Exposure内部専用フィールド・他人の個人情報・内部メモがレスポンスに混入レスポンスDTOを明示的に定義する（→ 1章）。モデルを直接返さない
Excessive Data ExposureClientが画面で隠しているだけで、APIは全部返しているUIでの非表示は対策ではない。APIレベルで返さない
Rate Limitの不備総当たり攻撃、スクレイピング、意図しない負荷認証前後で別々の制限。429 + Retry-After + RateLimit-*
InjectionSQL / NoSQL / コマンドインジェクションプレースホルダ。sortやfilterのカラム名はホワイトリスト（→ 4章）
SSRF「URLを指定してインポート」機能で内部ネットワークを叩かれるURLのスキーム・ホストを許可リストで制限。内部IPを拒否
リソース枯渇巨大なリクエスト、深いネスト、大量の配列ボディサイズ上限、配列長上限、JSONの深さ制限、タイムアウト
アカウント列挙エラーの差分でアカウントの存在が分かるログイン失敗は常に同じメッセージ・同じ応答時間に近づける
CORS設定の誤りAccess-Control-Allow-Origin: * + 認証情報の許可オリジンを明示的に列挙する。ワイルドカードと認証情報は併用しない

19-4. Rate Limit の設計

▸ 制限の単位を分ける

  • 認証前（IPベース） — ログイン・登録・パスワードリセット。総当たり対策。厳しめに
  • 認証後（ユーザー/APIキーベース） — 通常の利用。IPベースだと社内NATで共倒れになる
  • コストの高いエンドポイントは個別に — 検索・集計・エクスポートは別枠で厳しく
  • 成功と失敗で重みを変える — 認証失敗は重くカウントする
  • 制限に達したことをユーザーに伝える — 無言で遅くすると、Clientはリトライを増やして悪化させる

✓ これだけ覚える

  • BOLA（所有者チェック漏れ）がAPI脆弱性の最多。構造で防ぐ
  • Mass Assignmentは許可リスト方式のDTOで防ぐ。モデルに直接デコードしない
  • UIで隠すのは対策ではない。APIが返さないことが対策
  • Rate Limitは認証前後で単位を分ける。429 + Retry-After を返す

⇄ Trade-off

  • 厳しいRate Limit → 攻撃と過負荷を防げる / 正規利用者が引っかかる。バッチ処理が止まる
  • 詳細なエラー → 開発しやすい / 攻撃者に情報を与える
  • レスポンスDTOを個別定義 → 漏洩しない / 型定義が増える
  • モデルを直接返す → 実装が速い / 内部フィールドの漏洩が起きる

✕ よくある失敗

  • 認証だけで満足する — ログインできる全員が全データを見られる
  • フロントで項目を隠して対策とする — APIを直接叩けば全部見える
  • 管理者APIに認可を付け忘れる — 「管理画面からしか呼ばれない」は前提にならない
  • ログイン失敗で理由を詳しく返す — アカウント列挙に使われる

? 設計時に自問する質問

  • 他人のIDを入れたら何が返るか。全エンドポイントで確認したか
  • このリクエストで、想定外のフィールドを更新できないか
  • このレスポンスに、画面では表示していない項目が含まれていないか
  • このエンドポイントを1秒間に1000回叩かれたらどうなるか

20 Observability

結論: 「ユーザーから『エラーが出た』と言われて、5分以内に該当リクエストを特定できるか」。これができない状態は、設計が終わっていない。

20-1. Request ID と Trace ID

ID範囲用途
Request ID1つのHTTPリクエストエラーレスポンスに含めて返し、問い合わせ時に特定する
Trace IDサービスをまたいだ一連の処理マイクロサービス間で伝播させ、全体のフローを追う
Span ID処理の一区間どの処理に時間がかかったかを分解する
Correlation ID業務的な一連の処理非同期・Webhookをまたいで「この注文に関する全処理」を追う

20-2. 構造化ログに何を入れるか

■ ログに入れてはいけないもの

  • Authorizationヘッダ・Cookie・APIキー — マスクする仕組みをミドルウェアに入れる
  • リクエストボディをそのまま — パスワード・カード番号・個人情報が入る。必要ならフィールドを選んで記録する
  • ID付きの生パス — /v1/orders/01J8ZQ... をそのままラベルにすると、メトリクスの基数が爆発する。ルートパターンを使う

20-3. 見るべき指標

指標取り方気をつけること
Error Rate5xx / 全リクエスト、エンドポイント別4xxは分けて見る。4xxの急増はClientの不具合か攻撃のサイン
Latencyp50 / p95 / p99平均値は使わない。一部のユーザーだけが遅い状況が平均では見えない
ThroughputRPS、エンドポイント別急減は上流の障害、急増は攻撃かリトライストームの可能性
SaturationDB接続プール、ワーカーのキュー長レイテンシが悪化する前に現れる先行指標
業務指標注文数、決済成功率、Webhook配送成功率技術指標が正常でも業務が壊れていることがある

▲ 「5xxが0なのに壊れている」パターン

  • 200 + error=true を返している — 監視上は完全に正常（→ 21章）
  • 部分失敗のBulkで常に200 — データが欠けても気づかない（→ 14章）
  • Webhookが全部Dead Letterに落ちている — 自分のAPIは200を返し続けている
  • 非同期ジョブが全部failedで完了 — 受付の202は成功している
  • 対策: 業務的な成功を数える。「注文が作成された件数」が平常時より落ちていないかを監視する

20-4. 問い合わせから調査までの動線

ユーザー「昨日の15時ごろ、注文しようとしたらエラーになった」 ① エラー画面に request_id が表示されていたか？ YES → ログを request_id で検索。1秒で特定できる NO → 時刻 + actor_id + エンドポイントで絞り込む（数分〜数十分） ② ログから trace_id を取得 → 分散トレースで全サービスの処理を見る ③ どこで失敗したか特定 ・DBのタイムアウト？ 外部決済の遅延？ バリデーション？ ④ 再発防止 ・そのエラーがアラート対象になっていたか ・なっていなかったなら、なぜ検知できなかったのか 設計時にやること: ①でYESになるようにしておく → エラーレスポンスに request_id を必ず含め、 Client側にも「エラー時はこのIDを表示する」と依頼する

✓ これだけ覚える

  • エラーレスポンスに request_id を必ず含める。調査の起点になる
  • ログは構造化 + ルートパターン。生パスをラベルにしない
  • レイテンシはp95/p99で見る。平均は実態を隠す
  • 技術指標が正常でも業務は壊れうる。業務的な成功数を監視する

⇄ Trade-off

  • 全リクエストをトレース → 調査が容易 / コストとストレージが大きい
  • サンプリング → コストを抑えられる / 調べたいリクエストが記録されていない
  • ボディをログに残す → 再現が容易 / 個人情報・機密情報の保管リスク
  • ログを増やす → 情報が揃う / ノイズで重要なログが埋もれ、コストも増える

✕ よくある失敗

  • エラーに識別子が無い — 問い合わせを調査できない
  • 4xxと5xxを区別せず監視 — Clientのバグでアラートが鳴り続け、無視されるようになる
  • レイテンシを平均で見る — 一部ユーザーの深刻な遅延に気づけない
  • Authorizationヘッダをログに残す — ログが漏れた瞬間に全アカウントが危険にさらされる

? 設計時に自問する質問

  • 「エラーが出た」という問い合わせから、5分で該当リクエストを特定できるか
  • このAPIが全部200を返しながら壊れる方法はあるか
  • ログに秘密情報が混入していないか。マスクは仕組みになっているか
  • Clientのバージョン別に、エラー率とリクエスト数を出せるか

実践 — アンチパターンと通し設計

最後に、現場で繰り返し現れる12の失敗形と、EC APIをゼロから設計する通し演習。途中で「悪いAPI」を提示するので、何が問題かを自分で挙げてから読み進めること。

21 アンチパターン12

共通する構造: 短期的には動くが、Clientが増えたとき・障害が起きたとき・変更したいときに初めて代償が現れる。

① GETで更新する

■ GET /api/orders/123/cancel

  • 起きること: ブラウザのプリフェッチ、クローラ、リンクプレビュー、プロキシのキャッシュで意図せず実行される（→ 3章）
  • 直し方: POST /v1/orders/123/cancellation。既存Clientがあるなら、GETを残しつつ内部で「確認画面を返すだけ」に変え、実行はPOSTに移す

② 何でもPOST

■ POST /api/getOrderList POST /api/deleteOrder

  • 起きること: キャッシュが効かない。冪等性が無いのでリトライ設計ができない。エンドポイントが無限に増える
  • 直し方: 名詞 + Method に置き換える。全面書き換えが無理なら、新機能から順次リソース指向にする（→ 2章）

③ 200 + error=true

✕ 常に200

  • 監視のエラー率が常に0%。障害が可視化されない
  • SDKやHTTPクライアントのエラーハンドリングが全く機能しない
  • リトライの判断ができない。CDN・プロキシがエラーをキャッシュする
  • Clientは全レスポンスで success を見る必要があり、1箇所忘れると無言で壊れる

✓ Statusで表す

④ DB Modelをそのままレスポンスにする

■ ORMの構造体をそのままJSON化

  • 起きること: カラム名の変更がAPIの破壊的変更になる。内部フィールド（internal_memo, deleted_at, password_hash）が漏れる（→ 1・19章）
  • 直し方: レスポンス専用のDTOを定義する。「返すフィールドを明示的に列挙する」だけで、漏洩の大半が防げる

⑤ Clientに内部エラーを漏らす

■ 例外メッセージ・スタックトレース・SQLをそのまま返す

  • 起きること: テーブル構造・ミドルウェア・ファイルパスが漏れる。攻撃の下調べに使われる（→ 6章）
  • 直し方: 未知のエラーは一律 500 + INTERNAL_ERROR + request_id。詳細はログにだけ出す

⑥ Boolean Parameterの乱立

✕ フラグで挙動を変える

✓ 意味のある軸にまとめる

⑦ 巨大レスポンス

■ 1回で全部返す

  • 起きること: モバイルでのパース時間とメモリ。データが増えるとある日突然タイムアウトする（線形に悪化し、閾値を超えた瞬間に壊れる）
  • 直し方: 最初からページングを入れる（→ 13章）。「今は100件だから大丈夫」は、3年後に必ず破綻する
  • 補助: fields による部分レスポンス、圧縮、不要な関連の同梱をやめる

⑧ N+1 API

✕ 一覧を取ってから1件ずつ

✓ 同梱かバッチ取得を用意する

  • サーバー側でN+1クエリにならないよう、まとめて取得する実装が前提

⑨ Chatty API

■ 1つの業務を完了するのに何往復も必要

注文を作るために必要なリクエスト: 1. POST /v1/orders （空の注文を作る） 2. POST /v1/orders/1/items （商品を追加）× 商品数 3. PUT /v1/orders/1/address （配送先を設定） 4. POST /v1/orders/1/confirm （確定） 問題: ・途中で失敗すると「中途半端な注文」が残る ・各ステップの間に他の操作が割り込む ・モバイルでは往復のたびに数百msかかる
  • 直し方: 業務的に1つの操作なら、1リクエストにする。POST /v1/orders で items も address も一度に受け取る
  • 逆に、カートのように「段階的に組み立てる」ことが業務要件なら、多段でよい。判断軸は「途中の状態に業務的な意味があるか」

⑩ 悪意のないBreaking Change

■ 「改善」のつもりの変更

  • フィールド名を統一する（name → product_name）
  • Enumに新しい値を追加する
  • レスポンスを「整理」して構造を変える
  • バリデーションを厳しくして不正データを防ぐ
  • 直し方: 互換性ポリシーを先に宣言し、CIで破壊的変更を検出する（→ 11・12・18章）

⑪ Authorization漏れ

■ 認証だけで安心する

  • 起きること: 他人の注文・他社のデータが見える。API脆弱性の最多（→ 10・19章）
  • 特に見落とされる箇所: 一覧API、非同期ジョブの結果取得、ファイルダウンロードURL、管理者向けエンドポイント、Webhookの再送API
  • 直し方: Repositoryのインターフェースに actor を必須引数として強制し、単独でIDだけで引けるメソッドを作らない

⑫ リトライで二重登録

■ 冪等性の設計が無い

  • 起きること: 二重注文、二重課金、在庫の二重減算。ユーザーは「押していない」と言い、ログには2回のリクエストが残っている
  • よくある誤解: 「フロントでボタンを二度押しできないようにしたから大丈夫」— ネットワークのリトライ、プロキシの再送、ユーザーの再読み込みは防げない
  • 直し方: Idempotency-Key、または一意制約（→ 8章）

✓ これだけ覚える

  • 12個の本質は「Clientが増え、障害が起き、変更が必要になったとき」に現れる
  • HTTPの意味を捨てると（GETで更新、200でエラー）、周辺のツールがすべて機能しなくなる
  • フロントで防いでいるものは、APIを直接叩かれれば防げていない
  • 「今は少ないから大丈夫」は、閾値を超えた日に突然壊れる

⇄ Trade-off

  • 1リクエストに集約 → 往復が減り原子性が保てる / リクエストが大きく複雑になる
  • 多段に分ける → 各操作が単純 / 中途半端な状態と往復コスト
  • include で同梱 → N+1を回避 / レスポンスが肥大し、サーバー側の実装が複雑
  • 専用エンドポイント → 最適化しやすい / 画面の数だけAPIが増える

✕ よくある失敗

  • 「社内APIだから」で全部を省略 — 社内APIも数年使われ、いつか外部に出る
  • アンチパターンを知っていても、締切で選ぶ — 選ぶのは構わないが、記録を残して後で返済する
  • 既存のアンチパターンに合わせて新しいAPIも作る — 一貫性の名の下に負債が増殖する

? 設計時に自問する質問

  • このAPIが全部200を返しながら壊れる方法はあるか
  • フロントの制御を外して直接叩いたら、何ができてしまうか
  • この画面を表示するのに、何リクエスト必要か
  • データが100倍になったとき、最初に壊れるのはどのエンドポイントか

22 ケーススタディ — EC APIを設計する

Product / Cart / Order / Payment を、Resource → Endpoint → Request/Response → Error → Authorization → Idempotency → Concurrency まで通しで設計する。途中の「悪いAPI」は、必ず自分で問題点を挙げてから読み進めること。

Step 0. 要件

● 前提

・顧客はWebとiOS/Androidアプリから利用する（モバイルは更新が遅れる） ・商品を検索し、カートに入れ、注文し、外部サービスで決済する ・在庫は売り越してはいけない ・注文のキャンセルは発送前のみ。誰がいつキャンセルしたか記録が必要 ・決済結果はWebhookで非同期に届くこともある ・管理者は全注文を閲覧できるが、顧客は自分の注文のみ

Step 1. Product — 検索と一覧

? Thinking Point 1 — この設計の問題点を3つ以上挙げよ

考えてから開く
  • POST で検索 — キャッシュ不可、ブックマーク不可、Safetyを失っている（→ 3章）
  • sortColumn を自由に受け取る — 索引のないカラムで全件ソート、injectionの入口（→ 4章）
  • forAdmin フラグ — Clientの自己申告で権限が変わる。true を送れば管理者用データが返る（→ 10章）
  • cost / supplier_id が漏れている — 原価と仕入先は顧客に見せてはいけない（→ 19章）
  • is_deleted — 内部の論理削除フラグが契約になっている（→ 1章）
  • success フィールド — HTTPが表すべきものを二重に持っている（→ 5章）
  • price が浮動小数点 — 金額の丸め誤差。通貨も不明（→ 1章）
  • 連番ID — 総商品数が推測でき、全件取得も容易
  • boolean パラメータ3本 — 組み合わせ爆発（→ 21章）
  • 日時形式が独自 — タイムゾーン不明（→ 2章）
  • perPage=100 に上限がない — 10000を送られたら（→ 4章）

✓ 設計判断

  • 在庫数ではなく availability を返す — 「残り3個」を見せるかは業務判断。数値を出すと競合に在庫回転を読まれる。必要なら low_stock に閾値を持たせる
  • 管理者向けは別エンドポイント — GET /v1/admin/products。フラグで切り替えない。認可もレスポンスの形も違うため
  • Cursor pagination — 商品数が多く、並び替えもあるため（→ 13章）
  • ETag を返す — 商品詳細はキャッシュが効く。GET /v1/products/{id} に ETag + Cache-Control: private, max-age=60

Step 2. Cart — シングルトンリソース

カートのエンドポイント

GET/v1/cart自分のカート。IDを取らない（→ 2章）
PUT/v1/cart/items/{product_id}商品を入れる / 数量を設定する（冪等）
DELETE/v1/cart/items/{product_id}取り除く（冪等）
DELETE/v1/cart空にする

▲ なぜ POST /cart/items ではなく PUT /cart/items/{product_id} か

  • 冪等になる。電波が悪い場所で「カートに追加」を押してタイムアウト → 再送されても、数量が2倍にならない（→ 8章）
  • 「カート内の商品は product_id で一意」という業務ルールが、URLの構造として表現される
  • ボディは {"quantity": 2} という「代入」。{"delta": +1} にすると冪等性が壊れる（→ 3章）

▸ カートの金額は「見積もり」であることを明示する

カート表示時の価格と、注文確定時の価格は一致しないことがある（価格改定・クーポン失効・在庫切れ）。
確定金額は注文作成時に決まるので、ドキュメントに「カートの金額は参考値」と書き、Clientには注文確認画面で再取得させる。ここを曖昧にすると「表示と請求額が違う」というクレームになる。

Step 3. Order — 最も設計が集中する場所

✓ 各フィールドの設計意図

  • items に unit_price を含めない — 価格はサーバーが決める。Clientから価格を受け取ると改ざんされる
  • expected_total を受け取る — Clientが表示していた金額。サーバーの計算と一致しなければ 409 を返す。「知らないうちに値上がりしていた」を防ぐ（Stripeなどが採用する手法）
  • address_id で参照 — 住所そのものを送らせない。ただしサーバー側では注文に値としてコピーして凍結する（データモデル側の責務）
  • Idempotency-Key は画面表示時に生成 — 送信ボタンごとではない（→ 8章）

? Thinking Point 2

注文作成のレスポンスは 201 でよいか。決済がまだ完了していないのに。

考えてから開く

「何のリソースを作ったか」で決まる。

  • 201 が正しいケース: 注文（Order）というリソースは確かに作成された。決済はその属性の一つ。payment_status: "processing" で状態を伝える。Clientは注文IDを受け取り、状態をポーリングするか、Webhook/プッシュ通知を待つ
  • 202 を選ぶケース: 「注文の受付だけして、実際の注文作成は非同期」という設計。在庫引当も決済もこれから、という場合。この場合レスポンスは注文ではなくジョブになる
  • 最も悪いのは 200 で返して、Clientが「完了した」と思うこと
  • 実務の推奨: 201 + payment_status を明示。「注文は作られたが、決済は進行中」という状態がスキーマ上に存在することが重要（→ 8・15章）

Step 4. キャンセルと並行性

注文の操作

PATCH/v1/orders/{id} {"status": "cancelled"}採用しない（→ 2章）

▲ なぜキャンセルにも Idempotency-Key と If-Match の両方か

  • Idempotency-Key は「同じ操作の再送」を吸収する。ネットワーク再送で返金が2回走らないように
  • If-Match は「他人が間に操作した」ことを検出する。顧客がキャンセルしようとしている間に、管理者が発送処理をしていた場合
  • 両者は防いでいるものが違う。片方だけでは不十分（→ 8・9章）
  • 実務では If-Match を任意にすることも多い。その場合はサーバー側で状態遷移を厳密にチェックし、409で弾く

▸ 顧客用と管理者用でエンドポイントを分ける理由

  • 返すフィールドが違う — 管理者には原価・仕入先・内部メモを返す。同じエンドポイントだとフィールド単位の出し分けが必要になり、漏洩しやすい
  • 認可の形が違う — 顧客は「自分のもの」、管理者は「全件だが自テナント内」。同じコードで両方を扱うと条件が複雑になり、バグが入る
  • レート制限・監査要件が違う — 管理者の操作は全件ログに残す必要がある
  • 分けるとエンドポイント数は増えるが、認可の事故は確実に減る

? Thinking Point 3 — 最後の問い

この設計で、モバイルアプリが「注文ボタンを押したがタイムアウトした」とき、ユーザーの画面には何を出すべきか。

考えてから開く

「注文に失敗しました。もう一度お試しください」は誤り。 注文が成立している可能性があるため。

  • 正しい挙動: 同じ Idempotency-Key で自動的に再送する。冪等なので、成立済みなら同じ注文が返り、未成立なら作成される
  • 再送も失敗したら「注文の状態を確認しています」と表示し、GET /v1/orders?limit=1 で直近の注文を確認する
  • それでも不明なら「注文が完了しているか確認中です。注文履歴をご確認ください」と案内する。「失敗しました」と断定して再操作を促すのが最悪（二重注文の原因）
  • ここで分かること: API設計はClientのUX設計と地続き。冪等性を用意しても、Clientがそれを使うUIになっていなければ事故は防げない。APIドキュメントに「タイムアウト時の推奨挙動」を書くのは、設計の一部
