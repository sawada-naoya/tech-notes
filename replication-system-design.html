00 はじめに — この本の例えの体系

専門用語は全部、現実世界のものに置き換えます。以下のマッピングは全章で一貫して使うので、迷ったらここに戻ってください。中心の比喩は「銀行の本店と支店」です。

図0-1 本書の比喩体系。「本店＝書ける唯一の場所」「支店＝読める写し」「配達＝ログ転送」の3つを最初に固定する。

この本を読む前に持っておく1つの問い

レプリケーションの設計判断は、最後は必ずこの問いに還元される。

「この書き込みは、どこまで届いたら "終わった" と言ってよいのか？」

  • 自分のディスクに書けたら終わり → 速い。でもそのサーバが燃えたらデータは消える（async）
  • 隣のサーバのメモリに届いたら終わり → まあまあ速い。同時に2台死ぬと消える（semi-sync）
  • 過半数のサーバのディスクに書けたら終わり → 遅い。でも少数派が全部死んでも残る（quorum / Raft / Paxos）
  • 全サーバに書けたら終わり → 最も安全に見えて、実は最も壊れやすい（1台でも遅いと全体が止まる）

この4択が、そのまま 耐久性・レイテンシ・可用性のトレードオフになる。7章で数字にする。

01 Replicationとは / なぜ必要なのか

レプリケーション＝「同じデータを、複数のマシンに、継続的に持ち続けること」。定義はこれだけ。難しいのは定義ではなく、複数持った瞬間に生まれる「どれが正しいのか」問題。この章はその出発点。

🏦 銀行の例え。 東京の本店に元帳が1冊だけある。全国の顧客が残高照会するたびに東京へ電話し、本店が火事になれば全記録が消える。だから支店に元帳の写しを置く。これがレプリケーション。
ただし置いた瞬間、こういう問題が生まれる: ①写しは常に少し古い（Lag）②本店が焼けたときどの支店が本店を名乗るか（Failover）③連絡が切れた支店が勝手に本店を名乗る（Split Brain）。この3つが本書の全て。

① この技術は何を解決するために生まれたのか

レプリケーションが解決するのは、実は4つの別々の問題。ここを混ぜて理解している人が非常に多い。「冗長化のため」だけだと思っていると、設計の半分を落とす。

  • 1. 可用性（Availability） — 1台死んでもサービスが続く。MTTR を人間の時間から機械の時間に落とす
  • 2. 耐久性（Durability） — ディスクが物理的に壊れてもデータが残る。RAIDは筐体単位、レプリケーションは建物単位で守る
  • 3. 読みのスケール（Read Scalability） — 読み専用の複製を増やして読みQPSを水平に伸ばす
  • 4. 地理的近接（Latency） — ユーザーの近くに複製を置く。これだけは他の手段で代替できない（光速は変えられない）

図1-1 4つの目的。面接で「なぜレプリケーションを入れますか」と聞かれたら、この4つのうちどれを狙うのかを明示すると設計が締まる。

② この技術がないと何が問題になるのか

レプリケーションが無い＝DBが1台だけの世界で何が壊れるかを、実際の数字で見る。ホテル予約サイト（月商5億円 / 平均5,000 req/s）を例にする。

図1-2 RTO/RPO の差。「98分 vs 23秒」「損失あり vs 0」。この2指標で経営に説明できると予算が通る。

③ 基本概念 — 5つの用語を先に固定する

Leader / Primary / Master書き込みを受け付ける唯一のノード。全部同義語（呼び方が製品で違うだけ）本店MySQL は source、PostgreSQL は primary、MongoDB は primary。「master/slave」は現在非推奨語

⑤ 実際のシステム構成でどう使われるのか

典型的な Web サービスの3層構成に、レプリケーションがどう入るか。重要なのは「アプリが接続先を2つ持つ」という点。ここを設計しないとレプリカを増やしても使われない。

図1-4 実務構成。レプリカには「Failover用」「読み分散用」「分析用」と役割があり、役割ごとに要求される lag が違う。

⑥ メリット

  • 可用性が桁で上がる — RTO が「人間の反応速度（分）」から「機械の検知速度（秒）」に落ちる
  • 読みが水平にスケールする — レプリカを足すだけ。アプリのロジック変更が（ほぼ）要らない
  • 重い処理を隔離できる — 分析クエリ・全件エクスポート・バックアップ取得を本番Leaderから追い出せる。これは実務で一番効く
  • アップグレードのダウンタイムを削れる — レプリカを先に新バージョンにして、切り替える（ローリング）
  • 地理的レイテンシを削れる — ユーザーの近くで読める。CDN が静的で解くことを、DB が動的データで解く
  • 副産物として CDC が手に入る — レプリケーションログは検索・キャッシュ・DWH の同期にも使える（9章）

⑦ デメリット・トレードオフ

⑧ 実務での利用例

  • 夜間バッチの隔離: 「月次集計が本番DBのCPUを食い潰す」→ 分析用レプリカに逃がす。最も費用対効果が高い導入理由
  • バックアップ取得: レプリカ側で mysqldump / スナップショットを取る。Leader のI/Oを汚さない
  • スキーマ変更のリハーサル: レプリカで先に ALTER を流し、時間と影響を測る
  • 検索インデックス同期: binlog → Debezium → Kafka → Elasticsearch。アプリ側に二重書きコードを書かなくて済む
  • DBのメジャーバージョンアップ: 論理レプリケーションで新バージョンにデータを流し、短時間の切替だけで済ませる（19章）

⑨ Googleレベルではどう設計されるか

  • 「レプリケーションは同期が既定」 — Spanner/Bigtable では、書き込みは Paxos の過半数同期が前提。非同期を選ばないことで「Lag をアプリに漏らさない」設計にしている（21章）
  • レプリカの配置は "障害ドメイン" で決める — 単に「3台」ではなく「3つの独立した電源・ネットワーク・ソフトウェアリリース波」に分ける。相関故障を切る設計
  • 故障は例外ではなく定常状態 — Jeff Dean の有名な「1年で1クラスタに起きること」リストの通り、数千台規模ではディスク故障・ラック障害は毎日起きる。Failover は非常時ではなく日常運転として設計する
  • レプリカ数はデータの重要度で変える — Colossus/GFS 系では、ホットなデータは複製数を上げ、コールドなデータは Erasure Coding（1.5倍程度の冗長度）に落とす。一律3コピーは素人設計
⑩ 面接 「なぜレプリケーションが必要なのか、30秒で説明してください」

模範解答の骨格:

「レプリケーションは4つの別々の目的で入れます。可用性・耐久性・読みのスケール・地理的レイテンシです。今回の要件では［どれ］が主目的なので、［構成］を選びます。
代償は一貫性です。レプリカは必ず遅れるので、『どの読み取りが古くても許されるか』をデータ種別ごとに決めるのが設計の本体になります。たとえば商品一覧はレプリカ、決済直後の残高表示は Leader、というように分けます。
また、レプリケーションは書き込みのスケールには効きません。書き込みが上限なら Sharding が必要です。」

面接官が見ているポイント:

  • 「冗長化のため」で終わらず、目的を分解できるか
  • 「一貫性を払う」というコストを自分から言えるか（言わないと減点）
  • レプリケーションと Sharding を混同していないか（最頻出の減点ポイント）
  • RPO/RTO という語を使えるか（ビジネス側と話せる証拠になる）

ありがちな失点: 「レプリカを増やせば性能が上がります」→ 読みだけです、と即座に訂正されて終わる。

02 複製 ≠ 分割 ≠ バックアップ

この3つの混同は、面接でも実務でも最も高頻度で致命的。「レプリカがあるからバックアップは要らない」は、データを失う考え方。ここで明確に切り分ける。

📚 図書館の例え。 複製（Replication）＝ 同じ蔵書を分館にも揃える。分割（Partitioning / Sharding）＝ あ〜さ行は本館、た〜わ行は分館に置いて、蔵書全体を分ける。バックアップ＝ 蔵書の状態を毎晩写真に撮って金庫に入れる。
違いが決定的に出るのは「司書が誤って本を全部処分した」とき。複製は分館でも同時に処分される（同じ命令が伝わるから）。バックアップだけが助けになる。

① この区別は何を解決するために必要なのか

3つは「守っている脅威」が違う。守備範囲を混同すると、守れているつもりの穴ができる。

図2-1 3者の違い。「レプリカがあるからバックアップ不要」は最も危険な誤解。守っている脅威が違う。

③ 基本概念 — 「シャードごとにレプリカを持つ」が標準形

図2-2 標準形。Vitess（YouTube）・MongoDB Sharded Cluster・DynamoDB は全部この構造。shard 内は Single Leader が主流。

⑩ 面接 「レプリケーションとシャーディングの違いは？ どちらを先に入れますか？」

模範解答: 「レプリケーションは同じデータを複数箇所に置く技術で、可用性・読みスケール・地理的近接を解きます。シャーディングはデータを分けて複数箇所に置く技術で、容量と書き込みスループットを解きます。
導入はレプリケーションが先です。理由は3つ。①ほとんどのサービスは読みが支配的で、レプリカで足りることが多い。②レプリケーションはアプリの変更がほぼ不要だが、シャーディングはクロスシャードのJOINとトランザクションという恒久的な設計制約を生む。③レプリケーションは可用性も同時に上がるが、シャーディングはむしろノード数が増えて障害確率が上がる。
書き込みが本当に1台の上限に達してから、シャードキーを慎重に選んで導入します。」

深掘り: 「では両方入れる場合の構成は？」
→ 「シャードごとにレプリカセットを持たせます。3 shard × 3 replica なら9ノード。ルーティング層（Vitess の VTGate、MongoDB の mongos）がシャードキーから shard を決め、その中で Leader/Replica を選びます。Failover はシャード単位で独立して起きるのが重要な性質です。」

追い打ち: 「レプリカがあればバックアップは要りませんよね？」（これは引っかけ）
→ 「いいえ。レプリケーションは論理的な誤りも忠実に複製します。DROP TABLE やアプリのバグによる不正な更新は、全レプリカに0.1秒で伝わります。守っている脅威が違うので、バックアップ（できれば別アカウント・イミュータブル）は独立して必要です。加えて復元テストをしていないバックアップは存在しないのと同じです。」

03 Single Leader（Leader-Follower）

世の中のデータベースの9割はこれ。MySQL・PostgreSQL・MongoDB・Kafka・etcd・Spanner（split単位）・DynamoDB（partition単位）— 全部 Single Leader。「まずこれを選ぶ、外す理由があるときだけ他を検討する」が正しい態度。

🏦 銀行の例え。 全国どの支店で照会してもいいが、記帳できるのは本店だけ。支店に「入金したい」と言うと、支店は本店に電話をつなぐ。本店が記帳し、その内容を全支店に配る。
なぜこんな面倒なことをするのか？ 「順番」を1箇所で決めるため。同じ口座に東京と大阪から同時に出金が来ても、本店が受けた順に処理すれば残高は絶対に狂わない。Single Leader の本質は冗長化ではなく「順序の一元化」。

① この技術は何を解決するために生まれたのか

解決するのは 「複数のコピーがあるときに、どの順番で更新を適用するかが決まらない」問題。これを全順序（total order）の決定問題という。

Single Leader の答えはシンプル: 「順序を決める係を1人だけ置く」。Leader が受け付けた順番がそのまま正解になり、全 Follower はその順番通りに再生するだけ。分散合意アルゴリズムのような難しい話が要らなくなる。

図3-1 順序の一元化。「決定的な操作を、同じ順序で、同じ初期状態に適用すれば、同じ結果になる」— これが複製の理論的な土台。

② この技術がないと何が問題になるのか

  • 分岐（divergence）が起きる — 上図の通り、2つのノードが永久に違う状態を持つ。しかもどちらが正しいか原理的に決められない
  • アプリが衝突解決を書かされる — 「同じレコードが2つのバージョンで存在します、どうしますか？」をアプリが毎回判断する羽目になる（4章・15章）
  • 一意制約が守れない — 「メールアドレスの重複禁止」を複数ノードで同時に判定できない。同じメールで2アカウント作られる
  • 「在庫を1減らす」が壊れる — 読んで書くタイプの更新（read-modify-write）は、順序が決まらないと成立しない

③ 基本概念 — 4つのルール

ルール1: 書き込みは Leader のみ

クライアントの書き込みは全て Leader に送る。Follower は書き込みを拒否する（read only モード）。ここを間違えると即座に分岐する。

ルール2: 読み取りはどこでもよい

Leader からも Follower からも読める。ただし Follower は少し古い。この「少し」の扱いが8章。

ルール3: 変更は必ずログ経由で伝わる

Leader は変更をログに書き、その順序でだけ配る。ログの順序 = 真実の順序。ログを飛ばして直接データを書き換えることはしない。

ルール4: Leader は交代しうる

Leader が死んだら Follower の1つが昇格する（Failover, 16章）。「Leader が固定」ではなく「Leader は常に1人」が正しい理解。

④ 内部でどのように動くのか — Leader が抱える3つの仕事

図3-2 Leader の内部。「実行」「ログ書き」「送信」が別スレッドなので、どこがボトルネックかで対処が変わる。

⑤ 実際のシステム構成でどう使われるのか

Single Leader の構成パターンは3つに整理できる。要件（RPO/RTO・コスト）で選ぶ。

B. 1 Leader + N Read Replica非同期。全レプリカで読むRPO 数秒 / RTO 数分1+N倍読みが支配的な一般Webサービス。最頻出

⑥ メリット

  • 衝突が原理的に起きない — 書き込みが1箇所を通るので、衝突解決のコードをアプリに書かなくてよい。これが最大の価値
  • 一意制約・外部キー・トランザクションがそのまま使える — RDBMS の機能を全部使える
  • 運用が単純 — 「Leader はどれか」を見ればよい。デバッグが人間の頭に収まる
  • read-modify-write が安全 — 在庫減算・カウンタ・残高更新が正しく動く
  • 既存のツールが全部使える — ORM・マイグレーション・監視ツールが前提としている構成

⑦ デメリット・トレードオフ

  • 書き込みが単一障害点 — Leader が死んでいる間は書けない。Failover の数十秒は「書き込み不能」（16章）
  • 書き込みがスケールしない — Leader 1台の性能が天井。超えたら Sharding へ（2章）
  • 遠いユーザーの書き込みが遅い — 米国ユーザーが東京の Leader に書くと +120ms。これは Single Leader では絶対に解けない（4章へ）
  • Failover 自体がリスク — 誤発火（healthy な Leader を降格）、Split Brain、昇格時のデータ欠損。「Failover しない構成のほうが安定していた」は実際にある話
  • レプリカ数の上限 — Leader の送信帯域とCPUがボトルネックになる（実用上10〜15台程度、カスケードで緩和）

⑧ 実務での利用例

⑨ Googleレベルではどう設計されるか

  • Leader は「選挙で決まる」もの — 手動設定ではなく、Paxos/Raft の合意で常に自動決定。人間が Leader を指定する運用は存在しない
  • Leader にはリース（lease）がある — Spanner の Paxos leader は数秒〜10秒のリースを持ち、期限が切れる前に更新する。リースが切れた Leader は自発的に書き込みを止めるので、Split Brain が原理的に防がれる（17章）
  • Leader の配置を最適化する — Spanner では「書き込みが多い地域に Leader を置く」ようリーダー配置を制御できる（leader_placement_policy）。Leader の位置＝書き込みレイテンシだから
  • 粒度を細かくする — 1つの巨大な Leader ではなく、数百万の split それぞれに Leader がいる。Leader は分散配置されるので、実質的に書き込みも水平スケールする
⑩ 面接 「Single Leader の弱点は？ それをどう補いますか？」

模範解答: 「弱点は3つあります。

  1. 書き込みの単一障害点: Leader 障害中は書けません。補うには自動 Failover ですが、これ自体が Split Brain のリスクを生むので、fencing（旧 Leader の隔離）を必ずセットにします。RTO は現実的には10〜60秒です。
  2. 書き込みがスケールしない: これはレプリケーションでは解けないので、Sharding に進みます。ただし読み9割のサービスなら、レプリカとキャッシュで数年は戦えます。
  3. 遠隔地の書き込みレイテンシ: 米国から東京 Leader へは片道60ms。これは物理法則なので、Multi Leader かリージョンごとのデータ分割（partition by region）で解きます。私は後者を推します。ユーザーデータのように地域をまたいで同じ行を更新しない種類のデータなら、リージョン分割で衝突をゼロにできるからです。」

深掘り: 「レプリカを増やせば書き込みも速くなりませんか？」
→ 「逆です。レプリカが増えると Leader は同じログを台数分だけ送るので、ネットワークとCPUの負荷が増えて書き込みが遅くなります。準同期にしていればさらに、遅いレプリカが書き込みを引きずります。レプリカ追加は読みのスケールと引き換えに、書きを少し犠牲にする操作です。」

深掘り: 「Leader が死んだかどうか、どうやって判定しますか？」
→ 「これは原理的に確実には判定できません（FLP不可能性 / 非同期ネットワークでは故障と遅延が区別できない）。実務ではタイムアウトで近似します。短くすると誤検知で不要な Failover が起き、長くすると復旧が遅れる。だから『Leader が死んでいるかもしれない』前提で、旧 Leader を強制的に書けなくする fencing が必須になります。」（この答えができると評価が跳ねる）

04 Multi Leader

複数の場所で書き込みを受け付ける構成。「便利そう」に見えて、実務では最も慎重に扱うべきトポロジ。DDIA の著者 Martin Kleppmann も「明確な理由がない限り避けるべき」と書いている。なぜ危険で、それでも必要になるのはいつかを理解する章。

🏦 銀行の例え。 東京本店と大阪本店の両方で記帳できるようにした。それぞれの本店は自分の元帳に記帳し、後で互いに写しを送り合って統合する。
平常時は速い。だが、同じ口座の残高1万円に対して、東京で1万円の出金、大阪でも1万円の出金が同時に起きたら？ 両方とも自分の元帳では成立してしまい、統合したときに残高が -1万円になる。これが衝突（conflict）。
Multi Leader は「速さと引き換えに、この矛盾をアプリで処理する義務」を買う構成。

① この技術は何を解決するために生まれたのか

3つの、Single Leader では原理的に解けない問題を解く。

  • 1. 遠隔地の書き込みレイテンシ — 光速の制約。東京⇄米西海岸は片道約60ms。これは投資では縮まらない
  • 2. リージョン全体の障害でも書き続けたい — Single Leader ではリージョンが落ちたら書けない
  • 3. オフライン動作 — スマホアプリ・カレンダー・メモアプリ。実は各デバイスが「Leader」の Multi Leader システム

図4-1 Multi Leader の動機。ただし「衝突が起きうるデータ設計かどうか」が先。分割で回避できるなら、そちらが常に正しい。

② この技術がないと何が問題になるのか（＝ Multi Leader を「使わない」判断が難しいケース）

  • オフラインファーストのアプリ — 飛行機の中でメモを編集する。ネットが無いのだから、デバイスがローカルに書くしかない。これは Multi Leader 以外に選択肢が無い
  • リアルタイム共同編集 — Google Docs / Figma / Notion。各クライアントがローカルに即反映し、後で統合する。UIの応答性のために Multi Leader が必須
  • DC間フェイルオーバーが分単位では遅すぎる場合 — 金融取引の一部など
  • DBのバージョン移行 — 旧クラスタと新クラスタを双方向レプリケーションで並走させる（一時的な Multi Leader）

④ 内部でどのように動くのか — 衝突の発生と検出

衝突とは 「同じデータに対する2つの更新が、互いを知らないまま行われた」状態。「同時」とは時刻の話ではなく、「互いに相手を見ていない」という因果関係の話であることに注意。

図4-4 二重予約。Multi Leader では「一意制約」「在庫チェック」「残高チェック」のようなグローバルな不変条件が守れない。これが最も重い制約。

⑤ 実際のシステム構成でどう使われるのか — 衝突を「起こさない」設計が本命

実務での正解は「衝突解決を頑張る」ではなく「衝突が起きないようにデータを分ける」。これを理解しているかで設計の質が決まる。

戦略やり方衝突適用できるデータ
1. リージョン固定（ホーム）ユーザーごとに「所属リージョン」を決め、そのユーザーの書き込みは必ずそこへルーティング原理的に0ユーザープロフィール・注文・投稿など所有者が明確なデータ。大半のデータはこれで解ける
2. データ種別で分ける在庫・決済は中央の Single Leader、閲覧履歴やいいねは Multi Leader重要データは0整合性要求が種別で大きく違うサービス
3. CRDT を使う「どの順で統合しても同じ結果になる」データ型を使う（カウンタ・集合・テキスト）自動収束いいね数・共同編集テキスト・ショッピングカート
4. LWW（最終書き込み優先）タイムスタンプが新しい方を採用データが消える失っても困らないデータのみ。残高・在庫には絶対に使わない
5. アプリで解決両方保存してユーザーに選ばせる（Git のコンフリクトと同じ）UI 負担ドキュメント編集・カレンダー

⑥ メリット

  • 書き込みレイテンシがローカルになる — 120ms → 5ms。他の手段では代替不能
  • リージョン障害に強い — 片方が落ちても、もう片方で書き続けられる。Failover 不要（そもそも両方 Leader）
  • ネットワーク分断に耐える — DC間が切れても各 DC 内では動き続ける（CAP でいう AP 寄り）
  • オフライン動作ができる — デバイスがローカルに書ける

⑦ デメリット・トレードオフ — なぜ「避けるべき」と言われるのか

  • 衝突解決がアプリの責務になる — DBが解決してくれない。しかもテストが極めて難しい（本番でしか起きない稀なタイミング）
  • 一意制約が守れない — 「メールアドレス重複禁止」「在庫は0未満にしない」が原理的に保証できない
  • 自動採番IDが衝突する — AUTO_INCREMENT を各リージョンで使うと同じIDが2つできる。UUID/Snowflake ID が必須
  • 因果順序が壊れる — 図4-3。会話・イベントの順序が入れ替わる
  • デバッグが困難 — 「なぜこのデータがこうなったか」を追うには、複数リージョンのログを時系列で突き合わせる必要がある
  • トリガー・自動採番・非決定的関数との相性が最悪 — MySQL の循環レプリケーションが非推奨なのはこれが理由

⑨ Googleレベルではどう設計されるか

  • Google は Multi Leader を「原則使わない」 — Spanner は Paxos による Single Leader（split単位）を採用し、グローバルに一貫した順序を維持する方を選んだ。TrueTime に投資してでも「衝突が起きない世界」を作った（21章）
  • その代わり Leader の位置を制御する — データの「主に書かれる地域」に Leader を置くことで、Multi Leader を使わずにローカル書き込みレイテンシを下げる
  • 読みは Multi Leader 相当にできる — Spanner の bounded staleness read なら、ローカルレプリカから読める。「書きは中央、読みはローカル」が Google 流の落とし所
  • Multi Leader が必要な領域は CRDT で解く — Google Docs の共同編集は OT/CRDT。DB層では避け、アプリ層の専用アルゴリズムで解決するという切り分け

「まずデータを2種類に分けます。
① 所有者が明確なデータ（ユーザープロフィール、注文、投稿）→ ユーザーごとにホームリージョンを固定します。そのユーザーの書き込みは必ずホームへルーティングし、他リージョンには読み取り専用レプリカを置く。これで衝突は原理的にゼロ、かつ大半のユーザーはローカルに書けます。旅行中など稀なケースだけ遠隔書き込みになりますが、許容できます。
② グローバルに共有され、複数地域から更新されるデータ（在庫、グローバルなカウンタ）→ ここだけが本当の課題です。在庫のように不変条件（0未満にしない）があるものは Multi Leader にできないので、中央の Single Leader かリージョンごとの在庫割り当てにします。いいね数のような可換な操作なら CRDT カウンタで Multi Leader にできます。
結論として、『全体を Multi Leader にする』のではなく、データ種別ごとに使い分けるのが答えです。」

深掘り: 「なぜ Multi Leader を避けたいのですか？」
→ 「衝突解決の責務がアプリに来るからです。しかも衝突は本番の稀なタイミングでしか起きないのでテストが難しく、バグが長期間潜伏します。さらに一意制約と『在庫を0未満にしない』のようなグローバル不変条件が守れません。失うものが大きい割に、得られるのは書き込みレイテンシだけです。それをリージョン分割で得られるなら、そちらを選びます。」

深掘り: 「LWW で解決すればいいのでは？」
→ 「LWW はデータを黙って捨てる解決策です。2つの書き込みのうち片方が消える。カートに商品を追加したのに消える、という形でユーザーに見えます。加えて、サーバの時計がズレていると『古い書き込みが勝つ』ことすら起きます。失ってよいデータ（最終ログイン時刻など）にだけ使い、注文や残高には使いません。」

05 Leaderless（Dynamo系）

Leader を置かず、全ノードが書き込みを受け付ける構成。Amazon Dynamo 論文（2007）に始まり、Cassandra・Riak・Voldemort が採用。「多数決で辻褄を合わせる」という発想が Single Leader と根本的に違う。

🗳 証人の例え。 重要な契約を記録するのに、金庫（Leader）を1つ置くのではなく、3人の証人に同じ内容を伝えて覚えてもらう方式。
記録するとき: 3人中2人に伝わればOKとする（1人は不在でもよい）。
読み出すとき: 3人中2人に聞く。もし答えが食い違ったら、より新しいバージョンを持っている方を信じる。
なぜ2人ずつなのか？ 「書いた2人」と「聞いた2人」は必ず1人以上重なるから。この重なりが、最新の値を必ず含むことを保証する。これが Quorum の全て（13章）。

① この技術は何を解決するために生まれたのか

Amazon が Dynamo を作った動機は明確だった。「ショッピングカートは、絶対に書き込みを拒否してはいけない」。クリスマス商戦で「カートに追加できません」と出ることの損失は、カートの中身が少し不整合になることの損失より遥かに大きい。

  • 1. Leader 障害中の書き込み停止をなくす — Leader がいなければ、Leader 障害も Failover も存在しない。「常に書ける」
  • 2. ノード追加・削除を無停止で行う — 全ノードが対等なので、増減が容易（Consistent Hashing）
  • 3. 一貫性のレベルをリクエスト単位で選ばせる — 「この読みは速さ優先」「この読みは正確さ優先」を呼び出しごとに指定できる
  • 4. テールレイテンシを抑える — N台中W台の返事で済むので、一番遅い1台を待たなくてよい（これが実は最大の実用的メリット）

図5-1 Leaderless の基本。W+R>N は「最新を1台以上含む」だけで、「常に正しい1つの答えが返る」ではない。ここを面接で正確に言えると強い。

② この技術がないと何が問題になるのか

  • Failover 中の書き込み停止 — Single Leader では Leader 障害時に10〜60秒書けない。Leaderless ならこの停止が存在しない
  • テールレイテンシの悪化 — Single Leader では Leader が遅ければ全リクエストが遅い。Leaderless なら遅いノードを無視できる（Amazon が最も重視した点）
  • 運用の重さ — Single Leader ではノード追加時に「どれをLeaderにするか」「どこから複製するか」の判断が必要。Leaderless は対等なので単に足すだけ

④ 内部でどのように動くのか — データの配置と修復

Leaderless の実装は 「Consistent Hashing でデータの置き場所を決める」+「3つの修復メカニズム」で構成される。

図5-2 Leaderless の全体像。「書き込みを止めない」代償として、修復の仕組みと運用が要る。

実装上重要な概念が Sloppy Quorum（ゆるいクォーラム）。「本来のN台のうちW台」ではなく、「クラスタ内の誰でもいいからW台」に書く方式。

図5-3 Sloppy Quorum。Cassandra/DynamoDB の既定動作。「書き込みの可用性」を最優先した結果、一貫性の保証が弱まっている。

⑥ メリット

  • 書き込みが止まらない — Leader 障害・Failover という概念が存在しない。可用性が構造的に高い
  • テールレイテンシが安定する — 遅い1台を待たない。p99 が Single Leader より良くなることが多い
  • 一貫性をリクエスト単位で選べる — 同じテーブルでも「この読みは ONE、この読みは QUORUM」と切り替えられる
  • ノード追加・削除が容易 — 対等なので、増やす／減らすが単純。数百〜数千ノードまでスケールする
  • マルチDCが自然 — LOCAL_QUORUM で「各DC内では強め、DC間は非同期」を素直に表現できる

⑦ デメリット・トレードオフ

  • トランザクションが（ほぼ）使えない — 複数行にまたがる ACID トランザクションは基本的に無い。これが最大の制約
  • read-modify-write が壊れる — 「在庫を1減らす」が安全にできない。カウンタすら難しい（Cassandra の counter は専用型で、それでも制約が多い）
  • JOIN・柔軟なクエリができない — クエリパターンを先に決めてテーブルを設計する（query-first design）
  • 修復の運用が必要 — repair を回さないとデータが分岐し、削除が復活する
  • 衝突は LWW で黙って消える — Cassandra はセル単位のタイムスタンプ比較。ズレた時計は静かにデータを壊す
  • 線形化可能性が無い — 「読んだら必ず最新」が保証されない（13章）

⑧ 実務での利用例

  • Netflix — 視聴履歴・再生位置・レコメンド用データを Cassandra で。マルチリージョン active-active、LOCAL_QUORUM。「1件の視聴履歴が数秒古くても誰も困らない」ので Leaderless が合う
  • Discord — メッセージ履歴を Cassandra（後に ScyllaDB へ移行）。書き込み量が膨大で、時系列に append するだけのデータ
  • Apple — 世界最大級の Cassandra 運用（数十PB規模と公表されたことがある）
  • Uber — 位置情報・分析系の一部。時系列で大量に書くデータ
  • 典型的な適用データ: 時系列ログ・イベント・IoT・センサー・メッセージ履歴・セッション。共通点は「追記中心で、更新と集計が少ない」

✕ Leaderless を採用してはいけないケース

  • お金・在庫・座席 — 二重引き落とし・オーバーブッキングが起きる。絶対に使わない
  • 一意制約が要る — ユーザー名・メールアドレスの重複禁止が保証できない
  • クエリパターンが未確定 — スタートアップの初期。後から JOIN したくなって詰む
  • 運用人員がいない — repair・compaction・tombstone 管理は専門知識が要る。「RDBMSで足りるなら RDBMS」

⑨ Googleレベルではどう設計されるか

  • Google は Leaderless を主力にしていない — Bigtable も Spanner も Single Leader 系。「一貫性をアプリに押し付けない」という思想が一貫している
  • Spanner 論文の有名な一節 — 「アプリケーション開発者が一貫性の問題に対処するコストは、性能上の利点を上回る」。だから TrueTime に投資してでも強い一貫性を提供する道を選んだ
  • Amazon は逆の判断をした — Dynamo 論文（2007）は「可用性が最優先、一貫性はアプリで」。これは思想の違いであって、どちらかが間違いではない。ただし Amazon 自身も後年 DynamoDB で「強い整合性のある読み取り」オプションを追加している
  • 面接での言い方 — 「Dynamo 系は可用性を最優先し、一貫性の責務をアプリに移した設計です。Spanner 系はコストを払ってでも一貫性をDBが持つ設計です。どちらを選ぶかは、アプリ開発者に一貫性の複雑さを扱わせるかどうかの組織的判断でもあります」— これが言えると深い
⑩ 面接 「W+R>N なら強い一貫性が保証されますか？」（頻出の引っかけ）

正解は「保証されません」。ここで yes と答えると分散システムの理解が浅いと判断される。

模範解答: 「W+R>N が保証するのは『読み取り集合が、最後に成功した書き込みを持つノードを少なくとも1台含む』ことだけです。これは線形化可能性（linearizability）ではありません。破れるケースが5つあります。

  1. Sloppy Quorum: 担当外のノードに書かれた場合、読み取りはそれを見に行かない
  2. 同時書き込み: 2つの書き込みが並行したとき、どちらが「最後」かが決まらない。LWW で片方が消える
  3. 部分的に失敗した書き込み: W台に届く前に失敗した場合、ロールバックされない。届いたノードには残る
  4. ノード復旧: 古いデータを持つノードが復旧して、レプリカ数を数える対象に戻ると、古い値が返る可能性がある
  5. 読み書きの並行: 書き込み中に読むと、一部のノードは新、一部は旧。R回の読みでどちらが返るかは非決定的

なので Cassandra で本当に線形化可能性が要るなら、LWT（Lightweight Transaction / Paxos ベースの compare-and-set）を使います。ただし通常の書き込みの数倍のレイテンシになります。」

深掘り: 「では Leaderless はいつ選びますか？」
→ 「書き込みの可用性が一貫性より重要で、かつデータが追記中心のときです。具体的には視聴履歴・イベントログ・メッセージ・センサーデータ。逆に、お金・在庫・一意制約があるデータには使いません。実務では『Cassandra に注文データを入れて後悔する』が典型的な失敗パターンです。」

07 Synchronous / Asynchronous / Semi-Synchronous

「いつクライアントに OK を返すか」の選択。この1つの設定が、データ損失量・書き込み速度・可用性の3つを同時に決める。レプリケーション設計で最も影響が大きいパラメータ。

📮 宅配便の例え。 荷物を出したとき「発送完了しました」の通知が来るタイミングは3種類ありうる。
① 集荷した瞬間（Async）— すぐ通知が来る。だがトラックが事故れば荷物は消える。
② 相手の地域の営業所に着いた時点（Semi-Sync）— 少し待つ。営業所が焼けない限り荷物は届く。
③ 相手が受け取ってサインした時点（Sync）— 一番安心。だが相手が旅行中で1週間受け取らないと、こちらは1週間待たされる。
③の危険性がポイント。完全同期は「相手の都合でこちらが止まる」設計。

① この選択は何を決めているのか

決めているのは 「commit の定義」。「データベースが OK と言った」の意味を、どこまで強くするか。

これは技術的な選択に見えて、実質はビジネス判断: 「Leader が突然消滅したとき、直近の何秒分の書き込みを失ってよいか？（RPO）」に答えている。

図7-1 3方式のシーケンス。③の「レプリカを増やすほど可用性が下がる」という逆説が最重要ポイント。

⑨ Googleレベルではどう設計されるか

  • Google は「Quorum 同期」を既定にする — Async / Semi-Sync という二分法ではなく、Paxos で過半数に書けたら commit。過半数なので「1台の遅延で止まらない」かつ「RPO=0」を両立する
  • これが本質的に優れている理由 — Semi-Sync は「特定の1台」を待つが、Quorum は「誰でもいいから過半数」を待つ。遅いノードを構造的に無視できる。5台構成なら2台が遅くても影響なし
  • 「hedged request」との組み合わせ — Google は遅いノードへのリクエストを別ノードに投げ直す手法も併用し、テールレイテンシを削る（The Tail at Scale 論文）
  • 面接での差別化 — 「Semi-Sync は1台指名なので、その1台が遅いと引きずられます。可能なら Quorum ベース（MongoDB の w:majority、etcd/Raft、Spanner の Paxos）を選びます。過半数方式なら遅い少数を無視できるからです」— これが言えると一段上
⑩ 面接 「同期レプリケーションと非同期、どちらを選びますか？」

模範解答: 「二択ではなく、混ぜます。
同一リージョン内の1台だけ準同期にし、残りは非同期にします。これで ack された書き込みの RPO は 0、かつ同期対象が1台なので可用性の掛け算劣化を避けられます。PostgreSQL なら synchronous_standby_names = 'ANY 1 (s1, s2)'、MySQL なら semi-sync で wait_for_replica_count = 1 です。
クロスリージョンは必ず非同期にします。同期にすると全書き込みに往復レイテンシが乗り、サービス全体が遅くなるからです。DR 用途なら RPO 数秒を受け入れます。
全レプリカ同期は選びません。1台でも遅延・障害があると書き込みが止まり、レプリカを増やすほど可用性が下がるからです。」

深掘り: 「準同期にしていたのに、障害後にデータが消えていました。なぜ？」
→ 「3つ考えられます。①タイムアウトによる自動降格: MySQL の準同期はレプリカの ack が rpl_semi_sync_source_timeout（既定10秒）内に来ないと非同期に降格します。この間の書き込みは RPO≠0 です。降格は Rpl_semi_sync_source_status で監視すべきです。②AFTER_COMMIT モードだった場合の phantom read。③fsync 設定: レプリカ側が sync_binlog=0 だと OS のバッファに乗っただけで ack を返し、レプリカの OS ごと落ちると消えます。」

深掘り: 「RPO 0 を保証したいが、レイテンシも守りたい。どうしますか？」
→ 「同期先を物理的に近く置きます。同一リージョンの別AZなら RTT 1〜2ms なので、+2ms 程度で RPO 0 が買えます。同一AZ内だと安いですが、AZ 障害で両方失うので別AZが最低ラインです。さらに遠隔地への DR は非同期で別途持ちます。『近くは同期、遠くは非同期』が原則です。」

08 Replication Lag と3つの異常

この章が本書で最も実務に直結する。非同期レプリケーションを使う限り Lag は必ず存在し、ユーザーには3つの決まった形の「バグに見える現象」として現れる。名前を知っていれば議論できる。

🏦 銀行の例え。 本店で入金したのに、支店の端末では残高が古いまま。3つの困り方がある。
① 自分が入金したのに、自分の残高が増えていない（Read-your-writes 違反）— 最も苦情になる
② 残高を2回見たら、1回目は5万円、2回目は3万円（Monotonic reads 違反）— 時間が巻き戻る
③ 「入金しました」の記録より前に「入金の取消」の記録が見える（Consistent prefix 違反）— 因果が逆転する

① この技術（一貫性保証）は何を解決するために生まれたのか

「非同期レプリカから読む」という選択をした瞬間に生まれる、3種類の観測異常を分類し、それぞれに対策を持つため。「結果整合性」という一言で片付けず、どの異常が問題なのかを特定するのが設計。

図8-1 3つの異常。この分類は DDIA の5章に基づく。面接でこの3つを名前で挙げられると、確実に「読んでいる人」と分かる。

⑧ 実務での利用例

  • Instagram — 書き込み後の一定期間、そのユーザーのリクエストを Primary にルーティングする方式を採用したことが公開情報として知られる。典型的な「パターンA」
  • Facebook (Meta) — 「Scaling Memcache at Facebook」論文で、書き込み後にリモートマーカーを置き、そのキーの読みだけをマスター DC に向ける仕組みを紹介。read-your-writes をキャッシュ層で解いた例
  • ProxySQL / MaxScale — 「トランザクション内は必ず Leader」「直前に書いたテーブルへの SELECT は Leader」といったルールをプロキシ層で自動適用できる
  • Aurora — レプリカ Lag が通常10〜20ms 程度と非常に小さいため、read-your-writes 問題が起きにくい（起きないわけではない）。これがマネージドを選ぶ実利
  • MongoDB — readConcern: "majority" や causal consistency セッション（afterClusterTime）で、セッション保証を DB 側が提供する

⑨ Googleレベルではどう設計されるか

  • そもそも Lag をアプリに見せない — Spanner は全ての読みにタイムスタンプを付け、「そのタイムスタンプ時点の一貫したスナップショット」を返す。古いデータが返ることはあっても、矛盾したデータは返らない
  • staleness を明示的に指定させる — Spanner の bounded staleness: 「10秒以内に古いデータでよい」と宣言すると、ローカルレプリカから高速に読める。「どれくらい古くてよいか」をAPIの一部にしたのが設計として秀逸
  • Lag は SLO の対象 — 「レプリカ Lag の p99 が X 秒以内」を SLO として運用し、逸脱したらそのレプリカを読み取り対象から外す
  • 面接での応用 — 「レプリカ Lag が閾値を超えたら、そのレプリカをロードバランサから自動的に外します。『遅れているレプリカに読ませ続ける』のが最悪で、外して他に寄せるほうが総合的に良い」— これが言えると運用感がある
⑩ 面接 「ユーザーが投稿した直後に一覧に表示されません。どう直しますか？」

模範解答: 「これは read-your-writes 一貫性の違反です。非同期レプリカから読んでいて、複製がまだ届いていない状態です。対策を3段階で考えます。

  1. 短期（すぐ効く）: そのユーザーが書き込みをしてから一定時間（例: レプリカ Lag の p99 の数倍、実測して決める）は、そのユーザーの読み取りだけ Leader に向ける。全体を Leader に向けるのではなく、「本人の投稿一覧」だけにすれば Leader 負荷の増加は数%で済みます。
  2. 中期（正確にする）: 書き込み時に LSN（PostgreSQL）や GTID（MySQL）を取得してセッションに保存し、読み取り時にレプリカの適用位置がそれ以上か確認します。満たすレプリカがあればそこで読む。無ければ Leader。「必要な時だけ Leader」が実現できます。
  3. UI 側: 楽観的更新で、投稿を即座に画面に反映します。ただしこれは見た目の解決であって、リロードすると消えるので、1 か 2 と併用が前提です。

まず1を入れて、規模が出てから2に進むのが現実的です。」

深掘り: 「他人の投稿はどうしますか？」
→ 「他人の投稿が数秒遅れて見えるのは問題になりません。ユーザーは『いつ投稿されたか』を知らないからです。だから『自分の書き込み』だけを特別扱いするのが効率的です。一貫性は一律に上げるのではなく、必要な箇所を特定して上げるのが設計だと考えています。」

深掘り: 「同じユーザーが2回読んで、件数が減って見えました」
→ 「monotonic reads 違反です。ロードバランサが2回目に別の（より遅れた）レプリカへ振ったのが原因です。対策はユーザーIDのハッシュで振り先レプリカを固定する（sticky routing）ことです。ただしレプリカ障害時に振り先が変わるので完全ではなく、厳密にやるならセッションに『最後に読んだ LSN』を持って、それ以上のレプリカだけを選びます。」

09 Log Shipping（WAL / binlog / oplog）

レプリケーションの実体は「ログを配ること」。データベースの中身をコピーしているのではなく、「変更の記録」を配って各自が再生している。この理解に到達すると、CDC・Kafka・イベントソーシングまで一本の線でつながる。

📮 郵便の例え。 本店が支店に「今の元帳の写真」を毎回送るのは非効率（100万ページある）。代わりに「今日の取引伝票だけ」を送る。支店は自分の元帳にその伝票を書き写す。
この伝票の束がレプリケーションログ。重要なのは 「伝票には通し番号があり、抜けや順序入れ替えが検出できる」こと。番号 #103 の次に #105 が来たら、支店は「#104 がまだ来ていない」と分かって待てる。

① この技術は何を解決するために生まれたのか

元々ログはレプリケーションのためではなく、クラッシュリカバリのために生まれた。「変更をデータファイルに書く前に、まずログに書く」＝ WAL（Write-Ahead Logging）の原則。停電時にログを再生すれば復旧できる。

そして誰かが気づいた: 「このログを別のマシンに送れば、そのマシンも同じ状態になるのでは？」 これがレプリケーションの起源。レプリケーションはクラッシュリカバリの副産物。

図9-1 ログの汎用性。「レプリケーションログは DB の外にも配れる」— この一言が言えると、CDC の議論に自然に入れる。

③ 基本概念 — 物理ログ と 論理ログ

ログには大きく2種類ある。この違いが「どのDBと繋げるか」「バージョン差を許すか」を決める。

図9-2 物理 vs 論理。「PostgreSQL のメジャーバージョンアップは論理レプリケーションでやる」が実務の定番テクニック（19章）。

④ 内部でどのように動くのか — ログの位置管理と replication slot

「どこまで送ったか」の管理が、実は運用上最も事故を生む部分。

図9-3 replication slot。PostgreSQL 運用で最も多い「本番停止」原因のひとつ。面接で言及すると実運用経験が伝わる。

⑦ トレードオフ

  • ログは容量を食う — binlog / WAL の保持期間はディスク容量とのトレードオフ。短すぎるとレプリカが復帰不能、長すぎると溢れる
  • ログ生成が書き込み性能を落とす — binlog を有効にすると MySQL の書き込みは 10〜30% 程度遅くなる（環境依存）。それでも有効にしない選択肢は無い（レプリケーションもPITRもできなくなる）
  • fsync のタイミング設定が耐久性を左右する — sync_binlog=1 + innodb_flush_log_at_trx_commit=1 が最も安全だが最も遅い。この2つを緩めた環境で「データが消えた」は非常に多い
  • ログの形式が将来を縛る — 物理ログを選ぶと異種間連携ができない。後から論理に切り替えるのは大工事
⑩ 面接 「レプリケーションはどうやってデータを同期していますか？」

模範解答: 「データそのものではなく、変更のログを配って各レプリカが再生します。
Leader は書き込みのたびに、変更を順序付きのログ（PostgreSQL なら WAL、MySQL なら binlog、MongoDB なら oplog）に追記します。このログには単調増加する位置情報（LSN / GTID / optime）が付いていて、レプリカは『自分はどこまで受け取ったか』を保持します。Leader はその位置以降を送り続けます。
レプリカ側は2段階で処理します。まず受信してローカルのログに書き、次にそれを適用してテーブルに反映します。この2段階が別なので、『受信済みだが未適用』という状態が存在し、これが replication lag の一因になります。
ログには物理ログと論理ログがあり、物理は速いが同一バージョン必須、論理は遅いが異種間・バージョン跨ぎができて CDC にも使える、という違いがあります。」

深掘り: 「レプリカが1日ダウンして復帰したらどうなりますか？」
→ 「Leader がその期間のログを保持していれば、続きから自動で追いつきます。保持していなければレプリケーションが再開できず、スナップショットから作り直しになります。
PostgreSQL では replication slot を使うと『レプリカが受け取るまで WAL を消さない』ようにできますが、レプリカが死んだまま放置されると Leader のディスクが溢れて Leader が停止します。だから max_slot_wal_keep_size で上限を設定し、非アクティブなスロットを監視するのが必須です。これは実際によくある本番停止の原因です。」

深掘り: 「そのログは他の用途に使えますか？」
→ 「使えます。CDC（Change Data Capture）です。Debezium などで binlog / WAL を購読して Kafka に流せば、検索インデックスの更新・キャッシュ無効化・DWH 連携がアプリコードを書かずにできます。アプリで二重書きすると書き漏れやトランザクション不整合が起きますが、ログを唯一の真実の源にすれば漏れが原理的に起きません。」

10 Statement Based / Row Based / Mixed

MySQL の binlog_format の話だが、「複製とは何を運ぶことか」という一般的な設計問題でもある。この章の比喩（レシピ vs 完成した料理）は非常に効くので、面接でそのまま使ってよい。

🍽 レストランの例え。 本店の味を支店で再現する方法は2つある。
① レシピを送る（Statement Based）— 「玉ねぎを刻んで、20分炒める」。紙1枚で済むので軽い。だが「冷蔵庫にある一番古い牛乳を使う」というレシピだと、支店では違う牛乳になり、味が変わる。
② 完成した料理を送る（Row Based）— 味は絶対に同じ。だが重い。100人前なら100皿分を運ぶ。
「1000人前を作る」場合、①はレシピ1枚、②は1000皿。この差が binlog サイズの差。

① この選択は何を解決するのか

ログサイズ（＝ネットワーク帯域・ディスク）と、再現の確実性のトレードオフ。歴史的には SBR が既定だったが、非決定性による事故が多すぎて RBR が既定になった（MySQL 5.7.7 以降）。

④ 内部でどのように動くのか — binlog_row_image による最適化

RBR のログ肥大化は、「どの列を記録するか」を調整することで緩和できる。

設定記録内容サイズリスク

⑦ トレードオフ — なぜ ROW が勝ったのか

  • ディスクとネットワークは安くなった — SBR のサイズ優位は、ハードウェアの進歩で相対的に価値が下がった
  • データの不一致は高くつく — 「レプリカと Leader の値が微妙に違う」は発見が遅れ、原因究明に何日もかかる。確実性のほうが遥かに価値が高い
  • CDC という新しい価値が生まれた — ROW 形式は外部システムから解釈できる。これが決定打
  • 並列適用がしやすい — 行単位なので、依存関係のない行を並列に適用できる（WRITESET ベースの並列化）

教訓として一般化すると: 「操作を送る」より「結果を送る」ほうが、分散システムでは安全。冪等性が得やすく、再実行しても壊れない。これは REST API 設計（PUT vs POST）や、イベント設計（コマンド vs イベント）にも通じる普遍的な原則。

⑧ 実務での利用例

  • Airbnb（SpinalTap） — MySQL binlog を読み取って変更ストリームを配信する自社 CDC 基盤。ROW 形式が前提
  • Debezium + Kafka Connect — デファクトの CDC ツール。MySQL は ROW 形式必須、PostgreSQL は論理レプリケーション必須
  • gh-ost（GitHub） — オンラインスキーマ変更ツール。binlog を読んで変更を新テーブルへ反映する。ROW 形式が前提
  • AWS DMS — DB 移行サービス。ソースの binlog / WAL を読んで別DBへ流す
⑩ 面接 「binlog_format は何を選びますか？ 理由は？」

模範解答: 「ROW を選びます。理由は3つです。
① 再現の確実性: STATEMENT は NOW() や RAND()、並行 INSERT の採番順など非決定的な要素でレプリカと値がズレます。ズレは発見が遅れて原因究明に時間がかかるので、確実性を優先します。
② CDC に使える: ROW 形式は構造化された変更イベントなので、Debezium で購読して検索インデックスやキャッシュ、DWH に流せます。アプリで二重書きするより漏れません。
③ 並列適用がしやすい: 行単位なので依存のない変更を並列に適用でき、レプリカ Lag を抑えられます。
代償は binlog サイズです。特に 1文で大量行を更新するバッチで爆発するので、そういう処理は 1000行程度に分割して間に sleep を入れる運用にします。」

深掘り: 「ROW にしたらレプリカ Lag が悪化しました。なぜ？」
→ 「まず主キーの無いテーブルを疑います。ROW 形式の UPDATE/DELETE は『この before の行を探して変更する』という動作なので、主キーもユニークインデックスも無いと全行スキャンになります。100万行のテーブルなら1行の更新に100万行のスキャンです。
次に大量更新のバッチを疑います。binlog が数GB になっていればネットワークで詰まります。
最後に並列適用が無効になっていないか確認します。replica_parallel_workers と replica_parallel_type=LOGICAL_CLOCK（8.0 なら WRITESET ベース）を設定すると大きく改善します。」

11 Snapshot + Catch-up（新しいレプリカの追加）

「レプリカを1台追加する」という日常操作の裏側。動いているデータベースを、止めずにコピーするのは意外に難しい。ここでスナップショットとログの接続点という概念が出てくる。

📚 図書館の例え。 開館中の図書館の蔵書リストを、新しい分館にコピーしたい。
1ページ目を書き写している間に、100ページ目の本が貸し出される。書き写し終わったリストは「どの時点のものでもない、混ざったリスト」になってしまう。
正解: 「◯時◯分時点のリストです」と時刻を確定させてコピーし、その後の貸出記録（ログ）を後から順に適用する。この「時刻の確定」がスナップショットで、「その後の記録」がログ。2つを正確に接続することが全て。

図11-1 4フェーズ。「スナップショットの位置とログの最古が繋がっているか」が全て。ここが切れると最初からやり直し。

② 素朴にやると何が問題になるのか

  • 単純な cp や mysqldump では一貫性が保てない — 書き込みが走っている最中にファイルをコピーすると、テーブルAは10:00、テーブルBは10:05 の状態、という混在が起きる（torn snapshot）
  • FLUSH TABLES WITH READ LOCK でロックすると本番が止まる — 一貫性のために書き込みを止めるのは、大規模DBでは選択肢にならない
  • スナップショットの「時点」が分からないと接続できない — どこからログを適用すればよいか判断できない
  • Catch-up 中にさらに遅れる — 追いつく速度 < 新しい変更が生まれる速度 なら永久に追いつかない。書き込みが激しいDBでは実際に起きる

④ 内部でどのように動くのか — MVCC を使った「止めないスナップショット」

現代のDBは MVCC（多版型同時実行制御）を利用して、書き込みを止めずに一貫したスナップショットを取る。

図11-2 MVCC スナップショット。「バックアップ中にディスクが増える」現象の正体。

大規模DBでの工夫: 500GB を超えると pg_basebackup が現実的でなくなる。その場合は EBS スナップショットからボリュームを複製して、そこから WAL を適用する方式が速い（数分で完了する）。Aurora ならストレージ共有なのでコピー自体が不要。

⑦ トレードオフと運用上の注意

  • Leader への負荷 — ベースバックアップは 500GB を読み出すので、Leader の I/O とネットワークを食う。既存のレプリカから取得する（cascading）のが定石
  • Catch-up が終わらないリスク — 書き込みが激しいDBでは、追いつく前に次の遅延が積み上がる。低トラフィックの時間帯に実施する
  • スナップショット中の VACUUM 阻害 — 長時間トランザクションで bloat が進む。実施後に VACUUM 状況を確認する
  • ログ保持期間の設定 — 転送時間より短いと詰む。「転送時間の3倍以上」を目安にする
⑩ 面接 「稼働中のDBに、無停止でレプリカを追加する手順を説明してください」

模範解答: 「4段階です。
① 一貫したスナップショットを取る。MVCC を使うので書き込みは止めません。重要なのは『そのスナップショットがログのどの位置に対応するか』を記録することです。PostgreSQL なら pg_basebackup -C -S slot でスロット作成とバックアップを同時に行い、MySQL なら xtrabackup が GTID を記録します。

深掘り: 「Leader に負荷をかけたくない場合は？」
→ 「既存のレプリカからバックアップを取ります。レプリカは Leader と同じデータを持っているので、そこから取れば Leader の I/O を使いません。取得後は Leader に接続し直すか、カスケード構成のままにします。クラウドなら EBS/ディスクのスナップショットから複製するほうが速く、Leader への影響もほぼありません。」

深掘り: 「Catch-up が終わらない場合は？」
→ 「追いつく速度より新しい変更のほうが速い状態です。3つ対処します。①低トラフィック時間帯に実施する。②レプリカ側の並列適用を有効化する。③それでも駄目なら、書き込み量そのものを減らす（バッチの停止など）。根本的には『1台のレプリカが Leader の書き込みを捌けない』状態なので、シャーディングを検討する段階に来ているサインでもあります。」

12 Read Replica と Write Routing

レプリカを作っただけでは意味がない。「どのクエリをどこへ送るか」を決めて初めて価値が出る。この振り分けはアプリ・プロキシ・DNS のどの層でやるかで、運用性が大きく変わる。

📚 図書館の例え。 本館（Leader）と分館3つ（Replica）がある。利用者に「どこへ行けばいいか」を教える方法は3つ。
① 利用者自身が判断する（アプリ側で振り分け）— 一番速いが、全利用者に教育が要る
② 案内所を置く（プロキシ）— 案内所に聞けばよい。ただし案内所が混むと全体が詰まる
③ 「図書館」と検索したら空いてる分館が出るようにする（DNS）— 楽だが、切り替わるまで時間がかかる（TTL）

① この技術は何を解決するために生まれたのか

2つの問題を同時に解く。

  • 1. 読み負荷の分散 — 典型的な Web サービスは読み:書き＝9:1。読みをレプリカに逃がせば Leader の負荷は1/10近くになる
  • 2. Failover 時の接続先切り替え — Leader が変わったとき、アプリの設定を変えずに新 Leader に繋ぎ直せる仕組みが必要。これが実は本命の要件

図12-1 3つの層とルーティングルール。「トランザクション内は全て Leader」を忘れると、トランザクション中の SELECT が古い値を返して整合性が壊れる。

④ 内部でどのように動くのか — Go での実装例

// レプリカを使う設計の最小形。「明示的に選ぶ」ことを型で強制する type Cluster struct { writer *sql.DB readers []*sql.DB // レプリカごとの lag を定期的に測って保持する lagMS []atomic.Int64 } // 読み取り用。lag が大きいレプリカを避ける func (c *Cluster) Reader(ctx context.Context) *sql.DB { // ① トランザクション中・書き込み直後なら Leader を返す if s := SessionFrom(ctx); s != nil && s.MustUseLeader() { return c.writer } // ② lag が閾値以内のレプリカだけを候補にする candidates := make([]*sql.DB, 0, len(c.readers)) for i, r := range c.readers { if c.lagMS[i].Load() < 1000 { // 1秒以内 candidates = append(candidates, r) } } if len(candidates) == 0 { // 全レプリカが遅れている → Leader にフォールバック // ここで Leader が過負荷になる連鎖障害に注意。流量制限も検討 return c.writer } // ③ セッションIDでレプリカを固定（monotonic reads を守る） idx := int(SessionHash(ctx)) % len(candidates) return candidates[idx] } // 書き込み。呼んだら「以後 N 秒は Leader を使う」印を付ける func (c *Cluster) Writer(ctx context.Context) *sql.DB { if s := SessionFrom(ctx); s != nil { s.MarkWrite(time.Now()) } return c.writer }

設計上のポイント: 「デフォルトで安全側（Leader）に倒れる」ように作る。レプリカを使うのは「明らかに安全な読み」だけにする。逆にすると事故る。

⑦ トレードオフ — レプリカに読ませることの隠れたコスト

  • レプリカ障害時に Leader へ雪崩れる — レプリカ2台のうち1台が落ちると、残り1台に2倍の負荷。それも落ちると Leader に全部来て連鎖障害。「レプリカが全滅しても Leader が耐えられるか」を必ず設計する
  • Lag があるレプリカに読ませ続ける危険 — 監視して自動的に外す仕組みが要る
  • 接続数の管理が複雑になる — Leader + レプリカ N台 × アプリPod数 の接続が発生。PgBouncer などのコネクションプーラが必要になることが多い
  • 「どこで読んだか」がデバッグしにくい — 「たまに古いデータが返る」の調査が困難。ログに接続先を出すと後で助かる

⑧ 実務での利用例

  • YouTube / Vitess — VTGate がクエリを解析し、シャードとレプリカを自動選択。「@primary」「@replica」というサフィックスでキーspace を指定できる
  • GitHub — MySQL + ProxySQL/自社ルーティング。読み取りの多くをレプリカへ
  • Rails / Django — フレームワークレベルで read/write splitting をサポート（Rails 6 の connected_to(role: :reading) など）
  • Aurora — reader endpoint が自動でレプリカに分散。ただし単純なDNSラウンドロビンなので、負荷が偏ることがある（カスタムエンドポイントで制御可）
⑩ 面接 「読み取りをレプリカに振り分ける設計を説明してください」

模範解答: 「プロキシ層で振り分けるのを基本にします。アプリに実装すると全サービスに散らばって漏れるからです。ProxySQL や Vitess、マネージドなら Aurora の reader endpoint を使います。
ルールは6つ設定します。①トランザクション内は全て Leader、②書き込み後 N 秒間の同一セッションは Leader、③FOR UPDATE は Leader、④在庫や権限など『判断に使う SELECT』は Leader、⑤重い分析クエリは専用レプリカ、⑥Lag が閾値を超えたレプリカは対象から外す、です。

深掘り: 「レプリカが全部落ちたらどうなりますか？」
→ 「読み取りが全部 Leader に来ます。これが最も危険な連鎖障害です。Leader は書き込み分の容量しか持っていないので、9倍の読みが来れば潰れます。対策は3つ。①Leader の容量に読みの一部を吸収する余裕を持たせる、②キャッシュ層で読みを減らす、③レプリカ全滅時は一部の読みを劣化させる（重要でない機能を止める、キャッシュの古い値を返す）。『レプリカが全滅した時に Leader は耐えられるか』を設計書に必ず書くべきだと考えています。」

深掘り: 「Failover したのにアプリがエラーを出し続けます」
→ 「アプリ側が古い接続を掴んでいる可能性が高いです。①コネクションプールの最大寿命（Go なら SetConnMaxLifetime）が設定されていないと、既存接続が生き続けます。②DNS キャッシュ。JVM は既定で DNS を永久キャッシュするので明示設定が必要です。③『read-only エラー』を検出してプールをリセットするロジックがあると復旧が速くなります。」

13 Quorum Read / Quorum Write

「過半数」という考え方は、レプリケーションだけでなく分散合意（Raft/Paxos）・Leader 選出・Split Brain 防止の全てに使われる、分散システムの中核概念。なぜ「過半数」なのかを1つの図で理解する。

🗳 多数決の例え。 5人の委員会がある。ネットワーク分断で3人グループと2人グループに分かれた。
「過半数（3人以上）がいる側だけが決定できる」というルールにすると、2つのグループが同時に決定を下すことは原理的にありえない。なぜなら、5人の中に3人以上のグループは同時に2つ存在できないから。
これが Quorum の全て。「過半数は必ず重なる」という集合論の性質を、分散システムの安全装置に使っている。

① この技術は何を解決するために生まれたのか

  • 1. 「全員の合意」を待たずに安全性を保つ — 全員待ちは1台の障害で止まる。過半数なら少数の障害を無視できる
  • 2. 分断時に2つの真実が生まれるのを防ぐ — Split Brain の根本的な防止策（17章）
  • 3. 遅いノードを構造的に無視する — 5台中3台の返事でよいなら、遅い2台を待たなくてよい

図13-1 Quorum の原理。この1枚で「Quorum とは何か」「なぜ Split Brain が防げるか」の両方が説明できる。

⑦ トレードオフ

  • レイテンシが「2番目に速いノード」で決まる — N=3, W=2 なら、Leader + 1台。同一AZなら速いが、AZ跨ぎだと +数ms
  • クロスリージョン Quorum は極めて遅い — 3リージョンに1台ずつ置くと、過半数を取るのに必ず1つの遠隔リージョンを含む。全書き込みに +50〜100ms。Spanner がこれを受け入れているのは、それだけの価値があると判断したから（21章）
  • 少数派は完全に停止する — CAP でいう「C を取って A を捨てる」。分断された側のユーザーはサービスを使えない
  • N を増やすとレイテンシが悪化する — N=7 の過半数は4台。より多くの ack を待つ

⑨ Googleレベルではどう設計されるか

  • Quorum の構成をリージョンで設計する — Spanner のマルチリージョン構成では、「2つのリージョンに read-write レプリカ、1つに witness レプリカ」という配置がある。witness は Paxos の投票には参加するがデータは持たない。投票権だけを安く追加するという発想
  • Leader を書き込みが多い地域に置く — Quorum のレイテンシは Leader からの距離で決まるので、Leader の配置が性能を決める
  • 読みは Quorum を使わない — Spanner の読み取りは、Leader からリース情報を得た上でローカルレプリカから読む（またはタイムスタンプ指定の stale read）。書きだけ Quorum、読みはローカルという非対称設計
  • witness / read-only レプリカの使い分け — 「投票する（witness）」「読ませる（read-only）」「両方（read-write）」を分けて、コストとレイテンシを最適化する
⑩ 面接 「なぜ過半数なのですか？ 全員の合意ではダメですか？」

模範解答: 「理由は2つあります。
① 可用性: 全員の合意を要求すると、1台でも落ちた瞬間に書き込みが止まります。5台構成なら、全員合意では1台の障害で停止、過半数（3台）なら2台の障害まで耐えます。冗長化した意味が出るのは過半数方式のほうです。
② 安全性が保てる最小の数だから: 過半数の集合は、どの2つを取っても必ず1台以上重なります。だから『前に書いた集合』と『今読む集合』が必ず交差し、最新のデータが必ず含まれます。同じ性質から、ネットワーク分断時に過半数を持つグループは最大1つしか存在できないので、Split Brain も防げます。
なお、N は奇数にします。4台の過半数は3で、耐えられる障害は1台。3台と同じ耐障害性でコストだけ増えるからです。」

深掘り: 「Quorum があれば必ず最新が読めますか？」
→ 「『最新を持つノードが読み取り集合に含まれる』ことは保証されますが、それだけでは足りません。返ってきた複数の値のうちどれが最新かを判別する仕組み（バージョン番号やタイムスタンプ）が必要です。
さらに Cassandra のような Leaderless では、Sloppy Quorum・並行書き込み・部分失敗などで保証が崩れます。厳密な線形化可能性が要るなら、Raft/Paxos のように『Leader を通す + Quorum で commit』という構成にします。」

深掘り: 「3リージョンに1台ずつ置いて Quorum を組むのはどうですか？」
→ 「リージョン全体が落ちても動くという点では理想的ですが、全書き込みに遠隔リージョンへの往復が入ります。東京・大阪・シンガポールなら +30〜70ms、グローバルだと +100ms 超です。これを受け入れられるかがすべてです。
受け入れられないなら、1リージョン内の3AZに置いて、別リージョンには非同期レプリカを置く構成にします。リージョン障害時は RPO 数秒を受け入れて手動昇格する、という判断です。『リージョン障害への耐性』と『書き込みレイテンシ』は直接トレードオフなので、ビジネス要件で決めます。」

14 Read Repair / Hinted Handoff / Anti-Entropy

Leaderless では「書けなかったノード」が必ず生まれる。それを後から静かに直す3つの仕組み。この3つの守備範囲を理解していないと、Cassandra 運用で必ず事故る。

🚚 宅配便の例え。
Hinted Handoff＝ 不在で受け取れない家の荷物を、隣の家が預かっておいて、帰宅したら渡す。ただし預かる期限がある（3日過ぎたら営業所に返す）。
Read Repair＝ 配達に行ったついでに「あれ、この家の荷物、古い伝票のままだ」と気づいて、その場で最新に差し替える。行った家しか直らない。
Anti-Entropy Repair＝ 定期的に全世帯の配達記録を突き合わせて、抜けを全部埋める。確実だが重い。

図14-1 3つの修復。「短期障害＝①、よく読まれるデータ＝②、それ以外＝③」と守備範囲が違うので、3つとも必要。

⑦ トレードオフ

仕組みコスト直せる範囲運用上の注意
Hinted Handoff低（自動）短時間の障害のみ（既定3時間）hint が溜まると預かるノードのディスクを圧迫。障害復旧時に一斉転送で負荷スパイク

  • Cassandra Reaper — repair をスケジュールし、範囲を分割して段階実行する運用ツール。Cassandra を本番運用するなら事実上必須
  • Netflix — 大規模 Cassandra 運用のため、repair の自動化と監視に多大な投資をしている（Priam などのツールを公開）
  • DynamoDB — これらの仕組みをマネージドサービスとして内部で実行。ユーザーは repair を意識しなくてよい（これがマネージドの価値）

⑩ 面接 「Leaderless で、書き込み時に落ちていたノードはどうやって最新になりますか？」

模範解答: 「3つの仕組みが協調します。
① Hinted Handoff: 書き込み時に不在だったノード宛のデータを、別のノードが『hint』として一時的に預かります。対象ノードが復旧すると自動転送されます。ただし保持期間に上限（Cassandra なら既定3時間）があり、それを超えると破棄されます。
② Read Repair: 読み取り時に複数ノードの値を比較し、古いノードを見つけたらその場で最新値を書き戻します。ただし読まれたデータしか直りません。
③ Anti-Entropy Repair: 定期的に Merkle Tree でノード間の差分を検出して同期します。全データが対象ですが重いので、低トラフィック時に範囲を分割して実行します。
3つとも必要で、特に③を怠ると削除したデータが復活します。tombstone の保持期間（gc_grace_seconds、既定10日）内に repair が完走しないと、削除を知らないノードから古い値が戻ってくるからです。」

深掘り: 「Merkle Tree を使う理由は？」
→ 「全データを比較すると転送量が膨大になるからです。Merkle Tree はハッシュの木構造で、root のハッシュが一致すれば全体が一致していると分かります。違えば子を比較し、違う枝だけを辿ります。これで差分のある部分だけを O(log n) で特定できます。Git のオブジェクトモデルやブロックチェーンでも同じ原理が使われています。」

15 衝突解決（LWW / Version Vector / CRDT）

Multi Leader / Leaderless を選んだ瞬間に必ず必要になる。「2つの更新が同時に起きたとき、どちらを採用するか」。ここには「正解が存在しない」という事実を受け入れることから始まる。

📝 Git の例え。 2人が同じファイルの同じ行を編集して push すると conflict になる。Git は勝手に解決しない。人間に選ばせる。
分散DBの衝突解決も同じ構造だが、DBは「ユーザーに聞く」ができないので、何らかの自動ルールを決めるしかない。そのルールが必ずどこかで間違えることを受け入れて設計する。

① この技術は何を解決するために生まれたのか

「同時」の定義から始める。分散システムでいう「同時（concurrent）」は、時刻が近いことではなく「互いに相手を知らないこと」。これを因果関係（happens-before）で定義する。

図15-1 因果と同時。「同時＝時刻が近い」ではないという理解が、この章の全ての土台。

④ 内部でどのように動くのか — Version Vector の判定ロジック

// Version Vector = 「各ノードが何回更新したか」のカウンタの集合 type VersionVector map[NodeID]uint64 // 2つのバージョンの関係を判定する func Compare(a, b VersionVector) Relation { aGreater, bGreater := false, false for _, node := range allNodes(a, b) { switch { case a[node] > b[node]: aGreater = true case a[node] < b[node]: bGreater = true } } switch { case aGreater && !bGreater: return ADescendsB // a のほうが新しい（因果あり） case bGreater && !aGreater: return BDescendsA // b のほうが新しい case !aGreater && !bGreater: return Equal default: return Concurrent // 両方が互いを含まない = 衝突 } } // 例 a := VersionVector{"mobile": 2, "pc": 1} b := VersionVector{"mobile": 1, "pc": 2} // mobile では a が大きく、pc では b が大きい → Concurrent（衝突） c := VersionVector{"mobile": 2, "pc": 2} // c は a も b も全要素で以上 → c は両方の子孫。衝突は解決済み

⑦ トレードオフ — LWW の危険性を具体的に

図15-3 時計ズレによる消失。エラーも警告も出ず、静かにデータが消えるのが最も恐ろしい点。NTP 監視が必須な理由。

  • LWW は「消えた」ことが検出できない — ログにも残らない。ユーザーからの問い合わせで初めて分かる
  • NTP でも完全には防げない — うるう秒・仮想マシンの時刻ジャンプ・NTP サーバ自体の障害
  • 対策: NTP の同期状態を監視する / 時計に依存しない設計（Version Vector、Lamport Clock）を選ぶ / 重要データには LWW を使わない

⑨ Googleレベルではどう設計されるか

  • 衝突が起きない設計にする（最優先） — Spanner は Paxos で単一の順序を作るので、そもそも衝突が発生しない。「解決する」より「起こさない」
  • 時計の誤差を「測って明示する」 — TrueTime API は時刻を「点」ではなく「区間 [earliest, latest]」で返す。誤差を隠さず、誤差の分だけ待つ（commit-wait）。これが Google の最も独創的なアイデア（21章）
  • CRDT はアプリ層の道具として使う — Google Docs の共同編集は OT。DB 層には持ち込まない
  • 面接での言い方 — 「衝突解決は最後の手段です。まず『衝突が起きないデータ設計』（リージョン固定・所有者の明確化）を検討し、それが不可能な場合にだけ CRDT を使い、LWW は失っても構わないデータにのみ使います」
⑩ 面接 「マルチリージョンで同じレコードが同時に更新されました。どう解決しますか？」

模範解答: 「まず『そのデータは本当に複数リージョンから更新される必要があるか』を問い直します。多くの場合、ユーザーやテナント単位でホームリージョンを固定すれば、衝突は原理的にゼロにできます。これが第一選択です。
どうしても必要な場合は、データの性質で戦略を変えます。

  • 可換な操作（いいね数、カウンタ） → CRDT。自動収束し、データが失われません
  • 集合的なデータ（カート、タグ） → OR-Set。和集合で解決します
  • 失っても実害のないデータ（最終ログイン時刻） → LWW。単純さを優先
  • 業務判断が必要なデータ（予定、ドキュメント） → 両方保持してユーザーに提示
  • 在庫や残高 → 自動解決してはいけません。「-1個」は解決不能なので、そもそも Single Leader にするか、リージョンごとに在庫を割り当てて分割します

深掘り: 「LWW でいいのでは？」
→ 「LWW はデータを黙って捨てる戦略です。ユーザーから見ると『カートに入れたのに消えた』という形で現れます。しかもログにも残らないので検出できません。
さらに深刻なのは時計への依存です。あるサーバの時計が5分進んでいると、そのサーバの書き込みが以後5分間の全ての正しい書き込みに勝ってしまいます。NTP でもズレは完全には防げません。だから失っても構わないデータにだけ使うのが正しい使い方だと考えています。」

深掘り: 「CRDT の限界は？」
→ 「グローバルな不変条件を表現できないことです。『在庫を0未満にしない』『座席は1人だけ』のような制約は、各レプリカが独立に判断できないので CRDT では実現できません。CRDT が扱えるのは『どの順で適用しても同じ結果になる操作』だけです。制約が必要なら、その部分だけ合意（Single Leader / Paxos）が必要になります。」

16 Failover の全手順

Leader が死んだときに新 Leader を立てる操作。「レプリケーションを入れる本当の目的」であり、同時に「最も事故が起きる操作」。手順を1つずつ分解する。

🏦 銀行の例え。 本店が火災で連絡不能になった。支店の1つを新しい本店にしなければならない。
問題は「本当に火災なのか、電話線が切れただけなのか分からない」こと。電話線が切れただけなら、旧本店はまだ記帳を続けている。そこに新本店を立てると本店が2つになる（Split Brain）。
だから正しい手順は「新本店を立てる前に、旧本店が絶対に記帳できないようにする」。これがFencing（17章）。

① この技術は何を解決するために生まれたのか

「書き込みができない時間」を、人間の反応速度（数分〜数十分）から機械の検知速度（数秒〜数十秒）に短縮すること。RTO の短縮そのもの。

図16-1 6ステップ。STEP 3（Fencing）を省略した Failover が、Split Brain の最大の原因。

⑦ トレードオフ — Failover 設計の3つの調整項目

  • 検知タイムアウト — 短い＝速い復旧だが誤発火。長い＝安定だが RTO 悪化。「そのシステムでネットワーク瞬断が何秒続きうるか」から決める（クラウドなら5〜10秒が典型）
  • 昇格の条件 — 「lag が X 秒以内のレプリカのみ昇格可」という制限を入れる。遅れたレプリカを昇格させると大量のデータを失う
  • 自動 vs 半自動 — 「検知は自動、昇格は人間が Slack のボタンを押す」という中間形もある。誤発火を避けつつ RTO を数分に抑える現実解

  • Netflix の Chaos Monkey — ランダムにインスタンスを落として、システムが耐えられるかを常時検証する。「Failover を日常にする」思想

特に注意するのは3点です。
① Fencing（旧 Leader の隔離）を必ず昇格の前に行う。故障と遅延は原理的に区別できないので、『旧 Leader は死んでいるはず』という仮定を置いてはいけません。ネットワーク遮断・read_only 強制・電源断のいずれかで、確実に書けない状態にしてから昇格します。
② 昇格候補を lag で制限する。分析用の遅れたレプリカを昇格させると大量のデータを失います。『lag が X 秒以内』という条件を設定し、分析用レプリカは昇格候補から外します。
③ 検知の判定を複数の観測点から行う。1つの監視サーバから見えないだけで Failover すると、ネットワークの片側障害で誤発火します。Orchestrator は他のレプリカからも Leader が見えているかを確認します。」

深掘り: 「自動 Failover が誤発火したらどうなりますか？」
→ 「健全な Leader が降格され、不要なダウンタイムが発生します。さらに悪いのは、Fencing が不十分だと旧 Leader が書き込みを続けて Split Brain になることです。
対策として、①タイムアウトを十分長く（クラウドなら10秒程度）、②複数観測点で合議、③Failover の頻度自体を監視して、頻発しているなら自動化を一時停止する、といったガードを入れます。『Failover が多すぎる』は自動化が悪さをしているサインです。」

深掘り: 「Failover でデータが失われないようにするには？」
→ 「準同期または Quorum 書き込みが前提です。非同期だと『Leader にはあったがレプリカに届いていない』分が確実に失われます。
その上で、昇格するレプリカが最も進んでいることを保証します。Raft は『ログが古い候補者には投票しない』ルールでこれを保証しています。MySQL では Orchestrator が GTID を比較します。
それでも旧 Leader にしか無いデータが残る場合があるので、旧 Leader の binlog を退避してから再構築する運用にします。後から差分を確認できるようにするためです。」

17 Split Brain と Fencing

レプリケーションで起こりうる最悪の障害。「Leader が2人いる」状態。データが分岐し、自動復旧が不可能になる。防ぐ方法は確立しているので、知っているかどうかだけの問題。

🏦 銀行の例え。 電話線が切れただけの本店が「自分はまだ本店だ」と記帳を続け、同時に支店が「本店が死んだ」と判断して新本店として記帳を始めた。
1時間後、電話線が復旧する。2冊の元帳には、それぞれ全く違う取引が記録されている。どちらが正しいか？ 両方正しい。そして統合は不可能。同じ口座から両方で出金されていたら、実際の残高は誰にも分からない。
これが Split Brain の恐ろしさ。データが壊れるのではなく、「正しさ」の定義が失われる。

図17-1 Split Brain の全経過。「復旧後にデータをマージできない」という点が、他の障害と質的に違う。

③ 基本概念 — 防止の3つのアプローチ

図17-2 3つの防止策とリース。リース方式は「時計に依存する」点に注意（時計が大きく狂うと破れる）。それでも実務では最も現実的。

④ 内部でどのように動くのか — Fencing Token の実装

// 各 Leader 世代に単調増加する番号を割り当てる // Raft の term / ZooKeeper の zxid / etcd の revision がこれに相当 type LeaderLease struct { Token uint64 // 世代番号。昇格のたびに +1 Expires time.Time } // 書き込み時に必ず token を添える func (s *Storage) Write(token uint64, data []byte) error { s.mu.Lock() defer s.mu.Unlock() // 自分が見た最大の token より小さければ拒否 if token < s.maxSeenToken { return ErrStaleLeader // 旧 Leader からの書き込み → 拒否 } s.maxSeenToken = token return s.doWrite(data) } // Leader 側: リースが切れていたら自分で書き込みを止める func (l *Leader) Write(data []byte) error { if time.Now().After(l.lease.Expires.Add(-safetyMargin)) { // 期限が近い or 過ぎている → 自ら降格 l.stepDown() return ErrNotLeader } return l.storage.Write(l.lease.Token, data) }

重要な設計: safetyMargin を引くことで、「時計の誤差」と「書き込みにかかる時間」の分だけ早めに止まる。ここを省略すると、リース切れの瞬間に飛んだ書き込みが新 Leader の書き込みと競合しうる。

⑦ トレードオフ — CAP 定理としての整理

図17-3 CP と AP。「Split Brain は AP を選んだ結果として意図的に起きる」場合と、「CP のつもりで実装が甘くて起きる」場合がある。後者が事故。

面接での注意: CAP 定理は「3つのうち2つを選ぶ」ではなく、「分断（P）は選べない前提条件であり、分断が起きたときに C と A のどちらを取るかの選択」と説明するのが正確。この説明ができると理解度が伝わる。

⑧ 実務での利用例 — 実際に起きた Split Brain

  • GitHub（2018年10月） — 東海岸と西海岸の DC 間で43秒のネットワーク分断が発生。Orchestrator が西海岸のクラスタを昇格させ、その後両 DC に別々の書き込みが入った。復旧に24時間以上を要した。公開ポストモーテムは分散システムを学ぶ上で必読
  • Kubernetes の split brain — etcd クラスタが分断されると、Kubernetes 全体が動作不能になる。etcd を3台/5台の奇数で、かつ別AZに配置するのが鉄則
  • MySQL の circular replication — 双方向レプリケーションで両側に書くと、常時 Split Brain 状態。これが「循環レプリケーションを使うな」と言われる理由
⑩ 面接 「Split Brain とは何ですか？ どう防ぎますか？」

模範解答: 「ネットワーク分断などによってLeader が同時に2つ存在してしまう状態です。両方が書き込みを受け付けるので、データが分岐します。
最悪なのは復旧後に自動でマージできないことです。同じ主キーに違う内容が入り、同じ在庫が両方で引き当てられます。どちらも実際の取引なので、片方を捨てるしかありません。データが壊れるのではなく、『何が正しいか』の定義が失われるのが本質的な問題です。
防ぎ方は3つあり、併用します。
① 過半数（Quorum）: 過半数を持たない側は自ら停止します。過半数のグループは同時に2つ存在できないので、原理的に Leader が2人になりません。Raft / Paxos / MongoDB がこれです。
② リース（Lease）: Leader は有効期限付きの権限を持ち、期限内に更新できなければ自ら書き込みを止めます。外部から殺しに行く必要がないのが優れている点です。新 Leader は期限が切れてから立てます。
③ Fencing Token: 昇格のたびに単調増加する世代番号を発行し、ストレージ側が『古い世代からの書き込みを拒否』します。旧 Leader が生きていても書けません。
Failover の手順としては、昇格の前に必ず旧 Leader を隔離するのが鉄則です。」

深掘り: 「2ノード構成で Split Brain を防げますか？」
→ 「防げません。2ノードの過半数は2で、1台落ちたら過半数を作れないので、可用性がまったく上がりません。かといって『1台でも動く』にすると、分断時に両方が動いて Split Brain になります。
解決策は3台目を追加することです。データを持つ必要はなく、投票だけする軽量なノード（MongoDB の arbiter、Spanner の witness、etcd の3台目）で十分です。『偶数ノード構成は危険』というのはこの理由です。
なお MongoDB の arbiter は、w:majority の書き込みと組み合わせると別の問題（データを持つノードが2台しかない状態での可用性低下）を生むので、可能ならデータを持つ3台目が望ましいです。」

深掘り: 「クラウドなら分断は起きませんよね？」
→ 「起きます。AZ 間のネットワークは高品質ですが、数十秒の断は現実に発生します。GitHub の2018年の障害も43秒の分断が起点でした。
さらに、『分断』でなくても同じ結果になる状況があります。GC で数十秒停止したノード、ディスク I/O で応答できないノード、VM のライブマイグレーション。『応答がない＝死んでいる』とは限らないので、Fencing は常に必要です。」

19 PostgreSQL のレプリケーション

WAL 1本で全てを賄う構造的に美しい設計。物理レプリケーションと論理レプリケーションの使い分けが肝で、特に「論理レプリケーションでメジャーバージョンアップ」は実務で非常に強力なテクニック。

図19-1 物理と論理。「無停止に近いメジャーバージョンアップ」は面接でも実務でも強い武器。

実務で設定すべきパラメータ

# ===== Primary 側 ===== wal_level = replica # 論理レプリケーションを使うなら logical max_wal_senders = 10 max_replication_slots = 10 max_slot_wal_keep_size = '64GB' # PG13+。これが無いとスロットで Leader が停止する（9章） wal_keep_size = '2GB' # スロット無しの場合の保険 # 準同期（7章） synchronous_commit = on synchronous_standby_names = 'ANY 1 (standby1, standby2)' # FIRST 2 (...) のように「2台とも必須」にしない。1台の障害で書き込みが止まる # ===== Standby 側 ===== hot_standby = on # 既定。読み取りを許可 hot_standby_feedback = on # Standby の長いクエリを Primary に伝えて VACUUM を待たせる # → クエリのキャンセルは減るが、Primary の bloat が増える max_standby_streaming_delay = 30s # 適用を最大何秒待つか。-1 は無限（Lag が無限に増える）

⚠ PostgreSQL 固有の罠: recovery conflict

Standby で長いクエリを実行していると、WAL の適用がそれと衝突することがある（Primary で VACUUM されたページを、Standby でまだ読んでいる場合など）。

  • 既定の挙動: max_standby_streaming_delay 秒待った後、クエリを強制キャンセルする（ERROR: canceling statement due to conflict with recovery）
  • 対策A: hot_standby_feedback = on — Standby の実行中クエリを Primary に伝え、必要な行を VACUUM させない。代償: Primary のテーブルが肥大化する
  • 対策B: max_standby_streaming_delay を長くする。代償: その間 Lag が増え続ける
  • 対策C（推奨）: 分析用の Standby を分ける。分析用だけ feedback を on にし、Failover 候補からは外す

監視すべき項目

Patroni による自動 Failover（実務の定番）

  • 構成: Patroni（各DBノードに常駐）+ etcd/Consul（分散合意ストア）+ HAProxy/PgBouncer（接続ルーティング）
  • 仕組み: 各ノードが etcd にTTL付きのリーダーキーを書き、期限内に更新できなければリーダー権を失う。これは17章のリース方式そのもの
  • Fencing: リーダーキーを失った Primary は自ら read-only に降格する（demote）。外部から殺しに行く必要がない
  • 重要な設定: maximum_lag_on_failover — この値以上遅れているレプリカは昇格させない（16章の「lag で昇格候補を制限」）
  • etcd は3台/5台の奇数で、必ず別AZに置く — etcd が Split Brain を起こすと Patroni 全体が壊れる

20 Amazon Aurora

「レプリケーションとは何か」の常識を変えた設計。"The log is the database" — ログだけを送り、ページを送らない。面接で Aurora の設計を説明できると、抽象化の理解力が伝わる。

🏦 銀行の例え。 従来のレプリケーションは「支店にも完全な元帳を持たせ、本店の伝票を送って書き写させる」方式。
Aurora は発想が違う。元帳を保管する巨大な共同倉庫（分散ストレージ）を作り、本店も支店もそこを見る。本店は倉庫に「伝票」だけを送る。倉庫の職員が伝票から元帳を作る。
だから支店は「書き写す作業」が不要になり、追加も一瞬で終わる。

図20-1 Aurora の構造。「ログをストレージ層に押し下げた」のが本質。SIGMOD 2017 の論文は分散システムの名作。

なぜ 4/6 Quorum なのか — 設計判断の読み解き

条件値意味
コピー数 V6（3AZ × 2）AZ障害 + 追加1台の障害に耐えるための最小構成
書き込み定足数 Vw4AZ1つ（2台）を失っても、残り4台で書ける
読み取り定足数 Vr3AZ1つ（2台）+ 1台を失っても、残り3台で読める
Vw + Vr > V4 + 3 = 7 > 6 ✓Quorum 条件を満たす（13章）
Vw > V/24 > 3 ✓書き込み同士が必ず重なる = 順序が保証される

設計の要点: 「AZ が1つ丸ごと落ちる」ことを起こりうる前提として設計している。3コピー（各AZ1つ）だと、AZ障害時に残り2つになり、そこからさらに1台落ちると書けなくなる。6コピーは「AZ障害中でも、もう1台の障害に耐える」ための数。

Aurora Global Database（クロスリージョン）

  • 構造: ストレージ層で直接リージョン間複製を行う。DB インスタンスを経由しないので Writer に負荷がかからない
  • 遅延: 通常1秒未満（AWS 公表値）。DB レベルの非同期レプリケーションより安定する
  • 用途: DR（災害復旧）と、遠隔リージョンでの低レイテンシ読み取り
  • 昇格: セカンダリリージョンを Writer に昇格できる（マネージド Failover: 通常1分程度、手動昇格はより短時間）
  • Aurora の write forwarding: セカンダリリージョンで書き込みを受け付け、プライマリに転送する機能。Multi Leader ではない（書き込みは1箇所を通る）ので衝突が起きない。「見かけ上マルチリージョン書き込み、実態は Single Leader」という賢い妥協
面接 「Aurora は普通の MySQL レプリケーションと何が違いますか？」

模範解答: 「複製の層が違います。通常の MySQL はDBインスタンス間でログを送り、各レプリカが SQL を再実行して自分のデータを作ります。Aurora はストレージ層で複製し、DBインスタンスはそのストレージを共有します。
Writer が送るのはredo ログレコードだけで、データページも binlog も double write もネットワークに流しません。ストレージ側がログからページを組み立てます。これを Aurora の論文は『The log is the database』と表現しています。
この設計の帰結が4つあります。①レプリカ追加が数分（データコピーが不要）、②レプリカ Lag が10〜20ms（SQL を再実行しないので、8章のような read-your-writes 問題が起きにくい）、③書き込み I/O が大幅に少ない、④ストレージが 6コピー・4/6 Quorum なので AZ 障害に強い。
代償はAWS ロックインと、Writer が1台のままなので書き込みはスケールしないことです。」

深掘り: 「なぜ 6コピーなのですか？」
→ 「『AZ が1つ丸ごと落ちている最中に、さらに1台が落ちても動く』ことを保証するためです。3AZ に2つずつ配置し、書き込みは4/6、読み取りは3/6 で定足数を満たします。AZ 障害で2台失っても、書き込みには4台残るのでちょうど成立します。3コピーだと AZ 障害で残り2台になり、さらに1台落ちると書けません。大規模環境では『AZ 障害中の追加故障』が現実に起きるので、この余裕が必要です。」

21 Google Spanner

「グローバルに分散していて、かつ強い一貫性がある」という不可能だと思われていたものを実現したシステム。鍵は TrueTime — 「時計の誤差を隠さず、誤差の分だけ待つ」という発想の転換。

⏰ 時計の例え。 世界中の支店の時計は必ずズレている。従来のシステムは「時計は合っている」ふりをして順序を決めようとし、失敗してきた。
Google のやったこと: 「今は 10:00:00 ± 3ms です」と誤差込みで答える時計を作った（原子時計 + GPS）。そして「取引を確定させる前に、誤差の分（6ms）だけ黙って待つ」。待った後なら、自分の取引が他のどの取引より確実に後だと言い切れる。
非常に泥臭いが、これで世界中で一貫した順序が実現した。

図21-1 Spanner の2本柱。「staleness を API の引数にした」という設計は、他のシステムを設計する際にも真似する価値がある。

トレードオフ — Spanner が万能ではない理由

  • 書き込みレイテンシが高い — マルチリージョン構成では、過半数の ack に遠隔リージョンが含まれるため 数十〜100ms。加えて commit-wait の数ms。単一リージョンの MySQL（1〜2ms）とは桁が違う
  • コストが高い — 専用ハードウェア（GPS/原子時計）とネットワークを前提とする。GCP の Spanner は小規模用途には割高
  • TrueTime は Google のインフラに依存 — 一般のクラウドで同じ精度は出しにくい。CockroachDB は同種の問題を HLC（Hybrid Logical Clock）+ 不確実性ウィンドウでのリトライで解決している（TrueTime なしで近い性質を得る工夫）
  • スキーマ設計の制約 — ホットスポットを避けるため、単調増加する主キー（連番・タイムスタンプ）を避ける設計が必要

面接での位置づけ: 「Spanner は『一貫性の複雑さをアプリに押し付けない』ためにレイテンシとコストを払うという判断です。Dynamo 系は逆の判断をしました。どちらが正しいかではなく、組織としてどちらのコストを払うかの選択です。」

23 Cassandra

現役で最も純粋な Leaderless 実装。「リクエストごとに一貫性レベルを選べる」という設計が最大の特徴で、マルチDC構成での表現力が非常に高い。

図23-1 Cassandra の一貫性レベル。「LOCAL_QUORUM」を知っているかどうかで、マルチDC設計の実務経験が測れる。

Cassandra 運用の3大落とし穴

  • 1. repair を回さない — 14章の通り、gc_grace_seconds（既定10日）以内に repair を完走させないと削除データが復活する。Reaper 等での自動化が事実上必須
  • 2. tombstone の蓄積 — 大量削除や TTL 切れが多いテーブルで tombstone が溜まると、SELECT が異常に遅くなる（読み取り時に全 tombstone をスキャンする）。tombstone_failure_threshold を超えるとクエリが失敗する
  • 3. 不適切なデータモデリング — Cassandra はクエリ駆動設計（query-first）が前提。「後から JOIN したい」「後から別の条件で検索したい」ができない。パーティションキーの選択を誤ると、ホットパーティションで特定ノードだけが死ぬ

加えて LWW の危険: Cassandra の衝突解決はセル単位のタイムスタンプ比較。ノード間の時計がズレていると、新しい書き込みが古い書き込みに負けてデータが消える（15章 図15-3）。NTP 監視が必須。

24 MongoDB

Raft 系の選挙 + 冪等な oplog という組み合わせ。writeConcern / readConcern / readPreference の3つの独立したダイヤルで一貫性を細かく制御できるのが特徴。

図24-1 MongoDB の3ダイヤルと rollback。「w:1 で ack されたのに消える」という現象の仕組み。w:majority を使う理由がこれ。

実務での推奨設定

// 重要データ（注文・決済） db.orders.insertOne(doc, { writeConcern: { w: "majority", j: true, wtimeout: 5000 } }) // 読みも majority にして、rollback されうる値を読まないようにする db.orders.find(q).readConcern("majority").readPref("primary") // 参照系（商品一覧など、多少古くてよい） db.products.find(q) .readPref("secondaryPreferred", [], { maxStalenessSeconds: 90 }) // maxStalenessSeconds で「遅れすぎた Secondary」を自動的に避ける // 因果一貫性（read-your-writes を保証したい場合） const session = client.startSession({ causalConsistency: true }) // 同一セッション内なら、書いた後の読みで必ず自分の書き込みが見える // → 8章の read-your-writes を DB 側が提供してくれる。実務では非常に便利

arbiter の注意: MongoDB には「データを持たず投票だけする arbiter」があるが、データノードが2台 + arbiter 1台の構成で w:majority を使うと、1台落ちた時点で書き込みができなくなる（過半数=2 だがデータノードが1台しかない）。可能な限り、データを持つ3台構成にする。

26 Replication 監視

レプリケーションは「静かに壊れる」種類の仕組み。止まってもアプリはエラーを出さず、正常に見える。監視していなければ、障害が起きた瞬間に初めて壊れていたことを知る。

🏦 銀行の例え。 支店への元帳送付が3日前から止まっていたとする。本店は普通に営業できているので誰も気づかない。気づくのは、本店が火事になって「支店の元帳で再開しよう」としたとき。そのとき初めて「3日分のデータが無い」と分かる。
これがレプリケーション監視が必要な理由。「保険が生きているか」を平時に確認し続ける。

図26-1 監視8項目。1〜4はアラート必須。特に「レプリケーションが止まっている」は無音で進行するので最優先。

-- Source 側: 1秒ごとにこれを実行するデーモンを置く CREATE TABLE heartbeat ( server_id INT PRIMARY KEY, ts TIMESTAMP(6) NOT NULL ); REPLACE INTO heartbeat (server_id, ts) VALUES (1, NOW(6)); -- レプリカ側: この行がレプリケーション経由で届く。差が実際の Lag SELECT TIMESTAMPDIFF(MICROSECOND, ts, NOW(6)) / 1000000.0 AS lag_seconds FROM heartbeat WHERE server_id = 1; -- この方式の利点 -- ① 書き込みが無い時間帯でも正しく測れる（1秒ごとに必ず書き込みがあるため） -- ② カスケード構成でも「大元の Source からの遅れ」が測れる -- ③ 「適用まで完了した」時点の遅れが測れる（受信だけでは行が更新されない）

9社に共通する5つのパターン

  1. データ種別で一貫性を分ける — 全社が例外なくやっている。「検索は古くてよい、決済は最新」。これが最も重要な共通パターン
  2. shard 内は Single Leader — 大規模化しても Single Leader は捨てられていない。粒度を細かくして生き残らせている（Vitess の shard、Spanner の split、DynamoDB の partition）
  3. ルーティングをプロキシ層に集約 — アプリに散らすと必ず漏れる。VTGate / mongos / Aurora endpoint
  4. レプリケーションログを外部にも配る — CDC。Airbnb の SpinalTap、Debezium。「二重書きしない」が共通思想
  5. Failover を日常的に訓練する — Netflix の Chaos Engineering が象徴的。訓練していない Failover は本番で失敗する

※ 各社の構成は公開情報（技術ブログ・論文・カンファレンス発表）に基づく整理であり、時期によって変化している。設計の「考え方」を学ぶ材料として読むのが適切で、細部をそのまま現在の構成として引用するのは避けるべき。

28 理解度チェック

各問、まず自分で答えを口に出してから開くこと。「読んで分かった」と「説明できる」は全く違う。

Q1 レプリケーションが解く4つの問題を挙げ、それぞれ「レプリカをどこに置くべきか」を答えよ

答え: ①可用性→別ラック・別AZ（同一ラックだと電源で全滅）②耐久性→別AZ・別リージョン ③読みスケール→どこでもよい（同一AZが安い）④地理的レイテンシ→ユーザーの近く。
ポイント: 目的によって配置が変わる。「3台置けばよい」ではなく「何から守るために、どこに置くか」。加えて相関故障を切る（同じ電源・同じソフトウェアリリース波を避ける）ことが台数より重要。

Q2 「レプリカがあるからバックアップは不要」— これが誤りである理由を1文で

答え: レプリケーションは論理的な誤り（DROP TABLE、アプリのバグ）も忠実に複製するので、人為ミスからは守れないから。守っている脅威が違う（2章）。
加えて復元テストをしていないバックアップは存在しないのと同じ。

Q3 Single Leader の本質的な役割は「冗長化」ではない。何か？

答え: 書き込みの順序を1箇所で決めること（全順序の確定）。
順序が決まれば、全レプリカが同じ順序で再生することで必ず同じ状態に収束する（state machine replication）。これにより衝突が原理的に起きず、一意制約・トランザクション・read-modify-write が成立する（3章 図3-1）。

Q4 全レプリカを同期にすると、なぜ可用性が下がるのか？ 数字で説明せよ

答え: 全員の ack が必要なので、書ける確率 = p^(N+1)。1台99.9%なら、Leader+2台で 0.999³ = 99.7%。1台構成（99.9%）より悪い。
正解の構成: 「ANY 1（誰か1台の ack でよい）」にすると、0.999 × (1 - 0.001²) ≒ 99.8999% でレプリカを増やしても劣化しないかつ RPO=0（7章 図7-4）。

Q5 Replication Lag が引き起こす3つの異常を、名前と症状で答えよ

答え:
①Read-your-writes 違反 — 自分の書き込みが自分に見えない。対策: 書き込み後は Leader へ / LSN 比較
②Monotonic reads 違反 — 2回読むと値が巻き戻る。対策: 同じユーザーは同じレプリカへ（sticky）
③Consistent prefix reads 違反 — 因果順序が逆転する（返信が質問より先に見える）。対策: 因果データを同一パーティションに / version vector
この3つは「セッション保証」と呼ばれ、DBを強一貫にしなくてもアプリ側で実現できるのがコスト効率上の重要ポイント（8章）。

Q6 Statement Based Replication が壊れる具体例を3つ

答え: NOW()（実行時刻が違う）、RAND()/UUID()（値が違う）、AUTO_INCREMENT + 並行 INSERT（採番順が変わる）。他に LIMIT 付き UPDATE の対象行順、ユーザー定義関数、トリガーの副作用。
一般化すると: 「操作を送る」より「結果を送る」ほうが分散システムでは安全。これは REST の PUT vs POST、イベント設計の command vs event にも通じる原則（10章）。

Q7 W + R > N は「強い一貫性」を保証するか？ 理由も

保証しない。保証するのは「読み取り集合が最新を持つノードを1台以上含む」ことだけ。
破れるケース: ①Sloppy Quorum ②並行書き込み（どちらが最後か決まらない）③部分失敗した書き込み（ロールバックされない）④古いノードの復旧 ⑤読み書きの並行。
線形化可能性が要るなら Paxos/Raft（Leader を通す + Quorum で commit）か Cassandra の LWT を使う（13章）。

Q8 Failover の6ステップのうち、最も忘れられがちで最も重要なのはどれか

答え: STEP 3 の Fencing（旧 Leader の隔離）。新 Leader を立てる前に、旧 Leader が絶対に書けない状態にする。
理由: 故障と遅延は原理的に区別できないので、「旧 Leader は死んでいるはず」という仮定を置いてはいけない。これを飛ばすと Split Brain（16章・17章）。

Q9 なぜノード数は奇数がよいのか

答え: N=4 の過半数は3で、耐えられる障害は1台。N=3 も1台。4台にしても耐障害性は3台と同じで、コストとレイテンシだけ増える。だから 3, 5, 7 を選ぶ。
2ノード構成は特に危険: 過半数が2なので1台落ちたら停止。かといって1台で動かすと分断時に Split Brain。3台目（投票だけの軽量ノードでも可）が必要（13章・17章）。

Q10 LWW を在庫管理に使ってはいけない理由を2つ

答え: ①データが黙って消える — 2つの引き当てのうち片方が消え、実在庫と帳簿がズレる。エラーもログも出ないので検出できない。②時計のズレで不公平が起きる — 時計が5分進んだサーバの書き込みが、以後5分間の正しい書き込みに全部勝つ。
根本的には: 在庫には「0未満にしない」というグローバルな不変条件があり、これは各レプリカが独立に判断できないので、自動衝突解決では原理的に守れない（15章）。

Q11 Aurora が「レプリカ追加が数分」で済む理由

答え: データをコピーしないから。Aurora は計算層とストレージ層を分離し、全 Reader が同じ分散ストレージを共有する。新しい Reader は既存のストレージを見るだけなので、500GB の転送が不要。
同じ理由でレプリカ Lag も 10〜20ms と小さい（SQL を再実行せず、ストレージ上の最新ページを読むだけ）（20章）。

Q12 Cassandra で repair を回さないと何が起きるか

答え: 削除したデータが復活する（ゾンビデータ）。
削除は tombstone として記録され、gc_grace_seconds（既定10日）後に消される。その前に repair が完走していないと、削除を知らないノードが残り、そこから古い値が返ってくる。
加えて、読まれないデータの不整合が永久に残る（Read Repair は読まれたものしか直さない）（14章・23章）。

Q13 MySQL の Seconds_Behind_Source を信用してはいけない理由と、正しい測り方

答え: ①書き込みが無い時間帯は実際に遅れていても 0 になる ②I/O スレッドが止まっていると 0 or NULL ③カスケード構成では直上のノード基準になる。
正しい測り方: ハートビートテーブル。Source で1秒ごとに現在時刻を UPDATE し、レプリカでその値と now() の差を取る（pt-heartbeat）。これなら書き込みが無い時間帯でも、カスケードでも正しく測れる（18章・26章）。

Q14 PostgreSQL で「レプリカを消したのに本番が止まった」— 何が起きたか

答え: replication slot を消し忘れた。スロットは「レプリカが受け取るまで WAL を消さない」ので、レプリカが永久に来ない状態だとWAL が無限に溜まり、Leader のディスクが満杯になって PostgreSQL が停止する。
対策: ①max_slot_wal_keep_size を設定（PG13+）②pg_replication_slots の active=false を監視 ③レプリカ削除手順にスロット削除を明記（9章）。

Q15 Multi Leader を「避けるべき」と言われる理由を3つ

答え: ①衝突解決の責務がアプリに来る（しかも本番の稀なタイミングでしか起きないのでテストが難しい）②一意制約とグローバル不変条件が守れない（メール重複禁止、在庫0未満禁止）③因果順序が壊れる（返信が質問より先に見える）。
代替案: 多くの場合、ユーザーごとにホームリージョンを固定することで衝突をゼロにしつつローカル書き込みを実現できる（4章）。

Q1 1日1億PV の EC サイトのDB構成を設計してください

  3. 一貫性の分離（ここが評価点）:
    • 商品一覧・検索 → レプリカ（数秒古くてよい）
    • 在庫の引き当て・決済 → 必ず Leader + トランザクション
    • 注文履歴 → 「注文直後は Leader、それ以降はレプリカ」
  4. 同期性: 注文・決済のため Semi-Sync（ANY 1）で RPO 0。分析用レプリカは非同期
  5. Failover: Aurora ならマネージド。自前なら Orchestrator/Patroni + fencing

深掘り: 「セール時に10倍のトラフィックが来たら？」
→ 「読みはキャッシュとレプリカ追加で対応します。問題は書き込みと在庫の引き当てです。人気商品1点に注文が集中すると、その行のロック競合で詰まります。対策は①在庫を N 個のサブカウンタに分割して競合を分散、②非同期の注文キューにして順番に処理（『申し込み受付』と『確定』を分ける）、③在庫を Redis で先に減らして DB は後追い（ただし整合性の設計が必要）。セール開始前にレプリカとキャッシュを温めておくのも重要です。」

Q2 日本・米国・欧州でサービスを展開します。DBをどう配置しますか？

回答の骨格: 「まずデータを3種類に分類します。

  • ユーザー所有データ（プロフィール・注文・投稿）→ ユーザーごとにホームリージョンを固定。書き込みはそこへ、他リージョンには読み取りレプリカ。衝突が原理的にゼロで、大半のユーザーはローカルに書けます
  • グローバル参照データ（商品マスタ・設定）→ 1箇所で書き、全リージョンに非同期複製。更新頻度が低いので Lag が問題にならない
  • グローバル共有かつ更新されるデータ（在庫・グローバルカウンタ）→ ここだけが本当の課題。在庫のように不変条件があるものは中央 Single Leader かリージョン別の在庫割り当て。いいね数のような可換な操作なら CRDT

この分類で、Multi Leader が本当に必要な範囲は非常に小さくなります。」

深掘り: 「Spanner を使えば全部解決では？」
→ 「解決しますが、対価があります。マルチリージョン構成では書き込みに過半数の ack が必要で、遠隔リージョンを含むので +50〜100ms。単一リージョンの MySQL（1〜2ms）とは桁が違います。加えてコストも高い。
リージョン固定で衝突をゼロにできるなら、そちらが速くて安いので、まずそれを検討します。Spanner が正解になるのは『どうしてもグローバルなトランザクションが必要』な場合、例えば国をまたぐ送金や在庫の共有があるケースです。」

深掘り: 「ユーザーが旅行で別リージョンからアクセスしたら？」
→ 「読みはローカルレプリカで速く、書きだけホームリージョンへ転送します。旅行中の書き込みは全体の1%未満なので、そのユーザーの体験が少し遅くなるだけで済みます。『全員を最適化する』のではなく『99%を最適化して1%は許容する』という判断です。」

Q3 Twitter のようなタイムラインを設計してください（レプリケーションの観点で）

回答の骨格: 「タイムラインの本質は『書き込み時ファンアウト』か『読み取り時マージ』かの選択です。

  • 書き込み時ファンアウト: 投稿時に全フォロワーのタイムラインへ書き込む。読みが速い（1回の取得で済む）が、フォロワー100万人だと1投稿で100万回の書き込み
  • 読み取り時マージ: 表示時にフォロー中の全員の投稿を集めてマージ。書きが軽いが読みが重い
  • ハイブリッド（実際の解）: 通常アカウントはファンアウト、フォロワーが極端に多いアカウントだけ読み取り時マージ。読み取り時に「ファンアウト済みのタイムライン」+「セレブの最新投稿」をマージする

レプリケーションの観点では: タイムラインは結果整合で十分です。「フォローした人の投稿が3秒遅れて出る」ことを誰も問題にしません。だからタイムラインストアは Leaderless（Cassandra）や Redis でよい。
一方「自分の投稿が自分のタイムラインに出ない」は苦情になるので、自分の投稿だけは楽観的更新 + Leader 読みにします（read-your-writes、8章）。」

Q4 「保存しました」と出るのに、リロードすると消えています。原因は？

回答の骨格（切り分けの順序を見せる）: 「4つの可能性を順に確認します。

  1. read-your-writes 違反（最も可能性が高い）: 書き込みは Leader、読みはレプリカで、複製が間に合っていない。リロードのタイミング次第で見えたり見えなかったりするのが特徴。→ 書き込み後は Leader から読む
  2. Failover でのデータ損失: 非同期レプリケーション中に Leader が落ち、ack 済みだがレプリカに届いていない書き込みが失われた。常に消えるのではなく、障害時だけ。→ Semi-Sync にする
  3. MongoDB の rollback: w:1 で ack されたが過半数に届く前に Failover し、旧 Primary の復帰時に取り消された。→ w:majority にする
  4. アプリのバグ: トランザクションが commit されていない（暗黙のロールバック）、または UI が楽観的更新をしているだけでリクエストが失敗している

切り分け方: 「常に起きるか、たまに起きるか」がまず重要です。たまに = レプリケーション起因、常に = アプリのバグの可能性が高い。次に Leader に直接接続して SELECT し、データが存在するかを確認します。」

Q5 レプリカの Lag が10分に達しました。どう対処しますか？

回答の骨格: 「即座の対処と原因究明を並行します。

即座の対処: そのレプリカを読み取り対象から外す（ロードバランサから抜く）。10分古いデータを返し続けるほうが、そのレプリカが無いことより有害です。同時に Failover の昇格候補からも外します。

原因究明（グラフの形で切り分ける、8章 図8-2）:

  • 単調増加 → 処理能力の恒常的不足。並列適用（replica_parallel_workers + WRITESET）を確認。設定済みなら書き込み量自体が多すぎる
  • スパイク → 特定のバッチ。大量 UPDATE を1文で流していないか（RBR だと binlog が GB 単位になる）。1000行ずつに分割して sleep を挟む
  • 階段状に固定 → 適用が停止している。エラーログを確認（重複キー・テーブル不整合・ディスク満杯）
  • 特定のレプリカだけ → そのレプリカで重いクエリが動いていないか。PostgreSQL なら recovery conflict の設定も確認

恒久対策: ①分析用レプリカを分離する ②大量更新を分割する運用ルール ③Lag が閾値を超えたら自動的に読み取り対象から外す仕組みを入れる。」

Q6 RPO 0 かつ書き込みレイテンシ 5ms 以内を実現してください

回答の骨格: 「同一リージョン内の別AZに1台だけ準同期で実現します。

  • 同一リージョンの AZ 間 RTT は 1〜2ms 程度。ローカルの fsync 1ms を加えても合計 3〜4ms に収まります
  • PostgreSQL なら synchronous_commit = on + synchronous_standby_names = 'ANY 1 (s1, s2)'。2台のうちどちらか1台でよいので、1台の障害で止まりません
  • MySQL なら semi-sync + wait_for_replica_count = 1、wait_point = AFTER_SYNC
  • クロスリージョンのレプリカは非同期にします。同期にすると +120ms で要件を満たせません

やってはいけないこと: 全レプリカを同期にする。1台の GC 停止で全書き込みが止まり、可用性が単体構成より悪化します。」

深掘り: 「リージョン障害でも RPO 0 にしたいと言われたら？」
→ 「その要件は書き込みレイテンシ 5ms と両立しません。リージョン間の往復が最低でも数十ms かかるからです。物理法則なので投資では解決できません。
選択肢は3つで、①レイテンシ要件を緩める（リージョン間同期で +50〜100ms を受け入れる、Spanner 的な構成）、②RPO を緩める（リージョン障害時は数秒の損失を受け入れる）、③3リージョンに配置して Quorum を組む（近い2リージョンで過半数を作れば、レイテンシを抑えつつリージョン障害に耐えられる）。③が最も現実的な折衷案です。どれを選ぶかはビジネス判断なので、コストと影響を数字にして提示します。」

Q7 500GB のDBを、無停止で PostgreSQL 14 から 17 に上げてください

回答の骨格: 「論理レプリケーションを使います（19章）。

  1. PG17 の新サーバを構築し、スキーマを事前に作成（DDL は複製されないため）
  2. PG14 側に PUBLICATION、PG17 側に SUBSCRIPTION を作成。初期同期が始まる
  3. 追いつくまで待つ（500GB なら数時間〜1日）。この間、本番は無停止で動き続ける
  4. 追いついたら PG17 側で動作検証（本番と同じデータで、アプリの結合テストまでできる）
  5. 切替: 書き込みを一時停止 → 残りの複製を待つ → シーケンスの値を手動で合わせる → 接続先を切り替え。ダウンタイムは数十秒
  6. 問題があれば旧環境に戻せるよう、逆向きのレプリケーションも準備しておく

代替案との比較: pg_upgrade --link は速いですがダウンタイムが必要で切り戻しが困難。dump/restore は500GBなら数時間〜十数時間の停止。論理レプリケーション方式が、大規模DBほど有利です。
注意点: DDL が複製されない / シーケンスが複製されない / 大きなテーブルの初期同期に時間がかかる（テーブルを分割して段階的に同期する手もある）。」

Q8 レプリカが全部落ちました。何が起きますか？ どう備えますか？

回答の骨格: 「読み取りが全部 Leader に来るので、Leader が過負荷で潰れる可能性があります。これがレプリケーション構成で最も危険な連鎖障害です。
読み:書き = 9:1 のサービスで、Leader が書き込み分の容量しか持っていなければ、10倍の負荷が来ることになります。」

備え方（設計時に決めておく）:

  1. Leader に余裕を持たせる — 「レプリカが半減しても耐えられる」容量にしておく
  2. キャッシュ層で読みを吸収 — Redis があれば DB への読みを 80% 減らせる
  3. 流量制限（rate limit） — Leader への読みに上限を設け、超えたら劣化応答（古いキャッシュ、簡易表示）を返す。全部落ちるより一部を諦めるほうが良い
  4. サーキットブレーカ — Leader の応答が遅くなったら、重要でない機能から順に切る
  5. 準同期の自動降格を確認 — レプリカが全滅したとき、準同期で書き込みが止まらないか（MySQL はタイムアウトで非同期に降格するので止まらない）

設計書に書くべき一文: 「レプリカが全滅した時、Leader は耐えられるか？ 耐えられないなら何を諦めるか？」— これを明示しているかで設計の質が分かります。」

Q9 Cassandra を使うべきケースと、使ってはいけないケースを説明してください

使うべきケース: 「①書き込みが絶対に止まってはいけない（Leaderless なので Leader 障害という概念がない）②データが追記中心（時系列・ログ・イベント・メッセージ履歴・センサー）③数百ノード規模のスケールが必要 ④マルチDCで active-active（LOCAL_QUORUM で自然に表現できる）⑤アクセスパターンが確定している。
具体例: Netflix の視聴履歴、Discord のメッセージ履歴、IoT のセンサーデータ。」

使ってはいけないケース: 「①お金・在庫・座席（トランザクションが無く、LWW で静かにデータが消える）②一意制約が必要（メールアドレス重複禁止が保証できない）③クエリパターンが未確定（後から JOIN したくなって詰む。Cassandra は query-first 設計が前提）④運用体制がない（repair・compaction・tombstone 管理は専門知識が必要）。
私の判断基準は『RDBMS で足りるなら RDBMS』です。Cassandra の運用コストは高く、それを払う理由が明確でなければ選びません。」

Q10 レプリケーションを設計する上での、あなたの原則を3つ挙げてください

模範解答（これは「設計哲学」を見る問題）:

  1. 一貫性は一律に決めず、データ種別ごとに決める — 「このシステムは結果整合です」ではなく、「商品一覧はレプリカ、在庫の引き当ては Leader + トランザクション」と分ける。一貫性を上げるコストは高いので、必要な箇所を特定して払うのが設計です。
  2. タダで良くなる選択肢は存在しない、と考える — レプリカを増やせば読みはスケールするが書きは遅くなる。同期にすれば RPO 0 になるが可用性が下がる。「何を買って、何を払うか」を明示できないなら、その設計は理解できていないと考えています。
  3. 静かに壊れるものには監視を付ける — レプリケーションは止まってもアプリはエラーを出しません。準同期はタイムアウトで非同期に降格しても気づけません。「保険が生きているか」を平時に確認し続ける仕組みと、定期的な Failover 訓練をセットにします。訓練していない Failover は本番で動きません。

余裕があれば加える4つ目: 「まず Single Leader を選び、外す理由があるときだけ他を検討する。Multi Leader も Leaderless も、単純さを捨てる代わりに何かを得る選択です。その『何か』が本当に必要かを厳しく問います。」

設計ミスの「型」に還元すると5つしかない

  1. 古い値で「世界を変える」判断をした（#5, #6）→ 最も危険。金銭損失とセキュリティ事故になる。「読むだけ」と「判断に使う」を分け、後者は必ず Leader。レビューの最優先項目
  2. 保険が効いていることを確認していなかった（#1, #3, #16, #19）→ レプリケーションは静かに壊れる。「動いているはず」を監視で検証する
  3. 「死んでいるはず」という仮定を置いた（#11）→ 故障と遅延は区別できない。必ず Fencing する
  4. 縮退時の挙動を設計しなかった（#13, #14, #22）→ 「1台落ちたら残りはどうなるか」を必ず考える。冗長化は縮退設計とセット
  5. 複製の仕組みへの理解不足（#7, #8, #9, #12, #15）→ 並列適用・主キー・接続プール・super_read_only。知っていれば5分で防げるもの

付録 チートシート

1. レプリケーションを入れる判断

目的を4つから特定する: 可用性 / 耐久性 / 読みスケール / 地理的レイテンシ。目的が言えないなら入れない。書き込みのスケールには効かない（それは Sharding）。

2. 3軸で考える

①誰が書けるか（Single / Multi / Leaderless）②いつ ack するか（Async / Semi-Sync / Quorum）③何を運ぶか（物理 / 論理 / 文）。製品名でなく3軸で答えると設計に聞こえる。

3. トポロジ選択

トランザクション・一意制約が要る → Single Leader（9割はこれ）。複数地域から同じ行を更新 → リージョン固定を先に検討。書き込みが絶対に止まってはいけない追記データ → Leaderless。

4. 同期性の既定解

同一リージョンの1台だけ準同期（ANY 1）、残りは非同期、クロスリージョンは必ず非同期。全レプリカ同期は可用性が台数分の掛け算で劣化するので選ばない。

5. RPO / RTO の目安

Async: RPO 数秒〜分 / Semi-Sync: RPO 0 / Quorum: RPO 0 + 遅いノード耐性。
RTO は 自動Failover で10〜60秒、手動なら10分〜1時間。

6. Lag の3つの異常

read-your-writes（自分の書き込みが見えない）/ monotonic reads（時間が巻き戻る）/ consistent prefix（因果が逆転）。この3語で議論できると強い。

7. read-your-writes の実装

①書き込み後 N 秒はそのユーザーを Leader へ（実務の第一手）②LSN/GTID を持ち回って比較（正確）③UI の楽観的更新（併用前提）。

8. ルーティングの6ルール

①トランザクション内は全て Leader ②書き込み後 N 秒は Leader ③FOR UPDATE は Leader ④判断に使う SELECT は Leader ⑤分析は専用レプリカ ⑥Lag 超過レプリカは外す。

9. Quorum の算数

W + R > N で読み書き集合が必ず重なる。N は奇数（4台は3台と同じ耐障害性でコスト増）。W+R>N は線形化可能性を保証しない。

10. Failover の6ステップ

検知 → 選出 → 旧Leader隔離（Fencing） → 昇格 → 経路切替 → 事後処理。3を飛ばすと Split Brain。昇格候補は lag で制限する。

11. Split Brain 防止

過半数（少数派は自ら停止）+ リース（期限切れで自ら降格）+ fencing token（古い世代の書き込みを拒否）。3つ併用が理想。

12. ログ形式

物理=速い・同一バージョン必須 / 論理=遅い・バージョン跨ぎ可・CDC に使える。MySQL は ROW 形式一択。PostgreSQL のメジャーアップは論理レプリケーションで。

13. 衝突解決

優先順位: ①衝突を起こさない設計（リージョン固定） → ②CRDT → ③アプリ/UIで解決 → ④LWW。LWW はデータを黙って捨てるので、失ってよいデータのみ。

14. 監視すべき最重要4項目

①レプリケーションの生死 ②Lag（ハートビート方式で測る）③準同期の降格 ④非アクティブなスロット。全部「静かに壊れる」ので必ずアラート。

15. レプリカの役割分担

Failover 用（準同期・lag 厳格）/ 読み分散用（非同期・lag 監視）/ 分析用（非同期・昇格候補から除外）。役割ごとに閾値と設定を変える。

16. 縮退設計

設計書に必ず書く: 「レプリカが全滅した時、Leader は耐えられるか。耐えられないなら何を諦めるか」。答えが無いなら設計が未完成。

17. 製品の第一選択

迷ったら PostgreSQL / MySQL。AWS なら Aurora（Lag 小・レプリカ追加が速い）。グローバル強一貫が本当に必要なら Spanner。追記中心の大規模なら Cassandra。

18. 必ずやる運用

定期的な Failover 訓練（四半期に1回）/ バックアップの復元テスト / 遅延レプリカ1台（オペミス保険）/ 整合性チェック（pt-table-checksum、repair）。

この本を1文にまとめると

レプリケーションとは「可用性と読みスケールを買い、一貫性と運用の複雑さを支払う取引」である。
だから設計とは「どのデータに、どこまでの一貫性を払うか」を決めることであり、運用とは「支払った保険が本当に効くかを確認し続けること」（監視・Failover 訓練・復元テスト）である。

面接でも実務でも、「同期にします」より「ここは非同期で構いません、理由はこうです」と言える人のほうが信頼される。そして「レプリカが全滅したらどうなるか」を答えられる人は、さらに信頼される。
