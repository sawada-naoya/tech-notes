Software Testing Strategy · Confidence over Coverage

図解ソフトウェアテスト戦略
Coverageではなく、変更へのConfidenceを買う

テストフレームワークの使い方は扱わない。扱うのは判断だけ。
何をテストするか / どの層でテストするか / どこまでMockするか / どのバグをどのテストで防ぐか / そのコストに見合うConfidenceが得られるか。
テストは資産であると同時に負債でもある。書けば書くほど良いという前提を、最初に捨てる。

主張1

Testは「正しさの証明」ではない。「変更しても壊れていないと信じられる根拠」を買う行為。だから目的は Coverage ではなく Confidence。

主張2

Mockしたものはテストされない。全部Mockしたテストが緑でも本番は落ちる。どこをMockするかが、そのテストが何を保証するかを決める。

主張3

テストには実行コスト・保守コスト・失敗時の調査コストがある。価値がコストを下回るテストは削除するのが正しい。

00 この教材が扱う範囲

結論: テストの議論が噛み合わないのは、「何を保証したいのか」を言わずに「どう書くか」を話しているから。まず言葉を揃える。

扱わない — ツールの使い方

testify の書き方 / Jest の設定 / Playwright のセレクタ / モックライブラリのAPI。
検索すれば出てくるし、数年で変わる

扱う — 判断

このバグはどの層のテストで防げたか / このMockは何を保証しなくしたか / このテストは何分かけて何を守っているのか / 消してよいテストはどれか。

Coverage思考が生む2つの失敗

✕ 失敗1: 価値のないテストが増える

  • このテストが落ちる変更 = 意図的な変更だけ。バグを検出しない
  • リファクタのたびに機械的な修正が必要になる。変更の足かせになる
  • Coverageの数字だけが上がり、「テストがあるから安心」という誤った自信を生む

✕ 失敗2: 本当に怖い場所がテストされない

  • 並行実行、トランザクションのロールバック、Webhookの重複、外部APIの仕様変更
  • これらはUnit Testでは原理的に検出できない。だがCoverageの計算には現れない
  • 結果: Coverage 85%、しかし本番障害はすべてカバー範囲外から出る

この2つは同じ原因から出る — 「何を守りたいか」ではなく「どこが通っていないか」を見ているため。

▸ 本教材を貫く4つの問い

  1. このテストは、どんな変更が入ったときに落ちてほしいか（守る対象）
  2. このテストが緑でも起きうるバグは何か（保証の穴）
  3. このテストは何秒かかり、何分の保守を毎月要求するか（コスト）
  4. 同じConfidenceを、もっと安い層で得られないか（配置）

テストを書く前・レビューするとき・消すか迷ったときに、この4つを聞く。

▸ 前提と表記

  • コード例は Go（標準の testing 中心）と TypeScript/React。題材はEC（Purchase機能）で統一する
  • レイヤーの表記: UNIT INTEGRATION API E2E PRODUCTION 防げない

00.5 Confidence vs Cost

テスト戦略とは「限られた予算で、どこにConfidenceを買うか」の配分問題。この図が本教材の全体地図になる。

図0.1 — 右上ほど「本番に近い確信」だが高価。戦略とは、この曲線上のどこに何本配置するかを決めること

▸ 配分の原則

  1. 同じConfidenceなら、より安い層で買う — 価格計算の検証にE2Eを使わない
  2. 安い層では買えないConfidenceがある — SQL・制約・並行性・配線・実際のブラウザ挙動
  3. 本数ではなく「守っているリスク」で数える — Unit 500本より、Integration 20本のほうが重要なことがある
  4. 最上段（本番監視）は代替不可 — どれだけテストしても、本番が動いている確信はデプロイ後にしか得られない（→ 19章）

Part 1

土台 — 目的・配置・単体

「なぜ書くのか」が曖昧なまま「どう書くか」を議論すると、テストは形式になる。目的を5つに分解し、それぞれがどの層で得られるのかを対応づけるところから始める。

01 なぜTestを書くのか

結論: テストの効用は5つあり、どれを狙っているかでテストの書き方が変わる。全部を1本のテストで狙うと、どれも半端になる。

1-1. 5つの効用

効用内容これを狙うときの書き方主な層
① Regression（回帰防止）一度直したバグが再発しないバグ修正時に、そのバグを再現するテストを先に書くUNIT INT
② Specification（仕様の表現）「この入力ならこの結果」が読めるテスト名を仕様文にする。実装ではなく振る舞いを書くUNIT
③ Design Feedback（設計の圧力）テストしにくさが設計の悪さを教える先にテストを書く。準備が長いなら依存が多すぎるUNIT
④ Refactoring Safety内部を変えても壊れていないと分かる公開された振る舞いだけを検証する。内部呼び出しを検証しないINT API
⑤ Documentation使い方の実例になる現実的な入力を使う。foo test1 のような値を避けるUNIT API

▲ ④ Refactoring Safety が最も見落とされる

  • リファクタとは「振る舞いを変えずに内部を変えること」。だからリファクタで落ちるテストは、リファクタの役に立たない
  • 内部のメソッド呼び出し回数を検証するテストは、実装を1つに固定してしまう。関数を分割しただけで赤くなる
  • 「テストがあるのにリファクタが怖い」状態は、テストが実装に密着しすぎているサイン
  • 判定: 「振る舞いを変えずに実装だけ書き換えたとき、このテストは緑のままか？」

1-2. テストは資産であり負債でもある

図1.1 — 「テストは多いほど良い」は成立しない。価値がコストを下回るテストは削除するのが正しい判断

✓ 消してよいテストの見分け方

  • 過去1年で一度も落ちていない、かつ落ちる想像ができない — getterのテストなど
  • 落ちるのは常に「意図的な変更をしたとき」だけ — バグを検出したことがない
  • 同じ内容を上位層のテストが確実にカバーしている — 重複は1本にまとめる
  • Flakyで、再実行で通すのが習慣になっている — 修正するか消すか。放置が最悪（→ 17章）
  • ただし「消す」判断は、なぜ消すのかをコミットメッセージに残す。後から「なぜこのケースが守られていないのか」を追えるように

1-3. Design Feedback — テストしにくさは設計の問題

✕ テストしにくいコード

  • テストが書けない = 呼び出し側も制御できない
  • 本番でも「年末だけ挙動が変わる」ことに気づけない

✓ 依存を引数にする

  • テストしやすさ = 依存が明示されているということ
  • 「テストのために設計を歪めた」のではなく、テストが設計の問題を可視化した

▸ ただし「テストのための設計」には限度がある

  • すべてをinterfaceにして注入可能にすると、実装を追うのに5ファイル開く必要があるコードになる
  • 注入する価値があるのは「テストで制御したいもの」だけ — 時刻、乱数、外部通信、DB、ID生成
  • それ以外（内部のヘルパー関数、値オブジェクト）は直接呼んでよい。抽象化のコストもまた負債

✓ これだけ覚える

  • テストの効用は5つ。どれを狙うかで書き方が変わる
  • リファクタで落ちるテストは、リファクタの役に立たない
  • テストは資産であり負債。価値がコストを下回るなら消す
  • テストしにくさは設計の問題を教えている。注入するのは「制御したいもの」だけ

⇄ Trade-off

  • テストを増やす → 回帰を防げる / CI時間と保守コストが増え、変更が重くなる
  • 厳密に検証する → 細かいバグを検出 / 意図的な変更のたびに落ち、信頼されなくなる
  • 依存を全部注入可能に → テストしやすい / 抽象化が増え、コードが追いにくくなる

✕ よくある失敗

  • Coverageのためにgetterをテストする — 数字は上がるが何も守らない
  • 内部メソッドの呼び出し回数を検証する — リファクタが不可能になる
  • 落ちるテストを一律で「直す」 — 仕様変更なら消す・書き換えるのが正しい
  • テストを消すことを禁止する文化 — 腐ったテストが永久に残る

? 設計時に自問する質問

  • このテストはどんなバグが入ったときに落ちるか
  • 実装を書き換えたら（振る舞いは同じ）、このテストは緑のままか
  • このテストは過去にバグを検出したことがあるか
  • 1年後の自分がこのテストを読んで、何の仕様か分かるか

結論: ピラミッドは「本数の比率」ではなく「コストと確信のトレードオフ」を表した図。「Unit 70% / Integration 20% / E2E 10%」という数字を守ることが目的ではない。

2-3. ピラミッド批判と Testing Trophy

▲ なぜ「Integrationを厚く」という主張が出てきたか

  • Unitを増やしても本番障害が減らなかったという経験の蓄積。障害の多くは「部品」ではなく「部品の間」で起きる
  • 型システムと静的解析が強くなった — 昔Unitで検出していた型の誤りは、コンパイル時に落ちる
  • 実行環境が速くなった — Docker・インメモリDB・並列実行で、Integrationのコストが下がった
  • 結果として、「中間層（Integration / API Test）を最も厚くする」という形（Testing Trophy）が支持されている

▸ どちらが正しいか、ではなく

  • ロジックが複雑なプロダクト（料金計算・在庫配分・スケジューリング）→ Unitが厚くなる。それが正しい形
  • CRUDが中心のプロダクト（管理画面・業務システム）→ Unitに書くことがほぼない。API Testを厚くするのが正しい
  • UIの状態遷移が複雑（エディタ・ダッシュボード）→ Component Testが厚くなる
  • 形は結果。「自分のプロダクトで壊れやすいのはどこか」から逆算する

? Thinking Point

CRUDばかりの管理画面APIで、Unit Testはほぼ書けない。これは「テストが足りない」のか？

考えてから開く

足りないのではなく、Unitで守るものが存在しない。

  • CRUDのUseCaseは「Repositoryを呼んで結果を返す」だけ。Repositoryをモックしてこれをテストすると、検証しているのは「モックを呼んだこと」だけになる（→ 8章）
  • そこで実際に壊れるのは、SQLの誤り・JSONのフィールド名・認可の漏れ・バリデーションの抜け。どれもUnitでは検出できない
  • 正しい対応: API Test（HTTPリクエスト → 実DB）を厚くする。1本で「配線 + SQL + JSON + 認可」を同時に守れるので、費用対効果が最も高い
  • 結論: 「Unitが少ない」は問題ではない。「壊れる場所にテストが無い」が問題

✓ これだけ覚える

  • ピラミッドは比率の指示ではなく、コストと確信の関係図
  • 重要なのは「下の層が保証しないものを、上で買っているか」
  • 形はプロダクトの性質で変わる。CRUD中心ならAPI Testが主役
  • 障害の多くは「部品」ではなく「部品の間」で起きる

⇄ Trade-off

  • Unitを厚く → 高速・原因が明確 / 配線・SQL・統合の誤りを検出できない
  • Integrationを厚く → 現実の障害に近いものを防げる / 遅く、並列化とデータ分離の工夫が要る
  • E2Eを厚く → ユーザー視点の確信 / Flaky・遅い・保守が重い。本数を増やせない

✕ よくある失敗

  • 「Unit 70%」を目標値として守る — プロダクトに合わない形を強制する
  • E2Eで異常系を網羅しようとする — CIが1時間を超え、誰も待たなくなる
  • 中間層が空洞 — Unitは大量、E2Eは数本、その間が無い。最も障害が出る領域が無防備
  • 層の役割を決めずに書く — 同じことを3層で検証し、変更のたびに3箇所直すことになる

? 設計時に自問する質問

  • 過去の本番障害は、どの層のテストがあれば防げたか
  • この層で保証できないことは何か。それはどこで買っているか
  • 同じ検証を複数の層で重複させていないか
  • CIの総実行時間は何分か。開発者は待てているか

03 Unit Test

結論: Unit Testの価値は「分岐が多く、人間が頭で追えない計算」にある。分岐がないコードをUnitでテストしても、得られるConfidenceはほぼゼロ。

3-1. 何をUnitでテストするか

対象Unitで書く価値理由
純粋関数（料金計算・日付計算・バリデーション）最も高い入力の組み合わせが多く、境界値が事故る。実行が速いので網羅できる
Domain（状態遷移・不変条件）高い「発送済みはキャンセル不可」などのルールが、コードで表現され検証される
UseCase（分岐・エラー処理・呼び出し順序）条件付き分岐があるなら価値がある。単に流すだけなら価値がない
Repository低いSQLの正しさはモックでは検証できない。Integrationの領域（→ 5章）
Handler低いJSON・Status・認可は実際にHTTPを通さないと意味が薄い（→ 6章）
getter / setter / DTOの変換ほぼ無価値落ちる想像ができないなら書かない

3-2. 純粋関数のTable Driven Test

▸ Table Driven Testの要点

  • nameは仕様文にする — "case1" ではなく "送料無料の1円手前"。失敗時の出力がそのまま仕様の説明になる
  • 境界値を必ず含める — ちょうど / 1つ手前 / 1つ後。バグの大半はここに出る
  • ケースを足すコストをゼロに近づける — 新しい仕様が来たら1行足すだけ。これが最大の利点
  • ループ内で t.Run を使う — 失敗したケース名が表示され、個別実行もできる
  • テーブルが巨大になったら分割する — 30ケースを超えたら、観点ごとに関数を分ける

■ Table Driven の落とし穴

  • 構造体にフラグが増えていく — wantErr bool skipValidation bool setupDB bool と増えると、テーブルが読めなくなる。別の関数に分ける合図
  • 期待値を計算式で書く — want: tt.subtotal * 108 / 100 のように書くと、実装と同じ間違いをする。期待値はリテラルで書く
  • ループ変数のキャプチャ — Go 1.22未満では tt := tt が必要。並列実行時に全ケースが最後の値になる

3-3. Domain のテスト — 状態遷移と不変条件

▸ テストデータビルダを用意する

  • 準備コードが本体より長いテストは、読まれない。読まれないテストは保守されない
  • 「デフォルトは妥当な値、テストで関心のある項目だけ上書き」という形にする
  • これにより、テストを読むと「何が重要か」が一目で分かる（上書きした項目 = そのテストの関心事）
  • フィールドを1つ追加したときに全テストを直す必要もなくなる

3-4. UseCase のテスト — 書く価値があるかを見極める

✕ 価値の薄いUseCaseテスト

✓ 価値のあるUseCaseテスト

  • 「起きてはいけないこと」を検証している
  • この順序を逆にした実装は、必ずこのテストで落ちる

▸ UseCaseテストを書く判断

  • 分岐があるか — if がなく上から下に流すだけなら、API Testで十分
  • 副作用の順序・有無に意味があるか — 「失敗したら課金しない」「成功したらイベントを出す」
  • 異常系の網羅が必要か — 外部が失敗したとき、ロールバックされるか・引当が解放されるか
  • この3つが無いUseCaseに、Unit Testは不要。書いても「モックの設定を書き写した」だけになる

3-5. Unit Testの書き方の基準

基準理由
1テスト1観点落ちたときに何が壊れたか即座に分かる。アサーションを10個並べない
Arrange / Act / Assert を視覚的に分ける空行で区切るだけでよい。何を準備し何を実行したかが読める
時刻・乱数・IDを固定するFlakyの最大の原因（→ 17章）。注入して固定値を渡す
エラーは errors.Is / As で比較メッセージ文字列で比較すると、文言変更で落ちる
ヘルパーには t.Helper()失敗時の行番号が、ヘルパー内部ではなく呼び出し側になる
テストは並列（t.Parallel()）を既定に速い。かつ「共有状態に依存していない」ことの証明になる

✓ これだけ覚える

  • Unitの価値は「分岐が多く人間が追えない計算」にある
  • Table Drivenは境界値を並べるための道具。nameを仕様文にする
  • 期待値はリテラルで書く。計算式で書くと実装と同じ間違いをする
  • UseCaseは分岐・副作用の順序・異常系があるときだけUnitで書く

⇄ Trade-off

  • Table Drivenにする → ケース追加が1行 / フラグが増えると読めなくなる
  • 個別の関数に分ける → 意図が明確 / 重複が増える
  • テストビルダを作る → 準備が短く読みやすい / ビルダ自体の保守が必要
  • UseCaseをUnitで書く → 異常系を網羅できる / モックの保守が発生し、実態との乖離が起きる

✕ よくある失敗

  • 期待値を実装と同じ式で計算 — 実装のバグをそのまま期待値にしてしまう
  • エラーメッセージの文字列比較 — 文言を直しただけで落ちる
  • time.Now() をそのまま使う — 月末・年末・うるう年に突然落ちる
  • 準備コードが本体の3倍 — 誰も読まなくなり、やがて消される

? 設計時に自問する質問

  • この関数の境界値は何か。テーブルに入っているか
  • このUseCaseに分岐はあるか。無いならUnitで何を守るのか
  • このテストは来月の月末に落ちないか
  • 失敗時の出力を見て、原因が分かるか

04 Mock / Stub / Fake / Spy

結論: Test Doubleの選択は「何を保証したいか」の宣言。Mockを選んだ時点で「呼び出し方を固定する」と決めており、Fakeを選んだ時点で「振る舞いだけ見る」と決めている。

4-1. 5種類の違い

種類中身検証するもの使いどころ
Dummy渡すだけで使われない何も検証しない引数を埋めるためだけ
Stub決まった値を返す戻り値に応じた結果「外部が失敗したらどうなるか」を作る
Spy実際の動作 + 呼び出しを記録呼ばれたか・何回・どの引数か「課金されていないこと」の確認
Mock期待する呼び出しを事前に宣言し、違反したら失敗相互作用（呼び出し方）そのもの呼び出し自体が仕様のとき（メール送信など）
Fake簡易だが動く実装（インメモリDB等）結果の状態Repositoryの代替。最も扱いやすい

▲ Mock と Stub/Fake の決定的な違い

  • Stub/Fake は「状態」を検証する — 実行後にどうなっているかを見る。実装を変えても、結果が同じなら緑のまま
  • Mock は「相互作用」を検証する — どう呼んだかを見る。実装を変えると、結果が同じでも赤くなる
  • つまりMockはリファクタ耐性を犠牲にして、呼び出し方を固定する。それが必要な場面でだけ使う

✓ FakeがMockより優れている点

  • テストごとに期待値を書かなくてよい — Mockは全テストで EXPECT() を書く必要がある
  • リファクタで壊れない — 呼び出し回数や順序を変えても、結果が同じなら緑
  • 複数回の操作を自然に書ける — 「保存してから取得する」がそのまま動く
  • テストが読みやすい — モック設定のノイズが消え、何を検証しているかが明確になる
  • コスト: Fakeを1つ書く手間。ただし1回書けば全テストで使い回せる

4-2. どこをMockすべきか — 境界の判断

図4.1 — 差し替えた境界の向こう側は、そのテストでは一切保証されない

4-3. Mockしてはいけないもの

■ やってはいけない差し替え

  • Domainオブジェクトをモックする — mockOrder.EXPECT().Total().Return(6000)。計算ロジックを検証しなくなるので、テストの意味が消える
  • テスト対象そのものを部分モックする — 一部のメソッドだけ差し替える（Partial Mock）。「テストしていない実装」が混ざる
  • 標準ライブラリをモックする — json.Marshal を差し替える必要があるなら、設計が間違っている
  • 自分が書いたユーティリティ関数をモックする — そのまま呼べばよい。速いし、実際の挙動が検証される
  • DBドライバをモックする（sqlmock等でSQL文字列を比較） — SQLの構文的一致を検証するだけで、実際に動くかは分からない（→ 5・20章）

? Thinking Point

sqlmock でRepositoryをテストするのは有効か？

考えてから開く

ほぼ有効でない。検証しているのは「自分が書いたSQL文字列と、自分が書いた期待文字列が一致すること」だけ。

  • 検出できないもの: 構文エラー、カラム名の誤り、型の不一致、JOIN条件の誤り、NULL の扱い、索引が効かない、制約違反、トランザクションの挙動
  • 実際に起きること: sqlmockのテストは緑。本番で Unknown column 'users.emial' で落ちる
  • 例外的に使える場面: 「DBエラーが返ってきたときのハンドリング」を検証したいとき。エラーを注入する目的なら意味がある
  • 正しい方法: Repositoryは実DBでテストする（→ 5章）。速度が問題なら、実行するテスト数を絞る

4-4. 選択のDecision Tree

この依存をどう扱うか？ ├─ 自分が書いた純粋なコードか？ │ └─ YES → そのまま呼ぶ （差し替えない。速いし実際の挙動が検証される） ├─ 実行すると外部に副作用が出るか？（課金・メール送信・SMS） │ └─ YES → Spy か Fake で差し替える + Contract Testで実物を別途検証（→12章） ├─ DBか？ │ ├─ 検証したいのはSQL・制約・トランザクションか？ │ │ └─ YES → 実DBを使う（Integration） （→5章） │ └─ 検証したいのはUseCaseの分岐か？ │ └─ YES → Fake Repository ├─ 時刻・乱数・ID生成か？ │ └─ YES → 必ず注入して固定する （Flakyの最大要因 →17章） ├─ 「呼ばれたこと自体」が仕様か？ │ └─ YES → Spy で回数・引数を検証 （「失敗時に課金しない」など） └─ 呼び出しの順序・引数が厳密な契約か？ └─ YES → Mock （使う場面は少ない。リファクタ耐性を失う覚悟で）

✓ これだけ覚える

  • 差し替えた境界の向こう側は、そのテストでは保証されない
  • 迷ったらFake。Mockはリファクタ耐性を犠牲にする
  • Domainと自分のコードは差し替えない。差し替えてよいのは外部・DB・時刻・乱数
  • sqlmockでSQL文字列を比較しても、SQLが動くことは検証できない

⇄ Trade-off

  • Mock → 相互作用を厳密に固定できる / 実装変更で落ち、テストが実装の写経になる
  • Fake → 読みやすくリファクタに強い / Fake自体の実装コストと、本物との乖離
  • 実物を使う → 乖離がない / 遅い・不安定・副作用
  • Stubで失敗を注入 → 異常系を網羅できる / 現実に起きない失敗を作り込むことがある

✕ よくある失敗

  • 全部Mockして「Unit Test」と呼ぶ — 検証しているのはモックの設定だけ（→ 8章）
  • Fakeが本物とズレる — 本物はUNIQUE制約で落ちるが、Fakeは通す。定期的に整合を確認する
  • Partial Mock — テスト対象の一部を差し替え、何をテストしているか分からなくなる
  • モックの設定が本体より長い — 読めないテストになり、保守されない

? 設計時に自問する質問

  • この差し替えによって、検証されなくなったものは何か
  • それは別のテストで買っているか
  • 実装をリファクタしたら、このテストは落ちるか
  • Fakeの挙動は、本物と同じ条件で失敗するか

Part 2

統合の層 — 部品の「間」を守る

本番障害の多くは、部品そのものではなく部品の接続点で起きる。SQL、シリアライズ、DIの配線、認可、外部との認識のズレ。ここを守る層が、実務では最も費用対効果が高い。

05 Integration Test

結論: Repositoryは実DBでテストする。SQLの正しさを検証する手段は、実際にそのDBで実行する以外に存在しない。

5-1. Integrationが唯一守れるもの

検出できる問題Unitで検出できるか
SQLの構文エラー・カラム名の誤字不可
JOIN条件の誤り・重複行の発生不可
UNIQUE / FK / CHECK 制約の違反不可
型の不一致（DECIMAL↔float、DATETIME↔string）不可
NULLの扱い（NOT IN と NULL、COUNT の挙動）不可
トランザクションのロールバック範囲不可
マイグレーションの適用漏れ・順序不可
文字コード・照合順序（大文字小文字・全角半角）不可
タイムゾーンの変換ミス不可
ORMが生成するSQLが意図と違う不可

▲ これらは全て「本番で起きる障害の常連」

そしてどれも、Unit Testが100%緑でも起きる。
Coverageを80%から90%に上げる工数を、Repository Testの整備に使うほうが、本番障害は減る。

5-2. SQLiteで代替してよいか

✕ SQLiteで代替した場合に通り抜けるもの

  • SQLの方言差 — ON DUPLICATE KEY UPDATE、INSERT IGNORE、ウィンドウ関数の挙動差
  • 型の扱い — SQLiteは型が緩い。VARCHAR(10) に100文字入る。本番では切り詰め or エラー
  • 照合順序 — MySQLの既定は大文字小文字を区別しない。SQLiteは区別する。「Aさん」と「aさん」の重複判定が逆になる
  • ロックの粒度 — SQLiteはDB単位ロック。行ロック・ギャップロック・デッドロックを再現できない
  • 同時実行 — 並行テストが書けない（→ 10章）
  • 日付関数・文字列関数 — 名前も挙動も違う

✓ 実MySQLを使う（Testcontainers等）

  • 本番と同じバージョン・同じスキーマ
  • CIでもローカルでも同じ手順で動く
  • 起動は10〜20秒。テストごとではなくパッケージごとに1回

▸ 「SQLiteでもいい」場合はあるか

  • 本番もSQLiteなら当然よい
  • SQLを一切書かず、ORMの基本的なCRUDしか使わないなら、リスクは下がる。ただしそれでも型と照合順序の差は残る
  • 判断: 「本番と違うDBでテストする」というのは、テスト結果の意味を弱める決定。速度のために意図的に選ぶのは構わないが、無自覚に選ばない

5-3. テストデータの分離戦略

方式やり方速度並列注意
トランザクションでロールバックテスト開始時にBEGIN、終了時にROLLBACK最速接続を分ければ可テスト対象がトランザクションを使うと入れ子になり、コミットの挙動を検証できない
毎回TRUNCATEテストごとに全テーブルを空にする中不可（共有DB）FK順序を考慮する必要。確実で分かりやすい
テストごとにDB/スキーマを作る並列ワーカーごとに別スキーマやや遅い可最も安全。Goなら t.Parallel() と相性が良い
一意なデータを使うテストごとに異なるIDプレフィックス速い可集計系テストが書けない（他のテストのデータが混ざる）

✓ Repository Testで必ず書くべきケース

  • 認可条件が効いているか — 他人・他テナントのデータが取得できないこと。一覧系は特に
  • 0件・1件・複数件 — 0件のときにエラーかnilか空スライスか
  • 制約違反の挙動 — 重複INSERTで期待通りのエラー型が返るか
  • NULL・ゼロ値の往復 — 保存して取得したとき、同じ値になるか（タイムゾーン・精度）
  • ページング — 境界（最終ページ・件数ちょうど）
  • 全メソッドを網羅する必要はない。「複雑なSQL」と「認可条件があるSQL」を優先する

5-4. Redis / Queue / 外部サービス

対象推奨理由
Redis実物（Testcontainers / miniredis）TTL・アトミック操作・Luaスクリプトの挙動はモックで再現できない。miniredis は軽量で実用的
Queue（SQS / RabbitMQ）Fake + 実物を1本大半はFakeで十分。可視性タイムアウト・DLQ の挙動だけ実物で確認（→ 11章）
S3 / オブジェクトストレージ互換実装（MinIO等）署名URL・権限・マルチパートの挙動が再現できる
外部API（決済など）Mock Server + Sandbox実物を毎回叩けない。使い分けは12章
メール送信Spy（送信内容を記録）実送信は不要。「誰に何を送ったか」だけ検証する

5-5. 速度との折り合い

⇄ Integrationが遅くなったときの手

  • 並列化する → 最も効く。スキーマ分離 + t.Parallel() で台数分の高速化
  • コンテナを使い回す → 起動コストを1回に。状態が残るのでデータ分離が前提
  • タグで分ける → go test -short でIntegrationをスキップし、PRでは全実行（→ 18章）
  • マイグレーションを毎回流さない → スキーマ作成済みのテンプレートDBをコピーする
  • 本数を絞る → 全Repositoryメソッドではなく、複雑なSQLと認可条件だけに絞る

✓ これだけ覚える

  • SQLの正しさは、実DBで実行する以外に検証できない
  • SQLite代替は型・照合順序・ロック・方言の差を通り抜ける
  • データ分離はスキーマ分離 + 並列が最もスケールする
  • Repository Testは認可条件と複雑なSQLを優先する

⇄ Trade-off

  • 実DB → 本番と同じ挙動 / 起動コストと実行時間
  • インメモリDB → 高速 / 方言・型・ロックの差で偽の安心を生む
  • トランザクションでロールバック → 最速 / コミット・トランザクション自体の検証ができない
  • スキーマ分離 → 並列可・確実 / セットアップが必要で、やや遅い

✕ よくある失敗

  • sqlmockでRepositoryをテストして満足する — SQLが動くことは検証できていない
  • テスト間でデータが残る — 実行順序で結果が変わるFlakyの温床（→ 17章）
  • 本番と違うバージョンのDB — MySQL 5.7とMySQL 8.0では挙動が違う
  • マイグレーションをテスト用に手書き — 本番のスキーマとズレる。本番と同じマイグレーションを流す

? 設計時に自問する質問

  • このSQLが間違っていたら、どのテストが落ちるか
  • テスト用DBは本番と同じバージョン・同じ照合順序か
  • テストを並べ替えて実行しても、全部通るか
  • 認可条件の付いたクエリに、他人のデータでのテストがあるか

06 API Test / Contract Test

結論: API Testは費用対効果が最も高い層。1本で「配線・シリアライズ・バリデーション・認可・SQL・Status」を同時に守れる。

6-1. どこまで通すか

図6.1 — 外部APIだけを差し替え、それ以外は実物を通す。これが最も費用対効果が高い構成

✓ API Testで必ず書く4本

  1. 正常系1本 — レスポンスの形とDBの状態を両方検証する
  2. 認可1本 — 他人のリソースで404/403になること。これが最も事故を防ぐ
  3. バリデーション1本 — 422とエラーコード・フィールド名
  4. 主要な業務エラー1本 — 在庫不足・状態不正など、Clientが分岐する409系

異常系を全部書く必要はない。細かい組み合わせはUnit（UseCase）に任せ、API層では「Statusとエラーコードの対応が正しいか」を確認する。

6-2. Contract Test — 2つのサービスの認識を揃える

■ Contract Testが解く問題

サービスA（Consumer） サービスB（Provider） 「注文APIは status を返す」 「status は order_status に と思ってコードを書いた リネームした。誰も使ってないはず」 Aのテスト: Bをモックして緑 ✓ Bのテスト: 自分のAPIをテストして緑 ✓ 本番: Aが落ちる ✕ 両者のテストが緑なのに壊れる。これが「モックの嘘」

⇄ Contract Test を導入するか

  • 導入する価値が高い — 複数チームがそれぞれのサービスを持ち、独立にデプロイしている。結合テスト環境を全部立てるのが現実的でない規模
  • 価値が低い — 単一チーム・モノリス・同時デプロイ。この場合はAPI Testで十分
  • 代替手段 — OpenAPIスキーマをCIで検証し、破壊的変更を検出する。Contract Testより軽量で、多くのケースで足りる
  • コスト — 契約の管理基盤（Pact Broker等）、CIでの双方向連携、チーム間の合意プロセス

? Thinking Point

フロントエンドとバックエンドが同じリポジトリ・同じチームなら、Contract Testは要らないか？

考えてから開く

Pactのような仕組みは不要だが、「型の共有」という形で同じ問題を解く必要がある。

  • 同時デプロイできるなら、破壊的変更の問題は小さい。両方を同時に直せる
  • ただしモバイルアプリが混ざると話が変わる — 古いアプリが数ヶ月生き残るため、実質的に別チーム・別デプロイと同じ制約になる
  • 最も安い解: OpenAPIからフロントの型を自動生成する。バックがフィールド名を変えたら、フロントがコンパイルエラーになる。これはテストより早く・確実に検出できる
  • それでも検出できないのは「型は同じだが意味が変わった」ケース（amount が円から銭になった等）。ここはAPI Testの期待値で守る

✓ これだけ覚える

  • API Testは1本で配線・JSON・認可・SQL・Statusを同時に守る。最も費用対効果が高い
  • 外部APIだけ差し替え、それ以外は実物を通す
  • 必ず書く4本: 正常系 / 認可 / バリデーション / 主要な業務エラー
  • レスポンスだけでなくDBの状態も検証する

⇄ Trade-off

  • API Testを厚く → 現実の障害を防げる / 遅い。異常系の網羅には向かない
  • Contract Test導入 → サービス間の齟齬を防げる / 基盤とプロセスのコスト
  • OpenAPIからの型生成 → 最も安く、コンパイル時に検出 / 型が同じで意味が変わる変更は防げない

✕ よくある失敗

  • Handlerを関数として直接呼ぶ — ミドルウェア（認証・認可）を通らず、最重要の検証が抜ける
  • レスポンスだけ見てDBを見ない — 「200を返したが保存されていない」を見逃す
  • API Testで異常系を全網羅 — 遅くなりすぎる。Unitに任せる
  • 両者がモックでテストして安心する — 契約のズレは検出されない

? 設計時に自問する質問

  • このテストは認証・認可ミドルウェアを通っているか
  • レスポンスのフィールド名を変えたら、このテストは落ちるか
  • DBに正しく保存されたことを検証しているか
  • Clientが依存しているフィールドは、どこで守られているか

07 E2E

結論: E2Eは「ユーザーが目的を達成できる」という唯一の証明。ただし高価なので、本数ではなく「落ちたら事業が止まる経路」の数だけ書く。

7-1. E2Eでしか検出できないもの

検出できる問題なぜ下位層では無理か
ボタンがクリックできない（他要素が重なっている）実際に描画しないと分からない
フロントとバックのURL・パラメータの不一致両者を実際に繋がないと分からない
ビルド後のバンドルで壊れる（環境変数・パス）ビルド成果物を動かす必要がある
CORS・Cookie・認証セッションの設定ミス実ブラウザの制約でしか再現しない
リダイレクト・履歴・戻るボタンの挙動ブラウザの機能
画面遷移をまたぐ状態の引き継ぎアプリ全体の結合が必要
「注文が完了しましたと表示される」これがユーザーにとっての唯一の成功条件

7-2. Flaky / Slow / Expensive

■ E2Eが信用されなくなるまでの典型的な経過

第1段階
E2Eを20本書く。CIで8分かかるが、価値があるので許容される
第2段階
本数が80本に増える。CIが35分になる。開発者はPRを出してから別の作業を始めるようになる
第3段階
週に2〜3本がランダムに落ちるようになる。原因は待ち時間・アニメーション・並行実行時のデータ競合
第4段階
「E2Eが落ちたらとりあえず再実行」が習慣になる。赤が情報を持たなくなる
第5段階
本物のバグでE2Eが落ちたが、いつも通り再実行され、そのままマージされる
結論
E2Eの敵は「遅さ」ではなく「信頼されなくなること」。1本でも恒常的に不安定なテストがあると、スイート全体の価値が失われる

✓ E2Eを維持可能にする規律

  • 本数の上限を決める — 「Critical Pathのみ、最大20本」のように明示的に制限する。追加するなら何かを消す
  • 固定の待ち時間を禁止する — sleep(3000) は遅く、かつ不安定。条件待ち（要素が表示されるまで）を使う
  • テストデータをテスト内で作る — 共有のシードデータに依存すると、他のテストの影響を受ける
  • UIからのセットアップを避ける — ログインや事前データはAPIで作る。検証したい経路だけをUIで操作する
  • Flakyを検出したら即座に隔離する — 修正するまでスイートから外す。「たまに落ちる」を放置しない（→ 17章）
  • セレクタは data-testid — CSSクラスやテキストに依存すると、デザイン変更で全部壊れる

7-3. 何本書くか — Critical Pathの選び方

▸ 「落ちたら事業が止まる経路」だけを列挙する

ECの場合E2Eに含めるか理由
商品を検索して購入する含めるこれが止まると売上がゼロになる
ログイン・新規登録含める止まると全機能が使えない
決済（サンドボックス）含める金銭に直結。外部との結合点
注文履歴の閲覧1本だけ止まっても売上は止まらない
商品のソート・絞り込みの全パターン含めないAPI Testで十分。E2Eでやると組み合わせ爆発
バリデーションエラーの全種類含めないComponent TestかAPI Testの領域
管理画面のCRUD基本含めない影響範囲が社内に限られる

目安: E2Eは「サービスが生きているか」を確認するもの。細かい振る舞いの検証には使わない。

7-4. E2Eと本番監視は同じもの

▸ 同じテストを本番に向ける

  • Critical PathのE2Eは、そのままSynthetic Monitoringとして本番に定期実行できる（→ 19章）
  • ステージングで通っても本番で落ちる原因（設定・証明書・DNS・外部連携）を、これで検出できる
  • 本番で実行するなら、テスト用アカウント・決済のサンドボックス・データのクリーンアップを設計する
  • 「E2Eを書く」と「本番監視を作る」を別々にやらない。同じ資産を2箇所で使う

✓ これだけ覚える

  • E2Eの価値は「ユーザーが目的を達成できる」ことの唯一の証明
  • 敵は遅さより「信頼されなくなること」。1本のFlakyがスイート全体を殺す
  • 準備はAPI、検証だけUI。固定待ちを使わない
  • 本数の上限を決める。Critical Pathのみ

⇄ Trade-off

  • E2Eを増やす → 本番に近い確信 / CI時間・Flaky・保守コストが指数的に増える
  • 最小限にする → 高速で信頼できる / UIの細かい不具合は検出されない
  • 準備をAPIで行う → 速く安定 / 「実際の登録フロー」は検証されない
  • 全てUIで操作 → 本物に近い / 遅く、些細な変更で壊れる

✕ よくある失敗

  • sleep で待つ — 遅いうえに、負荷が高い日に落ちる
  • Flakyを再実行で回避する運用 — 赤が情報を持たなくなる
  • E2Eで異常系を網羅 — 100本を超えてCIが崩壊する
  • 共有のシードデータに依存 — 他のテストが変更すると落ちる

? 設計時に自問する質問

  • このE2Eが落ちたら、事業が止まるか
  • 同じことをAPI TestかComponent Testで確認できないか
  • このテストは10回連続で実行して10回通るか
  • このE2Eを、そのまま本番監視に転用できるか

Part 3

難所 — Unitでは原理的に守れない領域

トランザクション、並行実行、非同期、外部API。これらはテストが書きにくいうえに、本番障害の原因としては上位に来る。書きにくさを理由に飛ばすと、そこだけが無防備になる。

08 Test Double Strategy

結論: 「全部緑なのに本番が壊れる」の原因は、ほぼすべてMockの置き方にある。Mockは検証範囲を狭める道具であり、狭めた分をどこかで買い戻さないと穴になる。

  • モックの応答を実物と照合しない — 外部の仕様変更に気づかない
  • 本番用の組み立てコードをテストで一度も通さない — 配線ミスが本番まで届く

09 Transaction Test

結論: 「ロールバックされること」はUnit Testでは検証できない。Fakeは常に成功し、Mockは呼び出しを記録するだけで、何も巻き戻らない。

9-1. Unitが通してしまうトランザクションのバグ

9-2. ロールバックのテスト

✓ 失敗をどこで注入するか

  • 処理の最後で失敗させる — 最も多くの副作用が積まれた状態でのロールバックを検証できる
  • 処理の途中の各段階で失敗させる — テーブル駆動で「どこで落ちても整合が保たれる」ことを確認する
  • DB側の失敗も注入する — 制約違反を意図的に起こす（重複キー）。アプリのエラーだけでなく、DBのエラーでもロールバックされるか
  • 注意: 「トランザクションでロールバックする」方式のテストデータ分離を使っていると、この検証ができない（→ 5章）。ロールバックを検証したいテストでは別方式を使う

9-3. 制約違反の挙動をテストする

▲ このテストが守っているもの

  • エラー番号のハードコード（MySQLなら1062、PostgreSQLなら23505）が正しいか
  • 制約名の一致 — uk_users_email を文字列で判定している場合、制約名を変えると検出できなくなる
  • DBを移行したときに落ちる — MySQLからPostgreSQLに変えると、このテストが即座に赤くなる。それが正しい

9-4. デッドロックのテスト

⇄ デッドロックのテストを書くか

  • 書く → リトライ機構が実際に機能することを確認できる / タイミング依存でFlakyになりやすい。必ずデッドロックするとは限らない
  • 書かない → CIが安定 / リトライが実装されているか誰も確認していない状態になる
  • 現実的な折衷: ①「ロック順序を統一する」という設計ルールをコードレビューで守る（テストより確実） ②リトライのロジック自体はUnitでテストする（エラーを注入する） ③デッドロック発生をメトリクスで監視する（→ 19章）

✓ これだけ覚える

  • 「ロールバックされること」はUnitでは検証できない。Fakeは何も巻き戻さない
  • 失敗を注入して「何も残っていないこと」を全テーブルで確認する
  • 制約違反が業務エラーに変換されているかを実DBで確認する
  • デッドロックはテストより「ロック順序の統一」という設計で防ぐ

⇄ Trade-off

  • ロールバックのテストを書く → 整合性の崩壊を防げる / 実DBが必要で遅い
  • 書かない → 速い / 部分コミットが本番まで届く
  • トランザクションでデータ分離 → テストが最速 / トランザクション自体を検証できない

✕ よくある失敗

  • 正常系だけテストする — 失敗時の整合性が誰にも分からない
  • ctxの受け渡しをテストで確認しない — トランザクション外実行が本番まで届く
  • ロールバック後に親テーブルだけ確認 — 子テーブルに残骸が残るパターンを見逃す
  • 制約違反を生のエラーのまま返す — 500になり、ユーザーに何も伝わらない

? 設計時に自問する質問

  • この処理が3行目で失敗したら、1〜2行目の変更はどうなるか
  • それを確認しているテストはあるか
  • DBの制約違反は、どの業務エラーに変換されるか
  • トランザクションの境界は、テストで実際に通っているか

10 Concurrency Test

結論: 並行性のバグは「確率的にしか再現しない」のではなく、「条件を揃えれば確実に再現できる」。テストで意図的にその条件を作る。

10-1. 並行実行を実際に起こす

▸ 並行テストの型

  1. goroutineを作って待機させる — <-start で全員を止めておく
  2. チャネルを閉じて一斉に開始 — これで衝突確率が跳ね上がる
  3. 結果の「個数」を検証する — 成功何件・失敗何件が期待通りか
  4. 最終状態の不変条件を検証する — 在庫がマイナスでない、合計が保存されている
  5. -race を付けて実行する — メモリ上の競合はこれで検出できる

10-2. 対象別のテスト方法

問題再現方法検証すること
Lost Update同じリソースを2つのgoroutineが読んで書く両方が成功しないこと（片方が412/409）。または最終値が正しいこと
売り越し在庫1に対してN並列成功がちょうど1件。在庫が負にならない
重複登録同じメールでN並列登録1件だけ成功し、残りは業務エラー（500ではない）

キャッシュのスタンピードキャッシュ切れの瞬間にN並列DBへのアクセスが1回に収束すること

10-3. 並行テストの限界と現実的な対処

■ 限界

  • 「通った」は「バグが無い」を意味しない — タイミング次第で再現しないことがある。検出はできるが、不在の証明はできない
  • CIのマシン性能で結果が変わる — コア数が少ないと並行度が下がり、衝突しにくくなる
  • 遅い — 100並列のテストを何十本も書くとCIが伸びる

✓ 現実的な方針

  • 書くのは「壊れたら金銭被害が出る箇所」だけ — 在庫・決済・ポイント・予約枠。全機能には書かない
  • 並行数は20〜100程度で十分 — 1000にしても検出力はさほど上がらず、遅くなるだけ
  • 構造で防ぐことを優先する — 条件付きUPDATE・UNIQUE制約・楽観ロック。テストは「その構造が効いていること」の確認に使う
  • -race は常時有効にする — CIの通常実行に含める。コストは実行時間2〜10倍だが、検出価値が高い
  • 本番でも監視する — 在庫がマイナスになっていないかを定期チェックする（→ 19章）

? Thinking Point

並行テストが「100回に1回落ちる」。これはテストの問題か、実装の問題か？

考えてから開く

まず「実装の問題」を疑う。並行テストの不安定さは、多くの場合バグの証拠。

  • よくある誤り: 「たまに落ちるからリトライ回数を増やす」「N=100をN=10に減らす」→ バグを見えなくしただけ
  • 正しい手順: ①落ちたときの状態を記録する（在庫がいくつだったか、成功件数は何件か） ②その状態が起きる経路を特定する ③構造で防ぐ（条件付きUPDATE等）
  • テスト側の問題であるケース: テスト自体が共有状態を持っている（他のテストと同じレコードを触っている）、アサーションがタイミングに依存している
  • 判別方法: 単独で1000回実行して落ちるならバグ、並列実行時だけ落ちるならテストの分離の問題

✓ これだけ覚える

  • 並行バグは「チャネルで待たせて一斉に開始」で確実に再現できる
  • 検証するのは成功件数と、最終状態の不変条件
  • 書くのは金銭・在庫が動く箇所だけ
  • 並行テストが不安定なら、まず実装のバグを疑う

⇄ Trade-off

  • 並行テストを書く → 売り越し・二重登録を防げる / 遅く、環境依存で不安定になりうる
  • 書かない → CIが速い / 最も被害の大きいバグが無防備
  • -raceを常時有効 → データ競合を確実に検出 / 実行時間が数倍になる
  • 並行数を増やす → 検出力が上がる / 実行時間とリソース消費

✕ よくある失敗

  • 不安定だからと並行数を下げる — バグを隠しているだけ
  • エラーの有無だけ見て、最終状態を見ない — 全部成功したが在庫が-5、を見逃す
  • SQLiteで並行テストを書く — DB単位ロックなので、本番の挙動を再現しない
  • -raceを使わない — メモリ上の競合が検出されないまま残る

? 設計時に自問する質問

  • この処理が100並列で呼ばれたら、何件成功すべきか
  • その期待値を検証しているテストはあるか
  • 不変条件（在庫≧0、合計が保存される）は何か。テストで確認しているか
  • このテストは単独で1000回通るか

11 Async / Event Test

結論: 非同期のテストは「Producer / Consumer / 配送の性質」の3つに分けて、それぞれ別々にテストする。全部を一度に通そうとすると、遅くて不安定なテストになる。

11-1. 3分割する

図11.1 — 「Producerを動かしてConsumerの結果を待つ」テストは、遅くてFlakyになる最悪の形

11-2. Producer — Outboxパターンのテスト

▲ なぜOutboxをテストするのか

  • 「DBに保存してからキューに送る」実装は、その2つの間で落ちると不整合になる — 注文は作られたがイベントが飛ばない、またはその逆
  • OutboxパターンはイベントもDBに書き、同一トランザクションにすることでこれを防ぐ
  • ただし実装をミスすると、Outboxを使っているつもりで別トランザクションになっていることがある。テストで確認する価値が高い

11-3. Consumer — 重複・順序・失敗を直接投入する

✓ Consumerで必ず書く4本

  1. 正常系 — 副作用が正しく起きる
  2. 重複配送 — 同じevent_idで2回呼んでも1回分の効果
  3. 順序逆転 — 古いイベントが新しい状態を上書きしない
  4. 処理失敗時の挙動 — 再試行されるようエラーを返すか、DLQに送るか。「握りつぶして成功を返す」実装になっていないか

この4本はキューを一切使わずに書ける。ハンドラ関数を直接呼ぶだけ。速くて決定的。

11-4. 配送層 — 最小限の実物テスト

検証すること実物が必要か理由
メッセージのシリアライズ形式Fakeでも可JSON化の検証はUnitで足りる
可視性タイムアウトの設定実物が必要処理が長引いたときに二重配送される設定になっていないか
再試行回数とDLQへの遷移実物が必要設定ミスで無限リトライになっていないか
メッセージサイズ上限実物が必要256KBを超えると送信できない、等
FIFO / 順序保証の設定実物が必要MessageGroupIdの指定漏れ
IAM権限・接続設定実物が必要本番でしか分からないこともある（→ 19章）

▸ 配送テストは「1本だけ・夜間実行」でよい

毎PRで実キューを立てるのはコストが見合わない。「Producerが送ったものをConsumerが受け取れる」という疎通を1本だけ書き、夜間バッチかマージ後に実行する。
設定変更（タイムアウト・リトライ回数）を行ったときだけ、手動で実行するという運用も現実的。

11-5. 非同期テストを安定させる技術

✕ sleepで待つ

✓ 条件が満たされるまでポーリング

  • そもそも同期的に呼べるなら、それが最善（11-3の方式）

✓ これだけ覚える

  • 非同期はProducer / Consumer / 配送に3分割する
  • Consumerはハンドラを直接呼ぶ。キュー無しで重複・順序逆転を検証できる
  • Outboxは「失敗時にイベントも記録されない」ことを検証する
  • 待つときはsleepではなく条件ポーリング

⇄ Trade-off

  • 全体を通すテスト → 本番に近い / 遅くFlaky。落ちても原因が分からない
  • 3分割する → 速く決定的 / 「繋がっていること」は別途確認が必要
  • 実キューを毎回使う → 設定ミスを検出 / CIが重くなる
  • Fakeキュー → 高速 / 可視性タイムアウト・DLQの設定ミスが通る

✕ よくある失敗

  • 重複配送のテストを書かない — At-Least-Onceなのに重複対策が検証されていない
  • Consumerでエラーを握りつぶす — 失敗が再試行されず、静かにデータが欠ける
  • sleepで待つ — 遅く、CIの負荷次第で落ちる
  • イベントのペイロードを検証しない — 後続システムが壊れる変更に気づかない

? 設計時に自問する質問

  • 同じイベントが2回届いたらどうなるか。テストはあるか
  • イベントが逆順で届いたらどうなるか
  • Consumerが失敗したとき、再試行されるか・DLQに行くか
  • 業務処理が失敗したのに、イベントだけ飛ぶ経路はないか

? Thinking Point

外部APIのSandboxが不安定で、CIが週に2回赤くなる。どうするか？

考えてから開く

「リトライを増やす」「テストを消す」はどちらも誤り。

  • 正しい対応: CIの必須パスから外し、独立したジョブにする。落ちたら通知するが、PRはブロックしない
  • 理由: このテストが検出したいのは「相手の仕様変更」であり、それは今すぐマージを止めるべき緊急事態ではない。一方、Sandboxの一時的な障害でチーム全体の開発が止まるのは明確な損失
  • ただし通知は必ず人に届くようにする — 「落ちてもPRは通る」を「落ちても誰も見ない」にしない
  • 一般化: 「自分が制御できないものに依存するテスト」は、CIの必須パスに置かない。これはFlaky対策の基本原則（→ 17章）

✓ これだけ覚える

  • 「自分のコードの正しさ」と「相手の仕様の理解」は別々に検証する
  • Mock Serverでタイムアウト・リトライ・エラー分岐を守る
  • 記録した実レスポンスでパース処理を常時検証し、Sandbox疎通は日次で回す
  • 自分が制御できないものに依存するテストは、CIの必須パスに置かない

⇄ Trade-off

  • Sandboxを毎回叩く → 仕様変更を即検出 / 相手の障害で開発が止まる
  • Mockだけ → 高速・安定 / 相手の仕様変更に本番まで気づかない
  • 記録レスポンスで検証 → 速く、パースの退行を防げる / 記録が古くなる
  • Contract Testを日次で回す → バランスが良い / 検出が最大1日遅れる

✕ よくある失敗

  • Mockのレスポンスを想像で書く — 実物と違っていても誰も気づかない
  • タイムアウトを設定せずMockでテスト — Mockは即答するので、設定漏れが発覚しない
  • 不安定なSandboxテストをリトライで誤魔化す — 本物の仕様変更も再実行で通してしまう
  • エラーレスポンスのテストを書かない — 相手が402を返したときの挙動が未定義

? 設計時に自問する質問

  • 相手がレスポンス形式を変えたら、どのテストがいつ落ちるか
  • 相手が10秒応答しなかったら、自分のサービスはどうなるか
  • Mockのレスポンスは、実物から取得したものか、想像で書いたものか
  • このテストが落ちたとき、PRを止めるべきか

手法 — フロントと、テストの質を測る道具

フロントエンドは「何をテストすべきか」の基準がバックエンドと違う。またCoverageという指標の限界を知り、Property BasedとMutationという2つの補完手段を使えるようにする。

13 Frontend Testing

結論: フロントのテストは「ユーザーに見えるもの・できること」だけを検証する。内部のstateやpropsを検証し始めた瞬間、リファクタのたびに壊れる負債になる。

13-1. 5つの層と、何を書くか

層対象書く価値判断基準
Pure Logic金額フォーマット、日付計算、バリデーション、ソート最も高い分岐と境界値がある。Reactを一切使わずテストできる

13-2. React Testing Library の思想

「テストがソフトウェアの使われ方に似ているほど、そのテストは確信を与える」（RTLの指導原則）。
ユーザーは state も props も見ていない。画面に表示された文字を読み、ボタンをクリックする。だからテストも同じものだけを触る。

✕ 実装の詳細を検証する

  • useStateをuseReducerに変えただけで全部落ちる
  • デザイン変更（クラス名の変更）で落ちる
  • 「モーダルが表示されている」ことは確認できていない（stateがtrueでも表示されないバグは検出できない）

✓ ユーザーに見えるものを検証する

  • 内部実装をどう変えても、表示と操作が同じなら緑
  • ロールとラベルで取るので、アクセシビリティの問題も同時に検出される

▸ クエリの優先順位

  1. getByRole — 最優先。ボタン・見出し・入力欄。支援技術から見える形と一致する
  2. getByLabelText — フォーム要素。ラベルが無ければアクセシビリティの問題でもある
  3. getByText — 表示テキスト
  4. getByTestId — 最後の手段。ただしE2Eでは最初から使ってよい（→ 7章）
  5. クラス名・タグ名での取得は使わない — ユーザーが見ているものではない

13-3. API連携のテスト（MSW）

✓ フロントで必ず書く4状態

  1. Loading — 読み込み中の表示が出る
  2. Success — データが正しく表示される（フォーマット含む）
  3. Empty — 0件のときの表示。最も忘れられ、最もクレームになる
  4. Error — エラー表示と復帰手段（再試行ボタン）

この4つを書くだけで、フロントの障害の大半は防げる。凝ったテストより先にこれを揃える。

? Thinking Point

スナップショットテストは有効か？

考えてから開く

「差分が読めるサイズか」で決まる。

  • 有効でない使い方: コンポーネント全体のDOMをスナップショット。差分が200行出るので、レビューで読まれず -u で機械的に更新される。「テストがある」という見た目だけが残る
  • 有効な使い方: 出力が小さく、変化が意味を持つもの。生成されたSQL・APIのクエリ文字列・整形された金額の一覧・エラーメッセージの集合
  • 判定基準: 「このスナップショットが変わったとき、レビュアーは差分を読んで正誤を判断できるか」。できないなら、そのテストは何も守っていない
  • 見た目の退行を検出したいなら、スナップショットではなくVisual Regression Test（画像比較）が正しい道具

✓ これだけ覚える

  • ユーザーに見えるもの・できることだけを検証する。state/propsを見ない
  • 取得は role → label → text の順。クラス名で取らない
  • APIはネットワーク層でモック（MSW）。fetchをモックしない
  • 必ず書く4状態: Loading / Success / Empty / Error

⇄ Trade-off

  • RTL方式（役割で取得） → リファクタに強くA11yも守れる / 慣れるまで書きにくい
  • 実装詳細を検証 → 書きやすい / リファクタのたびに壊れる
  • MSWでネットワークモック → URL・メソッドの誤りを検出 / セットアップが必要
  • スナップショット → 書くのが一瞬 / 差分が読めないと無価値

✕ よくある失敗

  • Empty状態を忘れる — 0件のときに空白の画面が表示される
  • クラス名でセレクト — デザイン変更で全テストが壊れる
  • fetchをモック — URLやメソッドが間違っていても検出されない
  • 巨大なスナップショットを -u で更新する運用 — 退行を素通りさせる

? 設計時に自問する質問

  • このテストはユーザーが認識できるものを検証しているか
  • useStateをuseReducerに変えたら、このテストは落ちるか
  • Empty / Error の表示は検証されているか
  • このスナップショットの差分を、レビュアーは判断できるか

14 Property Based Testing

結論: Example Basedは「自分が思いついた入力」しか試さない。思いつかなかった入力こそがバグの居場所。PBTは「常に成り立つべき性質」を書いて、入力を機械に探させる。

14-1. 2つの発想の違い

Example Based（通常のテスト）

  • 読みやすく、仕様書として機能する
  • 自分が思いついたケースしか試さない
  • 境界値を1つ書き忘れると、永久に検証されない

Property Based

  • 数千パターンを自動生成し、反例を探す
  • 見つけた反例を最小化して報告する
  • 「性質」を言語化するのが難しい

14-2. よく使う「性質」の型

性質の型意味例
往復（Round-trip）変換して戻すと元に戻るDecode(Encode(x)) == x。JSON・暗号化・シリアライズ。最も使いやすい
不変条件（Invariant）どんな操作をしても成り立つソート後も要素数が同じ。在庫は常に0以上。合計は変わらない
単調性入力が増えたら出力も増える（減らない）購入金額が増えたらポイントは減らない
冪等性2回適用しても1回と同じnormalize(normalize(x)) == normalize(x)
交換法則順序を変えても結果が同じカートに入れる順番を変えても合計は同じ
別実装との一致単純だが遅い実装と同じ結果最適化したコードが、素朴な実装と一致するか。リファクタの検証に強い
クラッシュしないどんな入力でもpanicしないパーサ・バリデータ。Fuzzingとほぼ同じ

14-3. どんなドメインに有効か

有効有効でない
金額・税・割引の計算（丸め誤差、境界）CRUDのRepository（性質が「保存したら取れる」だけ）
パーサ・シリアライザ（往復）UI表示（性質を定義しにくい）
日付・期間の計算（うるう年、月末、タイムゾーン）外部API連携（入力を機械生成する意味が薄い）
ソート・集計・配分アルゴリズム単純な分岐（例示で十分）
バリデーション（クラッシュしないこと）仕様がテーブルで与えられているもの
状態機械（どんな遷移列でも不変条件が保たれる）設定・定数の検証

▸ 実務での位置づけ

  • PBTはExample Basedの代わりではなく、追加。仕様の説明はExample Basedが担い、網羅はPBTが担う
  • 導入するなら、まず「往復」と「クラッシュしない」から。性質を考える負荷が低く、効果が出やすい
  • Goなら testing/quick か go test -fuzz。Fuzzingは「クラッシュしない」に特化したPBTと考えてよい
  • PBTが見つけた反例は、必ずExample Basedのテストケースとして追加する。同じバグが再発したとき、即座に分かるようにする

✓ これだけ覚える

  • Example Basedは「自分が思いついた入力」しか試さない
  • PBTは「常に成り立つ性質」を書き、入力を機械が探す
  • 使いやすい性質は往復・不変条件・別実装との一致
  • 見つけた反例は通常のテストケースに追加する

⇄ Trade-off

  • PBTを導入 → 思いつかない入力を検出 / 性質の言語化が難しく、失敗時の解読に時間がかかる
  • Example Basedのみ → 読みやすく仕様になる / 抜けた境界値は永久に検証されない
  • 生成回数を増やす → 検出力が上がる / 実行時間が伸びる

✕ よくある失敗

  • 性質として実装をそのまま書く — shipping(x) == (x >= 5000 ? 0 : 500) は実装のコピー。バグも一緒にコピーされる
  • 全部PBTにする — 仕様が読めなくなる。Example Basedと併用する
  • 反例をその場で直して終わり — 回帰テストとして残さない
  • 生成される入力が非現実的 — 負の金額や100万文字の文字列で悩む。生成範囲を絞る

? 設計時に自問する質問

  • この関数に「どんな入力でも必ず成り立つこと」はあるか
  • 変換して戻したら元に戻るか（往復性）
  • 素朴だが確実な実装と比較できないか
  • 境界値を書き忘れている可能性はないか

15 Mutation Testing

結論: Coverageは「テストがそのコードを通ったか」しか見ていない。通っただけで、検証していないかもしれない。Mutation Testingは「コードを壊したらテストが落ちるか」を実際に試して、テストの強さを測る。

15-1. Coverage 100% でもバグを検出しないテスト

■ Mutation Testingがやること

元のコード: return total * 90 / 100 ツールがコードを機械的に書き換える（Mutant を作る）: 変異1: return total * 91 / 100 → テストは落ちるか？ 変異2: return total * 90 / 101 → テストは落ちるか？ 変異3: return total → テストは落ちるか？ 変異4: if !isMember { → テストは落ちるか？ 変異5: return 0 → テストは落ちるか？ 全部「落ちない」= テストは1つも変異を殺せていない → Mutation Score 0%。Coverage 100% / Mutation Score 0%

✓ 意味のある指標

  • Mutation Score = 殺したMutant数 / 生成したMutant数
  • 「テストが検出できる変更の割合」を表す。Coverageより遥かに実態に近い
  • 生き残ったMutant（Survived）は、「ここを壊しても誰も気づかない」場所の一覧。これがそのまま改善タスクになる

15-2. 生き残ったMutantが教えること

生き残ったMutant意味対応
>= を > に変えても落ちない境界値のテストが無い境界ちょうどのケースを追加する
条件を反転しても落ちないその分岐の結果を検証していないアサーションを追加する
戻り値を定数にしても落ちない戻り値を見ていない結果を検証する
エラーを無視しても落ちない異常系のテストが無いエラーケースを追加する
その行を削除しても落ちないデッドコードの可能性コードを消す（テストを足すより良い）

▲ 「その行を消しても落ちない」が最も価値がある発見

  • テストが弱いのではなく、そのコードが不要である可能性がある
  • 「念のため」で書かれたnullチェック、到達しない分岐、重複した検証
  • Mutation Testingは、テストだけでなくプロダクションコードの贅肉も可視化する

15-3. 実務での使い方

⇄ コストと現実的な運用

  • コスト: Mutant 1つごとにテストスイートを実行する。通常のテストの数十〜数百倍の時間がかかる
  • だからCIの常時実行には向かない — 週次、または特定パッケージのみ
  • 最も費用対効果が高い使い方: 「金額計算」「割引」「在庫配分」など、壊れたら被害が大きいパッケージに限定して、月1回実行する
  • もう1つの使い方: 「Coverage 90%あるのに障害が出た」ときの調査。なぜ検出できなかったかが定量的に分かる
  • Mutation Score 100%を目指さない — ログ出力やエラーメッセージの変異など、殺す価値のないMutantも混ざる

▸ ツールを入れなくても、発想は使える

  • レビューで「この行を消したら、どのテストが落ちますか？」と聞く
  • 答えられないなら、そのコードは検証されていない
  • 自分で書いたテストの検証にも使える — テストを書いた後、意図的に実装を1箇所壊してみて、赤くなることを確認する
  • これは TDDの Red → Green が保証していたことと同じ。後からテストを書く場合、この確認が抜けやすい

✓ これだけ覚える

  • Coverageは「通ったか」、Mutation Scoreは「検出できるか」
  • 生き残ったMutantは「壊しても誰も気づかない場所」の一覧
  • 実行コストが高いので、重要なパッケージに限定して定期実行
  • ツール無しでも「実装を1箇所壊して、テストが赤くなるか確認する」は今日からできる

⇄ Trade-off

  • 導入する → テストの弱点が定量的に分かる / 実行時間が桁違いに長い
  • 導入しない → コストゼロ / テストの質を測る手段が無くなる
  • 全体に適用 → 網羅的 / 現実的でない実行時間
  • 重要な箇所のみ → 実行可能 / 対象外の弱点は見つからない

✕ よくある失敗

  • Mutation Scoreを新たなノルマにする — Coverageと同じ失敗を繰り返す
  • 全Mutantを殺そうとする — 価値のない変異のためにテストが増える
  • CIで毎回実行する — フィードバックが遅くなり、誰も待たない
  • 実行結果を見て「テストを足す」だけ — デッドコードを消す判断を見落とす

? 設計時に自問する質問

  • この行を消したら、どのテストが落ちるか
  • >= を > に変えたら落ちるか
  • テストを書いた後、実装を壊して赤くなることを確認したか
  • 落ちないなら、そのコードは必要か

16 Test Coverage

結論: Coverageは「テストされていない場所を見つける道具」としては優秀で、「テストの質を表す指標」としては無力。目標値を設定する前に、この違いを理解する。

16-1. 3種類のCoverage

種類測るもの限界
Function関数が1回でも呼ばれたか最も緩い。ほぼ意味がない
Line / Statementその行が実行されたか最も広く使われるが、分岐の片側しか通っていなくても100%になる
Branch各分岐のtrue/false両方を通ったかLineより有用。Goの標準ツールは対応していない点に注意
Condition / MC-DC複合条件の各項の影響を検証したか航空・医療など高信頼性領域で使われる。一般的なWebでは過剰

▲ どの種類でも共通する根本的な限界

  • 「実行した」と「検証した」は違う — アサーションが1つも無くてもCoverageは上がる（→ 15章）
  • 書かれていないコードは測れない — エラーハンドリングを書き忘れた箇所は、Coverageに現れない。存在しない行は分母に入らない
  • 組み合わせは測れない — 各行を通っていても、特定の組み合わせでのみ起きるバグは検出されない
  • 並行性・トランザクション・外部連携は対象外 — 本番障害の主要因が、この指標には一切現れない

16-2. 「Coverage何%を目指すか」への答え方

■ 単一の数字を目標にしたときに起きること

  • 80%に達しないPRがマージできない → getterのテストやアサーション無しのテストが書かれる
  • テストしにくいコードを書かなくなる → 正しい副作用だが、テストが面倒なので避ける
  • Coverage計測から除外する設定が増える → 実態が見えなくなる
  • 数字を満たしたので安心する → 最も危険。80%の内訳が、重要な20%を含んでいない可能性
  • これはGoodhartの法則 — 指標が目標になると、指標として機能しなくなる

✓ 代わりに設定すべき基準

  1. 全体の数字ではなく、領域ごとに分けて見る
    金額計算・認可・状態遷移 → 高いCoverageを要求する
    DTO変換・設定読み込み・生成コード → 計測対象から外してよい
  2. 絶対値ではなく差分を見る
    「このPRで追加された行のうち、テストが通っていない行」を表示する。既存の負債に引きずられず、新規コードの質だけを守れる
  3. 下がったら警告、という運用
    「80%を維持」ではなく「前回より2%以上下がったらレビューで確認」
  4. 数字より「カバーされていない行」のリストを見る
    Coverageの最大の価値はここ。「このエラーハンドリング、一度も通っていないな」という気づき
  5. 重要な箇所は個別に「必ずテストがある」と決める
    数値目標ではなく、チェックリストで担保する（→ 付録）

? Thinking Point

上司に「テストカバレッジは何%ですか」と聞かれた。どう答えるか。

考えてから開く

数字を言った上で、その数字が何を意味しないかを添える。

  • 悪い答え1: 「72%です」だけ — 相手は「80%にしましょう」と言う。数字を追う運用が始まる
  • 悪い答え2: 「Coverageは意味がありません」 — 会話が終わる。相手が知りたいのは「品質は大丈夫か」であって、指標論ではない
  • 良い答え: 「全体では72%です。ただし内訳が重要で、金額計算と認可の部分は95%以上あります。低いのはDTO変換と管理画面のCRUDで、ここはAPI Testで別途担保しています。直近3件の本番障害は、いずれもCoverageでは検出できない種類（並行実行・外部API仕様変更・設定ミス）だったので、そちらの対策を優先しています」
  • 要点: 「数字 + 内訳 + 実際の障害との対応」をセットで話す。これで議論が「数字を上げる」から「リスクを下げる」に移る

16-3. Coverageの正しい使い方

✕ 指標として使う

  • 「80%を下回ったらマージ禁止」
  • チーム間でCoverageを比較する
  • 目標値を四半期のKPIにする
  • 数字が上がったことを成果として報告する

✓ 発見の道具として使う

  • 「この関数、一度も呼ばれていない」→ デッドコードの発見
  • 「このエラー分岐、通っていない」→ 異常系テストの不足
  • PRの差分で、新規コードの未カバー行をレビューで見る
  • 障害が出たとき、その行がカバーされていたかを確認する
    カバーされていたのに障害が出た → アサーションが弱い（→15章）

✓ これだけ覚える

  • Coverageは「未テストの発見」には有用、「質の指標」としては無力
  • 書かれていないコードは測れない。最大の穴はここ
  • 単一の目標値を設定しない。領域別・差分ベースで見る
  • 数字ではなく「カバーされていない行のリスト」を見る

⇄ Trade-off

  • 目標値を設定 → 分かりやすく、最低限が担保される / 無意味なテストが増え、数字が目的化する
  • 設定しない → 本質的な議論ができる / 「テストを書かない」への歯止めが無くなる
  • 差分カバレッジ → 新規コードの質を守れる / 既存の負債は放置される
  • 領域別に基準を変える → 実態に合う / 基準の合意と維持にコストがかかる

✕ よくある失敗

  • 全体の数字だけを見る — 重要な領域が低くても気づかない
  • Coverageを上げるためにテストを書く — アサーション無しのテストが生まれる
  • 計測除外を増やして数字を作る — 実態が見えなくなる
  • 「Coverage 90%だから品質は高い」と報告する — 並行性・外部連携の障害は防げていない

? 設計時に自問する質問

  • この数字の内訳はどうなっているか。重要な領域は高いか
  • カバーされていない行のうち、壊れたら困るものはどれか
  • 直近の本番障害は、Coverageで検出できる種類だったか
  • カバーされているのに障害が出た箇所はないか（アサーションが弱い）

Part 5

運用 — テストを信頼され続ける状態に保つ

テストスイートは放っておくと必ず劣化する。遅くなり、不安定になり、やがて誰も赤を見なくなる。そして「テストはデプロイ前だけのもの」という前提自体も、本番では通用しない。

17 Flaky Test

結論: Flakyなテストは、無いより悪い。赤が「バグかもしれないし、いつものやつかもしれない」という状態になった瞬間、スイート全体が情報を失う。

17-1. 原因と対策の一覧

原因典型的な症状対策
① 時刻月末・年末・うるう日・深夜0時付近で落ちる。タイムゾーン境界Clockを注入して固定する。time.Now() を直接呼ばない
② 乱数・IDまれに重複、まれに順序が変わるシードを固定するか、生成器を注入する
③ ネットワーク外部APIの一時障害、DNS、レート制限CIの必須パスから外す（→ 12章）。Mock Serverを使う
④ 共有状態単独では通るが、他のテストと一緒だと落ちるテストごとにDB/スキーマを分離。グローバル変数を使わない
⑤ 実行順序への依存アルファベット順が変わると落ちる。-shuffle で落ちる常に -shuffle=on で実行する。依存を発見できる
⑥ 並行性CIのコア数やマシン負荷で結果が変わる実装のバグを疑う（→ 10章）。テストの分離を確認
⑦ 非同期・待ち速いマシンでは通り、遅い日に落ちるsleepではなく条件ポーリング（→ 11章）
⑧ マップ・集合の順序Goのmapは反復順序が不定。まれに順序が変わる比較前にソートする。順序非依存の比較を使う
⑨ リソース枯渇ポート・ファイルディスクリプタ・コネクション不足クリーンアップを t.Cleanup で確実に。ポートは0で自動割当
⑩ 浮動小数点まれに 0.1+0.2 != 0.3 で落ちる金額は整数で扱う。比較は許容誤差付きで

17-2. 発見と隔離のプロセス

図17.1 — 隔離は「諦め」ではなく、スイート全体の信頼を守るための処置

17-3. 「隔離」の具体的な形

✓ 消さずに、必須パスから外す

  • タグで分離する — //go:build flaky を付け、通常のCIから除外する。夜間ジョブでは実行して統計を取る
  • t.Skip() に理由とチケット番号を書く — t.Skip("flaky: 順序依存 #1234")。理由の無いSkipは永久に残る
  • Skipの一覧を定期的にレビューする — 月1回、まだ必要かを確認する。3ヶ月放置されたSkipは削除候補
  • 隔離した事実をチームに共有する — 「この機能のテストは今は効いていない」という認識を揃える

✓ これだけ覚える

  • Flakyなテストは、無いより悪い。赤の意味を壊す
  • 最大の原因は時刻・共有状態・sleep。すべて構造で防げる
  • 見つけたら即座に隔離し、起票する。放置しない
  • -shuffle と -race を常用する。Flakyを能動的に探す

⇄ Trade-off

  • 自動リトライを入れる → CIが安定して見える / 本物のバグも再実行で通ってしまう
  • 入れない → 赤の意味が保たれる / 一時的に開発が止まることがある
  • 隔離する → スイートの信頼が保たれる / その機能が一時的に無防備になる
  • -raceを常用 → 競合を検出 / 実行時間が数倍

✕ よくある失敗

  • 「再実行すれば通る」を運用にする — 本物の障害を見逃す文化ができる
  • sleepを伸ばして対処 — CI時間が伸び、いずれまた落ちる
  • 理由なしのSkip — 誰も消せず、永久に残る
  • Flakyの記録を取らない — どのテストが問題なのかが分からず、対処できない

? 設計時に自問する質問

  • このテストは来月の月末に落ちないか
  • 実行順序を変えても通るか（-shuffle=on で確認したか）
  • 他のテストと同じデータを触っていないか
  • sleepを使っていないか

18 CI Pipeline

結論: パイプライン設計の目的は「間違いを、できるだけ早く、できるだけ安く知らせること」。全部を1つのジョブで回すと、フィードバックが遅くなり、テストが避けられるようになる。

18-1. 段階的なパイプライン

ここが遅いとテストが敬遠される 並列化する。パッケージ単位で分割し、キャッシュを効かせる ③ PR: Integration 実DB・Redis を立ててRepository / API Test 〜8分 目的: SQL・配線・認可・トランザクションの検証。②と並列に走らせる マージの必須条件にする ④ マージ後 / Staging E2E（Critical Pathのみ）+ 外部Sandbox疎通 + セキュリティスキャン 〜20分 目的: 本番に近い環境での確認。PRはブロックしない（落ちたら即通知して巻き戻す） ⑤ デプロイ後 Smoke Test → Canary（一部トラフィック）→ 全展開 〜5分 目的: 本番設定・接続・権限の確認。失敗したら自動ロールバック（→ 19章） ⑥ 夜間 / 週次: Mutation Testing・負荷試験・フル回帰・Flaky検出（同一コミットの反復実行）・依存更新の検証

図18.1 — 上ほど速く・頻繁に、下ほど遅く・稀に。落ちたときの「巻き戻しコスト」も下ほど高い

18-2. 設計原則

▸ 5つの原則

  1. 速いものを先に、安いものを先に — Lintで落ちるPRに10分のIntegrationを走らせない。fail-fast を活用する
  2. PRの必須チェックは10分以内に収める — これを超えると、開発者は結果を待たずに別作業へ移り、コンテキストスイッチのコストが発生する
  3. 自分が制御できないものを必須にしない — 外部Sandbox・不安定な依存（→ 12章）
  4. 落ちたときに何をすべきか明確にする — どのジョブが落ちたら誰が対応するのか
  5. CIで実行できることは、ローカルでも同じコマンドで実行できるようにする — make test-integration のように。「CIでしか再現しない」状態を作らない

18-3. CIが遅くなったときの手

手段効果注意
並列化（ジョブ分割）最も効く。パッケージ単位で分けるDBを使うなら分離が必要（→ 5章）
キャッシュ依存のダウンロード・ビルド成果物キャッシュキーの設計を誤ると効かない
変更検出（影響範囲のみ実行）モノレポで特に効く依存関係の解析を誤ると、必要なテストが飛ぶ
遅いテストを後段へ移すPRの必須チェックが軽くなるマージ後に落ちたときの巻き戻し手順が必要
テストを消す価値の低いものは正しい選択→ 1章。何を失うかを理解して消す
マシンを強くする効くが根本解決ではないコスト。ただし開発者の待ち時間より安いことも多い

? Thinking Point

CIが25分かかる。開発者から「遅い」と苦情が出た。最初に何をするか。

考えてから開く

最初にやるのは「測定」。どのジョブ・どのテストに時間がかかっているかを出す。

  • やりがちな誤り: 感覚で「E2Eが遅いから減らそう」→ 実際は依存のインストールに8分かかっていた、というケースは多い
  • 測定の方法: go test -json で各テストの所要時間を出し、遅い順に並べる。CIのジョブ単位の時間も記録する
  • 典型的な内訳: 上位10本のテストが全体の50%を占めている、ということがよくある。1本の遅いテストを直すだけで効果が出る
  • 次にやること: ①キャッシュとセットアップの最適化 ②並列化 ③遅いテストの個別改善 ④後段への移動。「テストを減らす」は最後
  • 同時にやるべきこと: 「PRの必須チェックは何分以内」という目標を明示する。目標が無いと、じわじわ伸びて誰も気づかない

✓ これだけ覚える

  • 目的は「早く・安く間違いを知らせること」。段階で分ける
  • PRの必須チェックは10分以内。超えるとテストが避けられる
  • 自分が制御できない依存を必須にしない
  • 遅くなったら、まず測定する。感覚で減らさない

⇄ Trade-off

  • 全部PRで実行 → マージ後に壊れない / 遅く、開発のリズムが崩れる
  • 後段に移す → PRが速い / マージ後に落ちることがあり、巻き戻しが必要
  • 変更検出で絞る → 大幅に速い / 依存解析のミスでテストが飛ぶ
  • マシンを強くする → 即効性がある / 継続的なコスト

✕ よくある失敗

  • 全テストを1ジョブで直列実行 — 25分かかり、誰も結果を待たない
  • 外部APIテストを必須チェックに入れる — 相手の障害で開発が止まる
  • CIでしか実行できないテストがある — ローカルで再現できず、デバッグに時間がかかる
  • CI時間の目標を決めていない — じわじわ伸びて、気づいたら30分

? 設計時に自問する質問

  • PRを出してから最初のフィードバックまで何分か
  • どのジョブ・どのテストが時間を使っているか、データで言えるか
  • このテストをローカルで実行するコマンドは何か
  • このジョブが落ちたとき、誰が何をするか決まっているか

19 Production Testing

結論: 「本番が動いている」という確信は、本番でしか得られない。ステージングは本番ではない。設定・データ量・トラフィック・外部連携・証明書、すべてが違う。

19-1. デプロイ前のテストでは絶対に分からないこと

本番固有の問題例
設定・環境変数本番のDB接続先が旧環境のまま。APIキーが未設定。機能フラグの値が違う
権限・ネットワークIAMロールの権限不足、セキュリティグループ、VPCエンドポイント、DNS
証明書・ドメインTLS証明書の期限切れ、中間証明書の設定漏れ
データ量ステージングは1000件、本番は1億件。索引が効かないクエリが顕在化する
実データの汚れ過去の不正データ、NULLが入っているはずのないカラム、想定外の文字コード
同時実行数コネクションプール枯渇、ロック競合、レート制限
外部サービスの本番挙動Sandboxとレスポンスが違う、本番だけ遅い、レート制限が厳しい
キャッシュ・CDN古いアセットが配信される、キャッシュキーの設計ミス

19-2. 本番での4つのテスト

① Smoke Test（デプロイ直後）

最小限の動作確認を数十秒で。
ヘルスチェック / DB疎通 / 主要エンドポイントが200 / バージョンが期待通り
失敗したら自動ロールバックする。ここが自動化されていないと、デプロイのたびに人が張り付く

② Health Check（常時）

Liveness（プロセスが生きているか）と Readiness（リクエストを受けられるか）を分ける。
Readinessで外部依存を全部チェックすると、依存の一時障害で全台が離脱する。依存のチェックは慎重に

③ Canary（段階展開）

新バージョンに5% → 25% → 100% と徐々にトラフィックを流す。
エラー率・レイテンシを旧バージョンと比較し、悪化したら自動で戻す。「テストで見つからなかったバグ」の被害を5%に抑える手段

④ Synthetic Monitoring（常時）

本番に対して、定期的に実際の操作を実行する。
「ログイン → 商品検索 → カート投入」を5分おきに。ユーザーより先に障害を検知する（→ 7章のE2Eを転用）

19-3. 本番で「データを壊さずに」テストする

■ 本番テストの難所

  • 書き込みテストは実データを汚す — テスト注文が売上に混ざる、テストユーザーがメールを受け取る
  • 決済が実際に走る — 課金が発生する
  • 後始末が失敗すると残る — テストデータが蓄積していく

✓ 対処

  • 読み取り専用のSmoke Testから始める — これだけでも設定ミス・接続障害の大半は検出できる
  • テスト用のテナント / アカウントを分ける — 集計から除外できるフラグを持たせる
  • 決済はテストモードのカードを使う — 決済サービスのテストカード番号。本番環境でも課金されない仕組みがある
  • 後始末を冪等にする — 「テストデータを削除する」バッチを定期実行し、失敗しても次回で回収できるようにする
  • 機能フラグで新機能を隔離する — 本番にデプロイしても、社内ユーザーにだけ有効にする。これが最も安全な「本番テスト」

19-4. 監視は「常時実行されているテスト」

▸ 発想の転換

  • 「在庫がマイナスになっていないか」を日次で確認するクエリ — これは並行性テスト（→ 10章）の本番版
  • 「注文と支払いの金額が一致しているか」を日次で照合する — トランザクションテスト（→ 9章）の本番版
  • 「決済成功率が平常時から乖離していないか」 — 外部APIのContract Test（→ 12章）の本番版
  • 「Webhookの未処理が溜まっていないか」 — 非同期テスト（→ 11章）の本番版
  • テストで防ぎきれないものは、検出に切り替える。これは敗北ではなく、正しいリスク管理

✓ これだけ覚える

  • 「本番が動いている」確信は本番でしか得られない
  • Smoke Test + 自動ロールバックが最も費用対効果が高い
  • Canaryは「見つからなかったバグ」の被害を減らす手段
  • テストで防ぎきれないものは、検出に切り替える。不変条件を本番で定期検証する

⇄ Trade-off

  • 本番で書き込みテスト → 最も確実 / データが汚れ、後始末の設計が必要
  • 読み取りのみ → 安全 / 書き込み経路の障害は検出できない
  • Canary導入 → 被害を限定できる / 基盤とメトリクス比較の実装が必要
  • Synthetic Monitoring → ユーザーより先に気づける / 誤検知への対応コスト

✕ よくある失敗

  • デプロイ後に何も確認しない — 「デプロイは成功したが、アプリは起動していない」に気づかない
  • Readinessで外部依存を全部チェック — 依存の一時障害で全台が同時に離脱する
  • Smoke Testが失敗してもデプロイを続行 — 検出しているのに止めない
  • 本番のテストデータを削除する仕組みが無い — 数年で無視できない量になる

? 設計時に自問する質問

  • デプロイして5分後に、正常かどうかを何で判断しているか
  • Smoke Testが失敗したら、自動でロールバックされるか
  • 「起きないはず」の状態を、本番で定期的に検証しているか
  • ユーザーより先に障害を検知できる仕組みはあるか

Bug 1 — 価格計算の誤り

■ 症状

起きたこと
クーポン適用時、合計が5,000円ちょうどのときだけ送料が加算されていた。5,001円でも4,999円でも正しい
原因
if subtotal > 5000 と書くべきところが if subtotal >= 5000 の逆で、境界の1点だけがずれていた
既存のテスト
「4,000円のとき送料500円」「6,000円のとき送料0円」の2ケースのみ。境界を跨いでいるので両方とも通る
防げたテストは？

UNIT 境界値を含むTable Driven Test（→ 3章）

  • 「5,000円ちょうど」「4,999円」「5,001円」の3点を必ず入れる。境界は「ちょうど・1つ手前・1つ後」の3点セット
  • UNIT 補強: Property Based Testの単調性（金額が増えて送料が増えることはない）で、この種のバグは機械的に検出できる（→ 14章）
  • E2Eでは検出できない — 全金額パターンを画面から試すのは非現実的
  • Mutation Testingなら事前に警告できた — > を >= に変えても落ちないテストとして検出される（→ 15章）

Bug 2 — Repository の SQL バグ

■ 症状

起きたこと
注文一覧に、他のユーザーの注文が混ざって表示された
原因
JOINを追加したリファクタで WHERE o.customer_id = ? が WHERE oi.customer_id = ? になっていた（テーブル別名の取り違え）
既存のテスト
sqlmockでSQL文字列を比較していた。期待するSQL文字列も同時に書き換えたので、テストは緑のまま
防げたテストは？

INTEGRATION 実DBでのRepository Test（複数ユーザーのデータを投入する）（→ 5章）

  • 重要なのは「2人分のデータを作る」こと。自分のデータしか無いテストでは、認可条件が効いていなくても通る
  • API でも検出できる — 「ユーザーAのトークンで一覧を取り、Bのデータが含まれないこと」
  • sqlmockは構造的に検出できない — 自分が書いたSQLと、自分が書いた期待値を比較しているだけ（→ 4章）
  • 教訓: 認可条件のあるクエリには、必ず「他人のデータ」を含むテストを書く

Bug 3 — JSON フィールドの不一致

■ 症状

起きたこと
iOSアプリで注文金額が常に「¥0」と表示された。Web版は正常
原因
バックエンドがレスポンスを total_amount から total にリネームした。Web版は同時にデプロイされたが、審査中のiOSアプリは古いフィールド名を見ていた
既存のテスト
バックエンドのテストは構造体経由で検証していたため、JSONのキー名を変えても落ちなかった
防げたテストは？

API JSONのキー名を文字列として検証するAPI Test（→ 6章）

  • 構造体にデコードして比較すると、キー名の変更が検出されない（構造体のタグも一緒に変わるため）。生のJSONに対してキーの存在を確認する
  • INTEGRATION より確実なのは OpenAPIスキーマのCI検証 — 破壊的変更として自動検出される（→ api-design.html 18章）
  • 最も安い解: OpenAPIからフロントの型を生成する。コンパイルエラーになるのでテストより早い
  • 根本原因はテスト不足ではなく、互換性ポリシーの不在 — 「フィールドのリネームは破壊的変更」という合意があれば、そもそも実行されなかった

Bug 4 — ブラウザ上のUIバグ

■ 症状

起きたこと
スマートフォンで「注文する」ボタンが押せない。タップしても反応しない
原因
固定表示のクーポンバナーが、ボタンの上に重なっていた。DOMには存在し、表示もされているが、クリックが別要素に吸われる
既存のテスト
Component Testで getByRole("button", {name: "注文する"}) は取得でき、クリックイベントも発火していた
防げたテストは？

E2E 実ブラウザでのCritical Path（モバイルビューポート）（→ 7章）

  • jsdomベースのComponent Testでは原理的に検出できない — レイアウト計算・重なり判定を行わないため
  • PlaywrightなどはデフォルトでActionability チェック（要素が実際にクリック可能か）を行うため、このバグで落ちる
  • ビューポートを変えたテストが必要 — デスクトップでは再現しない
  • これがE2Eを捨てられない理由。少数でよいが、ゼロにはできない

Bug 5 — Race Condition

■ 症状

起きたこと
限定商品（在庫1個）のセール開始時、3人が同時に購入に成功した。在庫は -2 になっていた
原因
SELECT quantity → アプリで判定 → UPDATE quantity = ? という読み書き分離の実装（→ 7章のTOCTOU）
既存のテスト
「在庫3で2個注文 → 成功」「在庫1で2個注文 → 失敗」を検証。どちらも単一リクエストなので通る
防げたテストは？

INTEGRATION 実DBでの並行テスト（N並列で在庫1個を奪い合う）（→ 10章）

  • 「成功がちょうど1件であること」「在庫が負にならないこと」を検証する
  • Unitでは不可能 — Fakeは並行制御を持たない。SQLiteでも不可能 — DB単位ロックなので本番の挙動と違う（→ 5章）
  • 本来は構造で防ぐ — UPDATE ... WHERE quantity >= ? の条件付きUPDATE + CHECK (quantity >= 0)。テストは「その構造が効いていること」の確認
  • PRODUCTION 併用: 在庫が負になっていないかを日次で検証する（→ 19章）

Bug 6 — 外部APIの仕様変更

■ 症状

起きたこと
ある朝から全ての決済が「失敗」と記録された。ただしカードには正常に課金されていた
原因
決済サービスがレスポンスの status を "success" から "succeeded" に変更した。リリースノートには記載があったが、誰も読んでいなかった
既存のテスト
モックが "success" を返すよう書かれており、当然緑のまま
防げたテストは？

INTEGRATION Sandboxへの日次疎通テスト / Contract Test（→ 12章）

  • 実際のSandboxを叩き、レスポンス形式が記録済みのものと一致するかを検証する。変更があればその日のうちに通知される
  • どれだけモックのテストを増やしても検出できない — モックは「自分の理解」でしかない（→ 8章）
  • PRODUCTION 併用: 決済成功率の監視。平常時95%が0%に落ちれば、原因が何であれ即座に気づける（→ 19章）
  • 防御的実装も有効: 未知のstatusを「不明」として扱い、成功とも失敗とも判定せず保留にする。「課金されたのに失敗扱い」より被害が小さい

Bug 7 — Webhookの重複配送

■ 症状

起きたこと
一部の注文で、ポイントが2倍付与されていた。該当するのは、決済サービス側でタイムアウトが発生した注文だった
原因
Webhook受信の処理が5秒を超え、送信側がタイムアウトと判定して再送。受信側に重複排除が無く、2回処理された
既存のテスト
Webhookハンドラのテストは「1回呼んだら正しく処理される」のみ
防げたテストは？

INTEGRATION 同じevent_idで2回ハンドラを呼ぶテスト（→ 11章）

  • たった1行「もう一度呼ぶ」を足すだけで書ける。最も費用対効果の高いテストの1つ
  • 検証するのは「エラーにならないこと」ではなく、「副作用が1回分であること」（ポイントが1回分、payments が1件）
  • INTEGRATION 併せて: 5秒以内に200を返しているか（処理が遅いこと自体が原因）
  • PRODUCTION 併用: 同一event_idの重複受信数を監視する
  • 一般化: At-Least-Onceな経路（Webhook・キュー・リトライ）には、必ず「2回呼ぶテスト」を書く

Bug 8 — トランザクションのロールバック失敗

■ 症状

起きたこと
決済に失敗した注文が「存在しない」のに、在庫だけが引き当てられたまま残った。数日かけて在庫が徐々に減り、実在庫があるのに「売り切れ」表示になった
原因
在庫引当の処理に、トランザクションのcontextではなく context.Background() を渡していた。注文はロールバックされたが、在庫の更新は別接続でコミットされていた
既存のテスト
UseCaseのUnit TestはFakeを使っていたため、そもそもトランザクションが存在しなかった
防げたテストは？

INTEGRATION 失敗を注入し、全テーブルに何も残らないことを検証する（→ 9章）

  • 決済を失敗させ、orders / order_items / inventories / inventory_reservations すべてを確認する。親テーブルだけ見ると見逃す
  • Fakeを使ったUnitでは原理的に不可能 — 巻き戻す対象が存在しない
  • PRODUCTION 併用: 「引当済みだが対応する注文が無い」レコードを日次で検出する。これがあれば数日ではなく1日で気づけた（→ 19章）
  • 設計での予防: contextを引数で明示的に引き回し、context.Background() をUseCase層で禁止するLintルールを入れる

8件の集計 — どの層が何件防いだか

バグ防げる層Unitで防げたか本番監視の併用
1. 価格計算の境界UNIT可能—
2. SQLの認可漏れINT API不可—
3. JSONキーの不一致API + スキーマ検証不可—
4. UIの重なりE2E不可Synthetic
5. Race ConditionINT（並行）不可在庫の不変条件チェック
6. 外部APIの仕様変更INT（Contract）不可決済成功率の監視
7. Webhook重複INTFakeでも可能重複受信数の監視
8. ロールバック失敗INT不可孤児レコードの検出

▸ この集計から読めること

  • 8件中7件が、Unit Testでは防げない。Coverageを上げても、これらは減らない
  • 6件が Integration 層で防げる。ここが最も投資効率が高い
  • 5件は本番監視でも検出できる — 防げなくても、被害を最小化できる
  • 最も安く防げるのは、実は設計とポリシー — 条件付きUPDATE（5）、互換性ポリシー（3）、Lintルール（8）
  • 「テストを増やす」の前に「構造で防げないか」を考える。これが最も重要な教訓

Step 4. 書かないと決めたもの

✓ 明示的に「書かない」判断

  • Repositoryのモックを使ったUseCase Test（CRUD部分） — モックの設定を書き写すだけになる（→ 3章）
  • Handlerの単体テスト — ミドルウェアを通らないので、最重要の認可検証が抜ける（→ 6章）
  • DTOの変換テスト — API Testで間接的に検証される
  • E2Eでの異常系 — API Testに任せる。E2Eは購入完了パス1本のみ
  • 全Repositoryメソッドのテスト — 単純なfindByIDは書かない。認可条件があるものと複雑なSQLのみ
  • 「書かない」も設計判断。なぜ書かないかをチームで共有し、記録に残す

? Thinking Point — 最後の問い

この地図に沿ってテストを書いた。CIは6分で終わる。上司から「E2Eが1本しかないのは不安だ、もっと増やそう」と言われた。どう答えるか。

考えてから開く

「増やさない」と主張するのではなく、「何が不安か」を具体化して、最も安い層で買う。

  • 悪い答え: 「E2Eは遅いしFlakyなので増やしません」 — 相手の不安（本番が壊れること）に応えていない
  • 良い答え: 「具体的にどのシナリオが心配ですか？」と聞き、挙がったものを1つずつ層に割り当てる。「クーポン適用時の金額」ならUnit、「認可漏れ」ならAPI Test、「ボタンが押せない」ならE2E
  • データで示す: 「直近1年の本番障害8件のうち、E2Eで防げたのは1件です。残り7件はIntegration層とContract Testで防げるもので、そちらは既に整備しています」（→ 20章の集計）
  • 増やす場合の条件を提示する: 「E2Eを5本に増やすと、CIが6分から20分になります。それでも必要なら、対象を決めて増やしましょう。ただしFlakyになったら即座に隔離する運用もセットでお願いします」
  • 本質: テスト戦略の議論は「本数」ではなく「どのリスクを、いくらで買うか」。この言葉で話せると、議論が噛み合う

メインの決定木 — 何のテストを書くか

この機能で「壊れたら最も困ること」は何か？ │ ├─ 金額・在庫・ポイントの計算が絡むか？ │ └─ YES → UNIT: 境界値のTable Driven （ちょうど / 1つ手前 / 1つ後） │ ＋ 常に成り立つ性質はあるか？ → YES → ＋ Property Based Test │ ├─ 状態遷移があるか？（pending → paid → shipped …） │ └─ YES → UNIT: 遷移表の全パターン （許可される遷移 / 禁止される遷移） │ ＋ API: 禁止遷移が409で返ること │ ├─ 新しいSQL / クエリを書いたか？ │ └─ YES → INTEGRATION: 実DBでのRepository Test │ ＋ 認可条件（customer_id, tenant_id）があるか？ │ └─ YES → 必ず「他人のデータ」を投入して、取得できないことを検証 │ ├─ 新しいHTTPエンドポイントか？ │ └─ YES → API Test 4本 正常系（JSON + DB）/ 認可 / バリデーション / 主要な業務エラー │ ※ Handlerの単体テストは書かない（ミドルウェアを通らない） │ ├─ 複数テーブルを1トランザクションで更新するか？ │ └─ YES → INTEGRATION: 失敗を注入し、全テーブルに何も残らないことを検証 │ ├─ 同じリソースに同時アクセスが起きうるか？（在庫・残高・枠） │ └─ YES → まず構造で防ぐ 条件付きUPDATE / UNIQUE制約 / 楽観ロック │ ＋ INTEGRATION: N並列での並行テスト 成功件数と不変条件 │ ├─ リトライ・再送が起きうるか？（POST / Webhook / キュー） │ └─ YES → 「同じ入力で2回呼ぶ」テストを必ず書く │ 検証するのは「エラーにならない」ではなく「副作用が1回分」 │ ├─ 外部APIを呼ぶか？ │ └─ YES → UNIT: Mock Serverで 402 / 429 / 500 / timeout / 壊れたJSON │ ＋ INTEGRATION: 記録した実レスポンスでのパース検証 │ ＋ 日次: Sandbox疎通（CIの必須パスには入れない） │ ├─ 非同期処理・イベントがあるか？ │ └─ YES → Producer: 正しいイベントが記録される / 失敗時は記録されない │ Consumer: 正常系 / 重複配送 / 順序逆転 / 失敗時の挙動 │ ※ ハンドラを直接呼ぶ。キューは立てない │ ├─ 画面（フロント）を作ったか？ │ └─ YES → Loading / Success / Empty / Error の4状態 │ role・labelで取得する。APIはMSWでモック │ ├─ この機能が壊れると事業が止まるか？ │ └─ YES → E2E 1本（Critical Path）＋ 本番Smoke Test │ ※ 異常系はE2Eに入れない │ └─ 上のどれにも当てはまらない └─ API Test 1本で足りることが多い （単純なCRUD・設定変更など） 最後に必ず: ├─ 実装を1箇所わざと壊して、テストが赤くなることを確認する （→15章） ├─ 構造で防げなかったか？ → 制約・型・Lintで防げるなら、テストより先にそちらを入れる └─ テストで防ぎきれないものは？ → 本番監視で検出する （→19章）

補助の決定木 — このテストは書くべきか / 消すべきか

このテストを書くべきか？ ├─ 落ちる状況を具体的に想像できるか？ │ └─ NO → 書かない （getter / 単純な変換 / nilでないことの確認） ├─ 実装をリファクタしたら落ちるか？（振る舞いは同じ） │ └─ YES → 書き方を変える 内部呼び出しではなく、結果を検証する ├─ 同じことを上位の層が既に検証しているか？ │ └─ YES → どちらか一方にする 重複は保守コストを二重に払う └─ 書く このテストを消すべきか？ ├─ 過去1年で一度もバグを検出していない、かつ落ちる想像ができない → 消す ├─ Flakyで、再実行が常態化している → 隔離 → 修正 or 消す ├─ 意図的な変更のたびに必ず落ちる → 書き直す 実装に密着しすぎている ├─ 準備コードが本体の3倍以上ある → ビルダを導入するか、層を変える └─ 上のどれでもない → 残す

? 汎用の質問セット

  4. 同時に実行されたら、どうなるか
  5. 他人のIDでアクセスしたら、何が返るか
  6. 途中で失敗したら、何が残るか

  8. 構造（制約・型）で防げないか
