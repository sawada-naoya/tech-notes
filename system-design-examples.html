01 TinyURL — 読み偏重システムの基本形

結論: TinyURL の本質は「圧倒的に読みが多い KVS」です。難所は2つだけ——短いIDをどう衝突なく生成するか、読みをどう捌くか。最も多い減点は「ID生成にランダム値を使い、衝突チェックのために毎回DBを読む」設計です。

① 要件整理

機能要件（スコープ内）

・長いURLを短いURLに変換する
・短縮URLにアクセスすると元URLへリダイレクト
・カスタムエイリアス（任意）
・有効期限（任意）

スコープ外にする（面接で自分から言う）

・アクセス解析の詳細な集計
・ユーザー認証
・スパムURLの検出
→ 「今回は生成とリダイレクトに絞ってよいですか？」

非機能要件

・リダイレクトは 100ms 以内（ユーザーの体感に直結）
・可用性 99.99%（短縮URLは外部サイトに埋め込まれる）
・短縮URLは推測されにくいこと

最重要の確認事項

「読みと書きの比率は？」
→ 一般に 100:1 程度。この一言で、以降の設計（Cache 必須・レプリカ多め）が全部決まる。

④ Database

図1-1: 短縮キー生成の3案。案C（事前生成プール）が実務的に最も優れており、面接でも高評価。

⑤ Cache

  • このシステムで最も効く施策 — 読み 12,000 QPS の99% 以上を Redis で吸収できる。理由は ①データが小さい（600B）②不変（作成後に変わらない）③アクセスが極端に偏る（バイラルなリンクに集中）
  • 戦略: Cache-Aside — GET key → miss なら DB → Redis に SET（TTL 24h）。データが不変なので、更新時の無効化を考えなくてよい（削除時のみ DEL）
  • ヒット率の見積もり — 20% のリンクが 80% のアクセスを占める（べき乗則）。全データ 3.6TB のうち、直近1ヶ月ぶんの人気20%（約12GB）をキャッシュすれば、ヒット率 90%+ が現実的
  • キャッシュ貫通（Cache Penetration）対策 — 存在しないキーへの大量アクセス（攻撃・クローラ）で、毎回DBを叩く事故。「存在しない」という結果も短い TTL でキャッシュする（Negative Caching）、または Bloom Filter
  • キャッシュスタンピード対策 — 人気リンクの TTL が同時に切れると、DBに一斉にアクセスが行く。TTL にジッターを入れる + 分散ロックで1リクエストだけDBを引く

⑥ Replication

  • 読み専用レプリカを多めに置く — 読み偏重なので、レプリカを増やすだけで読みのスケールが解決する
  • レプリカラグの許容度が高い — 「短縮URLを作った直後にアクセスする」ケースだけが問題。対策は ①作成レスポンスを返す前にキャッシュに書く ②作成直後の N 秒はプライマリから読む（Read-Your-Writes）
  • マルチリージョン — 短縮URLは世界中から叩かれる。各リージョンに読み取りレプリカ + Redis を置き、書き込みだけ1リージョンに集約するのが単純で堅い
  • DynamoDB Global Tables を使う場合 — マルチマスターになるが、同じキーが同時に別リージョンで作られる可能性を潰す必要がある（キープールをリージョンごとに分ける）

⑦ Partitioning

  • シャードキー = short_key — アクセスパターンが完全に key → value なので、キーのハッシュで分割するのが最適。範囲クエリが不要なので、レンジ分割の理由がない
  • Consistent Hashing — シャードを追加するとき、移動するデータを最小にする
  • Hot Partition のリスクは低い — キーがランダムなので偏らない。ただし「1つのバイラルリンクへの集中」はシャードではなく Cache で吸収する
  • いつ分割するか — 3.6TB / 5年なら、最初は分割せず1台で始め、1TB を超えたら分割するという判断も正当。「最初から分割しない」と言えるのも設計力

⑧ Queue

  • クリックイベントの記録を非同期にする — リダイレクトの応答に解析処理を含めない。Kafka に click イベントを流し、後で集計する
  • キープールの補充 — 未使用キーが閾値を下回ったら、バックグラウンドで生成する
  • 期限切れURLの削除 — 定期バッチ、または TTL 機能（DynamoDB TTL / Redis EXPIRE）に任せる
  • スパム/マルウェアURLのチェック — 作成時に同期でやると遅くなるので、非同期でチェックし、問題があれば後から無効化する

⑨ CDN

  • このシステムでは CDN の役割は限定的 — 返すのはリダイレクトのヘッダーだけで、ボディが無いため
  • ただし有効なケースが2つある — ①エッジでのリダイレクト（Cloudflare Workers / Lambda@Edge で、エッジのKVから直接リダイレクトを返す）→ レイテンシが 100ms → 20ms になる ②DDoS 防御と TLS 終端
  • 301 を使うなら — ブラウザがキャッシュするので、実質的に「クライアント側 CDN」として機能する。ただし解析ができなくなるトレードオフ

⑩ Storage

  • オブジェクトストレージは不要 — 1レコード 600B なので、全てDB（KVS）に入る
  • クリックログは別ストレージへ — 大量に増えるので、S3 + Parquet（分析用）。これを urls テーブルに入れると、本体が肥大化してキャッシュ効率が落ちる
  • コールドデータの分離 — 1年アクセスの無いリンクは、安価なストレージ階層へ移動する（DynamoDB → S3 など）

⑪ ボトルネック

順位ボトルネック症状対策
1読み取り（リダイレクト）の QPSDBの CPU 飽和・レイテンシ悪化Cache（これでほぼ解決）+ 読み取りレプリカ

面接で言うべき一言: 「このシステムは書き込みが40QPSしかないので、実質的に『大規模な読み取りキャッシュ』の設計問題です」——本質を1文で言えると強い。

⑫ スケール方法（10倍・100倍になったら）

  • 10倍（読み 12万 QPS） — Redis クラスタを増やすだけでほぼ解決。アプリ内のローカルキャッシュ（数秒 TTL）を足すと、Redis の負荷もさらに下がる
  • 100倍（読み 120万 QPS） — エッジ（CDN の KV ストア）にホットなキーを配置し、オリジンに来る前に返す。これでオリジンへの到達は数%になる
  • 書き込みが増えた場合 — シャード追加 + キープールの並列生成。書き込みは元々軽いので、問題になる可能性は低い
  • データ量が増えた場合 — シャード追加 + コールドデータの階層化
  • スケールで解けない問題 — キー空間の枯渇。7文字で3.5兆なので当面は問題ないが、8文字への移行パスを設計に入れておく（可変長キーを許容する）

⑬ 障害発生時

障害影響対処 / Graceful Degradation
Redis が全断全読みがDBへ → DBが即死する可能性アプリ内ローカルキャッシュで一次防御 + DBへのレート制限（同時実行数を絞る）。「一部のリダイレクトが失敗しても、DBを守る」判断
DB プライマリ障害書き込み不可。読みはレプリカで継続できる自動フェイルオーバー。★書き込み（新規作成）だけ止め、リダイレクトは動かし続ける——これが Degradation の好例
1シャード障害そのシャードのキーだけリダイレクト不可レプリカへ切り替え。影響は全体の 1/N に限定される（分割の副次的な利点）
リージョン障害そのリージョンからのアクセスが不可DNS/GSLB で他リージョンへ。読みは各リージョンにレプリカがあるので継続可能
キープール枯渇新規作成が失敗するフォールバックとして「ランダム生成 + 衝突チェック」に切り替える。残数のアラートを必ず設定

「まず最も単純な形から始めます。

ここに、読みが100倍多いので Redis を Cache-Aside で足します。データは不変なので無効化を考えなくてよく、キャッシュとの相性が非常に良いです。ヒット率90%以上が期待でき、これだけで読みの問題はほぼ解決します。

次にID生成ですが、ここが実は最大の設計判断です。ランダム生成だと毎回衝突チェックのDB読みが要り、キー空間が埋まるほど悪化します。連番だと衝突はしませんが推測可能になります。
私は「事前生成キープール」を採ります——バッチでランダムキーを大量に作って未使用テーブルに入れ、各APIサーバが1000個ずつ払い出しを受けてローカルから配る。これで推測不可能かつ、書き込み時のDBアクセスがゼロになります。

追撃質問1: 「301 と 302、どちらを使いますか？」
「解析が必要かで決まります」
・301（恒久）: ブラウザがキャッシュするので、2回目以降サーバに来ない。負荷は劇的に下がるが、クリック数が数えられなくなる。
・302（一時）: 毎回サーバに来るので解析できる。負荷は増える。
「クリック解析が要件にあるので302にします。負荷は Cache で吸収します」——このように、要件に紐づけて選ぶのが正しい答え方。
追撃質問2: 「Redis が全部落ちたらどうなりますか？」
「12,000 QPS が丸ごとDBに来て、DBも落ちます」——まずこれを正直に認めるのが重要です。
対策は3段階:
① アプリ内のローカルキャッシュ（数秒 TTL）で一次防御。人気リンクはこれで吸収できる
② DBへの同時接続数を絞る（Bulkhead）。全リクエストを通そうとするとDBが死ぬので、溢れた分は 503 を返す
③ Redis 自体を複数AZに分散し、全断の確率を下げる
「一部のリダイレクトを失敗させてでも、DBを守る」という判断を明示的に言えると、運用感覚があると評価されます。
追撃質問3: 「存在しないキーに大量アクセスされたら？」
キャッシュ貫通（Cache Penetration）です。キャッシュにヒットせず毎回DBを叩くので、Cache が無効化されます。
対策:
① Negative Caching: 「存在しない」という結果も短い TTL（60秒程度）でキャッシュする
② Bloom Filter: 「確実に存在しない」を高速に判定する。偽陽性はあるが偽陰性は無いので、フィルタとして機能する
③ IP ベースのレート制限

02 Instagram — 画像配信とフィード生成

結論: Instagram の難所は2つ——「画像の配信帯域」と「フィードの生成方法」です。前者は S3 + CDN でほぼ機械的に解け、後者が本当の設計問題。Twitter ほど極端ではないものの、fan-out の判断がここでも中心になります。

① 要件整理

機能要件（スコープ内）

・写真/動画の投稿
・フォロー / アンフォロー
・タイムライン（フォロー中の投稿を新しい順に）
・いいね / コメント

スコープ外にする

・ストーリーズ / リール / DM
・レコメンドアルゴリズム（今回は時系列順）
・検索・ハッシュタグ
→ 「まず時系列フィードに絞ってよいですか？」

非機能要件

・フィード表示 200ms 以内
・投稿は「アップロード完了」が速いこと（変換は非同期でよい）
・結果整合性を許容（投稿が数秒後にフィードに出るのはOK）

最重要の確認事項

「フォロワー数の分布は？」
→ 一般ユーザーは数百人、著名人は1億人。この非対称性が fan-out 設計を決める。

④ Database

図2-1: Instagram の全体像。画像バイナリがAPIサーバを通らないことと、フィードのハイブリッド生成が2大ポイント。

  • posts / users は RDB でも Cassandra でもよい — 「1投稿 = 1行、post_id で引く」という単純なアクセスなので、KVS 的な使い方になる。書き込み 3,600 QPS はシャーディングすれば RDB でも捌ける
  • post_id は時系列ソート可能なIDにする — Snowflake ID（タイムスタンプ + マシンID + 連番）。これでフィードのソートとカーソルページングが単純になる
  • follows テーブルは双方向に持つ — 「自分がフォローしている人」（フィード生成用）と「自分のフォロワー」（fan-out 用）で、必要な向きが違う。1つのテーブルで両方引こうとすると、片方が全表スキャンになる
  • カウンタ（いいね数）は分離 — 投稿本体と同じ行を更新すると、人気投稿でロック競合が起きる。Redis の INCR + 定期的なDB反映、または分散カウンタ

⑤ Cache

  • 3層のキャッシュを使い分ける
    ① フィードのリスト（投稿IDの配列） — Redis の Sorted Set。ユーザーごとに直近数百件
    ② 投稿メタデータ — Redis の Hash。post_id → {user, caption, urls, counts}
    ③ カウンタ（いいね/コメント数） — Redis の INCR。DBへは非同期でバッチ反映
  • キャッシュ効率が最も高いのはフィードリスト — 「アクティブユーザーの直近フィード」だけを持てばよい。全ユーザーぶんは不要（ログインしないユーザーのフィードは作らない）
  • 画像はキャッシュしない — CDN の役割。Redis に数MBのバイナリを入れるのは、メモリの無駄遣い
  • 無効化 — 投稿の削除・編集時にキーを DEL。いいね数のような高頻度更新は、無効化せず Redis を真実とし、DBへ非同期反映する

⑥ Replication

  • 読み取りレプリカを多数配置 — 読み 36万 QPS なので、レプリカとキャッシュの両方が必要
  • Read-Your-Writes の保証が必要な場面 — 「自分が投稿した直後に自分のプロフィールを見る」。投稿直後の N 秒はプライマリから読む、または自分の投稿だけローカルに保持する
  • 他人の投稿は結果整合性でよい — 「フォロー相手の投稿が数秒遅れて出る」は誰も困らない。この非対称性を明示できると、整合性の理解があると評価される
  • マルチリージョン — ユーザーの所属リージョンにデータを寄せる（データレジデンシー要件にも対応）。クロスリージョンのフォロー関係が発生するので、フィード生成が複雑になるトレードオフ

⑦ Partitioning

  • posts のシャードキー = post_id（ハッシュ） — 均等に分散する。user_id にすると、著名人のシャードだけが極端に大きくなる（Hot Partition）
  • ただし「あるユーザーの投稿一覧」を取るには全シャードに問い合わせが必要 — 対策は ①user_id → post_id のインデックスを別に持つ ②プロフィール表示用に user_id でも分割したビューを作る
  • follows のシャードキー — 「follower_id で分割したテーブル」と「followee_id で分割したテーブル」の2つを持つ（非正規化）
  • フィード（Redis）のシャードキー = user_id — 各ユーザーのフィードは1箇所に集約される
  • Hot Partition の実例 — 「1億フォロワーの著名人」のフォロワーリストは1シャードに収まらない。フォロワーリストをさらに分割するか、そもそも fan-out しない（pull にする）

⑧ Queue

図2-2: Fan-out の3方式。ハイブリッドが実務の答えで、「非アクティブユーザーに push しない」が効果的な追加最適化。

  • Queue が担う処理 — ①画像/動画の変換（重い・失敗しうる）②fan-out（大量書き込み）③通知の送信 ④分析基盤への転送 ⑤コンテンツモデレーション
  • 画像変換のキューを分ける — サムネイル（2秒）と動画（10分）を同じキューに入れると、Head-of-Line Blocking が起きる
  • 投稿とイベント発行の原子性 — DBに書いてから Kafka に publish すると、間で落ちるとイベントが失われる。Outbox Pattern を使う

⑨ CDN

  • CDN は選択ではなく必然 — 1.9 Tbps の配信をオリジンで捌くのは不可能。「CDN を使います」ではなく「CDN 無しでは物理的に成立しません」と言えるかが差
  • キャッシュキーの設計 — /media/{media_id}/{preset}.webp のように不変な URL にする。画像が変わったら新しい media_id を発行する（キャッシュ無効化が不要になる）
  • プリセット（サイズ）の設計 — thumb(150px) / medium(600px) / large(1080px)。端末とネットワークに応じてクライアントが選ぶ
  • フォーマット — WebP / AVIF を Accept ヘッダーで出し分ける。JPEG より30〜50%小さくなるので、帯域コストに直接効く
  • プライベート画像の扱い — 非公開アカウントの画像を CDN でキャッシュすると漏洩する。署名付きURL（有効期限付き）+ CDN の署名検証
  • オリジンシールド — CDN のエッジがミスしたとき、全エッジがオリジンに殺到しないよう、中間層を挟む

⑩ Storage

  • 画像/動画 → オブジェクトストレージ（S3）。110 PB/年。DBに入れる選択肢は存在しない
  • ストレージ階層 — 直近30日は Standard、それ以降は Infrequent Access、1年以上は Glacier。Instagram の閲覧は圧倒的に新しい投稿に偏るので、階層化のコスト効果が極めて大きい
  • 原本の保持 — 変換版だけ残して原本を削除するとコストは下がるが、新しいプリセット（AVIF対応など）を後から作れなくなる。原本は安価な階層に残すのが定石
  • メタデータ → DB（18 TB/年）。シャーディングで対応

⑫ スケール方法

  • 帯域（最大の課題） — CDN のヒット率を上げる（キャッシュキーの統一・TTL の延長）、フォーマット最適化、端末に応じた解像度の出し分け（不要に大きい画像を送らない）
  • fan-out — ①閾値を下げて Pull の比率を上げる ②非アクティブユーザーへの push を止める ③フィードの保持件数を減らす（直近300件のみ）
  • 読み取り — キャッシュ層の多段化（アプリ内 → Redis → DB）
  • 書き込み — シャード追加。post_id ハッシュ分割なので追加が容易
  • スケールで解けない問題 — 「フォロー数が非常に多いユーザーのフィード生成」。5,000人フォローしている人の Pull は重い。フォロー数に上限を設ける（実際 Instagram は7,500）のは、技術的制約を製品仕様にした例

設計の提示（順序が重要）
「このシステムの本質的な難所は2つあります。画像配信の帯域と、フィードの生成方法です。

まず帯域から。概算すると配信は約 1.9 Tbps になります。これはオリジンで捌ける量ではないので、CDN は選択ではなく必然です。加えて、アップロードも Presigned URL でクライアントから S3 に直接送らせ、APIサーバにバイナリを通しません。

次にフィード。ここが本当の設計問題です。Push（投稿時に全フォロワーのフィードに書く）は読みが速いが、1億フォロワーの著名人が投稿すると1億回の書き込みになります。Pull（読み取り時に集める）は書き込みが軽いが、読みが100倍多いこのシステムでは不利です。
なので、ハイブリッドにします——フォロワー1万人未満は Push、それ以上は Pull。読み取り時に両者をマージします。さらに、30日ログインの無いユーザーには Push しません。これだけで fan-out の書き込みが半分以下になります」
追撃1: 「fan-out の閾値はどう決めますか？」
「固定値ではなく、システム負荷に応じて動的に変えます。
初期値は1万人程度から始めて、fan-out キューの滞留を監視し、詰まってきたら閾値を下げて Pull の比率を上げます。
重要なのは、Push と Pull が排他ではなく、比率を調整できる連続的なつまみだと捉えることです。
また、閾値だけでなく「配信の優先度」も分けます——アクティブユーザーから先に配信し、非アクティブは後回し、または配信しません」
追撃2: 「フィード表示が遅いです。原因は？」
「切り分けの順序で答えます。
① 最も疑うのは N+1。投稿20件それぞれに「投稿者情報」「いいね数」「自分がいいねしたか」を個別に問い合わせると60クエリになります。MGET / IN句でバッチ取得すれば1桁変わります
② 次に Pull 対象（著名人）が多すぎるケース。フォロー中の著名人が数百人いると、マージのコストが上がります
③ キャッシュミス率の悪化
④ 画像の読み込み（これはCDN側の問題で、APIのレイテンシとは分けて考える）
『まずどこが遅いかを分解して測る』という姿勢を示すのが重要です」
追撃3: 「非公開アカウントの画像が CDN から漏れませんか？」
「良い指摘です。CDN は基本的に誰でも取得できるので、対策が必要です」
① 署名付きURL（有効期限とパスを署名）を発行し、CDN 側で署名を検証する
② URL を推測不可能にする（media_id をランダムに）——ただしこれは URL が漏れたら終わりなので、単体では不十分
③ 非公開コンテンツは CDN にキャッシュせず、オリジンで認可判定する（帯域は増えるが確実）
「①を基本とし、特に機微なものは③」というのが現実的な答えです。この観点を自分から出せると、セキュリティ意識があると評価されます。

03 Twitter(X) — fan-out 問題の極北

結論: Twitter は「1つの投稿が最大1億人に届く」という、fan-out が極端に非対称なシステムです。データは小さい（280文字）のに、配信の掛け算だけが巨大。Instagram との違いは、帯域ではなく『書き込み増幅』が唯一のボトルネックであることです。

① 要件整理

機能要件（スコープ内）

・ツイートの投稿（280文字 + 画像）
・フォロー / アンフォロー
・ホームタイムライン（フォロー中の投稿）
・ユーザータイムライン（特定ユーザーの投稿）

スコープ外にする

・DM / リスト / スペース
・トレンド算出
・アルゴリズムによる並び替え（時系列に固定）
・検索

非機能要件

・タイムライン表示 200ms 以内
・投稿から配信まで数秒（結果整合性でよい）
・著名人の投稿でもシステムが落ちないこと

最重要の確認事項

「フォロワー数の最大値は？」
→ 1億人。この1つの数字が、システム全体の設計を規定する。「平均200人」だけ聞いて設計すると必ず破綻する。

④ Database

図3-1: Twitter の全体像。「タイムラインには ID だけを保存する」という判断が、設計を成立させる鍵。

  • tweets は KVS で十分 — 「tweet_id で1件引く」というアクセスのみ。結合もトランザクションも不要
  • タイムラインに本文を入れない — ID だけを保存する。本文をコピーすると容量が37倍になり、削除・編集への対応も不可能になる
  • Snowflake ID の採用理由 — ①分散生成できる ②時系列にソート可能なので、カーソルページングとマージソートが単純になる。Twitter が Snowflake を開発した理由そのもの
  • ソーシャルグラフにグラフDBは不要 — 「フォロー中の一覧」「フォロワーの一覧」しか引かない（2ホップ以上を辿らない）。「友達の友達」の推薦が要件に入るなら話は別

⑤ Cache

  • タイムライン（Redis）が実質のプライマリストア — 「キャッシュ」というより「事前計算された結果の保存先」。ミスしたら Pull で再構築する
  • 保持件数の制限 — 1ユーザー 800件程度で打ち切る。無制限に保持すると、容量が線形に増えてしまう。それ以上を遡るユーザーは Pull で対応
  • ツイート本文のキャッシュ — 人気ツイートは何百万回も読まれる。Redis + アプリ内ローカルキャッシュの2段構え
  • アクティブユーザーのみキャッシュ — 3億人全員のタイムラインを常に持つのは無駄。ログイン時に構築し、非アクティブになったら破棄する
  • ソーシャルグラフのキャッシュ — 「誰をフォローしているか」は Pull 時に毎回必要。これをキャッシュしないと、Pull が極端に重くなる

⑥ Replication

  • 読み取りレプリカ + マルチリージョン — 読み 30万 QPS。ユーザーに近いリージョンで読ませる
  • Read-Your-Writes が特に重要 — 「ツイートした直後に自分のプロフィールに出ない」はユーザーが即座に気づく。自分の投稿は、fan-out を待たずに自分のタイムラインに即座に挿入する
  • 他人の投稿は数秒遅れてよい — fan-out が非同期である以上、これは仕様
  • Redis のレプリケーション — タイムラインが失われると、全ユーザーぶんを Pull で再構築することになり負荷が爆発する。Redis もレプリカを持ち、AZ をまたいで配置する

⑦ Partitioning

  • tweets のシャードキー = tweet_id（ハッシュ） — 均等分散。user_id にすると著名人のシャードが偏る
  • timelines のシャードキー = user_id — 各ユーザーのタイムラインは1箇所にまとまる（読み取りが1回で済む）
  • follows の Hot Partition — 1億フォロワーのユーザーのフォロワーリストは1シャードに入らない。フォロワーリストを複数シャードに分割する（followee_id + bucket_id をキーにする）
  • 時系列でのシャーディングは避ける — 「今月のツイート」だけに書き込みが集中し、古いシャードは遊ぶ。ただしアーカイブ目的で、古いデータを別ストレージに移すのは有効

⑧ Queue

図3-2: fan-out の実装。「ジョブの分割」「優先度」「レート制限」の3点セットが必須。

⑨ CDN

  • Instagram ほど帯域は問題にならない — 本文は 300B なので、テキストの配信は軽い
  • 画像・動画があれば Instagram と同じ構成 — S3 + CDN + プリセット
  • API レスポンスの CDN キャッシュ — 「著名人のユーザータイムライン」は多くの人が同じものを見る。短い TTL（数秒〜数十秒）でエッジキャッシュすると、オリジンへの負荷が劇的に下がる
  • ホームタイムラインはユーザーごとに違うのでキャッシュできない — 「パーソナライズされたものは CDN に乗らない」という原則
  • 静的アセット（JS/CSS/フォント） — 当然 CDN

⑩ Storage

  • 本文は DB（KVS）で完結 — 16 TB/年は現実的な規模
  • メディアは S3 + CDN — Instagram と同じ
  • タイムライン（Redis）は「揮発してよいデータ」として扱う — 失われても Pull で再構築できる設計にしておく。これが Redis を「キャッシュ」と呼べる条件
  • アーカイブ — 古いツイートは低頻度アクセス。S3 + 検索インデックスで代替する

⑫ スケール方法

  • fan-out の比率調整 — Push/Pull の閾値を下げる。これが最も効く「つまみ」
  • 非アクティブユーザーの除外 — 30日未ログインには配信しない。実測で fan-out 量が半分以下になることが多い
  • タイムライン保持件数の削減 — 800件 → 300件。Redis の容量が 1/2.7 に
  • 読み取り — Redis シャード追加 + アプリ内キャッシュ
  • スケールで解けない問題 — 「1億フォロワーへの即時配信」は原理的に不可能。「著名人の投稿は数十秒〜数分遅れて届く」ことを仕様として受け入れる——これを明言できるのが設計者の判断

「同じ SNS でも、データサイズが2桁違うと設計の中心が変わる」という一般化ができると、深い理解を示せます。

結論: YouTube はシステム設計の中でも「桁が違う」問題です。配信帯域が数十〜数百 Tbps に達し、CDN の設計そのものが主題になります。加えて「アップロードから公開まで」のトランスコードパイプラインが、非同期処理の教科書的な例になります。

④ Database ／ ⑩ Storage ／ ⑨ CDN（一体で設計する）

図4-1: YouTube の全体像。トランスコードのセグメント並列化と、多段CDNによる帯域の階層的な吸収が2大ポイント。

⑤ Cache

  • 動画セグメントのキャッシュ = CDN そのもの — これが全て。「人気動画の上位1%が、視聴の90%を占める」というべき乗則により、CDNのヒット率が極めて高くなる
  • 多段キャッシュ — エッジ（ISP内）→ リージョナル → オリジン。エッジで95%、リージョナルでさらに4% を吸収し、オリジンに来るのは1%以下にする
  • メタデータのキャッシュ — 動画情報・再生回数は Redis。こちらは些末な負荷
  • 新着動画のキャッシュミス問題 — バイラルな新着動画は、最初は全エッジでミスする。オリジンシールド（中間層）を挟み、オリジンへの同時アクセスを1本にまとめる（Request Coalescing）
  • プリフェッチ — 人気が出そうな動画を、公開前にエッジへ事前配置する

⑥ Replication

  • 動画ファイルは地理的にレプリケーション — 人気動画は世界中のリージョンに複製し、不人気動画は1〜2リージョンのみ。「全動画を全リージョンに置く」のはコスト的に不可能
  • メタデータは通常のレプリカ構成 — 読み取りレプリカ + マルチリージョン
  • 再生回数の整合性 — 厳密な整合性は不要。各リージョンで独立にカウントし、後で集約する（12章の「分配可能な集計」）
  • アップロード直後の可用性 — 変換完了後、まず1リージョンで公開し、視聴が増えたら他リージョンへ複製する（需要駆動のレプリケーション）

⑦ Partitioning

  • 動画ファイル: video_id + セグメント番号でパス分割 — オブジェクトストレージが自動的に分散するので、明示的なシャーディングは不要
  • メタデータ: video_id ハッシュ — 均等分散
  • 再生イベントの partition key — video_id にすると人気動画で Hot Partition になる。集計目的なら video_id + ランダムサフィックス（Salting）で分散し、後で合算する
  • トランスコードジョブの分散 — セグメント単位なので自然に並列化できる

⑧ Queue

  • トランスコードキュー（最重要） — 解像度ごと・セグメントごとにジョブを分割。出力パスを決定論的にすることで、再実行が安全になる（冪等）
  • キューを処理時間で分ける — 「サムネイル生成（2秒）」と「4K変換（数十分）」を同じキューに入れると、Head-of-Line Blocking が起きる
  • 優先度キュー — 有料チャンネル・急上昇動画を優先。「全員平等」だと、重要な動画の公開が遅れる
  • 再生イベントのストリーム — Kafka → リアルタイム集計（速報値）+ バッチ（確定値）
  • その他 — 著作権チェック・モデレーション・通知・検索インデックス更新

⑨ CDN（詳細）

  • この規模では CDN が「システムの主役」 — 166 Tbps。CDN事業者から借りると、帯域コストだけで年間数千億円規模になるため、自社エッジ網を構築する経済合理性が生まれる
  • ISP内へのキャッシュサーバ設置 — ISP にとっても外部トランジット費用が減るので、双方に利益がある
  • キャッシュキー — /{video_id}/{quality}/segment_{n}.ts。完全に不変なので、TTL を極めて長くできる
  • コーデックの選択 — H.264（互換性）/ VP9・AV1（圧縮率）。AV1 は H.264 より30〜50%小さいので、帯域コストに直結する。ただし変換コストは高い——「再生回数の多い動画だけ AV1 に変換する」という費用対効果の判断がある
  • ABR（HLS / DASH） — 数秒のセグメント + manifest。プレイヤーが帯域に応じて解像度を切り替えるので、回線が細くても再生が止まらない

⑩ Storage（詳細）

  • 階層化が必須 — 直近/人気 = 高速ストレージ、古い/不人気 = アーカイブ層。EB級では、階層化しないとコストが成立しない
  • 原本の保持 — 新しいコーデック（AV1等）が普及したときに再変換するため、原本は残す。ただし最も安い階層へ
  • 不人気動画の扱い — 全動画の大半はほとんど視聴されない。低解像度だけを保持し、高解像度は視聴要求があったときにオンデマンドで生成するという選択肢もある
  • 削除の設計 — 動画削除時、全リージョンのレプリカとCDNキャッシュから消す必要がある。法的要件（権利侵害・違法コンテンツ）では即時性が求められる

05 Google Drive — メタデータの整合性と共有権限

結論: Drive の難所は「ファイル本体」ではなく「メタデータのツリー構造と権限」です。ファイルはS3に置けば終わりですが、『フォルダの移動』『共有権限の継承』『あるユーザーが見られるファイル一覧』が本当の設計問題。ここを「ファイルストレージの問題」と誤読すると、面接で表層的な答えになります。

① 要件整理

機能要件（スコープ内）

・ファイルのアップロード / ダウンロード
・フォルダ階層（作成・移動・削除）
・共有（ユーザー / グループ / リンク）と権限
・検索（ファイル名・本文）
・バージョン履歴

スコープ外にする

・リアルタイム共同編集（別の設計問題）
・Google Docs のようなドキュメント編集機能
・OCR / AI検索
→ 「まずファイル管理と共有に絞ってよいですか？」

非機能要件

・権限判定は強い整合性が必要（共有を解除した直後に見られてはいけない）
・ファイル一覧の表示 200ms
・耐久性 99.999999999%（データ消失は許されない）

最重要の確認事項

「権限の継承はありますか？」
→ ある。フォルダの権限が配下の全ファイルに継承される。これが設計を一気に難しくする。

④ Database

図5-1: 権限判定の3方式。「付与は非同期でよいが、剥奪は同期」という非対称性が実務の核心。

  • メタデータは RDB（強い整合性が必要） — フォルダ移動時の循環チェック、権限の一貫性。シャーディングした RDB か、Spanner のような分散SQL
  • ツリー構造の表現 — ①隣接リスト（parent_id）: 更新は軽いが、祖先を辿るのが重い ②Materialized Path（/root/a/b/c）: 祖先の判定が1クエリ（LIKE 前方一致）だが、移動時に配下全部を更新 ③Closure Table: 全祖先-子孫のペアを持つ。読みが速いが容量が増える
  • 実務では Materialized Path + 非正規化された実効権限 が現実的。「深さの上限」を製品仕様として設けることで、移動時の更新量を抑える
  • 「自分に共有されたファイル一覧」の難しさ — 全ファイルを走査できないので、user_id → 共有されたfile_id の逆引きインデックスを持つ（非正規化）

⑤ Cache

  • フォルダ一覧のキャッシュ — 「よく開くフォルダ」は繰り返しアクセスされる。ただし権限が絡むので、ユーザーごとにキャッシュする必要がある
  • 権限判定結果のキャッシュ — 最も効果が大きいが、最も危険。TTL を短く（数十秒）し、剥奪時は明示的に無効化する
  • 拒否リスト（Deny List）のキャッシュ — 「最近権限が剥奪された (user, file) のペア」を小さな Redis Set に持ち、アクセス時に必ず確認する。これで「付与は非同期・剥奪は同期」を実現する
  • ファイルメタデータのキャッシュ — file_id → メタ情報
  • ファイル本体はキャッシュしない — 個人のファイルは共有されないので、キャッシュのヒット率が低い

⑥ Replication

  • 権限は強い整合性が必要 — レプリカラグ中に「剥奪されたはずの権限」で読まれるのは事故。権限判定はプライマリ、または線形化可能な読み取りを使う
  • ファイル一覧などは結果整合性でよい — 「共有されたファイルが数秒後に一覧に出る」は許容範囲
  • ファイル本体は多重レプリケーション — 耐久性 99.999999999% のため、複数AZ・複数リージョンに複製。Erasure Coding（消失訂正符号）で、3重コピーより少ない容量で同等の耐久性を得る
  • データレジデンシー — EU のデータは EU に置く等の法的要件。リージョンをまたぐ共有が発生すると設計が複雑になる

⑦ Partitioning

  • シャードキー = owner_id（または drive_id） — 「1人のユーザーのファイル群は1シャードに集約する」。フォルダ一覧・ツリー操作が1シャード内で完結する
  • 共有がシャードをまたぐ問題 — A のシャードにあるファイルを B が見るとき、B のシャードには情報がない。「自分に共有されたファイル」の逆引きインデックスを、B のシャードにも持つ（非正規化）
  • 企業アカウントの Hot Partition — 10万人規模の企業ドライブが1シャードに乗らない。大規模テナントは専用シャードに分離する
  • ファイル本体はオブジェクトストレージが自動分散 — 明示的なシャーディングは不要

⑧ Queue

  • 権限伝播（フォルダ移動・共有変更） — 配下数万ファイルの実効権限更新を非同期で。ただし剥奪だけは同期の拒否リストで即時反映
  • 検索インデックスの更新 — ファイル名 + 本文抽出（PDF/Office）→ Elasticsearch
  • サムネイル / プレビュー生成 — 重い処理なので非同期
  • ウイルススキャン — アップロード後に非同期。スキャン完了前はダウンロードを制限する設計もある
  • 通知 — 「ファイルが共有されました」「コメントが付きました」
  • ゴミ箱の完全削除 — 30日後にストレージから物理削除するバッチ

⑨ CDN

  • プライベートファイルは CDN でキャッシュしない — 個人のファイルは共有されないのでヒット率が低く、かつ漏洩リスクがある
  • 署名付きURL + 短い有効期限 — 権限判定してから、5分程度の有効期限付きURLを発行する
  • 公開共有リンクのファイルは CDN 可 — 「リンクを知っている全員が閲覧可」なら、キャッシュしても問題ない。大量ダウンロードされる配布ファイルで効果が大きい
  • サムネイル・プレビュー画像 — こちらは CDN に乗せる価値がある（一覧表示で大量に読まれる）
  • 静的アセット — 当然 CDN

⑩ Storage

  • 重複排除（Deduplication）が最も効く — 同じファイル（会社の資料・アプリのインストーラ）を何万人も持っている。content_hash が同じなら実体は1つだけ保存する。実効ストレージが数分の1になる
  • 重複排除のセキュリティリスク — 「ハッシュを知っていればアップロード済みと判定される」を悪用すると、ファイルの存在を推測できてしまう。対策: ユーザー単位でハッシュを分ける、または重複排除をサーバ側でのみ行う
  • バージョン履歴 — 全バージョンを保存するとコストが爆発。直近N世代 + 差分保存、古いものは自動削除
  • 階層化 — 長期間アクセスされないファイルは Coldline / Archive 層へ
  • Erasure Coding — 3重コピー（300%）より少ない冗長度（150%程度）で同等の耐久性

06 Dropbox — 差分同期と競合解決

結論: Dropbox の Google Drive との決定的な違いは「ローカルにファイルの実体があり、双方向に同期する」ことです。これにより『ブロック単位の差分同期』と『競合の解決』という、Drive には無い難所が生まれます。「1GBのファイルの1行を変えたら、1GB再送するのか？」——この問いが設計の出発点です。

① 要件整理

機能要件（スコープ内）

・デスクトップとクラウドの双方向同期
・複数デバイス間の同期
・オフライン編集 → オンライン復帰時の同期
・バージョン履歴 / 復元
・共有フォルダ

スコープ外にする

・リアルタイム共同編集
・ファイルのプレビュー生成
・Paper のような独自ドキュメント

非機能要件

・帯域の効率（大きいファイルの小さな変更を効率的に送る）
・変更の検知から同期完了まで数秒
・オフライン中の変更を失わない
・耐久性（データ消失は許されない）

最重要の確認事項

「同じファイルを2デバイスで同時に編集したらどうしますか？」

④ Database ／ ⑩ Storage（一体で設計する）

図6-1: ブロック分割による差分同期と、競合解決の方針。「両方残す」がデータ消失を避ける唯一の安全な選択。

⑤ Cache

  • ブロックの存在確認（hash → exists）のキャッシュ — アップロードのたびに大量のハッシュ問い合わせが来る。Bloom Filter + Redis で高速化する
  • メタデータ（ファイル一覧・rev）のキャッシュ — 同期のたびに読まれる
  • 変更ジャーナル（cursor → 差分）のキャッシュ — 「前回から何が変わったか」の問い合わせが最も頻繁
  • ブロック本体はキャッシュしない — 個人ファイルはヒット率が低い。ただし共有フォルダの人気ファイルは例外
  • クライアント側キャッシュが最も重要 — ローカルにブロックのハッシュインデックスを持つことで、サーバへの問い合わせ自体を減らす

⑥ Replication

  • メタデータは強い整合性が必要 — rev（バージョン番号）の一意性が競合検出の基盤。レプリカラグで古い rev を読むと、競合検出が破綻する
  • 同一ユーザーの操作は同一シャードのプライマリで処理 — これにより、rev の単調増加が保証される
  • ブロックは多重レプリケーション + Erasure Coding — 耐久性が最優先
  • 変更通知は結果整合性でよい — 「他デバイスへの反映が数秒遅れる」は許容範囲

⑦ Partitioning

  • メタデータのシャードキー = user_id — 1ユーザーの全ファイルが1シャードに集約されるので、rev の管理と差分計算が単純になる
  • 共有フォルダがシャードをまたぐ — 共有フォルダを「namespace」という独立した単位にし、それ自体をシャーディングの単位にする（Dropbox の実際の設計に近い）。ユーザーは複数の namespace に所属する
  • ブロックのシャードキー = ハッシュ — 自然に均等分散する
  • 大容量ユーザーの Hot Partition — 数TB・数百万ファイルを持つユーザー。namespace 単位で分割することで緩和

⑧ Queue

  • 変更通知の配信 — 1つの変更を、他デバイス + 共有相手の全デバイスに通知する。共有フォルダが100人と共有されていれば、100人 × 3デバイス = 300通知——小さな fan-out
  • ブロックの複製・階層移動 — アップロード後に他リージョンへ複製
  • 孤児ブロックの回収（GC） — どのファイルからも参照されなくなったブロックを削除する。参照カウントの管理が必要で、消してはいけないものを消す事故が起きやすい危険な処理
  • ウイルススキャン・インデックス生成

⑨ CDN

  • 個人ファイルのブロックは CDN 不要 — ヒット率が低く、プライベート
  • 公開共有リンクは CDN 有効 — 「大勢にファイルを配布する」用途では効果が大きい
  • エッジでのブロック存在確認 — アップロード時のハッシュ問い合わせをエッジで処理できれば、レイテンシが改善する
  • クライアントアプリの配布 — 当然 CDN

⑩ Storage（詳細）

  • ブロック単位の重複排除が極めて効く — ファイル全体が違っても、一部のブロックは共通していることが多い（同じテンプレートから作った資料など）。Drive のファイル単位より効率が良い
  • 参照カウントの管理 — ブロックを削除してよいのは、参照が0になったとき。分散環境で正確な参照カウントを保つのは難しく、「削除は保守的に（迷ったら消さない）」が原則
  • バージョン履歴 — ブロックリストを変えるだけで過去版を表現できるので、履歴の保存コストが小さい（変更ブロック分だけ）
  • 暗号化 — 保存時暗号化。ただしエンドツーエンド暗号化にすると、サーバ側で重複排除ができなくなるトレードオフ

  • 接続サーバをステートレスに保つ — 接続情報を Redis に外出しし、サーバを自由に増減できるようにする

この「挿入問題」に気づけるかは、差分同期を本当に理解しているかの試金石です。ただし可変長は計算コストが高いので、「まず固定長で始めて、必要なら可変長へ」という段階的な判断も正当です。

② 接続情報を Redis に外出しし、接続サーバをステートレスにする

「あります。2つ挙げます」

② ハッシュだけでダウンロードできる実装だと、内容を知らなくてもファイルを取得できる

・重複排除をユーザー/テナント単位に限定する（横断的な重複排除を諦める）
・ハッシュの問い合わせにレート制限をかける
・ダウンロードは必ずファイルの所有権を検証してから（ハッシュだけでは取得させない）

07 Chat（LINE / Slack / WhatsApp）— 接続の維持と順序保証

結論: Chat の難所は「メッセージの保存」ではなく「数億の常時接続をどう維持し、どのサーバに繋がっているかをどう知るか」です。加えて、順序保証・既読管理・オフライン配信という、他サービスには無い要件が加わります。「WebSocket を使います」で終わらせず、接続レジストリの設計まで踏み込めるかが分水嶺です。

① 要件整理

機能要件（スコープ内）

・1対1チャット / グループチャット
・オンライン/オフライン状態の表示
・既読 / 未読の管理
・オフライン中のメッセージ受信
・メッセージ履歴の取得

スコープ外にする

・音声/ビデオ通話
・エンドツーエンド暗号化（言及はするが実装は省く）
・リアクション / スレッド
・ファイル送信（画像はメタのみ）

非機能要件

・メッセージ配信 100ms 以内
・メッセージを絶対に失わない
・同一会話内の順序は必ず保つ
・オフライン中のメッセージを確実に届ける

④ Database ／ ⑧ Queue（一体で設計する）

図7-1: Chat の全体像。接続レジストリ・会話ごとの seq・既読の集約が3大設計ポイント。

  • messages は Cassandra 系が最適 — partition key = conversation_id、clustering key = seq DESC にすると、「この会話の最新50件」が1回のシーケンシャル読みで取れる。書き込みも追記のみで高速
  • seq の採番 — 会話ごとの単調増加。同一会話への書き込みを1箇所に直列化する必要がある（conversation_id でシャーディングすれば自然に達成される）
  • 未読数の計算 — conversations.last_seq - read_state.last_read_seq の引き算。レコードを数える必要がない
  • グループの大規模化 — 5万人グループでは fan-out が問題になる。その場合は push せず、クライアントがポーリング/購読する（Twitter の pull と同じ発想）

⑤ Cache

  • 接続レジストリ（Redis）が最重要 — user_id → server_id。これが落ちるとメッセージが誰にも届かなくなる。TTL + heartbeat で更新する
  • 最近の会話リスト — 「チャット一覧画面」で読まれる。会話ごとの最終メッセージ + 未読数
  • 直近メッセージのキャッシュ — 会話を開いたときの最新50件
  • オンライン状態（presence） — 最も更新頻度が高いデータ。Redis に TTL 付きで持ち、heartbeat で延長する。「TTL が切れた = オフライン」という設計にすると、明示的な切断通知が不要になる
  • presence の fan-out に注意 — 「友達1,000人がオンラインになった」を全員に通知すると爆発する。「今表示している画面の相手」だけを購読する

⑥ Replication

  • メッセージは絶対に失えない — 書き込みは複数レプリカへの同期書き込み（quorum）。「ack を返した = 確実に保存された」を保証する
  • ack のタイミングが設計判断 — DBに永続化してから ack を返す。「受け取ったら即 ack」だと、サーバが落ちたときにメッセージが消える
  • 読み取りは結果整合性でよい — 履歴の取得は多少古くても問題ない
  • マルチリージョン — 同じ会話の参加者が別リージョンにいる場合、どちらかをホームリージョンとして固定する。両方で書き込むと seq の一意性が壊れる

⑦ Partitioning

  • messages のシャードキー = conversation_id — 同じ会話のメッセージが1箇所に集まるので、seq の採番と履歴取得が単純になる
  • 巨大グループの Hot Partition — 5万人グループの会話が1パーティションに集中する。対策: 時間でさらに分割する（conversation_id + 年月）
  • read_state のシャードキー = user_id — 「自分の全会話の未読数」を1回で取れる
  • 接続サーバの割り当て — user_id のハッシュで固定するか、最も空いているサーバに割り当てるか。前者は接続レジストリが不要になるが、サーバ増減時に大量の再接続が発生する。実務ではレジストリ方式が柔軟

⑧ Queue

  • Pub/Sub による接続サーバへのルーティング — サーバごとにチャネルを持ち、該当サーバにだけ配信する。Redis Pub/Sub か Kafka
  • Push通知（APNs / FCM） — オフラインユーザーへの配信。外部サービスなので失敗しうる → キュー経由でリトライ
  • グループの fan-out — 大規模グループでは、メンバーへの配信をバッチ分割する
  • 既読状態の非同期反映 — 既読は高頻度更新なので、Redis を真実としてDBへは非同期でバッチ反映

⑨ CDN

  • テキストメッセージに CDN は無関係 — パーソナライズされたリアルタイム通信なのでキャッシュできない
  • 画像・動画・ファイルは CDN — 署名付きURL + 短い有効期限（プライベートコンテンツ）
  • WebSocket の接続点をエッジに置く — クライアントから最も近いエッジで TLS を終端し、そこからバックボーン経由でオリジンへ。RTT が改善し、モバイル回線での接続安定性が上がる
  • スタンプ・絵文字などの静的アセット — CDN

⑩ Storage

  • メッセージ本体は DB（2.2 PB/年） — 保持期間の設計が重要。「無期限保存」はコストが線形に増える
  • 階層化 — 直近3ヶ月は高速ストレージ、それ以前はアーカイブ。チャットの閲覧は圧倒的に直近に偏る
  • メディアはオブジェクトストレージ
  • エンドツーエンド暗号化を採用する場合 — サーバは中身を見られないので、検索・モデレーション・マルチデバイス同期が全て難しくなる。「E2EEにしますか？」は要件確認で必ず聞くべき項目

08 Uber — 地理検索とリアルタイムマッチング

結論: Uber の難所は「大量の位置更新（書き込み）」と「近傍検索（読み取り）」の両立です。緯度経度を素朴にDBに入れて範囲検索すると、確実に破綻します。Geohash / S2 による空間の1次元化が、この問題の中心的な解法です。

  • 位置履歴は別ストレージ — 5.4 TB/日。Kafka → S3/Cassandra へ非同期で流す（分析・請求・トラブル調査用）。「現在位置」と「履歴」で全く別の設計にするのが重要
  • rides（乗車）は RDB — 状態遷移とトランザクションが必要。量は少ない（3,000万/日）ので RDB で十分

⑤ Cache

  • Redis が「キャッシュ」ではなく「プライマリストア」 — 現在位置はここが真実。失われても、数秒後の位置更新で復元される（自己修復する）——これが位置情報の特殊な性質
  • ETA（到着予測時間）のキャッシュ — 経路計算は重いので、近似（直線距離 × 係数）で済ませ、正確な値は非同期で更新する
  • サージ倍率のキャッシュ — 地域 × 時間帯ごとの需給バランス。数分ごとに更新
  • 地図タイル・ジオコーディング結果 — 外部APIの呼び出しを減らす

⑥ Replication

  • 位置情報のレプリケーションは重要度が低い — 失われても数秒で復元されるので、耐久性より書き込み性能を優先してよい
  • rides（乗車データ）は強い耐久性が必要 — 決済に繋がるので、複数レプリカへの同期書き込み
  • リージョンごとに独立 — 都市単位でシャーディングしているので、リージョンをまたぐレプリケーションはほぼ不要。これが Uber の設計の綺麗なところ
  • DR（災害対策） — 都市単位のフェイルオーバー。「東京が落ちても大阪は動く」という分離が自然に達成される

⑦ Partitioning（詳細）

  • 地理シャーディングが最も自然 — マッチングが地理的に閉じているため、シャード間の通信がほぼ不要。これは他のサービスには無い利点
  • Hot Partition: 大都市の中心部 — 渋谷駅前のセルに数千人が集中する。セルの階層レベルを動的に変える（密集地は細かく、郊外は粗く）
  • 境界問題 — 都市の境界にいる乗客には、隣の都市のドライバーも候補になるべき。境界付近では複数シャードに問い合わせる
  • イベント時の集中 — コンサート終了時に1箇所へ需要が集中。サージプライシングは、技術的な負荷分散も兼ねている（価格で需要を分散させる）

⑧ Queue

  • 位置情報のストリーム — Kafka で受け、①リアルタイム処理（需給計算・サージ）②分析基盤への転送 ③履歴の永続化 に分岐させる
  • マッチングは同期に近い — 数秒以内に結果を返す必要があるので、キューを挟むと遅すぎる。ただしドライバーへのオファー配信は非同期
  • オファーのタイムアウト管理 — 「15秒で応答が無ければ次のドライバーへ」。タイマーが必要（Chat の既読タイムアウトと同じ構造）
  • 乗車後の処理 — 料金計算・決済・領収書・評価依頼を Saga として非同期実行
  • 需給の集計 — サージ倍率の計算はストリーム処理（Flink）

⑨ CDN

  • 位置情報にCDNは無関係 — 完全にリアルタイム・パーソナライズされたデータ
  • 地図タイル — これは CDN が極めて有効。全ユーザーが同じタイルを見るので、ヒット率が非常に高い
  • 静的アセット・アプリの配布 — CDN
  • エッジでの接続終端 — モバイル回線からの WebSocket 接続を、近いエッジで終端すると安定性が上がる

⑩ Storage

  • 現在位置 → Redis（メモリ）。250MB
  • 位置履歴 → 時系列DB / S3。5.4 TB/日。用途は分析・請求の根拠・トラブル調査。保持期間を明確に決める（法的要件と分析要件のバランス）
  • rides（乗車データ）→ RDB。永続保存（会計・法的要件）
  • プライバシーへの配慮 — 位置履歴は極めて機微な個人情報。保持期間の制限・匿名化・アクセス制御が必須

⑫ スケール方法

  • 地理シャーディングの細分化 — 都市 → 区 → セル。シャード間が独立しているので、追加が極めて容易
  • 位置更新の頻度を動的に変える — 停止中は10秒、高速移動中は2秒。これだけで書き込みが大幅に減る
  • 差分送信 — 前回から動いていなければ送らない
  • プロトコルの効率化 — HTTP → gRPC ストリーム / 独自バイナリ。50Bのペイロードに数百Bのヘッダーを付けるのは無駄
  • スケールで解けない問題 — 「イベント終了時の需要集中」。技術ではなくサージプライシング（価格で需要を分散させる）という事業的な解決が必要。これを「技術で解けないので、製品で解く」と言えると視野の広さを示せる

⑭ 面接での回答例

設計の提示（他サービスとの非対称性を指摘する）
「概算から始めます。同時オンラインドライバー500万人が4秒に1回位置を送ると、125万 QPS の書き込みになります。
一方、乗車リクエストは1日3,000万 ÷ 86,400 で 約350 QPS、ピークでも1,750 QPS。
つまりこのシステムは、これまでの読み偏重なサービスと逆で、書き込みが支配的です。

ここで重要な観察があります。現在位置は 500万 × 50B = 250MB しかありません。つまり全部メモリに載ります。DBに書く必要がないんです。
位置履歴は5.4TB/日と大きいですが、これは用途が違う（分析・請求根拠）ので、Kafka 経由で別ストレージに非同期で流します。

次に地理検索。緯度経度で範囲検索すると、2つの範囲条件でB-Treeインデックスが効かず、125万 QPS の更新にも耐えられません。
なので Geohash / S2 で空間を1次元化します。地球を格子に分け、各セルにIDを振る。近い場所は似たIDになるので、Redis の Set で『セル → ドライバー集合』を持てば、検索が数ミリ秒で終わります」
追撃1: 「位置更新のたびにインデックスを更新するのは重くないですか？」
「重要な指摘です。ここに最適化があります」
大半の位置更新では、ドライバーは同じセル内に留まっています（セルサイズを適切に選べば）。
なので:
・セルが変わらなければ、座標だけを更新する（Set の操作は不要）
・セルをまたいだときだけ、前のセルから削除して新セルに追加する

さらに:
・停止中のドライバーは更新頻度を下げる（4秒 → 10秒）
・前回から動いていなければ送らない
「125万 QPS を減らす」という発想を持てるかが、コスト意識の指標になります。
追撃2: 「同じドライバーに2件割り当てられませんか？」
「起きます。これがこのシステムで唯一、強い整合性が必要な場所です」
2つの乗車リクエストが近傍検索で同じドライバーを選ぶことは普通に起きます。

対策は条件付き更新（楽観ロック）:
UPDATE drivers SET status='assigned', ride_id=? WHERE driver_id=? AND status='available'
0行更新なら「既に取られた」と分かるので、次の候補へ移ります。

加えて:
・オファーには15秒のタイムアウトを設ける。応答が無ければ status を戻して次へ
・ドライバーが辞退した場合も同様
「システム全体は結果整合性でよいが、この1点だけは強い整合性が必要」という切り分けを示せると、整合性の理解が深いと評価されます。
追撃3: 「コンサート終了で1万人が同時に配車を求めたら？」
「3段階で答えます。
① 技術的な対処: そのセルの近傍検索が重くなるので、セル階層を細かくして分散させる。マッチングワーカーをスケールさせる
② キューイング: マッチング要求をキューに入れ、順番に処理する。待ち時間を正直に表示する（「現在10分待ち」）——期待値を管理することも設計の一部です
③ 最も重要: これは技術では解けません。1万人の乗客に対してドライバーが500人しかいなければ、どんなに最適化しても足りない。
サージプライシングが答えです——価格を上げることで、①需要を抑制し ②周辺のドライバーを引き寄せる。つまり価格が負荷分散の仕組みとして機能しています。

『技術で解けない問題を、製品の仕組みで解く』という視点を示せると、視野の広さが評価されます」

09 Booking.com — 在庫の同時実行制御

結論: 予約システムの本質は「有限な在庫を、同時に来た複数の人に正しく割り当てる」ことです。読みは1000:1で圧倒的に多いのにキャッシュしにくく、書き込みは少ないのに強い整合性が必要——この非対称性が、これまでのサービスと決定的に違う点です。

① 要件整理

機能要件（スコープ内）

・条件（場所・日付・人数）での検索
・空室・料金の表示
・予約の作成（在庫の引き当て）
・キャンセル
・施設側の在庫・料金管理

スコープ外にする

・決済の詳細
・レビュー / メッセージ
・ランキングアルゴリズム
・OTA間の在庫同期（言及はする）

非機能要件

・検索 300ms 以内（離脱率に直結）
・オーバーブッキングを起こさない（最重要）
・在庫表示は数秒古くてもよい
・予約の記録は絶対に失わない

最重要の確認事項

「オーバーブッキングは絶対NGですか？」
→ 「航空券のように意図的に許容する」設計もある。ホテルではNGが基本。ここで設計が分岐する。

④ Database

図9-1: 在庫の同時実行制御。条件付き更新・Hold・バッファ在庫の3層と、連泊予約の原子性が設計の核心。

  • 在庫は RDB 一択 — 連泊で複数レコードを原子的に更新する必要があるので、トランザクションが必須。「NoSQL のほうがスケールする」という理由で選ぶと、この要件で破綻する
  • 在庫の量は 750GB と大きいが、書き込みは 12 QPS — RDB で全く問題にならない。「スケールが心配」は杞憂
  • bookings（予約）も RDB — 状態遷移・決済との整合性・監査要件
  • 検索用のデータは別に持つ — 「在庫の正本（RDB）」と「検索用の非正規化データ（Elasticsearch）」を分離する。CDC で同期（後述）

⑤ Cache

図9-2: 検索と予約で整合性のレベルを変える。これにより、圧倒的な読みと厳密な書きを両立できる。

  • 検索結果のキャッシュ — 「東京・9/1・2名」のような人気の組み合わせは繰り返し検索される。TTL 数十秒
  • 「売り切れ」の即時反映 — 検索に出したのに予約できないのは最悪の体験。売り切れになった瞬間だけは、キャッシュを能動的に無効化する
  • 施設マスタ・写真・レビューのキャッシュ — ほぼ変わらないので長い TTL
  • 料金計算結果のキャッシュ — 割引・税・手数料の計算は重い

⑥ Replication

  • 在庫の読み取りは、予約時だけプライマリから — レプリカラグ中の古い在庫で予約を通すと、オーバーブッキングになる
  • 検索用の読み取りはレプリカ / Elasticsearch でよい
  • マルチリージョン — 検索は各リージョンで完結、予約は在庫のホームリージョンへルーティングする。「在庫の正本は1箇所」を守るのが最も単純で安全
  • bookings は同期レプリケーション — 決済に繋がるので、失われてはいけない

⑦ Partitioning

  • 在庫のシャードキー = hotel_id — 1つの施設の全在庫が1シャードに集まるので、連泊のトランザクションが1シャード内で完結する
  • 日付でシャーディングしてはいけない — 連泊予約が複数シャードにまたがり、分散トランザクションが必要になる
  • 人気施設の Hot Partition — 大規模ホテルチェーンに集中する。ただし書き込みが 12 QPS なので、実務では問題になりにくい
  • 検索インデックス（Elasticsearch） — 地理 + 日付でシャーディング。検索が地理的に閉じているので、Uber と同じく分割しやすい

⑧ Queue

  • 在庫変更 → 検索インデックスの更新 — CDC / Outbox で RDB の変更を捕捉し、Elasticsearch に反映する。アプリから両方に書くのは Dual Write で、必ず不整合が起きる
  • Hold の期限切れ処理 — TTL 切れの Hold を在庫に戻す。戻し忘れると在庫が永久に減るので、監視とリカバリバッチが必須
  • 予約確定後の非同期処理 — 確認メール・施設への通知・OTA間の在庫同期・分析（Saga として実行）
  • 料金・在庫の一括更新 — 施設側からの「今後3ヶ月の料金を変更」は大量更新になるのでキュー経由
  • キャンセル処理 — 在庫の返却 + 返金計算 + 通知

⑨ CDN

  • 施設の写真 — Instagram と同じ構成。検索結果に数十枚のサムネイルが並ぶので、量が多い
  • 検索結果ページの部分キャッシュ — 「東京の人気ホテル一覧」のような、パーソナライズされていない部分はエッジでキャッシュ可能
  • 在庫・料金は CDN に乗せない — 変動するデータなので、古い情報を返すと事故になる
  • 静的アセット・地図タイル — CDN

⑩ Storage

  • 在庫・予約 → RDB（750GB + 予約データ）
  • 検索インデックス → Elasticsearch — 非正規化された「施設 + 在庫 + 料金 + 属性」
  • 写真 → オブジェクトストレージ + CDN
  • 検索ログ → データレイク — 「検索されたが予約されなかった」データが、価格分析の最も重要な入力になる
  • 予約データの長期保存 — 会計・法的要件で数年間

⑤ Cache

  • 地図クラスタのキャッシュ — 「東京全体をズームアウトした表示」は多くのユーザーが同じものを見る。事前計算して長めの TTL でキャッシュ
  • 物件詳細・写真・レビューのキャッシュ — 変更頻度が低い
  • 検索結果のキャッシュは効きにくい — 地図の範囲 × 日付 × 20種類のフィルタの組み合わせが膨大で、ヒット率が低い。「よく使われる組み合わせ」だけを対象にする
  • 価格計算のキャッシュ — 動的価格・割引・手数料の計算結果

⑥ Replication

  • 予約時の在庫読み取りはプライマリから — Booking と同じ理由

  • 写真の変換・モデレーション

  • 物件写真が大量 — 1物件あたり20〜50枚。検索結果に数十物件 × サムネイル。Instagram と同じ構成

・機会損失を避けられる
・ホストに「他にも2件リクエストがあります」と表示することで、承認を促せる
・在庫を押さえないので、承認タイムアウト処理が止まっても他の予約が成立する（障害耐性が高い）

「技術的な選択が、製品体験とビジネスに直結する」ことを示せる良い例です。
追撃3: 「『9/1〜9/4 が全部空いている物件』をどう検索しますか？」
「これが検索設計で最も難しい部分です」
物件×日付で35億レコードあるので、検索時に日付ごとに JOIN するのは不可能です。

解決は、Elasticsearch のドキュメントに「空室情報」を非正規化して持たせること:
① ビットマップ方式: 500日先までを500bit（63B）で表現し、AND 演算で「連続して空いているか」を判定する。コンパクトで高速
② レンジリスト方式: 「空き期間」を区間の配列で持つ（[{9/1-9/10}, {9/15-9/20}]）。Elasticsearch の date_range フィールドで扱える

課題は更新コスト——1泊予約が入るたびに、その物件のドキュメント全体を更新する必要があります。ただし予約は6 QPS しかないので、実務では問題になりません。
ホストの一括カレンダー更新（1ヶ月分）のほうが、実は書き込み負荷が大きいという点に触れられると、深く考えていると評価されます。

💡 10サービスから抽出できる、7つの共通原則

  1. 要件と概算を飛ばさない — 「読み書き比」「1件のサイズ」「最大値の分布」の3つで、設計の8割が決まる
  2. バイナリをAPIサーバに通さない — Presigned URL でクライアント⇔ストレージを直結（Instagram・YouTube・Drive・Dropbox で共通）
  3. 重い処理は 202 を返して非同期化 — 画像変換・トランスコード・fan-out・権限伝播
  4. 整合性は場面ごとに変える — 「検索は緩く、確保は厳密に」「付与は非同期、剥奪は同期」
  5. 実体ではなく参照を配る — Twitter のタイムライン（ID のみ）、Dropbox のブロックハッシュ、Drive の署名付きURL
  6. 2箇所に書かない（Dual Write を避ける） — Outbox / CDC で、正本から派生させる（Booking・Airbnb の検索インデックス）
  7. スケールで解けない問題を認識し、製品で受ける — フォロー数の上限・サージ価格・「著名人の投稿は遅れる」・オーバーブッキング時の業務プロセス
