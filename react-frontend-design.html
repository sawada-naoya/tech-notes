状態の分類・フォーム・サーバー境界

Reactを「使いこなせない」と感じる原因は、閃きの不足ではなく分類ができていないことである。この教材は3つの分類を扱う。
①状態の分類（新しい状態に出会ったとき、7つのバケツのどれか即断できるか）
②フォームの分類（error は useState ではなく RHF の内部stateである、と言えるか）
③実行場所の分類（このコードはサーバーで動くのか、ブラウザで動くのか）

主張1

「stateを増やすほどバグる」の正体はバケツ違い。特に「サーバデータをuseState」「派生値をuseState+useEffectで同期」の2つが全体の8割。

主張2

RHFの動的配列が難しいのはAPIの形をそのままフォーム型にしているから。Form型はUI階層に合わせると、useFieldArrayは3行で終わる。

主張3

Next.jsの核心は「どこで動くか」。'use client' でfetchして配るのはBFFではない（ブラウザで動くので、ただのコンテナ）。

視覚的なマップ版: react-state-map.html に「7バケツのマップ + 実画面例（予約管理画面のどこが何状態か）+ 裏側の配管（orval → React Query → UI）」がある。この教材はその解説編。

00 はじめに — Reactは分類の問題

結論。Reactを使いこなす = 新しい状態に出会うたびに「どのバケツか」を即断できること。これは才能や閃きの問題ではなく、分類の問題である。分類表を持っていれば、毎回同じ手順で判断できる。

図0-1 分類しないと8個のuseStateになり、分類すると7つの適切な道具になる。

00.5 全体地図 — 3つの境界

この教材が扱うのは3つの「境界」。境界を意識せずにコードを書くと、必ずどこかで詰まる。

図0-2 3つの境界。それぞれ独立した判断軸で、混ぜて考えると混乱する。

Part 1

状態の分類（7バケツ）

判断は2つの軸で決まる。軸1: 所有者は誰か（サーバー / URL / クライアント全体 / コンポーネント自身）、軸2: 保存すべきか、導出すべきか（store する / 他stateから計算する）。この2軸で7つのバケツに落ちる。

01 なぜ分類が必要か / 2つの軸

結論。state のバグは「値が間違っている」ではなく「置き場所が間違っている」ことから生まれる。だから対策は「注意深く同期する」ではなく「置き場所を変える」。

図1-1 2軸のマトリクス。#6と#7は「stateではない」ことが本質。

④ 判断手順（この順で問う）

  1. 他のstate/propsから計算できるか？ → Yes なら #6 派生（持たない）。ここで大半が消える
  2. 値が変わったとき、画面は変わるべきか？ → No なら #7 useRef
  3. この値の「正本」はサーバーにあるか？ → Yes なら #1 React Query（絶対にuseStateにしない）
  4. URLで共有・ブックマーク・リロードしたいか？ → Yes なら #2 URL
  5. 複数の離れたコンポーネントが必要とするか？ → Yes なら #3 グローバル
  6. フォームの入力・検証・送信状態か？ → Yes なら #5 RHF
  7. ここまで全部Noなら #4 useState

この順序が重要: 多くの人は7番（useState）から始めてしまう。1番（計算できるか）から問うと、そもそもstateが要らないケースが大量に見つかる。

各バケツの「具体例・ツール・特徴・失敗するとどうなるか」を確定させる。

7バケツ一覧表

上級（+1）: 複雑な遷移フローは状態機械（XState / 自作のreducer）。「A→B→Cしか遷移しない」を型で縛る。ただし状態が4つ以上あり、遷移に制約がある場合だけ。それ未満はuseReducerで十分。

⑨ 過剰になる境界 — 分類しすぎる害

  • 全部URLに入れる — モーダルの開閉やhoverまでURLに入れると、URLが汚れ、履歴が壊れる。「共有したいか / 戻るボタンで戻りたいか」がNoなら useState
  • 小さなアプリでZustandを入れる — propsで2階層渡すだけなら、Contextもストアも不要。「バケツリレーが3階層以上」になってから導入する
  • すべての計算を useMemo で包む — useMemo 自体にコスト（依存配列の比較）がある。重い計算（1000件のソート・フィルタ）だけに使う。a + b を包むのは無駄
  • 状態機械を最初から入れる — 状態が2〜3個なら useState で十分。XStateは学習コストが高い

06 非同期の基礎（Reactの外・JSの世界）

重要な認識: fetch部分はReactの機能ではない。JS/ブラウザの非同期処理であり、React Queryはその上に「キャッシュ＆状態化」を乗せているだけ。層を混同すると、どこを直せばいいか分からなくなる。

Part 2

フォーム設計（React Hook Form）

結論を先に: 動的配列管理が難しく感じる本当の理由は、useFieldArray のAPIが難しいからではない。フォームstateの形をUI階層に合わせず、サーバーレスポンス（API）の形のまま使っていることが原因である。RHFは素朴なAPIなので、メンタルモデルを構築すれば終わる。

07 RHFのメンタルモデル

最低限これだけ。RHFの状態は React state ではなく、RHF内部のstoreに存在する。だから「値が変わっても再レンダリングが起きない」（それが速い理由）。

図7-1 RHFの3要素。「errorをuseStateで持つ?」という問い自体が的外れである理由がここにある。

④ 最低限のAPI（7つ）

API役割再レンダリング注意
register入力をRHFの内部storeに紐付ける。文字列パスでアクセス起きないパスは 'items.0.name' のドット記法
handleSubmit検証 → 成功なら onValid / 失敗なら onInvalid を呼ぶerrors更新時のみイベントハンドラを返す高階関数

洞察1

errors / isValid は派生（#6）。だから自分でuseStateにしない。「errorをuseStateにする?」という問い自体が的外れ（保存する種類の状態ではない）。

洞察2

isSubmitting は React Query の isPending と同じ構造。「非同期の実行中フラグ」はフォームでもサーバ状態でも同形。一度理解すれば全部に効く。

実務での使い道

10 「動的配列が難しい」5つの原因

ここが Part 2 の核心。難しさの原因はRHFではなく、設計にある。5つの原因を順に潰す。

図10-1 原因1。「フォームstateはUIに寄せる。APIの形と一致させない」が解。

原因2〜5

原因症状解
原因2: reset を「更新」のために使っている reset({ ...watch(), ...変更 }) — dirty/touched/defaultValues が破壊される。watch() が購読を発生させ、無駄な再レンダリング連鎖が起きる 1フィールド更新は setValue(path, value, { shouldDirty: true })。reset は初期化専用
原因3: useFieldArray を中途半端に使う ある配列だけ useFieldArray、別の配列は watch + index で触る混在。keyも field.id と index が混在 配列を扱うなら全部 useFieldArray で統一する。例外を作らない
原因4: 派生状態をフォームstateにしていない（またはその逆） 「あるモードがONかOFFか」を別の useState で持ち、フォームの値と同期が崩れる 送信に必要ならフォームのフィールドとして持つ。不要なら useState でよい（ただしRHFの値と双方向同期はしない）
原因5: API型をそのままフォーム型に流用 as unknown as ApiType の double cast が出始める = 設計の敗北 API型 → フォーム型 → API型 の変換関数を1箇所に閉じ込める（ch11）

11 Form型はUI階層に合わせる / 変換層

結論。API型とフォーム型は別物として設計し、境界に変換関数（adapter）を置く。これは Part 1 のDTO分離、そして ddd-practice.html の「型を分ける」議論と全く同じ構造。

図11-1 変換層。フロントエンドでもバックエンドと同じ「型を分ける」原則が効く。

⑨ 過剰になる境界 — 変換層を作らない方がよい場合

  • API型とUI階層が完全に一致している — 単純な設定画面（3〜5項目のflat）なら、生成型をそのままフォーム型に使ってよい。変換関数が恒等関数になるなら書かない
  • 判定基準: 「描画ループの中で groupBy / map による整形が必要か」がYesなら変換層を作る。Noなら不要
  • TypeScriptの限界を受け入れる — Path<T> / FieldPath<T> の型推論は深いネストで重くなる、または効かなくなる。Generic component（<TextInput<Form>>）で型を伝播させると、エディタが一気に遅くなることがある。これはRHFの限界であり、型ヒントが効かない箇所は string literal で諦めるのも判断。「型がきつい」と「設計がきつい」は別物なので混同しない

Part 3

Server / Client 境界（Next.js）

Next.js理解の核心は「どこで動くか」。同じReactコードでも、サーバーで動くかブラウザで動くかで全くの別物になる。最も多い誤解: 'use client' のコンポーネントでfetchして配るのはBFFではない（ブラウザで動くので、ただのコンテナ）。この Part では実行場所・データの受け渡し・レンダリング方式・認証を、すべて「どこで動くか」の視点で整理する。

13 どこで動くか（RSC / CC / hydrate）

結論。Server Component は「サーバーで動くUIコンポーネント」であり、BFFではない。ただしBFFの責務（データ取得・整形・秘密鍵の隠蔽）を吸収している。データの流れは Server → Client（props経由）の一方通行だけ。

図13-1 データの流れ。「同じツリーの別実行環境」と理解すると、4つのルールが自然に導ける。

④ 基本の違い（対比表）

Server ComponentClient Component
実行場所サーバー（Node.js）ブラウザ（+ 初回はサーバーでもSSR）
宣言方法デフォルト（何も書かない）ファイル先頭に 'use client'
JSバンドル含まれない含まれる
state / effect使えない使える
イベントハンドラ（onClick）使えない使える
DB・秘密鍵アクセス直接できるできない（バンドルに含まれ漏洩する）

② 境界のルール — 一度クライアントに入ると戻れない

14 'use client' と 'use server'

最も混同される2つ。名前が対称なので「対になる概念」と思われるが、'use client' はコンポーネントの宣言、'use server' は関数の宣言で、レイヤーが違う。

図14-1 レイヤーが違う。'use client' は境界、'use server' は関数の実行場所。

③ 「APIすら書かない」の正確な意味

正確な意味

「クライアントから叩くREST APIを自前で書かなくていい」という意味。APIが存在しないわけではない — 内部的にはServer ActionがPOSTリクエストになっており、Next.jsがラップしている。

それでもAPIが必要な場合

外部クライアント（モバイルアプリ・パートナー企業・Webhook受信）向けのAPIは、別途 Route Handler で作る必要がある。Server Action はNext.jsアプリ専用。

Server Action の注意点

①認可を必ずサーバー側で書く（Clientから呼べる=誰でも呼べる）②引数はシリアライズ可能な値のみ ③エラーハンドリングが独特（throwするとNext.jsのエラー画面になるので、戻り値でエラーを返す設計が実務的）

Go バックエンドがある場合の判断

Server Action は「Next.jsサーバーからGoバックエンドを呼ぶ薄い層」になる。ビジネスロジックはGo側に置き、Server Actionは認証情報の付与と呼び出しだけを担う。ここにロジックを書き始めると、Go/TSの二重実装になる。

15 BFFとの比較 / Route Handler

結論。Server Component は BFF の責務を UI コンポーネントに内包した設計。BFFそのものではないが、Next.jsがBFFの役割を吸収したと考えるのが正確。明示的なBFFが必要なら Route Handler を使う。

④ BFF / Server Component / Route Handler の比較

BFF（独立サービス）Server ComponentRoute Handler
役割フロント専用のAPIサーバーUIとデータ取得が同一コンポーネント内Next.js内のサーバー側API
HTTPエンドポイント持つ持たない持つ（app/api/*/route.ts）
ブラウザから直接叩けるかはいいいえはい
通信REST / GraphQLなし（直接DB / 内部API）REST

再利用性複数クライアント（Web/モバイル）で共有可Next.jsアプリ専用Next.jsのデプロイに紐づく
使う場面モバイルアプリもある / チームが別初回表示のデータ取得（大半のケース）Webhook受信 / 外部公開API / 複数API集約

何が似ているか

①バックエンドのDBやAPIに直接アクセスして、フロントに必要なデータを整形する ②クライアントに不要な情報（秘密鍵・内部ロジック）を隠蔽する

何が違うか

BFFは「APIレイヤー」として独立するが、Server Componentは HTTPエンドポイントを持たない。ブラウザから Server Component を直接叩くことはできない。「APIサーバー」ではなく「サーバーで動くUIコンポーネント」。

最も多い誤解

'use client' のコンポーネントで fetch して子に配るのは BFF ではない。ブラウザで動くので、それは単なるコンテナコンポーネント。BFFはサーバー側の層である。

Route Handler が要る場面

①OTAからのWebhook受信（外部がURLを叩く）②モバイルアプリ向けAPI ③複数APIを1画面用に束ねる（over-fetch削減）④ファイルアップロードの中継 ⑤Client Component から呼びたい処理で、Server Actionだと不自然なもの（GET系・キャッシュを効かせたい）

17 レンダリング4方式とホスティング

結論。レンダリング方式とホスティング方法はセットで決まる。「全部SSR」はコストが高い。管理画面（CSR）は静的配信、公開ページ（SSR）は稼働サーバー、と分けるのが定石。

④ なぜサーバーレンダリングするのか（5つの理由）

1. 初期表示が速い

ブラウザは完成したHTMLを即表示できる。「JS読込 → fetch → 描画」の3ステップが消える。モバイル回線で差が大きい。

2. SEO

クローラがJSを実行しなくてもコンテンツが読める。Googleは実行するが、他のクローラ・SNSのOGP取得は実行しない。

3. 秘匿

APIキー・内部APIのURL・DBの接続情報をサーバーに留められる。CSRでは全てバンドルに含まれる（環境変数も）。

4. JS削減

Server Component のコードはバンドルに含まれない。重いライブラリ（markdownパーサ・日付処理・チャート）をサーバー側に置けば、クライアントに送らずに済む。

5. データに近い

サーバー → DB の往復はms単位。ブラウザ → API → DB の往復（waterfall）を削減できる。特に「A取得 → Aの結果でB取得」の連鎖で効く。

それでもCSRを選ぶ場面

管理画面: ログイン必須（SEO不要）・操作が主役・データが常に変わる・静的ホスティングで安く運用できる。SSRの利点がほぼ効かない。

最も多い誤解: React Query の cache は「グローバル」だが、それは1アプリ内で共有の意味であり全ユーザー共有ではない。cacheもDOMも、各ブラウザのメモリにある。

20 認証（NextAuth）の全体像

結論。NextAuth = session管理（ログイン状態）／ Goバックエンド = tokenの真偽判定（認可の本体）。本当の判定はバックエンドにある。フロントのsession有無はUXのためであり、バックが署名検証しない限り詐称可能。

図20-1 認証の全体像。「フロントのsessionはUX、バックの署名検証が本体」。

④ NextAuth の2戦略

観点JWT戦略（既定）DB戦略
session の保存場所暗号化cookieに丸ごとDBの sessions テーブル（cookieはIDだけ）
DBアクセス不要毎リクエスト
スケール容易（ステートレス）DBがボトルネックになりうる
即時ログアウト（強制失効）しづらい（exp まで有効）できる（行を削除する）
cookieサイズsession全体が入るので大きくなる（4KB上限に注意）小さい
適する場面一般的なWebアプリ「今すぐ全端末からログアウト」が要件にある場合

⑩ 認証のレビュー観点

  • 認可をフロントだけで判定していないか — 「管理者だけボタンを隠す」はUX。バックが検証していなければ意味がない
  • accessToken を localStorage に入れていないか（XSSで盗まれる。httpOnly cookie が正解）
  • 秘密鍵・APIトークンが NEXT_PUBLIC_ 接頭辞の環境変数に入っていないか（バンドルに含まれ、ブラウザから見える）
  • Server Action で認可チェックをしているか（Clientから呼べる = 誰でも呼べる）
  • cookie に Secure / SameSite が付いているか
  • token の exp が切れたときの挙動（自動リフレッシュ / 再ログイン誘導）が決まっているか

21 データ整形をどこに置くか

結論。意味はバック・見た目はフロント・集約はBFF。「全部バックエンドで整形」というバックエンド主義は罠で、APIがUI専用に肥大し、UIの小変更でバックのデプロイが必要になるほど結合が強まる。

図21-1 3種類の整形。「意味 / 見た目 / 集約」を混ぜないのが原則。

③ 「全部バックで整形」が罠になる理由

症状1: APIがUI専用に肥大する

GET /reservations-for-dashboard-list-v2 のようなエンドポイントが増える。1画面 = 1エンドポイントになり、再利用性がゼロになる。

症状2: UIの小変更でバックのデプロイが必要

「日付の形式を変えたい」「ラベルを『確定』から『予約確定』に変えたい」でバックエンドのPRが必要になる。これは結合が強すぎる状態。

症状3: 多言語化ができない

バックがラベル文言を返していると、i18nをバックに実装することになる。ユーザーのロケールはフロントが持つ情報。

逆の罠: 全部フロントで計算する

金額計算をフロントでやると、必ずバックの計算と食い違う（税の丸め・割引の適用順）。「お金・権限・状態判定」はバックの独占領域。

Part 3 のまとめ

  1. Server Component は「サーバーで動くUI」。BFFではないが、BFFの責務を吸収している
  2. 'use client' は境界、'use server' は関数。レイヤーが違う
  3. Server → Client は props のみ。逆方向は Server Action
  4. 再取得が必要なら hydration、不要なら props。両方使うと二重管理
  5. レンダリング方式は1画面ごとに決める。管理画面はCSR + 静的配信で十分
  6. cacheは各ブラウザのメモリ。invalidateは自分にしか効かない
  7. 認可の本体はバックエンド。フロントのsessionはUX
  8. 意味はバック・見た目はフロント・集約はBFF
