最初に言っておく厳しい話

シャーディングは「最後の手段」である。垂直スケール・Read Replica・キャッシュ・不要データの削除・アーカイブ、この4つを全部やり切ってから初めて検討する。早すぎるシャーディングは、必要のない複雑さを永久に背負う最も高価な設計ミス。面接でいきなり「シャードします」と言う候補者は、そこで減点される。正しい順序は「まず分割しない理由を説明し、次に分割せざるを得ない数字を示す」。

🧭 分割 vs 複製 — 2軸で世界を捉える

分散データベースの設計は、実質この2軸の組み合わせでできている。両方やるのが現実の答え。

図M-2 分割と複製は直交する。「シャーディングすれば可用性も上がる」は誤り。むしろ台数が増える分、どこか1台が壊れる確率は上がる。

01 Partition とは / なぜ必要か

パーティショニングとは 「1つのデータ集合を、互いに独立して処理できる部分集合に分けること」。目的はただ1つ、1台では物理的に無理な量を扱うため。読みのスケールではない（それは Replication の仕事）。書き込みと容量のスケールのためにやる。

🍽 レストランの例え。 客が増えて行列ができた。まずやるのは「厨房を広くする・シェフを増やす」＝ 垂直スケール。だがこれは店舗の面積で必ず頭打ちになる。
次にやるのが「2号店・3号店を出す」＝ パーティショニング。1号店は渋谷担当、2号店は新宿担当。客を分けたので、各店は独立して回せる。
代わりに失うもの: 「全店舗の今日の売上合計」を出すには全店に電話が要る。「渋谷の予約を新宿に振り替える」処理は2店舗にまたがる（＝ Cross Shard Transaction）。

① この技術は何を解決するために生まれたのか

解決するのは 「1台のマシンの物理限界」。具体的には次の4つが同時に壁になる。

  • 容量 — ディスクは有限。1台に 100TB は載らない（載っても復旧に何日もかかる）
  • 書き込みスループット — Leader は1台。ここが詰まったら Read Replica を100台足しても無意味
  • メモリ（ワーキングセット） — インデックスがメモリに乗らなくなった瞬間、レイテンシが2桁悪化する
  • 障害の影響範囲（Blast Radius） — 1台に全データがあると、その1台の障害が全ユーザー障害になる

パーティショニングの答え: 「データを分けて、それぞれ別のマシンに置く」。これで容量・書き込み・メモリが台数に比例して伸びる（線形スケール）。

図1-1 Scale Up と Scale Out。面接では「まず Scale Up、次に Read Replica、それでも書き込みが足りない時に Shard」と順序を言えることが評価される。

② この技術がないと何が問題になるのか

  • サービスが物理的に成長を止める — 「これ以上ユーザーを増やせません」という事態。Twitter が2008年に何度も落ちたのはこれ（Fail Whale）
  • インデックスがメモリから溢れて突然死する — テーブルが 200GB を越えた夜、B-Tree のランダム read がディスクに落ちてレイテンシが 1ms → 200ms に跳ねる。じわじわではなく崖のように落ちる
  • 運用作業が現実的でなくなる — 10TB のテーブルに ALTER TABLE は打てない。バックアップの復元に12時間かかる（＝ RTO 12時間）
  • 1台の障害 = 全ユーザーの障害 — Blast Radius が 100%
  • コストが爆発する — 最上位インスタンスの月額が、シャード8台の合計より高くなる

図1-2 分割を先送りした場合の典型的な劣化タイムライン。「まだ大丈夫」と「もう間に合わない」の間が驚くほど短いのがこの問題の意地悪なところ。

③ 基本概念 — 5つの用語だけ覚える

Partition（パーティション）

データの部分集合。論理的な単位。1つのノードが複数のパーティションを持つことも普通にある（これが後で効いてくる、14章）。

Shard（シャード）

Partition とほぼ同義。慣習として「別サーバに置かれた partition」を指すことが多い。MongoDB は shard、Cassandra は partition、Elasticsearch も shard、HBase は region、Bigtable は tablet、Spanner は split、Kafka は partition と呼ぶ。名前が違うだけで概念は同じ。

Shard Key / Partition Key

「このレコードはどのパーティションか」を決める入力になる列。ここが全て。10章で徹底的にやる。

Partition Function

キーからパーティション番号を出す関数。hash(key) % N や範囲テーブルの参照。5〜8章。

Router / Coordinator

クライアントのリクエストを正しいシャードに届ける層。図書館の総合案内。16章。

Shared-Nothing アーキテクチャ

各ノードがCPU・メモリ・ディスクを一切共有しない設計。パーティショニングの前提思想。共有するものが無いから台数を増やしても競合が起きない。

⑤ 実際のシステム構成でどう使われるのか — 成長段階ごとの標準構成

実務では、いきなり最終形にはならない。サービスの成長に合わせて段階的に移行する。各段階の「卒業条件」を数字で持っておくのが良いエンジニア。

Stage構成目安の規模次に進む条件（卒業条件）
0. 単体DB 1台〜数万 MAU / 数十GB可用性が要件になったら次へ

⑥ メリット

  • 書き込みが線形にスケールする — これが唯一無二の価値。他の手段では代替できない
  • 容量が線形にスケールする — ペタバイト級を扱える
  • Blast Radius が 1/N になる — Shard 3 が落ちても、影響は「ユーザーの 1/N」。全断にならない。これは可用性ではなく「障害の分割」という別の価値
  • 運用単位が小さくなる — 1シャード 200GB なら、バックアップ復元も index 再構築も現実的な時間で終わる
  • 安いハードで組める — 最上位機を買わずに済む。コモディティサーバの経済性が効く
  • 地理配置ができる — 「EU のユーザーのデータは EU のシャードに」＝ データレジデンシー要件（GDPR）を構造で満たせる

  • Uber — Schemaless（MySQL 上の append-only データストア）を UUID ハッシュで分割
  • Netflix — Cassandra を大量に運用。パーティションキー設計のガイドラインを社内標準化（26章）
  • Airbnb — モノリシック MySQL から、機能分割 → SmartStack/サービス分離 → シャーディング の順に段階移行（26章）
  • Booking.com — 予約データを地域・プロパティ軸で分割。読み取りは大量のレプリカ、書き込みは分割で捌く

⑨ Google レベルではどう設計されるか

Google の設計思想は一貫して 「パーティションはアプリから見えてはいけない。かつ、自動で分割・移動されるべき」。

  • Bigtable（2006） — 行キーの range で tablet に分割。tablet はサイズが閾値を超えると自動で split され、負荷に応じて tablet server 間を移動する。データそのものは GFS/Colossus 上にあるので、tablet の「移動」は実データのコピーを伴わない（メタデータの付け替えだけ）— これが極めて重要な設計
  • Spanner（2012） — Bigtable の tablet を split と呼び、各 split が独立した Paxos グループを持つ。つまり「パーティション = 合意の単位」。さらに INTERLEAVE IN PARENT で「親子行を物理的に同じ split に置く」ことを言語仕様で表現できる（＝ co-location をスキーマで宣言する）
  • Colossus / GFS — ストレージ層でチャンク分割。計算層のパーティションと、ストレージ層のパーティションを分離することで、計算ノードをステートレスに近づけた
  • 共通する思想 — ①パーティション数は人間が決めない ②パーティションは小さく大量に作る ③移動コストを下げる設計（ストレージ分離）を先にやる

面接での使い方: 「手動の固定シャードではなく、Bigtable のように range split を自動化し、ストレージを分離して移動コストを下げます」と言えると、一段上の議論になる。

⑩ システム設計面接ではどう問われるか

質問評価される答え方
「このシステム、DB はどうスケールしますか？」いきなり「シャードします」と言わない。「まず read/write 比を見ます。読みが支配的なら Replica とキャッシュ。書き込みが上限なら分割を検討します」
「いつシャーディングを決断しますか？」数字で答える。「単一 Primary の書き込み IOPS が上限の 60% に達した時点」「ワーキングセットが RAM の 80% を超えた時点」など先行指標を挙げる
「シャードすると可用性は上がりますか？」罠質問。「上がりません。むしろ台数が増えるので、どれか1台が壊れる確率は上がります。上がるのは障害の局所化（Blast Radius が 1/N）であって、可用性はレプリケーションで別途担保します」
「何を犠牲にしますか？」JOIN・トランザクション・グローバル一意性・集計・運用コスト、を即座に列挙できるか
「シャード数はいくつにしますか？」「最初から多め（例: 1024 の論理パーティション）にして、物理ノードにマッピングします。論理と物理を分離すれば、後でノードを増やしてもキーの再計算が不要です」（14章）

🚫 分割してはいけないケース

  • データが 500GB 以下 — ほぼ確実に垂直スケールで足りる。分割は純粋な自傷行為
  • 読み取りが遅いだけ — Read Replica とキャッシュの話であって、分割の話ではない
  • 良い Shard Key が見つからない — キーが決まらないなら分割してはいけない。無理に分割すると Cross Shard Query だらけになり、分割前より遅くなる
  • 強い整合性のトランザクションが業務の中心 — 会計・在庫引当など。単体DB＋垂直スケール、または Spanner/CockroachDB のような分散SQLを買う
  • チームが3人以下 — 運用が回らない。マネージドサービス（DynamoDB / Spanner / Vitess as a Service）に金で解決させる

02 分割 ≠ 複製 ≠ Sharding — 用語の整理

この分野は同じものを違う名前で呼び、違うものを同じ名前で呼ぶので混乱しやすい。面接で用語を混同すると一気に信頼を失うので、ここで固定する。

📮 郵便の例え。 Partition（分割）は「配達区域を分ける」こと。Replication（複製）は「同じ手紙のコピーを複数の局に置く」こと。Backup（バックアップ）は「先月の郵便物を倉庫に保管する」こと。
3つは全部別の目的。「分割してるからバックアップ要らない」は「配達区域を分けたから倉庫が要らない」と言っているのと同じ。

① この整理は何を解決するのか

解決するのは 「議論が噛み合わない」問題。実務では「シャーディングしよう」の一言が、人によって「テーブル分割」「機能分割」「DB分割」「Consistent Hash 導入」を意味する。設計会議の半分は用語のズレで消える。

図2-1 5つの概念の区別。「シャーディング」という単語が指すのは①だけ。②③は別の技法で、順序としては②③を先にやる。

③ 基本概念 — 3つの語彙の使い分け

用語厳密な意味実務での使われ方本書での扱い

重要な区別: 単一DB内のパーティショニング（MySQL/PostgreSQL の PARTITION）は、書き込みスケールにはならない。同じサーバの同じCPU・同じディスクを使うから。効くのは「古いパーティションを DROP で一括削除できる」「パーティションプルーニングでスキャン範囲を絞れる」という管理性とクエリ効率。ここを混同する人が非常に多い。

⑩ 面接での問われ方

Q. MySQL の PARTITION BY を使えばシャーディングは不要では？
不要にはなりません。PARTITION BY は同一サーバ内の話なので、CPU・メモリ・ディスク I/O は共有されたままです。書き込みスループットの上限は変わりません。
得られるのは ①DROP PARTITION による高速な期限切れ削除 ②パーティションプルーニングによるスキャン削減 ③index の分割による局所性向上、の3つです。
「時系列ログテーブルの保持期間管理」には極めて有効、「書き込みが1台の限界」には無力、と区別して答えるのが正解です。
Q. シャーディングとマイクロサービスの関係は？
直交しますが、実務では機能分割（Functional Partition）＝サービス分割の副産物としてDBが分かれることが多いです。
順序としては ①機能分割（縦に切る）→ ②各サービスの中で必要なものだけ水平分割（横に切る） が健全です。逆順（先に水平分割して後からサービス分割）は、シャードキーとサービス境界がズレて地獄を見ます。

03 Horizontal Partition（水平分割 / Sharding）

水平分割は 「同じ形の表を、行で切って別々のマシンに置く」こと。スケーラビリティの本命であり、以降の章はほぼ全部これの話。「同じスキーマ・違うデータ」と覚える。

📦 物流倉庫の例え。 全国の在庫を1つの倉庫に置いていたが、限界が来た。そこで関東倉庫・関西倉庫・九州倉庫を作り、注文の届け先で振り分ける。
3つの倉庫は全く同じ棚のレイアウト（＝同じスキーマ）を持つ。違うのは中身だけ。だから「関東倉庫の運用ノウハウ」はそのまま関西で使える。
注意: 「関東の商品を関西の注文に使う」ような跨ぎ処理は、途端に難しくなる（＝ Cross Shard）。

① この技術は何を解決するために生まれたのか

解決するのは 「1つのテーブルが1台に収まらない」問題。行数が問題なので、行で切るのが自然な解になる。

重要なのは「切った後も、各シャードは普通の DB として完結している」こと。1シャード内では index も JOIN もトランザクションも全部使える。水平分割は「小さい DB を N 個作る」技法だと理解すると、以降の話が全部繋がる。

② この技術がないと何が問題になるのか

  • B-Tree の深さが増える — 10億行の index は木が深くなり、1回のルックアップに必要なディスクアクセスが増える
  • VACUUM / OPTIMIZE が終わらない — PostgreSQL の autovacuum が巨大テーブルに追いつかず、テーブル膨張（bloat）が始まる
  • ロック競合が発生する — 同じテーブルへの書き込みが1箇所に集中し、行ロック・ページロックの待ちが増える
  • 1回のフルスキャンで全体が巻き添え — 誰かが打った雑な集計クエリが buffer pool を汚染し、全ユーザーが遅くなる（Noisy Neighbor）
  • バックアップ・リストアが実用時間で終わらない — 5TB の pg_restore は半日仕事

図3-1 水平分割の基本形。設計の勝負は「主要クエリの何%が Single-Shard で済むか」。ここが 95% を切ると運用が苦しくなる。

③ 基本概念 — 「論理シャード」と「物理シャード」の分離

水平分割で最も重要な設計テクニックがこれ。キーを直接サーバに割り当てず、間に「論理シャード（パーティション）」を挟む。

図3-2 論理/物理の分離。面接で最も加点される設計テクニック。Instagram（数千の論理シャード）、Vitess、Cassandra（vnode）、Kafka（partition数固定）すべてこの構造。

④ 内部でどのように動くのか — Go での最小実装

概念だけだと掴みにくいので、ルーティングの実体をコードで見る。やっていることは驚くほど単純。

// 論理シャード数は最初に決めて、二度と変えない const numLogicalShards = 1024 // 論理シャード → 物理DB の割り当て表（メタデータストアから読む） type ShardMap struct { mu sync.RWMutex // logicalShardID -> *sql.DB assign []*sql.DB } // ① キーから論理シャードを決める（この関数は絶対に変えてはいけない） func logicalShardOf(userID uint64) int { h := fnv.New64a() binary.Write(h, binary.BigEndian, userID) return int(h.Sum64() % numLogicalShards) // ← 1024 は不変 } // ② 論理シャード → 物理DB（この対応表は運用で書き換わる） func (m *ShardMap) dbFor(userID uint64) *sql.DB { m.mu.RLock() defer m.mu.RUnlock() return m.assign[logicalShardOf(userID)] } // ③ 単一シャードクエリ — 分割前とほぼ同じコードで済む func (r *PostRepo) ListByUser(ctx context.Context, userID uint64, limit int) ([]Post, error) { db := r.shards.dbFor(userID) // ← ここだけが分割対応 return queryPosts(ctx, db, `SELECT post_id, body, created_at FROM posts WHERE user_id = ? ORDER BY created_at DESC LIMIT ?`, userID, limit) } // ④ クロスシャードクエリ — 一気に複雑になる（17章で詳述） func (r *PostRepo) SearchAll(ctx context.Context, kw string, limit int) ([]Post, error) { // 全シャードに並列で投げて、集めて、再ソートして、切り詰める ctx, cancel := context.WithTimeout(ctx, 300*time.Millisecond) // ← タイムアウト必須 defer cancel() g, ctx := errgroup.WithContext(ctx) g.SetLimit(16) // ← 同時接続数を制限しないと自分でDBを殺す results := make([][]Post, len(r.physicalDBs)) for i, db := range r.physicalDBs { i, db := i, db g.Go(func() error { ps, err := queryPosts(ctx, db, `... WHERE body LIKE ? ORDER BY created_at DESC LIMIT ?`, kw, limit) if err != nil { return err } // ← 1台失敗で全部失敗にするか、部分結果を返すかは設計判断 results[i] = ps return nil }) } if err := g.Wait(); err != nil { return nil, err } return mergeTopN(results, limit), nil // アプリ側で ORDER BY / LIMIT をやり直す }

このコードから読み取るべきこと: ③と④の複雑さの差が、そのまま「Shard Key 設計の価値」。良いキーを選べば、コードの99%は③のまま。悪いキーを選ぶと、あらゆるクエリが④になる。

⑧ 実務での利用例

  • Instagram: PostgreSQL、user_id で分割。数千の論理シャード（PostgreSQL の schema として実装）を数十台の物理マシンに配置。移動は schema 単位。ID は Snowflake 風の「タイムスタンプ + シャードID + 連番」を DB の stored procedure で生成（＝ ID を見ればシャードが分かる）

⑨ Google レベルではどう設計されるか

  • 「シャード数」という概念をアプリから消す — Bigtable/Spanner ではユーザーはシャード数を指定しない。行キーの設計だけをする。分割は自動
  • パーティションは「小さく大量に」 — Spanner の split は数百MB〜数GB。大量にあることで、負荷分散の粒度が細かくなる
  • Co-location を言語仕様にする — INTERLEAVE IN PARENT で「Albums 行は、対応する Singers 行と物理的に同じ split に置く」と宣言できる。これにより 親子JOINが単一シャード内で完結する
  • 計算とストレージを分離 — tablet server は状態を持たず、実データは Colossus 上。だから「担当替え」が数秒で終わる（データコピー不要）
-- Spanner: 親子を物理的に同じ split に置く宣言（co-location をスキーマで表現する） CREATE TABLE Singers ( SingerId INT64 NOT NULL, Name STRING(MAX), ) PRIMARY KEY (SingerId); CREATE TABLE Albums ( SingerId INT64 NOT NULL, -- 親のキーを先頭に持つ AlbumId INT64 NOT NULL, Title STRING(MAX), ) PRIMARY KEY (SingerId, AlbumId), INTERLEAVE IN PARENT Singers ON DELETE CASCADE; -- ↑ これにより Singers(42) と その Albums 群は必ず同じ split に入る -- = 「あるアーティストとそのアルバム一覧」の JOIN が単一シャードで完結する -- = Cross Shard Transaction にもならない

⑩ システム設計面接ではどう問われるか

Q. シャード数はいくつにしますか？ 3台から始めるとして。
「物理3台、論理1024パーティション」と答える。
理由: 論理数を最初から多め・固定にしておけば、物理台数を 3 → 8 → 20 と変えてもキーの計算式が変わらないため、データ移動は「移す論理パーティションの分だけ」で済みます。
論理数の目安は「想定最大ノード数 × 10〜100」。1024 や 4096 がよく使われます。多すぎるとメタデータとコネクション数・ファイルハンドルが増えるので無限には増やせません。
Q. 分割したのに遅くなりました。何を疑いますか？
順に3つ。
1. Scatter-Gather になっていないか — Shard Key を含まないクエリが主要導線に混ざっている。スロークエリを Shard Key の有無で分類する。
2. Hot Partition が無いか — シャード別の QPS / CPU を並べる。1台だけ突出していないか（11章）。
3. Router の N+1 — アプリが1リクエストで複数シャードに順次アクセスしている（並列化していない）。
「シャード別のメトリクスを持っているか」を先に確認するのが実務家の答え方です。
Q. 1シャードが大きくなりすぎたらどうしますか？
3段階で答える。
短期: そのシャードを別の空いている物理マシンに単独で移す（論理/物理分離があれば設定変更だけ）。
中期: 論理シャードを split する（Auto Sharding, 15章）。ただし固定 hash 方式では split できないので、range 方式か、最初から論理数を多くしておく必要がある。
根本: 1つの論理シャードが大きすぎるのは Shard Key の失敗。tenant_id で分割していて、1テナントが全体の30%を占める場合など。その場合は複合キー (tenant_id, bucket) への変更を検討する（11章）。

04 Vertical Partition（垂直分割）と機能分割

垂直分割は 「列で切る」。行数は変わらず、テーブルの幅を狭くする。水平分割より圧倒的に簡単で、効果が出るのも早い。にもかかわらず飛ばされがちな、コスパ最強の手段。

📚 図書館の例え。 貸出カウンターに置く台帳には「本のタイトル・貸出中か・返却日」だけを書く。あらすじ・書評・表紙画像は別の分厚いファイルにして書庫に置く。
なぜか？ カウンターの台帳は1日に何千回も引かれる。薄ければ手元（＝メモリ）に置ける。あらすじは月に数回しか見られないので、取りに行く時間があってよい。
垂直分割の本質は「アクセス頻度が違うものを、同じ場所に置かない」。

① この技術は何を解決するために生まれたのか

解決するのは 「めったに使わない重い列が、よく使う軽い列の足を引っ張る」問題。

行指向DB（MySQL / PostgreSQL）は行を丸ごとページに詰めて読み書きする。1行に 2KB の bio が入っていると、SELECT id, name しか要らなくてもその 2KB がページごとメモリに載る。結果、1ページに入る行数が減り、同じデータ量を読むのに必要な I/O が増える。

図4-1 垂直分割の効果はページ密度で説明できる。「行を細くする」ことが「キャッシュヒット率を上げる」ことと直結している。

③ 基本概念 — 垂直分割の3レベル

レベルやること難易度効果
L1: 同一DB内でテーブル分割users / user_details に分ける。JOIN は使える低ページ密度改善・キャッシュ効率。まずこれ
L2: 別DBサーバへ分離重いテーブルを別インスタンスへ。JOIN 不可、アプリで2回引く中I/O とメモリを物理的に分離。Noisy Neighbor 解消
L3: 機能分割（Functional）テーブル群ごとに別DB。users DB / orders DB / events DB中〜高要件（整合性・可用性・保持期間）ごとに最適な構成を選べる。シャーディングの前にやるべき

図4-2 機能分割の判断基準。面接で「まず機能分割を検討します、理由はこの4軸です」と言えると、水平分割一辺倒の候補者と明確に差がつく。

⑥ メリット

  • 実装コストが極めて低い — テーブルを分けるだけ。ルーティング層もリバランスも要らない
  • 効果が即座に出る — キャッシュヒット率とページ密度が改善する
  • 戻せる — 水平分割と違い、失敗しても統合し直せる
  • シャーディングを不要にすることがある — 巨大な列を外に出しただけで、主テーブルが1台に収まるケースは非常に多い
  • セキュリティ境界を作れる — 個人情報だけ別DB・別暗号鍵にできる（GDPR / PCI-DSS の分離要件）

⑦ デメリット・トレードオフ

  • 全列が要る画面で必ず JOIN / 2回クエリになる — プロフィール詳細画面など。N+1 になりやすい
  • 別DBに分けると整合性が壊れる — users に INSERT 成功、user_details に失敗、という中途半端な状態がありうる。外部キー制約も効かない
  • 行数のスケールには効かない — 10億行問題は垂直分割では解決しない。あくまで「1行が太い」問題への対処
  • 分割の粒度を間違えると逆効果 — よく一緒に使う列を分けてしまうと、常に JOIN が発生して遅くなる

⑧ 実務での利用例

  • 典型的な垂直分割の対象: プロフィール本文 / 商品説明 HTML / JSON設定 / 画像バイナリ（そもそも S3 へ）/ 監査ログの詳細 / 検索用の巨大テキスト
  • Booking.com: 予約の「検索に使う軽い属性」と「予約詳細・ゲスト情報」を分離。検索は超高頻度、詳細は予約1件あたり数回しか読まれない
  • Airbnb: モノリシック MySQL から 機能分割 → サービス分離 の順で移行。水平分割ではなく機能分割を先にやったことが後の移行を楽にした
  • Netflix: 視聴履歴を「直近（Cassandra・小さく高頻度）」と「過去分（圧縮してまとめて保存）」に分離。時間軸での垂直分割とも言える

⑨ Google レベルではどう設計されるか

  • Bigtable の Column Family — 垂直分割が製品機能として組み込まれている。同じ行キーの下で、Column Family 単位に物理ファイルが分かれる。「頻繁に読む cf:meta」と「巨大な cf:content」を分け、読むときに必要な CF だけを I/O する
  • CF ごとに設定を変えられる — 保持世代数（GC ポリシー）、圧縮方式、ブロックキャッシュの有無を CF 単位で指定できる。「メタは常にキャッシュ、本文はキャッシュしない」が宣言できる
  • Capacitor / Colossus（BigQuery） — 完全な列指向。クエリで参照した列のファイルしか読まない。垂直分割を極限まで押し進めた形

この視点が有用な理由: 「垂直分割」を手作業のテーブル分割としてではなく、ストレージ層の設計パラメータとして捉えられる。面接で「Bigtable の Column Family は垂直分割の内蔵実装です」と言えると強い。

⑩ 面接での問われ方

Q. ユーザーテーブルが遅いです。まず何をしますか？
順序を示すのが答え方。
1. スロークエリと実行計画を見る（index が効いているか）
2. 1行の平均サイズと、クエリが実際に使う列を確認する → 使わない巨大列があれば垂直分割
3. buffer pool hit 率とワーキングセットサイズ → RAM を増やす（垂直スケール）
4. 読みが支配的なら Read Replica
5. ここまでやって書き込みが上限なら、初めて水平分割
いきなり 5 に飛ぶ人が多いので、1〜4 を先に言うだけで差がつきます。
Q. 垂直分割と水平分割、どちらを先にやりますか？
垂直（および機能分割）が先です。理由は3つ。
① 実装コストが1桁小さい ② 失敗しても戻せる ③ 垂直分割の結果、水平分割が不要になることがある（主テーブルが1台に収まる）。
逆順は危険です。先に水平分割してしまうと、後から機能分割しようとしたときに「シャードキーとサービス境界がズレている」問題に必ずぶつかります。

05 Range Partition（範囲分割）

キーの順序をそのまま使って「A〜F は Shard 0、G〜M は Shard 1」と切る方式。範囲検索が速い代わりに、偏りやすい。Bigtable・HBase・Spanner・MongoDB(range) が採用。

📚 図書館の例え。 五十音順に本を並べ、「あ〜き」は1階、「く〜と」は2階、「な〜ん」は3階に置く。
良いこと: 「さ行の本を全部見たい」と言われたら1階に行くだけでいい（＝範囲スキャンが速い）。
悪いこと: 日本の本は「さ行」「た行」が異常に多い。1階だけ棚が溢れ、3階はガラガラになる（＝偏り）。さらに新刊が「わ行」に集中する時期があれば、3階だけに人が殺到する（＝ Hot Partition）。

① この技術は何を解決するために生まれたのか

解決するのは 「範囲でまとめて取りたい」という要求。時系列データ、ID順のページング、辞書順のスキャン。ハッシュで散らすとこれが全部できなくなるから、順序を保つ分割が必要になる。

もう1つの動機は 分割の柔軟性。範囲の境界は後から自由に変えられる（＝ split / merge できる）。ハッシュ分割ではこれが難しい。Bigtable / Spanner が range を選んだ最大の理由がこれ。

② この技術がないと何が問題になるのか

  • 時系列クエリが全シャードスキャンになる — 「先週の全ログ」を出すのに、ハッシュ分割だと全シャードを舐める必要がある
  • ページングが破綻する — 「id 1000 以降を100件」が単一シャードで完結しない
  • 古いデータの一括削除ができない — range なら「2023年のパーティションを DROP」で一瞬。hash なら全シャードで DELETE（＝地獄）
  • 分割の粒度を後から変えられない — hash 分割は「特定の重い範囲だけ細かく割る」ができない

図5-1 Range Partition の全体像。範囲検索の速さと、偏りやすさは同じコインの裏表。順序を保つ＝似たキーが近くに集まる＝負荷も集まる。

④ 内部でどのように動くのか — 境界の探索と split

Range 分割の実装は「ソート済みの境界配列を二分探索する」だけ。その単純さの代わりに、境界表そのものが可変（＝メタデータ管理が必要）になる。

type RangeMap struct { // 境界は昇順ソート済み。boundaries[i] 以上 boundaries[i+1] 未満 が shards[i] の担当 boundaries []string // ["", "2026-03-01", "2026-06-01", "2026-08-01"] shards []*sql.DB } func (m *RangeMap) Lookup(key string) *sql.DB { // 二分探索: key 以下で最大の境界を持つシャード i := sort.Search(len(m.boundaries), func(i int) bool { return m.boundaries[i] > key }) - 1 return m.shards[i] } // 範囲クエリは「重なるシャードだけ」に絞れる — ここが Range の価値 func (m *RangeMap) LookupRange(lo, hi string) []*sql.DB { start := m.indexOf(lo) end := m.indexOf(hi) return m.shards[start : end+1] // ← hash 分割だと必ず全シャードになる } // split: 重いシャードの境界を1つ増やすだけで分割できる（14/15章） func (m *RangeMap) Split(shardIdx int, at string, newShard *sql.DB) { // 1. at より大きいデータを newShard へコピー（この間も読み書きは継続） // 2. コピー完了後、境界表を書き換える（アトミックに） m.boundaries = insertAt(m.boundaries, shardIdx+1, at) m.shards = insertAt(m.shards, shardIdx+1, newShard) // hash 分割ではこれができない — キーの計算式自体が変わってしまうため }

図5-2 自動 split のシーケンス。「計算とストレージを分離すると、パーティションの移動が安くなる」という設計原則が最もよく表れる場面。

  • 範囲クエリが効率的 — 対象シャードだけに絞れ、ディスク上も連続配置
  • ソート済みで返せる — シャード内で既に順序が保たれているので、マージソートが軽い
  • split / merge が自由 — 境界を動かすだけ。Auto Sharding が実装できるのは実質 range だけ
  • パーティション単位の一括削除 — TTL 管理が DROP 一発
  • 局所性を設計できる — 「同じテナントのデータを隣に置く」を明示的に指定できる

  • Hot Spot が起きやすい — 単調増加キー（時刻・連番ID）は常に最後のシャードに書き込みが集中。これが range の最大の弱点
  • 分布が事前に読めない — 「均等な境界」を最初に決めるのは不可能に近い。だから自動 split が必須になる
  • 境界表というメタデータが必要 — hash なら計算だけで済むところが、状態を持つコンポーネントになる（＝可用性の設計が要る）
  • リバランスが常時発生する — split が起きるたびにデータ移動・キャッシュ無効化・一時的なレイテンシ悪化がある

⑧ 実務での利用例

  • Google Bigtable / HBase — 行キーの range で tablet / region に分割。行キー設計が全てで、公式ドキュメントも「単調増加キーを先頭に置くな」を最重要警告として書いている
  • Google Spanner — split 単位。PRIMARY KEY の順序がそのまま物理配置になる
  • MongoDB（ranged sharding） — デフォルトは range。ObjectId をシャードキーにすると単調増加のため hot spot になるのは古典的な罠
  • CockroachDB / TiDB — range 分割 + 自動 split/merge。「Region」「Range」と呼ぶ
  • PostgreSQL 宣言的パーティショニング — PARTITION BY RANGE (created_at)。単一サーバ内だが、TTL管理には極めて有効

⑨ Google レベルではどう設計されるか — 行キー設計の作法

Bigtable の行キー設計は、Google 内部でも「最も重要かつ最も間違えられる設計判断」とされている。公式のアンチパターンと推奨パターンを押さえる。

行キー判定理由

⑩ 面接での問われ方

Q. 時系列データのストアを設計してください。パーティションキーは？
「timestamp」と答えると即失格。
正解は 複合キー (entity_id, timestamp)。
理由: timestamp 単独だと全書き込みが最新パーティションに集中します（Sequential Write Hotspot）。entity_id を先頭に置けば、書き込みは entity 数だけ分散し、かつ「あるデバイスの過去1時間」という主要クエリは単一パーティション内の範囲スキャンで済みます。
追加で言えると強い: 「entity_id のカーディナリティが低い場合（例: 10個のサービス名）は、さらに時間バケット (entity_id, hour_bucket, ts) を挟んで分散させます」（8章）。
Q. Range 分割で、あるシャードだけ大きくなりました。どうしますか？
1. split する — 中央値のキーで2つに割り、片方を別ノードへ。range 分割の最大の利点はこれが可能なこと。
2. なぜ大きくなったかを見る — ①データ量が多い（split で解決）②アクセスが集中している（split しても同じキーへのアクセスなら split では解決しない。11章の Hot Key 問題）。
3. 恒常的なら境界設計を見直す — 「特定テナントが全体の40%」なら、そのテナント専用シャードを切る（＝ Directory Partition 的な例外処理、7章）。
「split で直る問題か、キー設計の問題か」を切り分けて答えられるかが評価点です。

06 Hash Partition（ハッシュ分割）

キーをハッシュ関数に通して、その値でシャードを決める。分布が均等になる代わりに、順序が完全に失われる。Cassandra・DynamoDB・Kafka（デフォルト）・MongoDB(hashed) が採用。

📚 図書館の例え。 五十音順をやめて、ISBN の下2桁で置き場所を決める。00〜33 は1階、34〜66 は2階、67〜99 は3階。
良いこと: ISBN はほぼランダムなので、どの階も同じ冊数になる。「佐藤」が多かろうが関係ない。新刊も均等にバラける。
悪いこと: 「さ行の本を全部見たい」が不可能になる。3階全部を回って探すしかない。「あるシリーズの1巻から10巻まで」も、10冊が全部バラバラの階に散る。

① この技術は何を解決するために生まれたのか

解決するのは 「Range 分割の偏り」。ハッシュ関数は入力の分布に関係なく出力を一様分布に近づけるので、キーの分布がどんなに歪んでいても、パーティションのサイズはほぼ均等になる。

もう1つの動機は 「メタデータを持ちたくない」。境界表を持たなくても、hash(key) % N の計算だけでシャードが決まる。状態を持つコンポーネントが減る＝可用性が上がる。

③ 基本概念 — ハッシュ関数の選び方

言語組込みの hash——絶対に使わない。Go の map ハッシュも Java の String.hashCode() も、バージョンやプロセスごとに値が変わりうる。永続化する分割には致命的

絶対に守るべきルール: ハッシュ関数は一度決めたら永久に変えられない。変えた瞬間、既存の全データの位置が変わる。ライブラリのバージョンアップでハッシュ実装が変わるだけでも壊れるので、実装を自プロジェクトに固定（vendoring）するか、仕様が保証された関数を使う。

// ✕ やってはいけない: 言語組込み・実装非固定のハッシュを永続分割に使う func badShardOf(key string) int { h := maphash.String(seed, key) // seed がプロセスごとに変わる = 再起動で全部壊れる return int(h % numShards) } // ◎ 正しい: 仕様が固定されたハッシュ + 論理シャード固定 import "github.com/cespare/xxhash/v2" const numLogicalShards = 1024 // 永久に不変。これがマジックナンバーの正しい使い方 func shardOf(key string) uint64 { return xxhash.Sum64String(key) % numLogicalShards } // 複合キーの場合は「区切り文字を必ず入れる」— 入れないと衝突する func compositeShardOf(tenantID, userID string) uint64 { // ✕ tenantID + userID → ("ab","c") と ("a","bc") が同じキーになる return xxhash.Sum64String(tenantID + "\x00" + userID) % numLogicalShards } // 分布の検証は必ずやる（デプロイ前に本番相当のキーで測る） func verifyDistribution(keys []string) { counts := make([]int, numLogicalShards) for _, k := range keys { counts[shardOf(k)]++ } // 期待値からの偏差を見る。max/avg が 1.2 を超えるなら要調査 max, sum := 0, 0 for _, c := range counts { if c > max { max = c }; sum += c } avg := float64(sum) / float64(numLogicalShards) log.Printf("skew factor = %.2f (max=%d avg=%.1f)", float64(max)/avg, max, avg) // skew > 2.0 なら、キー自体に強い偏りがある（＝ Hot Key。11章へ） }

⑥ メリット

  • 分布が均等になる — キーの偏りをハッシュが吸収する。これが唯一にして最大の価値
  • 境界表（メタデータ）が不要 — 計算だけでシャードが決まる。クライアント側で計算でき、状態を持つコンポーネントが減る
  • 書き込みが自然に分散する — 単調増加キーでもハッシュを通せば散る。Sequential Hotspot が起きない
  • 実装が単純 — 数行で書ける。バグが入りにくい

⑦ デメリット・トレードオフ

  • 範囲クエリが全滅する — BETWEEN、ORDER BY id LIMIT、プレフィックス検索が全て Scatter-Gather に
  • ノード数の変更が高コスト — % N をそのまま使うと、N の変更でほぼ全データが動く（→ 13章 Consistent Hash / 3章 論理シャード固定で解決）
  • Hot Key は解決しない — 「1つのキーにアクセスが集中する」場合、ハッシュしても行き先は1つのシャードのまま。分布の均等化と、負荷の均等化は別問題（11章）
  • split ができない — 「重いパーティションだけ2つに割る」ができない。パーティション数は最初に決めるしかない
  • ハッシュ関数を変えられない — 永続的な制約になる

⑨ Google レベルではどう設計されるか

Google の主要ストレージ（Bigtable / Spanner）は hash 分割を採用していない。これは意図的な設計判断で、理由が学びになる。

  • 理由1: split/merge の自由度 — range なら「重いところだけ細かく割る」が可能。負荷は事前に予測できないので、後から適応できることを優先した
  • 理由2: 局所性を設計させたい — 関連データを隣に置くことで、JOIN やトランザクションを単一 split に閉じ込められる（INTERLEAVE）
  • 理由3: ハッシュは「アプリ側でできる」 — 均等分散が欲しければ、行キーの先頭に自分でハッシュを付ければよい（salt）。逆に、システムが強制的にハッシュしてしまうと、局所性を取り戻す手段が無くなる
  • 結論: 「システムは range で提供し、ハッシュはアプリが必要な時だけ使う」。柔軟性を上位レイヤに残す設計思想

対照的に DynamoDB / Cassandra は hash を強制する。これは「ユーザーに hotspot を作らせない」ための安全側に倒した設計。どちらが優れているかではなく、「誰に責任を持たせるか」の違い。

⑩ 面接での問われ方

Q. Hash と Range、どちらを選びますか？
「クエリパターン次第」ではなく、具体的に切り分けて答える。
Range を選ぶ: 範囲スキャンが主要導線（時系列・ページング・プレフィックス検索）、期間単位の一括削除が必要、split による動的な負荷適応が欲しい。
Hash を選ぶ: アクセスが点取得（key-value）中心、キーの分布が読めない・歪んでいる、単調増加キーしか無い、メタデータ層を持ちたくない。
実務の答えは「両方」: 複合キー (hash対象のpartition key, range対象のsort key) にすれば、パーティション間は均等分散、パーティション内は範囲スキャン可能になります（8章）。DynamoDB と Cassandra がまさにこの形です。
Q. hash(key) % N でシャーディングしています。ノードを3台から4台に増やすには？
この質問は「% N の罠を理解しているか」のテストです。
まず問題を指摘する: 「そのままだと約 3/4 のキーが別シャードに移動するので、実質的に全データ移行になります」
解決策を3つ挙げる:
① 論理シャードの固定 — % 1024 にして、1024個を物理ノードに割り当てる。ノード追加時は割り当て表だけ変える（推奨）
② Consistent Hashing — 移動を 1/N に抑える（13章）
③ 2の冪で倍々に増やす — 3→4 ではなく 4→8 にすれば、各シャードのちょうど半分だけが移動する（split しやすい）
①が最も実務的で、「最初からこうしておくべきだった」という話に持っていけると良いです。
Q. Hash 分割していれば Hot Partition は起きませんよね？
起きます。これは罠質問です。
ハッシュが均等にするのは「キーの個数の分布」であって、「キーごとのアクセス量」ではありません。
例: セレブのアカウント。user_id = 12345（フォロワー1億人）は1つのキーなので、ハッシュしても行き先は1つのパーティション。そこに全リクエストが集中します。
これを Celebrity Problem / Hot Key と呼び、ハッシュでは解決しません。対策はキーの分割（user_id#bucket）、キャッシュ、読み取り専用レプリカの追加など（11章で詳述）。

07 Directory Partition（ディレクトリ / ルックアップ分割）

計算でシャードを決めるのをやめて、「キー → シャード」の対応表を明示的に持つ方式。最も柔軟で、最も運用が重い。Vitess の lookup vindex、多くの自社実装がこれ。

📚 図書館の例え。 五十音でもISBNでもなく、「この本はC館の3番棚」と1冊ずつ書いた台帳を総合カウンターに置く。
良いこと: どの本をどこに置いてもいい。人気の本だけ広い館に移す、特定の作者だけ専用の館を用意する、全部できる。
悪いこと: 台帳が失われたら全ての本の場所が分からなくなる。台帳を引く時間も毎回かかる。台帳自体が巨大になったら、今度は台帳を分割する必要が出てくる。

① この技術は何を解決するために生まれたのか

解決するのは 「計算式による割り当てでは、個別の事情に対応できない」問題。

  • 「この大口顧客だけ専用シャードに置きたい」（SLA 差別化）
  • 「EU のユーザーは EU リージョンのシャードに置かねばならない」（GDPR / データレジデンシー）
  • 「このテナントだけ突出して重いので、単独で隔離したい」
  • 「シャードキー以外の列（メールアドレス等）からも引きたい」（＝ Secondary Index としてのルックアップ、12章）

ハッシュも範囲も「一律のルール」しか表現できない。ディレクトリは「例外」を表現できる。

  • 完全な柔軟性 — 任意のキーを任意のシャードに置ける。例外処理ができる唯一の方式

  • 異機種混在ができる — 大きいシャードと小さいシャードを混ぜられる（ハード世代の混在にも強い）

  • 単一障害点になる — ディレクトリが落ちたら全断。高可用構成が必須で、それ自体がコスト

  • 運用が人力になりがち — 「どのテナントをどこに置くか」を人間が判断し始めると、規模とともに破綻する

08 複合戦略（Hash + Range）— 実務の主流

Range と Hash は排他ではない。「パーティション間は Hash で均等に散らし、パーティション内は Range で順序を保つ」のが現代の標準解。DynamoDB・Cassandra・Bigtable の実務設計はほぼ全部これ。

📦 宅配便の例え。 全国の荷物を「送り先の郵便番号のハッシュ」で12の営業所に均等に振り分ける（＝ Hash でパーティション決定）。
各営業所の中では、荷物を「配達時刻の順」に並べておく（＝ Range で内部順序）。
結果: 営業所ごとの荷物量は均等になり、かつ各営業所内では「午前中の便だけ」をまとめて取り出せる。両方の良いとこ取り。

① この技術は何を解決するために生まれたのか

解決するのは 「均等分散と範囲スキャンを両立したい」という、単独方式では不可能な要求。キーを2つのパートに分けることで両立させる。

Q. チャットアプリのメッセージテーブルを DynamoDB で設計してください。

・「ユーザーの全メッセージ検索」は別アクセスパターンなので、GSI（Global Secondary Index）で PK=user_id を張るか、検索は Elasticsearch に逃がす（12章）
Q. Partition Key のカーディナリティが低いとき（例: status が5種類）はどうしますか？
そもそも status を Partition Key にしてはいけません、が第一声。
カーディナリティの低い列は、パーティション数の上限を決めてしまうため、5パーティションより先にスケールできなくなります。
対処:
① 高カーディナリティな列を PK にし、status は SK かフィルタ条件にする
② どうしても status で引きたいなら、PK = status#bucket（bucket は 0〜N のランダム） にして Write Sharding する。読むときは N 個のパーティションに並列クエリ
③ 件数が少ないなら Secondary Index（GSI）を張る
「カーディナリティ = 分散の上限」という理解を示せると評価されます。

10 Shard Key の選び方 — 設計の99%

この章が本書で最も重要。分割方式（hash/range）を間違えても後から直せることがあるが、Shard Key を間違えると全データ移行しか手がない。面接でも、ここを深く聞かれる。

📦 物流倉庫の例え。 商品を倉庫に分けるとき、何を基準にするか。
「商品カテゴリ」で分ける → 「食品」倉庫だけ常に忙しく、「楽器」倉庫はガラガラ（偏り）。
「入荷日」で分ける → 新しい荷物が全部「今日」の倉庫に入る（hotspot）。
「注文者の地域」で分ける → 1件の注文に必要な商品が全部同じ倉庫にある（＝ 1回のピッキングで済む）。これが良いキー。
基準は「1つの作業が1つの倉庫で完結するか」。作業単位を先に考え、それに合わせて分ける。

① Shard Key とは何を決めているのか

Shard Key が決めているのは、実は3つのこと。単に「どこに置くか」ではない。

  • データの配置 — どのシャードに行くか
  • クエリの効率 — どのクエリが Single-Shard で済み、どれが Scatter になるか
  • トランザクションの境界 — 同じシャードに置かれたデータ同士は、原子的に更新できる。これが最も見落とされる

つまり Shard Key の選択は、データモデルとトランザクション境界の設計そのもの。「後で決めればいい」ものではない。

⑨ Google レベルではどう設計されるか

  • 「キー設計 = スキーマ設計」として扱う — Spanner では PRIMARY KEY の列順がそのまま物理配置になるため、主キーの設計がパフォーマンス設計そのもの。レビューで最も時間をかける箇所
  • トランザクション境界から逆算する — 「原子的に更新したいデータの集合」を先に定義し、それが同じ split に入るようにキーを設計する（INTERLEAVE）。アクセスパターンより先に、整合性の単位を決める
  • キー分布の自動監視 — 本番で「key range ごとのQPS」を常時監視し、閾値を超えたら自動 split。人間が偏りを発見する設計にしない
  • 設計時のシミュレーション — 想定トラフィックをキー分布に流して、パーティションごとの負荷を事前計算する。「やってみて偏ったら直す」を許さない文化

Q. Twitter のようなサービスを設計してください。ツイートテーブルのシャードキーは？
この質問は「読みと書きでキーの最適解が違う」ことに気づけるかのテストです。
候補1: user_id — 「あるユーザーのツイート一覧」は Single-Shard。書き込みも分散。だが「フォロー中1000人のタイムライン」は1000シャードへの Scatter になる。
候補2: tweet_id（時刻順） — 全体の時系列は取りやすいが、書き込みが最新シャードに集中。
正解の方向性: 「ツイート本体は user_id（または tweet_id のハッシュ）で分割し、タイムラインは分割の問題として解かない。書き込み時に fan-out して、各ユーザーのタイムラインを別ストア（Redis）に事前構築する」
さらに: 「セレブ（フォロワー100万人以上）は fan-out すると書き込みが爆発するので、読み取り時に取りに行く hybrid 方式にします」（25章）
「分割で解けない問題は、データモデルを変えて解く」という視点を示せるかが評価点です。
Q. 選んだシャードキーが間違っていたと後で分かりました。どうしますか？
正直に「痛い」と言った上で、現実的な手順を答える。
1. 本当にキーの問題か切り分ける — Scatter が多いだけなら、Secondary Index や非正規化テーブルの追加で救えることがある（12章）。全移行は最後の手段。
2. 部分的な救済 — 問題のあるクエリ用に、別のキーで分割した「読み取り専用の複製テーブル」を作る（CQRS 的アプローチ）。
3. 全移行が必要なら — 二重書き込み → バックフィル → 読み取り切り替え → 旧削除、の4段階（19章）。数ヶ月かかる前提でプロジェクト化する。
「そもそも防ぐには」: 論理シャードを多めに取っておく、ID にシャード情報を埋め込む、キー変更を見越して抽象化層を1枚挟んでおく。
Q. 複数のアクセスパターンがあり、1つのキーでは満たせません。
これが現実で、正解は「1つに決めない」です。3つの選択肢を提示する。
① 非正規化して複製する — 同じデータを、異なるキーで分割した2つのテーブルに持つ。書き込みコストと整合性が犠牲（結果整合になる）。EC の「買い手視点」「売り手視点」がこれ。
② Global Secondary Index — DynamoDB GSI のように、別キーで分割されたインデックスを持つ（12章）。実質①の自動化。
③ 別のストアに逃がす — 検索は Elasticsearch、集計は BigQuery、リアルタイム集計は Redis。「1つのDBで全部やろうとしない」のが正解であることが多い。
重要な原則: 主要クエリ（QPS の80%）を Single-Shard にすることを優先し、残りは別の仕組みで救う。

11 Hot Partition と Celebrity Problem

分割された環境で最も頻繁に起きる障害。「均等に割ったはずなのに1台だけ落ちる」。ハッシュ分割でも起きるし、対策はキー設計・キャッシュ・複製の組み合わせになる。

🛣 道路の例え。 都心を分散させるために環状道路を8本作った。それでも「新宿駅前」の1区画だけは毎日渋滞する。道路を増やしても、目的地が1箇所なら意味がない。
Hot Partition の本質は「分散の失敗」ではなく「需要そのものが1点に集中している」こと。だから解決策は、道路を増やすことではなく、①目的地を分散させる（キーを割る）②手前で捌く（キャッシュ）③目的地の複製を作る（レプリカ）のどれか。

① 何が問題なのか — 2種類の Hot を区別する

種類定義原因ハッシュで直るか
Hot Partition（容量）特定パーティションのデータ量が突出キーの分布の偏り（大口テナント等）△ 一部改善する
Hot Partition（負荷）特定パーティションへの QPS が突出アクセスの偏り（人気コンテンツ）✕ 直らない
Hot Key（Celebrity）単一のキーにアクセスが集中セレブ、バズった投稿、人気商品✕ 原理的に直らない

最重要の理解: ハッシュ分割が均等にするのは「キーの個数」であって「キーごとのアクセス量」ではない。1つのキーに全リクエストが来るなら、そのキーの行き先は1つのパーティションしかない。

⑧ 実務での実例

  • Twitter のセレブ問題 — フォロワー数百万のアカウントの投稿を全フォロワーのタイムラインに fan-out すると、1投稿で数百万の書き込みが発生する。対策: セレブの投稿は fan-out せず、読み取り時にマージする hybrid 方式（25章）
  • Instagram のバズ投稿 — 特定投稿へのアクセス集中。CDN + 多層キャッシュで DB まで到達させない
  • EC のセール — 「iPhone の在庫」という1レコードに全リクエストが集中。在庫を N 個のバケットに分割して確保する（分散在庫）のが定番
  • DynamoDB のパーティション上限 — 1パーティション 3000 RCU / 1000 WCU の壁。超えると ProvisionedThroughputExceededException。「テーブル全体では余裕があるのにエラーになる」のが典型的な症状。Adaptive Capacity がある程度自動で吸収するが、単一キーの集中は救えない
  • Cassandra の wide partition — 1パーティションが数百MB になると、そのノードの GC が止まらなくなりノード全体が死ぬ。時間バケット必須（8章）

⑨ Google レベルではどう設計されるか

  • Bigtable の load balancing — tablet ごとの負荷を常時計測し、サイズだけでなく「アクセス頻度」でも split する。データ量が小さくても、アクセスが集中していれば分割される
  • Spanner の split by load — 同様に、負荷に基づいて split point を決める。「1行だけの split」も作られうる
  • それでも単一行の集中は解けない — 物理法則として、1つの行は1つの場所にしかない。Google の答えは「アプリ側でカウンタを分割する（sharded counter）」。Datastore/Firestore の公式ドキュメントに「sharded counter パターン」として明記されている
  • 検知の自動化 — 「hot key を人間が発見する」設計にしない。key range ごとの QPS メトリクスを自動収集し、閾値超えで自動対処 or アラート

⑩ 面接での問われ方

Q. ある芸能人が投稿しました。システムはどうなりますか？
Meta / Twitter 系の面接で頻出。「読み」と「書き」を分けて答える。
読み（投稿の閲覧）: 1つの post_id に数百万 QPS。→ ①CDN / エッジキャッシュ ②アプリ層のローカルキャッシュ（数秒 TTL）③Redis ④それでも溢れるならレプリカ増設。DB まで到達させないのが答え。
書き（いいね・コメント）: 1つのカウンタへの集中。→ ①Redis の atomic counter で受けて非同期 flush ②sharded counter（キーを100分割）③厳密な数値が不要なら近似カウント。
fan-out（フォロワーのタイムラインへの配信）: 数百万件の書き込み。→ セレブは fan-out しない。読み取り時にマージする（25章）。
締めの一言: 「Hot Key は分割では解けない問題なので、キャッシュ・非同期化・データモデルの変更で解きます」
Q. Hot Partition をどうやって検知しますか？
「平均CPUを見ます」は不正解。
1. シャード次元のメトリクス — シャードごとの QPS / CPU / レイテンシを個別に記録し、max と平均の比（skew factor）をアラート対象にする。「max/avg > 2.0 で警告」など。
2. Top-K キーの計測 — アクセス頻度上位のキーをサンプリングで記録（Count-Min Sketch / heavy hitter 検出）。DynamoDB なら CloudWatch Contributor Insights。
3. パーティションサイズの分布 — 容量の偏りは日次バッチで十分。max/median を追う。
4. エラーの内訳 — スロットリングエラーがどのキーで起きているかを記録。
重要な原則: 「平均は嘘をつく。分散システムでは常に max / p99 / 分布を見る」

12 Secondary Index — Local と Global

「Shard Key 以外の列で検索したい」は必ず来る要求。分割環境ではインデックスの置き方に2通りしかなく、それぞれ性質が正反対。DDIA でも1章を割いている重要トピックで、面接でも深掘りされる。

📚 図書館の例え。 本は著者名で分館に分けてある。だが「ミステリーの本を全部見たい」と言われた。
Local Index（各館が自館の目録を持つ）: 各分館に「うちのミステリー一覧」がある。全館に電話して集めれば答えは出るが、3館全部に聞く必要がある。
Global Index（全館共通のジャンル別目録を作る）: 「ミステリー → A館の3番, C館の7番, …」という中央目録を作る。1回引けば全部分かる。
代償: 新しい本を1冊入れるたびに、その館の目録と中央目録の両方を更新しなければならない。中央目録は別の場所にあるので、更新が2箇所に跨る＝分散トランザクション問題。

Q. user_id でシャードしています。email でログインさせるにはどうしますか？
頻出中の頻出。3つの選択肢を提示して選ぶのが良い答え方。
① lookup テーブル（推奨） — email → user_id の小さなテーブルを、email でシャードして持つ。ログイン時は2ホップ（email→user_id→データ）。Vitess の lookup vindex がまさにこれ。
② Global Index — DynamoDB GSI 相当。ただし結果整合なので、新規登録直後にログインできない可能性がある。
③ Scatter-Gather — 全シャードに問い合わせ。ログインは最も頻度が高い操作なので、これは論外。
追加で言うと強い: 「email の一意制約も lookup テーブルで担保します。email テーブルへの INSERT が成功したら user を作る、という順序にすれば、分散トランザクションなしで一意性を保証できます」
Q. Global Index を強整合にできますか？
技術的には可能ですが、コストが高いと答える。
データ更新と索引更新を同じトランザクションに含める必要があり、両者は別シャードにあるので2PC（分散トランザクション）になります。結果、書き込みのレイテンシが2〜5倍、可用性は「両方のシャードが生きていること」に依存する形に落ちます。
Spanner はこれを実際にやっています（TrueTime + Paxos + 2PC）。DynamoDB は「やらない」という判断をして、GSI を結果整合にしました。これは技術力の差ではなく、可用性とレイテンシを優先した設計判断です。
実務的な折衷案: 「Vitess の consistent lookup vindex のように、同じトランザクション内で lookup テーブルを更新する（同一 keyspace 内なら2PC不要にできる場合がある）」

13 Consistent Hashing（コンシステントハッシュ）

hash(key) % N の「N を変えると全部動く」問題を解く古典的アルゴリズム。ノードを1台追加したときの移動量を、全体の 1/N に抑える。面接で名前を出すだけでは足りず、仮想ノード（vnode）まで説明できて初めて合格。

📮 郵便の例え。 全国を12時間の時計盤に見立てて、配達員を盤上に配置する。荷物は宛先をハッシュして盤上の位置を決め、「そこから時計回りに最初に見つかった配達員」が担当する。
配達員が1人辞めたら、その人が担当していた荷物だけが次の配達員に引き継がれる。他の配達員の担当は一切変わらない。
これが「%N」との決定的な違い。%N だと1人辞めただけで全国の担当が総入れ替えになる。

① この技術は何を解決するために生まれたのか

解決するのは 「ノード数の変更で、ほぼ全データが移動してしまう」問題。1997年に MIT の Karger らが Web キャッシュの分散のために考案し、Amazon Dynamo（2007）で分散DBに応用されて有名になった。

方式N台 → N+1台 で移動するデータ量10→11台の実例
hash % N約 N/(N+1) ＝ ほぼ全部約 91% が移動
Consistent Hashing約 1/(N+1)約 9% が移動
論理シャード固定（3章）移す論理シャード分だけ約 9%（同等・より制御しやすい）

⑦ デメリット・トレードオフ / 代替手法

  • vnode 数が多いとメタデータが増える — 256 vnode × 1000ノード = 25.6万エントリ。gossip で共有すると重い（Cassandra が 256 → 16 にデフォルトを下げた理由）
  • それでも完全に均等ではない — 確率的な手法なので、±10% 程度の偏りは残る
  • 意図的な配置ができない — 「このキーはこのノードに」は表現できない（→ Directory 方式が必要）
  • 代替1: Rendezvous Hashing（HRW） — 各ノードについて hash(key, node) を計算し、最大値のノードを選ぶ。実装が単純でリング構造が不要。ノード数が少ないとき（〜数百）はこちらの方が良いことも多い
  • 代替2: Maglev Hashing（Google, 2016） — Google のロードバランサで使用。consistent hashing より均等（ほぼ完全均等）かつ高速なルックアップ。ルックアップテーブルを事前計算する方式
  • 代替3: 論理シャード固定（3章） — 実務ではこちらの方が多い。1024個の論理シャードを明示的にノードに割り当てる。制御しやすく、デバッグしやすい

⑩ 面接での問われ方

Q. Consistent Hashing を説明してください。
3段階で答える。
1. 解決する問題: 「hash % N はノード数変更で全データが移動します。Consistent Hashing は移動量を 1/N に抑えます」
2. 仕組み: 「ハッシュ空間を輪と見なし、ノードもキーも同じ空間にマップします。キーは時計回りに最初に見つかったノードが担当します。ノードを追加すると、そのノードの直前の範囲だけが移動します」
3. 仮想ノード（これを言えるかが分かれ目）: 「素朴な実装では担当範囲が不均等になり、さらに1台が落ちたときに負荷が隣の1台に集中してカスケード障害を起こします。そこで1物理ノードをリング上の100〜256箇所に配置します。これで均等性が上がり、障害時の負荷が全ノードに分散します」
締め: 「ただし実務では、論理シャードを固定数（例1024）作って割り当て表で管理する方が制御しやすいことも多いです」
Q. vnode 数はいくつにしますか？
トレードオフで答える。
多いほど: 均等性が上がる（偏差は 1/√vnode に比例）、障害時の負荷分散が滑らかになる。
少ないほど: メタデータが小さい、gossip の負荷が軽い、修復（repair）の並列度が制御しやすい。
実際の値: memcached の ketama は 160、Cassandra は歴史的に 256 でしたが、大規模クラスタで gossip とストリーミングが重くなったため、4.0 以降のデフォルトは 16 に下がりました。
目安: 「ノード数が少ない（〜20台）なら 128〜256、多い（100台〜）なら 8〜32」。ノード数 × vnode 数 が全体のパーティション数になるので、そこから逆算します。

14 Rebalancing（リバランス）の4方式

ノードを増やす・減らす・偏りを直す。「動いているシステムの下でデータを引っ越しさせる」のがリバランス。分散DBで最も事故が起きる操作であり、DDIA でも独立した節になっている。

📦 物流倉庫の例え。 倉庫を1棟増やした。既存3棟から新しい倉庫に在庫を移す必要がある。
制約: ①営業は止められない（移動中も注文が来る）②トラックの台数は限られている（帯域）③移動中の商品は「どちらの倉庫にあるか」が曖昧になる ④移動作業自体が既存倉庫の人手を奪う（＝ 本来の業務が遅くなる）。
リバランスの難しさは、アルゴリズムではなく「動きながらやること」にある。

① 何を解決するのか — リバランスが必要になる4つの場面

  • 容量が足りない — ノードを追加して、既存データの一部を移す
  • 負荷が偏った — Hot なシャードを空いているノードへ移す
  • ノードが故障した — 失われた担当を他ノードが引き継ぐ（＝ 緊急のリバランス）
  • ノードを縮退させたい — コスト削減。古い世代のハードを退役させる

リバランスに求められる4つの要件: ①移動後に負荷が均等になる ②移動中もサービスが継続する ③移動量は必要最小限 ④移動が本番トラフィックを圧迫しない（帯域・IOPS を食い潰さない）

図14-1 リバランス4方式。方式2（固定数パーティション）が、実務での第一選択。

図14-2 無停止パーティション移動。「コピー → 追いつき → 瞬間的な切り替え」は、リバランスでもリシャーディングでもDB移行でも共通の型。

⑦ リバランスの実務的な落とし穴

落とし穴何が起きるか対策

⑨ Google レベルではどう設計されるか

  • 「移動」からデータコピーを無くす — Bigtable/Spanner では実データが Colossus 上にあるため、tablet の移動は「担当の付け替え」だけで、実データは1バイトも動かない。移動が数秒で終わり、帯域も食わない。これが「計算とストレージの分離」の最大の実利
  • 負荷ベースの継続的な再配置 — 定期的に「各 tablet server の負荷」を評価し、常に少しずつ再配置し続ける。「たまに大きく動かす」ではなく「常時小さく動かす」
  • 移動のレート制御をシステムが持つ — 本番トラフィックを圧迫しないことを、システムレベルで保証する
  • 面接での使い方: 「リバランスのコストを下げる最も効果的な方法は、共有ストレージを使ってデータ移動そのものを不要にすることです。Aurora・Neon・Snowflake も同じ発想です」

⑩ 面接での問われ方

Q. ノードを1台追加します。何が起きますか？
段階を踏んで答える。
1. 割り当ての再計算: 「固定パーティション方式なら、既存ノードから均等にパーティションを引き取る割り当てを計算します。1024パーティション・3→4ノードなら、各ノードから86個ずつ、計256個を新ノードへ」
2. データ転送: 「1パーティションずつ、コピー→差分追いつき→切り替え、を繰り返します。帯域にレート制限をかけ、同時移動数を制限します」
3. 期間中の性能: 「移行中は既存ノードのディスクIOと帯域が消費されるので、レイテンシが多少悪化します。ピーク時間帯は移行を止めるスケジューリングをします」
4. リスク: 「古いルーティング情報を持つクライアントの誤書き込みを防ぐため、ノード側で担当検証をします」
締め: 「所要時間の見積もりも言えると良い: 10TB / 4 = 2.5TB を 200Mbps に絞って転送すると約28時間、といった具体性」

15 Auto Sharding（自動分割 / Split・Merge）

人間が「このパーティションを割る」と判断するのをやめ、システムが負荷とサイズを見て自動で分割・統合する。Bigtable・HBase・Spanner・CockroachDB・MongoDB が実装。Range 分割でのみ成立する。

🍽 レストランの例え。 1つのフロアが満席になったら、自動的に「2階を開ける」。逆に閑散期になったら2階を閉めて1階にまとめる。
判断基準は「席数（サイズ）」だけではない。「入り口に行列ができている（アクセス集中）」でも分けるべき。サイズと負荷の両方を見るのが、良い Auto Sharding。

⑩ 面接での問われ方

Q. 自動分割の仕組みを設計してください。
4つの要素で構成する。
1. 計測: パーティションごとに サイズ / QPS / CPU時間 を継続的に集計。ローカルで集計して定期的に中央に報告。
2. 判定: 「サイズ > 512MB」または「QPS が全体平均の3倍」で split 候補に。ヒステリシスを入れて、閾値付近での振動を防ぐ。
3. 分割点の決定: 行キーの分布から中央値を求める（サンプリングで近似）。負荷ベースなら「アクセスが集中しているキーの直前・直後」で切る。
4. 実行: 14章の「コピー→追いつき→切り替え」。同時実行数を制限し、レート制御をかける。
必ず言及すべき制約: 「単一キーへの集中は split では解決できません。分割点が作れないので。その場合はアプリ側でキーを分割する必要があります」

📮 郵便の例え。 荷物をどこに持ち込むか。

どれも正解で、どこにコストと複雑さを置くかの違い。

推奨: プロキシ層。理由は ①アプリコードが分割を知らなくて済むので、シャード構成の変更がアプリのデプロイを伴わない ②接続プーリングを集約できる（接続数の爆発を防ぐ）③クエリの書き換え・scatter-gather のマージを一箇所で実装できる。

17 Cross Shard Query（Scatter-Gather）

Shard Key を含まないクエリは、全シャードに投げて結果をマージするしかない。これが分割の最大の代償であり、実運用で最も多く遭遇する性能問題。

📚 図書館の例え。 「全分館の中で、今一番貸出されている本は？」と聞かれた。
3館全部に電話して、各館のトップ10を教えてもらい、手元で合計して並べ直す。
問題は3つ: ①1館でも電話が繋がらないと答えが出せない ②1館の返事が遅いと、全体がその館を待つ ③各館から10件ずつ取っても、正しい全体トップ10になるとは限らない（ページングの罠）。

① なぜこれが問題なのか — 3つの独立した問題

問題内容効いてくる規模
1. Tail Latency AmplificationN台に投げると「どれか1台が遅い確率」が N倍になる。全体のレイテンシは最も遅い1台で決まる10台〜で顕著
2. 可用性の掛け算各シャードの可用性 99.9% でも、10台全部必要なら 99.9%^10 = 99.0%。ダウンタイムが10倍全規模
3. リソースの N 倍消費1リクエストが N 個のクエリになる。QPS 1000 × 32シャード = 32,000 クエリ/秒QPS が高いとき

図17-1 Scatter-Gather とページングの罠。「OFFSET は分散環境で壊れる」は面接でも実務でも頻出の落とし穴。

④⑤ 対策 — Scatter を減らす / 速くする / 避ける

戦略手法効果
A. そもそも Scatter しない（最善）Shard Key をクエリに含めるよう API を設計する（「全体の新着」ではなく「自分がフォローしている人の新着」に変える）根本解決
非正規化: 別キーで分割した複製テーブルを持つ読みが Single-Shard に
集計結果を事前計算しておく（マテリアライズドビュー / ストリーム集計）クエリ時のコストがゼロに
B. Scatter するが範囲を絞るRange 分割なら、条件から関係するシャードだけに絞る（partition pruning）N → 数個に
Global Index（12章）で対象シャードを特定してから取りに行く2ホップだが Single-Shard に
Bloom Filter を各シャードのメタデータとして持ち、「存在しない」シャードを事前に除外不要な問い合わせを削減
C. Scatter を速くする並列実行（順次実行にしない。errgroup 等で）N倍 → 1倍の時間に
Hedged Request: p95 を超えたシャードに、別レプリカへ再送するtail latency を劇的に改善（Google の手法）
部分結果を許容: タイムアウトしたシャードを除いて返し、「一部欠けています」と示す可用性が上がる
各シャードに厳しいタイムアウトを設定（全体予算から逆算）暴走を防ぐ
D. 別系に逃がす検索は Elasticsearch、集計は BigQuery / ClickHouse、リアルタイム集計は Redis実務で最も多い解
// Scatter-Gather の実装で必ず入れるべき4つの防御 func (r *Repo) ScatterQuery(ctx context.Context, q Query) (Result, error) { // ① 全体のタイムアウト予算を決める（無いと1台の遅延で全部詰まる） ctx, cancel := context.WithTimeout(ctx, 200*time.Millisecond) defer cancel() g, ctx := errgroup.WithContext(ctx) // ② 同時実行数を制限（32シャード全部に一斉に投げるとコネクションが枯渇する） g.SetLimit(8) results := make([]partial, len(r.shards)) errs := make([]error, len(r.shards)) for i, sh := range r.shards { i, sh := i, sh g.Go(func() error { res, err := sh.Query(ctx, q) if err != nil { errs[i] = err return nil // ③ 1台の失敗で全体を失敗にしない（部分結果を返す設計） } results[i] = res return nil }) } _ = g.Wait() // ④ 部分結果の扱いを明示する。「全部揃った」と嘘をつかない failed := countNonNil(errs) if failed > len(r.shards)/2 { return Result{}, fmt.Errorf("too many shards failed: %d/%d", failed, len(r.shards)) } out := mergeTopN(results, q.Limit) out.Partial = failed > 0 // 呼び出し側が判断できるようにする out.FailedShards = failed return out, nil } // Hedged Request: 遅いシャードに対して、別レプリカへ二重に投げる（Google の "The Tail at Scale"） func (s *Shard) QueryHedged(ctx context.Context, q Query) (partial, error) { first := make(chan partial, 2) go func() { r, _ := s.replicas[0].Query(ctx, q); first <- r }() select { case r := <-first: return r, nil case <-time.After(s.p95): // p95 を超えたら諦めず、別レプリカにも投げる go func() { r, _ := s.replicas[1].Query(ctx, q); first <- r }() return <-first, nil // 先に返った方を採用 } // 代償: リクエスト量が数%増える。だが p99 は劇的に改善する }

⑨ Google レベルではどう設計されるか — "The Tail at Scale"

Jeff Dean と Luiz Barroso の論文（CACM 2013）が、この問題の教科書。Google 検索は1クエリを数千のシャードに fan-out するので、tail latency は死活問題。

手法内容
Hedged Requestsp95 を超えたら2つ目のレプリカにも送り、先に返った方を使う。追加負荷 5% で p99 が大幅改善
Tied Requests最初から2台に送り、片方が処理を始めたらもう片方をキャンセルする
Micro-partitionsノード数よりずっと多いパーティションを作り、遅いノードから素早く移す
Selective Replicationアクセスの多いパーティションのレプリカを増やす
Good Enough 応答締切までに返ってきた分だけで応答を作る。「完全な答えを遅く返す」より「99%の答えを速く返す」

最も重要な思想: 「レイテンシのばらつきは避けられない。だから、ばらつきに強いシステムを作る（latency tolerant）」。個々のノードを速くしようとするのではなく、遅いノードがあっても全体が速い設計にする。

⑩ 面接での問われ方

Q. 「全ユーザーの中で今月の売上トップ10」を出したい。どう実装しますか？
「全シャードに投げます」で終わると減点。
1. まず問い返す: 「リアルタイム性はどれくらい必要ですか？ 1時間前のデータで良いなら、話が全く変わります」
2. リアルタイム不要なら（大半のケース）: 「CDC でイベントを分析基盤（BigQuery / ClickHouse）に流し、定期バッチでランキングを事前計算して Redis に置きます。OLTP のDBで集計クエリを走らせないのが原則です」
3. 準リアルタイムなら: 「Kafka + ストリーム処理（Flink）で継続的に集計し、トップKを常に更新しておきます」
4. どうしても即時なら: 「Scatter-Gather しますが、各シャードにトップ10だけ返させ（N×10件）、タイムアウトを厳しく設定し、部分結果を許容します。ただしこれは最後の手段です」
評価点: 「分割されたDBで全体集計をやろうとしない」という判断ができるか。
Q. シャード数を増やしたらレイテンシが悪化しました。なぜですか？
Tail Latency Amplification です。
各シャードの p99 が 100ms（つまり1%の確率で100ms かかる）の場合:
・4シャードに fan-out すると「どれかが遅い確率」= 1-(0.99)^4 = 約4%
・32シャードなら 1-(0.99)^32 = 約27%
全体のレイテンシは最も遅いシャードで決まるので、シャードを増やすほど Scatter-Gather クエリは遅くなります。
対策: ①Scatter するクエリ自体を減らす（Shard Key を含める設計にする）②Hedged Request ③部分結果の許容 ④各シャードの p99 を下げる（GC チューニング等）。
重要な洞察: 「シャーディングは Single-Shard クエリには線形の効果があるが、Scatter-Gather クエリには逆効果。だから設計段階で『何%が Single-Shard か』を測るべき」

18 Cross Shard Transaction（分散トランザクション）

「A シャードから引いて、B シャードに足す」を原子的にやりたい。これが分割で失うものの中で最も痛い。選択肢は 2PC / Saga / そもそも跨がない設計の3つ。

🏦 銀行の例え。 東京支店の口座から大阪支店の口座に送金する。
問題: 東京で引き落としに成功した直後に、大阪の回線が切れた。お金が消えた状態になる。
2PC の解決: 「まず両支店に『準備できるか』を確認し、両方OKなら『実行せよ』と指示する」。ただし「実行せよ」を送った直後に本部が倒れると、両支店は指示待ちのまま口座を凍結し続ける（ブロッキング問題）。
Saga の解決: 「先に東京で引き落とし、大阪で失敗したら東京に払い戻す」。一時的に「お金が消えた状態」が外から見えるが、システムは止まらない。

図18-1 2PC のシーケンスとブロッキング問題。「2PC は原子性を保証するが、可用性を犠牲にする」——CAP の C を取って A を捨てている。

図18-2 Saga パターン。「原子性」を「補償可能性」に置き換えるという発想の転換。業務的に補償できない操作（メール送信済み等）には使えない。

⑨ Google レベルではどう設計されるか — Spanner

Spanner は「分散トランザクションは無理」という業界の常識を覆したシステム。どうやったかを理解すると、この分野の到達点が見える。

  • 各 split が Paxos グループを持つ — シャードのリーダーが単一障害点にならない。2PC の参加者が「1台のマシン」ではなく「合意グループ」になるので、参加者が落ちてもブロックしない
  • Coordinator も Paxos で複製 — 2PC の最大の弱点（Coordinator の SPOF）を潰した
  • TrueTime — GPS と原子時計で「時刻の不確実性の上限（通常 <7ms）」を保証する API。これによりグローバルに一貫したタイムスタンプ順序（external consistency）が実現できる
  • commit-wait — コミット時に不確実性幅ぶんだけ意図的に待つ。「待つことで、正しさを買う」という割り切り
  • それでもコストはある — 単一 split のトランザクションと比べて明確に遅い。だから Google 内部でも INTERLEAVE による co-location が推奨される。「分散トランザクションができる」ことと「使うべき」ことは別

⑩ 面接での問われ方

Q. ユーザーAからユーザーBへの送金を、シャード環境で実装してください。
典型的な分散トランザクション問題。3段階で答える。
1. まず跨がない方法を探す: 「送金元と送金先が同じシャードなら、通常のトランザクションで済みます。ユーザーではなく『口座グループ』でシャードできないかを検討します。ただし任意のユーザー間送金なら跨ぐのは避けられません」
2. 実務解 = Saga + 冪等性:
　① 送金元で「引き落とし」をローカルコミット（同時に Outbox に「入金指示」を書く）
　② 別プロセスが Outbox を読み、送金先に「入金」を実行（idempotency key 付きなのでリトライ安全）
　③ 入金が恒久的に失敗したら、補償として送金元に払い戻す
　④ 「送金中」という状態を明示的にモデル化し、ユーザーにも表示する
3. 厳密な原子性が必要なら: 「Spanner や CockroachDB のような分散SQLを使います。自前で 2PC を実装するのは、Coordinator の可用性設計が難しく推奨しません」
評価点: 「銀行の送金は実際には即時完結しない（結果整合）」という業務の現実に触れられると強い。
Q. 2PC を使わない理由を説明してください。
4点で答える。
1. ブロッキング問題: Coordinator が prepare 後・commit 前に落ちると、参加者はロックを持ったまま固まります（in-doubt）。復帰まで該当データが触れません。
2. 可用性の掛け算: 全参加者が生きている必要があるので、参加者が増えるほど成功率が下がります。
3. レイテンシ: 往復2回 + 各所での fsync。単一シャードの 3〜10倍。
4. ロック保持時間が長い: prepare から commit までロックを持つため、スループット全体が落ちる。
ただし正しく使える場合もある: 「Spanner のように Coordinator と参加者の両方を合意グループで複製すれば、ブロッキング問題は解消できます。実際 Spanner はそうしています。問題は 2PC そのものではなく、単一障害点のある Coordinatorです」——この整理ができると一段上に見えます。

19 Resharding — 無停止でシャード構成を変える

「分割していないDBを分割する」「シャードキーを変える」「シャード数を変える」。これらは全て、数ヶ月かかるプロジェクト。手順は決まっているので、それを知っているかどうかが実務力の差になる。

📦 物流倉庫の例え。 営業を止めずに、倉庫の配置を全面的に変える。
手順: ①新倉庫を建てる ②入荷を両方の倉庫に行う（二重書き込み） ③既存在庫を少しずつ移す（バックフィル）④棚卸しして両者が一致することを確認 ⑤出荷を新倉庫に切り替える ⑥しばらく旧倉庫も残しておく（戻せるように）⑦問題なければ旧倉庫を閉じる。
最も危険なのは ⑤ の瞬間ではなく、②〜④で「両者がズレていることに気づかないまま進む」こと。

図19-1 無停止 Resharding の6フェーズ。この手順は、DB移行・クラウド移行・スキーマ変更にもそのまま使える汎用パターン。

Q. DynamoDB でテーブル全体のキャパシティは余裕があるのに、スロットリングが起きます。なぜ？
Hot Partition です。
DynamoDB のキャパシティはパーティション単位に分配されるので、テーブル全体で 10,000 WCU あっても、10パーティションなら1つあたり 1,000 WCU です。特定のパーティションキーにアクセスが集中すると、そのパーティションの割り当てを超えてスロットリングします。

歴史的な補足: 「一時的にキャパシティを大きく上げるとパーティションが分割され、キャパシティを戻してもパーティション数は減らないため、1パーティションあたりの割り当てが減って以前より弱くなる、という問題が古くはありました」——これを言えると相当詳しいと見なされます。

⑩ 面接での問われ方

Q. MongoDB でシャードキーを選ぶとき、hashed と ranged のどちらにしますか？
まず「シャードキー候補が単調増加かどうか」を確認します。
ObjectId / timestamp / auto increment 系なら hashed — そのまま ranged にすると最後の chunk に書き込みが集中します。
範囲クエリが主要導線なら ranged — hashed にすると範囲クエリが全シャードに散ります。
4.4 以降の最適解は compound hashed shard key: {tenant_id: "hashed", created_at: 1} のように、先頭を hashed にして分散させ、後続で範囲を絞る。DynamoDB / Cassandra の PK+SK と同じ考え方です。
最重要の注意: 「MongoDB には Global Secondary Index が無いので、シャードキーを含まないクエリは必ず scatter-gather になります。だからシャードキーの選択は他のDBより重い判断です」

28 理解度チェック

答えを見る前に、自分の言葉で説明してみること。「説明できない = 理解していない」。全20問。

Q1 Partitioning と Replication の目的の違いを1文ずつで。
Partitioning: 容量と書き込みスループットをスケールさせるため（データを分ける）。
Replication: 可用性と読み取りスループットを上げるため（データを写す）。
両者は直交し、実務では両方使う。「シャードすれば可用性が上がる」は誤り。上がるのは障害の局所化（Blast Radius が 1/N）。
Q2 水平分割と垂直分割の違いは？ どちらを先にやるべき？
水平 = 行で切る（同じスキーマ・違うデータ）。垂直 = 列で切る（行数は同じ、テーブルを細くする）。
垂直（および機能分割）が先。理由: ①実装コストが1桁小さい ②失敗しても戻せる ③垂直分割の結果、水平分割が不要になることがある。
Q3 Range 分割と Hash 分割、それぞれの最大の弱点は？
Range: 単調増加キー（時刻・連番ID）で最新パーティションに書き込みが集中する（Sequential Write Hotspot）。分布が事前に読めず偏りやすい。
Hash: 範囲クエリが全滅する。% N のままだとノード数変更で全データが移動する。split ができない。
Q4 Shard Key の4条件は？
①高カーディナリティ（値の種類がパーティション数の上限になる）②分布が均等（種類が多くても偏っていたら無意味）③主要クエリがそのキーで絞れる（Single-Shard 率）④不変（変わるとレコードが引っ越す = 分散トランザクション）。
Q5 なぜ「論理シャード」と「物理ノード」を分離するのか？
直接 hash(key) % ノード数 にすると、ノード数を変えた瞬間にほぼ全データが移動するため。
論理層（例 1024 個）を固定すれば、キーの計算式は永久に変わらず、物理割り当て表だけを書き換えて増設できる。移動量も理論最小になる。Instagram・Vitess・Redis Cluster・Kafka すべてこの構造。
Q6 ハッシュ分割していれば Hot Partition は起きない。○か×か。
×。ハッシュが均等にするのは「キーの個数の分布」であって「キーごとのアクセス量」ではない。1つのキー（セレブのアカウント等）にアクセスが集中する場合、その行き先は1パーティションのままで、ハッシュでは解決しない（Celebrity Problem）。
Q7 Hot Key への対策を5つ挙げよ。
①キャッシュ（読み集中の第一手）②該当シャードのレプリカ増設（読みのみ）③キーを人工的に分割（write sharding: key#bucket、書き込み集中の本命）④隔離（専用シャードへ）⑤そもそもDBに書かない（Redis カウンタ + 非同期 flush）。
読み集中か書き込み集中かで対策が全く違う。
Q8 Consistent Hashing の仮想ノード（vnode）は何のためにあるか。2つ答えよ。
①担当範囲の均等化（ノードをリング上の複数箇所に配置することで、大数の法則により偏りが減る）
②障害時の負荷分散（1台が落ちたときに、その担当が「隣の1台」ではなく全ノードに分散して引き継がれる。カスケード障害を防ぐ）。
②の方が重要だが、忘れられがち。
Q9 Local Index と Global Index の違いと、それぞれの弱点は？
Local（document-partitioned）: 各シャードが自分の分だけ索引を持つ。書き込みはローカルで完結し常に整合。読みが全シャードへの scatter-gather になる。
Global（term-partitioned）: 索引を別のキーで分割。読みが Single-Shard で済む。書き込みが2箇所（データと索引）に跨るため、分散トランザクションか結果整合になる。
Q10 Scatter-Gather のレイテンシは何で決まるか。シャードを増やすとどうなるか。
最も遅いシャードで決まる。シャードを増やすと「どれかが遅い確率」が上がるため、Scatter-Gather クエリは台数に比例して遅くなる（Tail Latency Amplification）。
各シャードの p99 が 1% なら、32シャードでは 1-(0.99)^32 ≒ 27% の確率でどれかが遅い。
対策: Hedged Request、部分結果の許容、そもそも scatter しない設計。
Q11 なぜ分散環境で OFFSET ページングが壊れるのか。
「シャード0の201件目」は「全体の201件目」ではないため。正しくやるには各シャードから 0〜220件を取って再ソートする必要があり、ページが深くなるほど転送量が増える。
正解はカーソルページング（keyset pagination）: WHERE ts < :last_ts LIMIT 20。各シャードが常に20件だけ返せばよく、ページの深さに関係なく一定。
Q12 2PC の致命的な弱点は？
ブロッキング問題。Coordinator が prepare 後・commit 前に落ちると、参加者は「in-doubt」状態でロックを保持したまま固まる。勝手に commit も abort もできない（片方だけ実行される危険があるため）。
Coordinator が復帰するまで該当データが触れない。
解決策: Coordinator も合意グループ（Paxos/Raft）で複製する。Spanner がこれをやっている。
Q13 Saga パターンで失われるものは何か。
Isolation（分離性）。各ステップは独立したローカルトランザクションなので、途中の中途半端な状態が外から見える（「在庫は減ったが決済されていない」）。
また、補償は「なかったこと」にはできない（返金記録が残る）。業務的に補償できない操作（送信済みメール等）には使えない。
Q14 無停止 Resharding の手順を5段階で。
①準備（DBアクセスを1箇所に集約、フラグ導入、検証ツール作成）→ ②二重書き込み（新旧両方に書く、読みは旧）→ ③バックフィル（既存データを冪等にコピー）→ ④検証（全件比較 + シャドーリード。差分0まで進まない）→ ⑤カナリア切り替え（読みを 1%→100%）→ ⑥旧側の停止（1〜2週間の猶予を置く）。
Q15 Resharding で最も危険なタイミングはどこか。
切り替えの瞬間ではなく、二重書き込み〜検証の期間に差分が静かに溜まること。
新側への書き込み失敗を握り潰していたり、忘れられた書き込み経路（管理画面・バッチ）が旧DBを直接更新していたりすると、差分に気づかないまま切り替えてデータ不整合が発覚する。
だから差分メトリクスを常時可視化し、Phase 0 でDBアクセスを1箇所に集約するのが重要。
Q16 Cassandra で「1パーティションを100MB以内に」と言われる理由は？
パーティションが大きくなると、読み取り時に巨大な行群を展開することになり、ヒープを圧迫して GC が止まらなくなり、ノードごと死ぬ（wide partition 障害）。compaction も重くなる。
対策は時間バケット: PRIMARY KEY ((device_id, day), ts) のように、パーティションキーに時間の粒度を含めて、無限に育たないようにする。
Q17 Bigtable で tablet の移動が速い理由は？
実データが Colossus（共有分散ファイルシステム）上にあり、tablet server はキャッシュと書き込みバッファしか持たないため。
tablet の「移動」はメタデータの担当付け替えだけで、実データは1バイトも動かない。だから数秒で終わる。
ローカルディスク型なら同じ操作に数十GBの転送が必要で数十分かかる。「計算とストレージの分離」がリバランスを安くする。
Q18 Twitter のタイムラインを、なぜ「分割で解かない」のか。
「フォロー中1000人の最新ツイート」は、user_id で分割していると1000シャードへの scatter になり成立しないため。
Fan-out on Write（投稿時に全フォロワーのタイムラインリストに配る）でデータモデル側を変えて解く。読みは自分のリストを1回読むだけ（Single-Shard）。
セレブは fan-out すると書き込みが爆発するので、読み取り時にマージするハイブリッドにする。
Q19 分散環境の監視で「平均CPU」を見てはいけない理由は？
Hot Partition は平均に埋もれるため。8シャードのうち1台が CPU 100%、残り7台が 12% でも、平均は 23% で健全に見える。しかしユーザーの 1/8 は完全に障害中。
見るべきは max / avg（skew factor）、シャード別 p99、パーティションサイズの分布。メトリクスに shard ラベルを付けることが前提。
Q20 「シャーディングしましょう」と言う前に確認すべきことを5つ。
①垂直スケールの余地があるか（大半のサービスは最後までこれで足りる）②読みの問題なら Read Replica とキャッシュで済まないか ③垂直分割・機能分割で主テーブルを小さくできないか ④不要データのアーカイブ・削除で減らせないか ⑤良い Shard Key が存在するか（キーが決まらないなら分割してはいけない。全クエリが scatter になり、分割前より遅くなる）。

29 システム設計面接 10問 — 想定問答

Google / Meta / Amazon のシステム設計面接で、パーティショニングが論点になる典型問題。答えの丸暗記ではなく、「考える順序」を身につけることが目的。

🎯 全ての問題に共通する回答フレーム

  1. 要件を数字にする — MAU / QPS（読み・書き別）/ データ量 / 増加率 / レイテンシ要件 / 整合性要件
  2. 分割が本当に必要か検証する — 「書き込み QPS × レコードサイズ」が単一DBの限界を超えるか
  3. 主要クエリを列挙する — QPS 順に上位5つ。ここを飛ばす候補者が非常に多い
  4. Shard Key を選び、Single-Shard 率を示す
  5. 残る Scatter クエリをどう救うか述べる — 非正規化 / Global Index / 別ストア
  6. Hot Partition のリスクと対策を先回りして言う
  7. 運用（リバランス・監視・移行）に触れる
Q1 Twitter のようなサービスを設計してください。
数字: 5億 MAU、読み 30万 QPS、書き 5,000 QPS（read/write 比 60:1）。
ツイート本体: tweet_id（Snowflake ID = 時刻 + シャードID + 連番）で分割。ID からシャードが分かるので GET /tweet/{id} が Single-Shard。
ユーザーの投稿一覧: user_id でシャードした索引テーブルを別に持つ。
タイムライン: 分割では解かない。Fan-out on Write で各ユーザーのタイムラインリスト（Redis）を事前構築。セレブ（フォロワー10万超）は fan-out せず読み取り時にマージするハイブリッド。
Hot 対策: バズったツイートは CDN + 多層キャッシュ。いいね数は Redis の分散カウンタ。
検索: Elasticsearch に CDC で同期。OLTP で検索しない。
Q2 Instagram のようなサービスを設計してください。
Twitter とほぼ同じだが、メディアの扱いが論点になる。
写真・動画本体: DBに入れない。オブジェクトストレージ（S3）+ CDN。DBにはURLとメタデータだけ。
メタデータ: user_id で分割。「自分の投稿一覧」「プロフィール」が Single-Shard。
ID: Snowflake 風（時刻 + シャードID + 連番）。Instagram の実際の実装がこれ。
フィード: Fan-out on Write + セレブのハイブリッド。
ストーリーズ: 24時間で消えるので、時間バケットで分割して TTL / DROP PARTITION で一括削除できる設計にする（DELETE を打たない）。
Q3 YouTube のようなサービスを設計してください。
動画本体: オブジェクトストレージ + CDN + トランスコーディングパイプライン。分割の議論の対象外。
メタデータ: video_id で分割。「動画の詳細ページ」が Single-Shard。
チャンネルの動画一覧: channel_id でシャードした索引テーブル（非正規化）。
再生数: Hot Key の典型。バズった動画への書き込みが1キーに集中。→ Redis の分散カウンタで受け、定期的にまとめて DB に flush（近似値でよい）。
コメント: (video_id, comment_id) の複合キー。人気動画のコメントが wide partition にならないよう、時間バケットを併用。
推薦: 完全に別システム（オフライン計算 + 特徴量ストア）。
Q4 Uber のようなライドシェアを設計してください。
トリップ: trip_id（UUID のハッシュ）で分割。1トリップの全処理が1シャードで完結する。
ドライバーの現在位置: DBの分割問題ではない。更新頻度が極めて高い（数秒ごと × 数百万台）ので、Redis / インメモリ + 地理インデックス（H3 / S2 / Geohash）で別システム化する。
「近くのドライバー検索」: 地理セル（H3 の cell id）をキーにした空間分割。これは通常のシャーディングとは別の理論（空間分割）。
Hot 対策: 都心のセルは常に混む → セルの粒度を可変にする（都心は細かく、郊外は粗く）。
地域性: city_id でリージョンを分けると、地理的な局所性も得られる（レイテンシ・データレジデンシー）。
Q5 Slack のようなチャットを設計してください。
最も素直に分割できるケース。
Shard Key: team_id（ワークスペース）。1ワークスペースのデータが全部1シャードに閉じるので、ほぼ全クエリが Single-Shard。
方式: Directory Partition（7章）。テナント数は数十万で、ディレクトリのサイズが現実的。大口顧客を専用シャードに隔離でき、データレジデンシーにも対応できる。
メッセージ: (channel_id, message_id) の複合キー。「このチャンネルの最新50件」が単一パーティションの範囲クエリ。
巨大チャンネル対策: channel_id#yyyymm の時間バケットで、パーティションが無限に育つのを防ぐ。
検索: Elasticsearch（ワークスペース単位でインデックスを分ける）。
Q6 Netflix のような動画配信を設計してください。
視聴履歴 / 再生位置: (customer_id, ...) で分割（Cassandra）。「自分の続きから再生」が最頻出で、customer_id で完全に閉じる。
無限に育つ問題: 視聴履歴は増え続けるので、「直近（小・高頻度アクセス）」と「過去（圧縮してまとめる）」に分けて別テーブルにする（Netflix の実際の設計）。
作品カタログ: 小さいので分割不要。全ノードに複製する（reference table）。
動画配信: CDN（Open Connect）。DBの話ではない。
推薦: オフラインバッチ + 特徴量ストア。
ポイント: 「何を分割し、何を分割しないか」の切り分けを示すこと。
Q7 Airbnb / Booking.com のような予約サービスを設計してください。
最大の論点は「検索」と「予約の整合性」。
予約データ: property_id で分割。「この宿の空室確認と予約」が単一シャードのトランザクションで完結する。在庫の二重予約を防ぐには、これが決定的に重要。
ゲスト視点の「自分の予約一覧」: guest_id でシャードした索引テーブルを非正規化して持つ（結果整合を許容）。
検索（「東京・1万円以下・Wi-Fi あり」）: OLTP で絶対にやらない。Elasticsearch に CDC で同期。数秒の遅延を許容。
在庫の Hot 問題: 人気物件のセール時に1レコードへ集中 → 楽観ロック + リトライ、または在庫を分割して確保。
整合性: 予約と決済が別サービスなら Saga（18章）。
Q8 URL 短縮サービス（bit.ly）を設計してください。
分割の観点で最も単純な問題。
Shard Key: short_code のハッシュ。アクセスは完全に点取得（key → URL）なので、Hash 分割が最適。範囲クエリの需要がない。
採番: 中央のカウンタは単一障害点になるので、各ノードに ID 範囲を事前配布する（range allocation）か、Snowflake 風 ID を base62 エンコードする。
Hot Key: バズった短縮URL に全アクセスが集中する。→ CDN + 多層キャッシュで DB まで到達させない。read-heavy（100:1 以上）なのでキャッシュが極めて有効。
分析（クリック数）: 同期的にカウントアップしない。イベントを Kafka に流して非同期集計。
締め: 「この規模ならそもそも分割不要で、Redis + 1台のDBで足りる可能性が高いです」と言えると良い。
Q9 分散レートリミッターを設計してください。
Shard Key: api_key または user_id。1つのキーのカウンタが1ノードに乗ることで、アトミックなインクリメントがローカルで完結する。
なぜ分割が効くか: レートリミットは「キーごとに独立」なので、キー単位で分けると調整が一切要らない（shared-nothing の理想形）。
Hot Key: 巨大顧客の api_key に集中 → その顧客のリミットを N 分割し、各ノードに 1/N ずつ配る（local token bucket）。厳密さは落ちるが、実務では許容される。
実装: Redis Cluster（CRC16 % 16384 の hash slot）+ Lua スクリプトでアトミックに。
フォールバック: Redis が落ちたら fail-open か fail-close かを決めておく（通常は fail-open だが、決済APIなら fail-close）。
Q10 1日1兆行のメトリクス基盤を設計してください。
Shard Key: (metric_name + tags のハッシュ, time_bucket) の複合キー。
なぜ: ①先頭を系列（series）のハッシュにすることで書き込みが均等分散する ②time_bucket を含めることでパーティションが無限に育たない ③「ある系列の直近1時間」が単一パーティションの範囲スキャンになる。
やってはいけない: timestamp を先頭に置く（全書き込みが最新パーティションに集中）。
ダウンサンプリング: 生データは短期保持（7日）、集約データを長期保持。パーティション単位で DROP できる設計にする。
ストレージ: 列指向 + 時系列圧縮（Gorilla / delta-of-delta）。行指向DBは選ばない。
カーディナリティ爆発: tag の組み合わせが series 数を決めるので、高カーディナリティなタグ（user_id 等）を入れさせないガードを設ける。これが実運用で最大の問題。

30 実務でよくある障害例・設計ミス集

実際に起きる（そして繰り返される）失敗を、症状 → 原因 → 対処 の形でまとめる。面接で「障害対応の経験」を聞かれたときのネタにもなる。

🔥 障害例1: 「平均は健全なのに、一部ユーザーだけ全滅」

症状: 監視は全部緑。だがサポートに「サービスが使えない」という問い合わせが継続的に来る。
原因: Hot Partition。1シャードだけ CPU 100%。平均値の監視では検知できない。
対処: シャード別メトリクスを追加し、skew factor（max/avg）をアラート化。該当キーを特定して分割・キャッシュ・隔離。
予防: 設計段階から shard ラベル付きメトリクスを入れる（27章）。

🔥 障害例2: 「深夜に1ノードだけ死ぬ」

症状: Cassandra の1ノードが OOM で落ちる。再起動しても数時間後にまた落ちる。
原因: wide partition。特定のパーティションが数百MBに育ち、読み取り時にヒープを圧迫して GC が止まらなくなった。時間バケットを入れ忘れていた。
対処: 該当パーティションを特定（nodetool tablehistograms）。緊急対応はそのキーへのアクセスを遮断。恒久対応はスキーマ変更（時間バケット追加）＋データ移行。
予防: パーティションサイズの max を常時監視。設計時に「このパーティションは3年後に何MBになるか」を必ず計算する（8章）。

🔥 障害例3: 「リバランス中にクラスタ全体が遅くなり、さらにリバランスが走った」

症状: ノード追加後、全体のレイテンシが悪化。自動リバランスが次々と起動し、収束しない。
原因: データ転送が帯域とディスクIOを食い潰し、既存ノードが遅くなった。それを「ノード異常」と誤判定してさらにリバランスが発火（カスケード）。
対処: 即座にリバランスを停止。レート制限をかけて再開。
予防: ①転送のレート制限 ②同時移動数を1〜2に制限 ③自動リバランスの実行に人間の承認を挟む ④故障判定に長めのヒステリシス（14章）。

🔥 障害例4: 「移行後にデータが一部消えていた」

症状: シャード移行完了の1ヶ月後、「去年の注文が見えない」という報告。
原因: バックフィルが、二重書き込みで既に更新済みの行を古いスナップショットで上書きしていた。あるいは、月次バッチが旧DBに直接書いていて移行対象から漏れていた。
対処: 旧DBのバックアップから復旧（旧DBを消していたら復旧不能）。
予防: ①バックフィルは updated_at 比較付きの条件付き UPSERT ②全件比較バッチで差分0を確認してから切り替え ③旧DBは最低1ヶ月残す ④Phase 0 でDBアクセス経路を棚卸しする（19章）。

🔥 障害例5: 「新機能をリリースしたら全体が遅くなった」

症状: 管理画面に「全ユーザーの一覧」機能を追加したら、サービス全体のレイテンシが悪化。
原因: Shard Key を含まないクエリが追加され、全シャードへの scatter-gather が発生。しかも管理画面は1日数回しか使われないのに、1回の実行で全シャードのリソースを消費していた。
対処: 管理画面のクエリを分析系（レプリカ or 分析DB）に向ける。
予防: ①Single-Shard 率をメトリクス化し、下がったらアラート ②コードレビューで「このクエリは Shard Key を含むか」をチェック項目にする ③管理画面・バッチは最初から別経路にする。

🔥 障害例6: 「スケールアウトしたのに性能が上がらない」

症状: シャードを8台から16台に増やしたが、スループットがほとんど改善しない。むしろ一部のクエリは遅くなった。
原因: 主要クエリの多くが scatter-gather だった。scatter クエリはシャードを増やすほど遅くなる（Tail Latency Amplification）。
対処: クエリを Single-Shard 化する（Shard Key を API に含める / 非正規化テーブルを追加）。
予防: 分割前に Single-Shard 率を測る。95% を切るならシャードキーを見直す（10章・17章）。

📋 付録: チートシート（面接直前用）

面接の直前に、ここだけ読み返す。

1行で言うと

Partitioning は「書き込みと容量のスケールを買い、JOIN とトランザクションと全体集計を売る」取引。

最初に言うべきこと

「まず分割しない選択肢（垂直スケール・Replica・キャッシュ・機能分割）を検討します」。いきなり分割すると減点。

Shard Key の4条件

①高カーディナリティ ②分布が均等 ③主要クエリで指定される ④不変。

方式の選び方

範囲検索あり＋絞り込みキーあり → 複合（PK hash + SK range）／範囲のみ → Range／点取得のみ → Hash／個別配置が必要 → Directory。

必ず言うべき設計

論理シャード（1024個固定）と物理ノードの分離。これを言えると即座に評価が上がる。

Hot Partition の本質

ハッシュはキーの個数を均等にするがアクセス量は均等にしない。単一キー集中は分割では解けない。

Scatter-Gather の本質

レイテンシは最遅シャードで決まる。台数を増やすほど遅くなる。

Cross Shard TX の順序

①跨がない設計（co-location）→ ②Saga → ③2PC。2PC は最後の手段。

Resharding の型

準備 → 二重書き込み → バックフィル → 検証 → カナリア切替 → 旧停止。切替の瞬間より、差分が溜まる期間が危険。

監視で見るもの

平均ではなく max / avg（skew）とシャード別 p99。メトリクスには shard ラベルを付ける。

Google 的な視点

①パーティション数を人間が決めない ②小さく大量に作る ③計算とストレージを分離して移動コストを下げる。

締めの一言

「分割で解けない問題（タイムライン・検索・集計）は、データモデルか別のストアで解きます」。

🎓 この本の結論

Partitioning とは「1台では無理な量を扱うために、独立して処理できる単位に分ける技術」であり、その代償として「まとめて見る力」を失う取引である。

だから設計とは「どの単位で独立させるか」を決めることであり、それは Shard Key の選択に集約される。そして運用とは「偏りを検知し、動きながら直し続けること」（監視・リバランス・リシャーディング）である。

面接でも実務でも、「分割します」より「まだ分割しません、理由はこの数字です」と言える人のほうが信頼される。そして「このクエリは Single-Shard になりません、なのでこう救います」と先に言える人は、さらに信頼される。
