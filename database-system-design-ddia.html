01 Databaseとは — なぜファイルではダメなのか

「データを保存したい」だけならファイルで足りるはずです。ではなぜ世界中がDBを使うのか。この章はその理由を分解します。

🏛 例え: ファイル保存＝自分の部屋に本を積む。1人・100冊なら困らない。
DB＝図書館。10万冊・100人が同時に借りに来て、火事があっても蔵書リストが復元できる仕組み。
① 問題

予約管理をJSONファイルで保存する実装を考えます。次の5つが全部襲ってきます。

  • 探せない: 「8月の予約だけ」を出すのに全ファイルを読む必要がある
  • 壊れる: 書き込み途中で電源が落ちるとファイルが半分だけ書かれた状態になる
  • 混ざる: 2人が同時に書くと後の人が前の人の変更を消す
  • 矛盾する: 「予約は消えたのに支払いだけ残る」中途半端な状態ができる
  • 入らない: メモリに乗らないサイズになった瞬間に破綻する
② なぜ起きる？

ファイルは「バイト列を置く場所」以上の意味を持たないからです。ファイルシステムが提供するのは「名前で開く・読む・書く」だけで、探索・原子性・並行制御・整合性チェックは誰も面倒を見ません。全部アプリ側の自作になります。

図1-1: DBは「保存する箱」ではなく検索・耐障害・並行制御・整合性の詰め合わせ。

③ 解決策 — DBが提供する5つの機能

02 RDB と NoSQL — どちらを選ぶか

「NoSQLの方が新しくて速い」は誤解です。両者はアクセスパターンの違いで選び分けます。DDIA第2章の核心はここです。

📚 例え: RDB＝図書館（分類が決まった書架）。全部が同じ棚規格に従うので、横断検索も集計もできる。
NoSQL(ドキュメント)＝1人1箱のロッカー。箱の中身は自由。自分の箱を丸ごと出すのは最速だが、「全員の箱を横断して集計」は苦手。
① 問題

SNSのユーザープロフィールをRDBで作ると、こんな設計になります。

  • users / profiles / skills / jobs / educations … 1画面を出すのに5テーブルJOIN
  • ユーザーごとに項目がバラバラ（ある人は職歴5件、ある人は0件、ある人だけ特殊項目）
  • 「1人のプロフィール全体」を読むだけなのに、毎回JOINのコストを払う
② なぜ起きる？ — インピーダンスミスマッチ

アプリのメモリ上ではネストした1つのオブジェクトなのに、RDBは平らな表の集まりしか持てません。この形の不一致をインピーダンスミスマッチと呼びます。だから保存時にバラし（分解）、読み出し時にJOINで組み立て直す作業が毎回発生します。

図2-1: 同じデータの2つの持ち方。読みやすさ（Document）と横断性・更新安全性（RDB）のトレードオフ。

③ 解決策 — 4つのモデルと選択基準

ドキュメント1人1箱のロッカーMongoDB / Firestore / DynamoDB1件を丸ごと読む・スキーマ自由・水平分割横断JOIN・複雑集計・多対多
Key-Valueコインロッカーの番号札Redis / Memcachedキー1発の超高速取得・キャッシュキー以外での検索
グラフ人脈の相関図Neo4j「友達の友達」を何段も辿る単純な集計・大量書き込み

図2-2: 「新しいから」ではなくアクセスパターンで選ぶ。RDBが既定、外れるものだけ別のDBへ。

④ 内部処理 — スキーマの検証タイミングの違い

図2-3: スキーマレスは「検証しない」ではなく「検証責任がアプリと未来の自分に移る」だけ。

🚫 採用しない場合どうなるか（NoSQLを選ばず全部RDB / RDBを捨てて全部NoSQL）

全部RDBにした場合

  • ログ・イベントなど形が毎回違うデータで列が増え続け、NULLだらけの巨大テーブルになる
  • セッションやランキングをRDBに置くと書き込みが集中してDBが詰まる（Redisの領域）
  • アクセス数が伸びた時に水平分割の設計が後付けで地獄

全部NoSQLにした場合

  • 「売上を月別・店舗別に集計」の一言でアプリ側に集計コードを書く羽目になる
  • 同じ会社名を10万ドキュメントに埋め込み、社名変更で全件更新が必要になる
  • FKがないので親が消えても子が残る（孤児データ）
  • 「予約と支払いを同時に確定」が原子的にできない

実務の落とし所: 業務の中核はRDB、キャッシュ・セッション・ランキングはRedis、ログ・イベント・全文検索は別store。これが Polyglot Persistence（18章で実例）。

03 Table / Row / Column — 物理的には何なのか

「表」という説明で止まると、後の章（ページI/O・Index・MVCC）が全部わからなくなります。ディスク上でどう置かれているかまで降ります。

📦 例え: Table＝本棚、Row＝1冊の本、Column＝背表紙の項目（書名・著者・年）。
そしてPage＝段ボール1箱。倉庫から本を1冊取るときも、箱ごと運んでくるのがDBの世界です。
① 問題

「100万行のテーブルから1行だけ取る」のに数秒かかることがあります。行1つは200バイトなのに、なぜ?

② なぜ起きる？ — DBは行単位ではなくページ単位で読む

ディスクI/Oの最小単位がページ（PostgreSQL 8KB / MySQL InnoDB 16KB）だからです。1行だけ欲しくても、その行が入っているページを丸ごとメモリに読みます。
つまりコスト = 何ページ読むか。1行200バイトなら1ページに約40行入るので、100万行 ≒ 25,000ページ。全部読めば25,000回のI/Oです。

図3-1: Table→Page→Row→Column の入れ子。以降の章の計算は全部「ページ数」で行う。

③ 解決策 — 行指向と列指向の選択

「1行を丸ごと使う（OLTP）」か「1列を集計する（OLAP）」かで、ページへの詰め方自体を変えます。

図3-2: 行指向 vs 列指向。「1件を読む」か「1列を集計する」かで物理配置が変わる。

④ 内部処理 — 型・制約がどこで効くか
仕組み役割図書館の例え無いとどうなるか
NOT NULL値の欠落を禁止書名のない本を置かせないNULL判定漏れでアプリが落ちる
UNIQUE重複禁止（裏でIndexが作られる）同じ整理番号を2冊に付けない同じメールで二重登録
CHECK値の範囲を制限出版年が未来の本を弾くマイナスの金額が保存される
FOREIGN KEY参照先の存在を保証存在しない著者を指させない親が消えて孤児データが残る
DEFAULT省略時の値受入日は今日で埋めるアプリごとに初期値がズレる

重要: これらはDBサーバー側で強制されます。アプリにバグがあっても、バッチが直接叩いても、手作業のSQLでも守られる。「アプリでバリデーションしているから不要」は誤り——入口はアプリだけではないからです。

⑤ トレードオフ
  • 制約を厳しくする → データは堅牢。だが仕様変更時のマイグレーションが重い（NOT NULL列の追加は既存行の埋め方を考える必要あり）
  • 列を増やす → 1行が太る → 1ページに入る行数が減る → 同じ件数でも読むページが増えて遅くなる
  • 正規化する → 更新は安全、読みはJOINが増える（13章の主題）
  • 可変長列（TEXT/JSON）を多用 → 行がページに収まらず外部領域（TOAST）に追い出され、読み取りが余分なI/Oになる
🚫 制約を使わない場合どうなるか

図3-3: 制約はDBの仕事。アプリの検証は「親切」、DBの制約は「保証」。

04 Primary Key — 行を一意に指す住所

PKは「IDを付けるだけ」ではありません。InnoDBではPKの選び方がテーブル全体の物理配置を決めます。ここを知らないと6章で詰まります。

🏷 例え: PK＝本の整理番号（背ラベル）。図書館では整理番号順に本を並べるので、番号の付け方が棚の並び順そのものになる。ランダムな番号を付けると、新しい本を入れるたびに棚の途中に割り込む作業が発生します。
① 問題
  • 「同じ予約が2件登録された」——どの行が正しいか分からない
  • 「PKをUUIDにしたら、行数が増えるにつれINSERTが目に見えて遅くなった」
  • 「複数列をPKにしたら、他のテーブルからの参照が全部太った」
② なぜ起きる？ — PKは「並び順」でもある

MySQL InnoDB ではPKのB+Treeの葉に行本体が入っています（Clustered Index / 6章）。つまりPK順にデータが物理的に並ぶ。
連番なら常に「棚の一番右端」に追加するだけ（追記）ですが、UUID v4 のようなランダム値だと毎回棚の真ん中に割り込むため、ページ分割とランダムI/Oが多発します。

図4-1: PKの選び方が書き込み性能を左右する。面接で「UUIDをPKにしますか?」は定番の踏み込み質問。

③ 解決策 — PK設計の指針
方式内容◎△使い所
代理キー（連番）BIGSERIAL / AUTO_INCREMENT挿入が最速・8バイトで細い・不変採番がDB依存・件数が推測可能既定解
UUID v7 / ULID時刻順ソート可能なランダムID分散採番できて挿入も速い16バイト（連番の2倍）分散・マイクロサービス
UUID v4完全ランダム衝突なし・どこでも生成可挿入が遅い・断片化小規模テーブルのみ
自然キーメールアドレス・注文番号など追加の列が不要値が変わると全参照を更新ほぼ非推奨（UNIQUE制約で十分）
複合キー(order_id, line_no)中間テーブルで自然参照側が太る・ORMが辛い多対多の中間表

3原則: ①不変であること（変わる値をPKにしない） ②細いこと（全Secondary Indexに複製されるので） ③単調増加が望ましいこと（挿入性能）。

④ 内部処理 — PKが太るとSecondary Indexも太る（InnoDB）

図4-2: 「PKは細く」の理由。UUIDを使うなら文字列ではなくバイナリ16Bで持つ（BINARY(16) / uuid型）。

⑤ トレードオフ

🚫 PKを付けない場合どうなるか
  • 1行を特定できない → 重複行の片方だけを消せない（DELETE が両方消える）
  • レプリケーションが壊れる → 行ベースレプリケーションはPKで対象行を特定するため、PKなしテーブルはレプリカ側で全表走査になり遅延が爆発する（MySQLの有名な事故）
  • ORMが機能しない → 更新・削除の対象を指定できない
  • InnoDBは内部で隠しPKを勝手に作る → 自分では使えない6バイトのIDが付くだけで、上記の問題は解決しない

05 B+Tree — 索引の本体と探索の全手順

この章が本書の心臓部です。Indexとは何か＝B+Treeとは何か。構造・探索・挿入・なぜ他の構造ではないのかを全部図で追います。

📇 例え: B+Tree＝図書館の蔵書目録（カード式）。
「あ〜か行はこの引き出し、か〜さ行はこの引き出し」と大まかな仕切りから入り、引き出しの中で細かい仕切り、最後のカードに「棚3段目」と書いてある。しかも最後のカードは五十音順に並んで隣と繋がっているので、「か行の本を全部」も端から辿れる。
① 問題

100万行のテーブルで WHERE id = 520。Indexがなければ25,000ページを全部読みます。1件のために200MB読むのは無駄すぎる。

では単純な二分探索木でどうか? → 高さが約20段になります。ディスクは1回のアクセスに数百μs〜数msかかるので、20回のランダムI/Oは致命的です。

② なぜ起きる？ — ディスクは「1回でページ丸ごと」読める

メモリ上のアルゴリズム（二分探索木）は比較回数を最小化する設計です。しかしディスクの世界ではアクセス回数がコストで、しかも1回で8〜16KB（＝数百キー分）読めてしまう。
だったら1ノードをページいっぱいまで太らせて、木を極端に浅くするのが正解。これがB+Treeの設計思想です。

図5-1: 同じ「木」でも1ノードの太さが違うだけで高さが20→3になる。

行数木の高さ（fanout=300）点検索のページ読み例え

2,700万33 + 行1回棚 → 引き出し → カード

ここが log の威力: 行数が1万倍になっても、読むページは1〜2枚しか増えません。逆に言えば行数が少ないと差が出ません（8章の伏線）。

06 Clustered Index と Secondary Index

「Indexを貼った」と言うとき、実は2種類あります。この違いを知らないと、MySQLとPostgreSQLの挙動差も、なぜ2次Indexが遅いのかも説明できません。

🏷 例え: Clustered Index＝本棚そのものが整理番号順に並んでいる状態。目録を引かなくても番号順に歩ける。棚は1つの順序しか持てないので1テーブルに1つだけ。
Secondary Index＝「著者名 → 整理番号」の別の目録。著者で引いたら整理番号が分かるだけなので、本体を取るにはもう一度棚へ行く（＝2ホップ）。
① 問題

  • 「ORDER BY id は速いのに ORDER BY created_at は遅い」
② なぜ起きる？ — 葉に何が入っているかが違う

図6-1: この1枚でMySQLとPostgreSQLの性能差の大半が説明できる。面接で頻出。

③ 解決策 — Covering Index（テーブルを見に行かない）

07 Hash Index — O(1)なのに使われない理由

計算量だけ見れば O(1) のハッシュがB+Treeに勝つはずです。なのにRDBの既定はB+Tree。なぜかを理解すると「計算量だけで判断してはいけない」が体で分かります。

🔢 例え: Hash Index＝コインロッカーの番号札。番号を渡せば一発でその箱が開く。
しかし「101番から110番の中身を順に」と言われても、ロッカーの物理的な並びは番号順ではない（ハッシュでバラバラに配置されている）ので、1つずつ番号を指定して開けるしかない。「番号が分からないが最も大きい番号のもの」も無理。
① 問題

キー1つでの完全一致だけなら、B+Treeは3〜4ページ読みます。ハッシュなら理論上1回。なぜハッシュを既定にしないのか?

② なぜ起きる？ — ハッシュは「順序」を破壊する

08 Index あり / なし — なぜ行数が少ないと逆に遅いのか

この章は実務で最も誤解されている論点です。「Indexを貼れば速くなる」は条件付きの真。境界がどこにあるかを図で確定させます。

🚚 例え: Full Scan＝棚を端から端まで順に歩く（歩き続けるので効率がいい）。
Index Scan＝目録で場所を調べてから、その本のところへ「飛ぶ」。1冊なら圧勝だが、100冊飛ぶなら、端から歩いた方が速い。宅配便で言えば「1軒だけ配達」vs「全戸配布」の違い。
① 問題
  • 「Indexを貼ったのに EXPLAIN が Seq Scan を選ぶ。DBのバグ?」
  • 「1,000行のテーブルでIndexを貼ったら逆に遅くなった」
  • 「status（3種類しかない）にIndexを貼ったが効果ゼロだった」

結論から言うと3つ全部が正常な挙動です。理由を4つに分解します。

② なぜ起きる？ — 理由①: BigOは定数を捨てる記法だから

O(n) と O(log n) は「nが十分大きい時」の比較です。実際のコストは:

  • Full Scan ≒ c₁ × n … c₁は小さい（順次I/O・先読みが効く・1ページに40行）
  • Index Scan ≒ c₂ × log n + c₃ × k … c₂,c₃は大きい（木を降りる＋行ごとにランダムI/O）

この2つの線は必ず交差します。交差点より左（＝行数が少ない / ヒット件数が多い）ではO(n)の方が実際に速い。

図8-1: 「O(log n) は切片が高くて平らな線、O(n) は切片が低くて右肩上がりの線」。2本は必ず交差する。

② 続き — 理由②: ランダムI/Oは順次I/Oの4倍高い

図8-2: PostgreSQLのコストパラメータはこの差をモデル化したもの。設定値を見れば設計思想が分かる。

② 続き — 理由③: 選択率（selectivity）／ 理由④: 書き込みコスト

図8-3: 理由③④。数百行のマスタにPK以外のIndexは不要、が実務の結論。

③ 解決策 — 具体的な数値で比較する（1,000行 vs 100万行）
ケースFull Scan のコストIndex Scan のコスト勝者
1,000行 / 1件ヒット25ページ × 1.0 = 253 + 1×4.0 = 7Index
1,000行 / 50件ヒット25ページ × 1.0 = 253 + 50×4.0 = 203Full Scan（8倍速い）

10 INSERT / UPDATE / DELETE と WAL

書き込みは「ディスクに書く」だけではありません。先にログ、あとで本体——この順序が耐久性（Durability）の全てです。

📒 例え: WAL＝図書館の貸出台帳。本を棚から動かす前に、まず台帳に「この本をこう動かす」と書く。
途中で停電しても、台帳を見れば「やりかけの作業」が分かるので復元できる。台帳は追記だけ（ペンで最後の行に書く）なので速い。棚を整理するのは後でまとめてやる。
① 問題
  • 「COMMIT が返ったのに、直後の電源断でデータが消えていたら困る」
  • 「1行の UPDATE なのに、ディスクI/Oが何回も発生している」
  • 「DELETE したのにテーブルのサイズが減らない」
② なぜ起きる？ — ランダム書き込みは遅すぎる

1行更新するたびに該当ページをディスクの正しい位置へ書き戻すと、毎回ランダム書き込みになります。しかも書き込み途中の停電でページが半分だけ書かれた状態（partial write）になり得ます。
そこで「変更内容を追記ログに順次書く（速い・安全）→ 本体ページの書き戻しは後でまとめて（Checkpoint）」という2段構えにします。

図10-1: WALファーストの原則。「先にログ、あとで本体」を覚えれば、COMMITコストもレプリケーションも説明できる。

③ 解決策 — 3操作の内部挙動の違い

DELETEすぐには消えない。削除マークだけエントリも即時削除されない領域は VACUUM / purge が回収するまで残る

11 JOIN の内部処理 — 3つのアルゴリズム

JOINは「表をくっつける」ではなく3つのアルゴリズムのどれかが選ばれる処理です。どれが選ばれたかで性能が100倍変わります。

📮 例え: 100人の名簿（users）と500通の郵便（reservations）を突き合わせる作業。
① Nested Loop＝郵便1通ごとに名簿を引く（名簿に索引があれば速い）
② Hash Join＝先に名簿を付箋で仕分けした箱に作り替え、郵便を放り込む（大量なら最速）
③ Merge Join＝両方をあらかじめ五十音順に並べ、端から突き合わせる（すでに並んでいれば最速）
① 問題
  • 「JOINは遅いから使うな」と言われるが、アプリでループする方が遅かった（9章のN+1）
  • 「テーブルが小さいうちは速かったのに、100万行を超えた途端にクエリが返ってこなくなった」
  • 「JOINの順番を変えたら速くなった」——なぜ?
② なぜ起きる？ — アルゴリズムが切り替わる（または切り替わらない）

行数が増えるとオプティマイザは Nested Loop → Hash Join に切り替えます。しかし統計が古い / 結合キーにIndexがない / 見積りを外すと、100万行同士で Nested Loop を選んでしまい O(n × m)＝1兆回の比較になります。これが「返ってこないクエリ」の典型です。

④ 内部処理 — 3アルゴリズムの動きを図で（※③解決策も含む）

(A) Nested Loop Join — 外側の各行について内側を探す

図11-1: Nested Loop。「内側にIndexがあるか」で天国と地獄が分かれる。

(B) Hash Join — 小さい方でハッシュ表を作り、大きい方を流す

図11-2: Hash Join。「Indexなしでも O(n+m) で殴れる」代わりにメモリを使う。EXPLAINで Hash Join + Batches: 8 が出たらメモリ不足。

(C) Merge Join — 両方をソートして端から突き合わせる

図11-3: Merge Join。「ソート済み」という前提が揃った時だけ強い。

アルゴリズム計算量Indexメモリ最初の1行結合条件得意な場面
Nested LoopO(n log m) / O(n×m)内側に必須ほぼ不要速い何でも外側が少ない・LIMIT付き
Hash JoinO(n + m)不要大量に必要遅い等価のみ大×大の集計
Merge JoinO(n + m)あると最良少ない中範囲もOKソート済み・ORDER BY併用
⑤ トレードオフ
  • JOINをDBに任せる: 最適なアルゴリズムを自動選択してくれる。ただし統計が古いと最悪の選択をする
  • アプリで結合する: DB負荷は下がるが往復回数とメモリが増え、ほぼ必ず遅くなる（9章のN+1）
  • 非正規化して JOIN をなくす: 読みは最速。ただし更新の整合性を自分で守る必要（13章）
  • 結合列にIndexを貼る: Nested Loopが安全になる。ただし書き込みコスト増（8章）
🚫 JOINを使わない場合どうなるか

図11-4: 「JOINは遅い」の多くは誤解。本当に遅いのは往復回数と、Index不足によるNested Loopの暴走。

12 Execution Plan — EXPLAIN の読み方

ここまでの知識を実際に確認する道具がEXPLAINです。推測でIndexを貼るのをやめ、計画を読んで判断できるようにします。

🗺 例え: 実行計画＝司書が書いた「取りに行く手順のメモ」。
「まず目録Aを引いて、次に棚3へ行って、最後に机で並べ替える」と書いてある。EXPLAIN＝メモを見せてもらう / EXPLAIN ANALYZE＝実際に行かせて時間を測る。
① 問題

「遅いクエリがある」→ とりあえずIndexを貼る → 変わらない → 別のIndexを貼る…推測のループに入ってしまう。

② なぜ起きる？ — 見積りと実測がズレていることに気付けない

オプティマイザは統計情報からの見積りで計画を決めます。統計が古ければ「1,000行だと思って Nested Loop を選んだが実際は100万行だった」が起きます。この乖離はEXPLAIN ANALYZEでしか見えません。

③ 解決策 — 実際の出力を読む

図12-1: 見積りrows と actual rows の乖離が最重要のシグナル。ここが合っていれば大抵の計画は妥当。

④ 内部処理 — 改善のシーケンス

図12-2: 「1つだけ変えて測る」のが鉄則。複数同時に変えると何が効いたか分からなくなる。

⑤ トレードオフ
  • EXPLAIN（計画のみ）: 実行しないので安全・速い。ただし見積りしか分からない
  • EXPLAIN ANALYZE: 実測が取れる。ただし実際に実行される（UPDATE/DELETEでは BEGIN … ROLLBACK で囲む）
  • work_mem を大きくする: ソート・Hash Joinが速くなる。ただし接続数×並列度で掛かるのでOOMリスク
  • 統計対象を増やす（ALTER TABLE … SET STATISTICS）: 見積り精度が上がるが ANALYZE が重くなる
🚫 実行計画を見ない場合どうなるか
  • 効かないIndexが増え続ける → 書き込みが遅くなり、Buffer Poolを食い、状況が悪化する
  • 本当の原因（統計・ソート溢れ・N+1）に到達できない
  • 本番だけ遅い理由が分からない（開発環境はデータ量が少ないので別の計画が選ばれている）
  • 「なぜ速くなったか」も説明できない → 再発時に同じ調査を繰り返す

13 正規化 と 非正規化

正規化は「教科書の作法」ではなく「事実を1箇所にだけ書く」という更新安全性の設計です。非正規化はそれを意図的に崩して読みを速くする取引です。

📖 例え: 正規化＝会社名は「会社台帳」に1回だけ書き、本には台帳の番号だけ書く。社名が変わっても台帳の1行を直せば全部直る。
非正規化＝全部の本に会社名を直接書く。読むときは台帳を見に行かなくて済む（速い）が、社名変更で全部の本を書き直すことになる。
① 問題
  • 「会社名が変わったので10万行を更新した。途中で失敗して一部だけ古い名前が残った」
  • 「同じ住所が複数テーブルに散っていて、どれが正しいか分からない」
  • 逆に「正規化しすぎて、1画面のために7テーブルJOINになった」
② なぜ起きる？ — 同じ事実が複数箇所にある（更新異常）

図13-1: 正規化の目的は「美しさ」ではなく更新の原子性。1事実1箇所なら矛盾が構造的に起きない。

③ 解決策 — 正規形の実務的な理解（1NF〜3NF）
正規形ルール違反の例直し方
1NF1セルに1つの値（繰り返し列や配列を持たない）tags='go,sql,aws' / phone1, phone2, phone3別テーブルに縦持ち
2NFPKの一部にだけ依存する列を持たない（複合PK時）PK(order_id, product_id) なのに product_name があるproducts テーブルへ分離
3NFPK以外の列に依存する列を持たない（推移的関数従属）zip → city なのに両方持つzip マスタへ分離
実務の目安「同じ事実を2箇所に書いていないか」だけを問えば、ほぼ3NFに到達する。正規形の暗記より原則。
④ 内部処理 — 非正規化の4つのやり方（読みを速くする取引）
手法やること整合性の維持方法使う場面
列のコピー注文明細に商品名をコピー「その時点の事実」として意図的に固定（履歴の性質）請求書・注文明細（後で商品名が変わっても当時の名前が正しい）
集計列（カウンタ）posts.comment_countトリガー / アプリで更新 / 定期バッチで補正いいね数・コメント数（毎回COUNTすると重い）
マテリアライズドビュー集計結果を実体テーブルに保存REFRESH（DBが面倒を見る）ダッシュボード・日次集計
JSON列に埋め込み可変項目をJSONBで持つアプリ責任設定値・メタデータ・スキーマが安定しない部分

図13-2: 非正規化の代償はズレの検知と補正という運用コスト。

⑤ トレードオフ
観点正規化非正規化
読み性能JOINが必要1テーブルで完結
書き性能1箇所だけ更新全コピーを更新
整合性構造的に保証（FK・1事実1箇所）アプリ/運用の責任
容量小さい重複分だけ増える
スキーマ変更影響範囲が局所的コピー先を全部探す必要

順序が重要: まず正規化して作る → 計測する → 実測で問題が出た箇所だけ非正規化。逆順（最初から非正規化）は、必要のない借金を最初に背負う行為。

🚫 正規化しない場合 / しすぎた場合

しない場合

  • 社名変更で数万行のUPDATE、しかも漏れる
  • 「正しいのはどの行か」が誰にも分からなくなる
  • 集計値が合わず、経営数値が信用されなくなる

しすぎた場合

  • 1画面7テーブルJOINでオプティマイザが最適順序を見つけられない（結合順の組合せが爆発）
  • マスタが細分化されすぎてコードの見通しが悪化
  • 「注文時の価格」を正規化して後の値上げで過去の請求額が変わる（← これは非正規化が正解の例）

14 ACID — トランザクションが守る4つの約束

ACIDは暗記項目ではなく「4つの別々の問題への、4つの別々の解決策」です。それぞれ実装機構が違います。

🏦 例え: 銀行の振込＝「Aから引く」と「Bに足す」を必ずセットで。片方だけ成功したらお金が消える。
窓口の約束が4つ: A=途中でやめたら全部なかったことに / C=残高がマイナスにならない / I=隣の窓口の作業中が見えない / D=完了と言ったら停電でも消えない。
① 問題

図14-1: 「一部成功」が最悪の状態。エラーで全部失敗するよりタチが悪い。

③ 解決策 — 4つの約束と実装機構

図14-2: ACIDは4つの独立した機構。「Aはログ、Cは制約、IはMVCC/ロック、DはWAL」と対応で覚える。

④ 内部処理 — Goでの書き方と落とし穴
やること理由
defer tx.Rollback() を必ず書くエラー時にトランザクションが開いたまま残ると、ロックとVACUUM阻害が続く（10章のBloat原因）
トランザクションを短く保つ長いTxはロック保持時間が伸び、他をブロックし、旧バージョンの回収も止める
Txの中で外部APIを呼ばない外部の応答待ちの間ずっとロックを持つ。タイムアウトでDB接続も枯渇する
更新順序を全処理で統一するデッドロック回避の基本（17章）
リトライ可能な設計にするSerializable / デッドロックは正常にエラーになるので、アプリ側の再実行が前提
⑤ トレードオフ
  • 強いACID: 安全。だが単一ノードに集約しがちで水平スケールが難しい（分散トランザクションは高コスト）
  • 結果整合性（BASE）: スケールする。だが「一瞬古いデータが見える」を業務が許容できるかの判断が必要
  • 同期レプリケーション: データを失わない。だが書き込みレイテンシがネットワーク往復分増える
🚫 ACIDを採用しない場合（NoSQLの結果整合性で組む）
  • 「予約と在庫を同時に確定」が原子的にできない → 二重予約が発生し得る。補償トランザクション（Saga）を自作する必要
  • 読んだ値が最新でない → 在庫1個を2人に売る事故。業務がそれを許すかどうかで採用可否が決まる
  • 整合性チェックが全部アプリ側 → コードが増え、抜け道（バッチ・手作業SQL）から壊れる
  • 逆に許容できる場面もある: SNSのいいね数・閲覧数・タイムライン。1秒古くても誰も損しないならACIDのコストを払う必要はない

15 Isolation Level — 何をどこまで見せるか

分離レベルは「安全性 ↔ 並行性」のダイヤルです。強くすれば正しいが待ちが増える。弱くすれば速いが特定の異常が起きる。

🚧 例え: 図書館で司書が棚を整理している最中に、利用者が棚を見に来た。
①整理途中の棚をそのまま見せる（Read Uncommitted）②整理が終わった棚だけ見せる（Read Committed）③入館時点の写真を見せる（Repeatable Read）④整理中は入館そのものを待たせる（Serializable）
① 問題 — 3つの異常現象

図15-1: この4つの名前と発生条件を言えるかは面接の定番。特にLost Updateは実装で防ぐ意識が必要。

③ 解決策 — 4つの分離レベル
レベルDirty ReadNon-repeatablePhantom図書館の例え性能
Read Uncommitted起きる起きる起きる整理途中の棚を見せる最速（実用性なし）
Read Committed
PostgreSQL既定		防ぐ起きる起きる整理が終わった棚だけ見せる速い
Repeatable Read

重要な実務知識: MySQL(InnoDB)の既定は Repeatable Read、PostgreSQLの既定は Read Committed。同じアプリコードでもDBを変えると挙動が変わるのはこれが原因。

④ 内部処理 — Read Committed と Repeatable Read の違い（スナップショットを取る時点）

図15-2: 「写真をいつ撮るか」の違い。実装しているのはMVCC（次章）。

⑤ トレードオフ — どう選ぶか
要件推奨理由

複数テーブルを読む集計・帳票Repeatable Read読んでいる最中に値が変わらない＝合計が合う

🚫 分離レベルを意識しない場合どうなるか
  • 「テストでは動いたが本番の同時アクセスで壊れる」 → 分離性の問題は単体テストでは絶対に見つからない
  • MySQLからPostgreSQLへ移行して挙動が変わる（既定レベルが違う）
  • 在庫がマイナスになる（Lost Update / Phantom）
  • 逆に全部Serializableにすると、直列化失敗エラーが多発してユーザーに見えるエラーになる（リトライを書いていないため）

16 MVCC — 読む人と書く人を待たせない仕組み

「読み取りは書き込みをブロックせず、書き込みは読み取りをブロックしない」。この魔法の実装が MVCC（多版型同時実行制御）です。

📸 例え: 司書が棚を整理している間、利用者には「入館した時点の棚の写真」を見せる。
利用者は写真を見るので整理の完了を待たなくていい。司書も利用者を追い出さずに整理できる。代わりに古い写真（旧バージョン）を一定期間保管する倉庫が必要になる。
① 問題

単純なロック方式（読む時も共有ロックを取る）だと、集計クエリ1本が全ての書き込みを止めることになります。逆に書き込み中は誰も読めない。これでは並行性がゼロに近い。

② なぜ起きる？ — 1つの行に1つの値しか持たないから

「行に値が1つしかない」なら、書き換えている最中は誰にも見せられません。ならば行を複数バージョン持てばいい——それがMVCCの発想です。

③ 解決策 — 行に「いつ生まれ、いつ死んだか」を書く

図16-1: MVCCの実装。「行を書き換えず、新しい版を足す」のが本質。旧版の掃除が運用の要点。

④ 内部処理 — 読み取りと書き込みが並行に走るタイムライン

図16-2: MVCCの利益と代償。「読みが速い」の裏に「旧版の掃除」という運用がある。

⑤ トレードオフ
観点MVCC単純なロック方式（2PL only）
読み取りロック不要・待たない共有ロックが必要・書き込みをブロック
並行性高い低い
容量旧バージョン分が必要1版だけ
運用VACUUM / UNDO管理が必要不要
Lost Update防げない（別途ロックが必要）防げる

重要: MVCCは読み取りの一貫性を解決しますが、書き込み競合（Lost Update）は解決しません。だから17章のロックが必要になります。MVCCとロックは両方使うのが正解。

🚫 MVCCがない場合どうなるか
  • 集計クエリ（5分）の間、全ての書き込みが待たされる → 日次バッチ中はサービスが停止する
  • SELECTのたびにロック取得 → ロック管理のオーバーヘッドとデッドロックの増加
  • 読み取り専用のレプリカでも書き込み反映で読みが止まる
  • 逆にMVCCがあることで生じる問題: 長時間トランザクションを放置するとテーブル膨張とVACUUM停止で本番が劣化する（＝MVCCを理解していないと踏む罠）

17 Lock とデッドロック

MVCCで解決できない「書き込み同士の競合」を扱うのがロックです。そしてデッドロックは設計で予防できます。

🚧 例え: ロック＝棚に「整理中・触らないで」の札を掛ける。
デッドロック＝司書Aが棚1の札を持って棚2を待ち、司書Bが棚2の札を持って棚1を待つ。永遠に解けないので、館長（DB）がどちらかを強制退場させる。
① 問題
  • 在庫10個に対して2人が同時に購入 → 両方成功して在庫が9になる（Lost Update）
  • 本番で deadlock detected が突然発生し、片方の処理が失敗する
  • lock wait timeout でリクエストがタイムアウトする
③ 解決策 — 3つの防ぎ方

図17-1: ③の原子的更新が第一選択。「読んで→計算して→書く」をSQL 1文にできるなら競合は消える。

④ 内部処理 — デッドロックの発生と検出

図17-2: デッドロックはバグではなく設計の問題。順序統一とリトライで実務上は消せる。

⑤ トレードオフ
方式待ち失敗実装コスト向く場面
悲観ロック（FOR UPDATE）発生するしない（待てば成功）低い競合が多い・確実性優先
楽観ロック（version）しないする（要リトライ）中（リトライ実装）競合が稀・ユーザーに通知したい
原子的更新（SET x = x-1）最小しない最小まずこれ。表現できるなら最良
Serializable に任せる中する（要リトライ）低い（が要リトライ）複雑な不変条件
🚫 ロックを使わない場合どうなるか
  • 在庫が足りないのに売れる（オーバーブッキング）→ 顧客対応コストと信用の損失
  • ポイント・残高が二重加算される → 金銭的損失。しかもログを見ても正常に見える（両方のリクエストが成功しているため）
  • 同時編集で片方の変更が消える → ユーザーが「保存したのに消えた」と報告するが再現できない
  • これらはアクセスが増えるほど確率が上がるので、成功したサービスほど踏む

18 7社での使われ方 — 実例ベース

同じ「Database」でも、要件（読み書き比・整合性の必要度・規模）によって選択が全く違います。面接では「なぜその選択か」を問われます。

🔍 Google — Spanner / Bigtable

課題

全世界に分散しながらACIDトランザクションが必要（広告課金・決済）。従来は「分散するならACIDを諦める」が常識だった。

解決

Spanner: GPS＋原子時計による TrueTime API で全ノードの時刻を数ms以内に揃え、グローバルな順序付けを可能にした。結果として分散なのにSerializableを実現。

本書との対応

  • 14章 ACID / 15章 Serializable を分散環境で実装した例
  • 16章 MVCC の応用（タイムスタンプでバージョン管理）
  • Bigtable（NoSQL / LSM-Tree）は検索インデックスやMapsなど超大量書き込み用途

★ 面接での学び: 「CAP定理でCとAは選択」だが、ハードウェア（原子時計）に投資して制約を緩めたという発想。

🐦 Twitter (X) — タイムラインの Fan-out

課題

「自分がフォローしている全員の最新ツイート」を毎回JOINで取ると、読み取りのたびに数千人分の検索が必要。読み:書き = 100:1 なので読みを最適化したい。

解決（Fan-out on Write）

ツイート投稿時にフォロワー全員のタイムラインキャッシュへ書き込む。読む時は自分の箱を1回読むだけ（Redis）。読みのコストを書きに移した＝非正規化の極端な例。

残る問題とハイブリッド解

フォロワー1億人の有名人が投稿すると1億回の書き込みが発生（Celebrity Problem）。
→ 有名人だけ Fan-out on Read（読む時に取りに行く）に切り替えるハイブリッド構成。

Q1 インデックスを貼ると必ず速くなりますか?

結論: いいえ。行数が少ない場合・ヒット率が高い場合・書き込みが多い場合は逆に遅くなります。

理由: Index Scanは「木を降りる（3〜4ページ）」＋「ヒット件数分のランダムI/O（順次の約4倍のコスト）」が必要です。一方Full Scanは順次I/Oで先読みが効きます。O(n) と O(log n) の2本の線は必ず交差し、交差点より左（小さいn / 大きいヒット率）ではFull Scanが勝ちます（図8-1）。目安としてヒット率5〜20%を超えるとFull Scanが有利です。

トレードオフ: Indexは読みの資産ですが書きの負債で、INSERT/UPDATEごとにIndex本数分のB+Tree更新とページ分割が発生し、Buffer Poolも消費します。

実務: だから「Indexを貼ったのにSeq Scanが選ばれる」のは多くの場合オプティマイザの正しい判断です。疑う順序は ①行数 ②選択率 ③統計の古さ（ANALYZE） ④Index不能な書き方。

Q2 なぜRDBはハッシュではなくB+Treeを使うのですか?

結論: ハッシュは順序を捨てているため、範囲検索・ORDER BY・前方一致LIKE・MIN/MAXが全てできなくなるからです。

理由: B+Treeが選ばれる技術的理由は2つあります。①1ノードを1ページ（数百キー）にすることで木が極端に浅い——fanout 300なら100万行で高さ3、81億行でも4。ディスクのコストはアクセス回数なので、浅さが直接速さになります。②葉がソート済みで双方向リンクしているので、範囲検索は「1回seekして横に歩く」だけの O(log n + k) になります。

トレードオフ: 点検索だけならハッシュの O(1) が理論上速いですが、ハッシュはリハッシュ時に全体が停止し、最悪ケースが O(n) です。B+Treeはページ分割が局所的で、最悪でも O(log n) が保証されます。

ハッシュが正しい場所: Hash Join（メモリ上・等価のみ）、Redis、シャーディングキー、Bloom Filter。

Q3 PKにUUIDを使うことの問題は何ですか?

結論: 2つあります。①UUID v4はランダムなのでB+Treeへの挿入位置が毎回バラバラになり、ページ分割・断片化・キャッシュ効率の低下を招く。②36バイト（文字列なら）は太いため、InnoDBでは全ての2次Indexの葉にPK値が入るのでIndex全体が膨張してBuffer Poolを食い潰します。

理由: 連番PKなら挿入は常に最右の葉で、触るページが局所的なのでキャッシュに収まります。ランダムPKだと木全体に分割が散ります（図4-1）。

解決策: ① UUID v7 / ULID（先頭が時刻なのでほぼ単調増加＝分散採番と挿入性能を両立） ② Snowflake ID（Twitter方式の64bit整数） ③ 内部PKは連番、外部公開用に別途UUID列を持つハイブリッド ④ UUIDを使うなら文字列ではなくバイナリ16バイトで保存。

実例: Instagramは [timestamp 41bit][shard 13bit][連番 10bit] の64bit IDを採用。時刻順にソート可能かつIDからシャードが判別できます。

Q4 JOINの内部アルゴリズムを3つ説明し、それぞれいつ選ばれるか述べてください。

① Nested Loop: 外側の各行について内側を探索。内側の結合キーにIndexがあれば O(n log m)、なければ O(n × m)。外側が少なくLIMITが付く場合に最良（最初の1行が早く返る・メモリ不要）。

② Hash Join: 小さい表でハッシュ表を作り（Build）、大きい表を1回流す（Probe）。O(n + m) でIndexが不要。大×大の等価結合に最適。代償はメモリ——work_memを超えると一時ファイルへ分割（Batched Hash Join）して激遅になり、またBuildが終わるまで1行も返らない。

③ Merge Join: 両方をソート順に並べて同時に歩く。O(n + m)、省メモリ、範囲結合にも使える（Hash Joinは等価のみ）。両表がIndex順で取れる時に最良で、結果をそのままORDER BYに使えます。

事故パターン: 統計が古くて「1,000行だと思ったら100万行」だとNested Loopが選ばれて O(n×m) で返ってこなくなります。またPostgreSQLはFK制約を張っても子側のIndexを自動作成しないので、手で貼らないとJOINと親のDELETEが全表走査になります。

Q5 ACIDのそれぞれを、実装機構と対応させて説明してください。

A - Atomicity: 「全部成功か全部なし」。実装はUNDOログ（InnoDB）/ 旧行タプル（PostgreSQL）。ROLLBACKとクラッシュ時のUNDOで実現。同時実行の話ではなく失敗時の巻き戻しの話である点が誤解されやすい。

C - Consistency: 「ルールを破った状態にしない」。実装は制約（PK/FK/UNIQUE/CHECK/NOT NULL）。分散システムの「結果整合性」のCとは別概念。

I - Isolation: 「同時実行なのに順番に実行したように見える」。実装はMVCC + ロック。4つの中で唯一強さを選べる（分離レベル）ので、設計判断の対象になります。

D - Durability: 「COMMITしたら消えない」。実装はWAL + fsync、復旧時にREDO。「先にログ、あとで本体」が原則で、これによりランダム書き込みを避けつつ耐障害性を得ています。

深掘りへの備え: 「外部API（決済）はDBのトランザクションに入らない」ので、そこはSaga・補償トランザクション・冪等キーで設計する必要があります。

Q6 分離レベルを4つ挙げ、それぞれ何を防ぐか説明してください。実務では何を選びますか?

Read Uncommitted: 何も防がない（未コミットの値が見える＝Dirty Read）。実用性はほぼない。
Read Committed（PostgreSQL既定）: Dirty Readを防ぐ。文ごとにスナップショットを取り直すので、同一Tx内で値が変わり得る（Non-repeatable Read）。
Repeatable Read（MySQL既定）: Tx開始時のスナップショットを最後まで見るので同じ行は何度読んでも同じ。実装上PhantomもほぼFalse。
Serializable: Phantomまで防ぐ。ただし直列化失敗エラーが返るのでリトライ実装が前提。

実務の選択: 通常のCRUDはRead Committed（最新が見えて速い）。集計・帳票はRepeatable Read（読んでいる最中に合計が変わらない）。在庫・座席の確定はRead Committed + FOR UPDATE（全体をSerializableにせず該当行だけロックする）。複雑な不変条件だけSerializable。

重要な注意: MySQLとPostgreSQLで既定が違うため、同じコードでもDBを変えると挙動が変わります。またLost Updateは分離レベルだけでは防げないので、原子的更新か明示的ロックが必要です。

Q7 MVCCとは何ですか? その代償は?

結論: 行を1つの値ではなく複数バージョン持つことで、「読み取りは書き込みをブロックせず、書き込みは読み取りをブロックしない」を実現する仕組みです。

実装: PostgreSQLは各行に xmin（作成Tx ID）と xmax（削除Tx ID）を持ち、UPDATEは古い行にxmaxを立てて新しい行を追記します。読む側は自分のTx IDと比較して「自分に見えるバージョン」を選ぶので、ロックを1つも取らずに一貫した読みができます。InnoDBは本体を上書きし、旧値はUNDOログに置いて必要時に巻き戻して再構成します。

代償: ①旧バージョンの保管コスト——PostgreSQLはVACUUMが回収するまでテーブルが膨張（Bloat）し、Full Scanが読むページが増えて遅くなる。②長時間トランザクションが致命的——最古のTxより古い版は回収できないので、1時間のTxがあるとその間の全ての旧版が残る。③InnoDBではUNDOが伸びて古い版の再構成が遅くなる。

限界: MVCCは読み取りの一貫性を解決しますがLost Updateは防げません。だからロック（17章）と併用します。

Q8 「残り1室」の予約でダブルブッキングを防ぐ設計を説明してください。

結論: 「読んで→計算して→書く」をやめて、1文の原子的更新にするのが第一選択です。

UPDATE rooms SET stock = stock - 1
 WHERE room_id = :id AND stock > 0;
-- 更新行数が0なら在庫切れ → 予約を作らずエラーを返す

理由: この形ならDBが自動的に行ロックを取り、条件判定と更新が原子的に行われるので競合が原理的に起こりません。アプリのリトライも不要で、往復も1回です。

複数テーブルに跨る場合: BEGIN → SELECT … FOR UPDATE（該当室を悲観ロック）→ 在庫確認 → 予約INSERT → 在庫UPDATE → COMMIT。この間外部の決済APIを呼ばない（ロック保持時間が伸びて接続が枯渇するため。決済は予約確定後に別フェーズで、冪等キー付きで実行）。

「日付範囲の重複」を防ぐ場合: 行ロックでは足りずPhantomを防ぐ必要があります。PostgreSQLなら EXCLUDE USING gist 制約（範囲の重なりをDBが拒否）か Serializable。

表示との使い分け: 検索・一覧の在庫表示は結果整合で十分（1秒古くても成立）なのでキャッシュ/レプリカから読み、確定の瞬間だけ厳密にする。Booking.comの構成がこれです。

デッドロック対策: 複数室を確保する場合は常にIDの昇順でロックを取ると循環待ちが消えます。

Q9 「一覧画面が後半のページだけ遅い」原因と対策は?

結論: OFFSET ページングが原因です。LIMIT 10 OFFSET 100000 は100,010行読んで100,000行を捨てるので O(offset + k)。ページが進むほど線形に遅くなります。

対策1（keyset / seek方式）: WHERE id > :last_id ORDER BY id LIMIT 10。B+Treeで直接その位置にseekするので O(log n + 10)、何ページ目でも一定速度です。代償は「N ページ目に飛ぶ」ができないこと（無限スクロールや「次へ」なら問題なし）。

対策2（ソートをIndexで消す）: ORDER BY created_at DESC LIMIT 20 が非Index列だと O(n) + O(n log n)（全件読んでソート）。Indexの並びと一致させればソート処理そのものが消えて O(log n + k) になります。LIMITは最後にしか効かないので、ソートを消すのが本質です。

確認方法: EXPLAIN ANALYZE で Sort Method: external merge Disk: … が出ていたらメモリ溢れのディスクソート、Rows Removed by Filter が大きければ無駄読みです。

総件数表示も要注意: COUNT(*) は毎回全件確認になるので、概算（reltuples）や「100件以上」表示に逃がすのが実務的です。

Q10 RDBとNoSQLをどう選び分けますか? 併用する場合の境界は?

結論: 「新しさ」ではなくアクセスパターンで選びます。RDBが既定解で、そこから外れる要件だけ別のDBに出します。

判断順: ①「繋がりを何段も辿る」が主目的か → グラフ ②キー1つで引くだけ・揮発可 → Key-Value(Redis) ③1件を丸ごと読む＆項目が可変 → ドキュメント ④それ以外 → リレーショナル。

RDBを選ぶ理由: JOIN・集計・複数行にまたがるトランザクション・FKや制約による整合性の保証。業務システムはこれらがほぼ必ず要ります。

NoSQLを選ぶ理由: ネスト構造をそのまま保存（インピーダンスミスマッチの回避）、スキーマ可変、水平スケールが前提の設計、書き込み偏重（LSM-Tree）。

実務の境界（Polyglot Persistence）: 業務の中核＝RDB / キャッシュ・セッション・ランキング＝Redis / 全文検索・地理検索＝Elasticsearch（LIKE '%…%' はB+Treeで不可能なので） / ログ・イベント＝列指向やオブジェクトストレージ / 分析＝BigQuery等の列指向。

失敗例を言えると強い: 全部RDBにするとログで列が増え続けセッション書き込みでDBが詰まる。全部NoSQLにすると集計をアプリで書き、社名変更で10万ドキュメント更新、FKがないので孤児データが残り、「予約と支払いを同時に確定」ができない。Netflixも視聴履歴はCassandra、課金はRDBと分けています。

Q11 ボーナス: 「特定のAPIが遅い」と報告されました。どう調査しますか?

結論: 上流から順に切り分け、推測でIndexを貼らない。

  1. どこが遅いかを分ける: アプリのCPU / DB待ち / 外部API待ち / ネットワーク。APMやログのタイムスタンプで区間を測る。
  2. クエリ回数を数える: 1リクエストで何本SQLが飛んでいるか。N+1なら本数が行数に比例して増える（これはIndexでは直らない）。
  3. 遅いクエリを特定: pg_stat_statements / slow query log で合計時間が大きい順に見る（1本が遅いのか、速いのが大量か）。
  4. EXPLAIN (ANALYZE, BUFFERS): ①見積りrowsと実測rowsの乖離（→ANALYZE）②Seq Scanで少数返し（→Index / クエリ書き換え）③external merge（→work_mem / ソート消し）④Nested Loopのloops過大。
  5. 1つだけ手を打って再測定: 優先順は ANALYZE → クエリ書き換え → Index追加 → パラメータ → 最後に非正規化やキャッシュ。
  6. ロック待ちの可能性も見る: pg_locks / innodb_lock_waits。長時間トランザクションやDDLが原因なら、クエリをいくら直しても解決しない。

この質問の狙い: 「Indexを貼ります」と即答する候補者と、切り分けの順序を持っている候補者を見分けるためです。
