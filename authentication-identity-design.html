00 はじめに — 認証を貫く7つの質問

結論から。認証とは、クライアントがCredentialを提示し、サーバーがそれを検証してIdentityを確定する処理である。Password も Cookie も JWT も OAuth も SSH も mTLS も IAM も、この1文の変奏にすぎない。違うのは「Credentialが何か」「誰が発行したか」「誰がどう検証するか」「Stateがどこにあるか」「期限をどこで管理するか」「どうIdentityへ変換するか」「どう無効化するか」の7点だけだ。
本書は、この7つの質問を全24章で繰り返し当てはめる。最後まで読めば、初見の認証技術でも同じ7問で分解できるようになる。

Part I

基礎モデル — Password・Cookie・Session

最も古く、最も単純で、そして今も本番システムの大半を支えている認証。ここで「Credential を提示し、検証し、Identity を確定する」という骨格を体に入れる。後半の JWT・OAuth・SSH・mTLS は、この骨格の部品交換にすぎない。

01 Authenticationの全体像 — 認証・認可・識別・Credential・Identity

結論から。Authentication（認証）は「あなたは誰か」を確定する処理、Authorization（認可）は「その誰かに何を許すか」を判定する処理である。この2つは別のステップであり、別のコードであり、別のバグを生む。認証を通ったユーザーが他人の予約を見られる事故は、ほぼ全て「認証が済んだ＝許可された」という混同から生まれる。本章では、リクエストが Resource に到達するまでの6段階を固定し、以降すべての章でこの6段階を再利用する。

1. 誰が認証されるか

リクエストの主体（Principal）。人間のユーザー、他サービス、マシン

2. 認証する側

リクエストを受け取ったサーバー（またはそれが信頼する Auth Server）

3. Clientが持つCredential

本人性を証明する材料。Password / session_id / JWT / API Key / 秘密鍵 / 証明書

4. Serverが検証するもの

Credential が「正しい発行元から出て」「改ざんされておらず」「期限内」であること

5. Identity の特定方法

検証済み Credential を user_id / service_id に変換する。方式ごとに変換テーブルが違うだけ

図1-1 全章で使う6段階。Identification は「名乗り」、Authentication は「名乗りの検証」、Identity は「検証の出力」。Authorization はその出力を使う別の処理。

5つの用語を、混ぜずに定義する

用語一言で問いPMSでの例ありがちな混同
Identification名乗ること「私は誰と主張しているか」ログインフォームの email 欄、JWT の sub、SSH の ssh staff@host の staff名乗り＝認証と思う。email を送ってきたから本人だと扱う
Credential証明の材料「主張を裏付ける物は何か」Password、Cookie の session_id、Bearer の JWT、API Key、SSH 秘密鍵、クライアント証明書Credential と Identity を同じものだと思う（「JWT がユーザーだ」）

事実として、HTTP のヘッダ名は Authorization: Bearer ... だが、そこに載っているのは Credential であり、行われる処理は Authentication である。名前が悪い。この歴史的な命名ミスが混同を助長している。

なぜ Identification と Authentication を分けるのか — 「名乗りは無料、証明は有料」

  • 名乗りは誰でもできる。 HTTP リクエストに user_id=123 と書くのはタダだ。書いた人が 123 である保証はゼロ
  • 証明にはコストがかかる。 Password を知っている、Session Store に登録された乱数を持っている、秘密鍵を持っている。この「持っていること」の検証が Authentication
  • サーバーが信用してよいのは「検証の出力」だけ。 リクエスト body の user_id、クエリの ?uid=、Base64 decode しただけの JWT payload。これらは全部「名乗り」であって Identity ではない
  • 解釈：認証バグの半分は「名乗りを Identity として使った」で説明できる。IDOR（Insecure Direct Object Reference）はその典型

よくある設計ミス① — 「ログイン済み」で認可を終わらせる

実際の PMS で最も多い事故。認証は完璧に動いている。だが、認証を通った瞬間に全予約が見える。

  • 何が起きるか： 施設Aのスタッフが GET /reservations/999 を叩くと施設Bの予約が返る。URL の数字を変えるだけ
  • なぜ起きるか： user != nil は「Identity が確定した」という事実の確認にすぎない。Identity と Resource の関係は一切見ていない
  • 認証は正しい、認可が欠落している。 認証ライブラリをどれだけ強化しても直らない。直すのは handler 側の1つの if 文

よくある設計ミス② — 401 と 403 を混ぜる

Status意味段階Client への含意

403 Forbidden「誰かは分かった。だが許可しない」Authorization 失敗Credential を変えても無駄。権限がない
404 Not Found「存在しない」（存在を隠すために 403 の代わりに返す設計もある）Authorization の隠蔽他施設の予約IDが「存在するか」すら教えない

名前が逆に見える（401 が "Unauthorized" なのに認証失敗）のは、HTTP 仕様の歴史的な命名。解釈：「401 = Credential の問題、403 = 権限の問題」と覚え直す。混ぜると、フロントエンドが 403 でリダイレクトループを起こす、あるいは 401 なのに「権限がありません」と表示して再ログインを促せない、という UI バグになる。

Go での責務分離 — 認証は middleware、認可は handler / usecase

認証は「全リクエストに共通」で「Resource を知らなくてよい」。認可は「Resource ごとに違う」。だから置き場所が違う。

  • middleware は Credential の種類（Cookie / Bearer / API Key）を知っている。Resource は知らない
  • usecase は Resource のルール（施設スタッフは自施設の予約のみ）を知っている。Credential の種類は知らない
  • この分離により、認証方式を Session → JWT に変えても usecase は1行も変わらない。逆に、認可ルールが変わっても middleware は変わらない

図1-2 Authentication は middleware で完結し、Identity を渡す。Authorization は Resource を読んだ後にしか判定できない。だから置き場所が違う。

Identity は「サーバーが確定した値」だけを使う — 名乗りを混入させない

認証を通った後でも、リクエストの中には「名乗り」が残っている。それを Identity と混ぜた瞬間に認証は無意味になる。

  • body の user_id は Identification。Authentication の出力ではない。攻撃者は body の accommodation_id を対象の予約に合わせて書き換えるだけ
  • 解釈：Identity の唯一の出所は認証 middleware が context に入れた値。body / query / header の "user_id" は認可判定に使わない。DTO から消す

02 Password Authentication — 「知っている」ことの証明

結論から。Password 認証とは「サーバーが保存している Hash と、入力から計算した Hash が一致するか」を比べる処理である。サーバーは Password そのものを知らない。知らないから漏洩しても復元できない。この「知らないのに検証できる」という性質が、以降の全方式（署名、公開鍵、Challenge-Response）に受け継がれる最初の原理だ。

1. 誰が認証されるか

人間のユーザー（email で名乗る）

2. 認証する側

自社 Go API（users テーブルを持つ側）

3. Clientが持つCredential

Password（人間の記憶。ネットワークを1回だけ流れる）

4. Serverが検証するもの

入力 Password を同じ salt・同じアルゴリズムで Hash し、保存済み Hash と定数時間比較

5. Identity の特定方法

email → users 行 → hash 一致 → その行の user_id=123

Password 方式

user_id=123
（この直後に Session を作る → ch3）

図2-1 左：登録時は Hash だけ保存。右：ログイン時は同じ salt で再計算して比較。どちらの経路でも Password は保存されない。

なぜ「暗号化」ではなく「Hash」なのか

  • 暗号化は可逆。 鍵があれば復号できる。鍵はサーバーにある。つまりサーバーが侵害されれば全 Password が平文に戻る
  • Hash は不可逆。 hash から元の文字列は計算できない。サーバーは「一致するか」だけ判定でき、「何だったか」は知らない
  • 検証に復元は不要。 認証がしたいのは「同じ物を知っているか」の確認であって「何を知っているか」の取得ではない。復元できない方が要件を満たす
  • 事実：Password の「暗号化保存」を謳うシステムは、鍵管理の失敗で漏洩した際に全ユーザーの Password が平文で出る。他サービスで同じ Password を使うユーザーが多いため、被害は自社の外へ広がる
暗号化（AES など）汎用 Hash（SHA-256）Password Hash（bcrypt / Argon2）
可逆性可逆（鍵があれば戻る）不可逆不可逆
速度速い速すぎる（GPU で秒間数十億回）意図的に遅い（数十〜数百ms）
Salt—自分で付ける必要がある内蔵。出力文字列に含まれる
コスト調整—不可cost / memory / iterations を上げられる
Password 保存に不適不適適切

Salt — 「同じ Password でも違う Hash」にする理由

図2-2 Salt は「事前計算表を無効化」、遅い Hash は「総当たりを高コスト化」。2つは別の攻撃に対する別の対策。

Go 実装 — 登録とログイン

  • 定数時間比較： == や bytes.Equal は先頭バイトが違えば即 return する。応答時間の差から1バイトずつ当てられる。subtle.ConstantTimeCompare を使う。bcrypt ライブラリの CompareHashAndPassword は内部でこれをやっている
  • ユーザー存在の漏洩： 「メールアドレスが登録されていません」と「パスワードが違います」を分けると、攻撃者は登録済み email を列挙できる。メッセージを統一し、さらに処理時間も揃える（存在しないユーザーでも Hash を1回計算する）
  • ハッシュのアップグレード： PHC 文字列にパラメータが入っているので、ログイン成功時に「古いパラメータなら再 Hash して保存」ができる。平文を知っているのはログインの瞬間だけ。ここでしか再 Hash できない

攻撃と対策 — Brute Force / Credential Stuffing / Rate Limit / Account Lock

図2-3 3つの攻撃はサーバーを「通る/通らない」「集中/分散」で性質が違い、対策も対応が1対1ではない。

  • Account Lock の副作用： 攻撃者が「被害者の email に5回失敗」を繰り返せば被害者は永久にログインできない。恒久 Lock ではなく「15分の一時 Lock」＋「MFA での解除」にする
  • 失敗カウントのリセット： 成功時に email 側だけ消す。IP 側を消すと、攻撃者が「自分の正規アカウントで1回成功」を挟むだけで回避できる

MFA — 「知っている」だけでは Identity を確定させない

要素何を証明するか例弱点
Knowledge知っているPassword、PIN漏洩・推測・再利用
Possession持っているTOTP アプリ、SMS、FIDO2 キー、スマホの PasskeySMS は SIM swap、TOTP はフィッシングで中継可能
Inherenceである指紋、顔（多くは Passkey の端末ロック解除に使われる）変更不能。単体ではなくデバイスの鍵解放に使う
  • MFA の本質は「Credential を2種類要求する」こと。Password が漏れても、Possession 要素がなければ Verification が完了しない
  • 設計上の注意：Password 検証成功 → 「MFA 待ち」の中間状態 → TOTP 検証成功 → Identity 確定。中間状態で Session を発行してはいけない。発行するなら mfa_pending=true の限定 Session とし、認可 middleware がそれを弾く
  • 解釈：Passkey（WebAuthn）は「公開鍵認証を人間のログインに持ち込んだもの」。仕組みは ch15 の SSH と同じ。Password 認証の章の最後に置いたのは、これが Password の後継だからだ

図2-4 Password はログインの1回だけ流れる。以降は Session（ch3）が Credential を引き継ぐ。Password 認証の出力は user_id であり、Session はその「持ち運び形式」。

よくある誤解

  • 「Password を暗号化して保存しているので安全」 — 鍵がサーバーにある限り、侵害時に全 Password が復元される。Hash に変える
  • 「SHA-256 + Salt で十分」 — 速すぎる。GPU 1枚で 1秒に 100 億回。8文字英数字なら数時間で全探索。Argon2id / bcrypt に変える
  • 「Password を送る前にクライアント側で Hash すれば TLS は不要」 — その Hash が Credential になるだけ。盗聴者はその Hash を送れば通る（Pass-the-Hash）。TLS は必須
  • 「Password の定期変更を強制する」 — NIST SP 800-63B は定期変更の強制を推奨しない。ユーザーは末尾の数字を1つ増やすだけになり、漏洩リストと照合した方が有効

05 JWT — 署名付きの「自己申告書」

結論から。JWT は「私は user_123 です」という自己申告に、発行者の署名を貼り付けたものだ。中身は誰でも読める。暗号化されていない。それでも信用できるのは、署名が一致する限り、発行者以外の誰も中身を書き換えられなかったことが数学的に保証されるからだ。Session（ch3）は「サーバーが台帳を見る」ことで Identity を確定した。JWT は「サーバーが署名を確かめる」ことで確定する。台帳が要らない代わりに、台帳が無いことで生じる問題（即時無効化・Claim 更新）を全部引き受ける。

① Base64URL は暗号ではない — 「読める」ことを最初に体で理解する

Base64URL は、バイナリを URL に安全に載せるための表現変換にすぎない。鍵もパスワードも無い。だから次のコマンドで誰でも中身を読める。

  • Base64URL と Base64 の違い：+→-、/→_、末尾の = を除去。URL やヘッダに載せたときにエスケープが要らないようにしただけ
  • したがって、Payload に入れてよいもの：user_id、role、有効期限、発行者。入れてはいけないもの：パスワード、メールアドレス以上の個人情報、内部の秘密。「Token は本人しか持たない」は通信経路とブラウザが完璧なときしか成り立たない
  • 解釈：「JWT は暗号化されている」という誤解は、eyJ という見慣れない文字列が原因だ。eyJ は {" を Base64 したときに必ず現れる先頭3文字。JWT を見たら「これは読める JSON だ」と反射で思えるようになること

② Claims — Payload の「予約語」を全部覚える

Payload の中身は自由な JSON だが、RFC 7519 が定めた予約 Claim がある。これらは検証ライブラリが自動で見るため、名前を間違えると検証がスキップされる。

図5-2 署名検証。信用の根拠は「DB に居る」ではなく「鍵の持ち主が書いた文書が、1バイトも変わっていない」である。

③ 信用の連鎖をズームする — 「署名が正しい」から「user_id=123」までの3ステップ

署名検証が通っただけでは、まだ user_id=123 とは言えない。サーバーは暗黙に次の3段の推論をしている。この3段を言語化できるかが、JWT を理解しているかの境目だ。

  1. 署名が一致する → この HEADER.PAYLOAD は、鍵の持ち主が署名した時点から1バイトも変わっていない（完全性・Integrity）
  2. 鍵の持ち主は Auth Server だけ → この文書を作ったのは Auth Server である（発行者の真正性・Authenticity）。これは前提であって検証結果ではない。Secret が漏れていればこの段が崩れる（ch6）
  3. Auth Server は、Password 検証（ch2）を通ったユーザーにしか sub を書かない → sub=123 は本人である（ここで初めて Identity）。これも前提。Auth Server にバグがあれば崩れる

つまり JWT の信用 = 署名の数学 × 鍵管理の運用 × 発行時の認証の正しさ。数学の部分だけが「検証」で、残り2つは「信頼」だ。JWT を導入すると、信頼の対象が「自分の Session Store」から「Auth Server と鍵」に移る。楽になるのではなく、移るだけである。

④ 実例 — Go で JWT を発行・検証する（golang-jwt/jwt/v5）

発行側と検証側を分けて書く。実務では発行は Auth Server、検証は各 API Server の Middleware に置く。

  • なぜ WithValidMethods が必須か：Header の alg は攻撃者が書き換えられる。alg: none（署名なし）や、RS256→HS256 すり替え（Public Key を Secret として HMAC を作る）は、この1行が無いと成立する。「Header に書いてある alg で検証する」は自殺行為。詳細は ch22
  • なぜ aud を検証するか：同じ Auth Server が「決済API向け」「予約API向け」の JWT を発行する場合、aud 検証が無いと片方の Token でもう片方に入れる。Token の用途を Token 自身に書き、受け手が自分宛てか確認する
  • なぜ Leeway を入れるか：Auth Server と API Server の時計は数秒ズレる。ズレを許容しないと「発行直後なのに期限切れ」が散発する。30秒が相場

図5-3 JWT のシーケンス。8 で Reservation API は誰にも問い合わせていない。これが「Stateless」の実体であり、同時に「即時 Revocation ができない」理由でもある。

⑤ JWS と JWE — 「署名付き JWT」と「暗号化 JWT」は別物

本章で扱ってきた HEADER.PAYLOAD.SIGNATURE の3分割は正確には JWS（JSON Web Signature）だ。JWT にはもう一つの形式、JWE（JSON Web Encryption）がある。5分割で、Payload が本当に暗号化されている。

JWS（一般に「JWT」と呼ばれるもの）
  • 形式：header.payload.signature（3分割）
  • Payload は誰でも読める
  • 目的：改ざん検知と発行者確認
  • 用途：OAuth Access Token、OIDC ID Token、API 間の認証
  • 受け手が「読んで検証する」前提
JWE（暗号化 JWT）
  • 形式：header.encrypted_key.iv.ciphertext.tag（5分割）
  • Payload は鍵が無いと読めない
  • 目的：機密性（＋AEAD による完全性）
  • 用途：Auth.js の JWT strategy の Cookie（ch12）は JWE。alg: dir, enc: A256GCM
  • 発行者と受け手が同一（自分で暗号化して自分で復号）の場面で使われることが多い

先取り：ch12 で Auth.js の Cookie を decode しようとして「JSON にならない」と困る人が多い。それは JWE だからだ。Auth.js は AUTH_SECRET から導出した鍵で Payload を暗号化しており、Base64 decode だけでは読めない。「JWT は読める」と本章で言ったのは JWS の話であり、Auth.js は JWE を使っているという2点を分けて覚える。

⑥ よくある誤解と事故

  • 「JWT だから安全」：JWT が保証するのは改ざん検知だけ。盗まれた JWT は期限まで本人と完全に同じ権限で使える。Password を知らなくてもログインできる。Session ID が盗まれたのと同じことが起きるが、Session は Store から消せる。JWT は消せない
  • Payload をデコードして「検証した」と思う：jwt.decode() 系の関数は署名を見ない。Node の jsonwebtoken には decode（検証なし）と verify（検証あり）があり、前者で認可判定をしている事故が現実に多い
  • exp を長くして「ログイン維持」を実現する：exp=30日 の JWT は「30日間無効化できない Credential」である。ログイン維持は Refresh Token（ch14）で行う
  • role を Payload に入れ、権限変更を即時反映したい：JWT は発行時点のスナップショット。role を降格しても、手元の JWT には exp まで admin と書いてある。即時反映が要件なら role は Payload に入れず、リクエストごとに DB を見る（そのとき「JWT である意味」を再考する）
  • 1つの Secret で複数用途の JWT を発行し、aud を検証しない：メール確認リンク用 JWT を Access Token として受け入れてしまう

4. Serverが検証するもの

5. Identity の特定方法

一致すれば sub を採用。DB 不要

① HMAC とは何か — 「鍵付きハッシュ」の1行理解

HMAC-SHA256 は、SHA256(key ⊕ opad ‖ SHA256(key ⊕ ipad ‖ message)) という2重ハッシュだ。細部は覚えなくてよい。覚えるべき性質は3つ。

  • 鍵が無いと計算できない：message だけ知っていても正しい MAC は作れない（ハッシュの一方向性）
  • 鍵があれば誰でも計算できる：発行者と検証者に非対称性が無い。これが HS256 のすべての長所と短所の源
  • message が1bit 変わると MAC は全く別物になる：改ざん検知の根拠

解釈：HMAC は「電子署名」ではなく「メッセージ認証コード（MAC）」だ。署名には「署名者だけが作れ、第三者が検証できる」という否認防止の性質があるが、MAC には無い。「JWT の署名」と呼ばれているものは、HS256 の場合は厳密には署名ではない。用語の混同が設計判断を狂わせるので、ch8 の比較表で整理する。

② 実例 — Go で HS256 を発行・検証する

  • なぜ 256bit 以上か：攻撃者は正規の JWT を1つ入手すれば、サーバーに一切アクセスせず手元で Secret を総当たりできる（hashcat の mode 16500）。ネットワーク越しの Rate Limit は無意味。鍵空間の大きさだけが防御になる
  • なぜ定数時間比較か：== で比較すると、先頭何バイトが一致したかで処理時間が変わり、タイミング攻撃で1バイトずつ署名を当てられる。ライブラリは hmac.Equal を使っている。自作するな

③ メリットと問題を、構造から導く

メリット（N=1 のとき最大化）
  • シンプル：鍵は1本の []byte。鍵ペア生成・PEM・JWKS のどれも要らない
  • 高速：HMAC-SHA256 は RSA 署名の数百倍速い。1コアで毎秒数十万回。ES256 と比べても数倍速い
  • Token が短い：署名が 32 byte（Base64URL で 43 文字）。RS256 は 256 byte
  • 発行と検証が同一プロセスなら、そもそも「配布」が発生しない
問題（N≥2 で顕在化）
  • Secret 配布：全検証サービスに安全に届け、環境ごとに揃え、ローテーション時に同時更新する運用が要る
  • 漏洩面の拡大：どれか1サービスの侵害で、全サービス向けの任意 JWT が偽造可能になる
  • 全サービスが Token 生成可能：本来「検証だけ」でよい reservation-service が、admin Token を発行できる。最小権限の原則に反する
  • 否認防止が無い：「この JWT は Auth Service が発行した」と証明できない。検証者の誰かが作ったかもしれない
  • 外部に検証させられない：外部パートナーに JWT を検証させるには Secret を渡す = 発行能力を渡す

④ Secret Rotation が難しい理由をズームする

Secret を回す（Rotation）とき、次の状態が同時に成立しなければならない。

  1. 旧 Secret で署名されたまだ有効な JWT を、全検証者が受け入れ続ける
  2. 新 Secret で署名された JWT を、全検証者が受け入れる
  3. 発行者が新 Secret で署名を始める
  4. 旧 JWT がすべて exp を過ぎたら、旧 Secret を全検証者から削除する

つまり検証者は一定期間、複数の Secret を持って順に試す必要がある。HS256 の JWT Header には「どの Secret か」を示す標準的な仕組みが無い（kid は使えるが、共通鍵に kid を付ける運用は稀）。結果、検証コードは「全 Secret で HMAC を計算して1つでも一致すれば OK」になり、ローテーション中は検証コストが倍になる。

図6-3 HS256 では、侵害された検証者から流出した Secret で作られた Token は、Auth Service が発行したものと数学的に区別不能。ログにも「正規の JWT で認証成功」と残る。

⑤ よくある誤解と事故

  • 「HS256 は弱いアルゴリズム」：違う。HMAC-SHA256 自体は十分に強い。弱いのは鍵の配置。単一サービスなら HS256 を選ぶのが正しい。RS256 を単一サービスで使うのは無駄に遅くて複雑
  • Secret をフロントエンドの環境変数に入れる：NEXT_PUBLIC_JWT_SECRET はバンドルに埋め込まれ、全ユーザーに配布される。全ユーザーが admin Token を発行できる。実際に起きている事故
  • Secret をリポジトリにコミット：.env を .gitignore し忘れる。Git 履歴から消しても、クローン済みの人には残る。漏れたら即ローテーション
  • 開発環境と本番で同じ Secret：開発者全員が本番 admin Token を発行できる状態
  • 「Secret を Vault に入れたから安全」：Vault は「保管」の問題を解く。「検証者全員が発行できる」という構造の問題は解かない。構造を解くのは ch7

2. 認証する側

4. Serverが検証するもの

kid に対応する Public Key で Verify(pub, h.p, sig)、および exp/iss/aud

検証成功 → sub を採用。発行者が Auth Server であることも同時に確定する

① 「Public Key を公開しても偽造できない」のはなぜか

直感に反する部分なのでここで止まる。詳細な数学は ch8 だが、JWT の文脈で必要な理解は次の3点。

  • 鍵ペアは一方向の関係：Private Key から Public Key は一瞬で計算できる。逆は現実的な時間では不可能（RSA なら 2048bit の合成数の素因数分解、EC なら離散対数問題）。「不可能」は証明されていないが、数十年の攻撃に耐えている事実がある
  • 署名と検証は別の計算：署名は Private Key を使う演算、検証は Public Key を使う演算。検証のアルゴリズムを知っていても、署名を作る鍵が無ければ正しい署名は作れない。ch6 の HMAC は「検証 = もう一度署名する」だったが、RSA では「検証 ≠ 署名」
  • だから Public Key は公開してよい：名前通り。Web で誰でも取れる場所（JWKS endpoint）に置いてよい。Google は https://www.googleapis.com/oauth2/v3/certs に全世界向けに公開している

解釈：「秘密鍵」「公開鍵」という日本語は正確だ。秘密にするのは1つだけ、もう1つは公開してよい。「暗号鍵」と一括りにすると、両方隠さなければならない気がしてくる。運用設計のミス（Public Key を Secrets Manager に入れて配布を面倒にする等）はこの言葉の混乱から生まれる。

③ 実例 — Go で JWKS を取得・キャッシュ・kid で選択する（API Server 側）

  • なぜ未知 kid で再取得するか：ローテーション直後、新鍵で署名された JWT が来る。キャッシュには無い。「未知 kid = 鍵が回ったかもしれない」と解釈して1回だけ取り直す
  • なぜ再取得をレート制限するか：攻撃者が kid: "xxx" をランダムに変えた JWT を送り続けると、無制限実装は毎回 Auth Server を叩く。「未知 kid でも1分に1回しか取り直さない」で防ぐ
  • 実務では：github.com/MicahParks/keyfunc や lestrrat-go/jwx がこれを実装している。自前実装は理解のためで、本番はライブラリを使う。ただし「何をしているか」を知らずに使うと、Google の JWKS が返す Cache-Control の意味が分からずデバッグで詰む

④ RS256 vs ES256 — 選び方

鍵長（同等の安全性）2048 bit（3072 推奨に移行中）256 bit256 bit
署名サイズ256 byte（Base64URL 342 文字）64 byte（86 文字）64 byte
署名速度遅い（〜1ms）速い（〜0.1ms）最速

解釈：JWT の「検証は頻繁、署名は稀」という非対称性を考えると、検証が速い RS256 は理にかなっている。ES256 の利点はサイズ。Cookie の 4KB 制限や、毎リクエストのヘッダ帯域を気にするなら ES256。迷ったら RS256、理由は互換性。

⑤ Algorithm Confusion — 公開鍵方式にしても消えない罠（ch22 で詳述）

RS256 にしても、検証コードが Header の alg を信用していると、次の攻撃が成立する。

  1. 攻撃者が JWKS から Public Key（PEM 文字列）を取得する。公開情報なので合法
  2. 攻撃者が Header を alg: HS256 に書き換え、Public Key の PEM 文字列そのものを HMAC の Secret として署名する
  3. 脆弱な検証コード：「alg が HS256 だから HMAC で検証しよう。鍵は… 設定されている Public Key を渡す」→ 攻撃者と同じ鍵・同じアルゴリズムで計算 → 一致

golang-jwt v5 は *rsa.PublicKey を HMAC の鍵として受け取ると型エラーで拒否するので、鍵を正しい型で渡していれば防げる。だが PEM を []byte のまま渡す実装は現実に多い。「検証側が alg を決める。Token に決めさせない」を原則にする。

図7-3 Go API は Google の Private Key を知らないし、Google に「この Token は本物か」と聞いてもいない。公開されている Public Key だけで、Google が署名したことを確定している。

  • Public Key を Secrets Manager に入れて配布を面倒にする：公開してよい鍵を秘匿すると、ローテーションのたびに全サービスへの再配布が発生し、ch6 と同じ運用負荷になる。JWKS で公開せよ
  • Private Key を全 API Server に配る：「検証のために鍵が要る」と思い込み、Private Key の PEM を配ってしまう。これで RS256 は HS256 と同じ漏洩面になる。検証に要るのは Public Key だけ
  • JWKS を HTTP で取得する：中間者が偽 JWKS を返せば、攻撃者の Private Key で署名した JWT が「正規」になる。JWKS 取得は HTTPS 必須、かつ証明書検証を無効化しない（ch16）
  • kid を検証せず「最初の鍵」で試す：ローテーション中に旧鍵で署名された JWT が全滅する
  • 「公開鍵方式にしたから Revocation できる」：関係ない。RS256 でも JWT は exp まで有効。鍵ローテーションで全 Token を無効化はできるが、個別無効化はできない（ch13-14）

08 共通鍵暗号と公開鍵暗号 — JWT・SSH・TLS の共通の土台

結論から。認証で使う暗号は「秘密を守る（暗号化）」と「本人性と完全性を示す（署名 / MAC）」の2用途しかない。そして鍵の持ち方は「1本を共有する（共通鍵）」と「2本1組で片方だけ隠す（公開鍵）」の2種類しかない。2×2 = 4 通りの組み合わせを混同せずに言えれば、JWT（ch5-7）、SSH（ch15）、TLS（ch16）、mTLS（ch17）、AWS SigV4（ch19）はすべて同じ部品の組み合わせとして読める。この章は認証方式ではなく部品の章だ。

1. 誰が認証されるか

（部品の章）署名の場合：Private Key の所有者。MAC の場合：共有鍵を持つ誰か

2. 認証する側

署名：Public Key を持つ誰でも。MAC：同じ共有鍵を持つ者

3. Clientが持つCredential

署名：Private Key（送らない）。MAC：共有鍵（送らない）。送るのは署名 / MAC 値

4. Serverが検証するもの

署名：Verify(pub, msg, sig)。MAC：HMAC(key, msg) == mac

5. Identity の特定方法

「この鍵を持つ者」= 事前に登録された主体。鍵 → 主体の対応表がどこかに要る

図8-1 共通鍵は「速いが配るのが難しい」、公開鍵は「配れるが遅い」。だからほぼ全てのプロトコルは公開鍵で共通鍵を配り、共通鍵で本文を守る。

① 公開鍵暗号の2用途を絶対に混同しない — 「暗号化」と「署名」は鍵の使う向きが逆

ここが本章で最も重要で、最も混同される点。どちらの鍵で「掛け」、どちらの鍵で「外す」かが、目的によって反転する。

暗号化（Confidentiality）— 「Bob だけが読める」
  • Public Key で暗号化 → Private Key で復号
  • 誰でも（Bob の Public Key で）暗号化できる
  • Bob だけが（Private Key で）読める
  • 守るもの：内容の秘密
  • 使う場面：鍵交換（古い TLS の RSA 鍵交換）、PGP メール、JWE（RSA-OAEP）
  • 認証には直接は使わない。誰が暗号化したか分からないから
署名（Authenticity + Integrity）— 「Alice が書いた、改ざんなし」
  • Private Key で署名 → Public Key で検証
  • Alice だけが（Private Key で）署名できる
  • 誰でも（Alice の Public Key で）検証できる
  • 守るもの：誰が書いたか・変わっていないか。内容は隠さない
  • 使う場面：JWT RS256/ES256、SSH 認証、TLS 証明書、コード署名、Git commit 署名
  • 認証の主役はこちら。本書で「公開鍵」と言うときは 9 割これ

図8-2 左は「秘密を届ける」、右は「本人性を示す」。認証の文脈で登場するのはほぼ右の図。左を「認証」と誤解すると SSH や JWT の説明が全部おかしくなる。

② なぜ Public Key を公開しても安全なのか — 一方向性関数

「Public Key から Private Key を逆算できないのはなぜか」に、実装者が知っておくべき粒度で答える。

  • RSA：Private Key は2つの巨大な素数 p, q（各 1024bit）。Public Key はその積 n = p × q（2048bit）と指数 e。掛け算は一瞬、素因数分解は現在の計算機で宇宙の年齢より長くかかる。署名は「n を法とする d 乗」、検証は「e 乗」で、d は p, q を知らないと計算できない
  • 楕円曲線（ECDSA / Ed25519）：Private Key は乱数 d。Public Key は Q = d × G（曲線上の点 G を d 回足したもの）。d 回足すのは速い（倍加と加算で log 回）、Q と G から d を求める（離散対数）のは総当たりしか無い。同じ安全性を RSA の 1/8 の鍵長で達成できる
  • 共通の構造：「片方向は多項式時間、逆方向は指数時間（と信じられている）」関数。これを一方向性関数、逆方向を秘密の情報で可能にするものを落とし戸（trapdoor）付き一方向性関数と呼ぶ
  • 事実と解釈を分ける：「不可能」は証明されていない。P≠NP も未証明。安全性は「数十年間、世界中の数学者が攻撃して破れていない」という経験的事実に立っている。量子計算機（Shor のアルゴリズム）は RSA と EC の両方を破るため、耐量子暗号（ML-DSA 等）への移行が 2030 年代に向けて進んでいる。今日の設計判断には影響しないが、「鍵アルゴリズムは差し替え可能に」という設計原則の根拠にはなる

⑤ 鍵交換（ECDH）— 「共通鍵をネットワーク越しに合意する」魔法の正体

TLS（ch16）を理解する最後の部品。「Alice と Bob は盗聴されている回線しか無いのに、どうやって同じ共通鍵を手にするのか」。答えが Diffie-Hellman 鍵交換で、現代の TLS 1.3 は楕円曲線版（ECDHE, X25519）を使う。

  1. Alice は乱数 a を選び、A = a × G を Bob に送る（G は公開の基準点）
  2. Bob は乱数 b を選び、B = b × G を Alice に送る
  3. Alice は a × B = a × b × G を計算。Bob は b × A = b × a × G を計算。両者は同じ点 abG に到達する
  4. 盗聴者は A, B, G を全部見ているが、a も b も知らない。A から a を求めるのは離散対数問題で不可能。よって abG を計算できない
  5. abG をハッシュして AES の Session Key にする。以降は共通鍵暗号で高速に通信

ただし ECDH 単体は認証しない。中間者が Alice に対して Bob を演じ、Bob に対して Alice を演じれば、双方と別々の鍵を合意できる。「今鍵交換している相手が本当に Bob か」を保証するのが証明書と署名（ch16）。ここで暗号化用途（鍵交換）と署名用途（本人確認）が合流する。

図8-3 鍵交換（暗号化用途の公開鍵）で共通鍵を合意し、署名（署名用途の公開鍵）で相手が本物だと確認する。ch16 の TLS は、この図に「証明書チェーン」を足しただけである。

⑥ よくある誤解と事故

  • 「JWT は Private Key で暗号化されている」：署名であって暗号化ではない。Payload は誰でも読める。ch5 の decode 実演を思い出すこと
  • 「Public Key で署名する」「Private Key で検証する」：向きが逆。Private を使う操作 = 本人しかできない操作、と覚え直す
  • SHA-256 でパスワードを保存する：Hash は速すぎる。GPU で毎秒数百億回試せる。パスワードには意図的に遅い bcrypt / Argon2（ch2）。「ハッシュ化した」の中身を言えるか

09 API Key / API Token — プログラムを認証する最小の Credential

結論から。API Key とは「長寿命で、認可フローを経ずに手渡しされる、共有秘密（shared secret）型の Credential」である。Session ID と構造は同じで、違いは「人間のブラウザではなくプログラムが持つ」「ログイン操作なしに発行される」「寿命が長い」の3点。サーバー側の検証は Password と同じく「ハッシュして DB と比較する」だけだ。だから API Key を受け取ったサーバーが「誰の Key か」を知る方法は、Session Store の lookup とまったく同じ原理になる。特別な暗号技術は登場しない。

② なぜ API Key は「平文で DB に保存してはいけない」のか — Password と同じ理由、しかし関数は違う

Password（ch2）と同じく、DB が漏れたとき Key がそのまま使えてしまうのが平文保存の問題だ。API Key は Password より被害が大きい。Password は人間が覚えているので漏洩後に変更を促せるが、API Key は連携先の .env に埋まっていて、漏れたことに誰も気づかない。

平文保存（sk_live_… をそのまま列に）
  • 検索は WHERE key = ? で単純
  • 管理画面で Key を「再表示」できてしまう → 便利だが、内部犯・スクショ・ログ経由で漏れる
  • DB dump / バックアップ / read replica / BI ツール経由でそのまま流出
  • DB 漏洩 = 全 API クライアントの Credential 漏洩
ハッシュ保存（SHA-256(key) を列に）
  • 検索は WHERE key_hash = SHA256(?)。決定的ハッシュなので index が効く
  • 発行時に一度だけ表示。以後は誰も（運営者も）元の Key を知れない
  • DB が漏れてもハッシュから Key は復元できない（Key が十分ランダムなら）
  • DB 漏洩 ≠ Credential 漏洩。Stripe / GitHub / AWS はすべてこの方式

ここが Password と違う重要な点：Password は bcrypt / Argon2 で「遅く」ハッシュする（ch2）が、API Key は SHA-256 で「速く」ハッシュしてよい。理由は2つ。

  • API Key は十分にランダム（256bit）なので、辞書攻撃・総当たりが不可能。Password は人間が選ぶので弱い → 遅いハッシュで守る必要があった。Key は crypto/rand で生成されるので、遅くする理由がない
  • bcrypt はソルト付きで非決定的なので、index 検索できない。bcrypt(key) は毎回異なる値を返すため WHERE key_hash = ? が書けない。全行を取り出して1件ずつ bcrypt.Compare する羽目になり、Key が1万件あれば1万回の bcrypt（各 100ms）= 1000 秒。API のリクエストごとには不可能

結論：人間が選ぶ秘密（Password）は遅いハッシュ、機械が生成した秘密（API Key / Session ID / Refresh Token）は SHA-256。この区別を間違えると、どちらの方向でも事故になる。

図9-2 「ハッシュして保存」は共通でも、関数は秘密の出自で変える。bcrypt で API Key を保存すると検索不能になり、SHA-256 で Password を保存すると辞書攻撃で割られる。

⑤ Rate Limit は Identity 単位で — IP ではなく api_client_id

認証の直後に置くべきものが Rate Limit だ。Identity が確定したからこそ、公平な制限ができる。IP 単位の制限は NAT 越しの正規クライアントを巻き込み、逆に攻撃者は IP を変えて回避する。

middleware の順序は TLS終端 → 認証（API Key）→ Rate Limit → Authorization（scope）→ handler。認証前に Rate Limit を置くと未認証の総当たりには効くが、Identity 単位の公平性は得られない。両方置くのが正解で、前段は IP 単位の粗い制限、後段は client_id 単位の精密な制限になる。

10 OAuth 2.0 — Delegated Authorization。ログイン方式ではない

結論から。OAuth 2.0 は「ユーザーが、自分のリソースへの限定的なアクセス権を、パスワードを渡さずに第三者アプリへ委譲する」ための仕組みである。認証（Authentication）のプロトコルではない。「Login with Google」が OAuth に見えるのは、その上に OpenID Connect（ch11）が乗っているからで、OAuth 単体が答える質問は「このアプリは何をしてよいか」であって「このユーザーは誰か」ではない。この区別を曖昧にしたまま Access Token を「ログイン済みの証」として扱うと、ch11 で説明する脆弱性をそのまま踏む。

ホテルの比喩で言えば、OAuth は「バレーキー」だ。 宿泊者（Resource Owner）が、駐車係（Client）に車（Resource）を動かしてほしい。マスターキー（Password）を渡せば動かせるが、トランクも開けられるし合鍵も作れる。だからバレーキー（Access Token）を渡す。エンジンはかかるがトランクは開かない（scope）。数時間で無効になる（expiration）。そして重要なのは、バレーキーを持っていても、駐車係が「この車の所有者」だと名乗れるわけではない。バレーキーは「この車を動かしてよい」を証明するだけで、「あなたは誰か」は証明しない。これが OAuth と OIDC の境界だ。

1. 誰が認証されるか

厳密には「誰も認証されない」。Client（アプリ）が Resource Owner から委譲された権限が確認される。Authorization Server の内部では Resource Owner のログインが起きるが、それは OAuth の外側

2. 認証する側

Access Token を検証するのは Resource Server（例：Google Calendar API）。Token を発行するのは Authorization Server（例：accounts.google.com）

3. Clientが持つCredential

Access Token（Bearer）。取得のために一時的に Authorization Code、更新のために Refresh Token。Client 自身の身元証明として client_id + client_secret

4. Serverが検証するもの

Access Token の有効性（署名 or introspection）、有効期限、scope にこの操作が含まれるか、aud がこの Resource Server か

5. Identity の特定方法

Token に紐づく「Resource Owner + Client + scope」の組。sub（誰の代理か）と client_id（どのアプリか）の2つの主体が同時に確定する

② なぜ Implicit Flow は死んだのか — Token を front channel に流した代償

OAuth 2.0 の初版（2012）には、SPA 向けに「Code を省略して Access Token を直接 URL fragment で返す」Implicit Flow があった。https://app/callback#access_token=ya29… という形だ。当時の SPA は CORS が未整備で back channel を持てなかったからだが、2019 年の OAuth 2.0 Security Best Current Practice で非推奨、OAuth 2.1 では削除された。

  • Token が Browser 履歴・Referer・ログに残る。fragment はサーバーには送られないが、JavaScript には見えるし、ブラウザ履歴には残る
  • Token の受け取り手を検証できない。Code なら「/token で client_secret（or verifier）を出せる者だけ」が Token 化できるが、Implicit では URL に届いた瞬間に Token が完成している。redirect_uri の検証がすり抜ければ即漏洩
  • Refresh Token を返せない。長寿命の秘密を front channel に流すのは論外なので、Implicit では Access Token 切れ = 再認可。UX が悪く、結果として Access Token を長寿命にする誘惑が生まれる
  • 代替：Authorization Code + PKCE。PKCE は元々モバイル向けだったが、SPA でも「client_secret を持てない Client」の問題を同じ方法で解決できると分かり、公開クライアントの標準になった。Auth.js も内部で PKCE を使う

③ Authorization Code Flow + PKCE — 完全シーケンス

これが現代の OAuth の唯一の「ユーザー同意フロー」だ。Auth.js の Google Provider も、モバイルアプリも、SPA も、全部これ。10 ステップを暗記するのではなく「どの経路（front / back）を、何が、なぜ通るか」で覚える。

図10-3 ピンクの矢印が front channel（Browser 経由）、緑が back channel（サーバー間）。秘密（client_secret / verifier / Access Token / Refresh Token）は緑の線にしか乗らない。

④ state と PKCE — 2つの「ランダム値」はそれぞれ何を防ぐのか

どちらも Client が生成するランダム値だが、防いでいる攻撃が違う。混同すると「PKCE を使っているから state は要らない」という誤った判断になる（実際には OIDC の nonce も含めて 3 つの役割がある。ch11）。

⑥ Access Token は opaque でもよい — Resource Server が「誰の Token か」を知る2つの方法

Access Token の形式は OAuth 2.0 の仕様では規定されていない。Google の ya29.… は意味のないランダム文字列（opaque）、Auth0 や Keycloak はデフォルトで JWT を返す。Resource Server にとって「この Token が誰の・どの scope か」を知る方法は2つに分かれ、これが ch13 の「Database Session vs JWT Session」とまったく同じ構造になる。

opaque Token + Introspection（RFC 7662）
  • Token はランダム文字列。AS の DB に token → {sub, client_id, scope, exp} の行がある
  • Resource Server は毎回（or キャッシュして）AS の /introspect に問い合わせる
  • 即時 Revocation 可能（行を消せば次の introspection で active:false）
  • RS → AS のネットワーク往復。AS がボトルネック
  • ch3 の Session Store lookup と同じ構造
JWT Access Token（RFC 9068）
  • Token 自体に {sub, client_id, scope, exp, aud, iss} が入り、AS の秘密鍵で署名
  • Resource Server は JWKS で公開鍵を取り、ローカルで署名検証（ch7）
  • AS への問い合わせ不要。水平スケールしやすい
  • exp までは Revocation できない。だから短命（5〜15分）にする
  • ch5〜7 の JWT 検証と同じ構造

Client（自社アプリ）は Access Token の中身を見てはいけない。opaque か JWT かは AS と RS の間の契約であって、Client は「不透明な文字列を Bearer で送る」だけ。Google の Access Token を decode しようとするコードを見たら、それは設計の誤解のサインだ。ユーザー情報が欲しいなら OIDC の ID Token（ch11）を使う。

⑦ Client Credentials Grant — ユーザーのいない OAuth（ch18 への橋）

OAuth には「ユーザーの同意」が登場しない Grant もある。Client Credentials Grant は、Client 自身が Resource Owner でもある場合、つまりサービス間通信のための Grant だ。フローは1ステップ。

  • API Key（ch9）との違い：API Key は長寿命の Credential をそのまま毎回送る。Client Credentials は長寿命の client_secret を短命の Access Token に交換してから送る。Resource Server は client_secret を一切見ない
  • 利点：Resource Server が複数あっても、それぞれが client_secret を知る必要がない。JWT なら AS の公開鍵だけで検証できる。secret の漏洩面が AS 1箇所に集まる
  • Identity：sub は client_id（例：sub=svc-reservation）。「誰の代理か」ではなく「どのサービスか」が確定する
  • ch18 で mTLS / IAM / Signed JWT と横並びで比較する

⑧ よくある誤解と事故

  • 「OAuth でログインを実装した」 — OAuth の Access Token を「ログインの証」として扱うのは、ch11 で説明する Token 置換攻撃に脆弱。ログインには OIDC の ID Token を使う。Auth.js が Provider を「OAuth」と「OIDC」で区別しているのはこのため
  • 「redirect_uri の検証を前方一致にする」 — https://pms.example.com/ で前方一致させると https://pms.example.com/open-redirect?to=evil が通り、Code が攻撃者に流れる。AS 側の完全一致検証が OAuth の生命線。自社で AS を作るなら絶対に妥協しない
  • 「state を省略する」 — 「PKCE があるから」「ログイン済みだから」は理由にならない。図10-4 の左側の攻撃はどちらでも防げない
  • 「Access Token を Browser に返す」 — Client が自社サーバーなら、Token はサーバー側で保管し、Browser には自社 Session（Cookie）だけを渡す。Auth.js のデフォルトも Access Token を Cookie の JWT に入れないのはこの理由（ch12）
  • 「Refresh Token を平文で DB 保存」 — Refresh Token は「ユーザーの Google カレンダーへの永続的アクセス権」そのもの。ch9 の API Key と同じ理屈で保護する。ただし Refresh Token は「送信する」必要があるので、ハッシュではなく暗号化（AES-GCM + KMS）で保存する
  • 「scope を広く取る」 — 「後で必要になるかもしれないから」で calendar（全権）を要求すると、同意率が下がり、漏洩時の被害が広がる。必要な最小 scope（calendar.events）を、必要になった時点で追加要求する（incremental authorization）

Q4. State はどこ？opaque なら AS の DB（introspection で参照）。JWT なら Token 内（stateless）。Code / state / verifier は一時的に AS と Client に
Q5. 期限はどこで管理？expires_in（Token 応答）/ JWT の exp。短命。Refresh Token で延命（ch14）
Q6. どう Identity へ変換？introspection 応答 or JWT claim の sub（誰の代理か）+ client_id（どのアプリか）+ scope（何を許されたか）
Q7. どう Revocation する？ユーザーが AS の設定画面で取り消す / Client が /revoke を叩く。opaque は即時、JWT は exp 待ち + Refresh Token 失効

② なぜ ID Token を API アクセスに使ってはいけないのか

「ID Token も JWT で sub が入っているなら、これを Bearer で自社 API に送ればいいのでは？」という発想は自然だ。実際、初期の Auth0 のチュートリアルにさえ混同があった。やってはいけない理由は4つあり、どれも「Token の宛先（aud）が違う」という1点に集約される。

  • aud が Client ID である。ID Token の aud は「pms-web-client」であって「pms-api」ではない。自社 API が aud を正しく検証すると、ID Token は必ず拒否される。「aud を検証しない」で回避したら、それは 別のアプリ向けに発行された ID Token を自社 API が受け入れるということ。攻撃者が自分のアプリで被害者に Google ログインさせ、得た ID Token を自社 API に投げれば通る（Token 置換攻撃）
  • scope が無い。ID Token には「何をしてよいか」の情報が無い。「Google が認証した」以上のことを言っていないので、API 側の認可判断の材料にならない
  • Revocation できない。ID Token には対応する introspection / revoke endpoint が無い。exp まで有効。Access Token なら AS 側で取り消せる
  • Resource Server（自社 API）にとって Google は「認証者」ではない。自社 API が信じるべきは「自社の Session / 自社発行の Token」であって、Google の言い分をそのまま API 層で信じる設計は、Identity 変換（Google の sub → 自社 user_id）を毎リクエスト API 層で行うことになる。責務が Client 層から漏れている

正しい配置：ID Token は Client（Next.js の Auth.js）が受け取り、その場で検証し、自社 user_id に変換し、自社の Session（Cookie）または自社発行の JWT を作る。自社 API は自社の Credential だけを検証する。Google の ID Token は callback ハンドラの中で寿命を終える。

⑥ よくある誤解と事故

  • 「GitHub ログインも OIDC」 — GitHub は OIDC を実装していない（純 OAuth 2.0）。ID Token を返さないので、Auth.js は Access Token で /user API を叩いて profile を組み立てる。「OAuth で認証している」例外的なケースで、GitHub が Access Token に紐づくユーザーを返す API を提供しているから成立する。同じ穴（aud 不在）は理論上あるので、GitHub の Access Token を自社 API に送る設計は論外
  • 「ID Token を Cookie に入れて Session にする」 — ID Token は Google の鍵で署名されている。自社が読むことはできるが、自社の Session 状態（role の変更、accommodation の切り替え）を書き込めないし、Google の exp（1時間）に縛られる。Auth.js が「ID Token を検証して、自社の鍵で暗号化した別の JWT を Cookie に入れる」のはこの理由（ch12）
  • 「email で users を検索してログイン」 — 改姓・ドメイン変更で別人扱いになる。email_verified=false の IdP 経由で乗っ取られる。sub で検索し、email は表示に使う
  • 「nonce を省略する」 — Code Flow なら nonce は「推奨（SHOULD）」だが、省くと callback の再送でログインが再現できる。Auth.js はデフォルトで付ける。自前実装で省く理由はない
  • 「OIDC = SSO」 — OIDC は「Google での認証結果を自社が信じる」仕組み。SSO（一度のログインで複数アプリに入る）は、その上に「IdP 側の Session」が存在することで実現される副産物。「Google にログインしたままなら PMS にも即入れる」のは Google 側の Session Cookie が生きているからで、PMS 側の Session とは無関係。Logout の設計を間違える典型の原因（PMS からログアウトしても Google の Session は残るので、再度ボタンを押せば即再ログインされる）

ズーム：session.user はどこから突然出てくるのか — JWT strategy の内部処理

Server Component で const session = await auth() と書くと session.user.id が手に入る。これは「Cookie を復号して callbacks を2回通した結果」であり、その6ステップを追う。

  1. Cookie 取得：リクエストヘッダから __Secure-authjs.session-token（HTTPS）または authjs.session-token（HTTP）を読む。なければ session = null で終わり
  2. 鍵導出：AUTH_SECRET をそのまま鍵にはしない。HKDF（HMAC-based Key Derivation Function）で salt = cookie名、info = "Auth.js Generated Encryption Key (<cookie名>)" を混ぜて 256bit の鍵を作る。だから Cookie 名を変えると既存 Session は全部無効になる
  3. 復号：jose の jwtDecrypt(token, key)。A256GCM の認証タグが合わなければ例外（= 改ざん or 別 Secret）。exp が過去なら例外。成功すると payload = { sub: "123", name, email, picture, iat, exp, jti }
  4. jwt callback（2回目以降）：callbacks.jwt({ token: payload, trigger: undefined }) を呼ぶ。ここで user は undefined。「初回ログイン時だけ user が来る」の理由はここ。token に載せ忘れた情報は2回目以降は取り出せない
  5. session callback：callbacks.session({ session: { user: { name, email, image }, expires }, token })。既定では token の name / email / picture だけが session.user に写される。id や role は自分で写さない限り消える
  6. Sliding Expiration：exp - now < maxAge - updateAge（= 最後の更新から updateAge 以上経過）なら、新しい exp で JWE を作り直して Set-Cookie する（Part I の Session Renewal）

結論：session.user は「Cookie の JWE を復号した payload を、session callback で整形したもの」。DB も外部通信も介在しない。だから速いし、だから DB の role を変えても即時反映されない（次章）。

Database strategy の内部処理 — session.user は DB の行から来る

Adapter を渡し strategy を省略すると Database strategy になる。Cookie の中身は JWE ではなく意味のない 32byte の乱数（sessionToken）になる。

  1. ログイン時：Adapter.createSession({ sessionToken: randomUUID相当, userId: "123", expires: now + maxAge }) → sessions に INSERT → Set-Cookie で sessionToken を返す
  2. 次のリクエスト：Cookie から sessionToken を取り出し、Adapter.getSessionAndUser(sessionToken) を呼ぶ。1回の JOIN クエリで sessions と users の行を得る
  3. 期限：session.expires < now なら deleteSession して null。expires - now < maxAge - updateAge なら updateSession で expires を延長
  4. callbacks：jwt callback は呼ばれない。session({ session, user }) が呼ばれ、第2引数が token ではなく DB の user 行になる。ここで user.role を写せば、DB を更新した瞬間に次のリクエストから反映される
  5. Logout：signOut() で deleteSession → 即時無効化。Cookie が残っていても lookup で行が無いので session = null

これは Part I の Redis Session と構造が同じだ。Redis が PostgreSQL に、session_id が sessionToken に名前が変わっただけ。

JWT Session — 得るもの / 失うもの

得るもの

  • Stateless。Session Store の運用（冗長化・TTL・容量）が丸ごと消える
  • 水平スケールで Sticky Session が不要。Edge / Serverless（Vercel、Lambda@Edge）で DB なしに認証判定できる
  • 検証が CPU 内で完結し、latency のばらつきがない

失うもの

  • 即時 Revocation。退職者の Cookie は exp まで生き続ける。Auth.js 既定の 30日なら、30日間その人はログインできる
  • Claim の鮮度。role / accommodation_id を DB で変えても Cookie に反映されない。「権限を落としたのに操作できる」事故の温床
  • Token サイズ。Cookie は 4KB 制限。Claim を増やすと毎リクエストのヘッダが肥大化し、いずれ 431 / 400 で死ぬ
  • Secret ローテーションの痛み。Secret を変えれば全員ログアウト。複数 Secret 並行運用が必要
Database Session — 得るもの / 失うもの

得るもの

  • 即時 Revocation。DELETE 1文。退職者の全端末を一括ログアウトできる（WHERE user_id = ?）
  • 鮮度。毎回 users 行を JOIN するので、role 変更は次のリクエストから効く
  • 可視性。「誰が今ログイン中か」「このユーザーは何端末か」が SELECT で分かる。監査ログにそのまま使える
  • Cookie は 32byte。Claim をどれだけ増やしても Cookie は太らない

失うもの

  • 毎リクエストの Store 往復。RDB なら 2〜5ms、Redis なら 0.2〜1ms が確実に乗る
  • Store が SPOF。Redis 障害 = 全員ログアウト状態。Sentinel / Cluster / RDS Multi-AZ の運用が必須
  • Edge / middleware から DB に届かない構成では使えない
  • Session 行の肥大化。期限切れ行の掃除（TTL or cron）が必要。Redis なら EXPIRE で自動

図13-2 JWT Session の2つの事故。Claim 陳腐化と Revocation 不能は同じ原因（値のコピー）から生じる。対策は「窓を短くする」か「参照を1つ足す」の2系統。

中間案①：短命 JWT + jti denylist — Stateless の速さを残し、Revocation だけ買い戻す

「99% のリクエストでは Store を見ない。ログアウトされた Token だけ弾きたい」なら、denylist（拒否リスト）が最も安い。allowlist（有効な Session を全部持つ）は Database Session そのものだが、denylist は「無効化された Token」だけを持つので、通常は空に近い。

  • JWT に jti（一意 ID）を必ず入れる。Auth.js は既定で入れている
  • ログアウト時：SET deny:<jti> 1 EX <exp までの秒数>。exp を過ぎれば Token 自体が死ぬので、Redis から自動で消える。denylist が無限に育たない
  • 検証時：署名検証の後に EXISTS deny:<jti>。Redis 1往復（0.2〜0.5ms）
  • 全端末ログアウト：jti 単位ではできない。deny:user:<user_id> = <timestamp> を置き、token.iat < その timestamp なら拒否する。「この時刻より前に発行された Token は全部無効」というルールにする
  • 限界：Redis が落ちたら denylist が見えない。「落ちたら全部拒否」（安全側）か「落ちたら全部許可」（可用性側）かを決めておく。業務システムなら前者

中間案②：Database Session だが Store を Redis にして latency を潰す

Database Session の欠点は「毎回 Store を見る」ことではなく「毎回 RDB を見る」ことである。Store を Redis にすれば往復は 1ms 未満で、JWT の検証コストとの差はアプリ全体の latency に埋もれる。

  • Redis の TTLが Session 期限そのもの。SET sess:<token> <user_id> EX 2592000。期限切れ行の掃除が不要
  • Sliding Expirationは EXPIRE の打ち直し。updateAge ごとに1コマンド
  • 全端末ログアウトは SADD user_sessions:<user_id> <token> で逆引き集合を持ち、SMEMBERS → DEL
  • role の鮮度：Session に user_id だけ入れ、role は毎回 users を引くか、Session 値に JSON で持ち role 変更時に Session 側も更新するか。前者は RDB 往復が戻る。後者は「role を変える処理が Session 更新も担う」責務を持つ
  • Auth.js で使うなら：@auth/upstash-redis-adapter か、Adapter interface を自分で実装（createSession / getSessionAndUser / updateSession / deleteSession の4関数が Session まわりの全部）

14 Refresh Token — 短命な Credential を、長寿命な Credential で更新する

結論から。Refresh Token は「Access Token を短命にしたことで失った利便性を、別の Credential で買い戻す仕組み」である。Access Token（AT）は 5〜15分で死ぬ。だから盗まれても被害窓が狭く、Revocation しなくても勝手に無効になる。代わりに Refresh Token（RT）を 30日持たせ、AT が切れたら RT で新しい AT を取る。RT は Server 側に Hash で保存され（= Stateful）、使うたびに入れ替わり（Rotation）、古い RT が再利用されたら一族を全部無効化する（Reuse Detection）。これで「AT の Stateless な速さ」と「RT による Revocation」を両取りする。

ズーム：Rotation と Reuse Detection — 「盗まれた RT」をどう見つけるか

RT は長命なので、盗まれたことに気づけなければ 30日間攻撃者に AT を供給し続ける。Rotation（使うたびに RT を入れ替える）は利便性のためではなく、盗難を検知するためにある。

  1. Rotation：refresh のたびに新 RT を発行し、旧 RT を「使用済み」にする。正規 Client は常に最新の RT だけを持つ
  2. Family：ログイン1回で生まれた RT の系譜（rt1 → rt2 → rt3 …）を family_id で束ねる
  3. Reuse Detection：「使用済み」の RT が再び提示されたら、正規 Client か攻撃者のどちらかが古い RT を使っている = 盗難が起きた証拠。どちらが正規か区別できないので、family 全体を revoke する。正規ユーザーは再ログインを求められる（多少の不便）が、攻撃者の RT も死ぬ
  4. Grace Period（任意）：ネットワーク再送で同じ RT が2回届くことがある。数秒〜数十秒だけ旧 RT を許容し、同じ新 RT を返す実装もある。ただし窓が広いほど検知が鈍る

図14-3 Reuse Detection の2シナリオ。どちらが正規か Server は判定できないので family 全体を殺す。Rotation がなければ「2者が同じ RT を持つ」状態を検知する手段がない。

SPA での保存場所 — AT は Memory、RT は Path 限定の HttpOnly Cookie

Part VI で詳しく扱うが、Refresh を設計するなら保存場所も同時に決まる。

  • AT は JS の変数（Memory）に持つ。localStorage に置くと XSS で読まれる。Memory ならページを閉じれば消える。リロードで消えるが、RT で即座に取り直せるので問題ない
  • RT は HttpOnly Cookie、かつ Path=/auth/refresh。JS から読めず（XSS 耐性）、/api/* へのリクエストには付かない（露出面を Auth Server の 1 endpoint に限定）。SameSite=Strict にできる（refresh は自サイトの JS から fetch するだけなので、他サイト起点で送る必要がない）
  • Cookie に RT を入れるなら CSRF を考える。/auth/refresh が Cookie だけで動くと、他サイトから POST されて AT が発行される。ただし発行された AT はレスポンスボディに入り、攻撃者のサイトからは読めない（CORS）。SameSite=Strict と Origin 検証を足せば十分
  • Mobile アプリなら OS の Secure Storage（Keychain / Keystore）に RT を置く。Web の Cookie と同じ位置づけ
  • Next.js（Server Component 中心）なら SPA の話は当てはまらない。Auth.js の Cookie Session がそのまま RT の役割を果たし、Go 向け AT は BFF が毎回署名する（前々章 図12-5）。Refresh endpoint 自体が不要になる

  • 「Google の refresh_token が返ってこない」 → access_type=offline を付けていない、または既に同意済みで prompt=consent がない。Google は初回同意時にしか RT を返さない
  • 「Google の RT が失効したので自社もログアウトさせた」 → 混同。Google API が叩けないだけで、自社の Identity は健在。エラーを token に持たせて、Calendar 機能だけ「再連携が必要」と出す

15 SSH Authentication — 秘密鍵を送らずに本人を証明する

結論から。SSH 公開鍵認証は「サーバーが出したランダムな課題（Challenge）に、クライアントが秘密鍵で署名し、サーバーが登録済みの公開鍵で検証する」認証である。秘密鍵そのものは一度もネットワークを流れない。Password 認証が「秘密を送って、サーバー側の記録と比べてもらう」方式だとすれば、公開鍵認証は「秘密を持っていることだけを、送らずに証明する」方式だ。
Web の Session と構造は同じである。Cookie の session_id が Redis で user_id に変わるのと同じように、SSH では署名が authorized_keys の行と照合されて OS user に変わる。Credential の種類と Verification の中身が違うだけだ。

1. 誰が認証されるか

ログインしようとしている人（または CI / デプロイツール）。指定した OS user（deploy, ec2-user, git）として振る舞う権利を主張する主体

接続先の sshd。GitHub の場合は GitHub 側の SSH サーバー

3. Clientが持つCredential

秘密鍵（~/.ssh/id_ed25519）。送るのは秘密鍵ではなく「秘密鍵で作った署名」

4. Serverが検証するもの

Challenge（セッションID等）に対する署名が、~user/.ssh/authorized_keys に登録されたどれかの公開鍵で検証できるか

5. Identity の特定方法

Client が名乗った username + 一致した公開鍵の行 → その OS user として shell を起動。GitHub は公開鍵 fingerprint → アカウント lookup

図15-1 SSH 公開鍵認証のシーケンス。ネットワークを流れるのは「公開鍵」と「署名」だけ。秘密鍵はクライアントのディスク（または ssh-agent のメモリ）から出ない。

① なぜ「秘密を送らない」ことが決定的に重要なのか

Password 認証では、秘密（password）そのものがトンネルの中を流れ、サーバーはそれを受け取って Hash と比べる。この構造には3つの弱点がある。

  • サーバーが秘密を知ってしまう。偽サーバー（中間者、DNS 汚染、typo したホスト）に接続すると、password はそのまま攻撃者の手に落ちる。同じ password を使い回していれば被害は他システムへ波及する
  • 総当たりが可能。password は人間が覚えられる長さなので、インターネットに露出した sshd は常時ブルートフォースを受ける（/var/log/auth.log を見れば分かる）
  • サーバー側に「比較用の秘密」を保管する必要がある。/etc/shadow が漏れればオフライン攻撃が始まる

公開鍵認証はこの3つを構造的に消す。偽サーバーが得られるのは「そのセッション専用の署名」だけで、他では使えない。256bit の鍵は総当たりの対象にならない。サーバーが保管するのは公開鍵で、漏れても何も起きない。これが「認証の材料を、送る秘密から、持っていることの証明へ変える」ことの意味だ。

図15-2 対比。左は「秘密を送る」、右は「秘密を持っていることを署名で示す」。右の構造は ch07 の RS256 JWT、ch16 の TLS、ch19 の SigV4 にそのまま再登場する。

② サーバー側の State — authorized_keys は「公開鍵 → OS user」の Session Store

Web Session の Redis が session_id → user_id の対応表なら、SSH の ~/.ssh/authorized_keys は 公開鍵 → このファイルを持つ OS user の対応表だ。違いは、対応表がユーザーのホームディレクトリに分散して置かれていることである。

  • lookup の方向：Client が「私は deploy です」と名乗る（Identification）→ sshd は /home/deploy/.ssh/authorized_keys を開く → 提示された公開鍵が含まれるか探す → 含まれていれば Challenge 署名を要求する。username を先に名乗らせるのは、探すファイルを決めるためだ
  • Revocation：該当行を削除するだけ。Redis から session_id を DEL するのと同じ即時性がある。ただしサーバーが100台あれば100台から消す必要がある。この「分散した State の管理コスト」が、後述の SSH 証明書や、IAM のような中央集権モデルへの動機になる
  • Authorization の粒度：command= や from= オプションは、同じ OS user の中でも「この鍵からの接続はこのコマンドしか許さない」という鍵単位の認可だ。Web で言えば scope 付き API Key に近い
  • 解釈：sshd_config の AuthorizedKeysCommand を使えば、対応表をファイルではなく外部 API（LDAP / 社内 IdP）に置ける。GitHub Enterprise や Teleport はこの拡張点で「公開鍵 → 社員」を中央管理している

③ ssh-agent — 秘密鍵をディスクからも出さない

秘密鍵はネットワークに出ないが、プロセスのメモリには乗る。ssh-agent はそれをさらに一段隔離する仕組みだ。ssh コマンドは秘密鍵ファイルを読まず、UNIX ソケット経由で agent に「これに署名して」と頼む。agent だけが秘密鍵を保持し、署名結果だけを返す。

  • Agent Forwarding（ssh -A）：踏み台サーバー上の ssh が、あなたのローカル agent に署名を頼めるようにする。秘密鍵は踏み台に置かれない。ただし踏み台の root はあなたのソケットを使って署名を得られる（踏み台を信頼できないなら使わない）。ProxyJump（-J）の方が安全で、踏み台は TCP を中継するだけになる
  • 解釈：agent は「秘密鍵を持つプロセスを最小にする」というCredential の隔離であり、Web で言えば HttpOnly Cookie（JS から秘密に触れない、ch21）と同じ発想だ

④ 逆方向の認証 — known_hosts は「サーバーを認証する」ための State

ここまでは「サーバーがクライアントを認証する」話だった。SSH にはもう1つの認証がある。クライアントがサーバーを認証するための Host Key だ。初回接続時に出るあの警告がそれである。

  • サーバーも鍵ペアを持つ（/etc/ssh/ssh_host_ed25519_key）。接続時にサーバーは Host 公開鍵を提示し、鍵交換の結果に Host 秘密鍵で署名する。クライアントは ~/.ssh/known_hosts に記録された公開鍵と比べる
  • 初回は比較対象がない。だから「yes」を押させる。これは TOFU（Trust On First Use）と呼ばれ、SSH の最大の構造的弱点だ。この初回に中間者がいれば、以降ずっと偽サーバーを信じ続ける
  • fingerprint が変わったときの REMOTE HOST IDENTIFICATION HAS CHANGED は「サーバーの再構築」か「中間者攻撃」かのどちらかである。確認せずに known_hosts を消して繋ぎ直す習慣は、認証を自分で無効化している
  • TLS（ch16）はこの問題を CA という第三者で解決した。SSH でも同じ解決策が SSH 証明書（後述）と SSHFP DNS レコードとして存在する

⑥ 実例 — Go で SSH 公開鍵認証サーバーを書くと、Verification の中身が見える

  • 「公開鍵認証は鍵ファイルを送っている」 — 送っていない。送るのは公開鍵（誰に見られてもよい）と、そのセッション限定の署名だけ。これを理解していないと、TLS・JWT RS256・SigV4 も同じ誤解で読んでしまう
  • 「秘密鍵にパスフレーズを付ければ盗まれても安全」 — パスフレーズは秘密鍵ファイルを暗号化するだけ。オフラインで総当たりされる。盗まれた時点で失効させるのが正解であり、パスフレーズは時間稼ぎにすぎない
  • 「known_hosts の警告は消せばいい」 — Host Key の変更は「サーバーの本人性が変わった」という認証失敗のシグナルだ。再構築を自分で把握しているとき以外は、中間者を疑う

  • 「1つの秘密鍵を全端末・全CIにコピーして使う」 — 鍵は端末（またはワークロード）単位で作り、authorized_keys の行 = 端末にする。そうしないと1台の端末が漏れたとき、どの行を消せばよいか分からず、全端末の鍵を作り直すことになる

16 TLS / HTTPS — Browser は「本当に google.com か」をどう判断するか

結論から。TLS は「サーバーの認証」と「通信路の暗号化」を同時に行うプロトコルであり、認証の部分は SSH と同じ「秘密鍵で署名し、公開鍵で検証する」で動いている。SSH と違うのは、公開鍵を known_hosts に手で登録するのではなく、CA（Certificate Authority）が「この公開鍵は google.com のものだ」と署名した証明書を使う点だ。Browser は CA の公開鍵だけを最初から持っていて、それを起点に信頼を連鎖させる。
そして重要なのは、TLS が認証するのはサーバーであってユーザーではないことだ。HTTPS で通信しても、サーバーは「誰がリクエストしているか」を何も知らない。ユーザーの認証は TLS の上に載る Cookie / Token（Part I〜IV）の仕事である。TLS はその Cookie / Token を盗聴・改ざんから守る土台だ。

1. 誰が認証されるか

サーバー（pms.example.com というホスト名を名乗る主体）。ユーザーではない

2. 認証する側

① なぜ CA が必要なのか — SSH の TOFU 問題を第三者で解く

SSH（ch15）では初回接続時に Host Key を「yes」で受け入れるしかなかった。Web でこれをやると、世界中の初見サイトすべてで警告が出る。Browser は「サーバーの公開鍵を事前に知っている」代わりに「CA の公開鍵を事前に知っている」ことで解決した。

  • CA の仕事：「このドメインを管理している人が、この公開鍵を持っている」ことを確認して署名する。確認方法は DNS レコード追加や HTTP パス配置（Domain Validation）。CA はドメイン所有権を検証し、その結果を署名で他者に転送可能にする存在だ
  • 信頼の連鎖：Root CA の秘密鍵はオフラインの HSM に隔離され、日常の署名は Intermediate CA が行う。Root が漏れれば全 Browser の trust store 更新が必要になるが、Intermediate なら Root で失効させて差し替えられる。署名権限の階層化 = 秘密鍵の露出面積の最小化で、ch07 の Key Rotation と同じ動機
  • 解釈：CA モデルの弱点は「trust store に入っているどの CA も、任意のドメインに証明書を発行できる」点にある。ある CA の誤発行や侵害（DigiNotar 2011）は全ドメインに影響する。Certificate Transparency（全発行証明書を公開ログに記録）と CAA DNS レコード（このドメインに発行できる CA を限定）は、この構造的弱点への対策である

図16-2 チェーンの各段は「上位の秘密鍵で下位の公開鍵に署名」している。Browser は Leaf から順に上へ検証し、trust store に到達したら終わり。

② TLS 1.3 Handshake — 認証と鍵交換が1往復で終わる

Handshake で起きることは2つだけだ。(a) ECDHE で共通鍵の材料を交換する、(b) サーバーが証明書と署名で本人性を示す。TLS 1.2 以前は RSA で「共通鍵をサーバーの公開鍵で暗号化して送る」方式もあったが、1.3 では廃止され、鍵交換は常に ECDHE、公開鍵暗号は署名にしか使われない。

図16-3 TLS 1.3 Handshake。SSH（図15-1）と比べると、「鍵交換 → 署名で本人性証明 → 暗号化通信」の順序が同じであることが分かる。違いは公開鍵の信頼根拠（known_hosts か CA か）だけ。

③ なぜ本文は共通鍵暗号なのか — 公開鍵暗号は「本人性」と「鍵合意」にしか使わない

公開鍵暗号（RSA / ECDSA / Ed25519 / ECDHE）
  • 遅い（AES の数百〜数千倍の計算コスト）
  • 一度に暗号化できるデータが小さい（RSA 2048 で 190 バイト程度）
  • 得意なこと：事前に秘密を共有していない相手と、安全に「秘密」を作る（ECDHE）、本人性を署名で示す（CertificateVerify）
  • TLS での出番：Handshake の中だけ。1接続あたり数回
共通鍵暗号（AES-GCM / ChaCha20-Poly1305）
  • 速い（CPU の AES-NI 命令でギガビット級）
  • 任意長のデータをストリーム処理できる
  • 得意なこと：大量データの暗号化と改ざん検知（AEAD）
  • 苦手なこと：鍵をどう相手に渡すか（鍵配送問題）→ これを ECDHE が解決する
  • TLS での出番：Handshake 後の全 Application Data
  • ECDHE の要点：Client は乱数 a を、Server は乱数 b を秘密に持つ。互いに g^a と g^b を平文で送り合う。盗聴者は g^a と g^b を見ても、a も b も逆算できない（離散対数問題）。だが Client は (g^b)^a、Server は (g^a)^b を計算でき、両者は同じ値 g^ab になる。平文の通信だけで、盗聴者に分からない共通の秘密が生まれる
  • Forward Secrecy：a と b は接続ごとに捨てる（Ephemeral の E）。だから後日サーバーの秘密鍵 sk_leaf が漏れても、過去の通信は復号できない。sk_leaf は署名にしか使っていないからだ。TLS 1.2 の RSA 鍵交換にはこの性質がなく、それが廃止の理由
  • 解釈：Handshake は「認証 + 鍵合意」であり、Application Data は「認証済みの相手との共通鍵通信」だ。Web の認証で言えば、Handshake がログイン、共通鍵が Session、Application Data がログイン後のリクエストにあたる。TLS Session Resumption（PSK）はまさに「前回の Session を再利用してログインを省く」仕組みである

④ 実例 — Go の http.Server に TLS を設定し、何が検証されているかを見る

  • 事実：InsecureSkipVerify: true は「暗号化はするが、相手が誰かは確認しない」状態を作る。盗聴には強いが中間者には無力で、認証の観点では HTTP と等価だ
  • 解釈：これは「JWT の署名検証をスキップして payload だけ読む」（ch05）と同じ種類の過ちである。暗号化と認証は別の性質で、片方を捨てると Credential（Cookie / Token）が偽サーバーに流れる

⑤ Let's Encrypt / ACME — 「ドメインを制御している」ことの自動証明

CA が署名する前に確認するのは「申請者がそのドメインを制御しているか」だけだ（Domain Validation）。ACME はそれを自動化したプロトコルで、これ自体がひとつの認証フローである。

⑥ 期限と Revocation — 証明書の失効はなぜ難しいか

仕組み動き問題
CRL（Certificate Revocation List）CA が失効した証明書のシリアル一覧を公開。Client がダウンロードして照合リストが巨大化、更新間隔が長い、取得失敗時に「通す」実装が多い（fail-open）
OCSPClient が CA の OCSP サーバーへ「このシリアルは有効か」を問い合わせる接続ごとに CA へ問い合わせ → 遅延とプライバシー漏洩（CA が閲覧履歴を知る）、CA ダウンで fail-open
OCSP Staplingサーバーが OCSP 応答を事前取得して Handshake に添付サーバー側の実装が必要、must-staple でなければ省略可能
Browser 独自リスト（CRLSets 等）Browser ベンダーが重要な失効だけを配布網羅性がない
短命証明書有効期間を短くし（90日→47日→将来は数日）、失効を「待てば消える」に変える自動更新の運用が前提。更新が止まればサイトが落ちる

解釈：これは ch13 の「JWT は即時 Revocation が難しい」問題とまったく同じ構造だ。署名ベースの Credential は検証時に発行者へ問い合わせないから速い。その代償として失効が届かない。解決の方向も同じで、「有効期間を短くして Refresh させる」（Access Token 15 分、証明書 47 日）に収束している。

⑦ TLS はユーザーを認証しない — ここが Part I〜IV との接続点

図16-5 2層構造。mTLS（ch17）は、上の TLS 層に「Client も証明書を出す」を追加して、下の層なしで Client を認証する方式である。

  • Cookie の Secure 属性（ch03）は「この Cookie は TLS 層の上でしか送らない」という指示。TLS がなければ session_id は平文で流れ、Session Hijacking（ch22）が成立する
  • HSTS（Strict-Transport-Security）は「以降このホストには HTTPS 以外で繋ぐな」を Browser に記憶させる。初回の HTTP → HTTPS リダイレクトの隙（SSL Stripping）を塞ぐ
  • 解釈：TLS が守るのは「通信路」であり、Credential が正しい相手に届くことを保証する。Credential そのものの妥当性（期限、失効、署名）は各認証方式の責任であり、TLS はそれを代替しない

よくある誤解

  • 「HTTPS = 暗号化」 — 暗号化は半分。もう半分の「サーバー認証」がなければ、暗号化された通信を偽サーバーと行うだけになる。InsecureSkipVerify はまさにその状態
  • 「証明書を持っていれば本人」 — 証明書は公開情報で、誰でもダウンロードできる。本人性は Handshake 中の秘密鍵による署名（CertificateVerify）で示される。証明書は「この公開鍵はこのドメインのもの」という CA の保証にすぎない
  • 「Root CA は検証されている」 — Root は trust store に入っていることが信頼の根拠で、検証はされていない（自己署名）。OS / Browser ベンダーがどの CA を入れるかを決めており、そこは技術ではなく監査と契約の世界だ
  • 「HTTPS ならユーザーは認証済み」 — TLS は Client について何も確定しない。ユーザー認証は Cookie / Token の仕事
  • 「証明書の期限切れは些細な運用ミス」 — 期限は Revocation の代替手段そのものだ（短命化）。期限を長くする回避策は、失効の仕組みを自分で弱めている

結論から。mTLS（mutual TLS）は、通常の TLS に「Client も証明書と署名を出す」を1手足しただけの仕組みである。通常 TLS が「Client が Server を認証する」一方向なら、mTLS は双方向で、Handshake が終わった時点でサーバー側にも Client の Identity（証明書の SAN に書かれたサービス名）が確定している。Cookie も Token も HTTP ヘッダも要らない。
だから mTLS は「人間のログイン」にはほとんど使われず、Microservice 同士、サービスとデータベース、Zero Trust ネットワークの端末認証のように「Credential を安全に配布・保管できる機械同士」で使われる。人間は秘密鍵を持ち歩けないが、ワークロードは持てるからだ。

① なぜ内部サービス間の認証に mTLS を選ぶのか

内部通信なら認証不要、と考えるのは「ネットワーク境界の内側は安全」という前提に立っている。この前提は、1台のコンテナが侵害された瞬間に崩れる。侵害されたコンテナは同じ VPC の全サービスに平文で話しかけられるからだ。Zero Trust は「ネットワークの位置ではなく、Identity で判断する」への転換であり、mTLS はその最も低いレイヤーでの実装である。

  • Credential が HTTP ヘッダに現れない：API Key（ch09）や Bearer Token（ch05）はログや APM に漏れがちだが、Client 証明書の秘密鍵は TLS 層の外に出ない。署名しか流れない（ch15 と同じ原理）
  • アプリケーションコードが認証を実装しなくてよい：Service Mesh（後述）なら、アプリは平文 HTTP を書くだけで、sidecar が mTLS を透過的に行う。Go の Handler は X-Forwarded-Client-Cert か r.TLS から Identity を読むだけ
  • 通信路の暗号化と認証が同時に手に入る：API Key を使う場合、暗号化のために TLS を別途必要とする。mTLS なら1つで両方
  • 代償は証明書の配布と更新：全サービスに秘密鍵と証明書を安全に置き、期限前に更新し続けなければならない。手作業では破綻する。だから mTLS は「証明書自動発行の基盤（SPIRE / cert-manager / Mesh の CA）」とセットで導入するもので、単体で選ぶものではない

  • SAN の DNS 名：payment.prod.svc.cluster.local のようにサービスの DNS 名を書く方式。分かりやすいが、「名前空間」「環境」「どのクラスタか」が DNS 名の慣習に依存する
  • SPIFFE ID（SAN の URI）：spiffe://pms.internal/ns/prod/sa/payment という URI 形式。trust domain / namespace / service account の構造を持ち、Kubernetes の ServiceAccount と1対1に対応させられる。Istio・SPIRE・Linkerd が採用する事実上の標準

④ Service Mesh — アプリを変えずに mTLS を「透過的」に入れる

全サービスに上記の Go コードを入れるのは現実的でない。言語が混在し、証明書の更新をアプリごとに実装することになる。Service Mesh は各 Pod に sidecar proxy（Envoy / linkerd-proxy）を置き、アプリは localhost へ平文 HTTP を送るだけ、sidecar 同士が mTLS で話す構成にする。

図17-4 Mesh の本質は「Private CA の運用と証明書ローテーションを、アプリから切り離して自動化する」こと。認証の原理は図17-3 と同じ。

  • 証明書の寿命：Istio のデフォルトは 24 時間、SPIRE は 1 時間程度。短命なので Revocation の仕組み（CRL / OCSP）を持たず、「更新を止めれば数時間で失効する」で済ませる。ch16 ⑥ の結論と同じ
  • Workload Identity の起点：Mesh CA はどうして「この Pod は reservation の ServiceAccount だ」と分かるのか。Kubernetes API が Pod に発行する ServiceAccount Token（JWT、ch05）を提示させ、Kubernetes の公開鍵で検証する。mTLS の証明書は、別の認証（K8s SA JWT）を土台にして発行されている。認証は多段に連鎖する
  • 解釈：Mesh を入れると「認証はインフラの責務」になり、アプリ開発者は Authorization だけを考えればよくなる。これは良いことだが、X-Forwarded-Client-Cert を偽装できる経路（sidecar をバイパスした直接接続）があれば認証全体が崩れる。NetworkPolicy で sidecar 以外からの到達を禁止するのがセットである

⑤ mTLS の限界 — 何が苦手か

  • Load Balancer / CDN で TLS を終端すると Client 証明書が消える：ALB は Client 証明書をヘッダで後方に渡せるが（mTLS passthrough / verify モード）、設計時に意識しないとアプリまで届かない
  • ユーザー単位の認可には粗すぎる：mTLS の Identity は「サービス」だ。「reservation-service 経由で user_id=123 が操作している」を payment に伝えるには、mTLS の上でユーザーの JWT を転送する（Token Propagation）必要がある。サービスの認証（mTLS）とユーザーの認証（JWT）は別レイヤーで共存する
  • ブラウザには向かない：Client 証明書を人間の Browser に配る運用（企業内 PKI）は存在するが、UX が悪く、証明書の配布・失効が端末管理と結びつく。一般ユーザー向け Web では Cookie / OIDC が現実解
  • 秘密鍵の保管場所がそのまま攻撃面：Pod 侵害で秘密鍵が抜かれれば、その証明書の有効期間中はなりすませる。短命化と、可能なら TPM / KMS で鍵を非エクスポート化する

よくある誤解

  • 「mTLS は特別なプロトコル」 — TLS の Handshake に CertificateRequest を追加しただけ。Go では ClientAuth と ClientCAs の2フィールドで有効化できる
  • 「mTLS を入れれば認可も済む」 — Handshake が通るのは「Private CA が署名した誰か」であることだけを意味する。どのサービスが何を呼べるかは、SAN を読んだ後のポリシーで別に決める。図17-2 の⑤がなければ、marketing-service も決済を呼べる
  • 「内部ネットワークだから mTLS は過剰」 — 侵害された1コンテナが全サービスへ平文で到達できる構成は、「認証なし」と同義だ。過剰かどうかは、その状態を許容できるかで決める
  • 「証明書を手で配ればよい」 — 手配布は必ず期限切れ事故を起こす。mTLS は自動発行・自動更新の基盤とセットで導入する技術であり、それがないなら署名 JWT（ch18）の方が運用可能である

18 Service-to-Service Authentication — 機械同士は何を Credential にするか

結論から。Service-to-Service（S2S）認証の選択肢は6つ（Static API Key / 署名 JWT / OAuth Client Credentials / mTLS / AWS IAM SigV4 / Service Account）しかなく、違いは「Credential をどこに置き、誰が回転させ、どう失効させるか」の運用モデルだけである。認証の原理はどれも Part I〜IV と Part V 前半で見たものの組み合わせだ。
人間の認証と決定的に違うのは、Password も Consent もなく、Credential の「配布と保管」が問題の中心になる点である。人間は秘密を頭の中に持てるが、サービスは秘密をどこかのファイル・環境変数・メモリに置かなければならない。S2S の設計とは、この「置き場所」をいかに攻撃面から遠ざけ、いかに自動で回転させるかの設計だ。

1. 誰が認証されるか

ワークロード（Go API プロセス、Lambda 関数、Pod、CI ジョブ）。人間ではない

2. 認証する側

呼ばれる側のサービス（社内 Microservice、外部 OTA API、AWS S3、Google API）

3. Clientが持つCredential

方式で異なる：API Key 文字列 / 署名用秘密鍵 / client_secret / Client 証明書 / IAM 一時 Credential / SA Token

4. Serverが検証するもの

Hash 比較 / 署名検証 / Token Introspection or 署名検証 / 証明書チェーン / SigV4 再計算

5. Identity の特定方法

client_id / JWT の sub or iss / 証明書 SAN / IAM Role ARN → service=reservation-service のような主体名

19 AWS IAM Authentication — Lambda に Password を書かなくていい理由

結論から。AWS の認証は「全リクエストを Secret Access Key で HMAC 署名し、AWS 側が同じ Secret で再計算して一致を見る」SigV4 の一点に集約される。IAM User の長期 Access Key も、Role から得た一時 Credential も、最終的にはこの署名に使われる材料が違うだけだ。
そして「Lambda に Password を書かなくていい」のは、Lambda に IAM Role を付けると、実行環境が STS から短命の Credential を取得して環境変数に注入し、SDK がそれを自動で読んで署名し、期限前に自動更新するからである。開発者は秘密を一度も見ず、どこにも置かない。これが ch18 で目標とした Workload Identity の、最も普及した実装だ。

① なぜ「Password を書かなくていい」のか — Role とは何か

  • IAM Userは「人間や外部システムのための恒久的な Identity」で、長期の Access Key（AKIA...）を持てる。この Key は失効させるまで有効で、漏れれば誰でもその User になれる。長期の秘密を置く方式
  • IAM Roleは「誰でも一時的に被れる Identity」だ。Role 自身は Credential を持たない。代わりにTrust Policyで「誰がこの Role を Assume できるか」を定義する。lambda.amazonaws.com を信頼する Trust Policy を書けば、Lambda サービスがその Role を Assume できる
  • AssumeRoleは STS の API で、「私はこの Role を被る権利がある」と証明した主体に、その Role としての一時 Credential（最長 12h、Lambda では数時間で自動更新）を返す。Lambda の場合、この証明は「Lambda サービス自身の Identity」で行われ、開発者は関与しない
  • 解釈：Role モデルの本質は「Identity と Credential の分離」だ。Identity（Role）は永続だが、Credential（一時 Key）は短命で、必要なときにその場で作られる。Web で言えば、Role が user アカウントで、一時 Credential が Session / Access Token にあたる。Lambda は Role という「アカウント」に、パスワードなしで「ログイン済み」の状態で起動される

図19-2 左右の違いは強度ではなく寿命と置き場所。Role モデルは「秘密をどこにも置かない」を実現した最初の大規模な Workload Identity である。

② SigV4 — 「リクエスト全体に署名する」とは何を署名しているのか

SigV4 は Bearer Token（ch05）と根本的に違う。Bearer は「Token を持っていれば誰でも使える」が、SigV4 はリクエストごとに、そのリクエストの内容・日時・宛先に対して HMAC を計算する。盗聴しても、別のリクエストには使えない。SSH の「session_id を署名対象に含める」（ch15）と同じ Replay 対策を、HTTP レイヤーで実現している。

図19-3 SigV4。Bearer Token が「切符を見せる」なら、SigV4 は「毎回その場で、この切符のこの座席のこの時刻に対する署名を書く」。切符（Secret）自体は決して見せない。

  • なぜ共通鍵（HMAC）なのか：検証者が AWS だけなので、Secret を AWS と Client の2者だけが持てばよい。ch06 で見た HS256 の弱点（署名者＝検証者、Secret 配布問題）は、検証者が1者しかいない状況では弱点にならない。公開鍵暗号が必要になるのは「検証者が複数いる」とき（ch07）
  • なぜ日時が入るのか：X-Amz-Date が現在時刻から 15 分以上ずれていると AWS は拒否する。これにより、盗聴した署名済みリクエストの再送（Replay）は 15 分の窓に限られる。さらに派生鍵に日付が入るので、鍵の有効範囲も1日に閉じる
  • Presigned URL：SigV4 で署名した URL を第三者に渡すと、Secret を渡さずに「この S3 オブジェクトへの PUT を 10 分だけ許可」できる。Credential を渡さず、署名済みの権限だけを渡す。OAuth の Access Token と同じ「委譲」を、署名1つで実現している

③ 実例 — Go SDK v2 は Credential をどこから読むか（Credential Provider Chain）

  • 事実：どの環境でも LoadDefaultConfig だけで動くのは、Credential の「取得方法」が環境ごとに違っても、「SigV4 で署名する」という使い方が同じだからだ。取得と使用が分離されている
  • 注意：環境変数が最優先なので、Lambda に誤って AWS_ACCESS_KEY_ID を手動設定すると、Role の一時 Credential を上書きしてしまう。「Role を付けたのに権限エラー」の典型原因
  • 解釈：3 の Web Identity は「別の基盤（Kubernetes）が発行した JWT を、AWS が信頼して Role に交換する」仕組みで、認証の連鎖（ch17 ④）の AWS 版だ。Kubernetes の公開鍵（OIDC Discovery）を AWS 側に登録することで信頼関係を作る

④ AssumeRole のシーケンス — Cross-account で「別アカウントの Role を被る」

図19-4 AssumeRole は「今の Identity を Credential にして、別の Identity の一時 Credential をもらう」操作。OAuth の Token Exchange（ch10）や、SSH の踏み台経由と同じ「Identity の乗り換え」である。

  • Trust Policy は認証条件、Permission Policy は認可条件：Trust Policy「誰がこの Role になれるか」は Authentication に属し、Permission Policy「この Role は何ができるか」は Authorization に属する。この区別（ch01）が Role の2つの Policy にそのまま現れている
  • 解釈：Cross-account では Account B が「A の Role なら信頼する」と宣言することで信頼が成立する。B は A の Secret を一切知らない。信頼の表現が「秘密の共有」ではなく「Identity の指名」になっているのが、API Key 共有モデルとの本質的な差だ

⑤ IAM Policy 評価 — 認証の後、何が Allow を決めるか

図19-5 IAM の評価は「認証で確定した Principal」を入力にした純粋な認可処理。ch20 の RBAC / ABAC で言えば、Condition による ABAC を備えた RBAC である。

⑥ OIDC Federation — AWS の外からも「長期 Access Key を置かない」

GitHub Actions から AWS にデプロイするとき、以前は IAM User の Access Key を GitHub Secrets に置いていた。これは「長期の秘密を外部に置く」最悪のパターンだ。OIDC Federation は、GitHub が発行する短命の JWT（ch05 / ch11 の ID Token と同じ形式）を AWS STS に渡し、Role の一時 Credential に交換する。

図19-6 OIDC Federation。ch11 の OIDC を「人間のログイン」ではなく「ワークロードの Identity 交換」に使っている。EKS の IRSA、GCP の Workload Identity Federation も同じ構造。

  • Trust Policy の Condition が本丸：sub の条件を repo:org/pms:* と緩く書くと、PR ブランチや fork からも Role を Assume できてしまう。Identity の粒度（どのブランチ・どの環境か）を Condition で縛るのが、この方式の認可設計そのものだ
  • 解釈：ここで JWT（ch05）、JWKS（ch07）、OIDC（ch11）、STS（本章）が1本の線で繋がる。認証技術は個別に存在するのではなく、「ある基盤が保証した Identity を、別の基盤の Credential に交換する」連鎖として組み合わされる

よくある誤解

  • 「Lambda の環境変数に Access Key を設定する」 — Role の一時 Credential を上書きし、長期鍵をわざわざ露出させる二重の誤り。Lambda / EC2 / ECS / EKS で長期 Access Key を使う正当な理由は存在しない
  • 「IAM は認可の仕組みで、認証は別」 — IAM は SigV4 による認証（Principal 確定）と Policy による認可（Allow/Deny）の両方を担う。Trust Policy が認証条件、Permission Policy が認可条件
  • 「一時 Credential は漏れても大丈夫」 — 有効期間中（最長 12h）は完全にその Role になれる。「被害が有限」であって「無害」ではない。漏洩を検知したら Role のセッション失効（aws:TokenIssueTime Condition による Deny）で即時に切る
  • 「Root アカウントで作業する」 — Root は Policy で制限できない唯一の Principal であり、Identity と Credential の分離が効かない。MFA を付けて金庫に入れ、日常は Role（SSO）で作業する
  • 「SigV4 は AWS 独自の複雑な仕様」 — 中身は「HMAC で正規化リクエストに署名」（ch06 の HS256 と同じ）+「日時とスコープで鍵を派生」だ。複雑なのは正規化の規則であり、認証の原理は本書で見てきたものと同じである

20 Authentication vs Authorization — user_id=123 が確定した後に何が起きるか

結論から。認証は「誰か」を確定する処理、認可は「その誰かが、この資源に、この操作をしてよいか」を判定する処理である。両者は必ず直列で、認証が先。そして実務で最も多い事故は「認証は完璧なのに認可がない」状態、つまりログインさえしていれば他ホテルの予約が見えるという IDOR（Insecure Direct Object Reference）だ。middleware で「ログイン済みか」を確認しただけでは、認可は 1 行も書けていない。本章では認可を Identity → Role → Permission → Resource の 4 段に分解し、最後に PMS の 1 つの if 文までズームする。

1. 誰が認可されるか

認証済みの Identity（user_id=123 / service=ota-sync / role=worker）。未認証の主体に認可判定は存在しない（anonymous も 1 つの Identity として扱う）

2. 判定する側

Resource を持つサーバー。Go API の usecase 層、または外部の Policy Engine（OPA / Cedar / SpiceDB）

3. 判定の入力

Identity の属性（role, accommodation_id）+ 操作（action）+ 対象 Resource の属性（hotel_id, owner_id, status）

4. 何を検証するか

Policy（許可ルール）に対して入力の組が真か偽か。Credential の真正性はもう問わない（認証で済んでいる）

5. 出力

allow / deny。deny のとき 403（または存在を隠す 404）。allow でも Repository は tenant で絞る

なぜ「ログイン済みか」だけの middleware では足りないのか — IDOR / BOLA

OWASP API Security Top 10 の 1 位は毎回 Broken Object Level Authorization（BOLA）である。仕組みは単純で、認証を通った攻撃者が URL の ID を書き換えるだけだ。

  • 事実：予約 ID は連番か推測可能な UUID v1 であることが多い。攻撃者は自分のホテルで 9001 を見た後、9002 を叩くだけでよい
  • 解釈：これが多発するのは、開発者の頭の中で「認証が通った = 信頼できる人」に変換されるから。だが認証は「誰か」を確定しただけで、「何をしてよいか」は 1 ビットも言っていない
  • 解釈：Next.js 側で「他ホテルの予約はリンクが表示されない」設計にしても無意味。UI は認可ではない（後述）

実装 — middleware（AuthN）と usecase（AuthZ）を分離し、Principal で橋渡しする

鍵は Principal 型だ。認証の出力を「認可が読める形」に固定し、ctx で運ぶ。handler も usecase も、Cookie や JWT の存在を知らない。

Policy をコードに持つ（rolePerms map）
  • 向く：role が 3〜10 種で、権限の変更がリリースと同期してよい場合
  • 利点：型で守れる。テストが書ける。git に履歴が残る。デプロイなしに権限が変わる事故が起きない
  • 欠点：顧客ごとに権限をカスタムしたい要望に応えられない
  • PMS：cleaner / staff / manager / admin の 4 役なら十分
Policy を DB / Policy Engine に持つ
  • 向く：tenant ごとにカスタム role を作らせる、監査要件で権限変更を即時反映したい場合
  • 利点：デプロイなしで変更。管理画面から操作可能。ReBAC への拡張が容易
  • 欠点：判定のたびに I/O。ルールの正しさをテストしにくい。「誰が誰に何を許可したか」の監査ログが別途必要
  • PMS：グループ経営で本部が各ホテルの権限を設計したくなった時点で移行を検討

Repository を最後の砦にする — tenant を引数に取らないメソッドを存在させない

usecase の if は人間が書き忘れる。書き忘れても他 tenant の行が返らないようにするには、Repository のシグネチャで tenant を強制するのが最も確実だ。

  • 効果：usecase で u.repo.FindByID(ctx, actor.AccommodationID, in.ReservationID) と書かざるを得なくなる。コンパイラが認可を強制する
  • さらに：PostgreSQL の Row Level Security で SET app.tenant = 456 を接続ごとに設定し、DB 層でも絞る選択肢がある。アプリのバグが DB を越えられなくなる
  • 解釈：「二重に書くのは DRY 違反では？」という声が出るが、認可は防御の深さ（defense in depth）が正義。1 箇所の if に全信頼を置く方が危険

図20-4 攻撃者は正規ユーザー。認証は正常に通過する。止めるのは usecase と repository の認可であり、認証を強化しても IDOR は防げない。

よくある誤解 ① — 「Next.js 側でボタンを出さなければ安全」

  • 事実：UI の出し分け（{session.user.role === 'admin' && <DeleteButton/>}）はブラウザ上の JavaScript の挙動にすぎない。攻撃者は curl で API を直接叩く
  • 事実：Server Component や middleware.ts で redirect('/login') しても、Go API のエンドポイントが無防備なら意味がない
  • 結論：見せない ≠ 禁止する。UI 側の制御は UX（無駄な 403 を見せない）のためであり、認可は資源を持つサーバー（Go API）にしか存在しない
  • ただし：Next.js の Route Handler や Server Action が直接 DB を触る構成なら、そこが「資源を持つサーバー」なので認可はそこに書く。「Next.js だから不要」ではなく「資源に一番近い所に書く」が原則

よくある誤解 ② — 403 と 404 の使い分け

  • 403 Forbidden：「その資源は存在するが、あなたには権限がない」と存在を認めている。予約 ID が推測可能なら、攻撃者は 403 の有無で他ホテルの予約件数を列挙できる
  • 404 Not Found：「あなたの世界にはその資源は無い」。tenant 越しの参照は原則こちら。repository が tenant で絞っていれば自然にこうなる
  • 403 を返してよい場合：同一 tenant 内で role が足りないとき（cleaner が料金を変更しようとした）。存在は既に知っている相手なので隠す意味がない
  • 判断基準：「相手がその資源の存在を知る権利があるか」。tenant 外 → 404、tenant 内・権限不足 → 403

よくある誤解 ③ — 「JWT の claim に role が入っているから認可も済んでいる」

  • 事実：JWT の role=admin は「発行時点の Identity の属性」であって、認可判定ではない。属性を何と突き合わせるかを書かなければ認可は存在しない
  • 事実：JWT の claim には resource の属性（hotel_id=456 の予約かどうか）は入れられない。resource は毎回 DB から読む必要がある。だから認可は必ず「Token を検証した後、DB を読んだ後」に置かれる
  • 解釈：「Stateless な JWT なら DB を見ずに済む」は認証についてのみ真。認可では resource を読む I/O が消えない

この章の 7 つの質問 — 認可に当てはめると

  • Q1 Credential は？：認可には Credential がない。入力は「認証済み Principal」と「Resource の属性」
  • Q2 誰が発行？：Principal は middleware（認証）が発行。Resource 属性は DB が真実の源
  • Q3 誰が検証？：資源を持つサーバーの usecase。UI やゲートウェイは検証者ではない
  • Q4 State はどこ？：Policy（role→perm）はコードか DB。Ownership は resource の行そのもの
  • Q5 期限は？：認可判定に期限はない。毎リクエスト評価する（キャッシュするなら秒単位）
  • Q6 Identity 変換？：不要。むしろ Identity を Role / Attribute に展開する方向
  • Q7 Revocation？：role 剥奪 = DB or Session の属性更新。JWT 方式だと exp まで古い role が生きる（Part IV の再確認）

21 Tokenはどこに保存する？ — HttpOnly Cookie / localStorage / Memory と XSS・CSRF

結論から。ブラウザで長寿命の Credential を置く場所は HttpOnly Cookie 一択である。localStorage は XSS 1 発で Token がそのまま盗まれる。Cookie は XSS では読めないが CSRF に晒される。ただし CSRF は SameSite と Origin 検証で機械的に潰せる一方、XSS で盗まれた Token の流出は止めようがない。「読めない Credential」を作れるのは HttpOnly Cookie だけだ。SPA が API を直接叩く構成の問題は、Next.js を BFF（Backend for Frontend）にして Cookie → Bearer の変換をサーバー側で行えば消える。

1. 誰が認証されるか

ブラウザを操作する人間。保存場所の選択は「その人間以外（XSS の JS、別サイトのページ）が Credential を使えるか」を決める

2. 認証する側

変わらない。Go API / Next.js サーバー。保存場所はサーバーの検証手順に影響しない（Cookie か Header かの違いのみ）

session_id / Auth.js の暗号化 JWT / OAuth Access Token / Refresh Token。どこに置くかがこの章の主題

4. Serverが検証するもの

Credential 自体に加えて、CSRF 対策として Origin / Sec-Fetch-Site / CSRF Token を検証する

5. Identity の特定方法

なぜ XSS の方が CSRF より重いのか — 「対策の完了」が定義できるか

  • CSRF の本質：ブラウザが Cookie を「サイトをまたいで自動送信する」仕様の悪用。攻撃面はこの 1 つの仕様に限定される。SameSite 属性と Origin 検証で仕様レベルで塞げる。塞いだかどうかをテストで確認できる
  • XSS の本質：自分のオリジンで攻撃者の JS が動く。攻撃面はテンプレート・依存パッケージ・CDN・ブラウザ拡張・第三者スクリプトすべて。npm の 1 パッケージが汚染されただけで成立する（2018 年の event-stream、2024 年の polyfill.io）
  • 解釈：XSS 対策は「終わらない作業」。だからXSS が起きても被害を限定する設計（Credential を JS から読めない場所に置く）が必要。localStorage 設計は「XSS は起きない」に全額を賭けている
  • さらに：Content-Security-Policy で inline script を禁止し、Trusted Types を有効にすれば XSS の成立確率は下がる。ただし「下がる」であって「ゼロ」ではない

SameSite=Lax の「トップレベル GET 例外」を正しく理解する

  • 事実：Lax は「ユーザーがリンクをクリックして別サイトから遷移してきた GET」には Cookie を付ける。付けないとメールのリンクを開くたびにログアウト状態になり使い物にならないため
  • 含意：GET /reservations/9001/cancel のように GET に副作用を持たせると、Lax でも CSRF が成立する。GET を安全（冪等・副作用なし）に保つのは CSRF 対策の前提条件
  • 事実：「Site」の単位は eTLD+1。app.pms.example.com と api.pms.example.com は同一サイト。だからサブドメインに API を置けば Lax のまま Cookie が届く
  • 事実：Chrome は SameSite 未指定を Lax 扱いするが「Lax+POST」という緩和（Set-Cookie から 2 分間だけクロスサイト POST を許す）がある。OAuth の callback POST を通すための互換措置。明示的に Lax を書け。未指定の挙動に依存しない

Go での CSRF 対策 — SameSite Cookie + Origin / Sec-Fetch-Site 検証の二重化

SameSite だけに頼らず、サーバー側でも「どこから来たか」を見る。Sec-Fetch-Site はブラウザが付け、JS から偽装できない。

  • Bearer Token 方式の API には CSRF 対策が不要：Authorization ヘッダはブラウザが自動添付しないため。CSRF は「自動添付される Credential」にだけ発生する
  • CSRF Token（Synchronizer / Double Submit）はいつ要るか：SameSite=None が必要なとき、または古いブラウザを切れないとき。Auth.js は内部で Double Submit Cookie 方式の csrfToken を signIn / signOut に使っている
  • __Host- prefix：サブドメインからの Cookie 上書き（Cookie Tossing）を防ぐ。Session Fixation 対策にもなる（Part VI ch22）

  • 「SameSite=Strict が最強」：メールのリンクや外部サイトからの遷移で毎回ログアウト状態になる。操作系 Cookie を Strict、閲覧用 Cookie を Lax に分ける 2 枚構成が現実的

  • Q4 State はどこ？：BFF なら Token はサーバー側の session にあり、ブラウザは不透明な Cookie だけ持つ
  • Q5 期限は？：Memory 保存は「タブの寿命」が上限になる。Cookie は Max-Age

  • Q7 Revocation？：Cookie 方式は Session Revoke で即時。localStorage の JWT は exp まで止まらない。保存場所が Revocation の実効性を決める

  • 「TLS があれば Session Hijacking は起きない」：通信路の盗聴は防げる。端末上のマルウェア、ログへの混入、URL に載せた session_id、XSS による操作代行は TLS と無関係
  • 「MFA があれば安全」：TOTP は AiTM Phishing で中継される。Session Cookie が盗まれれば MFA は関係ない。MFA は「Password 単独の突破」を防ぐだけ。Origin 束縛があるのは Passkey / WebAuthn
  • 「JWT ライブラリを使っているから alg 攻撃は無関係」：ライブラリの既定が「Header の alg に従う」なら脆弱。golang-jwt v5 でも WithValidMethods を書かなければ全 alg を受け付ける
  • 「攻撃されたら認可で止まる」：止まらない。攻撃者は被害者の Identity を得ているので、認可は被害者の権限で正常に通る。ch20 の認可が防ぐのは IDOR（正規ユーザーの越権）であり、なりすましは防げない
  • 「うちは小さいから狙われない」：Credential Stuffing は自動化されており、サイトの規模を見ない。漏洩リストを全ドメインに流すだけ

この章の 7 つの質問 — 攻撃者の視点で読み直す

  • Q1 Credential は？：攻撃者が欲しい物そのもの。何が Credential かを列挙できなければ、何を守るかも決まらない
  • Q2 誰が発行？：発行者の Secret / Private Key が漏れれば全 Credential が偽造可能。発行者は最大の単一障害点
  • Q3 誰が検証？：B 型攻撃の標的。検証コードの既定値・自動選択・部分一致を疑う
  • Q4 State はどこ？：State があれば Revoke できるが Store が標的になる。State が無ければ Store は狙えないが Revoke もできない
  • Q5 期限は？：盗まれた Credential の価値 = 残り有効期間 × 権限。短命化は最も安い防御
  • Q6 Identity 変換？：ここは攻撃できない。攻撃は必ず変換の「前」（Credential）か「変換器」（Verification）を狙う
  • Q7 Revocation？：「盗まれた」と分かった瞬間に止められるか。止められない設計は、盗まれないことに全額を賭けている

結論：Passkey = 「SSH 公開鍵認証を Origin 束縛付きでブラウザに持ち込んだもの」。全く新しい技術ではなく、表の既存行の組み合わせで説明できる。これが「体系で理解している」状態だ。

よくある誤解 — 表を見れば消えるもの

  • 「JWT は Session より安全」「Session は古い」：安全性の軸ではなく State の有無の軸。Revocation では Session が勝ち、Scale では JWT が勝つ。優劣ではなくトレードオフ
  • 「OAuth は認証プロトコル」：表の「誰を認証するか」が「user が client に委譲した権限」であることに注目。人間を認証しているのは OIDC の ID Token の行
  • 「API Key と Bearer Token は別物」：運搬方法（ヘッダ名）が違うだけ。API Key を Authorization: Bearer で送っても構造は変わらない。違いは Credential が参照子か署名付きか
  • 「SSH や TLS は Web 認証とは別世界」：表の中で SSH は「Challenge 署名 + Store lookup」、TLS は「証明書チェーン検証」。JWT の公開鍵検証（ch07）と同じ暗号プリミティブを使っている
  • 「IAM は AWS 独自で理解不能」：SigV4 は「リクエスト全体を HMAC 署名する API Key」。STS は「短命 Credential を発行する Auth Server」。Role は「Credential を埋め込まずに Identity を与える仕組み」。全部 表の既存概念

Part VI のまとめ — 認証の「後」と「壊れ方」

  • ch20：認証は Identity を確定するだけ。認可は Identity 属性と Resource 属性の突き合わせ。usecase の 1 つの if と repository の WHERE で守る
  • ch21：長寿命 Credential は HttpOnly Cookie に。XSS は「対策の完了」が無いので、盗まれても複製できない場所に置く。BFF で Bearer をブラウザから消す
  • ch22：攻撃は「本物を盗む（A）」か「偽物を通す（B）」の 2 種。防御は露出減・束縛・検証固定・検知失効の 4 原則
  • ch23：10 方式の違いは Credential と Verification の 2 箱だけ。Credential の形が State・Revocation・Expiration を連鎖的に決める

7つの質問で分解する

  • Login 成功後に sid を再発行しない — Session Fixation（ch22）。Login 前から持っていた sid が Login 後も有効なら、攻撃者が仕込んだ sid で被害者がログインすることになる
  • Redis に入れる値に role を入れて、DB 側の role 変更を反映しない — 「30日間、降格が効かない」。role のように変わる属性はリクエスト毎に DB で引くか、変更時に Session を破棄する

なぜこれで「password を書かなくていい」のか — 信頼の連鎖を言葉にする

  1. Lambda Service は AWS の内部コンポーネントで、STS に対して既に認証済み（AWS が自分自身を認証している）
  2. Role の Trust Policy が「Lambda Service なら Assume してよい」と書いてある。これは人間が事前に置いた認可
  3. STS は Trust Policy を根拠に、短命の鍵を Lambda 実行環境に渡す。人間の Credential は一度も介在しない

  5. 結果：Identity は「コードに埋めた Secret」ではなく「実行環境そのもの」に紐づく。同じコードを別 Role の Lambda で動かせば別 Identity になる

25 Authentication Map — すべてを1枚で理解する

結論から。認証とは、クライアントがCredentialを提示し、サーバーがそのCredentialを検証してIdentityを確定する処理である。それ以上でも以下でもない。下の1枚は、本書で扱った全方式を「誰を認証するか」で3系統に分け、それぞれを同じ5段（Credential → Transport → Verification → Identity → Authorization）に押し込んだものだ。方式名を隠して5段だけ読んでも区別がつかない箱がいくつかある。それが「基本構造は共通」の意味だ。

図25-1 Authentication Map。3系統 × 11方式が、同じ5段へ収束する。方式名を隠して読めば、Session と API Key、JWT と Client Credentials、SSH と Passkey がほぼ同じ箱であることが分かる。

1文に収束させる — なぜこの定義で十分なのか

「クライアントが Credential を提示し、サーバーがその Credential を検証して Identity を確定する処理」。この定義には、意図的に含めていないものがある。

  • 「暗号」は含めない。暗号は Credential の作り方（署名）や Transport の守り方（TLS）の道具であって、認証の定義ではない。Password 認証に公開鍵暗号は登場しない
  • 「Token」も「Cookie」も含めない。それらは Credential の容れ物と運び方だ。Cookie の中に Session ID が入ることも JWT が入ることもある（ch3 の「Cookie ≠ Session」）
  • 「ログイン」も含めない。ログインは「Password という Credential を、Session ID という別の Credential に交換する」処理で、認証の1つの実装形にすぎない。API Key や mTLS にはログインがない
  • 「Authorization」は含めない。Identity が確定した後の別の処理。ここを混ぜると「認証は通っているのに 401 を返す」「認証を通せば何でもできる」という設計ミスが生まれる（ch1, ch20）

残るのは「Credential」「検証」「Identity」の3語だけだ。この3語で説明できない認証技術は存在しない。

「特別扱い」を捨てる — 3つの誤解を解体する

よくある感覚
  • 「JWT は Stateless だから Session とは根本的に違う技術」
  • 「OAuth はログインの仕組み。OIDC はその拡張」
  • 「SSH や TLS はインフラの話で、Web 認証とは別世界」
Map で見ると
  • JWT と Session はVerification の箱だけが違う（署名検証 vs lookup）。Credential も Transport も Identity も Authorization も同じ。Stateless は Verification の性質であって、技術の性質ではない
  • OAuth はAuthorization 段の委譲の仕組みで、認証ではない。OIDC が ID Token という Credential を足して初めて認証になる。Google Login は「OIDC で Credential を得て、Session 方式に接続する」だけ
  • SSH は署名検証型の認証で、RS256 JWT・mTLS・Passkey と同じ箱。違うのは Transport が SSH プロトコルであることだけ。SSH を理解していれば Passkey は初見でも分かる

結論：Credential と検証方法が違うだけで、基本構造は共通している。新しい認証技術を「別物」と感じたら、それは Map のどの箱が違うかをまだ特定していないだけだ。

演習 — 本書で扱っていない Passkey（WebAuthn）を7問で分解する

Map が「初見の技術」に効くことを実演する。Passkey は本書のどの章にも出ていないが、7問を埋めれば構造が見える。

Q1 Credential は何？

Authenticator（端末の Secure Enclave / iCloud Keychain）に閉じた秘密鍵で、サーバーの challenge に付けた署名。「署名できるもの」

Q2 誰が発行した？

登録時に Authenticator が鍵ペアを生成。公開鍵をサーバーへ登録。CA も IdP も介在しない（SSH と同じ「自分で作る」型）

Q3 誰が検証する？

自社サーバー（Relying Party）。登録済み公開鍵で署名を検証し、origin / rpId / challenge の一致も見る

Q4 State はどこ？

credentials 表（credential_id, public_key, user_id, sign_count）。Verification ③だが、公開鍵の置き場として State は必要（authorized_keys と同じ）

Q5 期限はどこで管理？

Passkey 自体は無期限。challenge は数分。認証成功後は Session を発行するので、以後の期限は Session 側（ch4）

Q6 どう Identity へ変換？

レスポンスの credential_id → credentials 表 → user_id。SSH の fingerprint → account と同型

Q7 どう Revocation？

credentials 表から該当行を削除。即時。端末紛失時は「その端末の公開鍵」だけを消せる

結論

Passkey = 「SSH 公開鍵認証を Browser で行い、成功したら Session 方式へ接続する」。Map 上では Machine/SSH の隣で、Authorization 段は Human/Password と同じ位置。Phishing 耐性は「origin が署名対象に含まれる」ことから来る

重要なのは、この分解に Passkey 固有の知識がほとんど要らなかったことだ。「③ 署名検証型で、公開鍵を Store に置き、成功後は Session に接続する」という3つの判断ができれば、State・期限・Revocation は自動的に決まる。これが本書で身につけてほしい読み方である。
