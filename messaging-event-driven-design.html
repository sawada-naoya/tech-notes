この本の主張1

非同期化は「速くするため」ではなく「相手の都合と自分の都合を切り離すため」に行う。ユーザーの待ち時間が減るのは結果であって目的ではない。

この本の主張2

メッセージングの全ての難所は「DBとブローカーは同じトランザクションに入らない」という一点に由来する。Outbox・CDC・Saga・Exactly Once は全部この一点への対処。

この本の主張3

Exactly Once は「配信」では存在しない。実在するのは At Least Once 配信 + 冪等な処理 だけ。この理解の有無が、面接でもプロダクションでも決定的な差になる。

01 同期処理 — 全ての出発点であり、全ての問題の出所

結論: 同期処理とは「呼び出した側が、結果が返るまで先に進まない」通信です。単純で、デバッグしやすく、失敗が即座に分かる——だから既定はこれで正しい。問題は、依存先が増えるほど「自分の可用性 = 全依存先の可用性の掛け算」になることです。非同期を学ぶ前に、まず何が壊れるのかを正確に見ます。

☎️ 電話で考える: 「この商品まだ在庫ありますか？」と店に電話する。相手が出て、調べて、答えるまで、あなたは受話器を持って立っている。
効率は悪いが確実——答えが返ってきたなら、それは本当に確認された答えです。
壊れ方: 店が電話に出ない、保留のまま5分待たされる、あなたが待っている間、他の誰にも電話をかけられない。これが同期処理の全ての障害の原型です。

① この技術は何を解決するために生まれたのか

  • ① 「結果を今すぐ知りたい」を満たす — これが本質。ログインできたか、在庫があったか、決済が通ったか。結果に応じて次の分岐が変わる処理は、同期でしか書けない
  • ② 因果関係を単純に保つ — 「A の後に B」がコードの並び順そのままになる。読める、追える、直せる
  • ③ 失敗の所在が明確 — エラーがその場で返る。スタックトレースが1本に繋がる
  • ④ トランザクション境界を作れる — 同一プロセス・同一DBなら ACID で守れる。これは非同期にすると失われる最大の資産
  • ⑤ 追加のインフラが要らない — Broker も worker も監視も不要。運用コストがゼロという点は、非同期の議論で常に過小評価される

② この技術がないと何が問題になるか（＝同期だけで押し通すと何が起きるか）

同期処理は「無いと困る」のではなく「それだけだと困る」技術です。困り方は3つの数式で表せます。

数式意味具体例（予約API）
レイテンシ = Σ(各依存先)待ち時間は足し算で増える。並列化しない限り縮まない在庫80ms + 決済1200ms + メール600ms + OTA同期2000ms + 通知300ms = 4.18秒
可用性 = Π(各依存先)可用性は掛け算で下がる。1つでも落ちれば全部落ちる99.9% を5個直列 = 99.5%（月間3.6時間の停止）
占有 = 同時実行数 × 処理時間遅い処理はゴルーチン・接続・メモリを長時間占有する4秒 × 500rps = 常時2000本のゴルーチンが待機

最も痛いのは2行目です。「メール送信サービスが落ちたので、宿泊予約ができなくなりました」——これは技術的な障害ではなく設計の失敗です。メールは予約の成立条件ではないのに、同期で繋いだせいで成立条件になってしまった。

図1-1: 同期処理の3つの壊れ方。②の「可用性の掛け算」が非同期化の最大の動機であり、③が本番で最も多い事故。

③ 基本概念

Blocking

呼び出し元のスレッド／ゴルーチンが結果を待って停止する。Go では goroutine が block しても OS スレッドは block しない（ランタイムが他の goroutine に切り替える）ので、Ruby/PHP より遥かに耐える。ただし DB接続などの有限資源の占有は同じ。

Request-Response

1つの要求に1つの応答が対応する形式。HTTP・gRPC unary・SQL。「誰に聞いたか」が明確なのが最大の利点。

Coupling（結合）

時間的結合（相手が今動いていること）・空間的結合（相手の住所を知っていること）・データ的結合（スキーマを共有すること）。同期はこの3つ全てを持つ。非同期化とは、このうち時間的結合を外す行為。

Fan-out（同期）

1つの要求から複数の依存先を呼ぶこと。直列にせず並列にするだけで、レイテンシは「合計」から「最大値」に変わる。非同期化の前に、まずこれを試すべき。

Backpressure

処理能力を超えた要求を「断る」仕組み。同期の世界では 429/503 を返すしかない（＝ユーザーが失敗する）。非同期ならキューに積める。

Critical Path

ユーザーへの応答に「本当に必要な」処理の連鎖。非同期設計とは、クリティカルパスを削る作業そのもの。

⑤ 実際のシステム構成でどう使われるか

  • 同期のままにすべきもの — 認証・認可、在庫の引き当て、決済の与信（authorize）、バリデーション、「予約IDを返す」こと。結果がユーザーの次の行動を変えるものは全部同期
  • 同期にしてはいけないもの — メール・SMS・Push通知、画像やPDFの生成、検索インデックス更新、レコメンド再計算、分析基盤への転送、外部システムへの同期反映、監査ログの永続化
  • 判断がグレーなもの — 決済の確定（capture）。予約時に確定するなら同期、チェックイン時に確定するなら非同期。ビジネス要件が決める
  • 典型的な構成 — API Gateway → アプリ（同期処理のみ）→ DB。同時に outbox へ書き、Relay が Broker へ。非同期処理は worker が担当（18章）

⑥ メリット

  • 単純さ — これが最大かつ唯一の、しかし極めて強力な利点。コードの並び順 = 実行順。障害調査でログを1本追えば終わる
  • 強い整合性が得られる — 同一DBのトランザクション内なら、部分的な成功が存在しない
  • エラーをユーザーに即返せる — 「在庫がありません」をその場で伝えられる。非同期だと後からメールで謝ることになる
  • 運用コストゼロ — Broker の可用性・DLQの監視・consumer lag のアラート・再処理の手順書、これら全部が不要
  • テストが容易 — 入力に対して出力が決まる。結合テストが書きやすい

⑧ 実務での利用例

  • Stripe の決済API — 与信は同期、Webhook は非同期という綺麗な分離。POST /v1/payment_intents は同期で結果を返すが、その後の状態遷移（3Dセキュア完了・入金確定・返金）は全部 Webhook で通知される
  • Amazon の「注文を確定する」 — 在庫引き当てと与信だけ同期。梱包指示・配送手配・レコメンド更新・レビュー依頼メールは全部非同期
  • Booking.com の予約 — 在庫確認は同期（ダブルブッキングは許されない）。宿泊施設への通知・OTA間の在庫同期は非同期
  • よくある失敗の実例 — 「サンクスメールを同期送信していたら、SendGrid の障害で会員登録が全部失敗した」。これは実在の事故パターンで、レビューで最初に指摘すべき箇所

⑨ Googleレベルではどう設計されるか

  • Deadline の伝播が標準 — gRPC の Deadline がリクエスト全体で伝播し、上流が諦めた瞬間に下流も停止する。「誰も待っていない処理を続けない」のが徹底されている
  • Critical / Sheddable の分類 — Google のサービスは全リクエストに criticality ラベルを付ける。過負荷時は sheddable なものから捨てる。「全部同じ重要度」という前提を置かない
  • 同期呼び出しの深さに上限を設ける — サービス間の呼び出しチェーンが深くなるとレイテンシと障害率が悪化するため、チェーンの深さ自体を SLO の対象にする
  • SRE Book の視点 — 「依存関係のグラフを描き、各エッジが hard dependency か soft dependency かを明示する」。soft dependency を同期で繋いでいたら設計ミスとして扱われる

⑩ システム設計面接ではどう問われるか

  • Q: 「この処理を同期にする理由は？」 → 「結果がユーザーの次の行動を変えるから」と答える。「速いから」は不正解
  • Q: 「依存が5個ある API の可用性は？」 → 掛け算で計算し、hard/soft dependency に分けて soft を非同期に落とす提案まで持っていく
  • Q: 「外部APIが遅くなったらどうなる？」 → 資源枯渇 → 無関係な API も死ぬまで言えると強い。対策は Timeout + Bulkhead + Circuit Breaker のセット
  • 評価される姿勢 — いきなり Kafka を描かない。「まず何が同期で必須かを列挙する」から始める候補者は、ほぼ確実に高評価になる

02 非同期処理 — 「後でやる」の技術

結論: 非同期処理とは「依頼を受け付けた事実だけを確定させ、実行は別の時間・別のプロセスに委ねる」ことです。得られるのは、依存先の障害と遅延からの独立。支払うのは、「終わったかどうかが分からない」という永続的な不確実性です。この章では「何を非同期にすべきか」の判断基準を作ります。

📮 宅配便の営業所で考える: あなたが荷物を出すとき、相手に届くまで窓口で待ちはしません。伝票を受け取った時点で「受付完了」であり、以後の配達は運送会社の責任です。
ここで交換されたもの: あなたは「すぐ帰れる自由」を得た代わりに、「今この瞬間、荷物がどこにあるか分からない」状態を受け入れた。だから運送会社は追跡番号を発行する。
追跡番号のない非同期処理は、事故です。ジョブID・ステータス取得API・進捗通知は、非同期化とセットで設計します。

① この技術は何を解決するために生まれたのか

  • ① 時間的結合の切断 — これが本質。「相手が今動いていること」を、自分が動く条件から外す。相手が落ちていても、自分は仕事を受け付けられる
  • ② クリティカルパスの短縮 — ユーザーの待ち時間を「本当に必要な処理」だけにする
  • ③ 負荷の平準化（Load Leveling） — スパイクをキューで吸収し、後ろは一定速度で処理する。これはスケールアウトでは解決できない種類の問題
  • ④ 失敗の再試行を仕組みに委ねる — 「失敗したら後でもう一度」を、アプリのコードではなくインフラの責務にする
  • ⑤ 1つの事実に対する処理の追加を、既存コードの変更なしに行う — イベント駆動の本領（8章）

② この技術がないと何が問題になるか

1章で見た3つの壊れ方に加えて、「スパイクを受け止める場所がない」という問題があります。

図2-1: キューは負荷を「失敗」から「遅延」に変換する装置。ただし平均処理能力が流入を上回っていることが絶対条件。

③ 基本概念 — 非同期の4つの型

型やり方使いどころ致命的な弱点
① goroutine で投げっぱなしgo func(){ sendMail() }()ほぼ無いプロセスが死んだら消える。リトライも監視もない。本番では禁止に近い
② DBをキューにするjobs テーブル + SELECT ... FOR UPDATE SKIP LOCKED小〜中規模。既存DBのトランザクションに乗るのが最大の利点数千 rps 程度で DB がボトルネックに。ポーリングの無駄
③ マネージドキューSQS / Cloud Tasks / RabbitMQジョブ実行の既定解。メール・画像変換・外部API呼び出しDBと別トランザクション → Dual Write 問題（17章）
④ ログ型ブローカーKafka / Kinesis / Pub/Sub複数の購読者・再生・イベント駆動アーキテクチャ全般運用が重い。小規模には過剰

①は「非同期にした」ではなく「エラーを握り潰した」だけです。Go は go が1文字で書けてしまうため、この事故が非常に多い。永続化されないものは非同期処理と呼ばない——これを原則にしてください。

④ 内部でどのように動くのか — 「投げっぱなし」と「キュー」の決定的な差

03 Message Queue — 預かって、確実に配る装置

結論: Message Queue とは「送り手と受け手の間に立ち、メッセージを永続化し、受け取り確認が返るまで消さない仲介者」です。価値の中心は『速さ』ではなく『消えないこと』と『再試行してくれること』。この章で、Queue と Topic の違い、Ack の意味、Visibility Timeout という最重要概念を押さえます。

📦 宅配便の営業所で考える: 荷物を預かった営業所は、受取人のサインをもらうまで「配達完了」にしません。不在なら持ち帰って翌日また行く。
配達中の荷物は、他の配達員には見えない——これが Visibility Timeout。ただし配達員が事故で戻ってこなければ、その荷物は再び「配達可能」に戻る。
ここに二重配達の芽がある: 配達員が荷物を渡した直後に倒れてサインを持ち帰れなかったら、営業所はもう一度配達に行きます。受取人は同じ荷物を2回受け取る。10章・11章の話は全部ここから始まります。

① この技術は何を解決するために生まれたのか

  • ① メッセージの永続化 — これが本質。プロセスが死んでも、デプロイしても、依頼が消えない。「go func で投げっぱなし」との決定的な差はここだけ
  • ② 受け取り確認（Ack）による配達保証 — 処理が完了したという signal が返るまで、メッセージを消さない
  • ③ 再試行の自動化 — 失敗したメッセージを、指定時間後に自動で再配信する
  • ④ 流量の緩衝 — 送り手の速度と受け手の速度を切り離す（2章の Load Leveling）
  • ⑤ 作業の分配 — 複数の worker に自動で振り分ける。worker を増やすだけでスループットが上がる（Competing Consumers パターン）

③ 基本概念 — Queue と Topic、そして Ack

図3-1: Queue と Topic の違い、そしてメッセージのライフサイクル。Visibility Timeout の理解が10章以降の前提になる。

Producer / Consumer

送る側と受け取る側。Broker はこの2者が互いを知らなくても成立させる。

Ack / Nack

「処理した／できなかった」の通知。受信した瞬間に ack するか、処理完了後に ack するかで配信保証が変わる（10章）。

Visibility Timeout

受信されたメッセージが他の consumer から隠される時間。処理時間より短いと二重処理、長すぎると障害時の復旧が遅い。

Prefetch / Batch Size

1回の受信で何件取るか。大きくするとスループットが上がるが、1件失敗したときの巻き添えが増える。

Queue Depth（滞留数）

未処理メッセージの数。これと「最古メッセージの年齢」が最重要メトリクス。

Competing Consumers

複数の worker が同じ Queue から取り合う構成。worker を増やすだけで水平スケールする——ただし順序は保証されなくなる。

Message TTL

メッセージの消費期限。「3日前の在庫更新通知」を今更処理しても害しかないケースがある。

Priority Queue

優先度付き。実装は「キューを分ける」ほうが確実——単一キュー内の優先度は多くの実装で弱い。

⑤ 実際のシステム構成でどう使われるか

  • 基本形 — API（producer）→ Queue → Worker（consumer）→ 外部サービス。Worker は Auto Scaling で Queue Depth に応じて増減させる
  • Queue Depth ベースのオートスケール — CPU ではなく「滞留数 ÷ worker数」で判断する。AWS なら ApproximateNumberOfMessagesVisible をターゲット追跡に使う
  • キューの分割 — 重い処理と軽い処理を同じキューに入れない。動画変換（10分）とサムネイル生成（2秒）が同居すると、サムネイルが動画待ちで詰まる（Head-of-Line Blocking）
  • テナント分離 — 大口顧客の大量投入が他の顧客を詰まらせる（Noisy Neighbor）。キューを分けるか、消費レートに上限を設ける
  • FIFO キュー vs 標準キュー — SQS FIFO は順序と重複排除を提供するがスループットが桁違いに低い（標準は実質無制限、FIFOは 300 msg/s ※バッチで3000）

⑥ メリット

  • メッセージが消えない — 最大の価値。デプロイ・クラッシュ・障害を跨いで生き残る
  • リトライがインフラの機能になる — アプリコードから再試行ロジックが消える
  • worker を増やすだけでスケールする — コード変更なしにスループットを上げられる
  • producer と consumer を別々にデプロイできる — worker のデプロイ中もメッセージは溜まるだけ
  • DLQ で「壊れたメッセージ」を隔離できる — 1件の不正データが全体を止めない（13章）

⑦ デメリット・トレードオフ

  • 新しい単一障害点 — Broker が落ちたら全部止まる。マネージド（SQS/Pub/Sub）を選ぶ最大の理由がこれ
  • Dual Write 問題 — 「DB に書いて、Queue にも送る」は原子的にできない（17章）。Queue を導入した瞬間に必ずこの問題が発生する
  • 順序が保証されない — 標準キューは順序を保証しない。「更新」が「作成」を追い越す
  • 重複が発生する — At Least Once が既定。冪等性が必須になる
  • Poison Message — 処理できないメッセージが無限に再配信され、キューを占拠する。DLQ がないと詰まる
  • 可観測性の低下 — 「今どこで何件処理中か」が見えにくい。専用の監視設計が要る
  • コストの見落とし — SQS はリクエスト課金。ショートポーリングで空振りを繰り返すと、何もしていないのに課金される。ロングポーリングは必須

⑧ 実務での利用例

  • Amazon の注文処理 — SQS の起源そのもの。注文確定後の梱包指示・配送手配・在庫補充がキュー経由。2004年から公開サービス化された、最も古いAWSサービスの1つ
  • Airbnb — 予約後の各種通知・写真処理に大量のキューを使用。キューごとにSLO（処理遅延の上限）を定義している
  • Instagram — 投稿後のフィード配信・通知処理。Python の Celery + RabbitMQ から始まり、規模拡大に伴い独自基盤へ
  • 典型的な事故 — 「動画変換キューが詰まって、サムネイル生成も止まった」。処理時間の桁が違うジョブを同居させた結果。キュー分割で解決する

⑨ Googleレベルではどう設計されるか

  • キューは「無限」ではないと扱う — 滞留数に上限を設け、超えたら producer 側で load shedding する。無限に積める設計は、障害時に無限に遅れる設計と同義
  • Drain 時間を常に監視 — 「今の滞留を処理し切るのに何分か」= 滞留数 ÷ 処理レート。これが SLO を超えたらアラート（絶対数ではなく時間で見る）
  • Cloud Tasks の設計思想 — タスク単位で「いつ実行するか」「最大何回リトライするか」「最大同時実行数」を個別に指定できる。キュー単位ではなくタスク単位の制御が Google 的
  • 優先度は「キューを分ける」で実現 — 単一キューの優先度フィールドは飢餓（starvation）を生むため、物理的に分離して worker の配分で制御する

⑩ システム設計面接ではどう問われるか

  • Q: 「Queue と Topic の違いは？」 → 「1メッセージを1人が処理するか、全員が受け取るか」。さらに「仕事の分配 = Queue、事実の通知 = Topic」と用途で言い換えられると強い
  • Q: 「worker がクラッシュしたらメッセージはどうなりますか？」 → Visibility Timeout 満了で再配信される → 二重実行のリスク → 冪等性が必要、まで一息で言えるか
  • Q: 「Visibility Timeout はどう決めますか？」 → 処理時間の P99 の3倍。長時間処理は heartbeat で延長。この質問に答えられる候補者は実装経験があると判断される

  • Q: 「キューを1本にしますか、分けますか？」 → 処理時間の桁・優先度・テナントで分ける。Head-of-Line Blocking を挙げる

⚠ 「イベント駆動にすべきでない」ケースを言語化する

  • 購読者が1つしかなく、今後も増えないと分かっている — それは「命令」であって「イベント」ではない。Queue か、そもそも同期呼び出しでよい
  • 強い整合性が要件 — 「送金元から引いて送金先に足す」を非同期にすると、途中の状態が見える。Saga で許容できるかを先に検討する（20章）
  • チームが小さく、運用体制がない — Kafka の運用は片手間ではできない。SQS か DB キューから始めるのが誠実
  • 処理の全体像を人が追う必要が頻繁にある — イベント駆動は「誰が何をしたか」が分散する。分散トレーシングを最初に入れられないなら、時期尚早
  • 逆に、イベント駆動にすべき明確な signal — 「新機能を追加するたびに、既存サービスのコードを変更している」。これが出たら Topic 化のタイミング

05 Kafka — 「消さないキュー」という発想の転換

結論: Kafka はキューではなく「追記専用のログ（台帳）」です。読まれてもメッセージは消えず、保持期間まで残る。この一点から、複数購読・巻き戻し・再生・順序保証という Kafka の全ての性質が導かれます。逆に、1件ずつの細かい制御（優先度・個別の再配信・遅延実行）は苦手です。

📖 図書館の新聞の縮刷版で考える: 新聞は読まれても消えません。誰が何日分まで読んだかは、読者が自分の「しおり」で管理する。
A さんは今日の朝刊まで、B さんは3日前まで読んでいる——新聞側は誰がどこまで読んだかを気にしない。読者が増えても新聞の仕事は変わらない。
新しく入った読者は、1ヶ月前から読み直せる（＝再生）。ただし保管期限を過ぎた号は捨てられる（＝ retention）。これが Kafka の全てです。

① この技術は何を解決するために生まれたのか

Kafka は LinkedIn で2010年頃、「サービス間のデータ連携が N×N のスパゲッティになった」という問題から生まれました。

  • ① N×N の連携を N+M に減らす — これが原点。各システムが互いに直接繋ぐのをやめ、「全部一旦 Kafka に流す」ことで、連携数が掛け算から足し算になる
  • ② 1つのデータを複数の用途で使う — 同じ「クリックログ」を、リアルタイム集計・機械学習・監査・データウェアハウスがそれぞれのペースで読む
  • ③ 再処理を可能にする — 集計ロジックにバグがあったとき、過去1週間分を巻き戻して再計算できる。従来のキューでは不可能
  • ④ 超高スループット — 1台で秒間数十万メッセージ。ディスクへのシーケンシャル書き込み + ゼロコピーで実現している
  • ⑤ 順序の保証（局所的に） — 同じキーのメッセージは必ず同じ順序で処理される

② この技術がないと何が問題になるか

図5-1: Kafka の原点は「スループット」ではなく「連携の数を減らすこと」。この視点は面接で差がつく。

③ 基本概念 — 5つの用語だけ覚える

Topic

メッセージのカテゴリ。「reservation.confirmed」のように「名詞.過去形の動詞」で命名するのが慣習。

Partition

Topic を分割した単位。並列度の上限 = partition 数。順序は partition の中でだけ保証される。

Offset

partition 内の連番。「どこまで読んだか」を表す、ただの整数。consumer が管理する。

Consumer Group

協調して読むグループ。同じ group 内では1 partition を1 consumer だけが読む。group を分ければ同じデータを何度でも読める。

Key

partition の割り当てに使う値。同じ key は必ず同じ partition へ = 同じ key の順序が保証される。これが Kafka 設計の最重要判断。

Retention

保持期間（既定7日）またはサイズ上限。期限を過ぎると、読まれていなくても消える。

Replication Factor

各 partition の複製数（通常3）。1台壊れてもデータは残る。min.insync.replicas=2 と acks=all をセットで使う。

Log Compaction

同じ key の古い値を削除し、最新の値だけ残すモード。「現在の状態」を表す topic に使う（例: 商品マスタ）。

⑤ 実際のシステム構成でどう使われるか

  • 中央イベントバス — 全サービスが「起きた事実」を publish し、必要なサービスが購読する。Netflix / Uber / LinkedIn の基本形
  • CDC の受け皿 — Debezium が DB の変更ログを Kafka に流し、検索インデックス・キャッシュ・DWH がそれを購読する（19章）
  • ストリーム処理の入力 — Kafka Streams / Flink で集計・結合・ウィンドウ処理を行い、結果を別 topic に出す
  • topic の設計指針 — 「1 topic = 1つの意味を持つイベント」。reservation.confirmed, payment.captured のように分ける。「全部 events topic に入れる」は最悪——購読者が不要なメッセージを全部読むことになる
  • partition 数の決め方 — 目標スループット ÷ 1 partition あたりの処理能力。迷ったら多め（12〜24）にする。後から減らせないが、増やすと順序が壊れるため
  • 3層構成 — raw topic（生データ、長期保持）→ processed topic（整形済み）→ aggregate topic（集計結果）。層ごとに保持期間を変える

⑥ メリット

  • 再生できる — 他のキューにない決定的な強み。バグ修正後に過去データを再処理、新サービスの初期データ投入、障害復旧が全部「offset を巻き戻す」で済む
  • 複数の購読者が独立して読める — consumer group を分けるだけ。producer は無関係
  • 圧倒的なスループット — シーケンシャル書き込み + ページキャッシュ + ゼロコピー（sendfile）で、1台で数十万 msg/s
  • key 単位の順序保証 — 同一 key は必ず順序どおり
  • 長期保持がストレージ次第で可能 — Tiered Storage を使えば数ヶ月〜数年も現実的
  • エコシステム — Kafka Connect（各種DBへの入出力）、Schema Registry、Kafka Streams が揃っている

⑧ 実務での利用例

  • Uber — 乗車リクエスト・ドライバー位置・料金計算のイベントを Kafka で。uReplicator という独自のクロスDCレプリケーション基盤も開発
  • Twitter(X) — 長らく独自の EventBus（DistributedLog ベース）を使っていたが、2021年頃に Kafka へ移行。理由は「エコシステムと運用コスト」——独自基盤の維持より、Kafka の Kafka Streams / Connect を使うほうが総コストが低いと判断された
  • Airbnb — サービス間のイベント連携基盤 SpinalTap（CDC）→ Kafka の構成。DB の変更が自動的にイベントになる

⑨ Googleレベルではどう設計されるか

  • Google 社内は Kafka ではなく Pub/Sub（+ その前身の PubSub2） — 「partition という概念をユーザーに見せない」設計思想。スケールは自動、順序は ordering key でオプトイン。「運用を利用者に押し付けない」という思想の差
  • スキーマの強制 — Protobuf + Schema Registry で、後方互換性のない変更を CI で弾く。イベントは一度公開したら API と同じ。壊すと全購読者が死ぬ
  • イベントの命名と所有権 — topic ごとにオーナーチームを定義し、スキーマ変更にはレビューが必須。「誰でも publish できる共有 topic」は禁止
  • Consumer Lag を SLO 化 — 「99%のイベントは publish から30秒以内に処理される」を SLI として定義し、エラーバジェットで管理する
  • Dataflow（Beam）との組み合わせ — ストリーム処理は Watermark と Windowing の概念で「遅れて来たデータ」を明示的に扱う。「イベント時刻」と「処理時刻」を区別するのが Google 流

⑩ システム設計面接ではどう問われるか

  • Q: 「Kafka と SQS、どちらを使いますか？」 → 「再生が必要か」「購読者が複数か」の2点で切る。単なるジョブ実行なら SQS。「Kafka のほうが速いから」は減点
  • Q: 「partition のキーは何にしますか？」 → これが Kafka の面接で最も重要な質問。「順序を守りたい単位」を答える。同時に「そのキーは偏らないか（hot partition）」まで言及する。例: 大手ホテル1社に予約が集中すると1 partition だけ詰まる
  • Q: 「consumer を増やしてもスループットが上がりません。なぜ？」 → partition 数が上限だから。partition を増やすか、処理自体を並列化する
  • Q: 「重複処理をどう防ぎますか？」 → 防げない。At Least Once を前提に consumer を冪等にする（11章）
  • Q: 「Kafka が落ちたら？」 → producer 側で一時的にローカルバッファ or DB の outbox に溜める（18章）。「Kafka は落ちない前提」で設計しない
  • Q: 「1件だけ処理に失敗し続けたら？」 → その partition が止まる（Head-of-Line Blocking）。retry topic / DLQ に逃がして先に進む

06 RabbitMQ — 賢いルーティングを持つ「郵便局」

結論: RabbitMQ は「メッセージを1件ずつ丁寧に配る」ことに最適化されたブローカーです。強みは柔軟なルーティング（Exchange）と、1件単位の細かい制御——優先度・遅延・個別の再配信・per-message TTL。弱みは、読まれたメッセージが消えること（再生できない）と、超大規模でのスループット。

📮 郵便局の仕分け場で考える: 手紙は「宛名」だけでなく「郵便番号」「速達か普通か」「地域」で仕分けられます。この仕分けルールを自由に組めるのが RabbitMQ の Exchange。
Kafka との決定的な違い: 郵便局は配達し終えた手紙のコピーを保管しません。「先月の手紙をもう一度配って」は不可能。
逆に「この手紙は速達で」「この手紙は3日後に配達」「この手紙は5回配達を試みてダメなら返送」といった1通ごとの細かい指示は RabbitMQ の得意分野です。

① この技術は何を解決するために生まれたのか

  • ① 柔軟なルーティング — これが本質。「どのメッセージを、どのキューに入れるか」を、producer のコードを変えずに設定で変えられる
  • ② 1件単位の配信制御 — 優先度・TTL・遅延配信・個別の再送。Kafka では offset が連番なので原理的にできないこと
  • ③ 標準プロトコル（AMQP）による相互運用 — 言語・ベンダーに依存しない
  • ④ 確実な配信の追求 — Publisher Confirm・Consumer Ack・永続化キューの組み合わせで、メッセージの消失を防ぐ
  • ⑤ RPC 的な使い方も可能 — reply-to と correlation-id で「非同期だが応答がある」パターンを標準サポート

② この技術がないと何が問題になるか

RabbitMQ が無い場合、ルーティングのロジックが producer のコードに埋まります。「このイベントは A と B に送る」を producer が知っているということは、購読者が増えるたびに producer を変更するということです。

要件Exchange なしだとRabbitMQ なら
「日本の予約だけ通知したい」consumer 側で全件受けてフィルタ（無駄な転送）topic exchange で reservation.jp.* だけ bind
「VIP顧客の処理を優先」キューを物理的に分けて producer が振り分けpriority キュー or routing key で分岐
「10分後に再送」アプリで sleep（worker を占有）TTL + Dead Letter Exchange で遅延キュー
「3回失敗したら隔離」DBで試行回数を管理x-death ヘッダーで自動カウント → DLX

⑤ 実際のシステム構成でどう使われるか

  • 典型構成 — API → events exchange (topic) → 用途別のキュー → 各 worker。exchange を1つ、キューを用途ごとに作るのが基本形
  • リトライ階層 — work → 失敗 → retry.30s → retry.5m → retry.1h → dlq。x-death ヘッダーの回数で振り分ける
  • Quorum Queue — RabbitMQ 3.8+ の推奨。Raft ベースで、旧来の Mirrored Queue より障害時の挙動が正しい。新規なら必ず Quorum Queue を選ぶ
  • クラスタ構成 — 3ノード以上の奇数。ネットワーク分断時の split-brain 対策（pause_minority）を必ず設定する
  • Lazy Queue — メッセージをメモリに載せずディスクに置くモード。大量に溜まる可能性があるキューでは必須（メモリ枯渇でブローカー全体が停止するのを防ぐ）

⑥ メリット

  • ルーティングの柔軟性 — producer を変えずに配信先を変更できる。他のどのブローカーよりも強力
  • 1件単位の制御 — 優先度・TTL・遅延・個別 nack。Kafka が原理的にできない領域
  • 低レイテンシ — メッセージ数が少ない状態では、Kafka よりレイテンシが小さい
  • 成熟した管理UI — キューの状態・滞留・スループットがブラウザで見える。運用の初期コストが低い
  • DLX が標準機能 — 設定だけで DLQ とリトライ階層が作れる
  • RPC パターンの標準サポート — reply-to / correlation-id

⑦ デメリット・トレードオフ

  • 再生できない — 読まれたら消える。「バグを直して過去1週間を再処理」ができない。これが Kafka との最大の違い
  • 大量滞留に弱い — メッセージがメモリに載るため、数百万件溜まるとブローカーが不安定になる。Lazy Queue で緩和するが、Kafka のような「溜めても平気」ではない
  • スループットの上限 — 1キューあたり数万 msg/s 程度。Kafka の数十万には届かない
  • キューがスケールの単位 — 1つのキューは1ノードに置かれる（Quorum Queue でも leader は1つ）。「1本の巨大キュー」は水平スケールしない
  • クラスタ運用の難しさ — ネットワーク分断時の挙動が複雑。Erlang の知識が要求される場面がある
  • 順序保証が弱い — 複数 consumer で並列消費すると順序は崩れる。Single Active Consumer を使えば守れるが、並列度が1になる

⑧ 実務での利用例

  • Instagram（初期） — Django + Celery + RabbitMQ で、フィード配信・通知を処理。スタートアップの標準構成だった
  • Reddit — 投票の集計・コメントツリーの更新に長年 RabbitMQ を使用
  • 決済系のバックオフィス — 「1件ずつ確実に、失敗したら段階的に再送、最終的に人が見る」という要件に RabbitMQ の DLX が最適
  • OTA連携 — 「施設ごとに順序を守りつつ、失敗したら5分後・30分後・2時間後に再送、それでもダメなら運用チームへ」——これは RabbitMQ の得意領域そのもの
  • 典型的な事故 — 「Nack(requeue=true) で無限ループし、CPU 100% でブローカーが停止」。RabbitMQ で最も多い事故

⑨ Googleレベルではどう設計されるか

  • Google 社内で RabbitMQ 相当の役割を担うのは Cloud Tasks — 「タスク単位で実行時刻・リトライ回数・同時実行数を制御する」という思想は RabbitMQ より徹底している
  • 「ブローカーにビジネスロジックを持たせない」 — 複雑な routing key の設計は、実質的にビジネスロジックの分散を意味する。Google 系の設計では、ルーティングは単純に保ち、フィルタは consumer 側で行うことが多い
  • スケールの単位を「キュー」にしない — Cloud Tasks / Pub/Sub は内部で自動的に分散する。「キューが1ノードに乗る」という制約自体を設計から排除している
  • 示唆 — RabbitMQ を選ぶなら、「1キューの限界（数万msg/s、数百万件）を超えない規模である」という確信が必要。超える見込みがあるなら最初から Kafka か Pub/Sub

⑩ システム設計面接ではどう問われるか

  • Q: 「Kafka ではなく RabbitMQ を選ぶ理由は？」 → ①遅延実行・優先度など1件単位の制御が必要 ②複雑なルーティングが必要 ③再生は不要 ④規模が数万msg/s以下。この4点を挙げられれば十分
  • Q: 「メッセージが失われないことをどう保証しますか？」 → 4つ全部が必要: ①Publisher Confirm ②DeliveryMode=Persistent ③Durable Queue ④手動 Ack。1つでも欠けると失われる
  • Q: 「リトライはどう実装しますか？」 → TTL + Dead Letter Exchange で階層化。「Nack(requeue=true)」と答えると無限ループを知らないと判断される
  • Q: 「キューが詰まってブローカーが落ちました」 → メモリにメッセージが載るため。Lazy Queue / 最大長（x-max-length）の設定 / consumer のスケール

07 Amazon SQS — 「運用しなくていいキュー」の完成形

結論: SQS は機能を極限まで削ることで、運用ゼロ・実質無制限のスケールを実現したキューです。サーバもクラスタもない。容量計画も不要。落ちない。代わりに、再生も、複雑なルーティングも、push 配信もない。「非同期ジョブを動かしたいだけ」なら、これが最も正しい選択です。

📦 コインロッカーで考える: 誰かが荷物を入れ、誰かが取り出す。ロッカーの管理人は存在しない——壊れることも、満杯になることもない。
代わりにできないこと: 「取り出された荷物をもう一度見る」（再生なし）、「この荷物を優先的に」（優先度なし）、「Aさんに通知して」（push なし）。
この割り切りが SQS の設計思想です。「キューに求められる80%の機能を、運用コストゼロで提供する」。

① この技術は何を解決するために生まれたのか

  • ① キューの運用そのものを消す — これが本質。ブローカーの障害・容量・パッチ・スケールという「本業ではない仕事」を全部 AWS に渡す
  • ② 事実上無制限のスケール — 標準キューはスループット無制限。「秒間100万件送っても壊れない」という前提でアーキテクチャを組める
  • ③ 従量課金 — 使わなければ0円。アイドル時にコストが発生しないのは Kafka/RabbitMQ にはない性質
  • ④ AWS 統合 — Lambda のトリガー、Auto Scaling のメトリクス、SNS からの配信先、EventBridge のターゲット
  • ⑤ シンプルな API — Send / Receive / Delete / ChangeVisibility の4つで完結する

② この技術がないと何が問題になるか

自前で Kafka や RabbitMQ を運用する場合、以下が全部あなたの仕事になります。

作業自前運用SQS
クラスタ構築3ノード以上、AZ分散、ネットワーク設計URL を1つ作るだけ
容量計画ディスク・メモリ・partition 数の見積もり不要（無制限）
バージョンアップローリング再起動、互換性検証不要
障害対応深夜のページャー、split-brain の復旧AWS の仕事
スケールノード追加、partition 再配置自動
監視Prometheus + Grafana の構築CloudWatch に最初からある

面接でも実務でも、この「運用コスト」を計算に入れない議論は未熟だと見なされます。「Kafka のほうが高機能」は正しいが、「その機能を使わないなら、運用コストぶんだけ損をしている」。

⑤ 実際のシステム構成でどう使われるか

  • SNS → SQS のファンアウト — これが AWS の定番パターン。SNS topic に publish し、複数の SQS キューが購読する。「Pub/Sub の柔軟性」と「キューの永続性・リトライ」を両立する（8章）

⑥ メリット

  • 運用ゼロ — 最大の価値。障害対応・容量計画・バージョンアップが全部不要
  • 実質無制限のスケール（標準キュー）— スパイクを気にしなくてよい
  • アイドル時のコストがゼロ — Kafka/RabbitMQ は使わなくてもインスタンス代がかかる
  • 14日間の保持 — consumer が2週間止まっても、メッセージは残る
  • DLQ が設定だけで作れる — Redrive Policy を書くだけ。DLQ からの再投入（Redrive）もコンソールでできる
  • AWS エコシステムとの統合 — Lambda・Auto Scaling・CloudWatch が最初から繋がっている

⑦ デメリット・トレードオフ

  • 再生できない — 削除したら終わり。「先月のデータを再処理」は不可能。これが必要なら Kafka か Kinesis
  • 1つのメッセージは1つの consumer だけ — 複数の購読者が必要なら SNS や EventBridge を前に置く必要がある
  • pull のみ（push できない） — consumer が能動的に取りに行く必要がある。ロングポーリングで緩和されるが、レイテンシは Kafka より大きい（数十ms〜）
  • メッセージサイズ 256KB 上限 — 大きいデータは S3 に置き、キューには参照だけ入れる（Claim Check パターン）
  • 順序保証は FIFO のみ、しかも低スループット
  • 優先度がない — キューを分けるしかない
  • AWS ロックイン — API が独自。移行は容易ではない

⑧ 実務での利用例

  • Amazon 自身 — 注文処理・在庫更新・配送手配。SQS は Amazon の内部システムから生まれ、2004年に公開された最古の AWS サービスの1つ
  • Netflix — エンコーディングジョブの分配に SQS を使用。数千の worker が同じキューから取り合う典型的な Competing Consumers
  • Airbnb — 写真のリサイズ・メール送信・外部連携。SNS→SQS のファンアウトが基本形
  • 典型的な事故① — 「Visibility Timeout が処理時間より短く、同じ画像を10個の worker が変換していた」。CloudWatch の NumberOfMessagesReceived が異常に多いことで発覚する
  • 典型的な事故② — 「DLQ を設定していなかったので、壊れた1件が永久にリトライされ、CloudWatch の請求が跳ねた」
  • 典型的な事故③ — 「ショートポーリングで空振りし続け、SQS の請求が月数万円になった」

⑨ Googleレベル（AWS/GCP レベル）ではどう設計されるか

  • SQS の内部 — メッセージは複数のサーバに冗長化して保存される。順序が保証されないのは「速いコピーから返す」ため——つまり可用性と順序のトレードオフを、可用性側に振り切った設計
  • Amazon Builders' Library の視点 — 「キューは負荷の緩衝材だが、障害時には『毒』にもなる」。障害中に溜まったメッセージが、復旧直後に一気に流れ込んで再度落とす（Thundering Herd）
  • 対策 — 復旧時は consumer の同時実行数を段階的に上げる。古すぎるメッセージは処理せず捨てる判断も設計に入れる
  • 「キューの深さ」ではなく「最古メッセージの年齢」で監視 — ApproximateAgeOfOldestMessage が本当に見るべきメトリクス。深さは処理レートによって意味が変わるが、年齢はユーザー影響に直結する

⑩ システム設計面接ではどう問われるか

  • Q: 「なぜ Kafka ではなく SQS？」 → 「再生も複数購読も不要で、単に非同期ジョブを流したいから。運用コストが決定的に違う」
  • Q: 「複数のサービスに同じイベントを届けたい」 → SNS → 複数 SQS のファンアウト。SQS 単体ではできないことを知っているかが問われる
  • Q: 「順序が必要ならどうしますか？」 → FIFO + MessageGroupId。ただし 300msg/s の制約を必ず言及する。それを超えるなら「順序に依存しない設計（version 比較）」に変える
  • Q: 「10MBの画像をキューで送りたい」 → Claim Check パターン: S3 に置いて、キューには S3 のキーだけ入れる。256KB 制限を知っているかのチェック
  • Q: 「障害から復旧したら大量のメッセージが溜まっていました」 → Thundering Herd。同時実行数を絞りながら段階的に流す・古いメッセージは捨てる

08 SNS / Google Pub/Sub — 「事実を配る」ためのマネージド Topic

結論: SNS と Pub/Sub は「1つのメッセージを、複数の宛先に配る」ためのマネージドサービスです。SNS は『配るだけ』で保持しない。Pub/Sub は『配って、確認が返るまで保持する』——この差が使い方を決めます。SNS を単体で使うと、購読先が落ちていたときにメッセージが失われます。

📢 SNS = 館内放送、Pub/Sub = 回覧板で考える。
館内放送（SNS）: 全員に一斉に伝わるが、その場にいなかった人には届かない。放送は保存されない。
回覧板（Pub/Sub）: 各人のポストに入れられ、読んで印鑑を押すまで残る。留守でも後で読める。
だから AWS では「SNS → SQS」という組み合わせが定番になります。放送を各人のポスト（SQS）に転記しておくわけです。

① この技術は何を解決するために生まれたのか

  • ① 送り手を受け手から完全に切り離す — これが本質。producer は「誰が聞いているか」を一切知らない。購読者を追加しても producer のコードは1行も変わらない
  • ② 1つの事実に対する処理の追加コストをゼロにする — 「予約が確定したらポイントも付与したい」→ subscriber を1つ足すだけ
  • ③ 扇形の配信（fan-out）を仕組みにする — producer が N 回送るのではなく、1回送れば N 箇所に届く
  • ④ 異種の宛先を統一的に扱う — SNS なら SQS・Lambda・HTTP エンドポイント・Email・SMS へ同じ API で配れる

② この技術がないと何が問題になるか

図8-1: SNS 単体の危険性と、SNS→SQS ファンアウト。Pub/Sub は両者を統合したモデルを持つ。

③ 基本概念

Topic

publish 先。1つの「事実の種類」に1 topic。

Subscription（Pub/Sub）

topic に紐づく「読み口」。各 subscription が独立した未読状態を持つ——Kafka の consumer group に相当。

Subscription（SNS）

配信先の登録。SQS・Lambda・HTTPS・Email・SMS。SNS 側にメッセージは保持されない。

Message Filtering

属性でフィルタして、必要な subscriber にだけ配る。SNS の Filter Policy / Pub/Sub の filter。不要な配信のコストと処理を削減できる。

Push vs Pull

Pub/Sub は両方選べる。push は「相手のエンドポイントに HTTP POST する」ので、相手のスケールを超えると 429 の嵐になる。pull のほうが流量制御しやすい。

Ordering Key（Pub/Sub）

Kafka の key と同じ。同じ ordering key のメッセージは順序どおりに配信される。オプトインなので、必要な topic だけ有効にする。

Seek（Pub/Sub）

subscription を過去の時刻または snapshot に巻き戻す。「限定的な再生」ができる、SQS にはない機能。

SNS FIFO Topic

SQS FIFO と組み合わせて順序と重複排除を実現。同じくスループット制約あり。

  • EventBridge との使い分け — SNS は「速く、安く、単純に配る」。EventBridge は「ルールベースのルーティング・スキーマレジストリ・AWSサービス連携・アーカイブと再生」が必要なとき。EventBridge は SNS よりレイテンシが大きく高価だが、機能は豊富

⑥ メリット

  • 購読者の追加が producer に影響しない — イベント駆動の本質的な価値
  • 運用ゼロ・自動スケール — Pub/Sub には partition の概念すらなく、スループットに応じて自動的に分散される
  • フィルタリングで無駄な配信を削減
  • 異種の宛先を統一的に扱える（SNS: SQS/Lambda/HTTP/Email/SMS）
  • Pub/Sub の Seek で限定的な再生ができる — Kafka ほどではないが、7日以内なら巻き戻せる
  • グローバル配信（Pub/Sub）

⑦ デメリット・トレードオフ

  • SNS 単体はメッセージを保持しない — 最大の落とし穴。必ず SQS を挟む
  • 全体の流れが見えなくなる — 「この topic を誰が購読しているか」がコードから読めない。インフラ定義（Terraform）を読まないと分からない。イベント駆動の最大の運用コスト
  • スキーマ変更が破壊的 — 購読者が誰か分からないまま payload を変更すると、知らないところで壊れる。スキーマレジストリと後方互換のルールが必須
  • ordering key の Head-of-Line Blocking — 順序を有効にすると、1件の失敗が同一 key の後続を全部止める
  • Pub/Sub の exactly-once は「同一 subscription 内」限定 — 過信しない（16章）
  • コスト — fan-out すると配信数ぶん課金される。10 subscriber なら10倍

⑧ 実務での利用例

  • Google 社内 — ほぼ全てのサービス間非同期通信が Pub/Sub。Gmail・Ads・YouTube の内部連携基盤
  • Spotify — GCP 移行時に、イベント配信を全面的に Pub/Sub へ。1日あたり数千億イベントを処理していると公表されている
  • Airbnb / Booking.com — 「予約状態が変わった」を SNS/Kafka で配信し、通知・分析・在庫同期・カスタマーサポートツールが各自購読する
  • Uber — 位置情報のストリームは Kafka だが、システム間の状態変更通知には Pub/Sub 的なモデルを使用
  • 典型的な事故 — 「SNS から Lambda に直接繋いでいて、Lambda の同時実行数上限に達してスロットリング。SNS のリトライが尽きて、その間のイベントが完全に消失した」

⑨ Googleレベルではどう設計されるか

  • partition を隠す — Pub/Sub は Kafka と違い、利用者に partition 数を意識させない。「スケールの設計をサービス側が引き受ける」という思想
  • スキーマを Protobuf で強制 — Pub/Sub Schema で publish 時に検証。互換性のないスキーマは publish 自体が失敗する
  • イベントを API と同等に扱う — バージョニング・非推奨化の手順・購読者のインベントリ管理が正式なプロセスとして存在する
  • Dead Letter Topic を必ず設定 — 「配信できないメッセージを黙って捨てる」ことを許さない
  • 「push か pull か」を明確な基準で選ぶ — consumer が自分でスケールを制御できるなら pull、サーバーレスで即応性が要るなら push

⑩ システム設計面接ではどう問われるか

  • Q: 「1つのイベントを5つのサービスに届けたい」 → SNS → 5つの SQS（AWS）/ 1 topic → 5 subscription（GCP）/ 1 topic → 5 consumer group（Kafka）。「SQS を5本作って producer が5回送る」は明確な減点
  • Q: 「なぜ SNS から直接 Lambda に繋がないのですか？」 → SNS はメッセージを保持しないため、Lambda が落ちている間のイベントが失われるから。SQS を挟むとバッファになる
  • Q: 「購読者が増えるとどうなりますか？」 → 配信コストが線形に増え、下流のDBへの負荷も購読者数倍になる。フィルタリングと、共有DBを避ける設計
  • Q: 「イベントのスキーマを変えたい」 → 後方互換な追加のみ（フィールド追加は可、削除・型変更は不可）。破壊的変更は新しい topic を作って移行。ここまで言えると設計経験があると評価される

10 配信セマンティクス3種 — At Most / At Least / Exactly Once

結論: 「いつ ack するか」だけで、配信保証が決まります。処理の前に ack すれば At Most Once（消えうる）、後に ack すれば At Least Once（重複しうる）。そして Exactly Once は、配信レイヤーには原理的に存在しません。実務の正解は例外なく「At Least Once 配信 + 冪等な処理」の1つだけです。

📦 宅配便のサインで考える: 配達員が荷物を渡す。受取人がサインする。この2つの間には必ず「隙間」があります。
渡す前にサインをもらったら（＝処理前 ack）: 配達員が転んで荷物を紛失しても、記録上は「配達済み」。荷物は永久に失われる。
渡した後にサインをもらうなら（＝処理後 ack）: 渡した直後に受取人が倒れてサインできなければ、営業所は「未配達」と判断して翌日もう一度届ける。荷物は2つ届く。
「渡すこと」と「サインすること」を同時にする方法は、物理的に存在しない。これが Exactly Once が不可能である理由の全てです。

① この概念は何を解決するために生まれたのか

  • ① 「何が起こりうるか」を言語化する — これが本質。「たぶん届く」ではなく「最低1回は届く。2回届くこともある」と明確に定義することで、consumer 側の設計が決まる
  • ② 失うものと引き受けるものの選択を明示する — 欠損を許すか、重複を許すか。両方を許さない選択肢は存在しない
  • ③ 責任の境界を定める — 「ブローカーはここまで保証する。それ以上はアプリの責任」を明確にする

② この概念がないと何が問題になるか

「たぶん1回届くだろう」で実装すると、必ず本番で事故ります。典型的な症状は以下です。

⑤ 実際のシステム構成でどう使われるか

  • データの性質で選ぶ — 金銭・在庫・予約 = At Least Once + 厳格な冪等性。メトリクス・アクセスログ = At Most Once でもよい（コストが安く、欠損の影響が小さい）
  • 「重複の影響度」で対策のレベルを決める — メールが2通 = 軽微（謝罪で済む）。ポイント二重付与 = 重大（金銭）。対策コストは影響度に見合わせる
  • End-to-End で考える — producer → broker → consumer → 外部API の全区間で保証を確認する。1箇所でも At Most Once があれば、全体が At Most Once

⑥ メリット（At Least Once を選ぶことの）

  • データが失われない — ビジネス上、これがほぼ常に最優先
  • 実装が単純 — 「処理してから ack」だけ。特別な仕組みが不要
  • 全ブローカーが標準でサポート — 移植性がある
  • 障害からの復旧が自動 — 未 ack のメッセージが自動的に再配信される

⑦ デメリット・トレードオフ

  • 冪等性の実装が必須になる — 全ての consumer に、重複排除のコードが必要。これはコストであり、忘れると事故になる
  • 重複排除のためのストレージが必要 — 処理済み event_id を保存する場所（DB / Redis）。TTL の設計が必要（永久に保持はできない）
  • 処理が遅くなる — 重複チェックの分だけレイテンシが増える
  • 「稀だから無視」の誘惑 — 重複は普段起きないので、対策を後回しにしやすい。しかしデプロイのたびに（SIGTERM で処理中のメッセージが再配信されるため）確実に起きる

⑧ 実務での利用例

  • Stripe — 全ての書き込みAPIが Idempotency-Key ヘッダーを受け付ける。「クライアントは何度でも再送してよい。重複排除はこちらでやる」という宣言。これが決済APIの業界標準になった
  • AWS SQS — 標準キューは明示的に「重複がありうる」とドキュメントに書かれている。隠さずに仕様として公開している
  • Kafka の Transactional Producer — Kafka 内部で完結する処理（topic → topic）に限り Exactly Once を提供。外部システムへの副作用には効かない（16章）
  • 典型的な事故 — 「Kubernetes のローリングアップデートで SIGTERM を受けた worker が、処理途中のメッセージを ack せずに終了。再配信されて、その日の全ユーザーに確認メールが2通届いた」

⑨ Googleレベルではどう設計されるか

  • 「Exactly Once」という言葉を使わない — Google の文書では "exactly-once processing"（処理として1回）と "exactly-once delivery"（配信として1回）を厳密に区別する。前者は達成可能、後者は不可能
  • Dataflow の Exactly Once — 内部で決定論的な処理とチェックポイントを組み合わせ、パイプライン内の効果を1回にする。ただし外部への書き込み（sink）は冪等でなければならないと明記されている
  • 全メッセージに一意な ID を強制 — Pub/Sub は message_id を自動付与する。重複排除のキーが最初から存在する設計
  • 「重複は起きる」を前提にテストする — カオステストで意図的にメッセージを重複させ、システムが正しく動くことを検証する

⑩ システム設計面接ではどう問われるか

  • Q: 「Exactly Once を実現できますか？」 → これは罠の質問。「配信としては不可能です。At Least Once + 冪等な処理で、効果として1回にします」と答える。「Kafka の Exactly Once を使います」だけだと、外部副作用に効かないことを知らないと判断される
  • Q: 「なぜ Exactly Once は不可能なのですか？」 → 「処理する」と「処理したと記録する」が別の操作であり、その間に必ずクラッシュしうるから。両者を原子的にできるのは、同じシステム内に閉じている場合だけ
  • Q: 「At Most Once を使う場面は？」 → メトリクス・サンプリングされたログなど、1点の欠損が意思決定を変えないデータのみ
  • Q: 「重複はどれくらいの頻度で起きますか？」 → 「普段は稀だが、デプロイ・障害・スケールイベントのたびに確実に起きる」。頻度ではなく「必ず起きる」と捉える姿勢が評価される

11 冪等性（Idempotency）— 非同期システムの生命線

結論: 冪等性とは「同じ操作を何回実行しても、結果が1回実行したときと同じになる」性質です。10章で見たとおり重複は原理的に避けられないので、冪等性は『あったほうがいい』ではなく『無ければ壊れる』。実装方法は4つあり、処理の性質によって使い分けます。

🏦 銀行の振込で考える: 「残高に1000円足す」は冪等ではありません（2回やれば2000円増える）。
「残高を5000円にする」は冪等です（何回やっても5000円）。
では「1000円足す」を冪等にするには？ → 取引番号を付ける。「取引番号 T-123 で1000円入金」なら、同じ番号の2回目は「もう処理済み」として無視できる。
これが Idempotency Key の全てです。エレベーターのボタンを何回押しても1回ぶんしか呼ばれない——それと同じ。

① この技術は何を解決するために生まれたのか

  • ① 重複実行の副作用を無害化する — これが本質。「2回届く」を防ぐのではなく「2回届いても平気」にする
  • ② リトライを安全にする — 冪等でなければ、タイムアウト後のリトライが常に危険。冪等性はリトライの前提条件
  • ③ 障害復旧を単純にする — 「どこまで処理したか分からない」ときに、最初から全部やり直せる
  • ④ 分散システムの「第3の結果」に対処する — 成功でも失敗でもない「不明」という状態に、安全に対応できる

② この技術がないと何が問題になるか

⑤ 実際のシステム構成でどう使われるか

  • event_id は producer が生成する — ブローカーが付ける ID（Kafka の offset、SQS の MessageId）は再送で変わることがあるため、重複排除には使えない。「業務上の同一性」を表す ID を producer が付ける
  • consumer ごとに記録を分ける — 同じイベントを5つの consumer が処理するなら、(event_id, consumer) の複合キーにする
  • API レイヤーでも冪等性を提供する — POST /reservations に Idempotency-Key ヘッダーを受け付ける。クライアントのネットワーク再送で二重予約が起きるのを防ぐ
  • 保持期間の設計 — 「メッセージの最大保持期間 + リトライ期間」より長く。SQS（14日）なら30日、Kafka（7日保持）なら14日

⑥ メリット

  • リトライが安全になる — これが最大の価値。「失敗したら再送」を何も考えずにできる
  • 障害復旧が単純になる — 「どこまで処理したか」を調べずに、全部やり直せる
  • At Least Once を安心して使える
  • バックフィル（過去データの再処理）が可能 — Kafka の offset を巻き戻して全件再処理しても、副作用が二重にならない
  • テストしやすい — 「同じイベントを2回流す」テストで、設計の正しさを検証できる

⑦ デメリット・トレードオフ

  • ストレージと書き込みコスト — 全イベントの ID を保存する。1日100万イベントなら、月3000万行。パーティション運用が必須
  • レイテンシの増加 — 毎回 INSERT が1回増える
  • 保持期間を超えた重複は防げない — 30日前のイベントが再送されたら、また処理される。これは許容するしかない（実質的にほぼ起きない）
  • 外部副作用は完全には守れない — 相手が Idempotency-Key に対応していなければ、二重実行のリスクは残る。その場合は「実行前に記録 → 実行 → 完了を記録」の3段階にして、不明状態を後から照合する
  • 部分的な冪等性の罠 — 「DBは冪等だがメール送信は冪等でない」consumer だと、DB更新は1回・メールは2回になる。consumer の中の全ての副作用を洗い出す必要がある

⑧ 実務での利用例

  • Stripe — Idempotency-Key の事実上の標準を作った。24時間キャッシュ、同じキーで違うパラメータを送るとエラー、というルールも含めて業界の参照実装になっている
  • AWS — EC2 の ClientToken、DynamoDB の条件付き書き込み。ほぼ全ての書き込みAPIに冪等性の仕組みがある
  • PayPal / Square / Adyen — 同様に冪等キーを必須または強く推奨
  • Booking.com / Airbnb の予約API — クライアント生成の予約IDを受け取り、二重予約を防ぐ。「ユーザーが送信ボタンを2回押した」を吸収する
  • 典型的な事故 — 「Idempotency-Key に uuid.New() を使っていて、リトライのたびに新しいキーになり、冪等性が全く効いていなかった」。コードレビューで必ず確認すべき箇所

⑨ Googleレベルではどう設計されるか

  • 冪等性を「オプション」ではなく「API設計の必須要件」にする — Google API Design Guide には、全ての変更系メソッドに request_id を持たせることが明記されている
  • Spanner のトランザクションで完全な原子性 — 処理済み記録と効果を、地理的に分散したDBでも1つのトランザクションで実行できる。TrueTime による外部一貫性がこれを可能にしている
  • 「不明」を明示的な状態として持つ — 外部呼び出しの結果が不明な場合、status = 'unknown' として記録し、後で照合（reconciliation）バッチが状態を確定させる。「成功か失敗か」の2値で設計しない
  • Reconciliation を設計に組み込む — 決済のような重要な処理では、「自分の記録」と「相手の記録」を定期的に突き合わせるバッチを最初から作る。冪等性だけに頼らない

⑩ システム設計面接ではどう問われるか

  • Q: 「重複処理をどう防ぎますか？」 → 「防がない。冪等にする」。processed_events テーブル + ON CONFLICT DO NOTHING を同一TXで、と具体的に言えるかが分かれ目
  • Q: 「冪等キーは何にしますか？」 → 最頻出の追撃質問。「業務上の同一性を表すID から決定論的に導出する」。「UUIDを生成」は明確な間違い
  • Q: 「SELECT で存在チェックしてから INSERT ではダメですか？」 → 競合状態で両方が「未処理」と判断する。DBの制約に判定を委ねる
  • Q: 「外部APIの二重呼び出しは？」 → 相手の Idempotency-Key を使う。対応していない場合は「呼ぶ前に記録 → 呼ぶ → 結果を記録」の3段階 + 照合バッチ
  • Q: 「processed_events が肥大化したら？」 → 時系列パーティション + 保持期間を過ぎたパーティションを DROP。「DELETE で消す」と答えると運用経験が疑われる

12 Retry と Backoff — 「もう一度」が障害を増幅させないために

結論: リトライは最も安価な耐障害性であり、同時に最も簡単に障害を増幅させる仕組みです。即座に何度もリトライすると、弱った下流に止めを刺します。必須の3点セットは「指数バックオフ + ジッター + リトライしてよいエラーの選別」。そしてリトライは冪等性とセットでなければ危険です。

📞 電話が話し中のときで考える: 話し中だからといって1秒ごとにかけ直したら、相手は永久に他の用事を済ませられません。
正しいのは「少し待ってからかけ直す。それでもダメならもっと待つ」——これが指数バックオフ。
さらに重要なのがジッター: 100人が全員「30秒後にかけ直す」と決めたら、30秒後に100件が同時に殺到します。全員が同じタイミングで再試行するのが、障害を長引かせる最大の原因。だから各自がバラバラの時刻にずらす。

① この技術は何を解決するために生まれたのか

  • ① 一時的な障害（transient failure）を吸収する — これが本質。ネットワークの瞬断、瞬間的な過負荷、デプロイ中の数秒間。分散システムの失敗の大半は一時的
  • ② 人手の介入を減らす — 自動で回復すれば、深夜のアラートが減る
  • ③ 下流の回復を待つ — 相手が復旧するまでの時間を稼ぐ

③ 基本概念

Exponential Backoff

試行ごとに待ち時間を倍にする。負荷を指数的に減らす。

Jitter

待ち時間にランダム性を加える。これが無い指数バックオフは、実質的に効果が半減する。

Max Attempts / Max Elapsed

回数と総時間の両方に上限を設ける。回数だけだと、バックオフが伸びて総時間が数時間になる。

Retry Budget

「全リクエストのうちリトライは10%まで」という総量制限。回数制限では総量を制御できないため、大規模では必須。

Circuit Breaker

失敗が続いたら、しばらく呼び出し自体をやめる。リトライと組み合わせて初めて機能する——「確実に失敗するなら待たずに失敗する」。

Retry-After

429/503 で相手が返すヘッダー。これを無視して自分のバックオフを使うのは、相手への攻撃に近い。必ず尊重する。

Retry Topic / 遅延キュー

非同期の世界でのリトライ。worker をブロックせず、メッセージを「後で処理する場所」に移動する。

Poison Message

何度リトライしても失敗するメッセージ。DLQ が無いと、これがキューを永久に占拠する（13章）。

⑤ 実際のシステム構成でどう使われるか

  • 同期と非同期でリトライの実装が全く違う — 同期はコード内で sleep、非同期は絶対に sleep せず、メッセージを遅延キューに移す
  • リトライ階層の設計例 — 30秒 → 5分 → 30分 → 2時間 → DLQ。合計約3時間の猶予。外部サービスの障害は大抵これで吸収できる
  • Circuit Breaker との組み合わせ — 下流が完全に落ちているなら、リトライせず即座に失敗させる。回復を検知したら半開状態で試す
  • リトライの可観測性 — 「試行回数」をメッセージヘッダーに入れて伝播させる。ログとメトリクスに出す。リトライ率の急増は障害の先行指標

⑥ メリット

  • 一時障害を自動で吸収する — 障害の大半は一時的。数行のコードで可用性が大きく上がる
  • 人手の介入が減る
  • 非同期なら「時間」を味方にできる — 同期では数秒しか待てないが、非同期なら数時間待てる

⑦ デメリット・トレードオフ

  • 障害を増幅させる — 多層リトライで指数的に負荷が増える
  • 冪等でない処理では二重実行を招く — リトライと冪等性は必ずセット
  • レイテンシが伸びる — 「3回リトライで9秒」になり、ユーザーの待ち時間が悪化する
  • 失敗が隠れる — リトライで成功すると、根本原因が見えなくなる。リトライ率をメトリクスに出す
  • 順序が壊れる — 1件だけリトライで遅れると、後続に追い越される。Retry Topic パターンは順序保証と両立しない——これは重要なトレードオフ

⑧ 実務での利用例

  • AWS SDK — 全ての SDK が既定でリトライを実装（既定3回、Adaptive モードあり）。アプリ側でもリトライすると二重になる——SDK の設定を確認せずにラップするのは典型的なミス
  • Stripe の Webhook — 指数バックオフで最大3日間リトライし続ける。相手のシステムが数時間落ちても届く設計
  • Google Cloud Tasks — タスク単位で min/max backoff・max attempts・max retry duration を設定できる
  • OTA連携の実例 — 「在庫更新が失敗 → 30秒後 → 5分後 → 30分後 → 2時間後 → 運用チームへ通知」。OTA側の定期メンテ（数十分）はこれで自動的に吸収される
  • 典型的な事故 — 「決済APIがタイムアウトしたのでリトライしたら、実は1回目も成功していて二重課金になった」。冪等キー無しのリトライの典型

⑨ Googleレベルではどう設計されるか

  • Retry Budget が標準 — Google/Envoy では「リトライは全トラフィックの X% まで」という総量制限が組み込まれている。回数制限では大規模障害時の総量を制御できない
  • リトライは「クライアントに最も近い1層」だけ — 多層リトライを設計レビューで禁止する
  • Deadline を必ず伝播 — 上流の残り時間を超えるリトライはしない。「誰も待っていない処理をリトライしない」
  • Adaptive Retry / Load Shedding との組み合わせ — 下流が過負荷を示したら、リトライ率を自動的に下げる
  • SRE Book の原則 — 「リトライは、成功率が上がる見込みがあるときだけ意味がある」。下流が完全に落ちているときのリトライは、純粋な害

  • Q: 「なぜジッターが必要ですか？」 → 全クライアントが同時に再試行すると、復旧しかけた下流を再び落とすから（Thundering Herd）
  • Q: 「各層が3回リトライすると？」 → 4層なら 3⁴ = 81倍。この数字が即答できるかで理解度が測られる
  • Q: 「非同期処理のリトライで worker を sleep させてよいですか？」 → ダメ。Kafka なら partition 全体が止まり、SQS なら worker のスロットが埋まる。遅延キュー / Retry Topic に移す

13 DLQ（Dead Letter Queue）— 「配達不能郵便」の保管棚

結論: DLQ とは「何度リトライしても処理できなかったメッセージを隔離する場所」です。目的は『壊れた1件が、健全な全体を止めるのを防ぐ』こと。そして DLQ の本質的な価値は『監視されて初めて生まれる』——誰も見ない DLQ は、静かなデータ消失と同じです。

📮 郵便局の「配達不能郵便物」の棚で考える: 宛先不明・住所不備の手紙は、配達員が何度行っても届きません。それを配達ルートに残し続けると、後ろの手紙が全部止まります。
だから郵便局は別の棚に移して、配達は先に進める。棚の手紙は後で人が調べて、住所を修正して再投函するか、差出人に返送する。
ここで最も重要なのは「棚を定期的に見る人がいること」。誰も見なければ、手紙は棚の上で永久に埃をかぶります。DLQ のアラートを設定していない実装は、この状態です。

① この技術は何を解決するために生まれたのか

  • ① Poison Message から全体を守る — これが本質。処理できない1件が無限にリトライされ、キューを占拠し、他のメッセージを遅延させるのを防ぐ
  • ② 失敗の可視化 — 「何が、なぜ、いくつ失敗したか」を1箇所に集める
  • ③ 手動での復旧を可能にする — バグを直してから再投入する（Redrive）
  • ④ 無限リトライによるコスト浪費を止める — SQS はリクエスト課金なので、無限リトライは金銭的損失に直結する

③ 基本概念

Poison Message

何度処理しても失敗するメッセージ。不正なフォーマット・存在しない参照・恒久的なビジネスエラーが原因。

maxReceiveCount（SQS）

この回数受信されたら DLQ へ移動する。3〜5 が目安。大きすぎると詰まり、小さすぎると一時障害で DLQ に落ちる。

Dead Letter Exchange（RabbitMQ）

reject/nack/TTL切れ/キュー溢れ のメッセージが送られる exchange。x-death ヘッダーに履歴が残る。

Redrive

DLQ から元のキューに戻すこと。原因を直さずに Redrive すると、また DLQ に戻る（ループ）。

DLQ topic（Kafka）

Kafka には DLQ の組み込み機能がない。アプリが明示的に別 topic へ produce する必要がある。

Parking Lot Queue

DLQ からさらに「人間の判断待ち」に移すキュー。大規模なシステムでは DLQ を2段にすることがある。

⑤ 実際のシステム構成でどう使われるか

  • リトライ階層の終端に置く — work → retry.30s → retry.5m → retry.30m → DLQ
  • DLQ を用途で分ける — 「データ不正」と「一時障害の枯渇」を別 DLQ にすると、対応が分かれて楽になる
  • DLQ の中身を検索可能にする — DLQ の内容を Elasticsearch や DB に写し、「どのユーザーの、どのイベントが失敗したか」を検索できるようにする
  • ダッシュボード — DLQ 件数の推移、エラータイプ別の内訳、最古メッセージの年齢
  • 「全件 DLQ 行き」への備え — 下流が完全に落ちると、全メッセージが DLQ に流れ込む。失敗率が閾値（例: 50%）を超えたら consumer を一時停止するほうが正しい

⑥ メリット

  • 1件の失敗が全体を止めない — 最大の価値
  • 失敗が可視化される — 「何が失敗しているか」が1箇所に集まる
  • コストの浪費を止める — 無限リトライによる課金を防ぐ
  • 手動復旧が可能 — バグを直してから再投入できる
  • データが失われない — 「処理できなかったが、消えてはいない」状態を保てる

⑦ デメリット・トレードオフ

  • 監視しなければ意味がない — DLQ の最大の失敗パターンは「作ったが誰も見ていない」
  • 順序が壊れる — DLQ に落ちたメッセージだけ遅れて再投入されると、順序保証が崩れる。順序が critical なら、DLQ ではなく「停止して人が対応」が正しい場合もある
  • 再投入の運用コスト — 手順・ツール・判断が必要。誰がいつやるかを決めておかないと放置される
  • DLQ にも保持期間がある — 放置すると DLQ からも消える
  • 「DLQ があるから安心」という油断 — DLQ に落ちるのは異常事態。DLQ の件数がゼロであることが正常という認識を持つ

⑧ 実務での利用例

  • AWS Lambda + SQS — Lambda の失敗が maxReceiveCount を超えると自動で DLQ へ。DLQ 件数のアラートは AWS の標準的なベストプラクティス
  • 決済システム — DLQ に落ちた決済は必ず人が確認する。金銭が絡むため自動 Redrive は危険
  • OTA連携 — 「OTA側が仕様変更してフォーマットエラー」が DLQ で発覚するのが典型。DLQ のエラーメッセージがそのまま原因調査の起点になる
  • 典型的な事故① — 「DLQ を設定していたが、アラートが無く、3ヶ月後に『あのメールが届いていない』というCS問い合わせで発覚。DLQ の保持期間14日を過ぎており、データは失われていた」
  • 典型的な事故② — 「原因を直さずに DLQ を全件 Redrive し、また全件 DLQ に戻り、その間の負荷で正常なメッセージまで遅延した」

⑨ Googleレベルではどう設計されるか

  • Dead Letter Topic の設定を必須にする — Pub/Sub の subscription 作成時に、DLQ 無しを組織ポリシーで禁止する
  • DLQ 件数を SLI にする — 「DLQ に落ちるメッセージは全体の 0.01% 未満」をエラーバジェットで管理
  • 自動分類 — DLQ のエラーメッセージをパターン分類し、「既知の一時障害なら自動 Redrive、未知なら人へ」という仕分けを自動化
  • Postmortem の対象にする — DLQ に一定件数以上落ちたら、障害として扱い振り返りを行う。「DLQ に入った = 設計に穴があった」と捉える文化

⑩ システム設計面接ではどう問われるか

  • Q: 「処理できないメッセージがあったら？」 → 「リトライ上限を超えたら DLQ へ隔離し、処理は先に進める。DLQ には1件でも入ったらアラートを出す」
  • Q: 「DLQ に入ったメッセージはどうしますか？」 → 原因を分類 → 修正 → 少数件でテスト Redrive → 全件 Redrive。「すぐ Redrive」と答えるとループを知らないと判断される
  • Q: 「Kafka で DLQ はどう実装しますか？」 → 組み込み機能はないので、アプリが別 topic に produce する。この事実を知っているかが実装経験の判定になる
  • Q: 「DLQ があれば安心ですか？」 → 「監視が無ければ静かなデータ消失と同じ」。この一言が言えると印象が変わる
  • Q: 「順序が重要なストリームで DLQ を使うと？」 → 順序が壊れる。その場合は「止めて人が対応」も正当な選択肢——トレードオフを認識していることを示す

14 Consumer Group と Offset — 並列度・進捗・障害復旧の要

結論: Consumer Group は「担当区域の割り当て」、Offset は「どこまで読んだかのしおり」です。この2つが、並列度の上限・処理の進捗・障害からの復旧位置を全部決めます。実務で最も重要なメトリクスである Consumer Lag も、ここから生まれます。

🚚 宅配便の配達区域で考える: 東京を3つの区域（partition）に分け、3人の配達員（consumer）が1区域ずつ担当します。
4人目を雇っても、区域が3つしかなければ1人は仕事がありません——これが「consumer > partition では並列度が上がらない」理由。
配達員が1人辞めたら、区域を2人で割り直します（Rebalance）。割り直しの間、配達は止まります。
「今日はここまで配った」という記録が Offset。これが無いと、翌日どこから始めるか分かりません。

① この技術は何を解決するために生まれたのか

  • ① 並列処理と順序保証の両立 — これが本質。partition 単位で担当を分けることで、「全体としては並列、partition 内では直列」を実現する
  • ② 障害からの復旧位置を記録する — consumer が落ちても、offset があれば続きから再開できる
  • ③ 複数の用途で同じデータを独立して読む — group を分けるだけで、互いに干渉せず読める
  • ④ 進捗の可視化 — 「最新の offset」と「commit された offset」の差 = Consumer Lag。これが遅延の唯一の正しい指標

② この技術がないと何が問題になるか

  • 「どこまで処理したか」が分からない — 再起動のたびに最初から読むか、全部飛ばすかしかない
  • 並列化すると順序が壊れる — 担当の割り当てが無いと、複数 consumer が同じメッセージを取り合う
  • 遅延が測れない — 「今どれくらい遅れているか」が分からず、障害の検知が CS 問い合わせ頼みになる

⑤ 実際のシステム構成でどう使われるか

  • partition 数 = 並列度の上限 — 目標スループットから逆算する。「1 partition あたり何件/秒処理できるか」× partition 数 = 上限
  • partition 数の余裕 — 将来 consumer を増やせるよう、consumer 数の2〜3倍の partition を用意するのが定石
  • consumer 内での並列化 — partition を増やせない場合、1 consumer が複数 goroutine で処理する。ただし順序保証が壊れるので、key 単位で goroutine を固定する
  • group の分割 — 「メール送信」「検索インデックス」「分析」で group を分ける。1つが遅れても他に影響しない
  • Auto Scaling — lag をメトリクスにして consumer 数を増減。ただし partition 数を超えて増やしても意味がないので、上限を設定する

⑥ メリット

  • 並列と順序を両立できる — partition という単位を作ることで実現
  • 障害復旧が自動 — offset があるので、続きから再開できる
  • 進捗が可視化される — lag が唯一の正しい遅延指標
  • 巻き戻しができる（Kafka）— offset を過去に戻すだけで再処理
  • 用途ごとに独立 — group を分ければ互いに影響しない

⑦ デメリット・トレードオフ

  • partition 数が並列度を縛る — 後から増やせるが、増やすと key → partition の対応が変わり順序が一時的に壊れる
  • Rebalance で処理が止まる — デプロイのたびにラグが出る
  • Hot Partition — key が偏ると、1つの partition だけ詰まる。大手ホテル1社の予約が全体の30%を占める、といった状況で発生
  • offset の管理ミスが致命的 — reset ポリシーの誤設定で、全件スキップまたは全件再処理が起きる
  • Head-of-Line Blocking — 1件が詰まると、その partition の後続が全部止まる

⑧ 実務での利用例

  • Uber — 都市ごとに partition を分け、都市単位の順序を保証しつつ並列処理。「順序の単位 = ビジネスの単位」の好例
  • Netflix — Consumer Lag を主要な運用メトリクスとして SLO 化。lag が閾値を超えると自動でスケールアウト
  • Twitter(X) — ユーザーIDで partition を分け、同一ユーザーの操作順序を保証
  • 典型的な事故① — 「新しい consumer group を auto.offset.reset=earliest で起動したら、7日分（数億件）を最初から処理し始めて、下流のDBが落ちた」
  • 典型的な事故② — 「処理が5分かかるメッセージがあり、max.poll.interval.ms（既定5分）を超えて consumer が group から追放され、Rebalance が無限に繰り返された」
  • 典型的な事故③ — 「Hot Partition。人気ホテルの予約が1 partition に集中し、そこだけ lag が数時間になった」

⑨ Googleレベルではどう設計されるか

  • partition を隠す — Pub/Sub には partition の概念がなく、内部で自動的に分散・再配分される。「並列度の上限を利用者に意識させない」
  • Lag を「時間」で定義 — oldest_unacked_message_age が Pub/Sub の標準メトリクス。件数ではなく年齢で見るのが正しい
  • Flow Control をクライアント側で — 未 ack の件数とバイト数に上限を設け、consumer が自分の処理能力を超えて受け取らないようにする
  • Hot Key の検出と自動分散 — 特定 key への集中を検知し、順序保証が不要な場合は自動的に分散させる仕組みを持つ

⑩ システム設計面接ではどう問われるか

  • Q: 「スループットを2倍にしたい」 → partition を増やして consumer を増やす。ただし partition を増やすと key の割り当てが変わり、順序保証が一時的に壊れることに言及できると強い
  • Q: 「consumer を10台にしたのに速くなりません」 → partition 数が上限。partition が3個なら、7台は遊んでいる
  • Q: 「デプロイのたびに遅延が出ます」 → Rebalance。Cooperative Sticky + Static Membershipで緩和
  • Q: 「Consumer Lag をどう監視しますか？」 → 件数ではなく時間に換算する。「lag ÷ 処理レート = 何秒遅れているか」。これが言えると運用経験があると判断される
  • Q: 「特定の partition だけ遅れています」 → Hot Partition。key の分布を確認 → key の設計を見直す（複合キーにする / 順序が不要なら key を外す）

15 Ordering（順序保証）— 「全順序」という幻想を捨てる

結論: 分散システムに「全体の順序」は存在しません。存在するのは「ある単位の中での順序」だけです。正しい設計は ①順序が必要な単位を特定する ②その単位を key にする ③そもそも順序に依存しない設計にするの3段階。「全部順番どおりに処理したい」という要求は、ほぼ常に要件の誤読です。

📦 宅配便で考える: 東京から大阪への荷物と、北海道から沖縄への荷物、どちらが先に着くかを保証する意味はありません。無関係だからです。
意味があるのは「同じ人への荷物の順序」——「家具」の後に「その組立説明書」が届くべき、といった関係。
そして最も堅牢な解決策は、順序に依存しないこと: 説明書に「この家具用」と書いてあれば、どちらが先に届いても問題ありません。これがバージョン番号やタイムスタンプによる設計です。

① この技術は何を解決するために生まれたのか

  • ① 因果関係のある操作の順序を守る — これが本質。「作成 → 更新 → 削除」が逆順に処理されると、削除済みのレコードが復活する
  • ② 状態遷移の正しさを保証する — 「pending → confirmed → cancelled」が守られないと、キャンセル済みの予約が確定状態に戻る
  • ③ 監査・会計の正確性 — 取引の順序が変わると、残高の履歴が意味を失う

② この技術がないと何が問題になるか

図15-1: 順序破壊の実例と3つの対処法。②の version 判定を入れておけば、①が壊れても最終状態は正しくなる。

③ 基本概念

Total Order（全順序）

全メッセージに一意な順序がある。分散システムでは、単一の直列化点を作らない限り実現できない——つまりスケールしない。

Partial Order（半順序）

関係のあるものだけ順序がある。実務で使うのはこれ。key 単位の順序保証がこれに当たる。

Causal Order（因果順序）

「A が B の原因である」場合だけ順序を守る。Vector Clock などで表現するが、実装は複雑。

Ordering Key

順序を守る単位を指定する値。Kafka の key / SQS の MessageGroupId / Pub/Sub の ordering key。

Monotonic Version

単調増加する番号。「順序保証に依存しない」設計の要。DBの version カラムや、イベントのシーケンス番号。

Last-Write-Wins

タイムスタンプが新しいほうを採用する。サーバ間の時刻ズレで誤判定するリスクがあるため、論理的なバージョンのほうが安全。

State vs Delta

「残5室」（state）を送るか「1室減」（delta）を送るか。state を送る設計は、順序が狂っても version で救える。delta は救えない。

Head-of-Line Blocking

順序保証の代償。1件の失敗が同一 key の後続を全部止める。

⑤ 実際のシステム構成でどう使われるか

  • key の設計が全て — 「順序を守りたい最小の単位」を key にする。粗すぎると並列度が下がり、細かすぎると必要な順序が守れない
  • key の例 — 決済: order_id / 在庫: hotel_id#date / ユーザー操作: user_id / チャット: room_id
  • リトライと順序は両立しない — Retry Topic に逃がした瞬間、そのメッセージは後続に追い越される。順序が critical なら、失敗時は「止める」ほうが正しい
  • 最良の設計は「順序に依存しないこと」 — state + version を送る設計にすれば、順序が壊れても最終状態が正しくなる（収束性）

⑥ メリット

  • 因果関係が守られる — 「作成 → 更新」が逆にならない
  • 状態遷移が正しく進む
  • key 単位なら並列度を犠牲にしない — 全順序と違い、スケールする

⑦ デメリット・トレードオフ

  • Head-of-Line Blocking — 1件詰まると同一 key の後続が全部止まる。順序保証の本質的な代償
  • リトライと両立しない — 遅延リトライした瞬間に順序が壊れる
  • Hot Key — 特定の key に集中すると、その partition だけ詰まる
  • 並列度が key の分散に依存する — key の種類が少ないと、partition を増やしても並列化しない
  • partition 数の変更で壊れる — key → partition の対応が変わるため、移行中は順序が保証されない
  • SQS FIFO のスループット制約 — 300 msg/s（バッチで3000）

⑧ 実務での利用例

  • Uber — 都市 ID を key にして、都市内の配車イベントの順序を保証
  • 決済 — order_id を key に。「与信 → 確定 → 返金」の順序は絶対
  • OTA在庫同期 — hotel_id#date を key に。加えて version による古いイベントの破棄を必ず入れる——リトライで順序が壊れるため
  • チャット / メッセージング — room_id を key に。同じ部屋のメッセージ順序を保証
  • CDC — 主キーを key に。同じ行への UPDATE の順序を保証（19章）
  • 典型的な事故 — 「key を指定し忘れて（null）、ラウンドロビンで partition に分散され、同じ注文の『確定』と『キャンセル』が逆順に処理された」

⑨ Googleレベルではどう設計されるか

  • 順序保証をオプトインにする — Pub/Sub の ordering key は明示的に有効化する必要がある。「既定では順序を保証しない」ことで、利用者に順序の必要性を考えさせる
  • 収束する設計を推奨 — 「順序に依存しない設計（CRDT / LWW / version）が、順序保証よりも堅牢である」という立場。順序保証は最後の手段
  • Spanner の外部一貫性 — TrueTime により、地理的に分散したDBでも「実時間の順序」を保証できる。ただしこれはコミット待ちのレイテンシと引き換え
  • Dataflow の Watermark — 「イベント時刻」と「処理時刻」を分離し、遅れて到着したデータを明示的に扱う。「順序が狂う」を異常ではなく前提として扱う

⑩ システム設計面接ではどう問われるか

  • Q: 「順序を保証できますか？」 → 「全体の順序は保証しません。key 単位の順序を保証します」。「はい、保証します」だけだと理解が浅いと見なされる
  • Q: 「key は何にしますか？」 → 最重要の質問。「順序を守りたい最小の単位」+「その key が偏らないか（Hot Key）」の2点を答える
  • Q: 「リトライすると順序が壊れませんか？」 → 壊れます。だから version による古いイベントの破棄を入れる、または順序が critical なら止める
  • Q: 「全順序が必要と言われたら？」 → 「本当に必要か要件を確認する」。多くの場合、必要なのは「同じエンティティに対する順序」だけ。これを確認する姿勢が最も評価される
  • Q: 「順序に依存しない設計とは？」 → delta ではなく state を送り、version で古いものを捨てる。「最終的に正しい状態に収束する」設計

16 Exactly Once の真実 — 何が可能で、何が不可能か

結論: 「Exactly Once Delivery（配信）」は不可能、「Exactly Once Processing（処理）」は条件付きで可能です。Kafka Transactions が保証するのは「Kafka の中で完結する処理」だけ。メール送信・外部API呼び出しなど、Kafka の外への副作用には一切効きません。この境界を正確に理解することが、この章の全てです。

🏦 銀行の窓口で考える: 「入金を記録する」と「記録したことを台帳に書く」——この2つが同じ帳簿の中なら、1つの取引としてまとめられます（Kafka Transactions）。
しかし「現金を客に手渡す」は帳簿の外の行為です。渡した直後に停電で記録が消えたら、渡したかどうかは帳簿からは分かりません。
だから銀行は、客に受領証を書かせる（＝冪等キー）。帳簿の外に出た瞬間、原子性は失われ、冪等性に頼るしかなくなる——これが Exactly Once の限界です。

① この技術は何を解決するために生まれたのか

  • ① ストリーム処理での集計の正確性 — これが本来の目的。「注文金額の合計」を計算するとき、重複があると合計がずれる。冪等性で解決できない類の問題
  • ② read-process-write の原子性 — 「入力 topic から読む → 処理する → 出力 topic に書く → offset を commit する」を1つの取引にする
  • ③ 障害時の中途半端な出力を防ぐ — 処理の途中で落ちたとき、出力だけ書かれて offset が commit されない、を防ぐ

② この技術がないと何が問題になるか

冪等性で解決できないケースがあります。それが「集計」です。

処理冪等性で解決できるか理由
メール送信できるevent_id で「送信済み」を記録すればよい
ステータス更新できる上書き操作なので自然に冪等
ポイント付与できるprocessed_events + UNIQUE で防げる
集計（合計・カウント）難しい「+1000円」を2回やれば +2000円。全ての入力の ID を記憶し続けないと防げない（＝集計状態が巨大になる）
ストリーム結合・ウィンドウ集計実質不可能状態が入力履歴に依存するため。ここで Kafka Transactions / Flink のチェックポイントが必要になる

  • Kafka Streams / Flink での集計 — これが本来の用途。「1時間ごとの売上合計」を正確に出す
  • topic → topic の変換パイプライン — raw → processed → aggregate の各段で使う
  • 使わない場面 — メール送信・外部API・通知。これらは冪等性で守る

⑥ メリット

  • 集計が正確になる — 冪等性では解決できない領域をカバーする
  • 中途半端な出力が見えない — read_committed により、アボートされた TX の出力は他から見えない
  • ストリーム処理のコードが単純になる — 重複排除のロジックを書かなくてよい

⑦ デメリット・トレードオフ

  • 外部副作用には効かない — 最も重要な制約
  • スループットが落ちる — TX のオーバーヘッドで20〜30%程度低下することがある
  • レイテンシが増える — TX の commit を待つため。read_committed の consumer は、TX が commit されるまでメッセージを読めない
  • 設定が複雑 — transactional.id の管理、インスタンスごとの一意性、ゾンビ producer のフェンシング
  • 誤解を生みやすい — 「Exactly Once を有効にしたから重複しない」と思い込み、consumer 側の冪等性を省いて事故る

⑧ 実務での利用例

  • 金融・広告の集計 — 「クリック数の集計」「広告費の計算」で使われる。1円のズレも許されない領域
  • Kafka Streams のアプリケーション — processing.guarantee=exactly_once_v2 を設定するだけで有効になる
  • Flink のチェックポイント — Kafka とは別方式（分散スナップショット）で Exactly Once を実現。状態を含めて巻き戻せる
  • 典型的な誤用 — 「Exactly Once を有効にしたので、メール送信の重複対策は不要」と判断して、実際には重複メールが送られた

⑨ Googleレベルではどう設計されるか

  • 用語を厳密に使う — "exactly-once processing" と "exactly-once delivery" を区別し、後者は達成不可能だと文書に明記する
  • Dataflow の設計 — 内部処理は Exactly Once だが、外部への sink は「冪等であること」を利用者に要求する。この責任分界が明示されている
  • 決定論的な処理を推奨 — 同じ入力から同じ出力が出ることを保証すれば、再実行が安全になる。「乱数・現在時刻・外部状態に依存しない処理」を書く
  • Reconciliation を必ず設ける — Exactly Once を信じきらず、定期的な突き合わせバッチで整合性を検証する

⑩ システム設計面接ではどう問われるか

  • Q: 「Kafka の Exactly Once を使えば重複しませんか？」 → 最重要の罠。「Kafka の中で完結する処理だけです。メール送信のような外部副作用には効きません」と答える
  • Q: 「では何をしますか？」 → At Least Once + 冪等な consumer。加えて「offset を自分のDBに保存して、効果と進捗を1つのTXにする」という手も提示できると強い
  • Q: 「冪等性で解決できないケースは？」 → 集計・ウィンドウ処理。ここで初めて Kafka Transactions / Flink が必要になる
  • Q: 「Exactly Once のコストは？」 → スループット20〜30%減、レイテンシ増、設定の複雑さ。「必要な範囲だけに使う」という判断を示す

17 Dual Write 問題 — 本書で最も重要な1章

結論: 「DBに書く」と「Brokerに送る」を続けて実行すると、必ずどちらかだけ成功する瞬間があります。これは実装の不備ではなく、2つの独立したシステムに原子的に書く手段が存在しないという原理的な問題です。解決策は3つしかありません: Outbox（18章）・CDC（19章）・Event Sourcing（21章）。

🍽️ レストランの注文で考える: ホールスタッフが「注文をレジに入力する」と「厨房に伝票を渡す」の2つを行います。
レジに入力した直後に倒れたら: 会計は発生しているのに、料理は作られない。
厨房に伝票を渡した後、レジ入力前に倒れたら: 料理は作られるのに、代金は請求されない。
解決策: レジに入力した瞬間に、伝票が自動的に印刷される仕組みにする。「レジ入力」と「伝票発行」を1つの動作にしてしまう——これが Outbox Pattern の発想です。

① この問題は何なのか

マイクロサービス・イベント駆動を採用した瞬間に、100%のシステムがこの問題に直面します。しかし多くのチームは、本番で不整合が発覚するまで気づきません。

  • 問題の定義 — 2つの独立したシステム（DB と Broker）に、原子的に書き込むことはできない
  • なぜ2PC（分散トランザクション）ではダメか — ①ほとんどの Broker が XA をサポートしない ②サポートしていても、コーディネータが落ちるとロックが残り、システム全体が止まる ③レイテンシが大きい ④可用性が全参加者の積になる
  • だから業界の答えは — 「原子性を諦め、代わりに『いつか必ず届く』を保証する」（結果整合性）

② この問題を放置すると何が起きるか

⑤ システム構成での位置づけ

  • この問題は「マイクロサービス化した瞬間」に発生する — モノリスで同一DBなら、全部1つのトランザクションで済んでいた
  • 逆方向の Dual Write もある — 「Kafka から読んで、DBに書いて、別の topic に publish する」も同じ問題。この場合は Kafka Transactions が使える（16章）
  • 複数DBへの書き込みも同じ — 「MySQL に書いて、Elasticsearch にも書く」は典型的な Dual Write。正しくは MySQL に書いて、CDC で ES に流す
  • キャッシュも同じ — 「DBを更新して、Redis も更新する」も Dual Write。だからキャッシュは「更新」ではなく「無効化」するのが定石

⑩ システム設計面接ではどう問われるか

  • Q: 「DBを更新してイベントを飛ばす、をどう実装しますか？」 → これは最頻出の質問であり、Dual Write を知っているかのテスト。「そのまま2つ書くと不整合が起きるので、Outbox Pattern を使います」と即答できるかで、実務経験が判定される
  • Q: 「なぜ2PCを使わないのですか？」 → コーディネータが SPOF・可用性が積になる・Broker が非対応。4つ挙げられると強い
  • Q: 「publish に失敗したらリトライすればよいのでは？」 → プロセスが死んだらリトライのコードも動かない。コードの書き方では原理的に解決できない
  • Q: 「DBとキャッシュの整合性は？」 → 同じ Dual Write 問題。キャッシュは更新せず無効化する、または CDC で反映する
  • この章を理解していない候補者は、イベント駆動の設計を任せられないと判断されます。それくらい中心的な概念です

18 Outbox Pattern — Dual Write への最も実用的な答え

結論: Outbox Pattern とは「送りたいイベントを、業務データと同じトランザクションで同じDBのテーブルに書き、別プロセスが読んで publish する」設計です。原子性の問題を『1つのDBの中に閉じ込める』ことで消し去ります。代償は、publish の遅延と、Relay という新しいコンポーネント。

🍽️ レストランの伝票プリンターで考える: レジで注文を入力すると、厨房のプリンターから伝票が自動で出てきます。
「レジ入力」と「伝票印刷」が1つの動作になっているので、「レジには入っているのに厨房に伝わっていない」が起きません。
では厨房のプリンターが壊れていたら？ → 印刷指示はレジのシステムにキューとして残っているので、復旧後に全部出てきます。
Outbox テーブル = この「印刷待ちキュー」。Relay = プリンター。重要なのは「注文の記録」と「印刷指示」が同じ台帳に書かれていることです。

① この技術は何を解決するために生まれたのか

  • ① Dual Write の解消 — これが唯一かつ全ての目的。書き込み先を1つ（自分のDB）にすることで、原子性を取り戻す
  • ② 「必ず届く」の保証 — DBに残っている限り、Relay が何度でも再試行する
  • ③ Broker 障害への耐性 — Kafka が落ちていても、アプリは通常どおり動き続ける。イベントは outbox に溜まり、復旧後に流れる
  • ④ 監査ログを兼ねる — 「いつ、何のイベントを送ったか」がDBに残る

③ 基本概念 と ④ 内部の動き

  • Relay の配置 — ①独立したデプロイ（推奨）②アプリと同じプロセス内の goroutine（小規模向け）③サイドカーコンテナ。独立させると、アプリのデプロイと Relay のスケールを分けられる
  • Relay の冗長化 — 複数台起動し、SKIP LOCKED で分担。ただし順序保証が必要なら、partition_key で担当を分けるか1台に絞る
  • ポーリング間隔 — 200ms〜1秒が実用的。短くすると遅延は減るがDB負荷が増える。LISTEN/NOTIFY で両立させる手もある
  • 監視すべき3つ — ①未送信の最古レコードの年齢（最重要）②未送信件数 ③Relay の publish エラー率
  • CDC への移行パス — Debezium の Outbox Event Router を使えば、outbox テーブルを CDC で読んで自動的に topic に振り分けられる。Relay を書かずに Outbox パターンを実現できる（19章）

⑥ メリット

  • Dual Write が原理的に消える — 最大の価値
  • 既存のDBだけで実装できる — 新しいインフラが不要。CDC より遥かに導入が軽い
  • Broker 障害に強い — Kafka が数時間落ちても、アプリは動き続け、outbox に溜まって後で流れる
  • イベントの内容をアプリが完全に制御できる — CDC と違い、DBのスキーマとイベントのスキーマを独立させられる
  • 監査ログを兼ねる — 「いつ何を送ったか」が残る
  • テストしやすい — outbox テーブルの中身をアサートするだけでよい

⑦ デメリット・トレードオフ

  • 遅延が増える — ポーリング間隔ぶん（数百ms〜数秒）。リアルタイム性が critical なら不向き
  • Relay という新しいコンポーネント — 開発・デプロイ・監視・障害対応の対象が増える
  • DBへの書き込み負荷が増える — 全イベントが DB に INSERT される。高頻度なら無視できない
  • テーブルの肥大化 — 定期削除の運用が必須
  • 順序保証が難しい — 複数 Relay で並列化すると崩れる
  • At Least Once は変わらない — 「publish 成功 → UPDATE 失敗」で再送される。consumer の冪等性は依然として必須

⑧ 実務での利用例

  • Shopify / Stripe など多数の SaaS — Outbox はマイクロサービスにおける事実上の標準パターン。「Transactional Outbox」として microservices.io にも掲載されている
  • Debezium の Outbox Event Router — Red Hat が公式にサポートする SMT（Single Message Transform）。outbox テーブルの内容を読んで、event_type ごとに別 topic へ振り分ける
  • 決済システム — 「決済が確定した」というイベントは絶対に失えないため、Outbox が必須
  • 典型的な事故① — 「部分インデックスを作らず、outbox が1億行に育ってポーリングクエリが数十秒かかるようになり、イベントが数時間遅延した」
  • 典型的な事故② — 「published_at を先に更新してから publish していたため、Broker 障害時にイベントが完全に失われた」

⑨ Googleレベルではどう設計されるか

  • Spanner のような分散DBなら、より強力に実装できる — 地理的に分散していても1つのトランザクションで書けるため、グローバルな Outbox が作れる
  • Relay を「フレームワークの機能」にする — 各サービスが Relay を実装するのではなく、共通のライブラリ or サイドカーとして提供し、アプリ開発者は「outbox に書く」だけにする
  • 遅延を SLO 化 — 「99%のイベントは outbox 書き込みから1秒以内に publish される」
  • スキーマの分離を強制 — outbox の payload はDBのスキーマではなく、公開用のイベントスキーマで書く。「テーブルの行をそのまま payload にする」と、DB の変更が全購読者に波及する

⑩ システム設計面接ではどう問われるか

  • Q: 「Outbox Pattern を説明してください」 → 「イベントを業務データと同じトランザクションで同じDBに書き、別プロセスが読んで publish する。書き込み先が1つになるので原子性が保てる」
  • Q: 「Relay が落ちたら？」 → イベントは outbox に残り続けるので失われない。ただし遅延するので、「未送信の最古レコードの年齢」を監視する
  • Q: 「複数の Relay を動かすには？」 → FOR UPDATE SKIP LOCKED。この SQL が即答できると実装経験があると判断される
  • Q: 「outbox テーブルが肥大化したら？」 → 部分インデックス + 時系列パーティション + DROP。「DELETE で消す」だと VACUUM の問題を知らないと見なされる
  • Q: 「Outbox で Exactly Once になりますか？」 → なりません。「publish 成功 → UPDATE 失敗」で再送される。At Least Once + consumer の冪等性
  • Q: 「CDC との違いは？」 → Outbox はアプリが明示的にイベントを書く（スキーマを制御できる）。CDC はDBの変更ログを自動で読む（アプリ変更不要だがスキーマが漏れる）

19 CDC と Debezium — DBの変更ログをイベントに変える

結論: CDC（Change Data Capture）とは「DBのトランザクションログを読んで、全ての変更をイベントとして流す」技術です。アプリのコードを1行も変えずに、DBの変更を確実に捕捉できる——これが最大の価値。代償は、インフラの複雑さと、DBのスキーマがイベントとして外部に漏れることです。

📖 図書館の貸出台帳で考える: 司書に「誰が何を借りたか教えて」と頼む代わりに、台帳そのものを直接読む。
司書の仕事を増やさずに、全ての貸出を漏れなく把握できます——記録は必ず台帳に書かれるので、見落としがない。
ただし台帳のフォーマットは図書館の内部都合で決まっています。台帳の書式が変わると、読む側も対応が必要。「内部の記録を外部が直接読む」ことの構造的な弱点です。

① この技術は何を解決するために生まれたのか

  • ① アプリを変更せずにイベント化する — これが本質。レガシーシステムや、他チームが所有するDBからでもイベントを取り出せる
  • ② 変更の取りこぼしをゼロにする — トランザクションログにはコミットされた全ての変更が必ず記録される。アプリ側の書き忘れが原理的にない
  • ③ Dual Write の解消 — DBに書けば自動的にイベントになるので、2箇所に書く必要がない
  • ④ 低遅延 — ポーリングではなくログのストリーミングなので、数ms〜数十msで伝播する
  • ⑤ 初期ロード（Snapshot）と継続的な同期を統一的に扱う — 既存データの全件取得から、以降の差分まで1つの仕組みで

③ 基本概念 と ④ 内部の動き

⑤ 実際のシステム構成でどう使われるか

  • Outbox + CDC の組み合わせ（最推奨） — アプリは outbox テーブルに書く、Debezium がそれを読んで topic に振り分ける。両方の欠点が消える
  • 検索インデックスの同期 — MySQL → CDC → Kafka → Elasticsearch。アプリから ES に直接書くのは Dual Write
  • データウェアハウスへの連携 — 本番DB → CDC → S3/BigQuery。夜間バッチの全件ダンプを、リアルタイム同期に置き換える
  • キャッシュの無効化 — DBの変更を検知して Redis のキーを削除する
  • Strangler Fig（レガシー移行） — 旧システムのDBを CDC で読み、新システムに流す。旧システムを一切変更せずに移行を進められる
  • マイクロサービス分割 — モノリスのDBから、各サービスが必要なテーブルの変更を購読する

⑥ メリット

  • アプリのコード変更が不要 — レガシー・他チーム所有のDBからでも取れる
  • 取りこぼしがない — トランザクションログには全ての変更が記録されている
  • 低遅延 — ポーリングより速い（数ms〜数十ms）
  • Dual Write が消える
  • before/after が両方取れる — 「何がどう変わったか」の差分が分かる
  • 初期ロードと差分同期が統一される

⑦ デメリット・トレードオフ

  • DBのスキーマが公開APIになる — 最大の問題。カラム名を変えると全 consumer が壊れる。Outbox テーブルだけを CDC 対象にすることで回避できる
  • 「意図」が失われる — 「status が変わった」は分かるが「キャンセルされた」のか「システムが自動更新した」のかが分からない。ビジネスイベントとしての表現力が低い
  • レプリケーションスロットの滞留がDBを殺す — consumer が止まると WAL が溜まり、本番DBのディスクが溢れる。監視必須
  • インフラが重い — Kafka Connect クラスタ、Debezium の運用、スキーマレジストリ
  • 大量更新でイベントが爆発する — バッチで1000万行更新すると1000万イベント
  • DDL の扱いが難しい — スキーマ変更時の互換性管理
  • 削除の扱い — 論理削除なら UPDATE として見えるが、物理削除は tombstone レコードになり、consumer 側の対応が必要

  • Airbnb（SpinalTap） — MySQL の binlog を読んでイベント化する自社基盤。検索インデックス・キャッシュ・分析基盤への同期を全てここから行う
  • Netflix（DBLog / Delta） — CDC を使ったデータ同期基盤。「アプリを変更せずにデータを配る」ことを重視
  • Shopify — MySQL → Kafka の CDC で、注文データを分析基盤とサービス間連携に流す
  • LinkedIn（Databus） — Kafka と同時期に生まれた、CDC の初期の実装例
  • Booking.com — 予約DBの変更を CDC で流し、検索・レコメンド・分析に配信
  • 典型的な事故① — 「Debezium を止めたまま週末を過ごし、PostgreSQL の WAL が数百GB溜まってディスクフル。本番DBが停止した」。CDC で最も有名な事故パターン
  • 典型的な事故② — 「テーブルにカラムを追加したら、Avro のスキーマ互換性チェックに引っかかって CDC が停止した」

  • Spanner Change Streams — DB自体が変更ストリームを提供する。外部ツールが不要で、DBの一部として保証される
  • 「CDC は内部連携、イベントは外部公開」と使い分ける — CDC のイベントをそのままサービス間の公開契約にしない。必ず変換層を挟んでビジネスイベントに翻訳する
  • スキーマ進化のルールを CI で強制 — 後方互換でない変更は、そもそもマージできない
  • スロット滞留を SLO 化 — 「レプリケーション遅延は常に1GB未満」を監視し、超えたら consumer を止めるのではなくスケールさせる

  • Q: 「テーブルにカラムを追加したら？」 → 後方互換なので大抵は問題ない。カラム名の変更・削除は破壊的。スキーマレジストリで互換性を強制する
  • Q: 「CDC のイベントをそのまま他サービスに公開してよいですか？」 → ダメ。DBの内部構造が公開契約になってしまう。変換層でビジネスイベントに翻訳する

20 Saga Pattern — 「ロールバックできない世界」の取り消し方

結論: Saga とは「複数サービスにまたがる処理を、小さなローカルトランザクションの連鎖として実行し、失敗したら『打ち消す取引』で元に戻す」設計です。ACID の原子性を諦め、代わりに『補償』で整合性を回復する。最大の設計判断は「補償トランザクションを、業務としてどう定義するか」——これは技術ではなくビジネスの問題です。

🏦 銀行の「赤伝（取消伝票）」で考える: 一度記帳した取引は、帳簿から消すことができません（監査上、消してはいけない）。
代わりに「マイナスの取引」を1本足す。結果として残高は元に戻りますが、履歴には「取引した」と「取り消した」の両方が残ります。
そして重要なこと: 取り消せない取引もあります。「送ってしまったメール」「発送してしまった荷物」——その場合は謝罪・返金・回収という『業務的な補償』を設計するしかない。Saga の本質はここです。

① この技術は何を解決するために生まれたのか

  • ① 分散トランザクションなしで整合性を保つ — これが本質。2PC は可用性を犠牲にするため、大規模システムでは使えない
  • ② 長時間かかる業務プロセスを表現する — 「予約 → 決済 → 在庫確保 → 通知」が数秒〜数日かかる場合、トランザクションを開いたままにはできない
  • ③ サービス間の独立性を保つ — 各サービスが自分のDBだけをコミットする。他サービスのDBをロックしない
  • ④ 部分的な失敗を業務として扱う — 「決済は通ったが在庫確保に失敗」を、システムエラーではなく「返金する」という業務プロセスとして設計する

② この技術がないと何が問題になるか

  • 中途半端な状態が残り続ける — 「決済済みだが予約が入っていない」ユーザーが発生し、CS対応でしか救えない
  • 2PC を使うと可用性が崩壊する — 決済サービスが遅いと、在庫サービスのロックも保持され続ける
  • エラーハンドリングがアドホックになる — 「決済に失敗したら在庫を戻す」処理が各所に散らばり、抜けが出る

⑤ 実際のシステム構成でどう使われるか

  • 状態機械として実装する — Saga の状態をDBに持ち、1ステップごとに永続化。プロセスが落ちても、再起動後に続きから再開できる
  • ワークフローエンジンを使う — Temporal / AWS Step Functions / Cadence。状態の永続化・リトライ・タイムアウト・可視化を全部やってくれる。自前実装より遥かに安全
  • セマンティックロック — Saga 実行中のレコードに status = 'pending' を付け、他の処理が触らないようにする。「中途半端な状態が外部から見える」ことへの対処
  • 補償不可能なステップは最後に置く — メール送信・外部通知・物理的な出荷
  • タイムアウト救済バッチ — 「N分以上 running の Saga」を検出して、補償するか人に通知する

⑥ メリット

  • 2PC なしで分散処理の整合性を保てる — 可用性を犠牲にしない
  • 各サービスが独立してデプロイ・スケールできる
  • 長時間の業務プロセスを表現できる — 数日かかる処理も扱える
  • 進捗が可視化される（Orchestration の場合）— 「どのステップで止まっているか」が分かる
  • ビジネス要件としての「取り消し」が明示的になる — 返金ポリシー・キャンセル料が設計に現れる

⑦ デメリット・トレードオフ

  • Isolation（分離性）が無い — 最大の代償。Saga の途中の状態が他から見える。「決済済みだが未確定」の予約が一覧に出る。セマンティックロックで緩和するが、完全には消せない
  • 補償が失敗しうる — 「返金しようとしたら決済APIが落ちていた」。補償の補償は存在しないので、人の介入が必要
  • 補償不可能な処理がある — 送ったメール、発送した荷物
  • 実装が複雑 — 各ステップに補償を書く。正常系の2倍のコードとテストが必要
  • デバッグが難しい — 特に Choreography
  • 「補償の定義」がビジネス判断になる — 「キャンセル料は取るのか」「手数料は誰が負担するのか」。エンジニアだけでは決められない

⑧ 実務での利用例

  • Uber（Cadence → Temporal） — 乗車の予約・マッチング・料金計算・支払いを Saga として実装。Cadence というワークフローエンジンを自社開発し、後に Temporal としてOSS化された
  • Airbnb — 予約フロー（在庫確保 → 決済 → ホスト通知 → カレンダー更新）を Saga で。途中失敗時の在庫解放が最重要
  • Booking.com — 予約と決済と施設への通知を、補償可能な単位に分割
  • Amazon の注文 — 「注文確定 → 与信 → 引き当て → 出荷指示」。出荷後は補償不可能なので、その前に全ての確認を終える
  • 典型的な事故 — 「決済は成功したが、在庫確保に失敗。返金処理を実装していなかったため、ユーザーから問い合わせが来るまで気づかなかった」

⑨ Googleレベルではどう設計されるか

  • 可能なら Saga を避ける — Spanner のような分散トランザクション対応DBを使い、そもそも Saga が不要な設計にする。Google の強みはここ
  • 境界の設計で回避する — 「1つのトランザクションで完結すべきものは、1つのサービスに置く」。Saga が多発するなら、サービス分割の粒度が間違っている可能性を疑う
  • Workflows / Cloud Tasks で状態を管理 — 状態の永続化を自前で持たない
  • Reconciliation を必ず併設 — Saga の結果を信じきらず、定期的に「自分の記録」と「相手の記録」を突き合わせる。「補償が失敗した Saga」を確実に検出する最後の砦
  • 補償失敗を最重要アラートに — 「compensation_failed」は即座に人を呼ぶ。放置すると金銭的損害が確定する

⑩ システム設計面接ではどう問われるか

  • Q: 「複数サービスにまたがる処理の整合性は？」 → 「2PC は可用性を落とすので Saga を使う。各ステップに補償トランザクションを定義する」
  • Q: 「Choreography と Orchestration、どちらを選びますか？」 → 「ステップが3つ以下なら Choreography、それ以上は Orchestration。理由は『今どこで止まっているか』が追えることの価値」
  • Q: 「補償トランザクションが失敗したら？」 → この質問への答えで深さが測られる。「リトライし、それでもダメなら人を呼ぶ。補償の補償は存在しない」。加えて Reconciliation バッチの存在に触れる
  • Q: 「Saga の途中の状態が見えてしまいます」 → Isolation が無いのが Saga の本質的な代償。セマンティックロック（status = pending）で緩和
  • Q: 「メール送信はどこに置きますか？」 → 補償不可能なので最後。全ステップ成功後に別イベントとして発行する。この判断ができると設計力が評価される

21 Event Sourcing と CQRS — 「状態」ではなく「出来事」を保存する

結論: Event Sourcing とは「現在の状態ではなく、そこに至った全ての出来事を保存し、状態はイベントの再生から導出する」設計です。Dual Write が原理的に消え、完全な監査ログが手に入る。代償は極めて大きい——クエリの難しさ、スキーマ進化の困難さ、学習コスト。「使うべき場面は限定的」というのが業界の共通見解です。

🏦 銀行の口座で考える: 銀行は「残高: 52,300円」という数字だけを保存しているのではありません。
「入金 100,000」「出金 30,000」「振込 -17,700」という取引の履歴を保存し、残高はそれを合計して求めます。
なぜか: ①監査（なぜこの残高なのかを説明できる）②訂正（間違いを打ち消す取引を足せる）③分析（過去のどの時点の残高も再現できる）。
代償: 「残高を知る」だけで全取引を合計する必要がある。だから銀行も「月末残高」というスナップショットを持ちます。これが Event Sourcing の Snapshot です。

① この技術は何を解決するために生まれたのか

  • ① Dual Write の原理的な解消 — イベントが唯一の真実なので、「DBに書いてイベントも送る」という構造自体が存在しない
  • ② 完全な監査ログ — 「なぜ今この状態なのか」を100%説明できる。金融・医療・法務で強く求められる
  • ③ 時間を遡れる — 任意の時点の状態を再現できる（Time Travel）
  • ④ 後から新しい読み取りモデルを作れる — 「3ヶ月前から集計したい」を、過去のイベントを再生するだけで実現できる
  • ⑤ ビジネスの意図が保存される — CRUD では「status が変わった」しか残らないが、Event Sourcing では「ユーザーがキャンセルした」「システムが自動失効させた」が区別される

⑤ 実際のシステム構成でどう使われるか

  • CQRS とセットで使う — Event Sourcing 単体では「一覧を出す」ことすら困難。Read Model が必須
  • システム全体に適用しない — 「ビジネス上、履歴そのものに価値がある集約」だけに使う。予約・決済・在庫はあり得るが、ユーザープロフィールやマスタデータには過剰
  • Event Store の選択 — PostgreSQL のテーブル（最も現実的）/ EventStoreDB / DynamoDB / Kafka（Kafka を Event Store にするのは非推奨——保持期間の管理と、集約ごとの読み出しが困難）
  • Projection の再構築 — バグ修正後にチェックポイントをリセットして全再生。この「作り直せる」性質が Event Sourcing 最大の実務的メリット
  • GDPR 対応 — 個人データを暗号化して保存し、削除要求時は鍵を捨てる（Crypto-shredding）。イベント自体は残るが読めなくなる

⑥ メリット

  • Dual Write が原理的に存在しない — 書き込み先が1つ
  • 完全な監査ログ — 規制産業では決定的な価値
  • 時間を遡れる — 任意の時点の状態を再現。バグの調査が劇的に楽になる
  • 新しい読み取りモデルを後から作れる — 過去のデータも含めて
  • ビジネスの意図が保存される — 「なぜ」が残る
  • Projection を捨てて作り直せる — 読み取りモデルのバグ修正が安全

⑦ デメリット・トレードオフ

  • クエリが根本的に難しい — 「今週キャンセルされた予約」を出すのに Projection が必要。ad-hoc なSQLが書けない
  • スキーマ進化が極めて困難 — 5年前のイベントも読めなければならない。アップキャストの仕組みを最初から作る必要がある
  • 結果整合性が UI に露出する — 「保存したのに一覧に出ない」
  • 学習コストが高い — チーム全員が理解しないと破綻する。部分的な導入が難しい
  • GDPR / 個人情報削除との衝突
  • 集約の粒度設計が難しい — 大きすぎるとイベント数が爆発、小さすぎると整合性が保てない
  • 「流行っているから」で導入すると、ほぼ確実に失敗する — 業界で最も多い後悔の1つ

⑧ 実務での利用例

  • 金融・会計システム — 元帳（ledger）はそもそも Event Sourcing の思想そのもの。「取引を追記し、残高は導出する」
  • 在庫管理 — 「入庫」「出庫」「棚卸調整」をイベントとして持ち、現在庫を導出する
  • Git — 最も身近な Event Sourcing。コミット（イベント）の連鎖から、任意の時点のファイル状態を再現できる
  • CQRS の部分適用（最も一般的） — Event Sourcing は使わず、「書き込みは RDB、読み取りは Elasticsearch」という CQRS だけを採用する。これは非常に多くのシステムで実践されている
  • 典型的な失敗 — 「マイクロサービス全体を Event Sourcing にしたが、簡単なクエリすら書けず、スキーマ変更のたびに全チームが止まり、2年後に CRUD へ戻した」

⑨ Googleレベルではどう設計されるか

  • Google 社内で Event Sourcing が全面採用されている例は少ない — Spanner のような強力なDBがあるため、Dual Write 対策としての動機が薄い
  • ただし「ログを唯一の真実にする」思想は随所にある — Bigtable の SSTable、Spanner の Paxos ログ、GFS のログ構造。「追記専用ログ + 導出された状態」はインフラ層の基本設計
  • CQRS は広く実践される — 書き込み用のストアと、検索・分析用のストアを分けるのは標準的
  • 示唆 — Event Sourcing を「アプリケーション設計」として採用するかは慎重に。しかし「イベントログを一次データとして持つ」という発想は、インフラ設計として極めて有用

⑩ システム設計面接ではどう問われるか

  • Q: 「Event Sourcing を使いますか？」 → 「監査要件が強い集約だけに限定的に使います。システム全体には使いません」。無条件に「使います」と答えると、経験が無いと判断される
  • Q: 「CQRS のデメリットは？」 → 結果整合性が UI に露出する。書き込み直後に読むと反映されていない。楽観的UI / 完了通知で吸収する
  • Q: 「イベントのスキーマを変えたい」 → Event Sourcing で最も難しい問題。アップキャストの仕組み。「後方互換な追加のみ」を原則にする
  • Q: 「状態の復元が遅くなったら？」 → Snapshot。加えて「集約の粒度が大きすぎないか」を疑う
  • Q: 「Kafka を Event Store にできますか？」 → 推奨されません。保持期間の管理、集約単位の読み出し、楽観ロックが困難。Event Store は RDB か専用DBを使い、Kafka は配信に使う

23 Webhook（送る側）— 会社の外へイベントを届ける

結論: Webhook とは「自社で起きたイベントを、相手のHTTPエンドポイントに POST して通知する仕組み」——つまりインターネット越しの Pub/Sub です。Broker と決定的に違うのは、相手のシステムを一切コントロールできないこと。相手は落ちるし、遅いし、二重処理する。だから署名・リトライ・順序の扱い・失敗の可視化を、送る側が全部設計する必要があります。

📬 速達郵便で考える: 相手の家（エンドポイント）まで自分で届けに行きます。相手が不在なら、時間を空けて何度も行く。
問題は、相手の家がどんな状態か分からないこと——ポストが壊れているかもしれないし、住所が変わっているかもしれない。
そして「本当にあなたからの手紙か」を相手が確認する手段が必要——これが署名（HMAC）。偽の Webhook で「決済が完了しました」と送られたら、相手は商品を無料で発送してしまいます。

① この技術は何を解決するために生まれたのか

  • ① 相手にポーリングさせない — これが本質。「決済が完了したか」を1秒ごとに聞かれると、API が無駄なリクエストで埋まる。起きたときにこちらから伝えればよい
  • ② 即時性 — ポーリング間隔の遅延がなくなる
  • ③ 組織をまたいだイベント駆動 — Kafka を相手に見せるわけにはいかないので、HTTP という共通言語で配る
  • ④ 非同期な状態遷移の通知 — 決済の3Dセキュア完了、返金の確定、審査の結果。元のAPI呼び出しでは返せない結果を後から伝える

② この技術がないと何が問題になるか

⑤ 実際のシステム構成でどう使われるか

  • 内部イベント → Webhook Dispatcher → 相手ごとのキュー → Sender が基本形
  • テナント分離が必須 — 1社の遅いエンドポイントが、全社の配送を詰まらせてはいけない。相手ごとにキューを分けるか、同時実行数を相手ごとに制限する
  • 順序の扱い — Webhook で順序を保証するのは非常に難しい（リトライで簡単に狂う）。payload に created_at と version を含め、「順序は保証しないので、相手側で判定してください」とドキュメントに明記するのが実務的
  • 大きなデータは送らない — 「IDだけ送って、詳細は相手がAPIで取りに来る」（Thin Payload）。セキュリティ的にも安全で、ペイロードのスキーマ変更にも強い
  • ダッシュボードと手動再送 — 相手が自分で失敗を確認・再送できるようにする

⑥ メリット

  • ポーリングの無駄が消える — 相手も自分も負荷が下がる
  • 即時性 — 数秒で伝わる
  • HTTP だけで済む — 相手に特別なライブラリを要求しない
  • 組織をまたいだイベント駆動が可能

⑦ デメリット・トレードオフ

  • 相手をコントロールできない — 落ちる、遅い、二重処理する、エンドポイントが変わる
  • 順序保証が実質不可能 — リトライで簡単に狂う
  • セキュリティの責任が重い — 署名の実装ミスは、なりすましを許す。SSRF の入口にもなる
  • 配送状態の管理が必要 — 「誰に、どのイベントが、何回目で、成功したか」を全部記録する
  • スケールの難しさ — 購読者×イベント数だけリクエストが発生する
  • 相手の実装品質に引きずられる — 「相手が10秒かかる」だけで、配送スループットが1/100になる

⑧ 実務での利用例

  • Stripe — Webhook 設計の事実上の参照実装。署名方式（Stripe-Signature: t=...,v1=...）、最大3日間のリトライ、ダッシュボードでの再送、テスト用のイベント送信機能
  • GitHub — push / PR / issue のイベントを Webhook で。X-Hub-Signature-256 ヘッダーで署名。配送履歴が UI で確認・再送できる
  • Shopify / Slack / Twilio — 同様の設計。署名 + リトライ + ダッシュボードが業界標準の3点セット
  • OTA連携 — 予約が入ったら施設管理システムへ Webhook。施設側のシステムは小規模で落ちやすいため、長期リトライとキュー分離が特に重要
  • 典型的な事故 — 「相手のエンドポイントが1社だけ10秒かかるようになり、共有ワーカープールが埋まって、全社への Webhook が数時間遅延した」

⑨ Googleレベルではどう設計されるか

  • Pub/Sub の push subscription — Google は Webhook を「Pub/Sub の配信方式の1つ」として抽象化している。OIDC トークンによる認証を標準サポート（HMAC より強い）
  • 相手の処理能力に応じた自動調整 — 429 や失敗率に応じて配送レートを自動的に下げる（adaptive push rate）
  • Dead Letter Topic — 配送不能な Webhook を捨てずに保持
  • 署名より OIDC/mTLS を推奨 — 共有秘密鍵はローテーションが難しいため、短命なトークンによる認証のほうが安全
  • SSRF 対策を基盤で強制 — 個々の実装に任せず、egress proxy で内部IPへのアクセスを遮断する

⑩ システム設計面接ではどう問われるか

  • Q: 「Webhook をどう設計しますか？」 → 署名（HMAC + timestamp）・指数バックオフの長期リトライ・相手ごとのキュー分離・配送履歴と手動再送UI・自動無効化の5点
  • Q: 「相手が二重に受け取ったら？」 → event_id を付けて、相手に冪等な処理を要求する。ドキュメントに明記する
  • Q: 「1社の遅延が全体に影響しないようにするには？」 → 相手ごとのキュー分離 + 同時実行数の制限 + Circuit Breaker。Noisy Neighbor の概念
  • Q: 「Webhook のセキュリティリスクは？」 → ①なりすまし（署名で対策）②リプレイ攻撃（timestamp）③SSRF（相手URLが内部IPを指す）。③を挙げられると強い
  • Q: 「順序は保証しますか？」 → 保証しない。payload に version/timestamp を含め、相手側で判定してもらう

24 Webhook（受ける側）— 外部からのイベントを安全に取り込む

結論: 受信側の鉄則は「検証 → 即 200 → キューに入れて後で処理」の3手順です。受信ハンドラの中で重い処理をするのが、最も多い設計ミス——相手のタイムアウトを超えて再送され、二重処理が始まります。Webhook 受信は『非同期化すべき処理』の教科書的な例です。

📮 宅配便を受け取るときで考える: 配達員が来たら、まず受領印を押します。中身を開けて検品して、問題があれば返品する——それを配達員を玄関に立たせたままやったら、配達員は次の家に行けません。
正しいのは「受け取ってサインし、中身の確認は後で」。
ただし受け取る前に1つだけ確認すること: 「これは本当に自分宛か、送り主は本物か」——これが署名検証です。偽の荷物にサインしてはいけません。

① この設計は何を解決するのか

  • ① 相手のタイムアウトを超えない — これが本質。多くの Webhook 送信元は5〜10秒でタイムアウトし、再送する。処理に15秒かかると、成功しているのに再送され続ける
  • ② なりすましを防ぐ — 署名検証がないと、誰でも「決済完了」を偽装できる
  • ③ 自分の障害を相手に見せない — DBが落ちていても、受信して溜めておけば後で処理できる
  • ④ 二重受信に耐える — At Least Once が前提

② この設計をしないと何が問題になるか

⑤ 実際のシステム構成でどう使われるか

  • 受信エンドポイントは薄く、独立させる — 業務APIとは別のサービス/ハンドラにして、障害の影響範囲を分ける
  • raw body をそのまま保存する — 後から仕様変更や調査があったとき、元のデータが残っていることの価値は極めて大きい
  • 順序に依存しない実装にする — 「payment.succeeded の前に charge.refunded が来る」ことがある。payload の created_at や状態を見て判定する
  • 受信APIの認証 — 署名が第一。加えてURLに推測困難なトークンを含める（/webhooks/stripe/8f3a9c...）と多層防御になる
  • 重要: 送信元の状態を信じすぎない — Webhook が届かない可能性を前提に、定期的に相手のAPIで状態を照合する（Reconciliation）

⑥ メリット

  • 相手のタイムアウト・リトライに巻き込まれない
  • 自分の障害が相手に見えない — DBが遅くても200を返せる（保存だけなら軽い）
  • 処理のリトライを自分で制御できる
  • raw body が残るので、後から再処理できる

⑦ デメリット・トレードオフ

  • 「200を返したのに処理していない」状態が生まれる — 自分の責任で確実に処理する義務を負う。DLQ と監視が必須
  • 実装が2段階になる — 受信と処理でコードが分かれる
  • Webhook が届かないことがある — 相手のバグ・ネットワーク・自分のダウンタイム。照合バッチが最後の砦
  • ストレージが増える — raw body の保存

⑧ 実務での利用例

  • Stripe の Webhook 受信 — 公式ドキュメントが「即座に 200 を返し、処理は非同期に」と明記している
  • 決済の状態同期 — payment_intent.succeeded を受けて予約を確定する。ただし Webhook だけに依存せず、ユーザーが戻ってきたときのリダイレクトと、定期照合の3系統で確実性を担保する
  • OTA からの予約受信 — 施設側システムが OTA の Webhook を受ける。OTA によっては順序も冪等性も保証されないため、受信側の防御が全て
  • 典型的な事故① — 「Webhook ハンドラでメール送信までやっていて、10秒を超えて再送され、確認メールが4通届いた」
  • 典型的な事故② — 「署名検証で JSON を再シリアライズしていたため、キーの順序が変わって全部 401 になった」
  • 典型的な事故③ — 「業務エラーで 500 を返していたら、Stripe が3日間リトライし続け、Slack のアラートが数万件になった」

⑨ Googleレベルではどう設計されるか

  • 受信を「メッセージング基盤への入口」として抽象化 — Webhook を受けたら即座に Pub/Sub に publish し、以降は通常のイベント処理と同じパイプラインに乗せる
  • OIDC トークン検証 — HMAC より強い認証。鍵のローテーションが自動
  • Reconciliation を必ず併設 — 「Webhook は届かないことがある」を前提に、定期的に相手のAPIで全件照合するバッチを最初から作る。これが無い決済連携は、いつか必ず不整合を起こす
  • 受信の可観測性 — 受信数・検証失敗数・処理遅延・未処理件数を全てメトリクス化する

⑩ システム設計面接ではどう問われるか

  • Q: 「Webhook をどう受けますか？」 → 「署名検証 → raw body を保存 → 即 200 → 非同期に処理」。この4手順が即答できるかで実装経験が判定される
  • Q: 「処理に時間がかかる場合は？」 → 受信ハンドラでは保存だけ。「非同期にします」だけでなく、理由（相手のタイムアウト → 再送 → 二重処理）まで説明する
  • Q: 「業務エラーのときは何を返しますか？」 → 200。受信は成功しているため。5xx を返すと相手が無限に再送する。「受け取れたか」と「処理できたか」を分けて考える
  • Q: 「Webhook が届かなかったら？」 → 定期照合バッチ（Reconciliation）。「Webhook だけに依存する設計は必ず穴が空く」という認識を示せると強い
  • Q: 「署名検証の実装で注意することは？」 → raw body で計算・timestamp を含める・定数時間比較（hmac.Equal）・鍵のローテーション

26 ユースケース② 画像変換 — 重い処理をどう捌くか

27 ユースケース③ 決済 — 「不明」という第3の状態を設計する

結論: 決済は「成功」「失敗」の2値では設計できません。必ず「不明（pending / unknown）」という第3の状態が存在します。設計の核心は ①与信は同期・確定は非同期 ②冪等キーを必須にする ③Webhook・リダイレクト・照合バッチの3系統で確実性を担保する。1つの経路だけに依存する決済実装は、必ず不整合を起こします。

図27-1: 決済の状態遷移と3系統の担保。unknown 状態と照合バッチが、実運用での事故を防ぐ2大要素。

⑩ 面接での問われ方

  • Q: 「決済APIがタイムアウトしました。どうしますか？」 → 最重要の質問。「失敗と決めつけず unknown として記録し、冪等キーで照会して確定させる」。「リトライします」だけだと二重課金のリスクを理解していないと判断される
  • Q: 「二重課金をどう防ぎますか？」 → Idempotency-Key を業務IDから決定論的に生成する
  • Q: 「Webhook が届かなかったら？」 → 照合バッチ。「3系統（同期応答・Webhook・照合）で担保する」
  • Q: 「予約と決済の整合性は？」 → Saga。authorize を先に、capture は最後に。失敗時は void（安い）で戻す
  • Q: 「返金の実装で注意することは？」 → 返金も冪等キーが必要。「返金 → 記録前にクラッシュ → 再度返金」で二重返金になる

29 9社の設計を読む — 実例から学ぶ判断基準

結論: 各社の設計は「その会社が何に困っていたか」の答えです。技術の選択ではなく、制約の違いを読むと学びが大きい。「Netflix が Kafka を使っているから」で真似すると、運用コストだけを引き受けることになります。

図29-1: 規模と整合性要件のマトリクス。自分がどこにいるかを認識することが、技術選定の出発点。

🔍 Google — 基盤を作る側の思想

  • Cloud Pub/Sub — partition の概念を利用者に見せない。スケールはサービス側の責任。順序が必要なら ordering key でオプトイン
  • Spanner — TrueTime による外部一貫性で、地理分散環境でも1つのトランザクションが可能。結果として Saga や Outbox の必要性そのものを減らしている
  • Dataflow (Beam) — 「イベント時刻」と「処理時刻」を分離し、Watermark で遅延データを明示的に扱う。「順序は狂うもの」を前提にした設計
  • Cloud Tasks — タスク単位で実行時刻・リトライ・同時実行数を制御。「命令（Task）」と「事実（Pub/Sub）」を明確に分ける
  • 学べること — 「運用の複雑さを利用者に押し付けない」という一貫した思想。自社で基盤を作るときも、この視点は有効

🔍 AWS — SQS から始まったメッセージングの歴史

  • SQS（2004年公開） — Amazon 社内の注文処理から生まれた。「機能を削ることで無限のスケールと運用ゼロを得る」割り切り
  • SNS + SQS ファンアウト — AWS における Pub/Sub の標準形。SNS が配り、SQS が受け止める
  • EventBridge — ルールベースのルーティング、スキーマレジストリ、アーカイブと再生。SNS より高機能だが高価でレイテンシも大きい
  • Amazon Builders' Library — 「キューは障害時に毒にもなる」という重要な指摘。障害中に溜まったメッセージが復旧直後に殺到する（Thundering Herd）
  • 学べること — 「機能を減らすことが価値になる」。SQS の割り切りは、設計における引き算の好例

🔍 Twitter(X) — Fan-out という永遠の課題

  • 問題 — 「ツイートを投稿したら、全フォロワーのタイムラインに反映する」。1億フォロワーのアカウントでは、1回の投稿が1億回の書き込みになる
  • 解決策: ハイブリッド Fan-out — 普通のユーザーは書き込み時に配る（fan-out on write）、著名人は読み取り時に取得する（fan-out on read）。タイムライン表示時に両者をマージする
  • メッセージング基盤 — 長らく独自の EventBus（DistributedLog ベース）を運用していたが、2021年頃に Kafka へ移行。理由は「エコシステムと総運用コスト」
  • 学べること — 「独自基盤の維持コスト」は想像より大きい。技術的に優れていても、エコシステムの差で標準に負けることがある

🔍 Instagram — シンプルさで押し切る

  • 初期 — Django + Celery + RabbitMQ + PostgreSQL。数千万ユーザーまでこの構成で耐えた
  • 重要な事実 — 「エンジニア数十人で数億ユーザーを支えた」。技術の新しさではなく、運用できる複雑さに収めたことが成功要因
  • Fan-out — 投稿は即座に成功させ、フィード配信は非同期。Twitter と同様のハイブリッド戦略
  • 学べること — 「枯れた技術を正しく使う」ことの強さ。RabbitMQ で数千万ユーザーを支えられる

🔍 Netflix — 「全部確実に」を諦める設計

  • Keystone パイプライン — 1日あたり数兆イベント。再生開始・停止・シーク・エラー・UI操作の全てが Kafka を通る
  • 重要な割り切り — この規模では「全イベントを確実に届ける」ことのコストが割に合わない。分析用データは一部の欠損を許容し、課金・視聴権限のような critical なものだけ厳密に扱う
  • Chaos Engineering — 意図的に障害を起こし、システムが耐えることを日常的に検証する。「壊れる前提」の運用文化
  • エンコーディングジョブ — SQS で数千の worker に分配。Spot インスタンスを活用し、中断されてもキューに戻る設計
  • 学べること — 「データの重要度で保証レベルを分ける」。全部を同じ厳密さで扱うのは、大規模では不可能

🔍 Airbnb — CDC を軸にしたイベント基盤

  • SpinalTap — MySQL の binlog を読んでイベント化する自社 CDC 基盤。「DBに書けば自動的にイベントになる」を実現
  • 用途 — 検索インデックス更新・キャッシュ無効化・分析基盤・サービス間連携。全部が同じ CDC ストリームから派生する
  • 予約フロー — Saga で「在庫確保 → 決済 → ホスト通知 → カレンダー更新」。途中失敗時の在庫解放が最重要
  • キューごとの SLO — 「このキューは5分以内に処理される」を定義し、遅延を監視
  • 学べること — CDC を全社基盤にすると、新しいデータ利用が「購読するだけ」になる

各問、まず自分で答えてから開いてください。「なんとなく分かる」と「説明できる」の間には大きな差があります。7割を自力で説明できなければ、該当章に戻ることを推奨します。

Part 1: 同期・非同期の基礎（1〜6）

Q1. 非同期化の本当の目的は何ですか
依存先の障害と遅延から自分を切り離すこと（時間的結合の切断）。
「速くするため」は結果であって目的ではない——実際、非同期化してもトータルの処理時間は減らない（別の場所に移動するだけ）。
面接で「速くなるから」だけを言うと、可用性の観点が抜けていると判断される。（1章・2章）
Q2. 依存先を5つ直列に呼ぶ API の可用性は？
各99.9%なら 0.999⁵ ≈ 99.5%（月間3.6時間の停止）。可用性は掛け算で下がる。
重要なのは「hard dependency（成立条件）と soft dependency（付随処理）に分け、soft を非同期に落とす」こと。「メールSaaSの障害で予約ができない」は技術障害ではなく設計ミス。（1章）
Q3. go func(){ sendMail() }() は非同期処理ですか
いいえ。「エラーを握り潰した」だけです。
①プロセスが死ねば消える ②デプロイの SIGTERM で途中終了する ③リトライも監視も無い ④panic すると誰も知らない。
「永続化されないものは非同期処理と呼ばない」を原則にする。最低でも DB の jobs テーブルに書く。（2章）
Q4. キューがあればスパイクを全部吸収できますか
できません。3つの前提が要ります。
①平均処理能力 > 平均流入（恒常的に上回るなら、キューは無限に伸びるだけ） ②遅延が許容される処理である ③溜まったことに気づける（監視がある）。
キューは「一時的な波」を「失敗」から「遅延」に変換する装置であって、処理能力の不足を解決しない。（2章）
Q5. Queue と Topic の違いは？
1つのメッセージを「1人が処理する」（Queue）か「全員が受け取る」（Topic）か。
用途で言い換えると「仕事の分配 = Queue（命令）」「事実の通知 = Topic（イベント）」。
「購読者が今1つでも、将来増えるか」で判断する。増えるなら最初から Topic。（3章）
Q6. Visibility Timeout はどう決めますか
処理時間の P99 の3倍程度が目安。
短すぎる → 処理中に再配信されて同じ処理が並行して走る。長すぎる → worker がクラッシュしたときの復旧が遅い。
10分かかるような長時間処理は、heartbeat（ChangeMessageVisibility）で延長し続ける。（3章・26章）

Part 2: メッセージング基盤（7〜12）

Q7. Kafka と SQS の使い分けは？
「再生が必要か」「購読者が複数か」の2点で切る。
両方 No なら SQS（運用ゼロ・無制限スケール・アイドル時0円）。どちらか Yes なら Kafka。
「Kafka のほうが速いから」は減点——大抵の要件ではどちらも十分速く、差を生むのは機能と運用コスト。（5章・7章・9章）
Q8. Kafka の partition key は何にしますか
「順序を守りたい最小の単位」。決済なら order_id、在庫なら hotel_id#date、ユーザー操作なら user_id。
同時に「その key は偏らないか（Hot Partition）」を確認する。人気ホテル1社に予約が集中すると、1 partition だけ lag が数時間になる。
key を指定し忘れる（null）と、ラウンドロビンで分散して順序が完全に壊れる。（5章・15章）
Q9. consumer を10台にしたのにスループットが上がりません
partition 数が並列度の上限だから。partition が3個なら、7台は何も割り当てられずに待機している。
対策: ①partition を増やす（ただし key → partition の対応が変わり、順序保証が一時的に壊れる）②consumer 内で key 単位に goroutine を分けて並列化。（14章）
Q10. SQS FIFO を選ぶ前に確認すべきことは？
スループットが 300 msg/s（バッチで3000）に制限されること。これが設計を根本から縛る。
さらに「FIFO = Exactly Once」ではない——重複排除は5分間の窓だけで、consumer 側のクラッシュによる再処理は防げない。
結局 consumer は冪等でなければならないので、順序が本当に必要かを先に検証する。（7章）
Q11. SNS から直接 Lambda に繋いではいけない理由は？
SNS はメッセージを保持しないから。Lambda が throttle されたり落ちていると、SNS のリトライが尽きた時点でイベントが完全に失われる。
SNS → SQS → Lambda にすると、SQS が最大14日間バッファになり、復旧後に自動で追いつく。（8章）
Q12. RabbitMQ で最も多い事故は？
Nack(requeue=true) による無限ループ。失敗したメッセージが即座に戻ってきて、CPU 100% でブローカーが停止する。
正解は Nack(requeue=false) で Dead Letter Exchange に逃がすこと。
次点は「メッセージがメモリに溜まってブローカーが落ちる」——Lazy Queue と x-max-length で対策。（6章）

Part 3: 配信保証・冪等性・順序（13〜19）

Q13. Exactly Once は実現できますか
配信としては原理的に不可能。「処理する」と「処理したと記録する」は別の操作であり、その間に必ずクラッシュしうるため。
実務の正解は「At Least Once 配信 + 冪等な処理 = Effectively Once」。
Kafka Transactions が保証するのは Kafka 内で完結する処理だけで、メール送信や外部API呼び出しには一切効かない。（10章・16章）
Q14. 「処理の前に ack」と「後に ack」の違いは？
前 = At Most Once（欠損しうる。クラッシュすると処理は永久に実行されない）。後 = At Least Once（重複しうる）。
実装上は autoAck=true / enable.auto.commit=true / ReadMessage() が At Most Once になる。ビジネスデータでこれをやると静かにデータが消える。（10章）
Q15. 冪等キーは何にしますか
「業務上の同一性」を表すIDから決定論的に導出する。例: "pay-" + reservation_id + "-v1"。
uuid.New() を使うと、リトライのたびに違うキーになり冪等性が全く効かない——実務で最も多いバグ。
ブローカーが付ける ID（Kafka の offset、SQS の MessageId）も再送で変わるため使えない。（11章）
Q16. 重複チェックを SELECT → INSERT でやってはいけない理由は？
2つの worker が同時に SELECT すると、両方が「未処理」と判断して二重実行する（競合状態）。
正解は INSERT ... ON CONFLICT DO NOTHING の影響行数で判定すること。判定をDBの制約に委ねる。
さらに、この INSERT と実際の効果を同一トランザクションに入れることが必須。（11章）
Q17. 各層が3回リトライすると負荷は何倍になりますか
4層なら 3⁴ = 81倍。既に苦しい下流に81倍が押し寄せ、軽微な障害が全断に発展する。
対策: ①リトライする層を1つに限定 ②Retry Budget（全リクエストの10%まで）③SDK の既定リトライを確認する（気づかず二重にリトライしていることが多い）。（12章）
Q18. なぜジッターが必要ですか
全クライアントが同じタイミングで再試行すると、復旧しかけた下流を再び落とすから（Thundering Herd）。
AWS 推奨は Full Jitter: sleep = random(0, min(cap, base × 2^attempt))。
ジッター無しの指数バックオフは、効果が半減する。（12章）
Q19. 非同期 worker の中で sleep してリトライしてよいですか
ダメです。Kafka なら partition 全体が止まり、SQS なら worker のスロットが埋まる。
正解は遅延キュー / Retry Topic にメッセージを移し、元の処理はすぐ次に進むこと。
RabbitMQ なら TTL + DLX、SQS なら ChangeMessageVisibility、Kafka なら retry topic を段階的に用意する。（12章）

Part 4: DLQ・順序・整合性（20〜26）

Q20. DLQ を作っただけでは不十分な理由は？
監視が無ければ「静かなデータ消失」と同じだから。
必要なのは4点セット: ①1件でも入ったらアラート（件数の閾値ではなく >0）②原因の分類（エラーメッセージを DLQ に含める）③Redrive の手順とツール ④DLQ 自体の保持期間の管理。
「3ヶ月後にCS問い合わせで発覚したが、DLQ の保持期間14日を過ぎていた」が典型的な事故。（13章）
Q21. Kafka で1件が処理できないと何が起きますか
offset は連番なので飛ばせず、その partition の後続が全部止まる（Head-of-Line Blocking）。50万件が滞留することもある。
Kafka には DLQ の組み込み機能が無いので、アプリが明示的に別 topic へ produce する必要がある。（13章）
Q22. Consumer Lag はどう監視しますか
件数ではなく「時間に換算した遅れ」で見る。lag ÷ 処理レート = 何秒遅れているか。
3200件の滞留は、100件/秒なら32秒だが、1件/秒なら53分。絶対件数で閾値を決めると、流量が変わるたびに調整が必要になる。
Pub/Sub の oldest_unacked_message_age、SQS の ApproximateAgeOfOldestMessage が正しい指標。（14章）
Q23. デプロイのたびに遅延が出るのはなぜ？
Rebalance。consumer が増減すると担当 partition が割り直され、既定の Eager Rebalance では全 consumer が一旦停止する（Stop-the-World）。
対策: ①Cooperative Sticky Assignor（影響のある partition だけ移す）②Static Membership（group.instance.id で、再起動しても同じ担当に戻る）。（14章）
Q24. 順序保証はどこまで可能ですか
全体の順序（全順序）は、単一の直列化点を作らない限り不可能——つまりスケールしない。
可能なのは「key 単位の順序（半順序）」だけ。
そして最も堅牢なのは「順序に依存しない設計」: delta（-1室）ではなく state（残5室）+ version を送り、consumer 側で WHERE version < $new により古いものを捨てる。（15章）
Q25. リトライと順序保証は両立しますか
両立しません。Retry Topic や遅延キューに逃がした瞬間、そのメッセージは後続に追い越される。
選択肢は3つ: ①version 判定で順序に依存しない設計にする（推奨） ②順序が critical なら失敗時は「止める」 ③DLQ ではなく人が対応する。
このトレードオフを認識していることを示すのが面接では重要。（12章・15章）
Q26. 「DBに書いてイベントを publish する」の正しい実装は？
そのまま2つ書くと Dual Write 問題が起きる——publish が失敗する / プロセスが2つの間で死ぬ / 逆順にすると幽霊イベントが出る。コードの書き方では原理的に解決できない。
正解は Outbox Pattern: イベントを業務データと同じトランザクションで同じDBの outbox テーブルに書き、別プロセス（Relay）が読んで publish する。
あるいは CDC（DBのログを読む）か Event Sourcing。この3つ以外に解はない。（17章・18章）

Part 5: Outbox・CDC・Saga・Webhook（27〜30）

Q27. Outbox テーブルの運用で必須のものは？
①部分インデックス CREATE INDEX ON outbox(id) WHERE published_at IS NULL——これが無いとテーブルが育つほど Relay が遅くなる。
②時系列パーティション + DROPによる削除（DELETE だと VACUUM の負荷とロックが問題になる）。
③「未送信の最古レコードの年齢」の監視——Relay が止まったことに気づく唯一の手段。
④複数 Relay なら FOR UPDATE SKIP LOCKED。（18章）
Q28. CDC の最大の運用リスクは？
PostgreSQL のレプリケーションスロットの滞留で、本番DBのディスクが溢れて停止すること。
Debezium が止まっている間、WAL が削除されずに溜まり続ける。週末に止めたまま放置して数百GB溜まったという事故が典型。
pg_replication_slots の遅延を監視し、使わないスロットは必ず drop する。
次に大きいのは「DBのスキーマが公開APIになる」問題——outbox テーブルだけを CDC 対象にすることで回避できる。（19章）
Q29. Saga で補償トランザクションが失敗したら？
補償の補償は存在しません。リトライし、それでもダメなら状態を compensation_failed として記録し、人を呼ぶ（オンコールにアラート）。
加えて照合バッチ（Reconciliation）を必ず併設し、中途半端な Saga を定期的に検出する。
設計原則として「補償が難しい/不可能なステップを、できるだけ後ろに置く」——メール送信は必ず最後。（20章）
Q30. Webhook を受ける正しい手順は？
①raw body を読む ②timestamp を検証（5分以上古ければ拒否）③HMAC 署名を hmac.Equal で検証 ④event_id で冪等に保存 ⑤即 200 を返す。処理は非同期。
ハンドラ内で重い処理をすると、相手のタイムアウト（5〜10秒）を超えて再送され、二重処理が始まる。
さらに業務エラーで 5xx を返してはいけない——「受け取れたか」と「処理できたか」は別。5xx を返すと相手が3日間リトライし続ける。（24章）

31 システム設計面接 — 12問と、評価される答え方

結論: 面接官が見ているのは「知識」ではなく「トレードオフを言語化できるか」です。正解を1つ言うより、選択肢を2つ挙げて理由付きで選ぶほうが評価されます。以下は各問について「弱い答え」「良い答え」「強い答え」を並べています。

Q1. 「1日1億件のイベントを処理するシステムを設計してください」
弱い答え: いきなり Kafka の構成図を描き始める。
良い答え: 要件を確認する——「イベントの種類は？」「購読者は何個？」「順序は必要？」「遅延はどこまで許容？」「再処理は必要？」
強い答え: 1億/日 = 平均1157 rps、ピークはその3〜5倍で約5000 rps と概算し、それが「1 partition あたり数千 msg/s」の Kafka で十分か検証する。その上で「再生が必要か」で Kafka と SQS を分岐させ、Outbox で publish の確実性を担保、consumer は冪等に、と一続きで説明する。
評価点: 数字で規模感を確認する姿勢。要件を聞かずに技術を選ばないこと。
Q2. 「予約が確定したら、メール送信・在庫反映・検索インデックス更新・分析転送を行いたい」
弱い答え: 「予約APIから4つのサービスを順に呼びます」→ 可用性が積で下がり、レイテンシも加算される。
良い答え: 「予約確定イベントを Topic に publish し、4つの consumer が購読します」
強い答え: さらに 「publish は Outbox 経由にします。DBのコミットと publish は原子的にできないので」と Dual Write に言及する。加えて「4つのうち在庫反映だけは順序が必要なので key を hotel_id にします」「メール送信は冪等キーで二重送信を防ぎます」まで踏み込む。
評価点: Dual Write を自分から持ち出せるか。これが最大の分岐点。
Q3. 「Exactly Once を実現できますか」
弱い答え: 「Kafka の Exactly Once を有効にします」→ 外部副作用に効かないことを知らないと見なされる。
強い答え: 「配信としては原理的に不可能です。『処理する』と『処理したと記録する』が別の操作で、その間に必ずクラッシュしうるため。At Least Once + 冪等な処理で Effectively Once にします。Kafka Transactions は topic → topic の処理には有効ですが、メール送信のような外部副作用には効きません」
評価点: これは罠の質問。「できます」と答えると即座に深掘りされる。
Q4. 「メールが2通届くという問い合わせが来ました。原因と対策は？」
強い答え: 「At Least Once 配信では、処理が成功して ack する直前にクラッシュすると再配信されるため、これは仕様上起こりうることです。特にデプロイのたびに SIGTERM で処理中のメッセージが再配信されるので、稀ではなく確実に起きます。
対策は consumer を冪等にすること: (event_id, template_id, recipient) をキーに送信記録テーブルへ INSERT ... ON CONFLICT DO NOTHING し、影響行数が0なら送信しない。この INSERT と送信記録の更新を同一トランザクションで扱います」
評価点: 「バグ」ではなく「仕様」と捉えられるか。頻度ではなく「必ず起きる」と認識しているか。
Q5. 「キューに100万件溜まりました。どう対応しますか」
強い答え: 手順で答える。
①切り分け: 流入が増えたのか / 処理が遅くなったのか / consumer が減ったのか / 1件が詰まっているのか。producer 側の rate と consumer 側の処理レートの両方を見る。
②即応: consumer をスケール（ただし Kafka なら partition 数が上限）。下流がボトルネックなら、増やしても悪化するだけなので注意。
③判断: 古いメッセージに価値があるか。「3日前の在庫更新通知」なら捨てる判断もある（TTL）。
④復旧時の注意: 溜まった分が一気に流れて下流を再び落とす（Thundering Herd）ため、同時実行数を絞りながら段階的に流す。
評価点: ④まで言及できると運用経験があると判断される。
Q6. 「複数サービスにまたがる予約処理の整合性をどう保ちますか」
弱い答え: 「分散トランザクション（2PC）を使います」
強い答え: 「2PC はコーディネータが SPOF になり、可用性が全参加者の積になり、そもそも Kafka も SQS も XA に対応していないので使いません。Saga を使い、各ステップに補償トランザクションを定義します。ステップが3つを超えるので Orchestration 方式で、状態をDBに永続化して『今どこで止まっているか』を追えるようにします。
補償のコストを下げるため、authorize（void は無料）を先に、capture（refund は手数料が発生）を最後に置きます。メール送信は補償不可能なので全ステップ成功後です」
評価点: 補償の「業務コスト」まで考えられるか。
Q7. 「決済APIがタイムアウトしました。どうしますか」
弱い答え: 「リトライします」→ 二重課金のリスクを理解していない。
強い答え: 「タイムアウトは『失敗』ではなく『不明』です。相手側で成功している可能性があります。
①呼び出す前に authorizing として記録しておく ②タイムアウトしたら unknown 状態にする ③冪等キーで照会APIを叩き、実際の結果を確定させる ④それでも不明なら人を呼ぶ。
そもそも最初の呼び出しに Idempotency-Key を付けておけば、リトライしても二重課金にはなりません。キーは pay-{reservation_id}-v1 のように業務IDから決定論的に導出します」
評価点: 「第3の状態」を設計に含められるか。決済系で最重要の質問。
Q8. 「Webhook を受けるエンドポイントを設計してください」
強い答え: 「検証 → 即 200 → キューに入れて非同期処理の3段階です。
検証は ①raw body で HMAC を計算（JSON をパースして再シリアライズすると、キーの順序が変わって不一致になる）②timestamp を含めてリプレイ攻撃を防ぐ ③hmac.Equal で定数時間比較。
業務エラーでは 5xx を返しません——受信は成功しているので 200 を返し、自分の DLQ で処理します。5xx を返すと相手が3日間リトライし続けます。
加えてWebhook は届かないことがあるので、定期照合バッチを併設します」
評価点: 最後の照合バッチに言及できると、実運用の経験があると判断される。
Q9. 「オーバーブッキングを防ぐ設計は？」
強い答え: 「これは非同期の問題ではなく同時実行制御の問題なので、3層で守ります。
層1: 在庫の引き当ては必ず同期で、条件付き更新（UPDATE ... SET rooms=rooms-1 WHERE rooms>=1）を使う。0行更新なら売り切れ。これで競合しても2件受け付けない。
層2: バッファ在庫——実在庫10室のうち OTA には8室だけ出す。同期の遅延を吸収する。
層3: それでも溢れたときの業務プロセス（アップグレード / 近隣手配 / 返金 + 補償）を設計に含める。
非同期にできるのは『在庫が変わったことを各OTAに知らせる処理』だけです」
評価点: 「同期にすべき1点」を見極められるか。
Q10. 「イベントのスキーマを変更したい。どうしますか」
強い答え: 「公開したイベントは API と同じ契約なので、破壊的変更はできません。
許される: フィールドの追加（オプショナル）、既定値の追加。
許されない: フィールドの削除、型変更、意味の変更。
必要な場合は新しいイベントタイプ（またはバージョン付き topic）を作り、旧新を並行運用して、全購読者の移行を確認してから旧を廃止します。
仕組みとしてはスキーマレジストリで後方互換性を CI で強制し、購読者のインベントリを管理します」
評価点: 「誰が購読しているか分からない」ことの怖さを認識しているか。
Q11. 「イベント駆動にすべきでないのはどんなときですか」
強い答え: 「4つあります。
①購読者が1つで、今後も増えないと分かっている——それは『命令』であって『イベント』ではないので、Queue か同期呼び出しでよい。
②強い整合性が要件——Saga で許容できるか先に検討する。
③チームに運用体制がない——Kafka の運用は片手間ではできない。SQS か DB キューから始めるべき。
④処理の全体像を人が頻繁に追う必要がある——分散トレーシングを先に入れられないなら時期尚早。
逆に『新機能を追加するたびに既存サービスを変更している』という signal が出たら、Topic 化のタイミングです」
評価点: 技術を「使わない」判断ができるか。最も成熟を示す回答。
Q12. 「このシステムを監視するとしたら、何を見ますか」
強い答え: 「5つです。
①最古の未処理メッセージの年齢（件数ではなく時間。ユーザー影響に直結する）
②DLQ の件数（1件でもアラート）
③Outbox の未送信レコードの最古の年齢（Relay が止まったことに気づく唯一の手段）
④リトライ率（急増は障害の先行指標）
⑤照合バッチの不一致件数（最後の砦。ゼロが正常）
加えて、これらをSLO として定義します——『99%のイベントは publish から30秒以内に処理される』のように」
評価点: 「件数ではなく時間」「1件でもアラート」の2点で、運用経験の有無が分かる。

32 実務でよくある障害例 — 24パターン

結論: 以下は全て実際に起きるパターンです。「症状 → 原因 → 対策」の形で頭に入れておくと、障害時の切り分けが劇的に速くなります。★印は特に頻度が高く、被害も大きいもの。

#症状原因対策
1 ★DBに予約はあるがメールが送られていないDual Write。DB commit 後の publish が失敗、またはその間にプロセスが死んだOutbox Pattern（18章）

5 ★consumer を増やしてもスループットが上がらないpartition 数が並列度の上限partition を増やす / key 単位で goroutine 分割（14章）
6 ★特定の partition だけ lag が数時間Hot Partition。key が偏っている（人気ホテルなど）複合キー化 / 順序が不要なら key を外す（15章）

🔧 障害時の切り分けフローチャート

  1. 「イベントが飛んでいない」のか「処理されていない」のかを最初に切り分ける → outbox / topic のメッセージ数を見る
  2. 飛んでいない → Outbox の未送信件数と最古の年齢 / Relay の生死 / producer のエラー率
  3. 飛んでいるが処理されていない → Consumer Lag / consumer の生死 / DLQ の件数
  4. 処理されているが結果がおかしい → 順序（version の逆転）/ 重複（冪等性の不備）/ 部分的失敗（Saga の中断）
  5. どこも異常が無いのに不整合がある → 照合バッチの出番。「自分の記録」と「相手の記録」を突き合わせる

33 よくある設計ミス — 判断のレベルで間違えるもの

結論: 32章の障害は「実装のミス」ですが、こちらは「判断のミス」です。実装ミスは直せますが、判断ミスは何年も引きずります。

ミス1: いきなり Kafka を入れる

「非同期 = Kafka」という短絡。1日数万件なら DB の jobs テーブル + SKIP LOCKED で十分実用的で、しかも Dual Write 問題が最初から発生しない。
正しい順序: DBキュー → SQS → Kafka。「Kafka を入れました」は成果ではなく、運用負債の獲得。

ミス2: 冪等性を後回しにする

「重複は稀だから後で」→ デプロイのたびに確実に起きる（SIGTERM で処理中のメッセージが再配信されるため）。
冪等性は最初の consumer を書くときに実装する。後から全 consumer に入れるのは苦行。

ミス3: Dual Write に気づかない

本書で最も重要な指摘。「DBに書いて publish する」を素直に実装してしまう。
不整合は静かに、少しずつ蓄積するため、数ヶ月後に「なぜかメールが送られていない予約が0.3%ある」という形で発覚する。

ミス4: 全部イベント駆動にする

日次集計・請求書生成・データ移行までイベント駆動にする。バッチのほうが単純で速くて安いケースは大量にある。
「締め日」という時点が本質の処理は、バッチが正しい。

ミス5: 「全順序が必要」を疑わない

要件として「順番どおりに」と言われたら、「何と何の順序ですか？」と聞き返す。
ほぼ常に必要なのは「同じエンティティに対する順序」だけ。全順序を実装するとスケールが完全に失われる。

ミス6: 監視を後回しにする

非同期システムは「静かに壊れる」のが最大の特徴。同期なら500エラーが出るが、非同期は何も起きないように見える。
DLQ・Lag・Outbox 未送信年齢の監視は、機能実装と同時にやる。

ミス7: 相関ID（trace_id）を通さない

後から入れるのは極めて困難。最初のHTTPリクエストからメッセージヘッダー、worker のログまで trace_id を貫通させる。
これが無いと「なぜこのメールが送られたか」の調査に半日かかる。

ミス8: イベントに「状態」ではなく「差分」を入れる

「-1室」を送ると、順序が狂ったときに回復不能。「残5室 + version 12」を送れば、古いものを捨てるだけで済む。
「順序保証に頼らない設計」が、順序保証そのものより堅牢。

ミス9: イベントに全データを詰め込む / 何も入れない

詰め込みすぎ → スキーマ変更が全購読者に波及、サイズ制限に抵触。
少なすぎ（IDだけ）→ 全 consumer が API を叩き、元サービスが過負荷に。
「購読者の8割が必要とする最小限」+ 詳細取得用のID が現実的な落とし所。

ミス10: 補償トランザクションを設計しない

正常系だけ実装して「失敗したときは手動で」と先送りする。Saga の各ステップには、実装前に補償を定義する。
補償不可能なステップ（メール送信）を最後に置くのは、この検討をして初めて分かる。

ミス11: 照合（Reconciliation）を作らない

「仕組み上は正しいから大丈夫」は成立しない。バグ・障害・相手側の問題で必ず不整合は起きる。
決済・在庫・外部連携には、日次の照合バッチを最初から作る。差分ゼロを毎日確認するのが品質保証そのもの。

ミス12: Event Sourcing を全面採用する

「イベント駆動だから Event Sourcing」という誤解。クエリの困難さ・スキーマ進化の地獄・学習コストで、2年後に CRUD へ戻すケースが多い。
監査要件が強い集約だけに限定する。CQRS（読み書き分離）だけなら広く有用。

ミス13: キューを1本にする

重い処理と軽い処理、大口顧客と小口顧客、優先度の高低を全部同じキューに入れる。
Head-of-Line Blocking と Noisy Neighbor が同時に発生する。処理時間の桁・優先度・テナントで分ける。

ミス14: 遅延の上限を定義しない

「非同期だからいつか処理される」で済ませる。遅延の上限を定義しない非同期は、無限に遅れてよいことになる。
「99%のイベントは5分以内に処理される」のような freshness SLO を定義する。

ミス15: 「誰が購読しているか」を管理しない

イベント駆動の最大の運用コスト。payload を変更したら、知らないところで何かが壊れる。
topic ごとのオーナー・購読者インベントリ・スキーマレジストリを、規模が出る前に整備する。

ミス16: マネージドだから安心と思う

SQS も Pub/Sub も、詰まるときは詰まる。ブローカーが落ちなくても、consumer が遅ければ同じこと。
「基盤の可用性」と「自分のシステムの可用性」は別。

🎯 この本を1文に圧縮すると

「同期にすべき1点を見極め、残りを非同期にし、その代償（重複・順序・不整合）を冪等性・version・Outbox・照合で払う」

非同期化は「速くする技術」ではなく「壊れ方を選ぶ技術」です。同期を選べば「一緒に落ちる」、非同期を選べば「別々に生き残るが、一時的にズレる」。
どちらを選んでも代償はあります。設計とは、どの代償なら払えるかを決めることです。

2最古の未処理メッセージの年齢SLO（例: 5分）を超えたら遅延に気づけない
3Outbox 未送信の最古の年齢1分を超えたらRelay 停止に気づけない
4照合バッチの不一致件数> 0 でアラート不整合が蓄積する
5CDC のレプリケーションスロット遅延1GB を超えたら本番DBがディスクフルで停止
6リトライ率平常時の3倍障害の予兆を見逃す
7consumer の処理レートとエラー率ベースラインからの乖離劣化に気づけない
8publish の失敗率> 0.01%イベントが消えている
