分散システムの一貫性と合意形成についてまとめています。

この本の主張1

整合性は ON/OFF ではなく「どこまで嘘をつかないか」の段階。強い保証は必ずレイテンシと可用性で支払う。無料の Strong Consistency は存在しない。

この本の主張2

Consensus は「投票の仕組み」ではなく「1本のログの順序を全員に同じ順で合意させる装置」。Raft も Paxos も ZAB も、やっていることはレプリケーテッドログただ1つ。

この本の主張3

実務の事故の中心は「死んだと思ったノードが生きていた」。Failure Detection は原理的に不完全なので、検知を完璧にするのではなくFencing で古いリーダーを無力化する。

専門用語は全部、現実世界のものに置き換えます。以下のマッピングは全章で一貫して使うので、迷ったらここに戻ってください。中心の比喩は「複数の支店を持つ銀行」です。整合性も合意も「支店ごとに違う残高が見えると困る」という問題から出発します。

この本の1行まとめ: Consistency は「クライアントに見せてよい嘘の範囲を決めるAPI仕様」、Consensus は「その仕様を満たすためにノード群が1本のログの順序を確定させる手続き」。前者が要求、後者が実装。この対応を最後まで手放さないこと。

01 なぜ整合性が問題になるのか — 複製した瞬間に生まれる嘘

結論: 整合性の問題は「複製」が原因ではなく、「複製 + 有限の通信速度」が原因。データを2箇所に置いた瞬間、両者が同じ値になる「途中の時間」が必ず生まれ、その間に読まれると嘘をつくことになります。この章はすべての土台です。

🏦 例え: 東京本店で ¥10,000 入金した。大阪支店には電話で伝える。電話が繋がるまでの 200ms、大阪支店の帳簿は「入金前」のまま。この 200ms に大阪の窓口で残高照会されたら、大阪は嘘をつく。この 200ms をどう扱うかが整合性モデルの全て。

① この技術は何を解決するために生まれたのか

整合性モデルという概念は「分散システムが返す答えのブレを、アプリ開発者が予測可能な形に押し込める」ために生まれました。解決したい対象は3つあります。

  • 複製の理由は3つしかない — ① 可用性（1台落ちても続ける）② スケール（読みを分散する）③ 地理的近接（ユーザーの近くで応答する）。この3つのどれかを取ると、必ず複製が発生する
  • 複製したら「一瞬の不一致」は消せない — 消せると信じる設計が事故を生む。だから「不一致がどこまで観測されうるか」を仕様化する
  • 仕様化されていれば、アプリ側で対処できる — 「自分の書き込みは必ず読める」と決まっていれば、UIは楽観更新を安全にできる

② この概念がないと何が問題になるか

  • バグの再現ができない — 「たまに古いデータが出る」を「たまに」で片付けると、原因がキャッシュか複製遅延かアプリのバグか永遠に分からない
  • 過剰設計か過小設計に振れる — 全部を Strong にすると遅くて高い。全部を Eventual にすると在庫がマイナスになる
  • 面接で落ちる — 「整合性はどうしますか？」に「強整合にします」と答えると、必ず「じゃあ地理分散のレイテンシは？」で詰まる

Fig 1-1: 複製の3動機と副作用。数値は一般的なオーダーの目安（事実というより設計時の桁感覚として使う）。

③ 基本概念 — 「整合性」とは何を約束するのか

整合性モデルは「起こりうる実行結果の集合」を定義する契約です。強いモデルは集合が小さく（結果が予測しやすい）、弱いモデルは集合が大きい（何が返るか分からない）。

用語定義銀行の例え
Replica同じデータのコピーを持つノード支店
Stale read最新でない値を読むこと更新前の残高を答える
Replication lagプライマリへの書き込みがレプリカに届くまでの遅れ電話が繋がるまでの時間
Divergenceレプリカ間で値が恒久的に食い違うこと2つの支店が別々の残高を「正」と主張する
Convergence書き込みが止まればいつか全レプリカが同じ値になる性質閉店後に必ず帳簿が一致する
Total order全操作に唯一の並び順が付くこと本部が採番した通し番号

⑥ メリット（整合性を明示的に設計する）

  • 障害時に「これは仕様内 / 仕様外」を即断できる
  • コストを必要な場所だけに集中できる
  • アプリ側の補償ロジック（冪等性・リトライ）の要否が決まる

⑦ デメリット・トレードオフ

  • データ種別ごとに整合性を分けると、システムが2〜3層に増えて運用が複雑化する
  • 「どこまで古くて良いか」の判断はビジネス側との合意が必要で、技術だけで決められない
  • 境界を跨ぐ処理（在庫=強 × カート=弱）で、結局アプリが整合性を面倒見る羽目になる

⑧ 実務での利用例

  • Instagram（事実）: いいね数やフォロワー数は結果整合で表示。一方で「自分の投稿が自分のプロフィールに出ない」のは許されないため、書き込み後の読みを工夫する必要がある — 公開資料では PostgreSQL の非同期レプリカ運用と Cassandra 併用が語られている
  • Amazon（事実）: S3 は 2020年12月に strong read-after-write consistency を全リージョンで提供開始。それ以前は「PUT 直後の GET で 404 / 旧版」があり得た。アプリ側の「リトライして待つ」コードが世界中で不要になった
  • Uber（事実）: 位置情報のような高頻度・許容度の高いデータと、決済のような厳格なデータでストアを分けている（Schemaless / Docstore などを用途別に構成）
  • 解釈: 成熟した組織はほぼ例外なく「強整合の面積を最小化する」方向に収束している。強整合を捨てるのではなく、必要な1点に閉じ込める

⑨ Googleレベルではどう設計されるか

  • 整合性を「選べる」基盤を作る: Spanner は 1つのシステムで「強整合の読み」「指定タイムスタンプの読み」「バウンデッドステイルネスの読み」を API で切り替えられる。アプリごとにDBを選ぶのではなく、クエリ単位で強さを選ぶ
  • デフォルトを強くする: 誤用しても壊れない方向（強整合）を既定値にし、性能が必要な箇所だけ明示的に弱める。「弱いのが既定」だと、弱さを理解していない人のコードが本番を壊す
  • 計測する: 複製遅延を p50 だけでなく p99 / p999 で監視し、SLO に含める。「遅延は普段 5ms」は無意味で、事故は p999 で起きる

⑩ システム設計面接ではどう問われるか

  • Q:「このシステムはどの整合性が必要ですか？」 → 全体で1つ答えるのは不正解。エンティティごとに分けて答えるのが正解（残高=線形化可能 / フィード=因果 / カウンタ=結果整合）
  • Q:「read-your-writes を保証するには？」 → ① 書き込み後 N 秒は primary から読む ② セッションをレプリカに固定 ③ 書き込み時に返る version をクライアントが保持し、その version 以上のレプリカから読む（最も実装が硬い）
  • 加点される言い方: 「複製遅延の p99 を測り、その値をユーザー体験の許容値と比べて判断します」— 数字で語ると一段上に見える

02 Consistency という語の3つの意味 — 用語事故を止める

結論: 「Consistency」は3つの全く違う意味で使われており、混同が議論の9割の混乱の原因。ACID の C、CAP の C、整合性モデルの C は別物です。面接でここを整理して話せると、いきなり信頼されます。

Fig 2-1: 3つの C。ACID の C は「業務ルール」、CAP の C は「線形化可能性」、モデルの C は「保証の段階」。

③ 基本概念 — Serializability と Linearizability の違い（最重要）

観点Serializability（直列化可能性）Linearizability（線形化可能性）
対象複数オブジェクトにまたがるトランザクション単一オブジェクト（1つのキー/レジスタ）への操作
約束並行実行の結果が、何らかの逐次実行と同じになる操作が実時間上のある1点で起きたように見える
実時間考慮しない（順番の入れ替えを許す）考慮する（後で始まった操作は前の結果を見る）
由来DBのトランザクション理論並行プログラミング / 分散レジスタ理論
両方満たすとStrict Serializability（＝Spanner の external consistency に相当する強さ）

覚え方: Serializable は「並べ替えてよいが、辻褄は合う」。Linearizable は「並べ替えを許さない（実時間順を守る）」。 Snapshot Isolation は Serializable より弱く、しかも Linearizable でもない（古いスナップショットを読むため）。

⑩ 面接での問われ方

  • 頻出:「Serializability と Linearizability の違いは？」 → 上の表を口で言えれば合格。加えて「Serializable な DB でも、レプリカから読めば stale な値を返しうる」と補足すると強い
  • 罠:「CAP の CP を選べば ACID ですか？」 → 別物。CP は分断時に可用性を捨てて線形化可能性を守る選択。ACID の C（業務不変条件）はアプリとスキーマが守るもの

03 Strong Consistency — 「1台に見せる」ための代金

結論: Strong Consistency とは「複製されている事実をクライアントから隠す」こと。実現手段は「書き込みも読み込みも、過半数（あるいはリーダー）を必ず経由させる」の一点に集約されます。代金はレイテンシと可用性。

📮 例え: 「本部に確認してからお答えします」と言う支店。必ず正しい残高を答えられるが、本部が停電したら何も答えられないし、本部が遠いほど待たされる。Strong Consistency はこの窓口ポリシーそのもの。

① 何を解決するために生まれたのか

  • アプリから分散を隠す — 開発者が「複製遅延」「古い値」を意識せずに、単一DBと同じコードを書けるようにする
  • 不変条件を守れるようにする — 「在庫 >= 0」「一意な予約」のような条件は、最新値を読めないと判定できない
  • リーダー/ロック/設定など「1つでなければならないもの」を扱う — 分散ロックや設定値は、複数の値が同時に見えたら意味を失う

② これがないと何が問題になるか

  • 売り越し・二重支払い — 在庫1個を2つのレプリカがそれぞれ「まだある」と判定して両方売る
  • 分散ロックが機能しない — 2つのノードが同時に「自分がロックを取った」と信じる（24章 split brain）
  • UI の不整合 — 「登録しました」と表示した直後の一覧に、その項目が出ない

⑥ メリット

  • アプリコードが単純になる（複製を意識しない）
  • 不変条件をDB層で守れる（在庫・一意制約）
  • 障害時の推論が容易（「見えた値は commit 済み」）

⑦ トレードオフ

  • 書き込みレイテンシが最低 1 RTT 増える
  • 分断時は可用性を失う（CP 側の選択・09章）
  • スループット上限がリーダー1台に縛られる → シャーディングが前提になる
  • コストが高い（Spanner のような基盤は運用も課金も重い）

⑧ 実務での利用例

  • Google Spanner（事実）: 外部整合性（external consistency）を提供。読み書きトランザクションは Paxos + 2PC + commit-wait を経る
  • AWS DynamoDB（事実）: 既定の読みは結果整合だが、ConsistentRead=true で強整合読みが選べる（コストは 2倍の読み取りキャパシティ）。「整合性を課金メニューにした」設計として示唆的
  • Amazon S3（事実）: 2020年12月から strong read-after-write。以前は「書いた直後の一覧に出ない」前提のコードが必要だった
  • Airbnb / Booking.com（事実 + 解釈）: 予約確定は強整合（DBの一意制約やトランザクション）、空室検索は結果整合のインデックス。「検索は多少古くてよい、確定は絶対に間違えない」という典型的な二層構成

⑨ Googleレベルの設計

  • 強整合の粒度を「グループ」に切る: Megastore は entity group 単位、Spanner は split 単位で Paxos グループを持つ。グループ内は強整合、グループ間は2PCで例外的にという構造にして、グローバルな直列化点を作らない
  • 読みは強整合でも安く: Spanner の read-only トランザクションはロックを取らず、タイムスタンプを1つ選んで各レプリカのローカル読みで済ませる（safe time を超えていれば）。「強整合な読み」を「合意なしの読み」にするのが核心的な工夫
  • 強整合をSLOに翻訳する: 「強整合」ではなく「p99 の commit latency が X ms 以内、可用性 99.999%」と数字で契約する

⑩ 面接での問われ方

  • Q:「全世界のユーザーに強整合な残高を見せるには？」 → ユーザーをリージョンに固定（ホームリージョン）→ そのリージョン内で Raft/Paxos → 他リージョンからは stale read か proxy。「全世界で1つの強整合クラスタ」は避けるのが正解
  • Q:「強整合読みのコストを下げる方法は？」 → ① リーダーリース read ② ReadIndex（21章） ③ follower read + safe time ④ クライアントが version を持ち回る
  • 減点される答え: 「Redis で分散ロックを取って強整合にします」→ 24章の fencing 問題を知らないと見なされる

04 Eventual Consistency — 「いつか揃う」の正体

結論: Eventual Consistency は「書き込みが止まれば、いつか全レプリカが同じ値に収束する」だけを約束するモデル。それ以外は何も約束しません。「いつ」も「途中で何が見えるか」も「どの値が勝つか」も規定されていないのが最大の落とし穴です。

📦 例え: 全国の倉庫に「在庫数」を書いた紙を貼っている。更新は宅配便で各倉庫に送る。送り終われば全倉庫が同じ数字になる（＝収束）。しかし 宅配便が到着する順序は保証されず、大阪には新しい紙が先に、名古屋には古い紙が後から届くこともある。名古屋は古い紙で上書きしてしまうかもしれない。→ だから「どちらが新しいか」を紙に書く必要がある（＝バージョン/タイムスタンプ）。

① 何を解決するために生まれたのか

  • 可用性を最優先したい — ネットワーク分断中でも書き込みを受け付け続けたい（Amazon のカート: 「カートに入れられない」は売上の直接損失）
  • 地理分散で低レイテンシを出したい — 手元のレプリカに書いて即 ack（合意を待たない）
  • 書き込みスループットを上げたい — 合意プロトコルの調整コスト（1 RTT + fsync）を省く

② これがないと（つまり全部強整合だと）何が問題になるか

  • 1台の遅いノードが全書き込みを引きずる — 強整合は「一番遅い必要ノード」に律速される（tail latency amplification）
  • 分断で書き込み不能 — リージョン間リンク断で「投稿できない」「カートに入れられない」
  • コストが正当化できない — 「いいね数」を線形化可能にするのは、価値ゼロに対する高額支払い

③ 基本概念 — Eventual が「約束していないこと」の一覧

期待Eventual は保証するか起きうる現象
いつか全レプリカが同じ値になるする（これだけ）—
自分が書いた値を自分で読めるしないプロフィール更新後、旧値が表示される
一度見えた新しい値が消えないしないリロードで値が古くなる（時間が巻き戻る / monotonic read 違反）
因果順が守られるしない返信が本文より先に表示される
同時更新の勝者が決まっているしない（実装依存）LWW で片方が黙って消える（lost update）
収束までの時間に上限があるしないヒント滞留やノード復帰待ちで数時間ずれることもある

実務上の重要点: 「Eventual Consistency で十分」と言うとき、本当に必要なのはたいてい read-your-writes + monotonic read（＝セッション整合性）です。これは Eventual に安価なオプションを足すだけで実現できます（07章）。

④ 内部でどのように動くのか — 収束の仕組み3点セット

  • 1. 書き込みの伝播 — gossip / hinted handoff（宛先が落ちていたら他ノードが預かり、復帰後に渡す）
  • 2. 読み時修復（read repair） — 読んだときに古いレプリカを見つけたら、ついでに直す
  • 3. 定期修復（anti-entropy） — Merkle tree でレプリカ間のハッシュを比較し、差分だけ転送する

⑤ 実際のシステム構成でどう使われるか

  • マルチリージョン active-active: 各リージョンでローカル書き込み → 非同期で相互複製。競合は CRDT か LWW か業務ルールで解決
  • キャッシュ層: DB は強整合、キャッシュは TTL 付き結果整合。「キャッシュ無効化の伝播遅延」がそのまま整合性の窓になる
  • 検索・分析: CDC（変更データキャプチャ）で Elasticsearch / データウェアハウスへ流す。ここは分単位の遅延が普通
  • カウンタ: 各ノードでローカル加算 → 定期集計（＝可換な操作なので競合しない）

Fig 4-2: 競合解決の3方式。「不変条件を守る必要があるか」で選ぶ。守る必要があるなら結果整合ではなく合意が必要。

⑥ メリット

  • 分断中も書き込みを受け付けられる（可用性が最大）
  • レイテンシが最小（ローカル書き込み + 即 ack）
  • ノード追加でほぼ線形にスケールする
  • 運用が単純（リーダー選出も切り替えもない）

⑦ トレードオフ

  • 不変条件を守れない（在庫・残高・一意制約は不可）
  • 競合解決の複雑さがアプリに漏れる
  • デバッグが難しい（「そのとき何が見えたか」を再現できない）
  • 収束時間に上限がなく、監視しないと気付けない

⑧ 実務での利用例

  • Amazon（事実）: Dynamo 論文（2007）はショッピングカートを題材に「書き込みを絶対に落とさない」設計を示した。競合は和集合で解決 — 削除が復活する副作用より、カートに入らないことの方が損失が大きいという明確な business trade-off
  • Netflix（事実 + 解釈）: 全世界の視聴履歴やレコメンドは Cassandra 中心で結果整合。「再生ボタンが押せること」の方が「視聴位置が完全に最新であること」より重要という優先順位が設計に現れている
  • Twitter/X（事実）: フォロワー数やいいね数はキャッシュ・集計経路を通り、瞬時に厳密一致しない。一方でツイートIDは Snowflake で時系列ソート可能に設計されている（＝順序だけは別の仕組みで担保）
  • Instagram（事実 + 解釈）: いいね数の表示は結果整合。ただし「自分のいいねが反映されない」は許されないため、クライアント側の楽観更新でユーザー視点の read-your-writes を作る。整合性をサーバだけで解こうとしないという実務的な解

⑨ Googleレベルの設計

  • 「結果整合で良い」を検証可能にする: 収束遅延をメトリクス化し（例: replication lag p999、未収束キー数）、SLO 違反をアラートにする。「Eventually」を運用可能な数字に翻訳する
  • 不変条件が要るデータを混ぜない: 結果整合のストアに「絶対に重複してはいけないID」を置かない。必要なら別の強整合ストア（Spanner / etcd）に切り出す
  • クライアントを設計に含める: サーバ側だけで整合性を作らず、クライアントの楽観更新・バージョン保持・再試行を含めた end-to-end で体験を設計する

⑩ 面接での問われ方

  • Q:「結果整合で問題ないデータは？」 → 「読み手が古い値を見ても業務不変条件を壊さないデータ」と定義してから例示（カウンタ・レコメンド・検索インデックス・視聴履歴）
  • Q:「結果整合だと『保存したのに消えた』とユーザーが言います。どうしますか？」 → read-your-writes を追加（セッション固定 / version トークン / 書き込み後は primary 読み）。モデルを Strong に上げるのではなく、必要な保証だけを足すのが正解
  • Q:「LWW の危険は？」 → ①書き込み消失 ②時計ずれで古い方が勝つ ③タイブレーク未定義。対策は vector clock / CRDT / サーバ側単調タイムスタンプ（HLC）

05 Linearizability — 最強の保証を、厳密に定義する

結論: Linearizability とは「各操作が、その開始と終了の間のどこか一点で瞬間的に効いたように見える」性質。言い換えると「システムが1台のマシンのように振る舞う（recency guarantee）」。CAP の C はこれです。この定義を口で言えるかどうかが、面接で最も差が出る一点です。

📚 例え: 図書館の貸出カウンターが1つしかない状態。誰が何時に借りたか・返したかが1本の台帳に一列に記録され、「返却された直後に来た人は必ず『貸出可能』と聞ける」。カウンターが複数あって台帳が別々だと、返却済みの本を「貸出中」と言われる（＝線形化可能でない）。

① 何を解決するために生まれたのか

  • 「最新」という言葉を数学的に定義する — 「最新の値を返す」を曖昧さなく検証可能にする（Jepsen などのテストが可能になる）
  • 合成可能（composable）な保証を作る — 個々のオブジェクトが線形化可能なら、それらを組み合わせたシステム全体も線形化可能。この性質は Sequential Consistency にはないため、部品ごとに検証できるのが実務上の巨大な利点
  • ロック・一意性・リーダー選出を安全にする — これらは線形化可能なストア（etcd 等）なしには正しく実装できない

② これがないと何が問題になるか — 4つの典型的な破綻

  • ロックが2重に取れる → 24章の split brain。データ破壊に直結する
  • 一意制約が破れる → 同じメールアドレスで2アカウント、同じ座席で2予約
  • cross-channel timing dependency → 画像アップロード後にキューへメッセージを送ったが、ワーカーがファイルストレージから読むと「まだ無い」。2つの経路の間で順序が壊れる
  • 時間が巻き戻る → 一度見えた新しい値が、リロードで古い値に戻る

③ 基本概念 — 「操作は区間、効果は一点」

操作には開始時刻（リクエスト送信）と終了時刻（レスポンス受信）があり、その間のどこかで効果が発生します。線形化可能とは「全操作について、その区間内の1点を選んで一列に並べ、その順序で単一コピーに適用したのと同じ結果になる」ことです。

Fig 5-1: 線形化可能性の判定。重なっている操作は自由に並べ替えてよいが、重なっていない操作の順序は実時間に従う。

⑥ メリット

  • アプリから見て「1台のDB」と同じ推論ができる
  • 合成可能: 部品ごとに線形化可能なら全体も線形化可能
  • ロック・一意性・リーダー選出・分散カウンタの正しい実装が可能
  • Jepsen などで自動検証できる（履歴からチェックできる）

⑦ トレードオフ

  • 分断時に可用性を失う（CAP の CP）
  • 読みも合意経路を通る → 地理分散で高レイテンシ
  • スループットが直列化点に縛られる
  • 「単一オブジェクト」の保証にすぎない → 複数キーの原子性は別途トランザクションが必要

⑧ 実務での利用例

  • etcd / ZooKeeper（事実）: etcd は既定で線形化可能な読みを提供（--consistency=l 相当）。ZooKeeper は読みがローカルなので線形化可能でない（書きは線形化可能）。sync() を呼ぶと線形化可能な読みになる — 20章
  • Kubernetes（事実）: リーダー選出は Lease オブジェクトへの条件付き更新（resourceVersion による楽観ロック）。線形化可能な etcd がなければ2つのコントローラが同時に動く
  • AWS S3（事実）: 2020年12月から strong read-after-write consistency。LIST も強整合になった
  • Google Spanner（事実）: external consistency = strict serializability。トランザクション単位で実時間順序まで保証する（線形化可能性をトランザクションに拡張したもの）

⑨ Googleレベルの設計

  • 「線形化可能な小さな核」を作り、周辺を弱くする: Chubby（Paxos ベースのロックサービス）が線形化可能な真実を提供し、Bigtable / GFS はそこに「誰がマスターか」だけを問い合わせる。強整合の面積を数KBに閉じ込める
  • 読みの線形化コストを構造で削る: Spanner の読み取り専用トランザクションはロックなし・合意なしで、タイムスタンプと safe time の比較だけで済む。「強い保証 = 遅い」を設計で覆す
  • 検証する: 内部でも Jepsen 的な線形化可能性チェッカを回し、「実装が主張通りか」を継続的に検査する。主張と実装の乖離は普通に起きる（実際、多くのDBが Jepsen で違反を指摘されて修正している）

⑩ 面接での問われ方

  • 最頻出:「Linearizability を定義してください」 → 「各操作がその開始と終了の間の一点で瞬間的に効いたように見え、全操作に単一の順序が付き、その順序が実時間の順序と矛盾しないこと。すなわちシステムが1台のコピーのように見えること」
  • Q:「Linearizable が必要なのはどこ？」 → ロック / リーダー選出 / 一意制約 / 在庫の最後の1個 / cross-channel の順序依存。「全部」と言わないのが重要
  • Q:「Linearizable な読みを安くする方法？」 → lease read / ReadIndex / follower read + safe time。「ZooKeeper の読みは線形化可能ではない」と言えると加点
  • Q:「線形化可能なら Serializable ですか？」 → 違う。線形化可能性は単一オブジェクトの話。複数オブジェクトの原子性・分離性は別（02章の表）

06 Sequential Consistency — 「順序はあるが、実時間はない」

結論: Sequential Consistency は「全ノードが同じ順序で操作を見る」だけを要求し、その順序が実時間と一致することは要求しない。Linearizability から「実時間の制約」を1つ外したモデルです。実務では ZooKeeper の読み、CPUのメモリモデル、非同期複製の一部がここに位置します。

🍽 例え: レストランの厨房で、伝票が1本のレールに並んでいる。全ての料理人は同じ順序で伝票を見る（＝順序は1つ）。しかし「10時5分に来た客の伝票が、10時3分の客の伝票より前に置かれている」ことはありうる（＝実時間は守らない）。客からは「なぜ後から来た人が先に出てくるのか」と見えるが、厨房の中では矛盾がない。

Fig 6-1: 3モデルの違い。Linearizable →（実時間の制約を外す）→ Sequential →（無関係な操作の順序合意を外す）→ Causal。

③ 基本概念 — 「単一の全順序」と「実時間」を分けて考える

性質LinearizableSequentialCausalEventual

その順序が実時間と一致はいいいえいいえいいえ

「合成可能でない」の意味: 個々のオブジェクトが Sequential Consistency を満たしていても、2つを組み合わせたシステムは Sequential にならないことがある。これが実務で Sequential を扱いにくくしている理由で、検証したいなら Linearizable、可用性が欲しいなら Causal、という二択に実質的に収束します。

④ 内部でどのように動くのか

  • 全書き込みを1本のログに直列化する（＝リーダー or 合意）ことで「単一の順序」を作る
  • 読みはログの任意の地点で行える — ここが Linearizable との違い。「ログの i 番目まで適用した状態」を読めば、順序は矛盾しないが最新ではない
  • 各クライアントは自分が見たログ位置（zxid / revision / index）を単調に進める — 巻き戻りを防ぐ。ZooKeeper がクライアントごとに zxid を追跡するのはこのため

⑤⑧ システム構成と実務例

  • ZooKeeper（事実）: 書き込みは ZAB で全順序、読みはローカルなので「古いが順序は正しい」。クライアントは自分が見た zxid 以降のみ見る（＝セッション内の単調性を保証）。最新が必要なら sync() を挟む
  • CPU のメモリモデル（事実）: x86-64 は TSO（Total Store Order）で、Sequential Consistency より弱い。Go の sync/atomic や channel が memory barrier を提供して順序を回復する。分散システムの整合性議論は、マルチコアCPUの議論と同じ構造
  • Kafka（事実 + 解釈）: 1パーティション内は全順序、パーティション間は順序なし。これは「因果のあるイベントを同じパーティションキーに寄せる」ことで Causal に近い保証を作る実務パターン

⑩ 面接での問われ方

  • Q:「Linearizability と Sequential Consistency の違いは？」 → 「Sequential は全員が同じ順序を見るが、その順序が実時間と一致しない。だから『5秒前に完了した書き込みを読めない』ことが許される。Linearizable はそれを許さない」
  • Q:「ZooKeeper は線形化可能？」 → 「書きは線形化可能、読みはローカルなので線形化可能でない。sync() を挟めば線形化可能な読みになる」— この答えは知っている人が少ないので差が付く

07 Causal Consistency とクライアント視点の4保証 — 実務の主戦場

結論: 実務で本当に必要なのは、たいてい Linearizability ではなく「Causal + セッション保証」。この組み合わせは分断中も可用性を保てる最強のモデル（理論的に、可用性を保ちながら達成できる最強の整合性は Causal であることが知られています）。しかも実装コストが低い。

📮 例え: 郵便で会話する。「元気？」の手紙(A)に対して「元気だよ」(B)と返す。B は A を読んだ結果なので因果関係がある。第三者に A より先に B が届くと会話が意味不明になる。一方、無関係な「明日は雨です」(C)が A より先に届いても誰も困らない。Causal Consistency は「返信は本文より後に届く」だけを保証する。

① 何を解決するために生まれたのか

  • 人間が知覚できる異常だけを潰す — 「返信が本文より先」「削除したのに復活」「自分の投稿が消えた」は苦情になる。「無関係な他人の投稿の順序が人によって違う」は誰も気付かない
  • 可用性を犠牲にしない — Causal は各レプリカがローカルで応答できるので、分断中も動く
  • 強整合の高いコストを回避する — 全操作の全順序合意（＝合意プロトコル）を必要としない

Fig 7-1: 4つのセッション/因果保証。ユーザーの苦情はこの4パターンにほぼ収まる。Strong にする前にこれで足りるか検討する。

④ 内部でどのように動くのか — 依存追跡の実装

// Go: read-your-writes を version トークンで実装する最小形 type ReadToken struct { MinRevision int64 // クライアントが「これ以上新しいレプリカで読みたい」下限 } func (s *Service) Update(ctx context.Context, u User) (ReadToken, error) { rev, err := s.primary.Write(ctx, u) // 書き込みは primary、戻り値に revision if err != nil { return ReadToken{}, err } return ReadToken{MinRevision: rev}, nil } func (s *Service) Get(ctx context.Context, id string, t ReadToken) (User, error) { for _, r := range s.replicas { if r.AppliedRevision() >= t.MinRevision { // 追いついているレプリカだけ使う return r.Read(ctx, id) } } return s.primary.Read(ctx, id) // 誰も追いついていなければ primary にフォールバック } // ポイント: トークンは Cookie / ヘッダ / gRPC metadata でクライアントに持たせる。 // サーバがセッション状態を持つ必要がなく、水平スケールしても壊れない。

この「バージョントークンを持ち回る」は、etcd の revision、MySQL の GTID、Spanner の read timestamp、Cosmos DB の session token と同じ発想です。整合性をサーバ内部で解こうとせず、クライアントに証拠を持たせるのが定石。

⑥ メリット

  • 分断中も読み書きできる（可用性を保てる最強の整合性）
  • ローカルレプリカで応答 → 低レイテンシ
  • ユーザーが体感する異常のほぼ全てを防げる
  • 実装が段階的（まず read-your-writes だけ、で十分なことが多い）

⑦ トレードオフ

  • 依存メタデータのサイズが増える（Vector Clock は O(ノード数)）
  • 不変条件（在庫・一意性）は守れない — 因果だけでは「同時に最後の1個を売る」を防げない
  • 「因果」の定義がシステム境界に依存する（DB外の会話は追跡できない: 電話で伝えた情報は因果として見えない）
  • sticky session は障害時に崩れる → 完全性はバージョン方式が必要

⑧ 実務での利用例

  • Azure Cosmos DB（事実）: 5段階の整合性レベル（Strong / Bounded staleness / Session / Consistent prefix / Eventual）を SLA 付きで商品化している。整合性モデルの教科書がそのまま製品仕様になっている稀な例で、面接で引用しやすい

  • Twitter/X（解釈）: 会話スレッドは因果が壊れると意味不明になるため、返信は親ツイートIDと共に扱われ、クライアント側でも順序を組み立てる
  • Instagram（事実 + 解釈）: コメント投稿の楽観更新は、実質的にクライアント側 read-your-writes。サーバ側整合性を上げるより安い解決策

⑨ Googleレベルの設計

  • 「保証を名前付きAPIにする」: Spanner の read at timestamp / bounded staleness(10s) のように、弱い読みを「明示的に選ぶ機能」として提供する。暗黙に弱くしない
  • 因果を切らない配線: 同一エンティティグループ内は順序保証、グループ間は明示的トランザクション。「うっかり因果が壊れる」構造をアーキテクチャで防ぐ
  • クライアントライブラリに埋め込む: セッショントークンの持ち回りをアプリ開発者に手作業でやらせない。SDK が自動で行う（Cosmos DB のセッショントークンがまさにこれ）

⑩ 面接での問われ方

  • 頻出:「結果整合だと困る具体例と、その最小の解決策は？」 → 4保証のどれが欠けているかを特定して、その1つだけを足す。「Strong にします」と答えるのは設計力が低いと判断される

09 CAP定理 — 正確な主張と、世に溢れる誤解の解体

結論: CAP定理の正しい主張は「ネットワーク分断が起きている間、線形化可能性（C）と全ノードが応答すること（A）は両立しない」だけです。「3つから2つ選べ」ではありません。P は選択肢ではなく前提条件（ネットワークは必ず切れる）。面接で「CAP は2つ選ぶ定理」と言うと即座に減点されます。

🛣 例え: 東京支店と大阪支店を結ぶ道路が通行止めになった。大阪支店に客が来て「残高を教えて」と言う。選択肢は2つしかない。
① 「道路が復旧するまでお答えできません」と断る（＝C を守り A を捨てる / CP）
② 「大阪の帳簿ではこうです」と、東京の最新情報を知らずに答える（＝A を守り C を捨てる / AP）
「正しくて、かつ即答する」は物理的に不可能。これが CAP の全て。

① 何を解決するために生まれたのか

  • 「なんでもできる分散DB」という幻想を殺す — 2000年に Eric Brewer が提示、2002年に Gilbert & Lynch が形式的に証明。当時「分散すれば全部良くなる」という空気を数学で止めた
  • 設計時に「何を諦めるか」を先に決めさせる — 分断は必ず起きるので、その時の挙動を設計時に選ばないと、障害時に「なんとなく壊れる」
  • ベンダーの主張を検証する道具になる — 「分断中も強整合で常に可用」と謳う製品があれば、定義を確認すれば嘘か定義のすり替えが分かる

③ 基本概念 — 3つの語の厳密な定義（ここを外すと全部間違える）

Availability故障していない全ノードが、有限時間で必ず応答を返す（エラーではなく正常なレスポンス）「99.99% 稼働」のような運用上の可用性だと思っている（CAP の A はもっと厳しい全か無か）
Partition tolerance任意のメッセージが無限に遅延・喪失しても、システムが動作し続けること「選べるオプション」だと思っている。現実には選べない前提

重要: CAP の A は非常に厳しい定義なので、実務の「可用性 99.99%」とは別物です。「CP システムでも実務的な可用性は極めて高くできる」（例: etcd は過半数が生きていれば動く）。この区別ができると議論が一段深くなります。

  • Google の答えは「分断を起こさないネットワークに投資する」（事実 + 解釈）: Spanner の論文と関連発表では、自社の専用WAN（B4 等）と冗長化により分断が極めて稀であることが強調される。CAP の制約は変えられないが、P の発生確率は工学で下げられる
  • 機能単位で degrade する設計: 分断中に「読みは提供、書きは拒否」「一部機能のみ提供」といった部分稼働（graceful degradation）を設計する。全か無かで考えないのがプロの設計

10 PACELC — 平常時にも取引をしている（CAPの続き）

結論: PACELC は「分断時（PA/PC）だけでなく、平常時（EL/EC）にもレイテンシと整合性のどちらを優先しているか」を明示する枠組み。CAP は分断時のことしか語らないので、実務の 99.9% の時間について何も言っていません。面接で PACELC を出すと、CAP を暗記しただけの候補者と差が付きます。

🍽 例え: レストランで「本部に電話して価格を確認してから注文を受ける」ポリシー。電話回線が切れたとき（P）に注文を断る（C）か、店の記憶で受ける（A）か — これが CAP。しかし電話が繋がっている平常時（E）も、毎回電話するなら注文が遅くなる（C を選んでいる）し、電話せずに店の記憶で受けるなら速い（L を選んでいる）。平常時にも同じ取引をしているのが PACELC の指摘。

Fig 10-1: PACELC の4象限。CAP は左半分だけを語っている。設計上重要なのは右半分（平常時）。

④ 内部で何が起きているか — tail latency amplification

強整合（EC）を選ぶと、レイテンシは「必要ノードのうち最も遅いノード」に律速されます。ノードを増やすと p99 が悪化する現象を tail latency amplification と呼びます。

Fig 10-2: quorum は「遅い少数を無視する仕組み」でもある。全同期複製（全台待ち）を選ぶと p99 が破壊される。

⑥ PACELC を使うメリット

  • 平常時のコストを議論に乗せられる（CAPだけでは抜ける）
  • 「設定次第で変わる」ことを表現できる（w:1 と w:majority）
  • 製品選定の比較軸として使える

⑦ 限界

  • 実際には「操作ごと」「キーごと」に選べるので、システム単位のラベルは粗い
  • gray failure（部分的な遅延）を表現できない
  • ラベルが同じでも実装の質（フェイルオーバー時間・データ喪失窓）は全く違う

⑧ 実務での利用例

  • Netflix（事実 + 解釈）: 全世界の複数リージョンで active-active、EL 側（低レイテンシ優先）。「再生開始が速いこと」がビジネス価値なので合理的
  • Booking.com / Airbnb（解釈）: 検索は EL（キャッシュとレプリカから即応答）、予約確定は EC（1リージョンの強整合）。同一サービス内で象限を分けるのが実務の標準解
  • Uber（事実 + 解釈）: 配車マッチングは低レイテンシ必須（EL）、決済と請求は正しさ必須（EC）。ドメインごとにストアを分ける
  • YouTube / Vitess（事実）: MySQL の semi-sync 複製で「1台の ack を待つ」= EC 寄りだが全台は待たない。現実的な中間点

⑩ 面接での問われ方

  • Q:「CAP 以外に整合性を語る枠組みは？」 → PACELC。「CAP は分断中の話しかしていないが、システムの 99.9% の時間は平常時。平常時にもレイテンシと整合性の取引がある」
  • Q:「強整合にするとどれくらい遅くなりますか？」 → 「同一リージョン内なら +1〜3ms 程度、リージョン間なら +70〜150ms。加えて quorum を待つので p99 は最も遅いレプリカに引かれます」— 数字で答える
  • 加点: 「レイテンシを守りつつ整合性を上げる手段として、リーダーをユーザーに地理的に近い場所へ置く（leader placement / follower read）があります」

11 物理時計はなぜ信用できないか — 「時刻」で順序を決める罠

結論: 分散システムで「タイムスタンプが大きい方が新しい」と仮定すると、いつか必ずデータを失います。物理時計はズレる・巻き戻る・跳ぶ。それでも時刻を使いたいなら、誤差の上限を明示的に扱う（TrueTime）か、論理時計に置き換える（Lamport / Vector）しかありません。

📮 例え: 各支店の壁時計で書類に時刻を書き込み、「時刻が新しい方を採用」というルールで運用する。ところが大阪支店の時計が3分進んでいた。東京で後から書いた正しい書類が「古い」と判定されて破棄される。しかも誰も気付かない（エラーが出ない）。これが LWW + 物理時計の事故そのもの。

① 何を解決したいのか / ② これを知らないと何が起きるか

  • 順序を決めたい — 「どちらの更新が後か」を判定して競合を解決したい。最も安直な手段が物理時刻
  • 知らないと起きること1: LWW で新しい書き込みが黙って捨てられる（エラーも警告も出ない）
  • 知らないと起きること2: time.Now() の差分でタイムアウトを測ると、NTP の時刻補正で負の経過時間や巨大な値が出て、リース判定が壊れる
  • 知らないと起きること3: ログの時刻順ソートで因果が逆転し、障害調査が迷路になる

12 Logical Clock / Lamport Clock — 時計を捨てて因果を数える

結論: Lamport Clock は「メッセージを受け取ったら自分のカウンタを相手より大きくする」だけの単純な仕組みで、因果関係を壊さない全順序を作れます。ただし「順序が付く」だけで「本当に因果があるか」は判別できません（逆は不成立）。この非対称性が Vector Clock（13章）を生みました。

📮 例え: 手紙のやり取りで、便箋の隅に「通し番号」を書くルールにする。相手の手紙に書かれた番号より必ず大きい番号を自分の次の手紙に書く。すると「返信の番号 > 本文の番号」が必ず成立するので、番号順に並べれば会話が崩れない。ただし、番号が大きいからといって「相手の手紙を読んだ結果」とは限らない（無関係に大きい番号を使っていただけかもしれない）。

① 何を解決するために生まれたのか

  • 物理時計なしで順序を決める — Lamport の1978年の論文「Time, Clocks, and the Ordering of Events in a Distributed System」（分散システム分野で最も引用される論文の1つ）
  • happens-before 関係を形式化する — 「a が b の原因になり得るか」を定義する
  • 全順序が必要な場面で使う — 分散ミューテックス、トランザクションIDの採番、状態機械の入力順序決定

③ 基本概念 — happens-before（→）とアルゴリズム3行

happens-before の定義

① 同じプロセス内で a が b より先に起きた → a → b
② a がメッセージ送信、b がその受信 → a → b
③ 推移律: a→b かつ b→c なら a→c
どちらでもない場合、a と b は concurrent（並行）と呼ぶ（a ∥ b）

Lamport Clock のアルゴリズム

1. 各プロセスは整数カウンタ C を持つ
2. イベント発生時（ローカル処理・送信）: C = C + 1
3. メッセージ受信時: C = max(C, 受信した C) + 1
これだけ。送信するメッセージに現在の C を添付する

保証する性質: a → b ならば C(a) < C(b)（因果があれば番号は必ず増える）。
保証しない性質: C(a) < C(b) ならば a → b は成り立たない。番号が小さいからといって原因とは限らない。

Fig 12-1: Lamport Clock の動作と限界。全順序は作れるが、並行かどうかは分からない。

⑥ メリット

  • 実装が数行。メタデータは整数1個だけ（Vector Clock より圧倒的に軽い）
  • 物理時計に一切依存しない
  • タイブレークを加えれば決定的な全順序が作れる → 状態機械複製に使える

⑦ トレードオフ

  • 並行（concurrent）を検出できない → 競合の自動解決に使えない
  • 「全順序」は作れるが、その順序は実時間と一致しない（後で起きた操作が小さい番号を持てる）
  • 因果を追跡するにはメッセージに必ずクロックを載せる必要があり、システム外の経路（電話・別API）は追跡できない

⑤⑧ システム構成と実務例

  • Cassandra の write timestamp（事実 + 解釈）: 既定は物理時刻だが、思想的には「単調なスタンプで LWW を判定する」構造。HLC（14章）を使う設計が現代的な改良版
  • Kafka の offset（解釈）: パーティション内の単調増加整数は、Lamport clock の特殊形（1つのプロセスが採番）と見なせる
  • MongoDB の causal consistency（事実）: clusterTime（HLC ベース）をクライアントが持ち回り、因果順序を保証するセッションを提供している。論理時計が製品APIとして露出している好例
  • Raft の (term, index)（解釈）: リーダーだけが採番する論理時刻。全順序が単一ノードで決まるので Lamport よりさらに単純

⑨⑩ Googleレベル / 面接での問われ方

  • Google レベルの視点: Lamport clock 単体はほぼ使われず、物理時刻と論理時刻を合成した HLC や、誤差付きの物理時刻（TrueTime）に発展している（14章）。理由は「人間が読める時刻」も同時に必要だから（デバッグ・保持期限・監査）
  • Q:「因果順序を保証する最小の仕組みは？」 → Lamport clock。「ただし並行検出はできないので、競合解決が必要なら Vector Clock」まで言えるとセット
  • Q:「Lamport clock で LWW をやると何が良くなる？」 → 「物理時計のドリフトの影響を受けない。ただし『どちらが後か』は因果がない場合には任意の決定になるので、失われる書き込みは依然として発生する」

13 Vector Clock — 「並行更新」を検出できる唯一の道具

結論: Vector Clock は各ノードのカウンタを配列で持つことで、「因果あり」と「並行」を厳密に区別できます。これにより「片方が明らかに新しい → 上書き」「両方が並行 → 競合として両方残す」という正しい競合解決が可能になります。代金はメタデータサイズ O(ノード数)。

📦 例え: 倉庫の在庫票に「東京版:3、大阪版:1、福岡版:0」と全拠点の改訂回数を書く。別の票が「東京版:3、大阪版:2、福岡版:0」なら、すべての数字が同じか大きいので後者が新しい（＝上書きOK）。しかし「東京版:4、大阪版:1」と「東京版:3、大阪版:2」ならどちらも相手より進んだ部分があるので、順序が付かない（＝両方が別々に更新された = 競合）。

①② 何を解決するか / これがないと何が起きるか

  • 解決すること: Lamport Clock の「並行を検出できない」欠点を埋める。競合を検出できれば、勝者を機械的に決めずアプリの業務ロジックに委ねられる
  • ないと起きること: LWW しか選択肢がなくなる → 04章の「黙って消える書き込み」が発生する。カートから商品が消える、共同編集で他人の編集が飛ぶ

④ 内部実装（Go）と Version Vector との違い

⑥ メリット

  • 並行更新を確実に検出できる → 書き込みを失わない設計が可能
  • 物理時計に依存しない
  • 因果順序を保った可視化（Causal Consistency の実装基盤）

⑦ トレードオフ

  • サイズが O(ノード数) — ノードが増減するたびにベクタが膨らむ。クライアントをエントリに含めると爆発する
  • 刈り込み（pruning）が必要 → 古いエントリを削ると偽の「因果あり」判定が起きうる
  • 並行を検出しても解決はアプリの仕事。実装忘れが本番事故になる
  • sibling が増殖するとオブジェクトが巨大化し、読み取り自体が失敗しうる（Riak 運用の既知の落とし穴）

⑧ 実務での利用例

  • Amazon Dynamo（事実）: 2007年の論文でカート用途に vector clock + siblings を採用。ただし現在の DynamoDB（マネージドサービス）は別設計で、条件付き書き込みや強整合読みを提供する。論文と製品を混同しないこと
  • Riak（事実）: siblings をアプリに返す設計。後に dotted version vector で sibling 爆発を緩和
  • CRDT ライブラリ（事実）: Automerge / Yjs（共同編集）は内部で因果履歴を管理し、並行編集をマージする。Figma や Google Docs 的な体験の理論的基盤
  • Cassandra（事実 + 解釈）: vector clock を採用していない（LWW を選択）。理由は運用の単純さと性能。「正しさ」より「シンプルさ」を選んだ設計判断として面接で語れる

⑨⑩ Googleレベル / 面接での問われ方

  • Googleレベルの視点: 大規模では vector clock のサイズが運用上の負債になるため、「そもそも競合が起きない設計」（キーごとに単一のリーダーを置く、パーティションで分ける）に寄せるのが基本。競合解決は最後の手段
  • Q:「Lamport Clock と Vector Clock の違いは？」 → 「Lamport は全順序を作れるが並行を検出できない。Vector は並行を検出できるがサイズが O(N)」
  • Q:「並行更新を検出したらどうしますか？」 → 「データの意味で決めます。カートなら和集合、カウンタなら加算（CRDT）、プロフィールならユーザーに選ばせる、決済ならそもそも並行更新が起きない設計にする」

14 Hybrid Logical Clock と TrueTime — 物理と論理を合成する

結論: HLC は「人間が読める物理時刻」と「因果を壊さない論理カウンタ」を1つの値に合成した現代的な標準解。TrueTime は Google が「時刻の誤差そのものをAPIで返す」ことで、地球規模の強整合を実現した特殊解です。両者は「時計の不確かさをどう扱うか」の2つの答え。

🏦 例え: 銀行の書類に「2026-08-18 10:00:00（誤差±3ms）」と誤差付きで記録する。2つの書類の誤差範囲が重なっていたら「どちらが先か断定できない」と正直に認める。断定したいときは、誤差の分だけ待ってから次の処理をする（＝commit wait）。TrueTime はこれをシステム全体でやっている。

Fig 14-1: HLC の構造と3つの時計の比較。実務で新規に設計するなら HLC が既定の選択。

④ TrueTime の内部 — 「誤差を返すAPI」という発明

Google の TrueTime は TT.now() が時刻ではなく区間 [earliest, latest] を返します。真の時刻はこの区間内にあることが保証されます（GPS受信機と原子時計をデータセンターに配備し、誤差を有界化）。公開論文では不確かさ ε は概ね数ms（1〜7ms程度、通常は約1ms〜4ms程度に収まると報告されている）。

Fig 14-2: TrueTime と commit wait。「書き込みで数ms 待つ代わりに、読みを世界中で安くする」という取引。

⑥ メリット

  • HLC: 因果保証と実時刻の可読性を両立、サイズ定数
  • TrueTime: 地球規模で strict serializability、読みが安い
  • どちらも「時計のズレ」を設計内に明示的に取り込んでいる

⑦ トレードオフ

  • HLC: 並行検出不可、外部整合性なし、スキュー前提が破れると危険
  • TrueTime: 専用ハードウェア（GPS / 原子時計）が必要 → 自前では再現困難
  • commit wait は全書き込みに固定コストを課す
  • 「最大スキューの仮定」は仮定なので、破れたときの挙動を決めておく必要がある（停止するのが安全）

⑧⑨ 実務例と Googleレベルの設計

  • Google Spanner（事実）: TrueTime + Paxos + 2PC で external consistency。25章で全体構成を扱う
  • CockroachDB（事実）: HLC + 最大クロックオフセット（既定 500ms）。オフセット超過を検知したノードは自ら死ぬ（安全側に倒す設計）
  • MongoDB（事実）: clusterTime（HLC）でセッション単位の causal consistency を提供
  • AWS（事実）: Amazon Time Sync Service を提供し、高精度な時刻同期を一般ユーザーにも解放。「TrueTime 的な基盤」がクラウドの標準機能になりつつある
  • Googleレベルの視点: 「時計の精度」をインフラの投資対象として扱う。ε を半分にすれば commit wait が半分になる → 物理層への投資がソフトウェアの性能に直結するという思想は、面接で語ると強い視点

⑩ 面接での問われ方

  • Q:「Spanner はなぜ地球規模で強整合できるのですか？」 → 「TrueTime で時計の誤差に上限を与え、commit wait でその誤差分待つことで、タイムスタンプの順序が実時間の順序と一致することを保証しているからです」
  • Q:「TrueTime が無い環境で似たことをするには？」 → HLC + 最大スキュー仮定（CockroachDB）または中央 TSO（TiDB）。それぞれの弱点（スキュー破れ / TSO が単一障害点かつ地理的ボトルネック）まで言えると強い
  • Q:「HLC は何を保証しないのですか？」 → 「並行の検出と外部整合性。因果が追跡できるのはシステム内で観測できた経路だけです」

15 Consensus とは何か — 「1本のログの順序を全員で決める」

結論: Consensus（合意）とは「複数ノードが1つの値（正確には値の列＝ログ）について、一度決めたら覆らない合意に達すること」。分散システムのほぼ全ての難問（リーダー選出・分散ロック・一意採番・アトミックコミット）は、合意問題に還元できます。逆に言えば、合意を1つ持っていれば全部解ける。

🍽 例え: 3人の料理人が別々の厨房にいて、同じレシピ帳に同じ順序で手順を書き込みたい。電話は繋がったり切れたりする。ルール: 過半数（2人）が「この手順を n 番目に書く」と同意したら確定。一度確定した行は誰も書き換えられない。全員が同じ順序でレシピ帳を読めば、同じ料理が出来上がる。これが Replicated State Machine。

① 何を解決するために生まれたのか

  • 「誰が正しいか」を機械的に決める — 人間の介入なしに、故障を含む環境で一意な決定を作る
  • 状態機械を複製する — 同じ初期状態 + 同じ入力列 → 同じ最終状態。これが分散システムでフォールトトレランスを得る唯一の一般解
  • 個別の難問をまとめて解く — リーダー選出・ロック・membership・アトミックコミットが全部同じ道具で解ける

③ 基本概念 — 合意が満たすべき4性質と、還元される問題群

合意の4性質

Uniform Agreement: 2つのノードが異なる値を決定しない
Integrity: 決定は1回だけ（覆らない）
Validity: 決定された値は、誰かが提案した値である
Termination: 故障していないノードは最終的に決定に至る
※ 最初の3つが safety（安全性）、最後が liveness（活性）

合意と等価な問題（互いに変換できる）

・Total Order Broadcast（全ノードが同じ順序でメッセージを受け取る）
・Linearizable な CAS レジスタ
・Leader Election（一意なリーダーを選ぶ）
・Atomic Commit（全員が commit か全員 abort）
・Distributed Lock（一意な保持者）
→ どれか1つ解ければ全部解ける。だから etcd が1つあれば足りる

Fig 15-1: Replicated State Machine。合意が確定させるのは「ログの n 番目に何を置くか」だけ。それだけで全部が解ける。

④ 内部の限界 — FLP不可能性（なぜ「完璧な合意」は存在しないか）

FLP 定理（Fischer, Lynch, Paterson 1985）: 完全非同期のシステム（メッセージ遅延に上限がない）で、1台でもクラッシュしうるなら、常に終了する決定的な合意アルゴリズムは存在しない。

データは壊れていないのがポイント 障害モデルの階層（面接で「どの故障を想定するか」を聞かれる） Crash-stop / Crash-recovery 落ちるだけ / 復帰する。Raft/Paxos の想定 Omission（メッセージ欠落） 送ったのに届かない。再送で対処 Byzantine（嘘をつく） 3f+1 台必要。PBFT / ブロックチェーン Gray failure（遅い・片方向） 最も厄介。検知が難しく、実務事故の主因

Fig 15-2: FLP と回避策、障害モデルの階層。「safety は無条件、liveness は条件付き」が実務で覚えるべき1行。

⑥ メリット

  • ノードが落ちても（過半数生存なら）データを失わず継続できる
  • 「一意な決定」が得られるので、上位の設計が単純になる
  • 実装は既製品（etcd / ZooKeeper / Consul）を使えばよい

⑦ トレードオフ

  • すべての書き込みに 1 RTT + fsync のコスト
  • ノードを増やしても書き込みは速くならない（むしろ遅くなる）
  • 過半数を失うと書き込み不能（可用性を捨てている）
  • 自前実装は極めて危険（境界条件が多く、微妙なバグが数年後にデータ喪失を起こす）

⑨ Googleレベルの設計 — 合意は「小さく、少なく」使う

  • 合意はメタデータにだけ使う（事実）: Chubby / Spanner の設計思想は「合意が必要なのは『誰がリーダーか』『どこにデータがあるか』といった小さな真実だけ」。大量のユーザーデータを1つの合意グループに通さない
  • グループを大量に作る（事実）: Spanner はデータを split に分割し、split ごとに独立した Paxos グループを持つ。合意を水平スケールする唯一の方法は「独立した合意グループを増やす」
  • Chubby の教訓（事実 + 解釈）: Google は「開発者が Chubby をロックサービスではなく設定ストアや名前解決に使い始め、負荷が想定外に増えた」経験を公表している。合意サービスは便利すぎて濫用されるという運用上の警告

⑩ 面接での問われ方

  • Q:「Consensus とは？」 → 「複数ノードが1つの値、実際にはログの順序について、覆らない合意に達すること。安全性は常に守り、活性は通信が安定すれば保証される」
  • Q:「FLP 不可能性は実務にどう影響しますか？」 → 「安全性と活性の両方を無条件に保証できないので、実システムは活性を諦める（＝タイムアウトと再選挙で待つ）方を選んでいます。だから『etcd が選挙を繰り返して書き込めない』は起きるが、『データが分岐する』は起きない」
  • Q:「合意を使わずに済ませられますか？」 → 「単一シャードに閉じ込める、パーティションで競合を避ける、CRDT で可換にする。合意は本当に一意性が必要な最小の範囲に限定します」

16 Quorum — 過半数という発明と、その限界

結論: Quorum の本質は「必ず重なる集合を使うことで、常に最新を含む集合に触れられる」こと。ただし W+R>N は線形化可能性を保証しません。これは面接で最も多い誤解であり、ここを説明できると一気に評価が上がります。

🏦 例え: 5人の取締役会。決議には3人の署名が必要。3人の集合はどんな2つを取っても必ず1人は共通するので、「同時に矛盾する2つの決議が成立する」ことはない。これが過半数（majority quorum）の数学的な意味。

①② 何を解決するか / これがないと何が起きるか

  • 「全員の同意」を要求すると1台の故障で止まる — Quorum は「一部の故障・遅延を無視して進む」ための仕組み
  • 「1台だけの同意」だと分裂する — 2つの独立した書き込みが両方成功し、どちらが正しいか決まらない
  • Quorum があると: N台中 f 台の故障を許容しながら、矛盾する決定を防げる（majority なら f < N/2）

Fig 16-1: Quorum の数学と、W+R>N が線形化可能でない反例。B は N2（まだ古い）と N3 を読んだため古い値を返した。

④ どうすれば線形化可能になるのか — ABD アルゴリズムと現実解

  • 読み修復を「読みの完了前に」行う（read repair before return） — 読んだ最新値を quorum に書き戻してから返す。これで後続の読みが古い値を返せなくなる（ABD アルゴリズムの考え方）。代金: 読みが書き込みと同じコストになる
  • 合意プロトコルを使う — Raft/Paxos で全操作を1本のログに直列化する（＝etcd の方式）
  • CAS を使う — Cassandra の LWT（Paxos ベース）、DynamoDB の条件付き書き込み。quorum ストアでも「特定の操作だけ線形化可能にする」ことは可能
Quorum の種類定義用途 / 注意
Majority quorum⌊N/2⌋+1合意プロトコルの標準。安全
Sloppy quorum本来の担当ノード以外でも W 台に書けば成功とする可用性は上がるが、W+R>N の重なり保証が壊れる（04章 hinted handoff）
Flexible PaxosQ1（選挙）と Q2（複製）の交差だけ要求。例: Q1=4, Q2=2 (N=5)複製 quorum を小さくして書き込みを速くできる。選挙が重くなる
Witness / Tiebreakerデータを持たず投票だけする軽量ノード3拠点目に小さなノードを置いて偶数構成の分裂を防ぐ（Azure / MongoDB arbiter 等）
Grid / Tree quorumノードを格子や木に並べて交差集合を作る理論的な最適化。実務ではほぼ見ない

⑥ メリット

  • 一部の故障・遅延を無視して進める（tail latency を切れる）
  • 矛盾する2つの決定が同時に成立しないことを数学的に保証
  • W と R の配分で読み重視・書き重視を調整できる

⑦ トレードオフ

  • W+R>N だけでは線形化可能にならない（上の反例）
  • N を増やすと書き込みの必要 ack 数が増え、スループットが落ちる
  • 偶数台は無駄。2台構成は最悪（耐障害性 0 なのに複雑さだけ増える）
  • sloppy quorum を有効にすると保証がさらに弱まる

⑧ 実務での利用例

  • AWS Aurora（事実）: ストレージは6コピー（3AZ×2）で、書き込みは 4/6、読みは 3/6 の quorum。「AZ 1つ + 追加1台の故障」に耐える設計。2PC を使わずに quorum で耐久性を作った代表例
  • Cassandra（事実）: 整合性レベルを per-query で選べる（ONE / QUORUM / LOCAL_QUORUM / ALL）。マルチリージョンでは LOCAL_QUORUM がほぼ標準（リージョン間 RTT を払わない）
  • DynamoDB（事実）: 書き込みは複数AZに複製し、強整合読みではリーダーレプリカを参照する構成が公表されている。条件付き書き込みで不変条件を守れる
  • etcd / ZooKeeper（事実）: majority quorum が必須。3台なら1台、5台なら2台の故障に耐える。2台構成は禁止（1台落ちで全停止）
  • MongoDB（事実）: w:majority でなければフェイルオーバー時に ack 済み書き込みを失う（rollback される）

⑨ Googleレベルの設計

  • quorum を地理的に配置する（事実）: Spanner は Paxos グループのレプリカを「どのリージョンに置くか」を設定可能にし、書き込みレイテンシを quorum の地理配置で制御する。3リージョンなら、近い2つで quorum が成立するよう配置するのが定石
  • witness レプリカでコストを削る: データを持たない投票専用レプリカを遠隔地に置き、ストレージコストを払わずに耐障害性を得る
  • quorum を跨がせない: 1つの操作が複数の quorum グループを跨ぐと 2PC が必要になり遅くなる。スキーマ設計の段階で「同時に更新するデータを同じグループに置く」（Spanner の interleaved table がまさにこれ）

⑩ 面接での問われ方

  • 最重要:「W+R>N なら強整合ですか？」 → 「いいえ」。Fig 16-1 の反例を説明する。「最新の値を含む集合に触れることは保証されるが、返す値が最新であることは保証されない。読み時に quorum へ書き戻す（ABD）か、合意プロトコルを使う必要がある」
  • Q:「なぜ奇数台なのですか？」 → 「4台は3台と同じ1台耐性しかないのに quorum が3に増えるため。偶数は分断時に同数分裂の危険もある」
  • Q:「マルチリージョンで quorum をどう組みますか？」 → 「3リージョンに 2/2/1 のように配置し、近い2リージョンで quorum が成立するようにする。または LOCAL_QUORUM でリージョン内に閉じる」

17 Leader Election — 1人だけを選ぶ、という難問

結論: リーダーを置く理由は「順序を1点で決めれば整合性が自明になる」から。しかし「1人だけ」を保証するのは合意なしには不可能で、失敗すると 24章の split brain になります。実務では「選出は合意サービスに任せ、行動は fencing で守る」が唯一の正解です。

🍽 例え: 厨房のチーフを1人決める。チーフだけが伝票の順番を決める（＝直列化点）。チーフが倒れたら誰かが引き継ぐ必要があるが、「倒れたと思ったら実は休憩していただけ」だと2人のチーフが同時に指示を出す。だから「チーフの証」に連番を付けて、古い証を持つ人の指示は厨房全員が無視する（＝fencing token）。

① 何を解決するために生まれたのか

  • 順序決定を単純にする — 全書き込みが1点を通れば、順序は「到着順」で自明に決まる。合意プロトコルもリーダーがいる方が圧倒的に速い（Multi-Paxos / Raft）
  • 重複実行を避ける — cron / バッチ / コンシューマを「1インスタンスだけ」動かしたい
  • 調整役を1つにする — シャード割り当て、リバランス、2PCコーディネータ

② これがないと何が問題になるか

  • 全ノードが好き勝手に書く → 順序が決まらず、レプリカが分岐する
  • バッチが二重実行 → 請求書が2通、メールが2通、在庫が2回減る
  • 逆に選出が失敗すると → リーダー不在で全停止（liveness の喪失）。選出が過剰に起きると「選挙の嵐」でスループットが0になる

Fig 17-1: 選出の3方式と Lease ベースのシーケンス。「奪取された側が気付かない」ことが本質的な問題。

  • 順序決定が1点に集まり、整合性の推論が簡単になる
  • 合意プロトコルが速くなる（リーダーがいれば 1 RTT で commit）
  • バッチ・cron の重複実行を防げる

⑦ トレードオフ

  • リーダーがスループットの上限になる（→ シャーディングが必要）
  • フェイルオーバー中は書き込みが止まる（数百ms〜数十秒）
  • 誤検知による不要な切り替え（flapping）が性能を壊す
  • 「1人だけ」は fencing なしには保証できない

⑧ 実務での利用例

  • Kubernetes（事実）: kube-controller-manager / kube-scheduler は coordination.k8s.io/Lease で選出。既定 leaseDuration 15s / renewDeadline 10s / retryPeriod 2s
  • Google Bigtable + Chubby（事実）: タブレットサーバの生存とマスターの一意性を Chubby のロックで管理。「合意サービスに一意性を委譲する」設計の原型
  • Vitess / YouTube（事実）: トポロジ情報を etcd / ZooKeeper / Consul に保持し、シャードごとのプライマリを管理。MySQL 自体は合意しないので、外部の合意サービスに「誰がプライマリか」を持たせる
  • GitHub（事実）: Orchestrator による MySQL 自動フェイルオーバーを運用。2018年の障害では、43秒のネットワーク分断が引き金となって東海岸へフェイルオーバーし、書き込みが分岐して長時間の復旧作業になった（31章で詳述）
  • Uber Ringpop（事実）: SWIM gossip で membership を管理し、consistent hashing で担当を決める。合意ではないので「一意性が必要な仕事」には使わない設計判断

⑨ Googleレベルの設計

  • 選出は外部化、行動は検証: 「誰がリーダーか」は Chubby / etcd に委譲し、リーダーの行動は必ず世代番号（epoch / term / sequencer）付きで行い、受け側が検証する。Chubby の sequencer はまさにこの目的の API
  • リーダーを地理的に最適配置: Spanner は書き込みが多いリージョンにリーダーを寄せる（leader placement）。リーダーの位置が書き込みレイテンシを直接決めるため
  • フェイルオーバーを日常的にテストする: リーダーを意図的に落とす訓練（DiRT / chaos engineering）を運用に組み込む。フェイルオーバー経路は普段動かないので、本番で初めて動くと必ず失敗する

⑩ 面接での問われ方

  • Q:「cron を1インスタンスだけ動かしたい。どう実装しますか？」 → 「etcd/ZooKeeper の lease + CAS で選出し、実行中も lease の生存を監視して失効時は即中断。さらに副作用の宛先で冪等キーか fencing token を検証します」— 最後の一言が有無で評価が変わる
  • Q:「リーダーが死んだ判定はどうしますか？」 → 「ハートビート + タイムアウト。タイムアウトを短くすると誤検知（不要な切り替え）が増え、長くすると停止時間が伸びるトレードオフです。23章の phi accrual のような適応的検知も選択肢」
  • Q:「2人のリーダーが同時に存在することはありますか？」 → 「あります。GC・VM停止・ネットワーク遅延で古いリーダーが自分の失効に気付かない場合。だから一意性は選出ではなく fencing で守ります」

18 Raft 完全解剖 — 面接で口頭説明できるようになる

結論: Raft は「強いリーダー + 任期（term）+ ログの一致検査」の3点で合意を実現します。Paxos と同じ問題を解きますが、理解しやすさ（understandability）を明示的な設計目標にしたため、現代の実装（etcd / Consul / TiKV / CockroachDB / Kafka KRaft）はほぼ Raft 系です。この章は本書で最も重要な章です。

🍽 例え: 厨房のチーフ（Leader）が伝票（Log）に番号を振り、副料理長（Follower）全員に「これを n 番に書け」と伝える。過半数が書き終えたら「確定（commit）」と宣言し、実際に調理する。チーフが倒れたら、「一番進んだ伝票を持っている人」だけが次のチーフになれる（＝確定済みの料理を失わないため）。新チーフには新しい任期番号が付き、古いチーフの指示は全員が無視する。

① 何を解決するために生まれたのか

  • Paxos が理解しにくすぎた（事実）: Raft 論文（Ongaro & Ousterhout, 2014）の冒頭は「Paxos は理解が難しく、実装も難しい」という問題意識から始まる。「理解しやすさ」を第一級の設計目標にした最初の合意アルゴリズム
  • 実装の正しさを検証可能にする — 状態遷移とルールが明示されているため、テスト・形式検証・障害注入がしやすい
  • 実用機能を最初から含める — メンバ変更、ログ圧縮（スナップショット）、クライアント対話まで論文が扱う

③ 基本概念 — 3つの役割、term、3つの RPC

3つの役割

Leader: 唯一クライアント要求を受け、ログを複製する
Follower: 受動的。リーダーの AppendEntries に応答するだけ
Candidate: 選挙中の一時状態

term（任期）＝ 論理時刻

選挙ごとに +1 される単調増加の整数。term が fencing token として機能する: より小さい term のメッセージは全て拒否され、より大きい term を見たノードは即座に Follower に降格する

3つの RPC

RequestVote: 選挙で票を集める
AppendEntries: ログ複製 + ハートビート（entries が空ならハートビート）
InstallSnapshot: 遅れすぎた Follower にスナップショットを送る

永続化が必須の3状態

currentTerm / votedFor / log[] は応答を返す前にディスクへ fsync。ここを手抜きすると、再起動後に二重投票してデータが壊れる

  • メンバ変更・スナップショットまで仕様に含まれている

⑦ トレードオフ

  • リーダー1台が書き込みのボトルネック（水平スケールはグループ分割のみ）
  • 全書き込みに fsync が必要 → ディスク性能が直接スループットになる
  • 選挙中（数百ms〜数秒）は書き込み不能
  • 「強いリーダー」ゆえに、地理分散ではリーダーから遠いクライアントが常に遅い
  • 設定（heartbeat / election timeout）を誤ると選挙の嵐になる

⑧ 実務での利用例

  • etcd（事実）: Kubernetes の全状態を保持。既定 heartbeat-interval 100ms / election-timeout 1000ms。ディスクが遅いと fsync が詰まってリーダーが失われるため SSD 必須
  • Consul（事実）: HashiCorp の hashicorp/raft を使用。サービスディスカバリと KV
  • TiKV / CockroachDB（事実）: データを range に分割し、range ごとに独立した Raft グループを持つ（Multi-Raft）。これが Raft を水平スケールさせる標準手法
  • Kafka KRaft（事実）: ZooKeeper 依存を廃止し、メタデータ管理を Raft ベースの内部プロトコルに置き換えた（KRaft）。「外部の合意サービスへの依存をやめる」という近年の潮流
  • MongoDB（事実）: レプリカセットの選出は Raft に強く影響を受けた設計（論文でも言及されている）

⑨ Googleレベルの設計 — Multi-Raft と配置の最適化

  • 1クラスタ1 Raft ではなく、数万の Raft グループを回す: Spanner（Paxos）も CockroachDB / TiKV（Raft）も、データを細かく分割して各シャードに独立した合意グループを持たせる。合意のスケール手法はこれしかない
  • ハートビートを集約する: グループ数が増えると heartbeat のメッセージ数が爆発するため、同一ノードペア間のメッセージをバッチ化する（TiKV / CockroachDB が実装している最適化）
  • リーダーを需要に合わせて動かす: アクセス元に近いリージョンへリーダーを移す（leaseholder rebalancing）。「どこで合意するか」がレイテンシを決める
  • fsync をバッチ化する: 複数の書き込みを1回の fsync でまとめる（group commit）。合意のスループット限界はほぼディスクの fsync 回数で決まる

⑩ 面接での問われ方（Raft は最頻出。以下を暗記ではなく理解で答える）

  • Q:「Raft を説明してください」（3分版） → 「ノードは Follower / Candidate / Leader の3状態。選挙タイムアウトで立候補し、term を +1 して過半数の票を集めたらリーダー。リーダーだけがクライアント要求を受け、ログに追記して全 Follower に複製する。過半数が持ったら commit し、状態機械に適用する。より大きい term を見たノードは即座に降格するので、古いリーダーの指示は無効化される」
  • Q:「なぜ commit 済みデータが失われないのですか？」 → 「commit 済みは過半数が持ち、当選にも過半数が必要で、2つの過半数は必ず交差する。交差したノードが古いログの候補者を拒否するため」
  • Q:「線形化可能な読みはどうしますか？」 → ReadIndex / lease read / follower read の3択とそれぞれの前提
  • Q:「Raft のノードを何台にしますか？」 → 「3台か5台。奇数。5台なら2台故障に耐えるが、書き込みは3台の ack が必要になる。7台以上は書き込みが遅くなるだけで実用性が低い」
  • Q:「書き込みスループットを上げるには？」 → 「1つの Raft グループでは上げられない。データを分割して Multi-Raft にする。加えて group commit / pipelining / バッチ化」

19 Paxos / Multi-Paxos — 元祖を、2フェーズの意味から理解する

結論: Paxos の本質は「① 過去に決まった値がないか調べる（prepare）→ ② なければ自分の値を、あればその値を提案する（accept）」の2フェーズ。この「過去を調べる」ステップが、複数の提案者が同時に動いても一度決まった値が覆らないことを保証します。Raft を理解した後に読むと、驚くほど単純に見えます。

🏦 例え: 取締役会で議案を通したい。ルールは2段階。
① 根回し（prepare）: 「私は議案番号5で提案したい。過半数の人に『番号5より小さい提案は今後受け付けない』と約束してもらう。同時に『すでに何か承認済みなら教えてくれ』と聞く」
② 提案（accept）: 「誰も何も承認していなければ自分の案を出す。誰かが承認済みなら、その案をそのまま自分の案として出す」
後半が肝。自分の案を捨てて他人の案を運ぶことで、一度決まった内容が絶対に変わらなくなる。

①② 何を解決したか / これがないと何が起きるか

  • Lamport が1989年（発表は1998年）に提示した、最初の実用的な非同期合意アルゴリズム（事実）。「非同期環境で安全性を絶対に壊さない合意」の原型
  • ないと起きること: 素朴な「過半数が accept したら決定」だけでは、提案が競合したときに2つの異なる値が別々に過半数を得ることが起きる。prepare フェーズがそれを防ぐ

Fig 19-1: Basic Paxos の2フェーズ。P1 が自分の案を捨てて "B" を運ぶ動きが、安全性の全て。

④ Multi-Paxos — 実用化のための最適化

  • 問題: Basic Paxos は「1つの値」を決めるだけ。ログのように連続した値を決めるには、毎回2フェーズ（2 RTT）かかる
  • 解決: リーダー（distinguished proposer）を1人選び、Phase 1 を「一括で先に済ませる」。以降はリーダーが Phase 2 だけを実行 → 1 RTT で確定できる
  • これは Raft とほぼ同じ構造: Raft の「選挙」= Paxos の Phase 1、Raft の「AppendEntries」= Paxos の Phase 2
  • 違い: Paxos は各ログ位置（instance）が独立しているため「穴（gap）」を許す（index 5 が未決定でも 6 を決められる）。Raft は連続性を強制する（穴を許さない）

Fig 19-2: Paxos ファミリーと Raft の比較。両者は同じ問題を解き、単純化の方向が違うだけ。

⑥ メリット

  • 安全性の証明が確立しており、40年近く破られていない
  • ログの穴を許すため、並列度を上げられる（高スループット設計が可能）
  • リーダーレス変種（EPaxos）で地理分散のレイテンシを改善できる

⑦ トレードオフ

  • 理解と実装が難しい（Raft が生まれた理由そのもの）
  • 論文が実装レベルの詳細を書いていないため、各社実装が独自になる
  • dueling proposers による活性の問題（リーダー化で回避が必須）

⑧⑨ 実務例と Googleレベルの設計

  • Google Chubby（事実）: Paxos ベースのロックサービス。「Paxos の論文と実際に動くシステムの間には大きな溝がある」という有名な報告（Paxos Made Live, 2007）を残した。ディスク破損、メンバ変更、スナップショット、テストなど、論文外の課題が山積みだったことを率直に記している
  • Google Spanner（事実）: split ごとに Paxos グループ。リーダーは10秒程度のリースを持ち、その間ローカルで読みに応える
  • Google Megastore（事実）: entity group ごとに Paxos。「Paxos を大量に並べる」設計の先駆けだが、書き込みレイテンシが高いことが知られていた（Spanner がそれを改善した）
  • AWS（事実）: DynamoDB のレプリケーショングループのリーダー選出に Paxos を用いていることが公表されている。また EBS のコントロールプレーン向けに Physalia という Paxos セルの大群を設計した論文がある。「小さな Paxos セルを大量に配置し、障害の影響範囲を狭める」という発想が面接で光る

⑩ 面接での問われ方

  • Q:「Paxos を説明してください」 → 「prepare で『過去に決まった値がないか』を過半数に問い合わせ、あればその値を、なければ自分の値を accept フェーズで提案します。この『他人の値を運ぶ』動作により、一度決まった値は覆りません」
  • Q:「なぜ2フェーズ必要なのですか？」 → 「1フェーズだと、2つの提案者が別々の過半数から accept を得て、異なる値が決まる可能性があるため。prepare が『過去の決定を発見して尊重する』役割を担っています」
  • Q:「Raft と Paxos、どちらを使いますか？」 → 「新規なら Raft（成熟した実装があり、チームが読める）。ただし極限のスループットや地理分散が要件なら Multi-Paxos 系の穴を許す設計や EPaxos の検討価値がある」

20 ZooKeeper と ZAB — 「合意をサービスとして売る」の原型

結論: ZooKeeper は「合意プロトコルを直接使わせず、znode + watch + ephemeral という3つの部品で提供する」ことで普及しました。ZAB（ZooKeeper Atomic Broadcast）は Paxos ではなく全順序ブロードキャストに特化したプロトコルです。読みが線形化可能でないという重要な特性を持ちます。

📚 例え: 図書館の「予約札システム」。札には連番が付き（sequential znode）、持ち主が帰ると自動的に外れる（ephemeral znode）。誰かが札を外したら次の人に通知が飛ぶ（watch）。この3つの部品だけで、ロック・リーダー選出・メンバ管理が全部作れる。

③ 基本概念 — 3つの部品と保証

znode の3種類

persistent: 明示的に削除するまで残る（設定値）
ephemeral: 作成したセッションが切れると自動削除（生存証明・リーダー選出）
sequential: 名前に単調増加の連番が付く（/lock/n_0000000012）→ 順番待ち行列とロックが作れる

watch

znode の変化を1回だけ通知する（one-shot）。通知を受けたら再登録が必要。通知と実際の値取得の間に別の変更が入りうるので、「通知は変化のヒント、真実は読み直し」という設計が必須

ZooKeeper が保証すること

・書き込みは線形化可能（全順序でブロードキャスト）
・クライアントごとの FIFO 順序（自分のリクエストは送った順に処理される）
・単調な読み（自分が見た zxid より古いデータは見ない）

保証しないこと（最重要）

読みは線形化可能でない。任意のフォロワーがローカルで応答するため、最新でない値を返しうる。最新が必要なら sync() を呼んでから読む（＝リーダーに追いつくのを待つ）

Fig 20-1: ZooKeeper の構成と ZAB。「読みはローカル」という設計が性能と引き換えに整合性を1段落としている。

⑥ メリット

  • ephemeral + sequential + watch の3部品で、ロック・選出・メンバ管理が全部書ける
  • 読みがローカルなので読みスループットが高い（Observer を足せばさらに拡張可）
  • 10年以上の実運用実績（Hadoop / HBase / Kafka / Solr エコシステム）

⑦ トレードオフ

  • 読みが線形化可能でない — sync() を忘れると微妙なバグになる
  • watch が one-shot で、通知の取りこぼしを前提にコードを書く必要がある
  • JVM 運用（GC 停止がセッション切れを引き起こす）
  • データサイズが小さい前提（znode は1MB上限が既定。大きなデータを置く設計は誤り）
  • 近年は etcd への移行が進んでいる（Kafka も KRaft で ZooKeeper 依存を廃止）

⑧ 実務での利用例

  • Kafka（事実）: 長年 ZooKeeper でブローカー登録・コントローラ選出・トピック設定を管理。現在は KRaft（自前 Raft）へ移行済み。「外部依存を1つ減らす」という運用上の判断
  • HBase / Hadoop（事実）: HMaster の選出と RegionServer の生存管理、HDFS NameNode の HA（ZKFC）で使用
  • YouTube / Vitess（事実）: トポロジストア（どのシャードのプライマリがどれか）として ZooKeeper / etcd / Consul のいずれかを選択できる
  • Twitter/X（事実）: Snowflake ID 生成器が worker ID の割り当てに ZooKeeper を使う設計だった（各ワーカーに一意なIDを配る = 合意が必要な最小の仕事）。「合意を1点だけ使う」好例
  • Uber（事実）: 各種基盤で ZooKeeper を利用。同時に Ringpop（gossip）のような非合意型も併用し、用途で使い分けている

⑨ Googleレベルの視点 — Chubby との比較

  • Chubby（Google）は「ロックサービス」として設計され、ZooKeeper は「協調プリミティブ」として設計された（事実 + 解釈）。Chubby は明示的なロックとリース、sequencer（fencing token）を API として持つ。ZooKeeper は ephemeral/sequential znode という汎用部品を提供し、ロックは「レシピ」として実装する
  • Chubby の教訓（事実）: 開発者が「小さな設定ストア」「名前解決」として使い始め、想定外の負荷がかかった。Google はクライアント側にキャッシュとプロキシを入れて負荷を吸収した。合意サービスは「便利すぎるので濫用される」ことを前提に、レート制限とキャッシュを最初から設計する
  • 設計原則: 合意サービスに置くデータは「小さく、変更頻度が低く、失うと全体が止まるもの」に限定する。アプリのデータを置き始めた時点で設計が壊れている

⑩ 面接での問われ方

  • Q:「ZooKeeper で分散ロックを実装してください」 → ephemeral + sequential znode、自分の1つ前だけを watch（herd effect 回避）、そして「ロックだけでは安全でないので fencing token（zxid）を保護対象に渡す」まで言う
  • Q:「ZooKeeper の読みは強整合ですか？」 → 「いいえ。ローカル読みなので古い可能性があります。線形化可能な読みが必要なら sync() を先に呼びます」
  • Q:「ZooKeeper と etcd、どちらを選びますか？」 → 「新規なら etcd（Kubernetes エコシステム、gRPC API、MVCC の revision が扱いやすい、Go で運用が軽い）。既存が Hadoop / Kafka 系なら ZooKeeper のままでよい」
  • Q:「watch の注意点は？」 → 「one-shot なので再登録が必要。通知と読み取りの間に別の更新が入りうるので、通知は『変化のヒント』として扱い、必ず現在の値を読み直す」

21 etcd — 「小さく強い真実の1点」の実装を読む

結論: etcd は Raft + MVCC ストア + Lease + Watch の4つを組み合わせて「線形化可能な KV ストア」を提供します。Kubernetes の全状態がここに入っており、etcd の性能特性（＝ディスクの fsync 遅延）がクラスタ全体の限界を決めます。設計面接では「etcd を1つ置く」が強整合の標準解になります。

📚 例え: 図書館の「中央目録」。すべての改訂に通し番号（revision）が振られ、過去の版も読める（MVCC）。貸出札には有効期限があり、更新しなければ自動で外れる（Lease）。「この本の状態が変わったら教えて」と予約できる（Watch）。目録が壊れれば図書館全体が機能しないので、目録だけは絶対に守る。

①② 何を解決するか / これがないと何が起きるか

  • 解決すること: 「クラスタ全体で1つしかない真実」（誰がリーダーか、どのPodがどのNodeにいるか、設定は何か）を、線形化可能に、かつ変更通知付きで提供する
  • ないと起きること: 各コンポーネントが独自に状態を持ち、食い違う（＝制御プレーンの split brain）。Kubernetes なら「2つのスケジューラが同じ Pod を別のノードに配置する」

23 Failure Detection — 「死んだ」は原理的に判定できない

結論: 分散システムでは「故障」と「遅い」を区別できません（15章 FLP の実質的な意味）。したがって故障検知は必ず誤検知（生きているのに死んだと判断）か検知漏れ（死んでいるのに気付かない）のどちらかを含みます。設計とは「どちらの誤りを、どのくらい許すか」を決める作業です。

🛣 例え: 取引先が約束の時間に来ない。「事故で来られない」のか「渋滞で遅れている」のか、待っている側には区別できない。10分待って帰れば、11分後に来た相手とすれ違う（誤検知）。1時間待てば、事故だった場合に1時間を無駄にする（検知遅延）。どちらを選んでも損失があり、正解はない。

①② 何を解決するか / これがないと何が起きるか

  • 解決すること: 「このノードを外して先に進んでよいか」の判断材料を作る。合意プロトコルのリーダー切り替え、ロードバランサからの切り離し、シャード再割り当ての引き金
  • 誤検知の代償: 不要なフェイルオーバー → 一時的な停止、キャッシュ喪失、リバランスの嵐、最悪 split brain
  • 検知漏れの代償: 死んだノードにリクエストを送り続ける → タイムアウトの山、ユーザー体験の悪化

  • Consul / Serf（事実）: SWIM ベースの gossip で数千ノードのメンバ管理。「合意（Raft）で管理するもの」と「gossip で管理するもの」を分けている点が設計として重要
  • Kubernetes（事実）: kubelet が Lease を定期更新（既定 10秒間隔）、コントロールプレーンが期限切れで NotReady 判定、その後 5分（tolerationSeconds 300）で Pod 退避。「検知」と「対処」を分離し、対処を遅らせることで誤検知の被害を抑えている
  • Google（解釈 + 一般論）: 大規模では「ノードの故障は日常」なので、検知の正確さを追うより、故障を前提に自動修復とレート制限を設計する。修復が同時に大量発生してシステムを殺さないよう、必ず並行修復数に上限を置く
  • Q:「ヘルスチェックの間隔とタイムアウトはどう決めますか？」 → 「RTT の p999 と GC の最大停止時間から下限を決め、誤検知時の損害と検知遅延の損害を比較して調整。さらに『疑わしい』状態を挟んで即断しない設計にします」
  • Q:「ノードが遅いだけの場合はどうしますか？」 → 「死亡判定ではなく重み付けを下げる（LBの outlier detection / hedged request）。二値ではなく連続量で扱う」

24 Split Brain と Fencing — 実務事故の中心はここ

結論: Split Brain（2人のリーダーが同時に存在する状態）は、検知の改善では防げません。防ぐ唯一の方法は Fencing: 世代番号（token）を付けて、古い世代の書き込みを保護対象側が拒否すること。「ロックを取ったから安全」という思い込みが、実務で最も多いデータ破壊の原因です。

📚 例え: 図書館の貸出札に連番を打つ。書庫の係員は「今まで見た最大の連番より小さい札を持って来た人」を追い返す。札を持っている本人が「自分の札は有効だ」と信じていても関係ない — 判定するのは書庫の係員（＝ストレージ側）。これが fencing token の本質。

①② 何が起きるのか

  • 典型的な発生経路: ① プロセスが GC / VM 停止で数十秒フリーズ → ② その間にリースが失効し、別ノードが新リーダーになる → ③ 元のノードが復帰し、自分がまだリーダーだと信じて書き込む
  • 被害: データの上書き・二重処理・不整合な状態。しかも「エラーが出ない」ので気付かない
  • ネットワーク分断でも同じ: 分断された側が「相手が死んだ」と誤認して昇格し、両側が書く

⑧ 実務での障害例（有名な事例）

  • GitHub 2018年10月（事実）: 米国東海岸と西海岸の間で 43秒のネットワーク分断が発生。自動フェイルオーバーツール（Orchestrator）が東海岸のクラスタを昇格させたが、分断が回復した際に両側に独立した書き込みが存在する状態になった。公開ポストモーテムによれば、データの整合性を優先して段階的な復旧を選択し、機能低下が24時間以上続いた。教訓: 自動フェイルオーバーは「跨リージョン」では慎重に。分断の一時性を判断できないため
  • Redis の分散ロック論争（事実）: Redlock（複数 Redis でロックを取る手法）に対し、Martin Kleppmann が「GC 停止やクロックずれで安全性が保証されない。fencing token が必要」と指摘し、Redis 作者 antirez が反論した公開議論がある。結論として「ロック単体では相互排他を保証できず、保護対象側の検証が必要」という点は広く受け入れられている
  • HDFS NameNode HA（事実）: 2つの NameNode が同時に書くのを防ぐため、JournalNode が epoch 番号で古い NameNode の書き込みを拒否する。fencing をアーキテクチャに組み込んだ良い実装例
  • Kubernetes（事実）: resourceVersion による楽観的並行制御が事実上の fencing。2つのコントローラが同じオブジェクトを更新しようとすると、片方が conflict エラーになる

⑨ Googleレベルの設計

  • Chubby の sequencer（事実）: ロック取得時に「ロック名 + モード + 世代番号」を含む sequencer を返す API を持つ。クライアントはこれを保護対象サーバに渡し、サーバが Chubby に照会するか、キャッシュした世代番号と比較して検証する。fencing を「ロックサービスの機能」として最初から設計している
  • Spanner / Bigtable（事実 + 解釈）: リーダーはリースを持ち、リース期間内でのみ権限を行使する。リースの期限管理には TrueTime（誤差付き時刻）を使うため、「時計がずれていても安全」な境界計算ができる
  • 設計原則: 「安全性を人間の運用手順やタイムアウト調整に依存させない」。プロトコルの中に安全性を埋め込む（term / epoch / sequencer）

⑩ 面接での問われ方（このテーマは差が付く最大のポイント）

  • Q:「分散ロックを実装してください」 → ① 合意ベースのストア（etcd / ZooKeeper）で TTL 付きロックを取る ② 単調増加 token を取得し、保護対象で検証する ③ 副作用は冪等にする。②を言わないと「知らない人」と判定される
  • Q:「Redis で分散ロックは使えますか？」 → 「キャッシュの thundering herd 防止のような『失敗しても壊れない』用途なら十分。相互排他が正しさに直結する用途には使わない。Redis Cluster は非同期複製なのでフェイルオーバー時にロックが消える可能性があり、さらに GC 停止に対しては fencing がなければどのロックでも不十分」
  • Q:「2つのリーダーが同時に存在したらどうしますか？」 → 「起きることを前提に設計します。term/epoch を全書き込みに載せ、ストレージが古い世代を拒否する。検知の改善では防げません」
  • Q:「跨リージョンの自動フェイルオーバーは？」 → 「慎重に。一時的な分断と本当の障害を区別できないため、GitHub の事例のような分岐が起きうる。跨リージョンは手動承認 or 十分に長い待機時間を入れるのが実務的」

25 Google Spanner — 「時計に投資して整合性を買う」設計を読む

結論: Spanner は「Paxos で各シャードを守り、2PC でシャード間を繋ぎ、TrueTime で全体の順序を決める」3階建ての構造です。他システムとの決定的な違いは「読み取り専用トランザクションがロックも合意も必要としない」点。これが地球規模の強整合を実用にしました。

🏦 例え: 世界中に支店を持つ銀行。各支店グループ（部門）に部長を置き、部門内の決議は部門の過半数で確定（＝Paxos グループ）。複数部門にまたがる決議は幹事役が両部門に確認を取る（＝2PC）。そして全社で「誤差±3msの標準時計」を配り、すべての決議に時刻を刻む（＝TrueTime）。誰でも「10:00:00 時点の帳簿」を、部長に聞かずに近くの支店で読める。

①② 何を解決したか / これがないと何が問題か

  • 解決したこと: 「地理分散 × 強整合 × SQL × 高可用」を同時に満たす。それまでは「NoSQL で結果整合を我慢する」か「単一リージョンの RDB でスケールを諦める」の二択だった（事実: Google 社内でも Bigtable の結果整合とアプリ側の複雑さが問題視され、AdWords などが Spanner へ移行した経緯が論文に記されている）
  • ないと起きること: シャーディングした RDB でアプリが分散トランザクションを手書きし、整合性バグを永久に抱える

Fig 25-1: Spanner の3階建て構造。「2PC のコーディネータを Paxos にする」と「読みを safe time で解決する」が2大工夫。

⑥ メリット

  • Strict Serializability（外部整合性）を地球規模で提供
  • 読み取り専用トランザクションが極めて安価（ローカル読み可能）
  • SQL + 二次索引 + スキーマ変更をオンラインで行える
  • 可用性が非常に高い（Google の公表値では 99.999% クラス）

⑦ トレードオフ

  • 書き込みに commit wait（数ms）+ Paxos の RTT が常に乗る
  • 跨 split トランザクションは 2PC でさらに遅い → スキーマ設計の制約が強い
  • コストが高い（インフラも課金も）
  • TrueTime に相当する時計基盤がないと同じ設計は再現できない
  • ホットスポット（単調増加キー）に弱い → キー設計の規律が必要

⑧⑨⑩ 実務例 / 設計の教訓 / 面接

  • Google 社内（事実）: F1（AdWords のバックエンド）が MySQL シャーディングから Spanner へ移行した事例が論文で語られている。「手動シャーディングの運用コストが限界だった」という動機は、多くの企業が数年遅れで辿る道
  • Cloud Spanner（事実）: 外部提供されており、金融・ゲーム・小売などで採用されている。「グローバルに強整合が要件」という限られた場面で圧倒的な選択肢
  • 他社の追随（事実）: CockroachDB / YugabyteDB / TiDB は Spanner 論文の影響を明言している。TrueTime がないため HLC + スキュー仮定で代替しているのが最大の違い
  • 面接での使い方: 「グローバルに強整合が必要なら Spanner / CockroachDB。ただしまずユーザーをリージョンに固定できないか（ホームリージョン方式）を検討します。多くの業務ではその方が安く速い」— Spanner を「知っている」だけでなく「避ける判断もできる」のが評価される
  • Q:「Spanner はどうやって CAP を破っているのですか？」 → 「破っていません。CP システムであり、過半数を失えば書き込めません。ただし Google の専用ネットワークにより分断確率が極めて低く、実効的な可用性が高いだけです」

26 Kubernetes — 「強整合な意思決定 × 結果整合な現実」の教科書

結論: Kubernetes は「宣言された望ましい状態（etcd に強整合で保存）」と「実際の状態（結果整合で追いつく）」を分離した設計です。この分離は分散システム設計の最良の教材で、面接で自分の設計を説明するときのテンプレートとして使えます。

📦 例え: 物流センターの「あるべき在庫表」を1冊だけ本部に置く（etcd）。各倉庫の作業員（kubelet）は本部の表を見て、自分の倉庫の現実をそれに合わせようと働き続ける。本部の表は常に正しく、現実は少し遅れて追いつく。表と現実が食い違ったら、作業員が現実を表に合わせる（reconcile ループ）。

27 Redis Cluster — 「合意を使わない」側の設計を正しく理解する

結論: Redis Cluster は合意プロトコルを使わず、gossip + 非同期複製 + epoch で動きます。したがって公式ドキュメントが明記する通り「強整合を保証しない」。ack を返した書き込みがフェイルオーバーで失われることがあります。これは欠陥ではなく「速さのために選んだトレードオフ」で、その前提を守れば極めて優秀なツールです。

📦 例え: 超高速の配送センター。受け取った瞬間に「受領しました」と返事をし、記録の複製は後回しにする。だから速い。しかし受領直後にセンターが停電すると、その荷物の記録だけ消える。「受領書が出たのに荷物がない」ことがあると分かって使うなら問題ない。銀行の入金記録には使ってはいけない。

③ 基本概念 — Redis Cluster の3つの部品

16384 ハッシュスロット

キーを CRC16(key) mod 16384 でスロットに割り当て、各スロットを1つのマスターが担当。スロット割り当ての情報が「合意されるべき唯一の状態」

Cluster Bus（gossip）

ノード間で専用ポート（データポート+10000）を使い、生死・スロット割当・epoch を交換する。Raft ではなく gossipなので、状態は結果整合

非同期複製

マスターはクライアントに即応答し、レプリカへの複製は後追い。複製完了を待たない = 応答した書き込みが未複製の可能性がある

configEpoch / currentEpoch

スロット担当の衝突を解決するための世代番号。より大きい configEpoch を持つ主張が勝つ（＝一種の fencing）。ただしデータ自体は守られない

Fig 27-1: Redis Cluster の構成と2つの喪失経路。設定で窓を狭められるが、原理的に消せない。

⑥ メリット（正しい用途では最強）

  • レイテンシがサブミリ秒（合意の RTT も fsync もない）
  • Lua スクリプトで単一スロット内の原子操作が書ける（レート制限・在庫の一時確保など）
  • スロット単位で水平スケールできる
  • 運用がシンプルで、リソース効率が高い

⑦ トレードオフ（前提として受け入れるべきこと）

  • ack 済み書き込みが失われることがある
  • 複数スロットにまたがる原子操作ができない
  • 分散ロックの相互排他を保証できない（24章）
  • メモリ容量が上限（データセットがメモリに載る前提）
  • 大きな値・大量キーの操作（KEYS / 大 HGETALL）が全体を止める

⑧ 実務での正しい使い方 / 危険な使い方

⑨⑩ 強整合が必要な場合の選択肢 / 面接での問われ方

  • Redis で強整合が必要なら（事実）: Redis Enterprise の一部機能や RedisRaft（実験的プロジェクト）のように、合意プロトコルを載せる試みがある。「Redis に合意を足す」より「合意が必要な部分だけ etcd/RDB に置く」方が実務的
  • Redis Sentinel の注意点（事実）: Sentinel の quorum は「障害と判定するために必要な Sentinel 数」であり、フェイルオーバーの実行には別途 Sentinel の過半数が必要。quorum を小さくしても過半数要件は消えないため、Sentinel を偶数台や2台で運用すると期待通りに動かない
  • Q:「キャッシュと DB の整合性はどう保ちますか？」 → 「書き込みは DB を真実とし、キャッシュは無効化（delete）する。write-through は競合で古い値が残りうるので、TTL を必ず付けて最終的に収束させる。厳密さが必要なら CDC でキャッシュを更新する」
  • Q:「Redis Cluster は CP ですか AP ですか？」 → 「実質 AP。非同期複製なので分断・障害時に ack 済み書き込みを失いうる。公式にも強整合は保証しないと明記されている」

29 理解度チェック — 20問（クリックで解答）

まず自分で答えてから開いてください。「答えを知っている」ではなく「口で説明できる」が目標です。詰まった問題の章に戻ること。

Q1 Linearizability を1文で定義してください。
各操作がその開始と終了の間のある一点で瞬間的に効いたように見え、全操作に単一の順序が付き、その順序が実時間の順序と矛盾しないこと。すなわちシステムが1台のコピーのように振る舞うこと。（05章）
Q2 Serializability と Linearizability の違いは何ですか。
Serializability は複数オブジェクトにまたがるトランザクションの分離性で、実行順序の入れ替えを許す（実時間を考慮しない）。Linearizability は単一オブジェクトへの操作の最新性で、実時間の順序を守る。両方満たすと strict serializability（Spanner の external consistency 相当）。（02章）
Q3 CAP定理の主張を正確に述べてください。「3つから2つ選ぶ」はなぜ誤りですか。
主張は「ネットワーク分断が起きている間、線形化可能性（C）と、故障していない全ノードが応答すること（A）を同時に満たすことはできない」。P（分断耐性）は選択肢ではなく前提であり、分断していない平常時は C と A が両立するため、「常に2つを選ぶ」という表現は誤り。（09章）
Q4 W + R > N を満たせば線形化可能になりますか。
なりません。書き込み進行中に read 集合の重なりが「まだ古いノード」を含むと、先に新しい値を読んだクライアントの後に古い値が返る（時間が巻き戻る）。線形化可能にするには読み時に quorum へ書き戻す（ABD）か、合意プロトコルで直列化する必要がある。（16章 Fig 16-1）
Q5 Lamport Clock で分からないことは何ですか。
2つのイベントが「並行（concurrent）」かどうか。C(a) < C(b) は a → b を意味しないため、競合検出には使えない。並行を検出したいなら Vector Clock。（12・13章）
Q6 Vector Clock の最大の運用上の欠点は何ですか。
サイズが O(ノード数) で増えること。ノードやクライアントが増減するとメタデータが膨張し、刈り込み（pruning）が必要になる。刈り込みは偽の因果関係を生むリスクがある。（13章）
Q7 なぜ経過時間の測定に wall clock を使ってはいけないのですか。
NTP のステップ補正・うるう秒・VM 停止で時刻が跳んだり巻き戻ったりするため、差分が負になったり異常に大きくなる。Go では time.Since / t2.Sub(t1)（monotonic 成分）を使う。ただし monotonic はプロセス間で比較できない。（11章）
Q8 TrueTime は何を返し、commit wait は何のために必要ですか。
TT.now() は時刻の点ではなく区間 [earliest, latest] を返す（真の時刻はこの中）。commit wait は「選んだコミットタイムスタンプが確実に過去になるまで待つ」ことで、実時間で後に始まったトランザクションが必ず大きいタイムスタンプを持つことを保証する（＝外部整合性）。（14章）
Q9 FLP不可能性は実務にどう影響しますか。
非同期環境では safety と liveness を同時に無条件保証できない。実システムは safety を無条件に守り、liveness を「通信が一定期間安定すれば」の条件付きにしている。したがって「選挙を繰り返して書き込めない」は起きるが「データが分岐する」は起きない。（15章）
Q10 Raft で「commit 済みのデータが失われない」理由を説明してください。
commit 済みエントリは過半数のノードが持っており、リーダー当選にも過半数の票が必要。2つの過半数集合は必ず1台以上交差するため、その交差ノードが「ログが古い候補者」への投票を拒否する（election restriction）。ゆえに commit 済みを持たないノードはリーダーになれない（Leader Completeness）。（18章）
Q11 Raft のリーダーは、前 term のエントリを過半数が持っていれば commit してよいですか。
いけません（論文 Figure 8 の反例）。前 term のエントリは後で上書きされる可能性があるため、新リーダーは自分の term で no-op エントリを1つ commit し、それによって過去のエントリを間接的に commit する。（18章）
Q12 Paxos の Phase 1（prepare）は何のために存在しますか。
「過去に既に決まった（accept された）値がないか」を過半数に問い合わせるため。もし見つかればその値を自分の提案として運ぶことで、一度決まった値が覆らないことを保証する。これがなければ2つの提案者が異なる値を別々の過半数に通してしまう。（19章）
Q13 ZooKeeper の読みは線形化可能ですか。
いいえ。読みは接続先ノードのローカル状態から返るため古い可能性がある（書きは線形化可能）。最新が必要なら sync() を呼んでから読む。（20章）
Q14 etcd の線形化可能な読みは内部で何をしていますか。
ReadIndex: 現在の commitIndex を記録し、ハートビートで過半数に「自分がまだリーダーである」ことを確認してから、その index まで適用された状態を読む。ディスク I/O は不要だがクラスタ内 1 RTT かかる。（18・21章）
Q15 分散ロックを取ったのに、なぜ二重実行が起きるのですか。対策は。
ロック保持中に GC / VM 停止で数十秒フリーズすると、その間にリースが失効して別ノードが取得する。復帰した元の保持者は自分の失効を知らずに書き込むため二重実行になる。対策は fencing: 単調増加 token を発行し、書き込み先が「今まで見た最大値」未満を拒否する。（24章）
Q16 Redis Cluster で ack 済み書き込みが失われる2つの経路は。
① 非同期複製: マスターが応答後・複製前に死亡し、レプリカが昇格する。② 分断された少数側マスターが node-timeout の間に受け付けた書き込みが、復帰時にレプリカへ降格することで破棄される。設定で窓は狭められるが消せない。（27章）
Q17 「保存したのに古い値が表示される」というユーザー報告への最小の対策は。
read-your-writes を追加する。① 更新したエンティティは primary から読む ② 書き込み後 N 秒は primary 読み ③ 書き込みで返る version をクライアントが保持し、その version 以上に進んだレプリカだけから読む（最も硬い）。整合性モデル全体を Strong に上げる必要はない。（07章）
Q18 可用性を保ちながら達成できる最も強い整合性は何ですか。
Causal Consistency（＋セッション保証）。分断中も各レプリカがローカルで応答できるため可用性を維持できる。Linearizability や Sequential Consistency は分断中に可用性を諦める必要がある。（07・09章）
Q19 Raft クラスタのノードを 3 から 4 に増やすと何が変わりますか。
許容故障数は 1 のまま変わらず（quorum が 2 → 3 になる）、書き込みに必要な ack が増えて遅くなる。つまり損。奇数台（3 or 5）にすべき。（16章）
Q20 「制御プレーンは CP、データプレーンは AP」を Kubernetes で具体的に説明してください。
望ましい状態は etcd（Raft = CP）に線形化可能に保存され、過半数を失うと更新できない。一方 kubelet はローカルに望ましい状態を持ち、コントロールプレーンが落ちても Pod を動かし続ける（AP）。実際の状態は結果整合で、reconcile ループが差分を埋め続ける。（26章）

30 システム設計面接 12問 — 模範解答の骨格つき

結論: 面接官が見ているのは「知識」ではなく「トレードオフを数字と業務影響で語れるか」。以下の12問は、整合性・合意に関する頻出パターンです。各回答の 加点ポイント と 減点ポイント を明示しました。

🎯 Q1. 「グローバルなチケット販売システムを設計してください。座席の二重予約は絶対に許されません」

  • 骨格: ① 座席は「1公演 = 1シャード」に閉じ込め、座席確保を単一シャード内のトランザクションにする（03章 D案）→ 合意も 2PC も不要で最速 ② 公演ごとにシャードが分かれるので水平スケールする ③ 可用性が必要なら、そのシャードを Raft グループ（etcd / CockroachDB）にする
  • 読みは分ける: 「残席あり/なし」の表示は結果整合のキャッシュ（数秒古くてよい）、確保・確定は強整合。表示と確定で整合性を分ける
  • 地理分散: ユーザーを公演の開催地リージョンに寄せる（ホームリージョン）。全世界で1つの強整合クラスタは作らない
  • 加点: 「待ち行列（仮想待合室）で流入を制御し、DB のホットスポットを避ける」「確保には TTL を付け、決済失敗時に自動解放する」
  • 減点: 「全部 Spanner で」だけで終わる / Redis の分散ロックで座席を守る

🎯 Q2. 「1つのジョブを、複数インスタンスのうち1台だけで実行したい」

  • 骨格: ① etcd / ZooKeeper で lease 付きリーダー選出 ② 実行中も lease の生存を監視し、失効したら即座に処理を中断（Go なら context のキャンセル） ③ 副作用の宛先に fencing token を渡して検証させる、または冪等キーで二重実行に耐える
  • 加点: 「そもそも二重実行しても壊れない設計（冪等）にできないかを先に検討します。排他は最後の手段です」
  • 減点: 「Redis の SETNX でロックを取ります」で終わる（24章の fencing に言及しない）

🎯 Q3. 「SNS のタイムラインを設計してください。整合性はどうしますか」

  • 骨格: 投稿本体は耐久性重視（複製された永続ストア）、タイムラインは結果整合の fanout。必要な保証は「① 自分の投稿が自分のタイムラインに出る（read-your-writes） ② 返信が本文より先に出ない（causal）」の2つだけ
  • 実装: ①はクライアント楽観更新 + 書き込み後の primary 読み ②は「返信は親IDと一緒に扱い、親が未取得ならクライアント側で保留 or 親を取得する」
  • 加点: 「いいね数は CRDT 的なカウンタ集計で結果整合にします。厳密にする価値がないので」
  • 減点: タイムラインを強整合にしようとする（コストが業務価値に見合わない）

🎯 Q4. 「地理分散した在庫管理。東京・EU・米国で同じ商品を売ります」

  • 骨格（最重要の考え方）: 在庫をリージョンごとに「割り当てる」（例: 総在庫 300 を 100/100/100 に分割）。各リージョンは自分の配分内でローカルに強整合で売る → 跨リージョンの合意が一切不要になり、レイテンシもゼロ
  • 配分が枯渇したリージョンは、他リージョンから在庫を「移送」する非同期プロセスを回す（＝分割して支配する）
  • どうしても単一在庫プールが必要なら Spanner / CockroachDB で1リージョンにリーダーを置き、他リージョンは遅くなることを受け入れる
  • 加点: 「これは escrow / reservation パターンです。合意を避けるためにビジネスルールを変える提案をします」
  • 減点: 全リージョンで1つの強整合カウンタを共有する（毎回 150ms + 可用性リスク）

🎯 Q5. 「決済処理で二重支払いを防いでください」

  • 骨格: ① クライアントが冪等キー（idempotency key）を生成して送る ② サーバは (キー, 状態, 結果) を強整合ストアに一意制約付きで記録 ③ 同じキーの再送には保存済みの結果を返す ④ 外部決済APIにも冪等キーを転送する
  • 状態遷移は「開始 → 外部呼び出し中 → 完了 / 失敗」を永続化し、クラッシュ後に再開できるようにする（Saga / ワークフローエンジン）
  • 加点: 「『外部APIを呼んだが応答が返らなかった』が最悪のケース。呼んだ事実を先に永続化し、結果は照会APIで確定させます」
  • 減点: 分散ロックだけで防ごうとする（プロセス停止で破れる）

🎯 Q6. 「マルチリージョンで active-active にしたい。整合性はどうなりますか」

  • 骨格: ① データを「どのリージョンが所有者か」で分割する（ユーザーごとのホームリージョン）→ 同一データへの同時書き込みが原理的に起きない ② 所有者以外からの書き込みは所有リージョンへプロキシする ③ グローバルに読める必要があるものは非同期複製 + 結果整合
  • 分割できないデータ（グローバルな一意ID、共有カウンタ）は、CRDT にするか、単一リージョンに集約する
  • 加点: 「active-active は『同じデータを両方で書く』ではなく『別のデータを別の場所で書く』と定義し直すのが実務解です」
  • 減点: 双方向複製 + LWW で解決したと考える（書き込み消失が起きる・04章）

🎯 Q7. 「etcd / ZooKeeper クラスタは何台にしますか。なぜ」

  • 骨格: 3台（1台故障許容）または5台（2台故障許容）。奇数。4台は3台と同じ耐性で quorum が増えるだけ損。2台は最悪（1台故障で全停止）
  • AZ 配置: 3 AZ に 1/1/1。2 AZ に 2/1 だと、2台側の AZ が落ちると過半数を失う
  • 加点: 「7台以上はハートビートと ack のコストが増えるだけで、実用的な利点がありません。読みを増やしたいなら learner / observer を足します」

🎯 Q8. 「書き込みスループットが足りません。Raft クラスタを10台に増やしますか」

  • 骨格: 増やしても遅くなるだけ。1つの Raft グループのスループットはリーダー1台と fsync に律速される。解は ① データを分割してMulti-Raft（グループを増やす） ② バッチ化 / group commit / pipelining ③ ディスクを NVMe に ④ そもそも合意が必要なデータかを再検討
  • 加点: 「まず wal_fsync_duration と backend_commit_duration を見て、ボトルネックがディスクかネットワークか CPU かを切り分けます」

🎯 Q9. 「キャッシュと DB の整合性をどう保ちますか」

  • 骨格: DB を唯一の真実とし、更新時はキャッシュを削除（更新ではなく削除 = cache-aside の invalidation）。TTL を必ず付けて、無効化の失敗を最終的に収束させる
  • 厳密さが必要なら CDC（binlog / WAL）でキャッシュを更新 → DB のコミット順序でキャッシュも更新されるので競合が減る
  • 加点: 「キャッシュを1枚挟むだけで、システム全体の整合性モデルは1段落ちます（DB が線形化可能でも全体は結果整合）。それを明示的に受け入れるかを設計で決めます」
  • 減点: 「DB とキャッシュを両方書きます」（順序が逆転して古い値が残る典型パターン）

🎯 Q10. 「ネットワーク分断が起きたとき、あなたのシステムはどう振る舞いますか」

  • 骨格: 機能ごとに答える。「認証は読み取り中心なのでキャッシュで継続」「注文の確定は少数側では拒否（CP）」「閲覧・検索は継続（AP）」「非同期処理はキューに溜めて後で処理」
  • 復旧時の手順も述べる: 「分岐が起きうる部分については、復旧時の競合解決ルールを事前に決めています」
  • 加点: 「完全な分断より gray failure（遅い・片方向・ロス）の方が多く、検知が難しい。だから fencing と冪等性で守ります」
  • 減点: 「CP なので止まります」だけ（機能ごとの degrade を設計していない）

🎯 Q11. 「順序が重要なイベント処理システムを設計してください」

  • 骨格: ① 因果のあるイベントを同じパーティションキーに寄せる（Kafka なら同一パーティション = 全順序）② グローバルな全順序は要求しない（スケールしないので） ③ コンシューマは冪等 + 順序番号のギャップ検知
  • 順序が壊れても復元できるように、イベントに単調増加のシーケンス番号（または HLC）を持たせる
  • 加点: 「全順序が本当に必要かを問い直します。多くの場合『エンティティごとの順序』で足ります。それならパーティション分割でスケールできます」

🎯 Q12. 「整合性を強くしたら遅くなりました。どう説明・改善しますか」

  • 説明: 「強整合は全書き込みに quorum の 1 RTT + fsync を、読みに ReadIndex の 1 RTT を課します。同一リージョンなら +3〜6ms、跨リージョンなら +80〜150ms。加えて p99 は最も遅いレプリカに引かれます」
  • 改善の順序: ① 読みを lease read / follower read に変える ② リーダーをアクセス元の近くへ移す ③ 強整合が必要な操作だけに限定する（読みの大半を結果整合に） ④ トランザクションの範囲を単一シャードに収まるようスキーマを変える ⑤ バッチ化・group commit
  • 加点: 数字で語る + 「整合性を落とす」以外の改善策を先に出す

C. よくある設計ミス 12（レビュー時のチェックリスト）

1. 用語の混同

ACID の C / CAP の C / Isolation を混ぜて議論する。議論が噛み合わない最大の原因（02章）

2. 「強整合にします」で終わる

範囲（どのキー・どの操作）と代金（レイテンシ・可用性）を言わない。強整合は面積で語る

3. Quorum = 線形化可能だと思う

W+R>N の誤解。読み修復か合意が必要（16章）

4. fencing を実装しない

ロックだけで排他したつもりになる。実務で最も多く、最も被害が大きい（24章）

5. 物理時刻で順序を決める

LWW + NTP 依存。書き込みが静かに消える（11章）

6. タイムアウトを勘で決める

GC の最大停止時間と RTT の p999 を測らずに設定する（23章）

7. 合意サービスにデータを置く

etcd / ZooKeeper をアプリの DB として使う。サイズ上限とスループット上限で必ず破綻（21章）

8. 偶数台クラスタ / 2台構成

耐障害性が上がらないのにコストと複雑さだけ増える（16章）

9. 冪等でない副作用

再試行・二重実行に耐えられない。冪等性は分散システムの最低要件

10. キャッシュの整合性を無視

DB を強整合にしても、前段のキャッシュで全体が結果整合になることを設計に書かない

11. 分断からの復旧を設計しない

AP を選んだのに競合解決ルールを決めていない。「あとで考える」は必ず事故になる（09章）

12. フェイルオーバーを訓練しない

普段動かない経路は本番で初めて動くと失敗する。定期的に意図的に落とす（17章）

🧪 障害を減らすために最初にやる5つ（費用対効果順）

  1. すべての副作用を冪等にする — 二重実行・再試行・split brain の被害を同時に潰せる唯一の手
  2. 条件付き更新を標準にする — WHERE version = ? / resourceVersion / mod_revision。Lost Update が構造的に消える
  3. 複製遅延の p999 を監視して SLO に入れる — 「Eventually」を運用可能な数字にする
  4. fencing token を設計に入れる — 排他が必要な処理の書き込み先で世代番号を検証する
  5. 整合性の選択を ADR に書く — 「なぜここは結果整合なのか」を残す。数年後の自分と後任のために
