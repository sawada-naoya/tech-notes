01 Batch Processing — 「全部揃ってから、まとめて」の技術

結論: Batch Processing とは「有界データ（終わりが確定しているデータ）を、まとめて一括処理する」ことです。最大の価値は『正しさ』と『安さ』——全件が揃っているので集計は正確で、まとめて処理するので単価が最小になる。代償は遅延だけ。そして実務の分析処理の8割は、遅延を許容できます。

🏭 工場のロット生産で考える: 材料を1日分ためてから、まとめて機械にかけます。段取り替えの回数が減るので、1個あたりのコストが最も安くなる。
そして重要なのが「やり直せる」こと: ロットが不良だったら、材料はまだ倉庫にあるので、同じ材料でもう一度作れます。
ライン生産（ストリーム）ではこれができません——流れ去った材料はもう戻ってこない。「再実行できる」がバッチ最大の強みです。

① この技術は何を解決するために生まれたのか

  • ① 大量データを現実的なコストで処理する — これが本質。1件ずつ処理するとオーバーヘッドが支配的になる。1億件をまとめて読めば、ディスクのシーケンシャル読み出しが効いて桁違いに速い
  • ② 「全件を見た正確な答え」を出す — 平均・中央値・パーセンタイル・重複除外カウントは、全件が揃って初めて正確に計算できる
  • ③ 再実行可能性 — 入力が保存されているので、ロジックを直して何度でもやり直せる（Backfill）
  • ④ 複雑な処理を書ける — 巨大な結合、機械学習の学習、多段の変換。ストリームでは現実的でない処理が普通に書ける
  • ⑤ リソースの効率的な利用 — 夜間の安い時間帯に、Spot インスタンスで一気に回す

② この技術がないと何が問題になるか

やりたいことバッチ無しでやるとバッチなら
月次の請求金額を計算ストリームで逐次加算 → 1件でも重複・欠損すると金額がズレ、後から直せない月末に全件を再集計。何度でもやり直せる
ユニークユーザー数（DAU）ストリームでは近似（HyperLogLog）しかできない正確な COUNT(DISTINCT) が出せる
レコメンドモデルの学習過去1年分のデータを1件ずつ流す？ → 非現実的全データを読んで学習。数時間で完了
集計ロジックのバグ修正ストリームだと過去の結果は直せない過去90日分を再実行すれば全部直る
10億行の結合ストリームでは状態が爆発するシャッフル結合で普通に処理できる

最も重要なのは4行目です。「間違えたときに直せるか」——これがバッチとストリームの、実務における最大の差です。

③ 基本概念

図1-1: バッチ処理の3要素（DAG・冪等性・実行制御）。②の冪等性がバッチ設計で最も重要。

有界データ（Bounded Data）

終わりが確定しているデータ。「2026-08-19のログ」は有界。バッチが扱うのはこれ。

DAG

Directed Acyclic Graph。タスクの依存関係を表す。循環しないので、実行順序が一意に決まる。

冪等性（Idempotency）

何度実行しても同じ結果になる性質。バッチにおける最重要要件。パーティション単位の上書きで実現する。

パーティション

データを日付などで物理的に分割したもの。処理単位・冪等性の単位・クエリの絞り込み単位を兼ねる。

Backfill

過去の期間を遡って再処理すること。ロジック変更・バグ修正・新指標の追加で必ず必要になる。

Sensor / Trigger

「入力データが揃ったか」を待つ仕組み。時刻起動だけだと、上流が遅れた日に空の結果を出す。

Shuffle

ノード間でデータを再配置する処理（GROUP BY / JOIN で発生）。バッチ処理で最も重く、最も遅い部分。

SLA

「何時までに完了するか」の約束。これを定義しないと、遅延に誰も気づかない。

⑤ 実際のシステム構成でどう使われるか

  • 典型構成 — アプリログ → S3/GCS（日付パーティション）→ Spark/BigQuery で集計 → DWH のマート → BI ツール
  • スケジューラ — Airflow が事実上の標準。Dagster / Prefect / AWS Step Functions / dbt Cloud も選択肢
  • 実行時刻の設計 — 「日次 03:00」のようにピークを避ける。上流の到着を待つ Sensor を必ず入れる
  • コスト最適化 — Spot インスタンス（失敗してもリトライすればよい）・夜間実行・データ量に応じた動的なクラスタサイズ
  • 依存の連鎖に注意 — 「Aが遅れるとBもCもDも遅れる」。クリティカルパスを把握し、各ジョブに SLA を設定する

⑥ メリット

  • 再実行できる — 最大の価値。バグを直せば過去も全部直せる
  • 正確 — 全件が揃っているので、COUNT(DISTINCT) も中央値も正確に出せる
  • 単価が最小 — まとめて処理するのでオーバーヘッドが償却される
  • 複雑な処理が書ける — 巨大な結合・ML の学習・多段の変換
  • デバッグしやすい — 入力が残っているので、手元で再現できる
  • 障害の影響が限定的 — 失敗しても「今日の集計が遅れる」だけ。サービスは止まらない

⑦ デメリット・トレードオフ

  • 遅延 — 数時間〜1日。「今の状況」が分からない
  • 失敗の代償が大きい — 3時間かかるジョブが2時間50分で失敗すると、最初からやり直し。対策はジョブの分割とチェックポイント
  • リソースのスパイク — 深夜に一気に負荷がかかる。クラスタのサイジングが難しい
  • 依存の連鎖 — 1つ遅れると全部遅れる
  • データの鮮度が低い — 「昨日までの数字」しか見られない
  • スケジュール起動の罠 — 「03:00に実行」だけだと、上流が遅れた日に空の結果を出す

⑧ 実務での利用例

  • Netflix — レコメンドモデルの学習は日次バッチ。「何を推薦するか」の計算は重いので、事前計算して配信する（20章）
  • Google Analytics — 生のヒットデータからセッション化・属性付与を日次で確定させる。リアルタイムレポートは速報、標準レポートは確定値という二段構え（21章）
  • Airbnb — 数千のバッチジョブを Airflow で管理（Airflow は Airbnb 発のOSS）。宿泊実績・検索ログ・価格提案の集計
  • Booking.com — 価格弾力性の分析、需要予測モデルの学習。「明日の価格」を今夜のバッチで計算する
  • 典型的な事故 — 「ジョブが途中で失敗し、部分的に書かれた状態でBIに公開され、経営会議で誤った数字が報告された」

⑨ Googleレベルではどう設計されるか

  • バッチとストリームを同じコードで書く — Apache Beam の思想。「有界データを処理するバッチは、無界データを処理するストリームの特殊ケース」と位置づける（15章）
  • データの品質を SLO 化 — 「完全性（行数）」「鮮度（何時までに）」「正確性（既知の値との一致）」を自動チェックし、通らなければ公開しない
  • 系譜（Lineage）の自動追跡 — 「このテーブルはどのテーブルから作られたか」を自動記録し、障害時の影響範囲を即座に特定できる
  • Backfill を1コマンドで — 過去90日の再処理が、手作業なしで実行できることを設計要件にする
  • Dataflow / BigQuery のサーバーレス化 — クラスタのサイジングという作業自体を消す。バッチの運用コストの大半はここにあった

⑩ システム設計面接ではどう問われるか

  • Q: 「日次の集計バッチを設計してください」 → 入力の到着待ち → パーティション単位の冪等な処理 → 品質チェック → 公開。「INSERT する」だけだと冪等性を理解していないと判断される
  • Q: 「ジョブが失敗しました。どうしますか？」 → 冪等なら単に再実行するだけ。冪等でないなら、まず部分的に書かれたデータを削除する必要がある
  • Q: 「集計ロジックにバグが見つかりました」 → Backfill。「過去N日を再実行する」。その際、下流への負荷とコストを考慮して並列度を絞る
  • Q: 「3時間かかるジョブが毎回失敗します」 → ジョブを小さく分割する・中間結果を永続化する・データ量を減らす（パーティション絞り込み・不要なカラムの排除）
  • Q: 「なぜストリームにしないのですか？」 → 「この指標は日次で十分だから。ストリームにするとコストが一桁増え、正確性も落ちる」

02 Stream Processing — 「終わらないデータ」を処理する

結論: Stream Processing とは「無界データ（終わりのないデータ）を、到着した端から継続的に処理する」ことです。得られるのは低遅延。支払うのは『全件が存在しない』という根本的な制約——だから Window で人工的な境界を引き、Watermark で締め切りを推定し、State を持って途中経過を保持する必要が生まれます。8章以降の全ての概念は、この制約から導かれます。

🏭 ベルトコンベアのライン生産で考える: 材料が流れてくる端から加工します。ためないので、完成品がすぐ出てくる。
しかし「今日の生産数は？」と聞かれても答えられません——まだ流れ続けているからです。
だから「10分ごとに区切って数える」というルールを人間が決める（＝Window）。
さらに困るのが「遅れて届いた材料」: 10:00〜10:10の材料が10:15に届いたら、もう集計は締めてしまった。どこまで待つかを決めるのが Watermarkです。

① この技術は何を解決するために生まれたのか

  • ① 「今」を知る — これが本質。不正検知・障害検知・在庫の即時反映は、明日分かっても意味がない
  • ② 意思決定と行動の間の時間を縮める — 「異常が起きた → 気づく → 対処する」のサイクルを秒単位にする
  • ③ 負荷の平準化 — 深夜に一気に処理するのではなく、常に一定量を処理する
  • ④ 無限に増えるデータへの対応 — 「全部ためてから処理する」が物理的に不可能な規模
  • ⑤ 継続的な状態の更新 — レコメンド・パーソナライズ・リアルタイムダッシュボード

② この技術がないと何が問題になるか

やりたいことバッチだけだと必要な遅延
クレジットカードの不正検知翌日に「昨日不正がありました」→ 手遅れ100ms〜1秒
動画配信の障害検知翌朝に気づく → 一晩中エラー10秒〜1分
「今トレンドの動画」表示昨日のトレンドを今日見せる1〜5分
広告の予算上限チェック予算を大幅に超過してから気づく1秒〜1分
在庫のリアルタイム表示売り切れ商品が表示され続ける1秒
A/Bテストの異常検知悪い施策を1日流し続ける5〜30分
月次売上レポートバッチで全く問題ない1日
ML モデルの学習バッチで全く問題ない1日〜1週間

下2行に注目してください。ストリームが必要なのは「時間が価値を左右する」処理だけです。それ以外にストリームを使うと、コストと複雑さだけが増えます。

⑤ 実際のシステム構成でどう使われるか

  • 典型構成 — アプリ → Kafka → Flink/Kafka Streams → 出力（Redis / Druid / Elasticsearch / 別 topic）→ ダッシュボード or アラート
  • 出力先の選択 — 「更新可能」であることが重要。追記のみのストレージに出すと、遅延データの反映ができない
  • ストリームDBという選択肢 — Apache Druid / Apache Pinot / ClickHouse。ストリームから直接取り込み、低遅延で集計クエリを返す
  • ストリーム処理の並列度 — Kafka の partition 数が上限。キーの偏り（Hot Key）で特定タスクだけ詰まる
  • バッチとの併存 — 速報値をストリーム、確定値をバッチで出す。「同じ名前の指標が2つの数字を持つ」問題への対策が必須（3章）

  • 低遅延 — 秒〜分。これが唯一かつ決定的な価値
  • 負荷が平準化される — 常に一定量を処理する
  • 異常への即時対応が可能 — 不正検知・障害検知・予算超過

  • データをためる必要がない — 巨大なストレージが不要な場合もある

04 MapReduce — 全ての分散データ処理の原型

結論: MapReduce とは「大量データの処理を『Map（各要素を変換）』と『Reduce（キーごとに集約）』の2段階に固定することで、分散処理を誰でも書けるようにした」枠組みです。現代では直接書くことはほぼありませんが、Spark も BigQuery も Flink も、内部の考え方はここから出ています。特に Shuffle という概念は、今も分散処理最大のボトルネックです。

📚 図書館の蔵書カウントで考える: 100万冊の蔵書を、著者ごとに冊数を数えたい。1人でやったら何ヶ月もかかります。
Map: 100人の司書に本を1万冊ずつ配り、各自が「著者名 → 1」というメモを書く（並列に、独立して作業できる）。
Shuffle: 「あ行の著者のメモは全部Aさんへ」とメモを仕分けて配り直す。ここで全員が動き、全メモが移動する——最も時間がかかる工程。
Reduce: 各自が受け取ったメモを著者ごとに合計する。
この3段階が、全ての分散データ処理の骨格です。

① この技術は何を解決するために生まれたのか

Google が2004年に発表した論文が原点です。当時の問題は「Webのクロールデータを処理するたびに、分散処理のコードをゼロから書いていた」ことでした。

  • ① 分散処理の「難しい部分」を隠す — これが本質。並列化・データ配分・障害からの復旧・ノード間通信を、フレームワークが全部やる。開発者は Map と Reduce の2つの関数だけ書けばよい
  • ② 安価なマシンで大規模処理を可能にする — 高価なスパコンではなく、壊れる前提の commodity machine を数千台束ねる
  • ③ 障害を前提にする — 「数千台あれば、毎日どれかが壊れる」。壊れたタスクを別ノードで再実行するだけで済む設計にした
  • ④ データのある場所で計算する（Data Locality） — データをネットワーク越しに動かすのではなく、計算をデータのあるノードに送る

② この技術がないと何が問題になるか

  • 処理ごとに分散処理基盤を作り直す — タスク分割・進捗管理・失敗の再実行・結果のマージを、毎回書く
  • 1台が壊れると全部やり直し — 5000台で3時間の処理中に1台壊れる確率はほぼ100%。部分的な再実行ができないと、永久に終わらない
  • データの移動がネットワークを飽和させる — 数百TBをネットワーク経由で集めるのは非現実的

⑤ 実際のシステム構成でどう使われるか

  • 現代で MapReduce を直接書くことはほぼない — Hadoop MapReduce は事実上レガシー。Spark / BigQuery / Presto が置き換えた
  • しかし概念は生きている — Spark の map / reduceByKey、SQL の GROUP BY、Flink の keyBy + reduce は全て同じ構造
  • HDFS の後継 — 今は S3 / GCS などのオブジェクトストレージ。Data Locality は失われたが、ストレージと計算の分離という大きな利点を得た
  • YARN の後継 — Kubernetes。リソース管理の考え方は継承されている

⑥ メリット

  • 単純なモデル — Map と Reduce の2つだけ。誰でも分散処理が書ける
  • 障害に極めて強い — タスク単位の再実行。数千台規模で毎日壊れても動き続ける
  • 巨大なデータを扱える — メモリに乗る必要がない（全部ディスク経由）
  • スケールが線形に近い — ノードを増やせば増やしただけ速くなる（Shuffle がボトルネックになるまで）

⑦ デメリット・トレードオフ

  • 中間結果を必ずディスクに書く — 多段処理・反復処理が遅い
  • 表現力が低い — JOIN も TOP-N も自分で Map/Reduce に翻訳する
  • 起動オーバーヘッド — 小さいジョブには向かない
  • リアルタイム処理は不可能 — バッチ専用
  • Straggler 問題 — 1台の遅いノードが全体を待たせる

⑨ Googleレベルではどう設計されるか

  • MapReduce は Google 発だが、Google 内部ではとうに卒業している — FlumeJava → Dataflow → Beam という進化を経て、「Map/Reduce という2段階の制約」自体を捨てた
  • 最適化をフレームワークに任せる — 開発者は「何を計算するか」を書き、実行計画（どこで Shuffle するか、どう並列化するか）はエンジンが決める。SQL のオプティマイザと同じ発想
  • Dremel（BigQuery の原型） — MapReduce とは全く別系統。列指向 + ツリー状の集約で、対話的なクエリを秒で返す。「バッチで数十分」を「対話で数秒」に変えた
  • 教訓 — 「単純な抽象は普及するが、やがて表現力の限界で乗り越えられる」。MapReduce → Spark → SQL/Beam の流れがそれ

⑩ システム設計面接ではどう問われるか

  • Q: 「MapReduce の仕組みを説明してください」 → Map（並列変換）→ Shuffle（キーで再配置）→ Reduce（キーごとに集約）。Shuffle に言及できるかが分かれ目
  • Q: 「なぜ Shuffle が遅いのですか？」 → 全ノード間でデータが移動し、ディスク書き出しとソートが発生するから。ジョブ時間の50〜80%を占める
  • Q: 「Shuffle を減らすには？」 → ①事前集約（Combiner）②不要カラムの削除 ③フィルタの前倒し ④Broadcast Join
  • Q: 「average を Combiner で計算できますか？」 → できない。部分平均の平均は全体平均にならない。(sum, count) のペアで持ち回れば可能——この理解は12章の集計設計に直結する
  • Q: 「1台だけ極端に遅い場合は？」 → Straggler。投機的実行（同じタスクを別ノードでも走らせ、先に終わったほうを採用）。根本原因はデータの偏り（Skew）であることが多い

05 Apache Spark — メモリを使い、DAG で最適化する

結論: Spark は「中間結果をメモリに保持し、処理全体を DAG として最適化する」ことで MapReduce を置き換えました。反復処理で10〜100倍速く、SQL・ストリーム・MLを1つの基盤で扱える。実務の困りごとはほぼ全て「Shuffle」「データの偏り（Skew）」「メモリ不足」の3つに集約されます。

🏭 工場の作業台で考える: MapReduce は「1工程ごとに製品を倉庫に戻す」やり方でした。
Spark は「作業台の上に置いたまま次の工程に進む」——倉庫（ディスク）への往復が消えるので圧倒的に速い。
さらに Spark は「作業計画を先に全部立ててから動く」: 「最後に10件しか使わないなら、最初から10件だけ運べばいい」といった最適化を、実行前に自動で行います（遅延評価と Catalyst オプティマイザ）。
ただし作業台には限りがあります——載らなくなったら結局倉庫に置く（Spill）ことになり、遅くなります。

① この技術は何を解決するために生まれたのか

  • ① 反復処理の高速化 — これが原点。UC Berkeley で機械学習の研究者が「同じデータを何十回も読み直す MapReduce が遅すぎる」ことに困っていた
  • ② 多段処理での中間ディスク書き込みを消す — メモリに保持したまま次の処理へ
  • ③ 表現力を上げる — map/filter/join/groupBy/window など豊富な演算子。SQL も書ける
  • ④ 1つの基盤で全部やる — バッチ（Spark SQL）・ストリーム（Structured Streaming）・ML（MLlib）・グラフ（GraphX）
  • ⑤ 最適化を自動化する — Catalyst オプティマイザが実行計画を書き換える

  • MapReduce より10〜100倍速い（特に反復処理）

  • チューニングの知識が必要 — メモリ設定・パーティション数・Join 戦略。「動くが遅い」状態になりやすい

  • クラスタ運用のコスト — サーバーレス以外はサイジングが必要
  • 「なんでも Spark」の誘惑 — SQL で済むものに Spark アプリを書くのは、複雑さの無駄な追加

06 ETL と ELT — 「変換をどこでやるか」の逆転

結論: ETL は「変換してから入れる」、ELT は「入れてから変換する」。DWH のストレージが安く、計算が強くなったことで、2010年代後半に ELT が既定になりました。ELT の本質的な価値は速度ではなく「生データが残るので、後からロジックを変えられること」です。

🍳 料理で考える: ETL は「下ごしらえしてから冷蔵庫に入れる」——場所は取らないが、後から「やっぱり違う切り方にしたい」ができません。
ELT は「食材のまま冷蔵庫に入れ、使うときに調理する」——冷蔵庫が大きくて安いなら、こちらが圧倒的に柔軟です。
2000年代は冷蔵庫（DWH）が小さくて高かったので ETL が必然でした。今は S3 も BigQuery も安いので、ELT が既定になりました。
ただし ELT には「冷蔵庫が食材でいっぱいになり、何がどこにあるか分からなくなる」というリスクがあります（Data Swamp）。

① この技術は何を解決するために生まれたのか

  • ETL の目的（1990〜2000年代） — DWH のストレージと計算が高価だったので、入れる前にデータを最小化する必要があった。不要な列を削り、集計してから入れる
  • ELT の目的（2010年代後半〜） — これが本質: 「変換ロジックは必ず変わる」という現実への対応。生データが残っていれば、いつでも作り直せる
  • ② 変換の民主化 — ETL は専用ツール（Informatica等）とエンジニアが必要だった。ELT なら SQL が書けるアナリストが自分で変換できる
  • ③ 取り込みと変換の分離 — 取り込み（EL）は単純な作業として自動化し、変換（T）だけをビジネスロジックとして管理する
  • ④ 新しい要求への即応 — 「先月から新しい指標を出したい」→ ELT なら生データがあるので即座に可能

  • Modern Data Stack — Fivetran/Airbyte（EL）→ Snowflake/BigQuery（Load先）→ dbt（T）→ Looker/Tableau（BI）
  • 取り込みの手段 — SaaS のコネクタ（Fivetran）/ CDC（Debezium）/ ログの直接配置（S3）/ Kafka Connect
  • 変換のバージョン管理 — dbt のモデルは Git で管理し、PR レビュー・CI テストを通す。「SQL をアプリケーションコードと同じ扱いにする」のが最大の変化

  • ハイブリッド（EtLT） — 取り込み時に最小限の変換（PII マスキング・形式変換）だけ行い、残りは DWH で。実務ではこれが多い

⑥ メリット（ELT の）

  • 生データが残る — 最大の価値。ロジックを何度でも作り直せる
  • 変換の民主化 — SQL が書ければ誰でも変換を追加できる
  • スケールが自動 — DWH の計算力をそのまま使える
  • 取り込みが単純 — 変換を考えずに「とりあえず入れる」ができる
  • 変換をテスト・バージョン管理できる — dbt により SQL がソフトウェア工学の対象になった
  • 系譜（Lineage）が自動で得られる — 「この指標はどのテーブルから来たか」が可視化される

⑦ デメリット・トレードオフ

  • ストレージコストが増える — 生データを全部残す。ただしオブジェクトストレージは極めて安いので、大抵は許容範囲
  • Data Swamp のリスク — 「とりあえず入れる」が積み重なり、何がどこにあるか誰も分からなくなる。カタログとオーナーシップが必須
  • DWH の計算コスト — 変換のたびに課金される。非効率な SQL が積み重なると請求が跳ねる（19章）
  • 個人情報の扱い — 生データに PII が含まれると、アクセス制御が難しくなる。取り込み時のマスキング（EtLT）が必要な場合がある
  • SQL の限界 — 複雑な変換・非構造データは SQL では書きにくい
  • モデルの依存が複雑化する — dbt のモデルが数百になると、実行時間と依存関係の管理が問題になる

⑧ 実務での利用例

  • Airbnb — 大規模な ELT 基盤。「Minerva」という指標定義の統一プラットフォームを構築し、「同じ指標が部署ごとに違う」問題を解いた（22章）
  • Netflix — S3 + Iceberg を Raw 層とし、Spark / Trino で変換。「データは1箇所、処理エンジンは複数」という構成
  • Booking.com — 実験データの ELT。数千の A/B テストの結果を、統一された変換パイプラインで集計する
  • Google Analytics 4 — BigQuery へのエクスポートは生のイベントデータ（ELT 的）。ユーザーが自分で好きに集計できる（21章）
  • 典型的な事故 — 「Raw 層を『容量削減のため』90日で削除する運用にしていたら、半年前からの指標のバグが見つかっても直せなかった」

⑨ Googleレベルではどう設計されるか

  • 指標定義の一元化 — 「DAU」という指標の定義がコード上に1つだけ存在し、全ての利用者がそれを参照する。Airbnb の Minerva、LookML のセマンティックレイヤーが同じ思想
  • データ契約（Data Contract） — 上流のスキーマ変更を、下流が壊れる前に検出する。「ソースのカラム名が変わってパイプラインが止まった」を構造的に防ぐ
  • PII の自動検出とタグ付け — 取り込み時に個人情報を自動分類し、アクセス制御とマスキングを自動適用する
  • コストの可視化 — クエリごと・チームごとの課金を可視化し、非効率な SQL を検出する
  • 系譜の自動追跡 — 障害時に「このテーブルが壊れると、どのダッシュボードが影響を受けるか」を即座に特定できる

⑩ システム設計面接ではどう問われるか

  • Q: 「ETL と ELT の違いは？」 → 変換の位置。さらに「ELT の本質的な価値は速度ではなく、生データが残るので後から作り直せること」と言えると強い
  • Q: 「なぜ ELT が主流になったのですか？」 → DWH のストレージが安く、計算が強くなったから。制約が消えたので、柔軟性を取れるようになった
  • Q: 「集計ロジックにバグが見つかりました」 → ELT なら Raw 層から再構築（--full-refresh）。ETL だと元データが無いので直せない——この対比が答えられると理解が深いと判断される
  • Q: 「ELT のリスクは？」 → Data Swamp（何がどこにあるか分からない）と、計算コストの膨張。カタログ・オーナーシップ・コスト監視が必要
  • Q: 「個人情報を含むデータは？」 → EtLT。取り込み時にマスキング/トークン化だけ行い、残りは DWH で変換する

07 Data Warehouse / Data Lake / Lakehouse — データの置き場所

結論: DWH は「整理された製品倉庫」、Data Lake は「未加工の原材料倉庫」。そして両者の良いところを取ろうとしたのが Lakehouse（Iceberg / Delta Lake / Hudi）です。実務での判断軸は「スキーマをいつ決めるか（Schema-on-Write か Schema-on-Read か）」——ここが全ての違いの源です。

📦 2つの倉庫で考える:
Data Warehouse = 製品倉庫。入れる前に検品し、規格の箱に詰め、棚番号を振る。取り出すのは一瞬だが、入れるのに手間がかかり、規格外のものは入れられない。
Data Lake = 原材料倉庫。とにかく全部放り込む。安いし何でも入るが、「あの材料どこ？」が分からなくなる。
誰も管理しなくなった原材料倉庫が Data Swamp（沼）です。
Lakehouse は「原材料倉庫に、棚番号の台帳を付けた」もの——安さと柔軟性を保ったまま、検索性とトランザクションを足しました。

① これらは何を解決するために生まれたのか

  • DWH（1990年代） — 「業務DBに分析クエリを投げると本番が落ちる」という問題。分析専用の場所を作り、集計に最適化した構造（列指向・スタースキーマ）にした
  • Data Lake（2010年前後） — 「DWH に入れられないデータ（ログ・JSON・画像・センサー）が増えすぎた」という問題。スキーマを決めずに、とりあえず安く全部保存する
  • Lakehouse（2020年前後） — 「Lake は安いがトランザクションも品質保証も無い、DWH は高いが安全」という二重管理の苦痛への回答。Lake の上に台帳（メタデータ層）を載せて、DWH の機能を実現する

③ 基本概念 と ④ 内部の動き

図7-1: 3つの置き場所と、Lakehouse が ACID を実現する仕組み。メタデータ層の切り替えが原子性の源。

⑤ 実際のシステム構成でどう使われるか

  • 現代の標準構成 — S3/GCS（Raw、Parquet）+ Iceberg/Delta（テーブル層）+ Spark/Trino/BigQuery（計算）+ dbt（変換）+ BI
  • 「ストレージと計算の分離」が最大の変化 — 同じデータを Spark でも Trino でも BigQuery でも読める。ベンダーロックインが弱まった
  • ファイル形式は Parquet 一択 — 列指向・圧縮・統計情報付き。CSV/JSON で Lake に置くのは、コストとクエリ速度で数十倍の損失（19章）
  • DWH と Lake の使い分け — 「BI が直接見るのは DWH のマート、生データと大規模処理は Lake」が現実的。完全な統合は理想だが、移行コストが高い
  • 小さいファイル問題への対処 — 定期的な compaction ジョブ。Iceberg/Delta は最適化コマンドを提供している

  • Airbnb — Hive/S3 ベースの Lake + 上位に整形済みのマート。数万テーブルの管理のため、データカタログ（Dataportal）を自社開発

  • 典型的な事故 — 「S3 に CSV でログを置き続け、3年後にクエリが数時間かかるようになった。Parquet に変換したら10分になった」

⑨ Googleレベルではどう設計されるか

  • BigQuery は分類しにくい存在 — DWH でありながら、ネストしたJSON・巨大な半構造データ・ストレージと計算の分離を最初から備えている。「Lake vs DWH」の議論を製品として無効化した
  • Dremel の設計 — 列指向 + ツリー状の集約で、ペタバイト規模を対話的にクエリできる。「バッチで数十分」を「数秒」に変えたのが最大の貢献
  • BigLake / Iceberg 対応 — 「データは1箇所（オブジェクトストレージ）、エンジンは複数」という方向に収束しつつある
  • データガバナンスを基盤に組み込む — 分類・アクセス制御・系譜・保持期間を、テーブル作成時に必須項目にする。「後から整理する」は絶対に成功しないという経験則

⑩ システム設計面接ではどう問われるか

  • Q: 「Data Lake と DWH の違いは？」 → Schema-on-Read か Schema-on-Write か。ここから全ての違い（柔軟性 vs 速度・安全性）が導かれる
  • Q: 「Data Lake の課題は？」 → ACID が無い・UPDATE/DELETE ができない・Data Swamp 化。Lakehouse（Iceberg/Delta）が答え
  • Q: 「Lakehouse はどうやって ACID を実現していますか？」 → メタデータ層（台帳）で「現在有効なファイル集合」を管理し、その切り替えを原子的に行う。この説明ができると理解が深いと判断される
  • Q: 「GDPR の削除要求にどう対応しますか？」 → 素の Lake では困難（ファイル単位でしか消せない）。Lakehouse なら DELETE できる。加えて暗号化 + 鍵の破棄（Crypto-shredding）も選択肢
  • Q: 「ファイル形式は？」 → Parquet。列指向・圧縮・統計情報により、CSV より桁違いに速く安い

08 Event Time と Processing Time — ストリーム処理の全ての難しさの源

結論: Event Time は「出来事が起きた時刻」、Processing Time は「システムが処理した時刻」。この2つは必ずズレます。そして Processing Time で集計すると、結果が『いつ処理したか』に依存して毎回変わります——再実行すると違う答えが出るのです。9〜11章の概念は、全てこの1章から導かれます。

📮 郵便の消印と受取日で考える: 手紙には「投函した日（消印）」と「受け取った日」があります。
「8月の手紙は何通？」と聞かれたとき、消印（Event Time）で数えるのが正しい。受取日で数えると、配達が遅れただけで8月の集計が変わってしまう。
しかし消印で数えるには問題がある: 「8月の集計はいつ締めればいいのか？」——9月5日に8月31日消印の手紙が届くかもしれない。この「いつ締めるか」が Watermark（10章）です。

① この区別は何を解決するために生まれたのか

  • ① 結果を再現可能にする — これが本質。Event Time で集計すれば、何度実行しても、いつ実行しても、同じ入力からは同じ結果が出る
  • ② 事実を正しく記録する — 「10時に起きた出来事」は、いつ処理されても10時の出来事
  • ③ バッチとストリームの結果を一致させる — バッチは元々 Event Time で集計する。ストリームを Processing Time で集計すると、両者が永久に一致しない
  • ④ 障害・遅延の影響を隔離する — システムが1時間止まっても、Event Time なら集計結果は変わらない

② この区別がないと何が問題になるか

図8-1: Processing Time の破綻と Event Time の効果。「再処理しても同じ結果が出る」がEvent Timeの決定的な価値。

③ 基本概念 — 3つの時刻

Event Time

出来事が実際に起きた時刻。イベント自身が payload に持つ。集計の基準として正しいのはこれ。

Ingestion Time

システム（Kafka等）がイベントを受け取った時刻。Event Time より安定しているが、モバイルのオフライン遅延は反映されない。妥協案として使われる。

Processing Time

処理エンジンが処理した時刻。実装は最も簡単だが、結果が再現不可能。

Skew（時刻のズレ）

Event Time と Processing Time の差。これの分布（P50/P99/最大）を測ることが、Watermark 設計の出発点。

Out-of-Order

Event Time 順に到着しないこと。分散システムでは常態。

時計のズレ（Clock Skew）

クライアント端末の時計が狂っている問題。未来の時刻や1970年のイベントが混入する。サーバ側で検証・補正が必要。

④ 内部でどのように動くのか — 実装上の注意

⑤ 実際のシステム構成でどう使われるか

  • Event Time を必ず payload に含める — 後から追加するのは極めて困難。イベント設計の最初に決める
  • 時刻は UTC のエポックミリ秒で持つ — タイムゾーン付き文字列はパースコストと解釈違いの元
  • 遅延の分布を常に計測する — processing_time - event_time のヒストグラム。これが Watermark 設定の根拠になる
  • Skew のアラート — 「P99 の遅延が普段の3倍になった」は、上流の障害の先行指標
  • サーバ発イベントとクライアント発イベントを分ける — 前者は遅延が小さく Ingestion Time でよいが、後者は数日遅れることがある。同じパイプラインで扱うと Watermark 設計が破綻する

⑥ メリット（Event Time を使うことの）

  • 結果が再現可能 — 同じ入力なら常に同じ出力。これが最も重要
  • バッチとストリームの結果が一致する — 速報値と確定値の乖離が「遅延データの分だけ」に限定される
  • 障害・デプロイの影響を受けない — 偽の異常が集計に現れない
  • 再処理が意味を持つ — 過去のデータを流し直せば、当時と同じ結果になる

⑦ デメリット・トレードオフ

  • 「いつ結果を出すか」を決める必要がある — Watermark という新しい概念が必要（10章）
  • 遅延データの扱いが必須になる — 捨てるか、後から更新するか
  • State を長く保持する必要がある — 遅延を許容する分だけ、Window の状態をメモリ/ディスクに置き続ける
  • 結果が出るまでの遅延が増える — 「10:00-10:01 の集計」を出すのに、10:01:30 まで待つ必要がある
  • クライアントの時計を信用することになる — 検証と補正が必須。1台の壊れた端末が全体を壊しうる

⑧ 実務での利用例

  • Google Analytics — ヒットの発生時刻を基準に集計する。モバイルアプリのオフライン計測は、最大数日遅れて届くことを前提にしている（21章）
  • Netflix — 再生イベントは端末で生成され、オフライン視聴（ダウンロード再生）もあるため、Event Time での集計と、数日後の確定処理が必須
  • 広告システム — インプレッションとクリックの紐付け。クリックはインプレッションより後に起きるが、到着順は逆になりうる
  • IoT / センサー — ネットワーク断で数時間分がまとめて送られる。Processing Time で集計したら全く意味のないデータになる
  • 典型的な事故 — 「端末の時計が2038年になっていたイベントが1件混入し、Watermark が2038年まで進んで、以降の全イベントが『遅延』として破棄された」

⑨ Googleレベルではどう設計されるか

  • 「Event Time が第一級市民」 — Beam / Dataflow のモデルは Event Time を前提に設計されている。Processing Time での処理は、明示的に選択する例外
  • Streaming 102 の4つの問い — What（何を計算）/ Where（どの Window）/ When（いつ出力）/ How（更新の扱い）。この整理により、時刻の問題が構造化された
  • 時刻の検証を基盤で行う — クライアントの時計ズレを、収集レイヤーで自動的に検出・補正する
  • 遅延の分布を SLO 化 — 「99%のイベントは発生から30秒以内に到着する」を計測し、Watermark の設定根拠にする
  • Perfect Watermark は存在しないと認める — 「完全に正しい締め切り」は原理的に決められないので、ヒューリスティックと遅延データの再処理を組み合わせる

⑩ システム設計面接ではどう問われるか

  • Q: 「Event Time と Processing Time の違いは？」 → 「出来事が起きた時刻」と「処理した時刻」。集計は Event Time でなければ再現可能にならない
  • Q: 「なぜ Event Time を使うのですか？」 → 「再処理しても同じ結果が出るから」。「正確だから」だけだと弱い。再現可能性まで言えるかが差
  • Q: 「集計結果が実行するたびに変わります」 → Processing Time で集計している。Event Time に変える
  • Q: 「クライアントの時計が信用できません」 → サーバ側で範囲を検証し、異常値は受信時刻で置き換える + メトリクス化。「1件の未来時刻が Watermark を壊す」ことに言及できると強い
  • Q: 「Processing Time を使ってよいのはどんなときですか？」 → 運用監視（今システムがどう動いているか）。むしろこちらが正しい場合もある

09 Window — 終わらない流れに、境界を引く

結論: Window とは「無界データに人工的な境界を引いて、有界データにする」仕組みです。これによって初めて「合計」「平均」といった集計が定義できます。Tumbling / Sliding / Session の3種類があり、選択を間違えると計算量が爆発したり、意味のない結果が出たりします。

🏭 ベルトコンベアの数え方で考える: 流れ続ける製品を数えるには、区切りが必要です。
Tumbling: 「9:00-9:10」「9:10-9:20」と重ならないように区切る。1個の製品は必ず1つの区間に属する。最も単純。
Sliding: 「直近10分間」を1分ごとに計算する。区間が重なるので、1個の製品が10個の区間に数えられる。滑らかな推移が見えるが、計算量が10倍。
Session: 「製品が5分以上流れてこなかったら、そこで区切る」。区切りの位置がデータ次第で決まる——ユーザーの1回の訪問を捉えるのに使う。

① この技術は何を解決するために生まれたのか

  • ① 無界データに集計を定義する — これが本質。「終わりがない」ものの合計は計算できないので、境界を引く
  • ② State の量を有限にする — Window が閉じれば、その状態は捨てられる。Window が無ければ、状態は無限に増え続ける
  • ③ 時間的な文脈を与える — 「1分間に100回」と「1日に100回」は全く意味が違う
  • ④ 意味のある単位で区切る — Session Window は「ユーザーの1回の訪問」というビジネス的な単位を捉える

③ 基本概念 — 3種類の Window

図9-1: 3種類の Window。Sliding は重複度の分だけコストが増え、Session は遅延データによる結合という難問を持つ。

⑤ 実際のシステム構成でどう使われるか

  • Window のサイズは「使う側の粒度」に合わせる — ダッシュボードが5分刻みなら、1秒 Window を作る意味はない
  • 階層化する — 1分 Window で集計 → その結果を1時間・1日に再集計。生イベントから直接1日 Window を作ると State が巨大になる
  • Session Window のコスト — ユーザーごとに状態を持つので、1億ユーザーなら1億個の状態。gap を短くする・アクティブユーザーに限定する等の工夫が必要
  • 出力先は upsert 可能に — 遅延データで Window の結果が更新されるため（10章）
  • Window のキー設計 — keyBy の対象が並列度と State 分散を決める。Hot Key（人気動画・大口顧客）で1タスクだけ詰まる

⑥ メリット

  • 無界データに集計を定義できる — これが唯一かつ根本的な価値
  • State の量が有限になる — Window が閉じれば状態を捨てられる
  • 時間的な文脈が得られる — レート・トレンド・異常の検知が可能に
  • Session Window でビジネス的な単位を捉えられる

⑦ デメリット・トレードオフ

  • Sliding の計算量とState — 重複度に比例して増える。size/slide = 10 なら10倍
  • Session の実装の複雑さ — 遅延データによる Session の結合。既に出力した結果の取り消しが必要になる
  • 境界問題 — Tumbling では境界をまたぐ現象が見えなくなる
  • 結果が出るまでの遅延 — Window が閉じるまで結果が出ない
  • タイムゾーンの罠 — Window の起点が UTC 基準だと、日次集計が9時間ズレる
  • State のサイズ管理 — キー数 × Window 数 × 重複度。設計を誤ると OOM

⑧ 実務での利用例

  • Google Analytics のセッション — 30分の無活動で区切る Session Window そのもの。「1回の訪問」という概念を実装したもの（21章）
  • Netflix — 「1回の視聴セッション」（再生開始から離脱まで）を Session Window で捉え、離脱率や視聴完了率を分析する
  • 異常検知 — Sliding Window の移動平均と現在値の乖離でアラート。「直近5分のエラー率が過去1時間平均の3倍」
  • Booking.com — 「直近1時間の検索数」を Sliding で監視し、需要の急増を検知して価格に反映
  • 典型的な事故① — 「Session Window をユーザーIDでキー分割したが、ボットが1つのIDで大量アクセスし、その1つの状態が数GBに膨らんで OOM」
  • 典型的な事故② — 「1秒 slide の Sliding Window（size 1時間）を作り、重複度3600倍で State が爆発した」

⑨ Googleレベルではどう設計されるか

  • Window を "Where in event time" として抽象化 — Beam のモデルでは、Window は「イベント時刻のどこに割り当てるか」という関数に過ぎない。カスタム Window（カレンダー月・営業日）も自然に定義できる
  • Trigger と分離する — 「どう区切るか（Window）」と「いつ出力するか（Trigger）」を独立させた。これにより「途中経過を1分ごとに出しつつ、最終結果は Watermark 到達時に出す」が表現できる
  • Session の Merging を組み込みで扱う — 遅延データで Session が結合される場合、既存の Window を統合する処理をフレームワークが行う
  • 階層集計を推奨 — 細かい Window の結果を再集計する。巨大 Window を直接作らない

  • Q: 「日次集計が9時間ズレています」 → Window の起点が UTC 基準。タイムゾーンオフセットを明示する

10 Watermark と遅延データ — 「いつ締めるか」という永遠の判断

結論: Watermark とは「このイベント時刻より古いデータは、もう来ないだろう」という推定の宣言です。推定なので必ず間違えます——早すぎればデータを取りこぼし、遅すぎれば結果が出るのが遅れる。正解は「完璧な Watermark を作る」ことではなく、「間違えても壊れない設計にする」ことです。

📮 郵便の締切で考える: 「8月の売上を集計する」とき、いつ締めればいいか。
9月1日に締めると: 8月31日消印の郵便がまだ届いておらず、取りこぼす。
9月30日まで待つと: 正確だが、8月の数字が1ヶ月後にしか分からない。
現実の答え: 「9月5日に速報を出し、9月末に確定値で訂正する」。これが Watermark + allowed lateness + 更新可能な出力先という設計そのものです。
重要なのは「訂正できる仕組みを最初から作っておく」こと——後から入れるのは極めて困難です。

① この技術は何を解決するために生まれたのか

  • ① Window を「いつ閉じるか」を決める — これが本質。Event Time で集計する以上、「もう来ない」という判断が必要になる
  • ② State を有限に保つ — Window を永久に開いておけば取りこぼしはないが、State が無限に増えてシステムが死ぬ
  • ③ 進捗の指標を提供する — 「今、イベント時刻でいうとどこまで処理が進んだか」が分かる
  • ④ 遅延データの扱いを明示的にする — 「捨てる」「別扱いにする」「更新する」を設計として選べるようにする

⑤ 実際のシステム構成でどう使われるか

  • 標準的な構成 — Watermark 30秒 + allowed lateness 5分 + Side Output → S3 → 日次バッチで確定値を作る
  • Watermark が止まる問題 — Kafka partition の一部にイベントが来ないと、Watermark 全体が進まない。withIdleness の設定は実質必須

  • 出力の「確定フラグ」 — 「この Window は暫定値か、確定値か」を出力に含めると、下流が正しく扱える
  • 速報と確定の二層 — ストリームが暫定値、バッチが確定値。乖離率を監視して、Watermark 設定の妥当性を継続的に検証する

⑥ メリット

  • Event Time 集計を実用的にする — Watermark 無しでは Window を閉じられない
  • State を有限に保てる — 閉じた Window の状態を捨てられる
  • 進捗が可視化される — 「イベント時刻でどこまで処理したか」が分かる
  • 遅延データの扱いを明示的に選べる — 捨てる / 待つ / 逃がす

⑦ デメリット・トレードオフ

  • 必ず間違える — 推定なので、早すぎれば取りこぼし、遅すぎれば遅延
  • 遅延と正確さのトレードオフが固定される — 「速いが不正確」か「正確だが遅い」のどちらかしかない
  • Watermark が止まると全体が止まる — idle partition・入力の停止・時計の異常
  • 1件の異常値が全体を壊す — 未来時刻のイベントで Watermark が飛ぶ
  • 出力先の制約になる — upsert 可能でないと allowed lateness が使えない
  • デバッグが難しい — 「なぜこの Window が閉じないのか」の調査は経験を要する

11 State と Checkpoint — 途中経過を、落ちても失わない

結論: State とは「集計の途中経過」であり、Checkpoint とはその定期的なスナップショットです。ストリーム処理が『再起動できる』のは、この2つがあるからです。実務の障害は「State が大きくなりすぎる」「Checkpoint が失敗し続ける」の2つにほぼ集約されます。

🏭 工場の作業台と写真で考える: 組み立て途中の製品が作業台に載っています（＝State）。
停電したら、作業台の上の仕掛品はどうなるか——最初からやり直しですが、材料はもう流れ去っています。
だから定期的に「作業台の写真」を撮っておく（＝Checkpoint）。停電後は、最後の写真の状態から再開し、その時点以降の材料だけをもう一度流せばよい。
重要なのは「写真を撮る時刻と、材料の位置（offset）を一致させる」こと。ズレると、材料が二重に処理されるか、抜け落ちます。

① この技術は何を解決するために生まれたのか

  • ① 障害からの復旧 — これが本質。プロセスが落ちても、集計をゼロからやり直さずに済む
  • ② 「入力と状態の一貫性」を保つ — 「どこまで読んだか（offset）」と「集計の途中経過（state）」を同時に保存することで、二重集計も欠損も防ぐ
  • ③ メモリに乗らない状態を扱う — 1億ユーザーの状態はメモリに載らないので、ディスク（RocksDB）に逃がす
  • ④ スケールの変更を可能にする — 並列度を変えるとき、State を再分配する必要がある

③ 基本概念 と ④ 内部の動き

⑤ 実際のシステム構成でどう使われるか

  • Checkpoint の保存先は S3/GCS — ローカルディスクだとノード障害で失われる
  • Checkpoint 間隔の設計 — 短い = 復旧が速いが処理を圧迫、長い = 復旧時の再処理が増える。1分前後が標準的
  • State のサイズは設計で決まる — 「キーの種類は有限か？」を必ず問う。session_id や request_id をキーにすると無限に増える
  • Savepoint によるデプロイ手順を確立する — これが無いと、デプロイのたびに集計がリセットされる
  • Backpressure の監視 — 処理が追いつかないと Checkpoint も失敗し始める。Checkpoint の失敗は、多くの場合「症状」であって原因ではない

⑥ メリット

  • 障害から自動復旧できる — ストリーム処理を本番で使える唯一の理由
  • Exactly Once Processing が可能 — offset と state を一貫して保存することで実現（ただし外部 sink は冪等性が必要）
  • 大きな状態を扱える — RocksDB により TB 規模
  • Savepoint でアップグレードできる — 状態を保ったままコードを更新
  • 並列度の変更が可能 — State を再分配して、スケールを変えられる

⑦ デメリット・トレードオフ

  • State のサイズ管理が最大の運用課題 — TTL の設定漏れで無限に膨らむ
  • Checkpoint が処理性能を食う — 特に非増分だと、State 全体を毎回書き出す
  • コードの変更が難しくなる — State の互換性。UID の付与とスキーマ進化の設計が必要
  • 復旧に時間がかかる — 大きな State の復元は数分〜数十分
  • ストレージコスト — Checkpoint の保持
  • 「Checkpoint が失敗する」の原因調査が難しい — 実際は Backpressure・GC・ネットワークなど別の問題の症状であることが多い

⑧ 実務での利用例

  • Uber — Flink で TB 規模の State を運用。RocksDB + 増分チェックポイントが前提
  • Netflix — ストリーム処理基盤で Flink を採用。Savepoint によるゼロダウンタイムのアップグレード手順を確立している
  • Booking.com — リアルタイムのパーソナライズで、ユーザーごとの直近行動を State に保持
  • 典型的な事故① — 「State TTL を設定しておらず、1年後に State が2TB になって Checkpoint が失敗し続け、ジョブが復旧できなくなった」
  • 典型的な事故② — 「UID を付けていなかったため、コードにオペレータを1つ追加しただけで Savepoint から復元できず、集計をゼロからやり直した」
  • 典型的な事故③ — 「Checkpoint 間隔を10秒にしたら、Checkpoint 処理が本処理を圧迫して Backpressure が発生し、さらに Checkpoint が失敗する悪循環になった」

⑨ Googleレベルではどう設計されるか

  • Dataflow は State を利用者から隠す — Checkpoint の設定も State Backend の選択も不要。「運用の複雑さをサービス側が引き受ける」という一貫した思想
  • Dynamic Work Rebalancing — 遅いワーカーの作業を自動的に他へ移す。State の再分配も透過的に行う
  • Streaming Engine — State をワーカーから分離し、専用のサービスで管理する。ワーカーがステートレスになるので、スケールが自由になる
  • Chandy-Lamport アルゴリズム — Flink の Checkpoint は、この古典的な分散スナップショットアルゴリズムの応用。「処理を止めずに一貫したスナップショットを取る」という理論的な基盤がある

12 Aggregation — 集計の設計は「何を持ち回るか」で決まる

結論: 集計には「分割して合流できるもの（結合則を満たす）」と「そうでないもの」があります。sum/count/min/max は分散処理と極めて相性が良い。average・median・COUNT(DISTINCT) は素直には分散できず、工夫が必要です。この区別が、分散処理の性能とストリーム処理の可否を決めます。

🏭 工場の在庫カウントで考える: 各倉庫で数えた個数を、最後に足せば全体の個数が出ます（＝結合則を満たす）。
しかし「平均在庫日数」は、各倉庫の平均を平均しても正しくありません——倉庫の規模が違うからです。
正解は「合計と件数の2つを持ち回り、最後に割る」。
さらに難しいのが「何種類の商品があるか（重複を除いたカウント）」: 各倉庫の種類数を足しても、重複が二重に数えられます。これが COUNT(DISTINCT) が分散処理で高価な理由です。

  • Sketch の保存 — HLL の中間状態をテーブルに保存しておけば、任意期間の UU がマージだけで出せる。これは実務で極めて効果が大きい

  • 重複した集計テーブル — 似た集計が乱立し、どれが正か分からなくなる

⑩ システム設計面接ではどう問われるか

  • Q: 「1億ユーザーのユニークカウントを出したい」 → HyperLogLog。誤差1〜2%、メモリ数KB固定。正確な値が必要ならバッチで COUNT(DISTINCT)

  • Q: 「クエリコストを下げるには？」 → 階層集計。生データから直接ではなく、段階的に積み上げる
  • Q: 「ストリームで中央値を出せますか？」 → 正確には困難（全要素を State に持つ必要がある）。t-digest 等の近似を使う

13 Kafka Streams — 「クラスタを持たない」ストリーム処理

結論: Kafka Streams は「ただの Java ライブラリ」です。専用のクラスタが不要で、アプリケーションに組み込んで普通にデプロイするだけ。Kafka を既に使っているなら、追加の運用コストがほぼゼロで始められるのが最大の価値。代わりに、Kafka の外のデータソースは扱えず、大規模な State や複雑な処理には向きません。

🏭 「専用工場」と「作業台の追加」で考える: Flink は専用の工場（クラスタ）を建てて運用するやり方です。
Kafka Streams は「今あるオフィスの机の上でやる」——既存のアプリに1つライブラリを足すだけ。ジョブマネージャもタスクマネージャも要りません。
スケールも単純: アプリのインスタンスを増やすだけ。Kafka の Consumer Group の仕組みがそのまま並列度になります。
ただし「材料は Kafka から来るもの限定」——DB やファイルを直接ソースにはできません。

① この技術は何を解決するために生まれたのか

  • ① ストリーム処理から「クラスタ運用」を消す — これが本質。Flink/Spark はクラスタの構築・監視・アップグレードが必要。Kafka Streams は普通のアプリと同じようにデプロイできる
  • ② Kafka とのシームレスな統合 — State も changelog topic として Kafka に保存する。別のストレージが要らない
  • ③ マイクロサービスにストリーム処理を組み込む — 「集計するだけのサービス」を普通のサービスとして書ける
  • ④ Exactly Once の簡便な実現 — Kafka Transactions（read-process-write）をライブラリが内包している

③ 基本概念 と ④ 内部の動き

  • 向かないケース — ①Kafka 以外のソース（DB・ファイル）②数百GB以上の State ③複雑な多段処理 ④SQL で書きたい
  • ksqlDB という選択肢 — Kafka Streams の上に SQL インターフェースを載せたもの。簡単な集計なら、コードを書かずに済む

⑥ メリット

  • クラスタが不要 — 最大の価値。運用コストが劇的に低い
  • 既存のデプロイ基盤に乗る — CI/CD・監視・ログが既存のものを使える
  • Kafka との統合が完璧 — State も changelog topic として Kafka に保存
  • Exactly Once（Kafka 内）が簡単 — 設定1行
  • スケールが単純 — インスタンスを増やすだけ
  • KStream/KTable の抽象が優れている — 「イベント」と「状態」の区別が言語レベルで表現される

⑦ デメリット・トレードオフ

  • Kafka 以外のソース/シンクが扱いにくい — DB を直接読めない（Kafka Connect が必要）
  • 大規模な State に弱い — changelog からの復元に時間がかかる。数百GBになると復旧に数十分
  • Java/Scala のみ — Go や Python からは使えない
  • 複雑な処理の表現力は Flink に劣る — CEP・複雑なイベント時間処理
  • repartition topic が見えないところで増える — ディスクと帯域を消費
  • 並列度が partition 数に縛られる — 後から増やすと State の再構築が必要

⑧ 実務での利用例

  • マイクロサービス間の集計 — 「注文イベントを集計して、リアルタイムの売上を別サービスに公開する」
  • データのエンリッチメント — イベントにマスタ情報を join して付与する。KStream × KTable の最も典型的な用途
  • Booking.com — 検索イベントの正規化・エンリッチメント。「Kafka から読んで Kafka に書く」処理には Kafka Streams が最適
  • 不正検知の前段 — 「同一IPからの検索回数」をカウントし、閾値を超えたら別 topic へ
  • 典型的な事故 — 「APPLICATION_ID を変更してデプロイしたら、State がゼロから作り直され、changelog topic の全データを再処理して数時間止まった」

⑩ システム設計面接ではどう問われるか

  • Q: 「Kafka Streams と Flink、どちらを使いますか？」 → 「Kafka から読んで Kafka に書くだけで、State が数十GB以下なら Kafka Streams。クラスタが不要な運用の軽さが決定的」
  • Q: 「KStream と KTable の違いは？」 → 「出来事の連続」と「キーごとの現在の状態」。同じ topic でもどちらとして読むかで結果が変わる
  • Q: 「State はどこに保存されますか？」 → ローカルの RocksDB + バックアップとして Kafka の changelog topic（compacted）。別のストレージが不要なのが利点
  • Q: 「スケールさせるには？」 → インスタンスを増やす。ただし partition 数が上限
  • Q: 「障害時の復旧が遅いです」 → State が大きい。Standby Replica を設定する

14 Apache Flink — 真のストリーム処理エンジン

結論: Flink は「1件ずつ即座に処理する」真のストリーム処理エンジンです。Event Time・Watermark・State・Checkpoint の全てが一級市民として設計されており、ミリ秒レイテンシと大規模 State を両立できる。代償はクラスタ運用の複雑さ——State と Checkpoint の管理は片手間ではできません。

🏭 専用の生産ラインで考える: Spark のマイクロバッチが「1分ごとに材料をまとめて投入する」のに対し、Flink は「材料が来た瞬間にラインが動く」。
そして Flink は「時間」の扱いに特化した設計: 材料に押された製造日時（Event Time）で全てを判断し、「いつ締めるか」（Watermark）を明示的に管理します。
代わりに、この専用ラインは自分で建てて維持しなければなりません——ジョブマネージャ、タスクマネージャ、チェックポイントストレージ、監視。

① この技術は何を解決するために生まれたのか

  • ① 真の低レイテンシ — これが本質。マイクロバッチではなく、1件ずつ処理する。ミリ秒単位の応答が可能
  • ② Event Time 処理の完全なサポート — Watermark・allowed lateness・Side Output が言語レベルで用意されている
  • ③ 大規模 State の管理 — RocksDB + 増分チェックポイントで TB 規模
  • ④ 正確な障害復旧 — 分散スナップショット（Chandy-Lamport）による Exactly Once Processing
  • ⑤ バッチとストリームの統一 — 同じ API でバッチも書ける（「バッチは有界ストリーム」）

③ 基本概念 と ④ 内部の動き

  • Event Time 処理が最も充実 — Watermark・allowed lateness・Side Output・Timer

  • Exactly Once Processing — 分散スナップショットによる正確な復旧
  • SQL からProcessFunction まで、API の階層が揃っている
  • バッチとストリームの統一 — 同じ API で両方書ける
  • CEP ライブラリを標準で持つ（16章）

  • クラスタの運用が重い — 最大の障壁。State・Checkpoint・Backpressure の理解が必須
  • 学習コストが高い — Watermark・State・Savepoint・Barrier

  • デプロイが特殊 — Savepoint 経由の手順を確立する必要がある
  • コストが高い — 常時稼働 + 大きめのメモリ
  • 「Flink を入れたが誰も運用できない」 — 実務で最も多い失敗

  • Netflix — リアルタイムの障害検知・視聴イベントの処理。Flink のマネージドプラットフォームを社内に構築している
  • Alibaba — Flink の主要な開発元（Blink として大幅に改良し、本家にマージ）。セール時の秒間数億イベントを処理

  • 典型的な事故② — 「UID を付けずにデプロイし、Savepoint から復元できず、State をゼロから作り直した」

⑨ Googleレベルではどう設計されるか

  • Dataflow が同等の位置づけ — Flink と同じく Event Time を一級市民として扱うが、クラスタ・State・Checkpoint を利用者から完全に隠す
  • Flink の理論的基盤も Google 由来 — Beam の Dataflow Model 論文が、Flink の Event Time 処理設計に大きく影響している。Flink は Beam のランナーとしても動作する
  • Streaming Engine — State をワーカーから分離。ワーカーがステートレスになり、スケールと復旧が劇的に単純になる
  • 示唆 — Flink を選ぶなら、マネージドサービスを強く検討する。自前運用の価値は、よほど特殊な要件がない限り薄い

⑩ システム設計面接ではどう問われるか

  • Q: 「Spark Streaming と Flink の違いは？」 → Spark はマイクロバッチ（最小レイテンシ = バッチ間隔）、Flink は真のストリーミング（ミリ秒）。加えて Event Time 処理の充実度
  • Q: 「Flink はどうやって障害から復旧しますか？」 → Checkpoint Barrier をデータに挿入し、処理を止めずに一貫したスナップショットを取る。この説明ができると理解が深いと判断される
  • Q: 「一定時間イベントが来なかったことを検知したい」 → Window では書けない。ProcessFunction + Timer
  • Q: 「Flink を選ぶ理由は？」 → ①ミリ秒レイテンシが必要 ②大規模 State ③複雑な Event Time 処理 ④CEP。これらが不要なら Kafka Streams か Spark で十分
  • Q: 「Backpressure が発生しています」 → 下流のボトルネックを特定する（sink の書き込み・外部API・GC）。Checkpoint 失敗は多くの場合これの症状

15 Apache Beam / Dataflow — 「バッチはストリームの特殊ケース」という統一モデル

結論: Beam は「1つのコードで、バッチもストリームも書ける」プログラミングモデルであり、実行エンジンから独立しています。最大の貢献は実装ではなく『考え方の整理』——What / Where / When / How という4つの問いに分解したことで、ストリーム処理の議論が明快になりました。実務での採用判断は「GCP を使うか」にほぼ帰着します。

📐 設計図と工場の分離で考える: Beam は「設計図の書き方」だけを定めた規格です。
同じ設計図を、Dataflow という工場でも、Flink という工場でも、Spark という工場でも生産できる。
そして Beam の最も重要な洞察はこれ: 「倉庫にある材料（バッチ）とベルトコンベアで流れてくる材料（ストリーム）は、『終わりがあるかどうか』しか違わない」。
だから同じ設計図で両方作れる——これが Beam の中心思想です。

① この技術は何を解決するために生まれたのか

  • ① バッチとストリームの二重実装を消す — これが本質。Lambda Architecture（3章）の「同じロジックを2回書く」問題への根本的な回答
  • ② ストリーム処理の議論を構造化する — What / Where / When / How の4分解により、それまで曖昧だった議論が明快になった
  • ③ 実行エンジンからの独立 — ベンダーロックインを避ける（実際にどこまで機能するかは議論があるが）
  • ④ Google 内部の知見の公開 — MillWheel / FlumeJava で得た「大規模ストリーム処理の正しいモデル」を業界に提示した

  • Python / Java / Go SDK — 言語の選択肢がある

  • 可搬性は理想ほどではない — Runner ごとに対応機能とパフォーマンスに差がある
  • GCP 以外での採用が少ない — コミュニティとナレッジが GCP に偏る
  • デバッグが難しい — 抽象度が高く、実際の実行が見えにくい

  • Spotify — GCP 移行時に Dataflow を全面採用。Scio という Scala 向け Beam ラッパーを自社開発してOSS化した

  • Dataflow Templates — 「Pub/Sub → BigQuery」のような定型パイプラインを、コードを書かずに実行できる

  • The Dataflow Model 論文（2015） — ストリーム処理の設計に関する、最も重要な文献の1つ。Flink・Spark の Event Time 処理設計にも影響を与えた

  • Watermark をヒューリスティックと定義 — 「完璧な締め切りは存在しない」ことを前提にモデルを組んだ
  • Streaming Engine による State の分離 — ワーカーをステートレスにし、自動スケールを可能にした
  • 示唆 — Beam を採用しなくても、4つの問いによる設計の整理は全ての現場で有効

⑩ システム設計面接ではどう問われるか

  • Q: 「バッチとストリームの二重実装をどう避けますか？」 → Beam / Dataflow による統一モデル、または Flink の統一API。「バッチは有界ストリームの特殊ケース」という視点
  • Q: 「速報値と確定値を両方出したい」 → Beam の Trigger（early / on-time / late）。1つのパイプラインで両方出し、PaneInfo で下流が判別する
  • Q: 「Accumulating と Discarding の違いは？」 → 累積値を出すか差分を出すか。Discarding は1件でも欠けると永久にズレるので、通常は Accumulating + upsert
  • Q: 「ストリーム処理の設計をどう進めますか？」 → What / Where / When / How の4つを先に埋める。この答え方をする候補者は、設計の訓練を受けていると評価される

16 CEP（Complex Event Processing）— 「パターン」を検知する

結論: CEP とは「単発のイベントではなく、複数イベントの『並び方』を検知する」技術です。「A の後に B が起き、C が起きなかったら異常」といった時間的なパターンを宣言的に書けます。実装は状態機械（NFA）であり、State の量とパターンの複雑さが直結します。

🚨 工場の品質管理で考える: 「不良品が1個出た」は単発のイベント——閾値監視で足ります。
「不良品が3個連続で出た」「温度が上がった後10分以内に圧力が下がった」は、パターンです。
さらに難しいのが「起きなかったこと」の検知: 「ログインの後、30分以内に操作が無かった」。『何も来ない』を検知するには、タイマーを持つ必要があります。
これが CEP が単純な集計より難しい理由です。

① この技術は何を解決するために生まれたのか

  • ① 時間的な順序を持つパターンの検知 — これが本質。単純な集計や閾値では表現できない
  • ② 不正・異常の検知 — 「短時間に複数国からログイン」「カード決済の直後に高額購入」
  • ③ 「起きなかったこと」の検知 — 「注文の後、30分以内に発送されなかった」（タイムアウト検知）
  • ④ ビジネスプロセスの監視 — 「決済 → 在庫確保 → 発送」の各ステップが期限内に進んでいるか
  • ⑤ ルールを宣言的に書く — 状態機械を手書きすると、条件が増えたときに保守不能になる

⑤ 実際のシステム構成でどう使われるか

  • 不正検知の中核 — カード不正・アカウント乗っ取り・ボット検知
  • SLA / プロセス監視 — 「注文から発送までが期限内か」「決済から確定までが進んでいるか」

  • ML との使い分け — CEP は「明示的なルールが書ける」場合、ML は「特徴が複雑で人が書けない」場合。実務では両方を組み合わせる（CEP で候補を絞り、ML でスコアリング）
  • ルールの管理 — ルールが増えると保守不能になる。ルールを設定として外部化し、非エンジニアでも変更できる仕組みを作ることが多い

⑦ デメリット・トレードオフ

  • State が膨らむ — 同時進行の部分一致数に比例。within（タイムアウト）の設定は必須
  • 組み合わせ爆発 — followedByAny や繰り返しパターンで、一致数が指数的に増える
  • 遅延データでパターンが崩れる — 順序が前提なので、Watermark の設定がシビア
  • ルールの保守 — 数十のルールが絡み合うと、変更の影響が読めなくなる
  • 誤検知（False Positive）の調整 — 厳しくすると見逃し、緩くするとアラート疲れ。運用チームとの継続的な調整が必要

  • 決済の不正検知 — 「短時間に少額決済が連続 → カードテスティング」「異なる国から同一カード」
  • Booking.com — 「同一IPから短時間に大量の検索 → スクレイピング」の検知
  • Netflix — 「同一アカウントが同時に複数地域で再生 → アカウント共有」の検知
  • Uber — 「乗車リクエストの後、一定時間マッチングされなかった」の検知と対処
  • 典型的な事故 — 「within を設定せずにパターンを定義し、State が無限に増えてジョブが落ちた」

⑩ システム設計面接ではどう問われるか

  • Q: 「不正検知をどう実装しますか？」 → 単純な閾値なら Window 集計、順序を含むパターンなら CEP、特徴が複雑なら ML。3つを使い分けられることを示す
  • Q: 「『30分以内に発送されなかった』を検知するには？」 → Timer を張って、発送イベントが来たら消す。Window では書けないことに気づけるかが分かれ目
  • Q: 「CEP の State はどう管理しますか？」 → within（タイムアウト）を必ず設定する。State は同時進行の部分一致数に比例する
  • Q: 「next と followedBy の違いは？」 → 直後か、間に他のイベントが挟まってよいか。実務ではほぼ followedBy

18 分析基盤の全体設計 — 「信頼できる数字」を作る仕組み

結論: 分析基盤の価値は「データがあること」ではなく「その数字が信頼されていること」です。技術的に正しく動いていても、『この数字合ってる？』と毎回聞かれる基盤は失敗。信頼を作るのは、レイヤ設計・データ品質テスト・指標定義の一元化・系譜の可視化の4つです。

📚 図書館の運営で考える: 蔵書を増やすことは簡単です。難しいのは「探せること」「正しく分類されていること」「誰が責任者か分かること」。
誰も管理しない図書館は、本が増えるほど価値が下がります——目当ての本が見つからないからです。
そして最も重要なのが「この本の内容は正しいか」の保証。分析基盤では、これがデータ品質テストと指標定義の一元化にあたります。

① この設計は何を解決するために生まれたのか

  • ① 「その数字、合ってる？」を無くす — これが本質。信頼されない数字は、存在しないのと同じ
  • ② 同じ指標が複数の答えを持つ問題を消す — 「営業のDAUと分析チームのDAUが違う」
  • ③ 変更の影響範囲を把握する — 「このテーブルを消したら何が壊れるか」
  • ④ 障害を早期に検知する — 上流の異常が、ダッシュボードに出る前に気づく
  • ⑤ 誰でも安全に使えるようにする — アナリストが自分でデータを探し、正しく使える

⑦ トレードオフ

  • 層を分けるとコストが増える — 同じデータが3回保存される。ただしストレージは安く、作り直しは高いので、ほぼ常に元が取れる
  • 品質テストは実行時間を増やす — テストが多すぎるとパイプラインが遅くなる。重要なテーブルに絞る
  • 指標定義の一元化は組織的な合意が必要 — 技術だけでは解けない。「誰が定義を決めるか」を先に決める
  • カタログの陳腐化 — 手動で書く説明は必ず古くなる。自動で取れる情報（系譜・利用状況）を中心にする
  • 厳格すぎるガバナンスは使われなくなる — アナリストが「面倒だから自分でスクリプトを書く」ようになったら本末転倒

19 クエリを速く・安くする — 列指向・パーティション・事前集計

結論: 分析クエリのコストは「読んだデータ量」でほぼ決まります。だから最適化とは『読まなくて済むようにすること』の一点に尽きる——列指向で不要な列を読まず、パーティションで不要な行を読まず、事前集計でそもそも生データを読まない。この3つを知らないと、請求が10倍になります。

📚 図書館で調べ物をするときで考える: 「2026年8月に出版された本の著者一覧」が欲しいとき——
最悪: 全ての本を1冊ずつ開いて、全ページを読む（＝行指向 + フルスキャン）。
列指向: 「著者名だけが書かれた索引」を読む。本文は開かない。
パーティション: 「2026年8月の棚」だけを見る。他の棚には行かない。
事前集計: 「月別の著者一覧」が既に作られていて、それを見るだけ。
この3つを組み合わせると、読む量が1/1000になることも珍しくありません。

  • 事前集計は柔軟性を失う — 集計した粒度でしか分析できない。生データを残しておくことで回避（Raw 層）
  • パーティションが細かすぎると逆効果 — メタデータの処理が支配的になる
  • 列指向は書き込みが遅い — 1行ずつの更新には向かない。分析用途に特化した形式
  • クラスタリングは書き込み時にコストがかかる — 並べ替えが必要
  • 最適化しすぎると保守できなくなる — 「なぜこの構造なのか」が分からないテーブルが残る

20 ユースケース① Netflix レコメンド — バッチとストリームの役割分担

結論: レコメンドは「重い計算をバッチで事前に済ませ、直前の行動だけをストリームで反映する」ハイブリッドが答えです。全てをリアルタイムにするのは技術的にも経済的にも不可能。「どこまでを事前計算し、どこからを実行時にやるか」の線引きが設計の核心です。

図20-1: レコメンドの3層構造。「候補生成（バッチ）」と「再ランキング（オンライン）」の分離が設計の要。

📊 データパイプラインとしての要点

  • 特徴量の整合性（Training-Serving Skew） — 学習時とサービス時で特徴量の計算方法が違うと、モデルの性能が本番で出ない。実務で最も多い ML の失敗。Feature Store で計算ロジックを共通化する
  • 再生イベントの設計 — start / progress / complete / abandon。「途中で止めた」は「見た」なのか「つまらなかった」なのか——イベント設計がモデルの質を決める
  • オフライン評価とオンライン評価 — バッチで計算した精度と、実際のA/Bテストの結果は乖離する。最終的な判断はA/Bテスト
  • Event Time の重要性 — 「いつ見たか」で重み付けする（新しい視聴ほど重視）。Processing Time で学習すると、遅延データが混乱を生む
  • コールドスタート — 新規ユーザー・新作には履歴がない。人気順・コンテンツ属性ベースのフォールバックを必ず用意する

⑩ 面接での問われ方

  • Q: 「レコメンドシステムを設計してください」 → 3層（オフライン学習 / ニアライン更新 / オンライン再ランキング）。「リアルタイムで全部計算します」は非現実的
  • Q: 「なぜ全部リアルタイムにしないのですか？」 → モデル学習は数時間かかり、候補のスコアリングも100msでは終わらない。かつ、好みは1日で大きく変わらない
  • Q: 「直前に見た作品が推薦され続けます」 → ニアライン層で候補リストから除外する。バッチの更新を待つ必要はない
  • Q: 「学習時と本番で精度が違います」 → Training-Serving Skew。特徴量の計算ロジックが分岐している。Feature Store で統一する

21 ユースケース② Google Analytics — 速報と確定値の分離

結論: Google Analytics は「リアルタイムレポート（速報）」と「標準レポート（確定値）」を、別の製品機能として明確に分けています。これは3章で述べた『速報値と確定値を混同しない』の、最も洗練された実装例。「データ処理には最大24〜48時間かかる場合があります」という但し書きこそが、Watermark と遅延データの設計そのものです。

図21-1: アクセス解析基盤の2経路。「速報」と「確定値」を別機能として提供する設計が最大の学びどころ。

📊 データパイプラインとしての要点

  • GA4 の BigQuery エクスポート — 生のイベントデータをそのまま出す（ELT 的）。ユーザーが自分で好きな定義で集計できる。その代わり「GA画面の数字と自分で集計した数字が違う」問題が起きる——集計ロジック（セッション化・アトリビューション）が違うため
  • ネストした構造 — イベントパラメータが配列として入る。UNNEST を使わないと取り出せず、使い方を誤るとスキャン量が爆発する
  • パーティションの罠 — events_YYYYMMDD というワイルドカードテーブル。_TABLE_SUFFIX で絞らないと全期間をスキャンして請求が跳ねる（19章）
  • サンプリング — 大規模なプロパティでは、レポートが標本抽出になる。これは12章の「全体的な集計は高価」への現実的な妥協
  • セッション化の定義 — 30分の無活動、日付をまたぐ、参照元が変わる。この定義が違うと数字が合わない——指標定義の一元化（18章）の重要性の実例

⑩ 面接での問われ方

  • Q: 「アクセス解析基盤を設計してください」 → 収集（時刻検証・ボット除去）→ 速報（ストリーム）と確定（バッチ）の2経路 → セッション化は確定側で
  • Q: 「リアルタイムの数字と日次レポートが違います」 → 仕様。遅延データとセッション化の有無。「別の指標として提供する」のが正しい設計
  • Q: 「セッションをどう定義しますか？」 → Session Window（30分の無活動で区切る）。遅延データでセッションが結合されうることに触れられると強い（9章）
  • Q: 「ユニークユーザー数をどう出しますか？」 → 速報は HyperLogLog、確定値はバッチで正確に。日次UUを月で合計してはいけない（12章）
  • Q: 「1日数兆イベントをどう捌きますか？」 → エッジでの受信 → Pub/Sub → 収集層でのフィルタ（ボット・不正）→ 列指向で保存 → 事前集計

22 ユースケース③ Airbnb 分析基盤 — 「指標の定義」を組織的に解く

結論: Airbnb の分析基盤で最も学ぶべきなのは、技術ではなく「同じ指標が部署ごとに違う」という組織的問題への回答です。Minerva という指標定義プラットフォームで、指標を1箇所にコードとして定義し、そこから集計テーブルを自動生成する。これは18章のセマンティックレイヤーの、最も本格的な実装例です。

図22-1: 指標定義の一元化。技術的には単純だが、組織的な効果が極めて大きい設計。

📊 データパイプラインとしての要点

  • Airflow は Airbnb 発 — 数千のバッチジョブを管理する必要から生まれた。「依存関係をコードで書く」という発想が業界標準になった
  • データカタログ（Dataportal） — 「このテーブルは誰が作り、誰が使い、どれくらい信頼できるか」を可視化。数万テーブル規模になると、カタログ無しでは誰もデータを見つけられない
  • ほぼ全てがバッチ — 宿泊予約の分析にリアルタイム性はほぼ不要。日次で十分。これは「ストリームは必要な場所にだけ」の好例
  • CDC でサービスDBから取り込む — SpinalTap（自社製 CDC）で MySQL の binlog を Kafka へ（前作「Messaging」19章）
  • データ品質のスコアリング — テーブルごとに「信頼度」を計算して表示し、アナリストが「使ってよいデータ」を判断できるようにする

⑩ 面接での問われ方

  • Q: 「部署ごとに数字が違います。どうしますか？」 → 指標定義の一元化（セマンティックレイヤー）。「定義をコードとして1箇所に置き、全ての利用者がそれを参照する」
  • Q: 「なぜ数字がズレるのですか？」 → キャンセルの扱い・基準日・テストデータの除外・タイムゾーン。「誰も間違っていないのにズレる」ことを説明できると理解が深い
  • Q: 「数千のバッチジョブをどう管理しますか？」 → DAG によるオーケストレーション（Airflow）+ SLA + オーナーシップ + カタログ
  • Q: 「A/Bテストの分析基盤は？」 → 統一された指標定義 + 統一された統計処理。実験ごとに独自集計を許すと、結果が比較できなくなる

23 ユースケース④ Booking.com 価格分析 — バッチで学び、ストリームで追随する

結論: 価格分析は「需要予測モデルの学習（重い・日次バッチ）」と「競合価格・在庫変動への追随（軽い・数分）」に分解できます。秒単位のリアルタイム性は不要——価格は数分遅れて変わっても事業への影響はほぼありません。むしろ重要なのは「価格が異常な値にならないこと」の検知です。

図23-1: 価格分析の2層構造。学習はバッチ、短期変動への追随はストリーム、そして出力の妥当性チェックが必須。

📊 データパイプラインとしての要点

  • 検索ログの価値 — 「予約されなかった検索」にこそ情報がある。「この価格では売れなかった」というデータが、価格弾力性の推定に不可欠
  • 因果推論の難しさ — 「価格を下げたから売れた」のか「売れない日だから価格を下げた」のか。相関と因果を分けるには、A/Bテスト（価格実験）が必要
  • 粒度の設計 — 施設 × 日付 × リードタイム × 部屋タイプ。組み合わせると数十億行になるので、階層集計とパーティション設計が生命線（19章）
  • Event Time の重要性 — 「いつ検索されたか」ではなく「いつの宿泊日を検索したか」。2つの時間軸があることが、この領域の分析を難しくする
  • 実験基盤との統合 — 価格変更の効果測定はA/Bテストで行う。「価格を上げたら予約が減った」を、季節変動と分離して測る必要がある

⑩ 面接での問われ方

  • Q: 「動的価格設定の基盤を設計してください」 → モデル学習は日次バッチ、短期変動の補正は Micro-batch、出力の妥当性チェックは必須
  • Q: 「リアルタイムに価格を変えたい」 → 「何分遅れたら損失が出ますか？」と聞き返す。多くの場合、数分で十分
  • Q: 「価格が異常な値になったらどうしますか？」 → 配信前に妥当性チェック（範囲・前回比）→ 異常なら配信を止めて前回値にフォールバック。この観点を自分から出せると評価が高い
  • Q: 「数十億行のテーブルをどう扱いますか？」 → 階層集計 + パーティション + クラスタリング（19章）
  • Q: 「価格変更の効果をどう測りますか？」 → A/Bテスト。観察データだけでは因果が分からない（季節変動との交絡）

24 9社の設計を読む — 制約の違いが設計を決める

結論: 各社の設計は「その会社の制約への答え」です。データ量・鮮度要件・正確性要件・組織規模の4つが違えば、正解も変わります。「Netflix が Iceberg を使っているから」で真似すると、必要のない複雑さだけを引き受けることになります。

図24-1: データ量と鮮度要件のマトリクス。左下（バッチ + DWH）で足りるケースが圧倒的に多い。

🔍 Google — 「対話的なクエリ」という発明

  • MapReduce（2004） — 分散処理を「誰でも書ける」ものにした。ただし Google 内部ではとうに卒業している
  • Dremel（2010）→ BigQuery — 列指向 + ツリー状の集約で、ペタバイトを数秒でクエリする。「バッチで数十分」を「対話で数秒」に変えた。これは MapReduce とは全く別系統の発明
  • Dataflow / Beam（2015） — 「バッチはストリームの特殊ケース」という統一モデル。4つの問い（What/Where/When/How）による設計の整理は、業界全体に影響を与えた
  • Spanner — 地理分散でも強い整合性。分析基盤の上流（業務DB）を強くすることで、下流の複雑さを減らす
  • 学べること — 「クラスタ運用を利用者に押し付けない」という一貫した思想。BigQuery も Dataflow も、サイジングもチューニングも不要にした

🔍 AWS — 「組み合わせて作る」エコシステム

  • S3 — Data Lake の事実上の標準。「ストレージと計算の分離」を可能にした最大の要因
  • EMR / Glue / Athena — Spark・ETL・SQL を個別のサービスとして提供。Google の統合型と対照的に、組み合わせの自由度が高い（＝設計の責任も利用者側）
  • Redshift — MPP の DWH。近年はストレージと計算の分離（RA3）で BigQuery に近づいた
  • Kinesis — Kafka 相当のマネージドサービス。運用ゼロだが、Kafka ほどのエコシステムは無い
  • 学べること — 「S3 を中心に据える」設計が最も移植性が高い。Iceberg/Delta と組み合わせれば、計算エンジンを後から変えられる

🔍 Netflix — Iceberg を生んだ「規模の限界」

  • Apache Iceberg — 「Hive のパーティション管理が数百万ファイル規模で破綻した」という実問題から生まれた。メタデータ層でファイル集合を管理し、ACID・タイムトラベル・スキーマ進化を実現（7章）
  • Keystone パイプライン — 1日数兆イベント。分析用データは一部の欠損を許容し、課金・視聴権限のような critical なものだけ厳密に扱う
  • データの重要度で保証レベルを分ける — 「全部を同じ厳密さで扱う」のは、この規模では経済的に不可能
  • レコメンド — オフライン（バッチ学習）/ ニアライン（ストリーム更新）/ オンライン（実行時ランキング）の3層（20章）
  • 学べること — 「データの重要度で保証レベルを分ける」。全部を厳密にするのは、大規模では不可能

🔍 Uber — 「増分更新」という難題への回答

  • Apache Hudi — 「巨大なテーブルの一部の行だけを更新したい」という要求から生まれた。Data Lake では UPDATE が実質不可能だったため
  • Flink の大規模運用 — サージプライシング・不正検知・ETA計算。Uber は「秒単位の鮮度が事業に直結する」稀な例——ドライバーの位置が数分古いと配車が成立しない
  • データの種類で処理を分ける — 位置情報（高頻度・欠損許容）と配車リクエスト（低頻度・厳密）
  • 学べること — 「その鮮度が本当に事業に必要か」を問う。Uber は必要だが、多くの事業はそうではない

🔍 Airbnb — 「組織的な信頼」を技術で作る

  • Apache Airflow — Airbnb 発。数千のバッチジョブを管理する必要から生まれ、業界標準になった
  • Minerva（指標定義プラットフォーム） — 「同じ指標が部署ごとに違う」という組織的問題への技術的回答。指標を定義すると集計テーブルが自動生成される（22章）
  • Dataportal（データカタログ） — 数万テーブル規模では、カタログ無しでは誰もデータを見つけられない
  • ほぼ全てがバッチ — 宿泊予約の分析にリアルタイム性はほぼ不要。日次で十分と割り切っている
  • 学べること — 分析基盤の最大の課題は技術ではなく「信頼」。指標定義の一元化は、多くの組織で最も効果が大きい投資

🔍 Booking.com — 実験駆動の意思決定基盤

  • 常時数百〜数千のA/Bテストを並行実行 — 「意思決定を実験で行う」文化を、データ基盤が支えている
  • 実験の効果測定を統一パイプラインで — 実験ごとに独自集計を許すと、結果の比較ができず、実験の質が担保されない（22章）
  • 価格分析 — 需要予測モデルは日次バッチ、競合価格への追随は数分（23章）
  • 異常検知の重視 — 「価格が0円になった」を配信前に止める。データパイプラインの出力が直接ビジネスに影響する場合、妥当性チェックが必須
  • 学べること — 「分析基盤は意思決定の質を担保する仕組み」という視点。数字を出すことがゴールではない

🔍 Twitter(X) / Instagram — 「速度と可用性が正確さに勝る」領域

  • トレンドの算出 — 「今何が話題か」は数分遅れると価値が落ちる。正確な数字より、速く出ることが重要
  • 近似アルゴリズムの積極利用 — Count-Min Sketch / HyperLogLog による Top-K とユニークカウント（12章）
  • Instagram の割り切り — エンジニア数十人で数億ユーザーを支えた。枯れた技術（Celery + RabbitMQ + PostgreSQL）を正しく使うことの強さ
  • 学べること — 「正確さが常に最優先ではない」。指標の性質によって、速度・可用性・正確さの優先順位は変わる

🔍 YouTube — 「即時の概算」と「後からの確定」

  • 再生回数のカウント — 一定期間は概算値、後から確定する。不正クリックの除外も含めて非同期で処理される
  • 視聴ログは兆オーダー — サンプリングと欠損許容で捌く
  • アップロード後の処理 — トランスコードは解像度ごとに別ジョブ。低画質から順次公開
  • 学べること — 「ユーザーに見せる数字が概算でよい場面は多い」。正確さのコストを、価値と見合わせて判断する

各問、まず自分で答えてから開いてください。「なんとなく分かる」と「説明できる」の間には大きな差があります。7割を自力で説明できなければ、該当章に戻ることを推奨します。

Part 1: バッチとストリームの基礎（1〜6）

Q1. Batch と Stream の本質的な違いは何ですか
扱うデータが有界か無界か。それ以外に本質的な差はありません。
有界（終わりが確定している）なら全件が揃うので集計が定義でき、正確な答えが出せる。無界なら「全件」が存在しないので、Window で人工的な境界を引く必要が生まれる。
この視点が「バッチはストリームの特殊ケース」という Beam の統一モデルに繋がります。（1章・2章・15章）
Q2. バッチ処理の最大の価値は何ですか
再実行できること。入力が保存されているので、ロジックを直せば過去も全部作り直せる（Backfill）。
次点で正確さ（全件が揃うので COUNT(DISTINCT) も中央値も正確）と安さ。
ストリームでは「バグを直して過去を再計算」が原理的に困難——これが実務における最大の差です。（1章）
Q3. バッチジョブで最も重要な設計要件は？
冪等性。「何度実行しても同じ結果になる」こと。
実装はパーティション単位の上書き（INSERT OVERWRITE PARTITION / MERGE）。単純な INSERT だと、再実行で行が二重になり、途中失敗で部分的に書かれた状態が残る。
「1回の実行 = 1つのパーティションを丸ごと作り直す」が鉄則。（1章）
Q4. スケジュール起動だけでバッチを組むと何が問題ですか
上流のデータが遅れた日に、空の結果や不完全な結果を出す。
対策はSensor（データの到着待ち）。「03:00に実行」ではなく「入力ファイルの _SUCCESS が置かれたら実行」にする。
加えて品質チェック（行数が前日比 ±X% 以内か）を通ってから公開する。壊れた数字を配るくらいなら、古い数字のほうがマシ。（1章・18章）
Q5. ストリーム処理の4つの根本問題は？
①「全件」が存在しない（→ Window で境界を引く）②順序が保証されない（→ Event Time + Watermark）③状態を持つ必要がある（→ State + Checkpoint）④一度出した結果を訂正できない（→ allowed lateness + upsert 可能な出力先）。
8〜11章は全て、この4つへの対処法です。（2章）
Q6. キューがあればスパイクを全部吸収できますか
できません。「平均処理能力 > 平均流入」が絶対条件。恒常的に流入が上回るなら、滞留が無限に伸びるだけ。
加えて「遅延が許容される処理か」「溜まったことに気づけるか（監視）」の2つも前提。（2章）

Part 2: 処理基盤（7〜12）

Q7. MapReduce で最も時間がかかるのはどこですか
Shuffle。ジョブ時間の50〜80%を占めます。
理由は、全ノード間でデータが移動し、ディスクへの書き出しとソートが発生するため。
減らす手段は4つ: ①事前集約（Combiner）②不要カラムの削除 ③フィルタの前倒し ④Broadcast Join。この構造は Spark でも BigQuery でも全く同じ。（4章）
Q8. average を Combiner で計算できますか
そのままではできません。部分平均の平均は全体平均になりません（各グループのサイズが違うため）。
(sum, count) のペアを持ち回れば可能。これが「代数的（Algebraic）な集計」の定義そのもの。
Flink の AggregateFunction が accumulator 型を別に定義させ、merge を実装させるのは、この形を強制するため。（4章・12章）
Q9. Spark が MapReduce より速い理由は？
①中間結果をメモリに保持する（ディスク往復が消える）②DAG 全体を見て最適化する（Predicate Pushdown・Column Pruning）③Stage 内をパイプライン化する（中間結果を書かない）。
特に反復処理（機械学習）で10〜100倍の差が出ます。（5章）
Q10. Spark ジョブが遅い。何から見ますか
Spark UI で ①Shuffle Read/Write の量 ②タスク実行時間の分布 ③Spill の有無の順。
「199個のタスクは1分、1個だけ2時間」なら Data Skew。対策は Salting・null の事前除外・AQE の有効化。
Spark 3 系ならまず AQE（adaptive.enabled / skewJoin / coalescePartitions）を有効にするだけで多くの問題が消えます。（5章）
Q11. ETL と ELT の本質的な違いは？
変換の位置ですが、本質的な価値は「生データが残るので、後からロジックを作り直せること」。
ETL では元データが無いので、集計ロジックのバグが後から直せない。ELT なら Raw 層から --full-refresh で全部作り直せる。
ELT が主流になったのは、DWH のストレージが安く計算が強くなり、制約が消えたから。（6章）
Q12. Data Lake の課題と、Lakehouse の解決策は？
課題: ACID が無い・UPDATE/DELETE ができない・Data Swamp 化。
Lakehouse（Iceberg/Delta/Hudi）の解決策: データ本体は Parquet で S3 に置いたまま、メタデータ層で「現在有効なファイル集合」を管理し、その切り替えを原子的に行う。
これで ACID・タイムトラベル・スキーマ進化・GDPR の DELETE が可能になります。（7章）

Part 3: 時刻・Window・Watermark（13〜20）

Q13. なぜ Event Time で集計するのですか
結果が再現可能になるから。同じ入力なら、いつ実行しても同じ結果が出ます。
Processing Time で集計すると、デプロイで2分止まっただけで「その時間帯が0件、再開時に3倍」という偽の異常が記録され、再処理すると全く違う結果になります。
「正確だから」ではなく「再現可能だから」と答えられるかが理解の深さ。（8章）
Q14. Processing Time を使ってよいのはどんなときですか
運用監視（エラー率・レイテンシ・スループット）。「今システムがどう動いているか」を見たいので、むしろこちらが正しい。
ビジネス指標（KPI・請求・レポート）には Event Time が必須。（8章）
Q15. クライアントの時計が信用できません。どうしますか
サーバ側で受信時刻と比較して検証し、範囲外なら受信時刻で置き換える + メトリクス化する。
これを実装していないと、1件の「2038年」のイベントで Watermark が未来に飛び、以降の正常なイベントが全部『遅延』として破棄されます——極めて深刻な事故。（8章・10章）
Q16. Window の3種類と、それぞれのコストは？
Tumbling（重複なし・最も安い・迷ったらこれ）/ Sliding（重複あり・size÷slide の分だけ State と計算量が増える）/ Session（gap で区切る可変長・遅延データで2つのセッションが結合されうるため実装が最も難しい）。（9章）
Q17. Window の State が膨らんで OOM しました
①ProcessWindowFunction ではなく AggregateFunction を使う（前者は Window 内の全イベントをメモリに保持する。後者は中間値1つだけ）②Sliding の重複度を下げる ③Session の gap を短くする ④キーの偏りを解消する。
実務での OOM の大半は①の選択ミス。（9章）
Q18. Watermark とは何ですか
「この時刻より古いデータはもう来ないだろう」という推定の宣言。Window を閉じる判断に使います。
推定なので必ず間違えます——早すぎれば取りこぼし、遅すぎれば結果が遅れる。正解は「完璧な Watermark を作る」ことではなく「間違えても壊れない設計にする」こと。（10章）
Q19. 遅れて届いたデータの3つの扱いは？
A: 捨てる（単純・必ず件数をメトリクスに出す）/ B: allowed lateness で待って結果を更新（実務の標準・出力先が upsert 可能である必要がある）/ C: Side Output に逃がしてバッチで確定（1件も失わない・速報と確定の二層構成と相性が良い）。（10章）
Q20. Window の結果が全く出てきません
Watermark が進んでいない。原因は ①Kafka の一部 partition にイベントが来ない（idle）②入力の停止 ③時刻の異常。
withIdleness の設定は実質必須——Watermark は全 partition の最小値なので、1つ止まると全体が止まります。（10章）

Part 4: State・エンジン・集計（21〜26）

Q21. ストリーム処理のプロセスが落ちたらどうなりますか
最後の Checkpoint から State を復元し、その時点の offset から入力を読み直す。
鍵は「offset と state を同時に保存する」こと。これがズレると、二重集計か欠損が発生します。（11章）
Q22. State が大きくなりすぎました
①State TTL を設定する（未設定だと無限に増える）②キー設計を見直す——「そのキーは有限個か？」を問う。session_id や request_id をキーにすると無限に増える ③RocksDB + 増分チェックポイント ④AggregateFunction を使う。（11章）
Q23. Checkpoint と Savepoint の違いは？
Checkpoint: 自動・障害復旧用。Savepoint: 手動・アップグレード用・永続的。
コード変更時は「Savepoint を取る → 停止 → 新コードで復元」。全ての stateful な operator に UID を付けていないと、コードを少し変えただけで復元に失敗します。（11章）
Q24. Kafka Streams と Flink の使い分けは？
Kafka → 処理 → Kafka で完結し、State が数十GB以下なら Kafka Streams（クラスタ不要という運用の軽さが決定的）。
ミリ秒レイテンシ・TB規模の State・複雑な Event Time 処理・CEP が必要なら Flink（ただしマネージドを強く推奨）。（13章・14章・17章）
Q25. KStream と KTable の違いは？
KStream = 出来事の連続（同じキーの新レコードは「追加」）/ KTable = キーごとの現在の状態（新レコードは「更新」）。
同じ topic でも、どちらとして読むかで結果が全く変わります。集計結果は必ず KTable になるので、出力 topic は compacted にすべき。（13章）
Q26. 1億ユーザーのユニークカウントをどう出しますか
HyperLogLog（誤差1〜2%、メモリ数KB固定）。
さらに重要なのは「HLL の中間状態（sketch）を保存しておけば、任意期間の UU がマージだけで出せる」こと。
通常の COUNT(DISTINCT) では「月間UU = 日次UUの合計」にならないため、期間ごとに全件を再スキャンする必要があります。（12章）

Part 5: 分析基盤とコスト（27〜30）

Q27. クエリが高い。何をしますか
「読むデータ量を減らす」の一点: ①列を絞る（SELECT * をやめる）②パーティションで絞る ③クラスタリング ④事前集計（最も効果が大きい）。
「パーティションを設定したのに効かない」場合は、WHERE 句で関数を使っている（DATE(ts) = ...）ことがほとんど。（19章）
Q28. なぜ列指向（Parquet）が速いのですか
①必要な列だけ読める ②同じ型が並ぶので圧縮が極めて効く（1/5〜1/10）③列ごとの min/max 統計でブロックを読み飛ばせる。
CSV で Data Lake に置くのは、コストとクエリ速度で数十倍の損失。（19章）
Q29. 部署ごとに同じ指標の数字が違います
指標定義の一元化（セマンティックレイヤー）。定義をコードとして1箇所に置き、全ての利用者がそれを参照する（dbt metrics / LookML / Airbnb の Minerva）。
ズレる理由は「キャンセルの扱い・基準日・テストデータの除外・タイムゾーン」など、どれも正当な理由がある——だから技術で定義を強制する必要があります。（18章・22章）
Q30. ストリームの数字とバッチの数字が違います。どちらが正しいですか
どちらも正しい。別の指標として扱うのが正解。
ストリームは速報値（遅延データを含まない暫定値）、バッチは確定値。
やってはいけないのは「同じ指標名で2つの数字を出す」こと——必ず「どっちが本当？」問題が起きます。指標名を分け（plays_realtime / plays_final）、乖離率を監視する。Google Analytics が「リアルタイムレポート」と「標準レポート」を別機能にしているのが最良の実装例。（3章・21章）

26 システム設計面接 — 12問と、評価される答え方

結論: 面接官が見ているのは「知識」ではなく「要件を確認し、トレードオフを言語化できるか」です。特にこの領域では『何分遅れたら困りますか』と聞き返せるかが、最も強いシグナルになります。

Q1. 「リアルタイム分析基盤を設計してください」
弱い答え: いきなり Kafka + Flink の構成図を描き始める。
強い答え: まず「何分遅れたら、どんな損失が出ますか？」と聞き返す。
・秒〜1分 → Stream（不正検知・障害検知など、時間に比例して損失が増えるもの）
・5分〜1時間 → Micro-batch（ストリームの1/5のコストで8割の価値。実務の最適解）
・半日〜1日 → Batch（大半の分析指標はこれで足りる）
その上で「どの指標がどれに該当するか」を分類してから構成を描く。
評価点: 要件を確認せずに技術を選ばないこと。この質問で構成図を描き始める候補者は非常に多い。
Q2. 「1日1兆イベントのログ分析基盤を設計してください」
強い答え: まず数字で規模を確認する——1兆/日 = 平均1157万 rps、1イベント 500B なら 500TB/日。
その上で:
①収集: エッジで受信 → Pub/Sub/Kinesis。ここでボット除去と時刻検証を行う（下流の全指標が汚染されるため）
②保存: S3 + Parquet + 日付パーティション。CSV/JSON は論外
③速報: ストリームで主要指標だけ（全指標をリアルタイムにはしない）
④確定: 日次バッチで全件再集計。階層集計（raw → hourly → daily）でクエリコストを桁で下げる
⑤ユニークカウント: 速報は HLL、確定はバッチ
評価点: 概算計算をすること。全部を同じ厳密さで扱わないこと。
Q3. 「集計結果が実行するたびに変わります。なぜですか」
強い答え: 「Processing Time で集計している可能性が高いです。処理した時刻で集計すると、デプロイや障害で処理が止まった分が別の時間帯に計上され、再実行すると全く違う結果になります。
Event Time（イベント自身が持つ時刻）で集計すれば、同じ入力からは常に同じ結果が出ます。
ただし Event Time にすると『いつ Window を閉じるか』を決める必要が出るので、Watermark と allowed lateness を設計します」
評価点: 「再現可能性」という言葉が出るか。
Q4. 「遅れて届いたデータをどう扱いますか」
強い答え: 「まず遅延の分布を実測します。processing_time − event_time のヒストグラムを取り、P99 を Watermark の許容遅延、P99.9 を allowed lateness にします。
それを超えるものはSide Output に逃がし、日次バッチで確定値に反映します。
捨てる場合は、必ず捨てた件数をメトリクスに出します——これが無いと静かにデータが欠けます。
また、allowed lateness を使うなら出力先が upsert 可能である必要があります。追記のみだと同じ Window の行が複数できて二重カウントになります」
評価点: 「実測する」と「出力先の制約」の2点。
Q5. 「バッチジョブが失敗しました。どうしますか」
強い答え: 「冪等に設計してあれば、単に再実行するだけです。パーティション単位の上書きにしてあれば、途中まで書かれていても正しい結果になります。
冪等でない場合は、まず部分的に書かれたデータを削除する必要があり、その判断自体が難しくなります。
だからバッチ設計の第一要件は冪等性です。
また、3時間かかるジョブが2時間50分で失敗するなら、ジョブを分割して中間結果を永続化します」
評価点: 冪等性を自分から持ち出せるか。
Q6. 「集計ロジックにバグが見つかりました。過去のデータをどう直しますか」
強い答え: 「ELT で Raw 層を残していれば、--full-refresh で下流を含めて全部作り直せます。
バッチなら Backfill（過去N日を再実行）。その際、並列度を絞って下流への負荷とコストを制御します。
ストリームだけの構成だと、これが非常に困難です——Kafka の保持期間内でしか巻き戻せず、新旧を並行稼働させて切り替える運用になります。
これが『生データを残す』ことの最大の価値です」
評価点: バッチとストリームの非対称性を理解しているか。
Q7. 「Data Lake と Data Warehouse、どちらを使いますか」
強い答え: 「Schema-on-Read か Schema-on-Write かの違いです。
現代の答えはLakehouse——データ本体は S3 に Parquet で置き、Iceberg/Delta のメタデータ層で ACID・タイムトラベル・スキーマ進化を得ます。
メタデータで『現在有効なファイル集合』を管理し、その切り替えを原子的に行うことで実現しています。
ただし規模が小さければ、BigQuery/Snowflake だけで完結させるほうが運用が単純です」
評価点: Lakehouse の仕組みを説明できるか。規模に応じた判断ができるか。
Q8. 「Exactly Once の集計は可能ですか」
強い答え: 「パイプライン内（Kafka → 処理 → Kafka）なら可能です。Checkpoint で offset と state を一貫して保存することで実現されます。
ただし外部システムへの書き込み（sink）は、冪等でなければ保証できません。
実務では『At Least Once + 冪等な書き込み』——具体的にはパーティション単位の上書き、または (window, key) をキーにした upsert——にするのが正解です」
評価点: 保証の境界を正確に区切れるか。
Q9. 「BigQuery の請求が跳ねました。原因と対策は？」
強い答え: 「スキャン量で課金されるので、読むデータ量を減らすのが対策の全てです。
原因の切り分け: ①SELECT * ②パーティションで絞っていない ③WHERE 句で関数を使ってパーティションが効いていない（DATE(ts) = ...）④ダッシュボードが生データを毎回集計している
対策: 列を絞る・パーティション/クラスタリング・事前集計テーブル（最も効果が大きい）。
加えて、仕組みとして制御します——クエリごとのスキャン上限設定・課金の可視化・上位クエリの定期レビュー」
評価点: 個人の努力ではなく仕組みで制御する視点。
Q10. 「レコメンドシステムを設計してください」
強い答え: 3層に分ける。
①オフライン（日次バッチ）: 特徴量生成とモデル学習。数時間かかるのでリアルタイムには不可能。ユーザーごとの候補リスト（上位500件）を事前計算して KVS に保存
②ニアライン（ストリーム・秒）: 「今見た作品」を候補から除外し、類似作品を昇格。モデルを再学習するのではなく、結果を補正するだけ
③オンライン（リクエスト時・ミリ秒）: 候補500件を軽く再ランキングして20件返す
加えて Training-Serving Skew（学習時と本番で特徴量の計算が違う）に注意し、Feature Store で統一します
評価点: 「候補生成」と「再ランキング」の分離。この構造は価格設定・検索・広告にも適用できる一般原則。
Q11. 「速報値と確定値、両方作りますか」
強い答え: 「作る場合は、運用ルールを先に決めます。
・指標名を分ける（plays_realtime / plays_final）——同じ名前で2つの数字を出すと必ず組織が混乱します
・ダッシュボードで『速報値（暫定）』と明示する
・乖離率を監視し、閾値を超えたら Watermark 設定を見直す
Google Analytics が『リアルタイムレポート』と『標準レポート』を別機能として提供しているのが最良の実装例です。
なお、Lambda Architecture の『同じロジックを2回実装する』問題は、Beam の Trigger や Flink の統一APIで軽減できます」
評価点: 技術ではなく運用ルールから答えられるか。
Q12. 「この分析基盤を監視するとしたら、何を見ますか」
強い答え: 「6つです。
①データの鮮度（最新レコードの時刻が期待どおりか）——SLA 違反をユーザーより先に知る
②行数の異常（前日比・同曜日比で ±X%）——固定閾値ではなく相対閾値で
③品質テストの成否（unique / not_null / 参照整合性）——落ちたら下流を実行しない
④捨てた遅延データの件数（ストリーム）——0でないなら要調査
⑤Consumer Lag / Watermark の進行（ストリーム）
⑥クエリコストの上位——週次でレビュー
加えて、ダッシュボードに必ず『最終更新時刻』を表示します」
評価点: ①と③が出るか。「壊れた数字を配るくらいなら更新を止める」という判断。

🔧 障害時の切り分けフローチャート

  1. 「データが来ていない」のか「処理されていない」のか「結果がおかしい」のかを最初に切り分ける
  2. 来ていない → 上流の到着状況 / 収集層のエラー率 / Kafka の produce レート
  3. 処理されていない → ジョブの実行状態 / Consumer Lag / Watermark の進行 / Checkpoint の成否
  4. 結果がおかしい（少ない） → 捨てた遅延データの件数 / フィルタ条件 / 上流のスキーマ変更（NULL 化）
  5. 結果がおかしい（多い） → 冪等性の欠如による二重計上 / 重複排除の失敗 / ボットの混入
  6. どこも異常が無いのに数字が合わない → 指標定義の相違を疑う（基準日・キャンセル・テストデータ・タイムゾーン）

28 よくある設計ミス — 判断のレベルで間違えるもの

結論: 27章の障害は「実装のミス」ですが、こちらは「判断のミス」です。実装ミスは直せますが、判断ミスは基盤の寿命の間ずっと引きずります。

ミス1: 「リアルタイム」を目的にする

最も多く、最も高くつくミス。「リアルタイムにしたい」と言われたら、必ず「何分遅れたら、どんな損失が出ますか？」と聞き返す。
Airbnb がほぼ全てバッチで足りている事実は重い。ストリームはコストが一桁高く、運用が難しく、正確性も落ちる。

ミス2: 冪等性を設計に入れない

「INSERT すればいい」で始めると、最初の障害で必ず破綻する。「1回の実行 = 1パーティションを丸ごと作り直す」を最初から原則にする。
後から冪等にするのは、全ジョブの書き換えを意味する。

ミス3: Processing Time で集計する

実装は簡単だが、結果が再現不可能になり、バッチの確定値と永久に一致しない。
Event Time は「後から入れる」のが極めて困難——イベント設計の最初に event_time を含める。

ミス4: Raw 層を削る

「容量削減のため90日で削除」→ 半年前からの指標のバグが見つかっても直せない。
ストレージは安く、作り直しは高い。Raw 層の保持期間は、可能な限り長くする。

ミス5: 同じ指標を複数箇所で定義する

営業・PdM・分析が各自 SQL を書く → 会議で数字を争うことになる。
指標定義を1箇所にコードとして置き、全員がそれを参照する。技術的には単純だが、組織的な効果が最も大きい投資。

ミス6: 速報値と確定値を同じ名前で出す

「どっちが本当？」問題が必ず発生する。
指標名を分け（_realtime / _final）、ダッシュボードで「暫定」と明示し、乖離率を監視する。GA が別機能にしているのが最良の実装。

ミス7: 品質チェックを入れない

分析基盤は「静かに壊れる」。上流のカラム名変更でも、パイプラインはエラーにならず全 NULL になる。
unique / not_null / 行数の相対比較 / 鮮度の4つは最低限入れ、落ちたら公開しない。

ミス8: SQL で書けるものにアプリを書く

単純な集計に Spark アプリを書くと、保守性・可読性・レビュー可能性が全部落ちる。
「SQL で書けないか」を最初に必ず確認する。これが最もコストに効く判断。

ミス9: State TTL を設定しない

ストリーム処理の State は設定しない限り永久に残る。1年後に「Checkpoint が失敗してジョブが復旧できない」となる。
「そのキーは有限個か？」を設計時に必ず問う。

ミス10: パーティションキーを user_id にする

カーディナリティが高い列でパーティション分割すると、数百万ディレクトリができてメタデータ処理が支配的になる。
パーティションは日付、細かい絞り込みはクラスタリング。

ミス11: 事前集計を作らない

ダッシュボードが毎回生データを集計する → 1回のクエリで数百円、100回開かれたら…。
raw → hourly → daily → monthly の階層集計で、コストが桁で下がる。

ミス12: 出力先を追記のみにする

allowed lateness で Window の結果が複数回出力されるため、追記のみだと同じ Window の行が複数できて二重カウントになる。
upsert 可能な出力先（Redis / Iceberg MERGE / compacted topic）を最初から選ぶ。

ミス13: ストリームで正確な値を出そうとする

COUNT(DISTINCT)・中央値をストリームで正確に出すには、全要素を State に持つ必要がある。
ストリームで出す指標は「分配可能または Sketch 化できるもの」に限る。正確な値はバッチで。

ミス14: 収集層でボットと異常時刻を除去しない

下流の全指標が汚染される。1件の未来時刻で Watermark が壊れ、1台のボットで State が膨らむ。
「入口で捨てる」のが最も安い。後から除去するのは全パイプラインの修正を意味する。

ミス15: 系譜とオーナーを管理しない

数百テーブルを超えると、「これを消したら何が壊れるか」が誰にも分からなくなる。
全テーブルにオーナーを設定し、系譜を自動追跡する。持ち主のいないデータは必ず腐る。

ミス16: 運用できない複雑さを導入する

「Flink を入れたが、State も Checkpoint も Savepoint も理解している人がいない」。
エンジンの能力ではなく、チームが運用できる複雑さで選ぶ。Instagram が数千万ユーザーを枯れた技術で支えた事実を思い出す。

🎯 この本を1文に圧縮すると

「必要な鮮度を意思決定から逆算し、可能な限りバッチで済ませ、どうしても必要な部分だけをストリームにする。そして生データを残し、いつでも作り直せるようにしておく」

バッチとストリームは対立する技術ではなく、「有界か無界か」という境界の引き方の違いにすぎません。
そしてストリーム処理の全ての難しさ（Window・Watermark・State・遅延データ）は、「イベント時刻と処理時刻がズレる」という1点から導かれます。
設計とは、鮮度・正確さ・コストのどれを諦めるかを決めることです。3つ全てを最大化することはできません。
