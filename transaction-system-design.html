01 Transaction とは / なぜ生まれたか

トランザクションとは「複数の読み書きを、1つの不可分な単位として扱う契約」。実装ではなく契約（抽象）であることが重要。この契約があるから、アプリは「途中で落ちたらどうなるか」を毎回考えなくて済む。

🏦 銀行の例え。 送金伝票を1枚書くとき、あなたは「Aから引く」「Bに足す」という2つの操作を意識しない。「送金した」という1つの出来事として扱う。
ところが機械の中では、この2つは必ず別々の瞬間に起きる。その隙間に停電が起きたらどうするのか——この問いに対する答えが、トランザクションという発明。
トランザクションは「隙間を無かったことにする装置」である。隙間が無くなるわけではない。外から見えなくなるだけ。

① この技術は何を解決するために生まれたのか

解決するのは 「複数の操作の途中状態が、外部から観測されてしまう」問題。観測経路は2つある。

  • 時間軸の観測（クラッシュ） — 途中で落ちて、中途半端な状態が永久に残る → Atomicity が解く
  • 空間軸の観測（他のTx） — 同時に走る誰かが、書きかけの状態を見る → Isolation が解く

歴史的には1970年代の航空券予約システム（IBM の IMS、後の System R）で確立した。「座席は1つしかないのに、2つの窓口が同時に売った」という現実の事故が出発点。座席・在庫・残高——「有限のものを複数人が同時に取り合う」場面が全ての起源。

図1-1 2つの観測経路。Atomicity は時間軸、Isolation は空間軸を守る。両方が要る。

② この技術がないと何が問題になるのか

  • アプリ側が「掃除コード」を書き続ける羽目になる — 「前回落ちた分の中途半端な注文を検出して修復するバッチ」を毎テーブル分書くことになる。これは実際に分散システムで起きる（25章の Saga はまさにこれ）
  • 不変条件（invariant）が守れない — 「残高は負にならない」「借方＝貸方」「在庫は0以上」。これらは複数行にまたがる条件で、Tx なしには守れない
  • エラー処理が発散する — 5つの UPDATE のうち3つ目が失敗したときの復旧手順は、組合せ爆発する。Tx があれば「rollback して再試行」1択になる
  • 障害の原因が特定不能になる — 「合計が合わない」は再現しない。並行性の事故は再現しないのが最悪の性質

③ 基本概念 — 4つの用語だけ先に固定する

BEGIN / COMMIT / ROLLBACK

Tx の境界。COMMIT が返った瞬間だけが「約束が成立した瞬間」。それ以前は何も約束されていない。COMMIT がタイムアウトした場合は「成功か失敗か不明」という第3の状態になる（21章で重要）。

Atomicity（原子性）

「全部か無か」。誤解注意: atomic は「同時に起きる」という意味ではない。「分割できない＝途中が観測されない」という意味。並行性の話ではなくアボート可能性の話。

Isolation（分離性）

「他のTxが同時に走っていないかのように見える」。これは程度問題。完全な分離＝Serializable は高価なので、実務では弱いレベルを使う（Part 3）。

Durability（永続性）

「COMMIT したら、その後クラッシュしても残っている」。絶対的な永続性は存在しない（ディスクが全部燃えたら消える）。実際には「WAL を fsync 済み」＋「レプリカに届いた」の組合せで確率を上げる作業。

Tx の状態遷移は5つしかない。この図を頭に入れると、分散トランザクションの議論（22章）が一気に読めるようになる。

図1-2 Tx の状態遷移。commit point の不可逆性が、後半すべての議論の土台になる。

⑥ メリット

  • アプリのエラー処理が「全部捨てて再試行」に単純化される — これが最大の価値。部分失敗の組合せを考えなくてよくなる
  • 不変条件をDBに強制させられる — 制約（UNIQUE / CHECK / 外部キー）が意味を持つのは Tx があるから
  • 並行性のバグを「レベル選択」という設計判断に還元できる — 個別のレースコンディションを手で潰す必要がない
  • リカバリが自動化される — クラッシュ後の起動時に、DBが勝手に整合状態へ戻す

⑦ デメリット・トレードオフ

1. 並行性が下がる

ロックや検証が入る分、スループットは落ちる。同じ行に集中するワークロード（人気商品の在庫）では致命的。30章で対処法を扱う。

2. レイテンシに fsync が乗る

commit ごとにディスク同期。「1秒に何回 commit できるか」に上限がある。ループの中で1件ずつ commit するとバッチ処理が100倍遅くなる。

3. スケールアウトの障害になる

Tx は「1台のDBの中」の概念。シャーディングすると壊れる。分散すると2PC か Saga が必要になり、複雑さが跳ね上がる（Part 5）。

4. 「囲んだから安全」という誤解を生む

本書最大の主張。既定の Isolation Level では Lost Update も Write Skew も防げない。Tx で囲むこと自体は安全性を意味しない（Part 2）。

⑧ 実務での利用例

  • 決済（Stripe / PayPay / Uber） — 「課金レコード作成 + 残高更新 + 履歴追加」を1Tx。ここは絶対に妥協しない領域
  • SNSの投稿（X / Instagram） — 意外にTxを使わない。投稿本体はDBに1行 INSERT、フォロワーへの配信は非同期・冪等。「いいね数」も強整合を諦める（32章）
  • EC のカート → 注文確定（Amazon / 楽天） — カートは弱整合でよいが、注文確定と在庫確保は強整合が必要。境界がここに引かれる（30章）
  • 監査ログ・イベント記録 — Tx 内で INSERT するかは判断が要る。rollback すると監査ログも消えるので、「試行の記録」は別Txにするのが正しいことも多い

⑨ Googleレベルではどう設計されるか

  • Googleは一度トランザクションを捨て、そして戻ってきた — Bigtable（2006）は単一行の原子性のみを提供し、複数行Txを意図的に排除した。スケールと引き換えに。結果、アプリ開発者が整合性コードを書く負担が爆発した
  • Spanner 論文（2012）の主張 — 「トランザクションが無いことによる複雑さは、アプリ開発者に転嫁されるだけで、消えはしない」。だから難しくても分散Txを提供する側に立った。この一文は面接で引用できる強い論拠
  • 設計の順序 — Google内部では「まず単一エンティティグループ（同一シャード）に収める設計を試み、どうしても無理な場合のみ分散Txを使う」。Megastore の entity group、Spanner の directory がこの単位
  • 計測して語る — Spanner 論文には「Txの99%は単一Paxosグループ内で完結」といった分布が載る。「分散Txは必要だが、頻度は低いはず」という仮説を持つのがGoogle流

⑩ システム設計面接ではどう問われるか

Q. 「トランザクションとは何ですか」と聞かれたら
悪い答え: 「ACIDを満たす処理単位です」（暗記の再生に聞こえる）
良い答え: 「複数の読み書きを1つの不可分な単位として扱う契約です。守っているのは2つで、クラッシュしても中途半端が残らないこと（原子性）と、同時に走る他の処理から途中が見えないこと（分離性）。実装は WAL と undo、ロックまたは MVCC です。重要なのは分離性は強度を選べる点で、既定設定では Lost Update を防げないので、どこまで払うかが設計判断になります」
→ 「選べる」「代償がある」という言葉が入ると、暗記でなく設計者として聞こえる。
Q. 「なぜ NoSQL の多くは複数行トランザクションを持たないのですか」
「Txは状態を1箇所に集めて順序を決めることで成立するので、データを複数ノードに分散させると調整（2PC・合意）が必要になり、レイテンシと可用性を失うからです。初期の NoSQL はスケールと可用性を優先し、整合性の責務をアプリに移した。その後 DynamoDB も MongoDB も Spanner も『やはり必要』として実装を追加しました。トレードオフが変化した（ネットワーク・時刻同期・合意アルゴリズムの成熟）ことが背景です」
Q. 「Tx の境界はどこに引きますか」（設計問題の途中で必ず聞かれる）
3点セットで答える。①ユースケース単位に引く（HTTPハンドラでもRepositoryでもない）②外部通信を境界内に入れない（HTTP・S3・メール・キューは外へ出す。理由: 行ロックを外部の遅延に晒す）③どの不変条件を守るためのTxかを言語化する（「残高は負にならない」など）。「守る対象を言えないTxは、ただ遅くしているだけ」と付け加えると強い。

02 ACID の解剖 — 4文字のうち2つは誤解されている

結論から: ACID の4文字は等価ではない。A と D はDBが提供する機能、I は強度を選ぶダイヤル、C はそもそもDBの機能ではない。この非対称性を理解していない人が「ACID準拠だから安全」と言う。

🏦 銀行の例え。 ACID を銀行の窓口業務に置き換えると:
A（原子性）＝ 伝票は1枚まるごと処理するか、破棄するか。半分だけ処理された伝票は存在しない。
C（一貫性）＝ 「借方と貸方は必ず一致する」という会計のルール。これは銀行のシステムが決めた掟であり、机や金庫の性質ではない。
I（分離性）＝ 窓口の間の仕切り。仕切りの高さは選べる。低いと隣の作業が見えるが、その分回転は速い。
D（永続性）＝ 受領印を押したら、その日の帳簿が焼けても控えが残っている。

図2-1 ACID の非対称性。「I だけがダイヤル」「C はアプリの責務」の2点が要点。

① この概念は何を解決するために生まれたのか

ACID（1983年、Härder と Reuter が命名）は「信頼できるDBとは何か」の共通語彙を作るために生まれた。それ以前は各ベンダーが「安全です」と言うだけで、何を保証しているのか比較できなかった。

しかし現在はマーケティング用語としても使われる。「ACID準拠」と書いてあっても、Isolation の既定が Read Committed なら Write Skew は起きる。面接でも実務でも「ACID準拠か」ではなく「どの Isolation Level か」を聞くのが正しい。

② この語彙がないと何が問題になるのか

  • 「安全です」の意味が人によって違う — ある人は「クラッシュしても消えない」、別の人は「同時実行しても壊れない」を指す
  • 設計レビューが感覚論になる — 「ここはトランザクション張った方がいい気がする」で終わる。「守るべき不変条件は X、それを壊す異常は Lost Update、だから FOR UPDATE を使う」と言えるのが語彙の力
  • CAP の C と混同する — CAP の C は複数レプリカ間の「線形化可能性」。ACID の C は単一ノードでも成立する「不変条件」。この混同は面接で減点される

面接での言い方: 「システム全体で ACID か BASE かを選ぶのではなく、データの種類ごとに一貫性の要求を分類し、金銭に触る部分だけ強整合にします。全部強整合にすると、人気商品の在庫のような1点集中で必ず詰まります」

⑥ メリット — ACID という語彙を持つ価値

  • 要件を分解できる — 「安全にして」を「クラッシュ耐性（AD）」「同時実行耐性（I）」「ビジネスルール（C）」に分けて議論できる
  • コスト見積りができる — I を上げるとスループットが落ちる、D を上げるとレイテンシが増える、という払う場所が見える
  • 製品比較ができる — 「このDBは複数行Txを持つか」「既定の Isolation Level は何か」「Serializable の実装は何か」を聞くだけで、製品の性格が分かる

⑦ デメリット・トレードオフ — ACID という言葉の危険性

1. 「ACID準拠」は何も保証しない

Isolation の既定が弱ければ異常は起きる。「ACID準拠のDBを使っているので大丈夫です」は設計レビューで最も危険な発言。

2. C の意味が2つある

ACID の C（不変条件）と CAP の C（線形化可能性）は別物。この2つを同じ文の中で使うと議論が破綻する。面接では明示的に区別する。

3. 分散すると4文字全部の意味が変わる

複数ノードに分散すると、A は 2PC が必要になり、I は「どのノードから見た順序か」が問題になり、D は「何台に届いたか」になる。単一DBの ACID の直感は、分散では通用しない（Part 5）。

4. D を信じすぎる

「commit したから安全」は、レプリカに届く前に primary が死ぬと崩れる。非同期レプリケーション + フェイルオーバーで「commit したデータが消える」は現実に起きる（replication ノート参照）。

03 Atomicity / Durability の実装 — WAL・undo・commit point

結論: 「データ本体を書く前に、これから何をするかをログに書き切る」——これだけ。この1行の原則（Write-Ahead Logging）から、原子性・永続性・クラッシュ復旧・レプリケーション・MVCC が全部派生する。DBで最も投資対効果の高い知識。

🏦 銀行の例え。 窓口の行員は、金庫の中身をいきなり動かしたりしない。まず「取引伝票（ログ）」を1冊のノートに追記し、インクが乾いたことを確認してから、実際の記帳や金庫の整理を行う。
なぜか。金庫の整理は途中で中断され得るが、ノートへの追記は一瞬で終わるから。停電しても、翌朝ノートを読めば「何をやりかけていたか」が完全に分かる。
WAL の本質は「順序の入れ替え」。「変更を反映してからログを書く」を「ログを書いてから変更を反映する」に逆転させただけで、あらゆるクラッシュから復旧可能になる。

① この技術は何を解決するために生まれたのか

解決するのは 「ディスクへの書き込みは、複数箇所を同時に更新できない」という物理的制約。

  • 1回の書き込みで原子的に更新できるのは、せいぜい 1セクタ（512B）〜1ページ（4KB〜16KB）
  • ところが1つのTxは、複数のテーブル・複数のインデックス・複数のページを更新する
  • 「ページAは書けたがページBは書けなかった」状態が必ず起こり得る

WAL の答え: 「更新の意図を、1本の追記専用ファイルに、順序付きで書く」。追記は原子的に扱いやすく（末尾に書くだけ）、順序が保たれるので、後から「どこまでやったか」が判定できる。

図3-1 WAL の効果。「安全性」と「性能」が同時に手に入る、DB設計で数少ない両取りの発明。

② この技術がないと何が問題になるのか

  • クラッシュ後に「壊れているかどうか」すら分からない — 検知不能な破損が最悪。バックアップにも破損が伝播する
  • commit のたびに全データページを fsync する必要がある — ランダムI/Oが commit ごとに数十回。実用速度にならない
  • rollback が実装できない — 「元の値」を保存する場所（undo）が無いと、途中でやめられない
  • レプリケーションが作れない — レプリカに送るべき「変更の流れ」が存在しない。WAL があるからレプリカも CDC も Outbox も作れる（26章）

ほぼ全ての商用DBは ARIES（1992年、IBM）というアルゴリズムの系譜にある。「Analysis → Redo → Undo」の3フェーズで、どの瞬間に落ちても正しい状態に戻せる。

図3-2 ARIES の3フェーズ。「redo で歴史を繰り返してから、undo で敗者を消す」という順序が肝。

⑤ 実際のシステム構成でどう使われるのか — WAL は4つの用途に転用される

用途1: クラッシュ復旧（本来の目的）

再起動時に自動実行。起動が遅い＝復旧するログが多いということ。checkpoint 間隔のチューニング対象。

用途2: レプリケーション

同じ WAL をレプリカに送って再生させれば、同じ状態になる。PostgreSQL のストリーミングレプリケーション、MySQL の binlog がこれ。

用途3: PITR（ある時点への復元）

バックアップ + WAL を「時刻 T まで」再生すれば、任意の時点に戻せる。誤った DELETE からの救出はこれしかない。

用途4: CDC（変更データキャプチャ）

WAL を読んで Kafka や検索エンジンに流す。Debezium / Airbnb の SpinalTap / Netflix の DBLog。26章の Outbox と直結する最重要の応用。

⑥ メリット

  • commit のコストが「1回のシーケンシャル書き込み」に圧縮される — 安全性と性能の両立
  • group commit が可能 — 同時に commit しようとしている複数Txの WAL をまとめて1回の fsync で流す。同時実行数が増えるほど、1Txあたりのコストが下がるという性質を持つ
  • 変更の「流れ」が生まれる — レプリケーション・CDC・PITR という3つの重要機能が副産物として得られる
  • アプリが何もしなくてよい — アプリは BEGIN/COMMIT を書くだけ

⑦ デメリット・トレードオフ

1. 書き込み増幅（write amplification）

同じ変更を「WALに1回、データページに1回」書く。さらに MySQL は doublewrite で計3回。実際のディスク書き込みは論理的な変更量の2〜3倍になる。

2. WAL が消えないと困る

レプリカが停止したまま・レプリケーションスロットが放置されると、WAL が溜まってディスクが溢れ、DB全体が停止する。実運用で最頻出の障害の1つ。

3. 復旧時間がログ量に比例する

checkpoint 間隔を長くすると平常時は速いが、クラッシュ後の起動が遅くなる（RTO が伸びる）。トレードオフ。

4. fsync が嘘をつくことがある

一部のディスク/仮想環境では fsync が実際には永続化しない。過去に PostgreSQL の「fsync gate」問題（fsync エラーを1回しか通知しない Linux の挙動）もあった。耐久性は最終的にハードウェアへの信頼に依存する。

⑧ 実務での利用例

  • AWS Aurora — 「The log is the database」 — Aurora はデータページをストレージに書かない。redo ログだけをストレージノードに送り、ページの再構築はストレージ側でやる。ネットワーク転送量が桁違いに減り、6コピー中4つの ack で commit できる。WAL の思想を極限まで押した設計（SIGMOD 2017 の論文は必読）
  • Netflix / Airbnb / Uber — WAL を CDC で吸い出す — Airbnb の SpinalTap は MySQL の binlog を読んで変更イベントを配信。「DBを更新すればイベントが自動で流れる」構造を作るのが現代の定石（26章の Outbox の上位互換）
  • Kafka — ログそのものをプロダクトにした — Kafka は「追記専用ログ」というWALの構造を、そのままメッセージングの中核にした。DBの内部構造が外部システムになった例
  • 障害例 — 「レプリカを止めたままにしていたら本番DBのディスクが100%になり全断」。これは replication slot が WAL の削除を止めるため。35章 #3 で再掲

⑨ Googleレベルではどう設計されるか

  • ログを Paxos で複製する — Spanner は WAL 相当のログを Paxos グループで複製してから commit する。「fsync した」ではなく「過半数のレプリカのログに載った」が commit の定義。単一マシンのディスク障害は commit の意味に影響しない
  • ログとストレージの分離 — Spanner は Colossus（分散ファイルシステム）上に載る。Aurora も同様に「計算とストレージの分離」。これによりフェイルオーバーが「別のマシンが同じログを読み始める」だけになり、数十秒で完了する
  • commit-wait — Spanner は commit の直前に「TrueTime の不確実性幅（数ms）だけ意図的に待つ」。ログに書いたタイムスタンプが確実に過去になるまで待つことで外部整合性を得る（28章）。「待つことで正しさを買う」という発想
  • 面接での使い方 — 「commit の定義は何ですか？」と聞かれたら「単一ノードなら WAL の fsync 完了、分散なら合意グループの過半数への複製完了です」と答えられると、層1と層3が繋がっていることを示せる

Q. 「COMMIT が成功した直後にサーバが落ちました。データは残っていますか」
「残っています。ただし『COMMIT が成功した』の定義次第です。DBが COMMIT 成功を返す前に WAL を fsync しているので、ディスクが無事なら redo で復旧されます。

→ 3段階（ローカル永続 / レプリカ永続 / クライアント認知）で答えると、レベルが高く見える。
Q. 「WAL が無いとどうなりますか / なぜログを先に書くのですか」
「データページの更新は複数箇所へのランダム書き込みで、途中で落ちるとどこまで書けたか分からない状態になります。WAL は『これから何をするか』を1本の追記専用ファイルに順序付きで書くので、再起動時にログを読めば完全に状態を再構成できます。
副次効果として、commit に必要なディスクI/Oがシーケンシャル1回に減り速くなる。安全性と性能を同時に得る珍しい設計です。

Q. 「トランザクションを1万件ループで実行したら異常に遅い。原因は？」（実務寄りの頻出質問）
「1件ずつ commit していて、commit ごとに fsync が発生している可能性が高いです。fsync は 0.1〜数ms かかるので、1万件なら数秒〜数十秒がそこだけで消えます。
対策: ①複数件を1Txにまとめる（1000件ごとに commit など。ただしロック保持時間と rollback 時のコストが増える）②バルクINSERT にする ③どうしても1件ずつなら、並列度を上げて group commit を効かせる。
『まとめすぎ』も危険で、100万件を1Txにすると undo が肥大し、ロックが長く、失敗時に全部やり直しになります。1000〜10000件程度のチャンクが実務の相場です」

04 異常の全体地図 — 壊れ方は6種類しかない

結論: 並行実行で起きる異常は6つに分類でき、それは「読み×書き」の組合せから機械的に導ける。名前を丸暗記するのではなく、「誰が何をしている隙間に、誰が何をしたか」で覚える。この章が Part 2 のインデックスになる。

🏦 銀行の窓口の例え。 異常の全ては「2人の行員が、同じ帳簿を、同時に触っている」から生まれる。組合せは3つしかない。
書き × 書き → 互いの記入を上書きする（Dirty Write / Lost Update）
読み × 書き → 相手の書きかけを読む、または読んでいる間に変わる（Dirty Read / Non Repeatable Read / Phantom）
読んで判断 × 読んで判断 → 2人とも「大丈夫」と判断してから、別々の場所に書く（Write Skew）← 最も見つけにくい

図4-1 異常の分類木。A-2（Lost Update）と C-1（Write Skew）の2つが実務の事故のほぼ全て。

読み方の指針 — 「異常」は理論用語ではなく、事故報告書の見出しである

覚え方のコツ1: 主語で分ける

Dirty ○○ = 相手が commit していない（未確定を見た/上書きした）。Non Repeatable / Phantom = 相手が commit した（確定したものが自分の途中で見えた）。Dirty かどうか＝相手のcommit前か後か。

覚え方のコツ2: 単数か範囲か

Non Repeatable Read = 特定の行の値が変わった。Phantom Read = 条件に合う行の集合が変わった。この違いが「行ロックでは防げない」理由になる（存在しない行はロックできない → ギャップロック、15章）。

覚え方のコツ3: 書く場所で分ける

Lost Update = 読んだ行と書いた行が同じ（行ロックで防げる）。Write Skew = 読んだ行と書いた行が違う（行ロックでは防げない）。この1点が Part 2 の最重要ポイント。

05 Dirty Write / Dirty Read — 「未確定」を見る・上書きする

結論: この2つは実務ではほぼ遭遇しない（既定設定で防がれているため）。しかし「なぜ防げているのか」の仕組み（書き込みロックと commit までの保持）が、後の全ての章の土台になる。面接では定義を正確に言えることが求められる。

現象 — 2つの定義

Dirty Write（汚い書き込み）

まだ commit していない他Txが書いた値を、上書きしてしまう。ANSI SQL標準には無く、Berenson らの批判論文（1995）で P0 として追加された概念。これを許すと rollback が壊れる（何を元に戻せばいいか分からなくなる）ので、全てのDBが全レベルで防いでいる。

Dirty Read（汚い読み取り）

まだ commit していない他Txが書いた値を、読んでしまう。その後 rollback されたら、存在しなかった値を根拠に判断したことになる。Read Uncommitted でのみ起きる。

図5-1 Dirty Write / Dirty Read。前者は「混ざる」、後者は「幻を信じる」。

内部で何が起きているか — なぜ Dirty Write は全レベルで防げるのか

答え: 書き込みロックだけは、どの Isolation Level でも commit まで保持されるから。

  • Isolation Level が制御しているのは、実は主に「読み取り側の振る舞い」（どのバージョンを見るか、読み取りロックをいつ離すか）
  • 書き込みロック（行の排他ロック）はレベルに関係なく commit / rollback まで保持される。これを Strict 2PL の「厳格」の部分という（15章）
  • だから「未commitの行を上書きしようとすると必ず待たされる」＝ Dirty Write は構造的に起こり得ない
  • 逆に言えば: Read Uncommitted にしても書き込みは速くならない。読みだけが緩む

補足: PostgreSQL では Read Uncommitted を指定しても Read Committed として動く。つまりPG では Dirty Read は原理的に起こせない。MySQL/InnoDB では本当に Read Uncommitted が実装されている（が使う理由はほぼ無い）。

実務での遭遇例（数少ない現実的なケース）

  • 巨大テーブルの概算件数を取りたくて RU にした — 「進行中のバッチの途中経過を覗きたい」という運用要求。監視・デバッグ目的では正当だが、業務ロジックに使ってはいけない
  • ロック競合を避けようとして RU にした（アンチパターン） — 前述の通り書き込みロックは緩まないので、期待した効果は得られない。MVCC 型DBなら RC でも読みは待たない
  • Dirty Write の実質的な発生: アプリレベルの read-modify-write — DBの1行に JSON を入れて「読んで、一部を書き換えて、丸ごと書き戻す」設計。これは DB から見ると正当な更新なので Dirty Write としては防がれない。実質的に Lost Update（6章）になる

面接ではどう問われるか

Q. 「Dirty Read が起きるとどんな実害がありますか」
「rollback される予定の値を根拠に判断してしまうことです。実害の大きさは『その判断の副作用が取り消せるか』で決まります。DB内の更新なら自分の Tx も rollback すれば済みますが、メール送信・決済API・在庫引当の外部呼び出しをしていたら取り返しがつきません。
ただし実務では Read Uncommitted をまず使わないので、この異常自体は稀です。むしろ『Tx 内で外部システムを呼ぶな』という設計原則の方が重要で、これは Dirty Read でなくても（自分自身が rollback するだけでも）同じ問題を起こします」
Q. 「Read Uncommitted にすると速くなりますか」
「ほとんど速くなりません。Isolation Level が主に制御するのは読み取り側の振る舞いで、書き込みロックはどのレベルでも commit まで保持されます。さらに PostgreSQL や MySQL のような MVCC 型のDBでは、Read Committed でも読み取りはロックを待たないので、RU にしても得るものがありません。
『ロック競合が辛いのでレベルを下げる』は、MVCC 型DBでは効果のない対処です。競合しているのは書き込み同士なので、対処はTx を短くする・ロックの順序を揃える・行を分割する（30章のホットスポット対策）になります」

06 Lost Update — 実務の事故の第1位

結論: 「SELECT して、アプリで計算して、UPDATE する」パターンは、既定の Isolation Level では壊れる。在庫・ポイント・残高・いいね数・カウンタ——数値を増減させる処理は全てこの異常の候補。本書で最も重要な章。

🛒 EC在庫の例え。 倉庫の棚に商品が10個ある。担当者2人が同時に伝票を見て「残り10個」と確認し、それぞれ1個ずつ出荷して、それぞれ「残り9個」と黒板に書いた。
実際には2個出荷したので残りは8個のはずなのに、黒板には9個と書かれている。後から書いた人が、先に書いた人の更新を「無かったこと」にした——これが Lost Update。
重要なのは、どちらの担当者も間違ったことをしていない点。手順は正しい。「読んでから書くまでの隙間」という構造そのものが欠陥。

図6-1 Lost Update のシーケンス。②〜⑦の隙間はネットワーク往復＋アプリ処理で数ms〜数百ms。同時アクセスがあれば必ず踏む。

発生条件 — どこに潜んでいるか

条件1: 読んだ値を使って書く

SELECT → 計算 → UPDATE の形。ORM を使うと自動的にこの形になる（エンティティを取得 → フィールドを変更 → save）。ORMは Lost Update 製造機と考えてよい。

条件2: 同じ行に同時アクセスがある

人気商品・キャンペーン・在庫僅少・バズった投稿。平常時は起きず、最も重要な瞬間（セール開始）に集中して起きるのが最悪の性質。

条件3: 隙間が長いほど確率が上がる

アプリでの計算だけなら数ms。外部API呼び出しを挟むと数百ms〜数秒で確率が跳ね上がる。人間の編集画面なら数分（この場合は必ず楽観ロックが要る）。

条件4: Isolation Level では防げない

RC でも MySQL の RR でも起きる。PostgreSQL の RR は検出してエラー（could not serialize access due to concurrent update）にする。Serializable なら両DBとも防ぐ。

内部で何が起きているか — DBごとの違い（重要）

DB / レベルSELECT → UPDATE の挙動結果
MySQL RC / RRSELECT はスナップショット読み（ロック無し）。UPDATE 時は最新のcommit済みバージョンを読み直して更新Lost Update が静かに起きる
PostgreSQL RCUPDATE 時に他Txがロック中なら待ち、解放後に最新版で条件を再評価して更新（EPQ）起きる（ただし stock = stock - 1 形式なら防げる）
PostgreSQL RR自分のスナップショット以降に更新された行を更新しようとするとエラーで中断検出される（要リトライ実装）
MySQL RRスナップショットで読むが、UPDATE は最新版に適用される（半一貫読み）起きる。しかも「読んだ値と違う行を更新している」不整合
両DB SerializablePG は SSI が競合を検出、MySQL は読みにもロックを掛ける防ぐ（PGはエラー、MySQLは待ちまたはデッドロック）

MySQL RR の落とし穴（面接で刺さるネタ）: RR なのに UPDATE accounts SET balance = balance - 100 の「balance」はスナップショットの値ではなく最新のcommit済みの値が使われる。つまりこの書き方をしている限り Lost Update は起きない。しかし SELECT balance（=スナップショット）で読んだ値をアプリで使うと、UPDATE との間で値が食い違う。「同じTx内で読んだ値と、UPDATEが使う値が違う」という直感に反する挙動。

Googleレベルではどう設計されるか

  • そもそも「共有カウンタ」を作らない — YouTube の再生回数、Google Ads のクリック数は1行のカウンタを更新しない。イベントを追記し、非同期に集計する（Dataflow / Spanner への定期反映）。「読んで書く」を「追記して集計する」に置き換えると、Lost Update は原理的に消える
  • Spanner は Serializable のみ — 選択肢を消すことで、Lost Update を設定ミスで踏む余地を無くしている。代わりにアボート時のリトライをクライアントライブラリが自動化している（runTransaction が再実行してくれる）。「強いレベル + 自動リトライ」がセットで初めて実用になる
  • DynamoDB の条件付き書き込み — ConditionExpression: attribute_not_exists(...) or version = :v による楽観ロックが標準の作法。分散KVSでは楽観ロックが唯一の選択肢（行ロックを跨いで保持する概念が無い）
  • 分割カウンタ（sharded counter） — 「1つのカウンタを N 行に分割し、更新はランダムな1行へ、読み取りは SUM」。Google App Engine 時代からの定番パターン。書き込みスループットを N 倍にする代わりに、読み取りコストが N 倍になる

07 Non Repeatable Read（Read Skew）— 見ている世界が途中で変わる

結論: 1つのTxの中で同じ行を2回読むと、値が変わっているという現象。単発の読み取りでは問題にならないが、「複数の行を読んで整合性を判断する処理」（集計・バックアップ・レポート）では致命的。解決策は Snapshot Isolation（11章）。

📚 図書館の例え。 あなたが蔵書リストを1ページずつ書き写している最中に、司書が本を別の棚へ移動させた。あなたが写し終えたリストには、同じ本が2回載っているか、1回も載っていない。
あなたは間違っていない。司書も間違っていない。しかし「写している最中に世界が動いた」ため、あなたのリストは現実のどの瞬間とも一致しない。
解決策は「作業開始時点の目録のコピーを1部もらってから写す」——これが Snapshot Isolation。

面接ではどう問われるか

Q. 「Non Repeatable Read と Phantom Read の違いは？」（定番）
「対象が『特定の行』か『条件に合う行の集合』かの違いです。
Non Repeatable Read は『WHERE id = 1 を2回読んだら値が違う』。行が特定できるので、その行をロックすれば防げます。
Phantom Read は『WHERE date = '10/1' を2回読んだら件数が違う』。まだ存在しない行はロックできないので、範囲そのものをロックする（ギャップロック）か、述語ロック、あるいは MVCC のスナップショットが必要です。この『存在しないものを守れない』という点が、実装上の難しさの分かれ目になります」
Q. 「巨大テーブルの集計バッチが他の処理をブロックしています。どうしますか」
「まずロックを取っていないことを確認します。MVCC 型DBなら通常の SELECT はブロックしないので、犯人は別（FOR UPDATE や LOCK TABLES、あるいは I/O 帯域の飽和）のはずです。
正しい構成は『Repeatable Read の読み取り専用Tx』で、これなら書き込みを止めずに一貫したスナップショットを得られます。
ただし長時間のスナップショットは古いバージョンの回収（VACUUM / purge）を妨げるので、①レプリカで実行する ②Tx を分割する ③そもそも分析用DB（BigQuery 等）に CDC で流して集計する、のいずれかに移すのが本筋です」

08 Phantom Read と Write Skew — 「まだ無いもの」は守れない

結論: 「無いことを確認してから書く」処理は、原理的に壊れる。存在しない行にはロックを掛けられないから。ホテルの二重予約、重複アカウント、当直医が0人になる事故——全部これ。Snapshot Isolation でも防げないため、対策を知らないと必ず踏む。

🏨 ホテル予約の例え。 2人の予約担当者が、同時に「10月1日の501号室は空いていますか？」と台帳を確認した。両方とも「空いています」と答えた。そして両方が予約を書き込んだ。
どちらの担当者も、確認を怠っていない。問題は「確認した時点では、相手の予約はまだ台帳に存在しなかった」こと。存在しない行を見張ることはできない。
現実のホテルはどうしているか。「台帳のそのページを、書き終わるまで他人に渡さない」（範囲ロック）か、「501号室10/1という札は1枚しかない」（一意制約）。この2つが対策の本質。

内部で何が起きているか — なぜロックできないのか

  • 行ロックは「存在する行」にしか掛けられない — 「10/1に501号室の予約が無いこと」をロックしたいが、無いものにはロックする対象が無い
  • 理論的な解: 述語ロック（predicate lock） — 「room=501 AND date='10/1' という条件そのもの」をロックする。実装すると全ての読み書きで条件の重なり判定が必要になり、極端に遅いので、実際のDBはこれをやらない
  • 実装1: ギャップロック / next-key lock（MySQL InnoDB） — インデックス上の「隙間」をロックする。述語ロックの近似で、実装が単純で速い。ただしインデックスが無いと範囲が広がりすぎて、大量ブロックやデッドロックを招く（15章）
  • 実装2: SSI（PostgreSQL の Serializable） — ロックせずに実行し、「読んだ範囲に他Txが書き込んだか」を追跡（SIREAD ロック）して、commit 時に危険なら中断。楽観的アプローチ（12章）
  • 実装3: 制約に落とす — DBの一意制約は、内部的に「その値のインデックスエントリを排他的に保持する」ことで実現されている。つまり制約は最も安価な述語ロック。だから「無いことを確認して書く」は制約に置き換えられるなら置き換えるべき

Googleレベルではどう設計されるか

  • Spanner は述語ロックに近いものを持つ — Spanner の読み取りは範囲（key range）に対してロックを取れるため、「まだ存在しないキー」への他Txの挿入をブロックできる。分散環境で Serializable を名乗る以上、Phantom は防がなければならない

  • Google Calendar / 会議室予約 — 公開情報は限られるが、時間枠を離散化（15分刻み等）してスロット行を実体化するのが業界標準の設計。「連続的な時間」を「離散的な枠」に変換すると、範囲の問題が一意性の問題に落ちる
  • 面接での強い一言 — 「『無いことを確認して書く』という処理は、確認と書き込みの間に必ず穴があるので、可能な限り『書いてみて、制約に弾かれたら埋まっていた』という形に反転させます」。これは Compare-And-Swap の発想と同じで、分散システム全般に通じる

Q. 「Snapshot Isolation で Write Skew が防げないのはなぜですか」（理論の理解を測る質問）
「SI は『読み取りは開始時点のスナップショットから』『書き込みが衝突したら片方を中断』という2つのルールで動きます。Write Skew では2つのTxが別々の行に書くので、書き込みの衝突が発生しません。
破れているのは『読んだ結果に基づく前提』であって、書き込み同士ではない。SI は読み取りと書き込みの間の依存（rw依存）を追跡していないのです。
PostgreSQL の SSI（Serializable Snapshot Isolation）は、まさにこの rw 依存を追跡することで SI を Serializable に拡張したもので、『危険な構造（2つ連続する rw 依存）』を検出したら中断します」
→ 「rw依存を追跡していないから」まで言えると、DDIA を読み込んでいると分かる。

09 Read Uncommitted — 使わないレベルを、なぜ知る必要があるか

結論: 実務では使わない。しかし「なぜ使わないのか」「なぜ速くならないのか」を説明できることに価値がある。このレベルの存在理由は、ロックベースのDBが主流だった時代の遺産。

🏦 銀行の例え。 窓口の仕切りを完全に取り払った状態。隣の行員が鉛筆で書きかけている数字が丸見え。速く情報が手に入るように見えるが、その数字は消しゴムで消されるかもしれない。
現代のDB（MVCC型）では、仕切りを取り払っても速くならない。なぜなら「確定した過去の写しを見る」方式なので、そもそも隣を覗く必要が無いから。

① このレベルは何を解決するために生まれたのか

1970〜90年代のロックベースのDBでは、読み取りにも共有ロックが必要だった。つまり「誰かが書いている行は、読むこともできない」。長いバッチ処理が走ると、参照系のクエリが全部止まる。

Read Uncommitted は「読み取りロックを一切取らない」ことで、この待ちを消すために用意された。当時は「概算値でいいから今すぐ見たい」という要求に対する唯一の答えだった。

② 現代でこのレベルが不要になった理由

  • MVCC の登場 — PostgreSQL / MySQL InnoDB / Oracle は「読み取りは書き込みをブロックせず、書き込みも読み取りをブロックしない」。読みたいだけなら Read Committed で十分待たない
  • PostgreSQL は実装すらしていない — SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED と書いても、内部では Read Committed として動く。エラーにならないので気づかない
  • 残る用途は「監視・デバッグ」だけ — 「進行中の巨大バッチが今どこまで進んだか覗く」など。SQL Server の WITH (NOLOCK) がこの用途で乱用されがち

③④ 基本概念と内部動作

DBRead Uncommitted の実装実際の挙動
PostgreSQL実装していないRead Committed として動作。Dirty Read は原理的に起きない
MySQL InnoDB実装あり未commitの最新版を直接読む。undo を辿らない分わずかに速い場面もあるが誤差
SQL Server実装あり（NOLOCK ヒント含む）共有ロックを取らないため、ページ分割中の読み取りで行の重複・欠落が起きる（Dirty Read 以上の被害）
Oracle実装していないSQL文としては受け付けない（エラー）

SQL Server の NOLOCK は特に危険: Dirty Read だけでなく、B-Tree のページ分割中に走査すると、同じ行を2回返したり、存在する行を返さなかったりする。「概算でいい」の範囲を超えた壊れ方をする。SQL Server では RCSI（Read Committed Snapshot Isolation）を有効にするのが正しい対処。

⑥⑦ メリットとトレードオフ

メリット（ほぼ無い）

ロックベースDBにおいて、読み取りが待たない。MVCC型DBでは、このメリット自体が消えている。

デメリット

rollback される値を読む。集計が合わない。SQL Server では行の重複/欠落まで起きる。そして「速くなった」と誤解したまま運用が続く。

⑩ 面接ではどう問われるか

Q. 「Read Uncommitted を使ったことはありますか / 使うべき場面は？」
「業務ロジックでは使いません。理由は2つ。①MVCC型のDBでは Read Committed でも読み取りは待たないので、性能上のメリットが無い ②rollback される値を読むリスクだけが残る。
唯一の用途は運用時の観測——『長時間バッチが今どこまで進んだか概算で見る』など。それも本番の意思決定には使いません。
関連して、SQL Server の WITH (NOLOCK) は現場で乱用されがちですが、行の重複・欠落まで起こすので、代わりに RCSI を有効にするのが正解です」

10 Read Committed — 世界で最も使われているレベル

結論: PostgreSQL / Oracle / SQL Server の既定であり、実運用の大半がここで動いている。守るのは「未確定を読まない」ことだけ。Non Repeatable Read も Lost Update も Write Skew も起きる——それでも実用になる理由と、その前提を理解する章。

🏦 銀行の例え。 窓口の仕切りは「確定した記帳しか見えない」高さ。書きかけは見えない。
ただし照会するたびに最新の確定値が見えるので、同じ口座を2回照会すると違う残高が返ることがある。「今この瞬間の確定した事実」を毎回見に行く方式。
1回だけ読んで、すぐ判断して終わる業務にはこれで十分。複数回読んで整合を取る業務には足りない。

① このレベルは何を解決するために生まれたのか

解決するのは2つ。①Dirty Read の排除（rollback される値を見ない）②Dirty Write の排除（未確定の行を上書きしない）。「最小限のコストで、明らかにおかしい結果だけを排除する」という現実的な設計。

重要なのは、これが「最も安い実用的なレベル」だという点。MVCC 実装なら読み取りは一切ロックを取らず、書き込みロックも必要最小限。だから既定になっている。

② このレベルが無いと（＝RUだと）何が問題になるか

  • 存在しなかった値を根拠に判断する（5章）
  • ただしRC があっても防げないものが大量に残ることが、この章の本題。RC が守るのは「単発の読み取りの正しさ」だけ

③ 基本概念 — RC の正確な保証は「文単位のスナップショット」

保証すること

各SQL文が開始した時点で commit 済みのデータだけを見る。1つの SELECT 文の中では一貫している（文の途中で世界は変わらない）。

保証しないこと

Tx 内の文と文の間では、世界が変わる。同じ SELECT を2回実行すると、別の結果が返り得る。これが Non Repeatable Read。

書き込みの扱い

更新対象の行に排他ロックを取り、commit まで保持。他Txが同じ行を更新しようとしたら待たされる。この点はどのレベルでも同じ。

PG 特有: 待った後の再評価

PG の RC では、他Txのロック解放を待った後、最新版で WHERE 条件を再評価してから更新する（EvalPlanQual）。「読んだ条件と違う行を更新する」ことがある、直感に反する挙動。

図10-1 RC と RR の違いは「スナップショットを何回撮るか」だけ。この1点で全ての挙動差が説明できる。

④ 内部でどのように動くのか — MVCC 型とロック型の2つの実装

MVCC 型（PG / MySQL / Oracle）ロック型（旧SQL Server の既定）
読み取りロックを取らない。commit 済みの最新版を undo/バージョンチェーンから探す共有ロックを取る（読んだ直後に解放）
読み手と書き手互いにブロックしない書き手が読み手をブロックする
コスト古いバージョンの保持と回収（VACUUM / purge）ロック管理のオーバーヘッドと待ち
実務での影響長時間Txがバージョン肥大を招く参照系が更新でブロックされ「なぜか画面が固まる」

実務の含意: SQL Server を使っていて「参照が遅い・固まる」なら、まず READ_COMMITTED_SNAPSHOT ON を検討する。同じ「Read Committed」という名前でも、実装が違うと性能特性が正反対になる。

⑤ 実際のシステム構成でどう使われるか

使ってよい場面

単発の読み取り + 原子的な更新で完結する処理。API の GET、単一行の更新、UPDATE ... SET x = x + 1 形式の更新。Webアプリの9割はこれ。

危険な場面

複数行を読んで整合性を判断する処理（集計、レポート、残高チェック、在庫の合計判定）。ここだけ RR / Serializable に上げるか、明示ロックを使う。

RC + 明示ロックが実務の主流

「既定は RC のまま、危険な箇所だけ FOR UPDATE や原子的UPDATE、UNIQUE制約で守る」。これが世界で最も多く採用されている構成。

RC の隠れた利点: デッドロックが少ない

読み取りロックを保持しないので、ロックの絡み合いが起きにくい。Serializable にすると（特に MySQL では）デッドロックが増える。RC が既定である現実的な理由の1つ。

⑥ メリット

  • 最も安い実用レベル — 読み取りが待たず、保持するバージョンも最小限
  • 常に最新の確定値が見える — 在庫や残高の「今の値」を知りたい処理には、むしろ RR より適切
  • デッドロック・アボートが起きにくい — アプリにリトライ機構が無くても運用できる
  • スナップショットの保持期間が短い — 長時間Txでもバージョン肥大が RR より緩やか（ただし影響はゼロではない）

⑦ デメリット・トレードオフ

1. Non Repeatable Read が起きる

同じ行を2回読むと違う。複数テーブルを跨ぐ集計は信用できない。

2. Lost Update が起きる

read-modify-write は無防備。アプリ側で必ず対策が要る（6章）。

3. Phantom / Write Skew が起きる

「無いことを確認して書く」は壊れる（8章）。

4. 「既定だから安全」という誤解を生む

最も広く使われているがゆえに、「これでいい」と思考停止しやすい。RC は「明示的に守る箇所を決める」ことを前提にしたレベル。

⑧ 実務での利用例

  • 一般的な Web API（大半のサービス） — PostgreSQL 既定の RC のまま運用。危険な箇所（在庫・決済）だけ FOR UPDATE や原子的UPDATE で守る
  • Instagram（PostgreSQL） — シャーディングされた PG を使用。単一シャード内の単純な操作が中心の設計にすることで、弱いレベルでも問題が起きにくい構造にしている（32章）
  • 管理画面の一覧表示 — RC で全く問題ない。むしろ最新値が見える方が望ましい
  • アンチパターン: RC のまま「SELECT → 判断 → UPDATE」を全体に散らす — レビューでこれを見つけたら、原子的UPDATE か FOR UPDATE に書き換える

⑨ Googleレベルではどう設計されるか

  • Spanner には Read Committed が無い — 書き込みTxは常に Serializable。代わりに「読み取り専用Tx」と「ステイル読み（read_timestamp = now - 10s）」を提供する。「一貫性を弱める」のではなく「時間を古くする」ことで性能を出すという別解
  • 「弱いレベルは事故を誘発する」という思想 — 選択肢があると、誰かが必ず間違える。Google の内部設計レビューでは「なぜこのレベルで十分か」の説明責任が設計者側にある
  • 代わりに何を選ぶか — Google 流の答えは「レベルを下げる」ではなく「競合しないデータモデルにする」。追記のみのテーブル、ユーザーごとに独立したキー空間、非同期集計。同じ行を複数人が同時に更新する設計そのものを避ける

⑩ 面接ではどう問われるか

Q. 「なぜ多くのDBの既定が Read Committed なのですか」

さらにアボートやデッドロックが起きにくいので、リトライ機構の無いアプリでも運用できる。
ただしRC は『危険な箇所はアプリが明示的に守る』という前提のレベルです。既定のまま read-modify-write を書けば Lost Update が起きます。『既定＝安全』ではなく『既定＝最小限』と理解しています」
Q. 「Read Committed のシステムで、確実に正しく在庫を減らすには？」

11 Repeatable Read / Snapshot Isolation — 「一貫した過去」を見る

結論: Tx 開始時点の世界を丸ごと固定して、それを見続ける。読み取りが一切ブロックされないまま、一貫性のある複数行の読み取りができる。MVCC が可能にした最大の発明。ただしWrite Skew という穴が残ることと、MySQL と PostgreSQL で挙動が違うことが最大の注意点。

📚 図書館の例え。 作業を始めるとき、司書から「今この瞬間の蔵書目録のコピー」を1部もらう。以降どれだけ本が貸出・返却されても、あなたの手元のコピーは変わらない。
だから何度数え直しても同じ結果になる。合計も矛盾しない。代償は「あなたが見ている目録は少し古い」こと。
そして司書は、誰かがコピーを持っている限り、古い版の目録を捨てられない——これが VACUUM 問題（14章）。

① この技術は何を解決するために生まれたのか

解決するのは 「複数の行を読んでいる間に世界が動く」問題（7章の Read Skew）。従来のロック型DBでこれを防ぐには読んだ行を全部ロックし続けるしかなく、更新が完全に止まった。

Snapshot Isolation（1995年、Berenson らの論文で命名）の答えは「ロックする代わりに、古いバージョンを保存しておく」。読み手は書き手をブロックせず、書き手も読み手をブロックしない——この標語が SI の全て。

② この技術がないと何が問題になるか

  • 長時間の分析クエリが本番を止める — ロック型で一貫性を取ろうとすると、集計中は更新できない
  • バックアップが取れない — 一貫したダンプを取るためにテーブル全体をロックする必要があった（MyISAM 時代の --lock-all-tables がまさにこれ）
  • 「読むだけなのに待たされる」 — 参照系のレイテンシが書き込み負荷に引きずられる

③ 基本概念 — SI の3つのルール

ルール1: 読み取りはスナップショットから

Tx 開始時点（正確には最初のクエリ実行時点）で commit 済みのデータだけが見える。以降、他Txが何を commit しても見えない。

ルール2: 自分の書き込みは見える

自分が Tx 内で更新した行は、その後の SELECT で更新後の値が見える。「スナップショット + 自分の変更」を見ている。

ルール3: 書き込み衝突は片方が負ける

「first committer wins」。自分がスナップショットを取った後に他Txが更新した行を、自分も更新しようとしたら中断される（PG の挙動）。これが Lost Update の検出になる。

SI と RR の関係（重要）

ANSI 標準の「Repeatable Read」と Snapshot Isolation は厳密には別物。標準の RR は Phantom を許すが、SI は（スナップショットなので）Phantom を防ぐ。「RR」という名前で SI を提供しているDBが多いため混乱が起きる（13章）。

用途1: バックアップ / 論理ダンプ

mysqldump --single-transaction / pg_dump は内部で RR の Tx を使う。これにより「テーブルをロックせずに一貫したダンプ」が取れる。

用途2: レポート・集計バッチ

複数テーブルを跨ぐ集計。読み取り専用Txにすると意図が明確になる。

用途3: 整合性チェック

「accounts の合計 == ledger の合計」のような検査。RC だと検査自体が誤検知する。

使ってはいけない場面

「最新の在庫を見て判断する」処理。スナップショットは古いので、判断の根拠として不適切。この場合は RC + FOR UPDATE か原子的UPDATE。

⑥ メリット

  • 読み手と書き手が互いにブロックしない — MVCC の最大の価値。長時間の分析が本番の書き込みを止めない
  • 複数行の整合性が取れる — 「どの瞬間にも存在しなかった世界」を見ることがなくなる
  • 実装が単純で予測しやすい — 「開始時点の世界を見る」という1つのルールで挙動が説明できる
  • PG では Lost Update も検出される — RC よりも安全。リトライさえ実装すれば、かなりの異常が消える

⑦ デメリット・トレードオフ

1. Write Skew が防げない（最大の穴）

SI の理論的限界。「読んだ条件が他Txによって変えられた」ことを検出しない。8章の対策が必須。

2. 古いバージョンの保持コスト

長時間Txが1本あるだけで、DB全体のバージョン回収が止まる。PG のテーブル肥大、MySQL の undo 肥大。実運用で最も多い性能障害の原因。

3. 見えている値が古い

判断の根拠としては RC より劣ることがある。「一貫している」と「最新である」は両立しない。

4. DB間で挙動が違う

同じ「REPEATABLE READ」でも PG と MySQL で Lost Update の扱いが正反対。DBを移行すると静かに壊れる。

⑧ 実務での利用例と事故

  • MySQL が RR を既定にしている歴史的理由 — 初期のレプリケーションがステートメントベース（SQL文をレプリカで再実行）だったため、RC ではレプリカと結果が食い違う可能性があった。現在は行ベースレプリケーションが主流なので、RC を既定にしている大規模サービスも多い（RC の方がロック範囲が狭くデッドロックも少ないため）
  • 事故: 分析用の長時間Txでディスクが溢れた — BIツールが開いたままの Tx を放置。PG では idle in transaction のセッションが VACUUM を阻害し、テーブルサイズが数倍に。対策: idle_in_transaction_session_timeout の設定
  • 事故: PG から MySQL に移行したら在庫がズレ始めた — PG の RR では Lost Update がエラーになっていたが、MySQL RR では静かに通る。「移行してから、たまに数字が合わない」の典型的な原因

⑨ Googleレベルではどう設計されるか

  • Spanner の「スナップショット読み取り」 — Spanner は任意のタイムスタンプでの読み取りを提供する（exact_staleness / max_staleness）。「10秒前の世界を、グローバルに一貫した形で読む」ことがロックフリーでできる。分析クエリはこれを使い、本番の書き込みに一切影響しない
  • TrueTime があるから可能になった — 分散環境では「同じ時点のスナップショット」を定義するのが難しい（時計がズレるため）。Spanner は原子時計とGPSで時刻の不確実性を数msに抑え、タイムスタンプでスナップショットを定義できるようにした（28章）
  • 「古いデータを読む」を一級市民にする — Google の設計思想では、「弱い一貫性」ではなく「明示的に古い一貫したデータ」を選ばせる。前者は何が起きるか分からないが、後者は「10秒古い」と正確に言える。この違いは面接で強い論点になる

⑩ 面接ではどう問われるか

Q. 「MySQL と PostgreSQL の Repeatable Read の違いを説明してください」（差がつく質問）

12 Serializable — 唯一の完全な解と、その3つの実装

結論: 「Tx を1つずつ順番に実行したのと同じ結果になる」ことを保証する唯一のレベル。全ての異常が消える。実装は①本当に直列実行する ②2PL（ロック） ③SSI（楽観検証）の3つしかなく、それぞれ性格が全く違う。

🍽 レストランの例え。 3つの実装は、厨房の運営方式に対応する。
①直列実行＝ シェフが1人で、注文を1件ずつ完成させてから次に取りかかる。絶対に間違えないが、1人分の速度が上限。
②2PL＝ 複数のシェフが働くが、使う食材・調理器具を先に全部確保してから調理する。他人が使っていたら待つ。時々「AがフライパンをBが鍋を持ったまま互いに待つ」（デッドロック）。
③SSI＝ 全員が自由に調理し、提供の直前に「材料が他人と衝突していないか」を検査する。衝突していたら作り直し。空いていれば最速、混んでいると作り直しだらけ。

① この技術は何を解決するために生まれたのか

解決するのは「異常のカタログを1つずつ潰していくアプローチの限界」。Dirty Read を防ぎ、Non Repeatable を防ぎ、Phantom を防ぎ……としても、未知の異常が残るかもしれない。

Serializable の定義は異常のリストではなく、「何らかの直列実行順序と同じ結果になる」という1つの条件。これを満たせば定義上、並行性に起因する異常は存在し得ない。アプリ開発者が並行性を一切考えなくてよくなる——これが本質的な価値。

④ 内部でどのように動くのか — SSI が何を検出しているか

SSI の核心は「直列化不能な実行には、必ず特定の構造が現れる」という定理。その構造とは「連続する2つの rw依存（読み → 他Txの書き）を持つ Tx が存在する」こと。

i// rw依存（rw-antidependency）とは i// Tx1 が読んだデータを、Tx2 が後から書き換えた i// → 直列順序では「Tx1 が先」でなければならない（Tx1 は古い値を見たので） i// 8章の Write Skew の例で見ると: i// Tx_alice: doctors を読む → alice の行を書く i// Tx_bob: doctors を読む → bob の行を書く i// i// Tx_alice が読んだ「bob の on_call=true」を Tx_bob が書き換えた → rw依存: alice → bob i// Tx_bob が読んだ「alice の on_call=true」を Tx_alice が書き換えた → rw依存: bob → alice i// i// → 循環している = どちらを先にしても説明できない = 直列化不能 i// → SSI はこれを検出して、後から commit する方をアボートする i// 実装（PostgreSQL） i// SIREAD ロック（実際にはブロックしない「読んだ記録」）を、読んだ行/ページ/述語に付ける i// 書き込み時に「その行に SIREAD が付いているか」を見て、依存関係を記録する i// → メモリ上限を超えると、粒度を粗くする（行→ページ→テーブル）= 偽陽性が増える

共通の落とし穴: Serializable にしても「Tx の外」は守られない。Tx 内で読んだ値をキャッシュに書いたり、外部APIを呼んだりすれば、そこは並行性の穴として残る。Serializable は「DB内の一貫性」の保証であり、システム全体の一貫性ではない。

⑧ 実務での利用例

  • 金融・会計システム — 残高、仕訳、決済。「並行性のバグで1円ズレる」ことのコストが、性能低下のコストを大きく上回る領域
  • 部分適用が実務の主流 — 「システム全体は RC、金銭に触るユースケースだけ Serializable」。Go なら Tx ヘルパーを2つ用意して使い分ける
  • CockroachDB / YugabyteDB / Spanner — 既定が Serializable。分散DBの新世代は「弱いレベルを提供しない」方向に振れている
  • Redis / VoltDB の直列実行 — Redis のコマンドは単一スレッドで直列に実行される。Lua スクリプトを使えば、複数操作を1つの原子的かつ直列な単位にできる（ただし rollback は無い）

⑨ Googleレベルではどう設計されるか

  • Spanner: 2PL + Paxos + TrueTime で分散 Serializable — 読み書きTxは悲観ロック（2PL）、読み取り専用Txはタイムスタンプを付けてロックフリー。「書き込みは悲観、読み取りは楽観（というよりロック不要）」というハイブリッドが要点
  • External Consistency — Serializable は「何らかの順序と等価」であればよいので、実世界の時間順序と違う順序でもよい。Spanner はさらに強く「実時間の順序と一致する」ことを保証する。これが TrueTime を必要とする理由
  • Calvin / FaunaDB: 順序を先に決める — Tx を実行する前に「グローバルな順序」をログとして合意し、全レプリカが同じ順序で決定的に実行する。ロックも2PCも不要になる代わりに、Tx が読み書きする範囲を事前に知る必要がある（28章）
  • スケールさせる方法は1つ: パーティション分割 — 直列実行も 2PL も SSI も、「競合しないデータに分ければ並列化できる」。Google の答えは常に「まず競合を消せ、それでも残る競合だけを Serializable で守れ」

⑩ 面接ではどう問われるか

Q. 「なぜ全部 Serializable にしないのですか」（最頻出）
「コストが3つの形で現れるからです。実装によって払う場所が違います。
2PL 型（MySQL）: 読み取りにもロックが必要になり、読み手が書き手をブロックします。デッドロックが増え、P99 レイテンシが悪化します。
SSI 型（PostgreSQL）: 読み取りはブロックしませんが、競合時に 40001 でアボートするのでアプリ側にリトライ実装が必須です。高競合だとアボートの無駄が積み上がります。
直列実行型: そもそも1コア分のスループットが上限です。
そのため実務では『既定は Read Committed、金銭や在庫に触るユースケースだけ Serializable または明示ロック』という部分適用にします。ただしSpanner や CockroachDB のように既定が Serializable のシステムもあり、その場合はリトライを言語ライブラリが吸収しています」
Q. 「PostgreSQL の Serializable でアボートが多発しています。どう対処しますか」
「5段階で見ます。
①インデックスを確認——SSI は『読んだ範囲』を追跡するので、フルスキャンすると『全行を読んだ』ことになり偽陽性が激増します。適切なインデックスを張るだけでアボート率が劇的に下がることが多い。
②Tx を短くする——読んでから commit までの窓が短いほど衝突しない。外部API呼び出しを Tx 外へ。
③読み取り専用Txを明示——READ ONLY と宣言すると SSI の追跡対象から外れる（DEFERRABLE なら完全にロックフリー）。
④ホットな行を分割——同じ行への集中が原因なら、分割カウンタ等で分散させる。
⑤その処理だけ明示ロックに変える——競合が本質的に避けられないなら、楽観（SSI）より悲観（FOR UPDATE）の方が無駄が少ない。高競合では悲観が勝つ」
Q. 「Serializable と Linearizability の違いは？」（上級・Google/Meta で聞かれる）
「別の軸の保証です。
Serializability は複数オブジェクト・複数操作の保証で、『Tx の集合が、何らかの直列順序と等価』であること。その順序が実時間と一致する必要はありません。
Linearizability は単一オブジェクトの保証で、『各操作がある一点で起きたように見え、その順序が実時間と一致する』こと。
両方を満たすのが Strict Serializability で、Spanner の External Consistency がこれに相当します。
実務的な差: Serializable なだけのシステムでは、『commit した直後に別の Tx で読んでも、自分の書き込みが見えない』ことが理論上あり得ます（順序を過去に置かれた場合）。分散システムで『さっき書いたのに読めない』が起きるのはこの層の話です」

14 MVCC — 読み手と書き手を戦わせない仕組み

結論: 「上書きせず、新しいバージョンを追加する」。これだけで、読み取りがロックを一切必要としなくなる。現代のDBの性能の大半はこの1つのアイデアに由来する。代償は「古いバージョンをいつ捨てるか」という永遠の宿題（VACUUM / purge）。

📚 図書館の例え。 本の内容を修正するとき、元の本に上書きせず、改訂版を新しく棚に置く。既に旧版を読んでいる人はそのまま読み続けられ、新しく来た人は改訂版を手に取る。
誰も待たない。問題は「旧版をいつ捨てるか」。まだ誰かが読んでいるかもしれない本は捨てられない。1人が旧版を10年借りっぱなしにすると、その間の全ての版が倉庫を圧迫する——これが長時間トランザクションの害。

① この技術は何を解決するために生まれたのか

解決するのは 「読み手と書き手がロックで衝突する」問題。ロックベースのDBでは:

  • 読み取りには共有ロック（S）、書き込みには排他ロック（X）が必要
  • S と X は両立しないので、読んでいる間は書けず、書いている間は読めない
  • 結果、長い分析クエリが更新を止め、大きな更新が参照を止める

MVCC の答え: 「古い値を消さずに取っておけば、読み手は古い値を読めばよい。待つ必要がない」。時間軸を1つ増やすことで、空間的な衝突を消した。

⑥ メリット

  • 読み取りがロックを取らない — 参照系のレイテンシが書き込み負荷から独立する。これが最大の価値
  • 一貫したスナップショットが安価に得られる — バックアップ、レポート、CDC の基盤
  • 読み取り専用の処理でデッドロックが起きない
  • 時間軸の読み取りが可能になる — Oracle の Flashback Query、Spanner のステイル読みなど、「過去の一貫した状態を読む」機能の土台

⑦ デメリット・トレードオフ

1. ストレージが増える

同じ論理データに対して複数の物理バージョン。更新が激しいテーブルほど膨らむ。

2. 回収（GC）が必須で、失敗すると致命的

VACUUM / purge が止まるとDB全体の性能が劣化し、最悪は停止する。「MVCC の運用コストは GC の運用コスト」。

3. 長時間Txの害が全体に波及する

1本の放置Txが、無関係なテーブルの回収まで止める。局所的な問題がグローバルな障害になる数少ない例。

4. 書き込み同士の競合は解決しない

MVCC は読み書き間の競合を消すだけ。同じ行への同時更新は結局ロックか検証が必要。「MVCC だから速い」は書き込みには当てはまらない。

⑧ 実務での利用例

  • Instagram / Airbnb（PostgreSQL） — 大規模 PG 運用ではautovacuum のチューニングが最重要の運用課題になる。Instagram はテーブルごとの autovacuum 設定と、大量削除を避けるデータモデル設計で対処している
  • Uber の PostgreSQL → MySQL 移行（2016年の有名な記事） — 移行理由の1つが「PG の UPDATE は全インデックスを更新するため書き込み増幅が大きい」「レプリカへの WAL 転送量が多い」という MVCC の実装差だった。賛否のある記事だが、MVCC 実装の違いが運用に直結する実例として面接で使える
  • 分析クエリの分離 — 「長いクエリは MVCC の GC を妨げる」ため、分析専用レプリカに隔離するのが定石。replication ノートの内容と直結する

⑨ Googleレベルではどう設計されるか

  • Spanner: バージョンをタイムスタンプで管理する — 各バージョンにTrueTime のタイムスタンプが付く。「時刻 T の一貫したスナップショット」が分散環境で定義できる。これにより、複数ノードに跨る読み取りがロックも調整も無しで実行できる。分散システムで MVCC を機能させるには、グローバルに意味のある時刻が要る——これが TrueTime の存在理由
  • Bigtable / HBase: セルにタイムスタンプを持たせる — 各セルが複数バージョンを持ち、maxVersions や TTL で古いものを自動削除。MVCC を「データモデルとして露出」した設計
  • GC の設計こそが本体 — Spanner はバージョン保持期間を設定でき（既定1時間）、それを過ぎたスナップショット読みは失敗する。「無限に過去を読めるようにはしない」と割り切ることで、GC を確実に回す
  • 面接での応用 — 「MVCC のデメリットは？」に対し「古いバージョンの回収が止まると全体が劣化する。だから長時間Txを禁止し、分析は別レプリカかタイムスタンプ指定の読み取りに隔離する」と答えられると、運用を知っていると評価される

⑩ 面接ではどう問われるか

Q. 「MVCC の仕組みを説明してください」
「上書きせずに新しいバージョンを作り、各Txは自分のスナップショットから見えるバージョンだけを読む仕組みです。行に『作成したTxのID』と『削除したTxのID』を持たせ、Tx開始時の『実行中Txの一覧』と比較して可視性を判定します。判定に必要な情報が全て手元にあるので、読み取りがロックを一切必要としません。
実装は2系統あり、PostgreSQL は新旧バージョンをテーブル本体に並べて置き（追記型）VACUUM で回収、MySQL InnoDB は最新版のみをテーブルに置き、古い版は undo log から巻き戻して再構築します。前者はテーブル肥大、後者は undo 肥大と読み取り遅延として症状が出ます。
共通の弱点は『最も古い実行中Txが終わるまで、どのバージョンも捨てられない』ことで、長時間Txが1本あるだけでDB全体の回収が止まります」
Q. 「MVCC があれば全ての競合が解決しますか」
「いいえ。MVCC が消すのは『読み手と書き手』の競合だけです。書き手同士の競合（同じ行への同時更新）は、結局ロックを取るか、楽観的に検証してアボートするしかありません。
さらにMVCC は Write Skew を防ぎません。スナップショットで一貫して読めることと、その読み取り結果が commit 時点でも有効であることは別だからです。
『MVCC = 速い』ではなく『MVCC = 読み取りが待たない』と理解するのが正確です」

15 ロックの全体系 — 行・ギャップ・意図・2PL

結論: ロックは「対象」×「モード」×「保持期間」の3軸で理解する。実務の事故のほとんどは「ロックの範囲が想像より広い」ことに起因する。特に MySQL のギャップロックは、インデックスが無いと全行をロックする——この事実を知らないと本番を止める。

📚 図書館の例え。 ロックの種類は「本の借り方」に対応する。
共有ロック（S）＝ 閲覧室で読む。他の人も同時に読めるが、誰かが読んでいる間は書架から持ち出せない。
排他ロック（X）＝ 貸出。1人しか借りられず、他の人は読むこともできない。
ギャップロック＝ 「棚の "あ行" と "か行" のすき間」を予約する。まだ存在しない本を、他人が置けなくする。これが Phantom 対策。
意図ロック（IX/IS）＝ 「この書架のどこかの本を借りています」という札。書架ごと持ち出そうとする人が、1冊ずつ確認しなくて済むようにする効率化。

安全でデッドロックしにくいが、並行性が壊滅する。管理オーバーヘッドは小さい。

細かいロック（行・特定キー）

並行性が高いが、デッドロックのリスクが上がり、ロック管理のメモリと CPU を食う。

ロックエスカレーション

SQL Server などは、行ロックが増えすぎると自動的にテーブルロックへ昇格する。「大量更新をしたら突然全体が止まる」原因。InnoDB / PG にはこの機構が無い（代わりにメモリを使う）。

保持期間が全て

ロックの範囲より保持時間の方が影響が大きいことが多い。「Tx を短くする」が最も効くチューニング。

⑩ 面接ではどう問われるか

Q. 「1行だけ更新するクエリで本番が停止しました。原因は？」
「WHERE 句の列にインデックスが無かった可能性が高いです。InnoDB の行ロックはインデックスエントリに対して取られるので、インデックスが使えないと全行をスキャンし、走査した全行（+ REPEATABLE READ ではギャップ）にロックが掛かります。結果として実質テーブルロックになります。
確認方法は EXPLAIN でスキャン行数を見ること、performance_schema.data_locks で実際のロックを確認すること。
対策は①インデックスを張る ②主キーで更新する形にリライトする ③大量更新は主キー範囲で分割して少しずつ実行する。③は運用でも重要で、100万行の UPDATE を1文で実行しないという原則です」
Q. 「DBをジョブキューとして使う際の注意点は？」
「SELECT ... FOR UPDATE SKIP LOCKED を使うことが最重要です。これが無いと、複数ワーカーが同じ先頭行を奪い合って直列化してしまいます。
加えて①取得と同時に status を processing に更新して可視性を制御する ②可視性タイムアウト（処理中のままワーカーが死んだ場合の復帰）を持つ ③リトライ回数と dead letter を設計する ④ポーリング間隔と負荷のバランス（PG なら LISTEN/NOTIFY の併用）。
規模が大きくなったら専用のキュー（SQS / Kafka）に移すべきですが、Outbox パターン（26章）のように『DBのTxと同じ原子性が欲しい』場合は、DBキューが正解になります」

16 Pessimistic Lock — 先に取って、確実に守る

結論: 「壊れるかもしれないから、先に押さえる」アプローチ。SELECT ... FOR UPDATE が実体。競合が頻繁な場面では楽観ロックより効率的だが、待ち・デッドロック・Tx の長さという3つのコストを払う。

🏦 銀行の例え。 窓口で「この口座の処理をします」と宣言し、その口座のファイルを金庫から取り出して自分の机に置く。他の行員は同じファイルを使えず、あなたが戻すまで待つ。
確実だが、あなたが席を外して昼食に行ったら、他の全員が待たされる（＝長いTx）。
そして2人の行員が互いに相手の持つファイルを待つと、永久に動かない（＝デッドロック）。

① この技術は何を解決するために生まれたのか

解決するのは「読んでから書くまでの隙間に、他人が割り込む」問題（6章の Lost Update、8章の Write Skew）。答えは単純で、「読む時点で、書く権利も一緒に取ってしまう」。

  • 確実に守れる — 取得できた時点で、他Txは介入できない。判断ロジックがどれだけ複雑でもよい
  • 高競合で効率的 — 楽観ロックは競合するたびに「やり直し」で仕事が捨てられるが、悲観ロックは待つだけで仕事は無駄にならない
  • デバッグしやすい — 「誰がどのロックを持っているか」がDBの状態として観測できる（pg_locks / data_locks）
  • リトライ実装が不要（デッドロック時を除く）

⑦ デメリット・トレードオフ

1. 待ちが連鎖する

1つの遅いTxが、その行を待つ全てのリクエストを止める。接続プールが枯渇し、無関係な処理まで巻き込んで全断する（35章の典型的な障害）。

2. デッドロック

複数行をロックすると必ず可能性がある。対策は順序の統一（19章）。

3. 人間の思考時間を跨げない

編集画面を開いている間ロックを保持するのは非現実的。この場合は楽観ロック一択（17章）。

4. 分散システムでは使えない

マイクロサービス間・複数DB間では「DBの行ロック」を跨いで保持できない。分散ロック（Redis/etcd）は別の難しさを持つ（21章）。

⑧ 実務での利用例

  • 口座の残高更新（29章） — 送金元・送金先の両方を ID 昇順で FOR UPDATE。金融系では最も一般的な実装
  • 状態遷移の保護 — 「注文が pending のときだけ confirmed にできる」。ただしこれは UPDATE ... WHERE status='pending' の1文でも書ける（そちらの方が良い）
  • ジョブキュー — FOR UPDATE SKIP LOCKED（15章）
  • 採番（連番の発行） — 「請求書番号を連番で」という要件。シーケンスは欠番が出るため、法的に連番が必要な場合は行ロックで採番する。ただしこれは全体の直列化点になるので、テナントごとに行を分けるなどの設計が要る

⑨ Googleレベルではどう設計されるか

  • Spanner の読み書きTxは悲観ロック — 読んだ行にロックを取り、commit まで保持する（分散2PLの一種）。「分散環境でも悲観ロックは有効。ただしロックを持ったままネットワーク往復が発生するので、Txを極限まで短くする設計が前提」
  • ロック待ちを可視化する文化 — Spanner は「どのTxがどのキーのロックを待っているか」を診断ツールで公開している。ロック競合はブラックボックスにしない、という運用姿勢
  • Percolator は「ロック情報をデータとして書く」 — Bigtable 上のクライアント駆動2PC では、ロックを専用のカラム（lock 列）に書き込む。サーバがロックマネージャを持たないため、クライアントがクラッシュしたロックを他のクライアントが掃除する（lazy cleanup）という設計（28章）

⑩ 面接ではどう問われるか

Q. 「FOR UPDATE を使う際に気をつけることは？」
「4点あります。①ロック順序を統一する——複数行を取るならID昇順など決めておく。デッドロックの9割はこれで防げる。②Tx 内で外部通信をしない——相手の遅延がそのままロック保持時間になる。③WHERE 句にインデックスがあることを確認する——無いと走査した全行がロックされる。④NOWAIT かタイムアウトを設定する——待ち行列が伸びて接続プールが枯渇すると、無関係な機能まで巻き添えで落ちます。
加えて、『そもそも FOR UPDATE が必要か』を先に問うべきです。UPDATE ... WHERE 条件 の1文で表現できるなら、ロック時間が最短でデッドロックも起きにくい」

17 Optimistic Lock — 取らずに、後で検証する

結論: 「たぶん競合しないから、そのまま進めて、書く瞬間に確認する」。ロックを取らないので「ロック」という名前は本当は誤り（正しくは楽観的並行性制御）。人間の編集時間を跨げる唯一の手段であり、分散システムでは事実上これしか選択肢が無い。

📚 図書館の例え。 本を借りずに、その場でメモを取って持ち帰る。編集した内容を返しに来たとき、「あなたが見た版は第3版ですね？ 今は第4版になっています」と言われたら差し戻される。
誰も待たない。ただし差し戻されたら、作業をやり直す。
混雑していなければ最速。混雑していると、やり直しばかりで進まない——これが楽観ロックの全て。

① この技術は何を解決するために生まれたのか

解決するのは「ロックを保持できない/したくない期間を跨いで、一貫性を守る」問題。

  • 人間の編集時間 — 編集画面を開いてから保存するまで数分。この間 DB の行をロックし続けるのは不可能（そもそも HTTP はステートレス）
  • 分散システム — サービスAが読み、サービスBが書く。DBの行ロックはコネクションに紐づくので、サービスを跨いで保持できない
  • 読み取りが圧倒的に多いワークロード — 競合が稀なら、待つコストの方が高い

  • 誰も待たない — ロック待ちによる連鎖障害が起きない。P99 レイテンシが安定する
  • 任意の長さの「思考時間」を跨げる — 画面編集、複数リクエストに跨る処理、サービス間の処理

  • デッドロックが起きない — ロックを取らないので原理的に無い
  • 「上書きされたことに気づける」 — これ自体が価値。ユーザーに競合を伝えて判断させられる

⑦ デメリット・トレードオフ

1. 高競合では仕事が捨てられる

10人が同時に同じ行を更新したら、9人がやり直し。競合率が上がるほど、無駄になった計算が積み上がる（ライブロック的な状態）。この場合は悲観ロックの方が効率的。

2. 規律が必要

1つの更新経路で version の更新を忘れると、そこが穴になる。管理画面、バッチ、手動SQL、データ移行——全部で守る必要がある。トリガーで自動インクリメントする手もある。

3. 競合時のUXを設計する必要がある

「他の人が更新しました」だけでは、ユーザーの編集が消える。差分表示、マージUI、自動リトライのどれを選ぶかは設計判断。

4. 複数行にまたがる不変条件は守れない

version は「その行が変わっていない」ことしか保証しない。Write Skew（8章）は防げない。

⑧ 実務での利用例

  • 管理画面・CMS の編集 — 最も典型的な用途。Rails / Hibernate / GORM など主要ORMが標準機能として持っている
  • Google Docs / Figma の同時編集 — これは楽観ロックの先にある技術（OT / CRDT）。「競合したら差し戻す」ではなく「競合しないデータ構造にする」というさらに進んだ答え
  • DynamoDB / Cassandra / Spanner のアプリ — 分散DBでは条件付き書き込みが標準。Cassandra の LWT（IF NOT EXISTS）は Paxos を使うため遅く、多用は禁物
  • Kubernetes の resourceVersion — k8s の全リソースが楽観ロックで守られている。kubectl apply が「conflict」で失敗するのはこれ。分散システムにおける楽観ロックの最大級の実例
  • Git — git push が「rejected (non-fast-forward)」になるのは、まさに楽観ロックの検証失敗。「読んだ版（base commit）が変わっていたら拒否」

⑨ Googleレベルではどう設計されるか

  • Spanner の読み取り専用Tx + 条件付き書き込み — ロックを取らずに読み、書くときにタイムスタンプで検証する。「読み取りは絶対にブロックしない」を最優先に置いた設計
  • Percolator の楽観的2PC — Google のインデックス構築システムは、クライアントが自分でロック列を書き、commit 時に検証する。競合したら片方が abort し、ロックを掃除する。「サーバにロックマネージャを置かない」ことでスケールさせた
  • CRDT / OT へのエスカレーション — 競合が本質的に頻繁な領域（同時編集）では、「競合を検出する」から「競合しても自動的にマージできるデータ構造にする」へ移行する。Google Docs の OT がこれ
  • 面接での言い方 — 「楽観と悲観は『競合率』で選びます。競合率が数%以下なら楽観、数十%を超えるなら悲観。そして競合率が本質的に高い設計自体を疑い、データモデルで競合を消せないかを先に考えます」

⑩ 面接ではどう問われるか

Q. 「複数の管理者が同じ商品を編集するシステムを設計してください」
「楽観ロック（version 列）を使います。行ロックは HTTP のリクエストを跨いで保持できないし、編集画面を開いている数分間ロックし続けるのは非現実的だからです。
実装は①items に version 列 ②GET 時に version を返す（ETag でもよい） ③PUT 時に WHERE id=? AND version=? で更新し、影響行数0なら 412 Conflict。
UX の設計が本題で、単に『失敗しました』ではなく『Bさんが3分前に価格を変更しました。あなたの変更を上書きしますか / 差分を確認しますか』と出すのが望ましい。
さらに『同時編集を本当にサポートしたい』なら、フィールド単位の更新（部分更新）にして競合の粒度を下げる、あるいは編集中の表示（プレゼンス）を出して人間側で回避させる、という段階もあります」
Q. 「楽観ロックと悲観ロック、どちらを使いますか」（頻出）
「競合の頻度と、ロックを保持できる時間で決めます。
楽観を選ぶ: 競合が稀（数%以下）/ 人間の思考時間や複数リクエストを跨ぐ / 分散環境でロックを保持できない / 待ちによる連鎖障害を避けたい。
悲観を選ぶ: 競合が頻繁（同じ行に集中する）/ やり直しのコストが高い（重い計算を含む）/ 短いTxで完結する / 確実に順番に処理したい。

そして両方使う場面もあります。例えば注文確定では、在庫行は FOR UPDATE、注文エンティティは version で守る」

18 楽観 vs 悲観 — 選び方の定量的な判断

結論: 競合率が損益分岐点。競合率が低ければ楽観が速く、高ければ悲観が速い。「なんとなく」で選ばず、「同じ行への同時アクセスがどれくらいあるか」を見積もって選ぶ。

Q. 「競合率が高いことをどう見積もりますか」
「『同じ行への書き込みリクエストの到着率 × トランザクションの保持時間』で概算します。例えば1つの行に秒間100リクエスト来て、Tx が 10ms かかるなら、平均で常に1本が処理中という状態なので競合はほぼ確実に起きます。
実測なら、ロック待ち時間（PG の pg_stat_activity.wait_event、MySQL の lock_time）、デッドロック数、シリアライゼーション失敗数を計測します。
重要なのは『平均』ではなく『ホットスポット』を見ることで、100万商品のうち1商品にアクセスの半分が集中するのが現実です。平均競合率が低くても、その1行は詰まっています」

19 Deadlock — 互いに待って永久に動かない

結論: デッドロックは「バグ」ではなく「ロックを使う限り必ず起こり得る現象」。だから①発生確率を下げる（順序統一）②起きたら自動的に回復する（リトライ）の2段構えで設計する。「デッドロックを完全に無くす」は目標として間違っている。

🛣 交差点の例え。 信号のない十字路で、4方向から同時に車が入り、それぞれ「右の車が動いたら進もう」と待っている。全員が正しく譲り合った結果、誰も動けない。
解決策は3つ。①一方通行にする（ロック順序の統一）②タイマーで強制的に1台をバックさせる（タイムアウト）③警察官が来て1台を退場させる（デッドロック検出）。
実際のDBは③を採用し、犠牲者を1つ選んで rollback する。だからアプリはリトライすればよい。

① なぜ起きるのか — 4条件

デッドロックは以下の4条件が同時に成立したときにのみ起きる（Coffman の条件）。1つでも崩せば起きない。

1. 相互排除（Mutual Exclusion）

リソースは同時に1人しか使えない。→ 崩し方: MVCC で読みをロックフリーにする、楽観ロックを使う

2. 保持と待機（Hold and Wait）

持ったまま、次を待つ。→ 崩し方: 必要なロックを最初に全部取る、または1つずつ取って解放する

3. 横取り不可（No Preemption）

他人のロックを奪えない。→ 崩し方: DBのデッドロック検出が犠牲者を強制 rollback する（＝横取り）

4. 循環待機（Circular Wait）

A→B→C→A の待ちの輪。→ 崩し方: ロックの取得順序を全体で統一する。実務で最も効く対策

⑦ トレードオフ — 「デッドロックを消す」の代償

粗いロックにする

テーブル全体をロックすればデッドロックは減るが、並行性が壊滅する。

楽観ロックに切り替える

デッドロックは原理的に消えるが、高競合ではやり直しが増える。デッドロックがアボートに形を変えただけ、とも言える。

検出を切る（InnoDB）

超高並行時は検出コスト自体が問題になるので切ることがあるが、タイムアウトまで（既定50秒）待つことになり、レイテンシが壊滅する。設定するなら timeout も短くする。

本質的な対処

「そもそも複数行を跨いでロックしない設計」。1行で完結させる、キューで直列化する、集約単位を見直す（DDD の集約設計はまさにこの話）。

⑧ 実務での事故例

  • セール開始と同時にデッドロックが数千件/分 — 複数商品をカートで一括購入する処理で、商品IDの順序がバラバラだった。sort を1行入れるだけで解消
  • バッチとオンライン処理のデッドロック — バッチが ID 昇順、オンラインが更新時刻順で処理していた。「システム全体で1つの順序規約」でないと意味がない
  • 外部キーによる見えないデッドロック — 子テーブルへの INSERT が親行にロックを取ることを知らず、原因究明に数日
  • 1205 を握りつぶして中途半端に commit — 前述の innodb_rollback_on_timeout の罠。「送金の片側だけ実行された」という最悪の結果になる

原則1: UseCase 層が Tx の境界

Repository の中で BEGIN/COMMIT しない。Repository が commit すると、複数 Repository を跨ぐ整合が取れなくなる。

原則2: Tx を context で伝播させる

Go では context.WithValue に *sql.Tx を入れて、Repository が取り出す実装が一般的。型安全ではないが、シグネチャが汚れない。トレードオフ。

原則3: 集約 = Tx の単位

原則4: 副作用は Tx の外か Outbox へ

メール送信・通知・外部API。「Tx 内で送りたい」なら Outbox テーブルに INSERT する（26章）。

21 なぜ分散トランザクションが必要になるか

結論: 分散トランザクションは「解くべき問題」ではなく「避けるべき状況」。まず「なぜ分かれてしまったのか」を問い、境界を引き直せないかを検討する。それでも避けられない場合にだけ、Part 5 の道具を使う。面接でこの順序で話せるかが評価の分かれ目。

📮 郵便の例え。 同じ建物の中にいる2人なら、口頭で「せーの」と言えば同時に動ける。しかし相手が海外にいたら、手紙を出して返事を待つしかない。
そして手紙には3つの不確実性がある。①届いたか分からない ②返事が来ないのは相手が死んだのか、単に遅いのか区別できない ③同じ手紙が2回届くことがある。
分散トランザクションの難しさは全部この3つに由来する。技術の問題ではなく、物理と情報の問題。

② 分散すると何が根本的に難しくなるのか — 3つの不可能性

難しさ1: 障害と遅延が区別できない

「返事が来ない」＝相手が死んだのか、ネットワークが詰まっているのか、相手が処理中なのか原理的に区別できない。タイムアウトは「判断」であって「事実」ではない。

難しさ2: 部分故障（partial failure）

単一マシンなら「全部動く or 全部止まる」。分散では「3つのうち2つは成功、1つは不明」が常態。エラー処理の組合せが爆発する。

難しさ3: 共通の「今」が無い

各マシンの時計はズレる。「どちらが先に起きたか」を時刻で判定できない。だから順序を決めるには合意（Paxos/Raft）か特殊なハードウェア（TrueTime）が要る。

結果: 2つの選択肢しかない

①調整する（2PC / 合意）→ 遅く、可用性が下がる。②調整しない（Saga / 結果整合）→ 一時的な不整合を受け入れる。この二択が Part 5 の全て。

22 Two Phase Commit（2PC）— 原子性を分散で守る唯一の標準手法

結論: 「全員に『準備できたか』を聞き、全員がYESなら『実行せよ』と伝える」——たったこれだけ。しかし「コーディネータが死ぬと参加者が永久に待つ」というブロッキング問題があり、これが実務で嫌われる理由。面接では必ず問われる中核知識。

💍 結婚式の例え（2PC の古典的な比喩）。
フェーズ1（prepare）: 司式者が新郎に「誓いますか？」と聞く → 「はい」。新婦にも聞く → 「はい」。この「はい」は取り消せない。以降、司式者が「宣言します」と言えば必ず結婚が成立する。
フェーズ2（commit）: 司式者が「ここに夫婦の成立を宣言します」と言う。この瞬間、不可逆に確定する。
問題: 新郎新婦が「はい」と言った直後に司式者が倒れたら？ 2人は「結婚したのかしていないのか分からないまま、他の誰とも結婚できない」状態で固まる。これがブロッキング問題。

① この技術は何を解決するために生まれたのか

解決するのは「複数の独立したノードで、commit するかしないかを一致させる」問題（原子的コミットメント問題）。

難しさの核心は「commit は不可逆だが、通信は信頼できない」点。もし各ノードが独立に commit を判断したら、「ノードAは commit、ノードBは abort」という取り返しのつかない不整合が生じる。2PC の発明は「commit する前に、全員から『必ず commit できる』という約束を取り付ける」ステップを挟んだこと。

図22-1 2PC の正常系。「prepare = 取り消せない約束」が全ての鍵。

図22-2 2PC の障害パターン。「in-doubt でロックを保持したまま固まる」が本質的な弱点。

④ 内部でどのように動くのか — prepare が特別な理由

⑥ メリット

  • 真の原子性が得られる — 中間状態が外部から観測されない。Saga では得られない性質
  • アプリのコードが単純 — 補償処理を書かなくてよい。「失敗したら全部無かったこと」
  • Isolation も保たれる — ロックを保持しているので、他Txから中間状態が見えない
  • 標準化されている — X/Open XA という業界標準がある

⑦ デメリット・トレードオフ

1. ブロッキング問題（本質的欠陥）

コーディネータの障害で参加者が in-doubt のまま固まり、ロックを保持し続けて他の処理まで止める。3PC はこれを解こうとして失敗した（23章）。

2. 可用性が掛け算で低下

参加者が N 個あれば、全員が生きている確率の積。99.9% × 5 = 99.5%。ノードを増やすほど壊れやすくなる。

3. レイテンシが大きい

ネットワーク往復2回 + 各ノードで fsync 複数回。単一DBのTxの数倍〜数十倍。

4. ロック保持時間が長い

prepare から commit までロックを持つ。その間、そのデータに触る全ての処理が待たされる。ホットな行では致命的。

⑨ Googleレベルではどう設計されるか

  • Spanner: 「コーディネータを冗長化する」ことでブロッキングを緩和 — コーディネータの決定ログを Paxos グループで複製するので、コーディネータのマシンが1台死んでも、別のレプリカが決定を知っていて続行できる。2PC の弱点は「単一のコーディネータ」であって「2PCそのもの」ではなかった、という洞察。これは面接で強い一言になる
  • participants も Paxos グループ — 参加者側も複製されているので、参加者1台の障害でも in-doubt にならない
  • 分散Txの頻度を下げる設計を強制する — Spanner の INTERLEAVE（親子行の同居配置）により、関連データが同じ Paxos グループに入るため、多くのTxが単一グループで完結する
  • Percolator: 「コーディネータ不要の2PC」 — Google のインデックス構築では、1つの行を「primary」に選び、その行のロック状態が Tx 全体の状態を表す。クライアントが死んでも、後から来た別のクライアントが primary を見て commit/rollback を判定できる。「決定の記録をデータの中に置く」ことで単一障害点を消した

⑩ 面接ではどう問われるか

Q. 「2PC を説明してください」（頻出。定義だけでなく弱点まで言えるか）
「複数ノードで commit の可否を一致させるプロトコルです。Phase 1（prepare）でコーディネータが全参加者に『commit できるか』を問い、各参加者は制約チェックとロック取得を済ませてログに永続化してから YES/NO を返します。この YES は取り消せない約束です。
Phase 2 で、全員 YES ならコーディネータが『commit』の決定を自分のログに書き（この瞬間が commit point）、全員に通知します。
弱点はブロッキング問題で、コーディネータが決定後・通知前に落ちると、参加者は prepared のまま commit も abort もできず、ロックを保持したまま固まります。これが可用性を下げ、マイクロサービスで避けられる理由です。
ただし Spanner のようにコーディネータ自体を Paxos で冗長化すれば、この弱点は緩和できます。実際 Spanner は 2PC を使っています」
Q. 「2PC はなぜ CAP の C を選んだと言われるのですか」
「ネットワーク分断が起きたとき、2PC は『不整合な状態で進む』ことを絶対に許さず、代わりに『止まる』ことを選ぶからです。参加者は分断の間 prepared のまま待ち続け、応答を返しません。
つまりPartition が起きたときに Consistency を守って Availability を捨てる = CP という選択です。
対照的に Saga は、分断中も各サービスがローカルに処理を進め、後から補償で整合させます。これはAP 寄りの選択で、『一時的な不整合を許すが止まらない』。どちらが正しいかはビジネス要件次第で、『座席の二重販売は絶対に許されない』なら CP、『通知が数秒遅れてもよい』なら AP です」

23 Three Phase Commit（3PC）— 教科書には載るが、使われない理由

結論: 3PC は「2PC のブロッキング問題を解こうとして、非現実的な前提を置いた」プロトコル。実運用のシステムではほぼ採用されていない。しかし「なぜ失敗したか」を理解すると、分散システムの本質的な難しさが分かる——面接ではこの理解が問われる。

💍 結婚式の例え（続き）。 2PC の問題は「司式者が倒れると2人が固まる」ことだった。
3PC の発想: 司式者が「これから宣言します」と予告してから、実際に宣言する。予告を聞いた2人は、司式者が倒れても「予告されたのだから、自分たちで結婚を成立させよう」と判断できる。
問題: 新郎だけが予告を聞き、新婦は聞いていなかったら？ 新郎は「成立」、新婦は「中止」と判断する。手紙が届くのに要する時間に上限がある（同期ネットワーク）ならこれは起きないが、現実の網はそうではない。

押さえるべき理論 — FLP 不可能性

1985年の FLP 定理（Fischer, Lynch, Paterson）は「完全非同期のネットワークで、1つでもノードが故障し得るなら、必ず合意に達する決定的アルゴリズムは存在しない」ことを証明した。

  • つまり「非同期 + 故障 + 必ず終わる + 必ず正しい」は同時に満たせない
  • 2PC は「必ず終わる」を諦めた（ブロックする）
  • 3PC は「必ず正しい」を（同期を仮定することで）諦めた——前提が崩れると壊れる
  • Paxos / Raft は「必ず終わる」を確率的に諦めた（理論上は終わらないことがあるが、実際にはほぼ必ず終わる）。これが現代の標準的な妥協点

面接での一言: 「3PC が使われないのは、『非同期ネットワークではブロックしない原子的コミットは不可能』という FLP の帰結を、同期の仮定で回避しようとしたが、その仮定が現実に成り立たないからです。現代は『コーディネータを Paxos で冗長化する』ことで実用的に解決しています」

面接ではどう問われるか

Q. 「3PC は 2PC の問題を解決しますか」
「理論上は解決しますが、実用上は解決しません。3PC は pre-commit フェーズを挟むことで、コーディネータ障害時に参加者が自律的に判断できるようにします。
しかしこれは『ネットワーク遅延に既知の上限がある』『故障を確実に検出できる』という前提の上でのみ正しいのです。現実のネットワークではこの前提が成り立たず、ネットワーク分断が起きると一部が commit、一部が abort という原子性の破壊が起こり得ます。
2PC は『止まる』のに対し、3PC は『壊れる』。安全性を優先する分散システムの価値観では、これは受け入れられません。
実務での答えは、コーディネータを Paxos/Raft で複製することです。Spanner や CockroachDB がこれをやっており、『コーディネータが単一障害点である』という 2PC の本当の問題を直接解いています」

24 XA と「DB + メッセージキュー」の罠

結論: XA は 2PC の業界標準実装だが、実務ではほぼ全ての場面で「使わない」が正解。特に「DBとメッセージキューを XA で結ぶ」は最も避けるべき構成。代わりに Outbox パターン（26章）を使う。この章は「なぜ避けるのか」を具体的に理解する章。

① XA とは何か

X/Open XA は、複数の異種リソース（DB、MQ、ファイルシステム）を1つの分散Txで束ねるための標準インターフェース。Java の JTA / JTS、アプリケーションサーバのトランザクションマネージャがこれを実装している。

⑦ XA を避けるべき5つの理由

#問題具体的に何が起きるか
1prepared Tx の滞留TM がクラッシュすると、DB に prepared な Tx が残る。ロックが解放されず、VACUUM も止まり、最終的にDBが停止する。手動で XA RECOVER して commit/rollback する運用が必要
2TM が単一障害点TM の可用性がシステム全体の可用性の上限になる。TM 自体を HA 構成にする複雑さが加わる
3対応リソースが限られるKafka、Redis、多くのクラウドサービス（S3、SQS、Stripe）は XA を実装していない。現代のアーキテクチャでは XA 対応リソースの方が少数派
4性能の低下ネットワーク往復とログ書き込みが増え、ロック保持時間が数倍〜数十倍に。スループットが1桁落ちる報告も多い
5MySQL の XA には歴史的な不具合があった5.7 以前では、XA prepare 後にサーバが再起動すると binlog との整合が壊れ、レプリカとデータが食い違うケースが知られていた。8.0 で改善されたが、この歴史が敬遠される一因

⑧ それでも XA が使われる場面

  • レガシーな基幹システム（金融・保険・製造） — メインフレーム、Oracle + WebLogic/WebSphere + MQ の構成。既に動いているものを書き換えるコストの方が高い
  • 同一ベンダーの製品同士 — Oracle DB + Oracle AQ など、組み合わせが検証されている場合
  • MySQL の内部XA（意識されない使用） — InnoDB の redo log と binlog の整合を取るために、MySQL は内部で 2PC を使っている。「XA を使わない」と言っても、DBの中では使われている
  • 新規設計で XA を選ぶ理由は、ほぼ無い

⑩ 面接ではどう問われるか

Q. 「DBに保存してKafkaにイベントを流したい。どう整合性を保ちますか」（超頻出・実務直結）
「これは二重書き込み問題（dual write problem）です。2つの独立したシステムに書くので、片方だけ成功する状態が必ず起こり得ます。
XA / 2PC で束ねるのは推奨しません。Kafka は XA を実質サポートしませんし、prepared Tx の滞留やトランザクションマネージャの単一障害点という運用負荷が大きすぎます。

これは『分散トランザクションを使わずに、分散トランザクションが欲しかった性質を得る』典型的な設計で、代償は『イベント配信が数秒遅れる』『重複が来る』の2つです。ほとんどの業務ではこれで十分です」
→ この答えができると、実務経験があると強く伝わる。

25 Saga Pattern — 「取り消す」のではなく「打ち消す」

結論: 長いトランザクションを、複数のローカルトランザクションの連鎖に分解し、失敗したら補償処理で打ち消す。原子性は得られるが、分離性は得られない——中間状態が外部から見える。この性質を理解した上で使うのが必須。マイクロサービスにおける事実上の標準解。

✈️ 旅行の予約の例え。 「航空券 + ホテル + レンタカー」を予約したい。3社に同時に「せーの」で予約させることはできない。
現実には1つずつ予約し、途中で失敗したら既に取った予約をキャンセルする。
重要なのは「キャンセル」は「予約が無かったこと」ではない点。キャンセル料が発生し、履歴に残り、その間に他の人がその席を見ることもできない。これが「補償は rollback ではない」ということ。

① この技術は何を解決するために生まれたのか

元論文は 1987年の "Sagas"（Garcia-Molina & Salem）で、当時の問題意識は「長時間実行されるトランザクション（LLT）がロックを保持し続けて、システム全体を止めてしまう」ことだった。

解決策: 長いTxを短いTxの列 T1, T2, ..., Tn に分解し、各 Ti に対する補償 Ci を定義する。途中で失敗したら、既に完了した Ti を逆順に補償していく。現代ではマイクロサービスの文脈で再発見された。

図25-1 Saga の全体像。「補償可能なものを前に、不可能なものを後ろに」がステップ順序の設計原則。

③ 基本概念 — 2つの実装スタイル

④ 内部でどのように動くのか — 実装の6つの必須要素

1. Saga の状態を永続化する

メモリ上で進行状況を持ってはいけない。オーケストレータがクラッシュしても、DBの状態から再開できること。「今どのステップまで完了したか」をテーブルに書く。

2. 全ステップを冪等にする

ネットワーク障害で「実行したか不明」が必ず起きるので、リトライしても同じ結果になる必要がある。冪等キー（saga_id + step）を各サービスに渡す。

3. 補償も冪等にする

補償のリトライも起こり得る。「2回返金した」は最悪の事故。

4. 補償は必ず成功するまで再試行する

補償が失敗したら Saga は不整合のまま止まる。補償は「絶対に成功する操作」として設計する（外部依存を最小に）。最終的には人間へエスカレーション。

5. タイムアウトと状態の可視化

「30分以上 pending の Saga」を検知するアラート。Saga は必ず滞留する。滞留の検知と手動介入の手段が運用に必須。

6. 意味的ロック（semantic lock）

中間状態を「処理中」と明示する（status = pending）。他の処理が「この注文は確定していない」と判断できるようにする。Isolation が無い Saga での唯一の防御。

i// Saga の状態テーブル（オーケストレーション型） CREATE TABLE saga_instances ( id uuid PRIMARY KEY, saga_type text NOT NULL, i// 'order_fulfillment' state text NOT NULL, i// 'started' | 'compensating' | 'completed' | 'failed' current_step int NOT NULL, payload jsonb NOT NULL, i// 注文ID、金額など completed_steps jsonb NOT NULL, i// ["create_order","reserve_stock"] ← 補償の対象 last_error text, retry_count int NOT NULL DEFAULT 0, created_at timestamptz NOT NULL, updated_at timestamptz NOT NULL ); CREATE INDEX ON saga_instances (state, updated_at); i// 滞留検知用 i// Go: オーケストレータの骨格 type Step struct { Name string Execute func(ctx context.Context, s *SagaInstance) error Compensate func(ctx context.Context, s *SagaInstance) error Retryable bool i// false なら即座に補償へ } func (o *Orchestrator) Run(ctx context.Context, saga *SagaInstance) error { for i := saga.CurrentStep; i < len(o.steps); i++ { step := o.steps[i] err := withRetry(ctx, step.Retryable, func() error { return step.Execute(ctx, saga) i// ★ 冪等キー = saga.ID + step.Name }) if err != nil { saga.State = "compensating" o.store.Save(ctx, saga) i// ★ 必ず永続化してから補償へ return o.compensate(ctx, saga, i-1) } saga.CurrentStep = i + 1 saga.CompletedSteps = append(saga.CompletedSteps, step.Name) if err := o.store.Save(ctx, saga); err != nil { i// ★ 各ステップ後に必ず保存 return err i// ここで落ちても、再開時に同じステップから（冪等なので安全） } } saga.State = "completed" return o.store.Save(ctx, saga) } func (o *Orchestrator) compensate(ctx context.Context, saga *SagaInstance, from int) error { for i := from; i >= 0; i-- { i// ★ 逆順に補償 step := o.steps[i] if step.Compensate == nil { continue } i// ★ 補償は成功するまで無限に近く再試行する（最終的には人間へ） if err := withInfiniteRetry(ctx, func() error { return step.Compensate(ctx, saga) }); err != nil { saga.State = "compensation_failed" o.alert.PageOnCall(saga) i// ★ 人間を起こす。放置してはいけない return err } } saga.State = "failed" return o.store.Save(ctx, saga) }

⑦ デメリット・トレードオフ — 「ACD」であって「ACID」ではない

性質Saga での扱い実務での意味
Atomicity補償により「実質的に」得られるただし「無かったこと」にはならない。履歴が残る
Consistency最終的には保たれる（結果整合）途中は矛盾している
Isolation得られない中間状態が他から見える。Dirty Read 相当のことが起きる。これが Saga 最大の弱点
Durability各ローカルTxで保証される問題なし

Isolation が無いことの具体例:

  • Lost Update 相当 — Saga の途中で別の処理が同じデータを更新し、補償で上書きしてしまう
  • Dirty Read 相当 — 「注文が作成された」状態を他サービスが見て処理を進めたが、後で補償されて消える
  • 対策1: 意味的ロック — status = 'pending' を立て、他の処理は pending を無視/拒否する
  • 対策2: 可換な操作にする — 「残高を100にする」ではなく「残高を-100する」。順序が変わっても結果が同じなら競合しない
  • 対策3: 悲観的な順序 — 「取り消す可能性が高いステップを最初に」。失敗の影響範囲を小さくする
  • 対策4: 値の再読み込み（reread value） — 更新の直前に値を読み直し、Saga 開始時と違っていたら中断する

⑧ 実務での利用例

  • Uber の配車フロー — 「乗車リクエスト → ドライバーのマッチング → 到着 → 乗車 → 決済」。各ステップは独立したサービスで、失敗時は補償（マッチング解除、返金）。物理世界が絡むので rollback は原理的に不可能——Saga しかない
  • Airbnb の予約フロー — 予約リクエスト → ホストの承認 → 決済 → 確定。「補償が業務プロセスとして最初から存在する」（キャンセルポリシー）のが Saga と相性が良い理由
  • AWS Step Functions — AWS が公式に「Saga パターンの実装手段」として Step Functions を紹介している。状態機械を定義し、失敗時の補償を Catch で書く
  • Temporal / Cadence（Uber 発） — 「コードとして書いたワークフローが、クラッシュしても続きから再開する」という実行基盤。Saga の状態管理を丸ごと引き受けてくれるので、現代の第一選択肢
  • Netflix の課金・配信フロー — 「サブスク登録 → 決済 → 権限付与」。決済の非同期性を前提に、権限付与を後追いで整合させる

⑨ Googleレベルではどう設計されるか

  • まず「Saga が要らない設計」を探す — Google 内部では、可能な限りSpanner の分散Txで済ませる。Saga は「外部システムが絡む」「補償が業務として自然」な場合に限定される。「インフラで解けるなら、アプリの複雑さを増やさない」という判断
  • Workflow エンジンを共通基盤にする — 各チームが独自に Saga を実装すると、状態管理・リトライ・可視化が毎回再発明される。共通のワークフロー実行基盤（Temporal 相当）を提供して、アプリは「ステップと補償」だけを書く
  • 冪等性を「プラットフォームの契約」にする — 全ての内部 RPC に冪等キーを持たせる規約を作る。個々のエンジニアが忘れる可能性を、フレームワークで消す
  • 観測性が設計の一部 — 「Saga が今どこで止まっているか」がダッシュボードで即座に分かること。Saga の運用コストの大半は『詰まったものの調査』なので、ここに最初から投資する

⑩ 面接ではどう問われるか

Q. 「Saga パターンを説明し、2PC との違いを述べてください」（頻出）
「Saga は長いトランザクションを複数のローカルトランザクションの列に分解し、各ステップに補償処理を用意して、失敗したら逆順に補償する手法です。
2PC との違いは3点。①ロックを跨いで保持しない——各ステップが即座に commit するので、可用性とスループットが高い。②Isolation が無い——中間状態が他から見えるので、意味的ロック（status=pending）などで自衛が必要。③『取り消し』ではなく『打ち消し』——注文はキャンセル済みとして残り、課金は返金として履歴に残る。
選択基準は『補償がビジネスとして自然か』です。EC の注文キャンセルや旅行予約は、そもそも業務プロセスとしてキャンセルが存在するので Saga が自然。一方、『座席を二重に売ってから片方を取り消す』が許されない領域では、2PC か単一DBに寄せるべきです」
Q. 「Saga の途中でオーケストレータがクラッシュしたらどうなりますか」
「Saga の状態をDBに永続化していれば、再起動後に続きから再開できます。これが必須要件で、メモリ上に進捗を持つ実装は使い物になりません。
再開時に問題になるのは『最後のステップが実行されたかどうか不明』な場合です。ステップ実行後・状態保存前に落ちると、同じステップを2回実行することになります。だから全てのステップを冪等にする必要があります——冪等キーとして saga_id + step_name を渡し、受け手側が重複を検出する。
運用面では、『N分以上進んでいない Saga』を検知するアラートと、手動で補償を起動できる管理画面が必要です。Saga は必ず詰まるので、詰まった時の運用手段を最初から設計に含めるのが実務です」
Q. 「補償処理が失敗したらどうしますか」（意地悪だが重要な質問）
「補償は『必ず成功する』ように設計するのが原則です。具体的には、補償処理の中で外部依存を最小にし、リトライ可能にし、副作用を単純にします（『在庫を戻す』のような単純な UPDATE）。
それでも失敗する場合は、①指数バックオフで長時間リトライし続ける（数時間〜数日）②それでも駄目なら人間にエスカレーションする（オンコールを起こす、管理画面に『要対応』として出す）。
絶対にやってはいけないのは、補償の失敗を握りつぶすことです。不整合が残ったまま気づかれず、後日の突合で発覚するのが最悪のパターンです。
設計としては、『補償が失敗し得るステップは、そもそも Saga の後半（ピボット以降）に置き、失敗したら前進で完遂する』という選択もあります」

26 Outbox Pattern — 分散トランザクションを「消す」

結論: 「DBに書く」と「イベントを送る」を1つのローカルトランザクションに畳み込む。これで二重書き込み問題が消える。現代のマイクロサービス設計で最も費用対効果の高いパターンであり、面接で知らないと減点されるレベルの必須知識。

📮 郵便の例え。 手紙を書いてポストに投函するとき、「書いた」と「投函した」の間で家が火事になったら手紙は失われる。
Outbox の発想は、「机の上の『発送トレイ』に置くところまでを1つの動作にする」。トレイに置いた時点で、記録として確実に残る。実際の投函は、後で郵便屋が回収してやってくれる。
郵便屋が2回配達してしまうことはある（重複）。だから受取人側が「この手紙は前に受け取った」と分かるようにしておく（冪等性）。

① この技術は何を解決するために生まれたのか

解決するのは 二重書き込み問題（dual write problem）——「DBとメッセージキューの両方に書く必要があるが、両者を原子的に更新できない」（24章）。

発想の転換: 「2箇所に原子的に書く」のではなく、「1箇所に書いて、そこから確実に伝える」。分散トランザクションを解くのではなく、分散トランザクションが不要な形に問題を変形する——これが優れた設計の典型例。

⑥ メリット

  • 分散トランザクションが要らなくなる — 使うのは普通のローカルTxだけ。運用の複雑さが激減する
  • イベントが絶対に失われない — DBに commit された時点で、イベントの配信が保証される
  • ブローカーが落ちていても業務は続く — outbox に溜まるだけ。復旧後に一気に配信される（障害の分離）
  • 監査ログとしても機能する — 「いつ何が起きたか」の完全な記録が残る
  • CDC への発展が容易 — outbox テーブルを Debezium で読めば、そのままイベント基盤になる

⑦ デメリット・トレードオフ

1. 配信が遅れる

ポーリング間隔分（数百ms〜数秒）の遅延。「即座に」が必要な処理には向かない。CDC なら数十ms まで縮む。

2. 重複配信が起きる（at-least-once）

受け手の冪等性が必須。これを忘れると「二重に在庫が減る」事故になる。Outbox は半分の解決策で、Inbox とセットで完成する。

3. 順序保証が限定的

グローバルな順序は保証されない。aggregate_id をパーティションキーにすることで「同一エンティティ内の順序」だけ保証するのが実務。

4. テーブルの肥大とDB負荷

大量のイベントで outbox が膨れる。送信済みの定期削除、パーティショニング、TTL の運用が必要。ポーリングはDBに継続的な負荷をかける。

⑧ 実務での利用例

  • Debezium + Outbox Event Router — Debezium は「Outbox パターン専用のルーター」を公式機能として提供している。outbox テーブルへの INSERT を検知し、指定されたトピックに自動でルーティングする。現代のデファクト実装
  • Airbnb の SpinalTap — MySQL の binlog を読んで変更イベントを配信する内製 CDC。「DBを更新すれば、検索インデックスもキャッシュも自動で追従する」基盤
  • Netflix の DBLog / Delta — 同様に CDC を基盤にしたデータ同期。「二重書き込みを設計から排除する」という思想が大規模組織で共有されている
  • Shopify / Stripe のイベント配信 — 外部向け Webhook も同じ構造。Stripe の Webhook が「同じイベントを複数回送ることがある」と明記しているのは、まさにこの at-least-once の性質
  • Uber の LedgerStore / 決済 — 金銭の記録とイベント配信を分離せず、同一Txで記録してから配信する設計

⑨ Googleレベルではどう設計されるか

  • 「ログを真実の源にする」思想 — Outbox の発展形は「DBの変更ログ（WAL）そのものをイベントストリームとして扱う」こと。別テーブルすら不要になり、DBへの書き込み＝イベント発行になる。Google 内部の多くのパイプラインはこの形
  • Spanner の Change Streams — Spanner はテーブルの変更を公式機能としてストリーム配信する。Outbox テーブルを手で作る必要が無い。「よくあるパターンは、インフラの機能として吸収する」という発想
  • 冪等性を全RPCの規約にする — 「受け手が冪等かどうか」を個々のエンジニアの注意力に任せない。フレームワークが request_id を強制し、重複検出を共通ミドルウェアで行う
  • 「exactly-once は存在しない」という共通理解 — 分散システムで exactly-once 配信は原理的に不可能。実現できるのは「at-least-once 配信 + 冪等な処理 = exactly-once 効果（effectively-once）」だけ。この区別を面接で言えると強い

⑩ 面接ではどう問われるか

Q. 「Outbox パターンを説明してください」
「二重書き込み問題を解くパターンです。業務データの更新とイベントの記録を、同じデータベースの同じトランザクションで行い（outbox テーブルへ INSERT）、別プロセスがそれを読んでメッセージブローカーに配信します。
これにより『DBは成功したがイベントが送られない』『イベントは送られたがDBが rollback された』という不整合が原理的に消えます。
配信は at-least-once なので、受け手側で event_id による重複排除（Inbox パターン）が必須です。この2つが揃って初めて『実質 exactly-once』になります。
Relay の実装はポーリングか CDC（Debezium）で、後者の方が遅延が小さくDBへの追加負荷もありません」
Q. 「exactly-once 配信は可能ですか」（引っかけ・上級）
「分散システムにおいて、厳密な exactly-once『配信』は不可能です。送信側は『届いたか』を知るために ACK が必要ですが、ACK が失われた場合に再送するか諦めるかを選ばねばならず、前者は重複、後者は欠落を生みます（two generals problem）。
実現できるのは『at-least-once 配信 + 冪等な処理 = effectively-once（実質1回）』です。Kafka の『exactly-once semantics』も、内部的にはプロデューサの冪等性とトランザクションによって『Kafka の中では』重複が見えないようにしているもので、外部システムとの間では成り立ちません。
だから設計では『重複は必ず来る』を前提に、冪等キーと重複排除を必ず入れます」
Q. 「Outbox のイベントの順序はどう保証しますか」
「グローバルな順序は保証しません（するべきでもありません）。全イベントを1本の列に直列化すると、スループットの上限がそこになるからです。
実務では『同一エンティティ内の順序』だけ保証します。具体的には outbox に aggregate_id（order_id など）を持たせ、それをKafka のパーティションキーにする。同じ注文のイベントは同じパーティションに入るので順序が保たれ、異なる注文同士は並列に処理できます。
加えて、受け手側でも順序が入れ替わり得る前提で設計するのが安全です。イベントにバージョン番号を持たせ、古いイベントが後から来たら無視する（順序に依存しない設計）」

Googleレベルの設計思想 — 5つの共通原則

  • 1. 弱い選択肢を提供しない — Spanner には Read Committed が無い。「選べる」ことは「間違えられる」こと。代わりに「古いデータを読む」という別軸の逃げ道を用意する
  • 2. 分散Txを「例外」にする配置設計 — INTERLEAVE、シャードキー設計、entity group。「大半のTxが単一グループで完結する」ようにデータを配置してから、残りを分散Txで扱う
  • 3. 単一障害点を合意アルゴリズムで消す — コーディネータも、ロック情報も、メタデータも、全て複製する。「1台が死んでも進む」を全レイヤで満たす
  • 4. リトライを言語/ライブラリレベルで吸収する — Serializable にすればアボートは必ず起きる。アプリ開発者にリトライを書かせず、クライアントライブラリが自動で再実行する（Spanner の runTransaction）
  • 5. 観測可能性を設計に含める — どのTxがどのキーで待っているか、アボート率、ロック待ち時間の分布。「なぜ遅いか分からない」状態を作らない

Q. 「Spanner はどうやってグローバルな強整合を実現していますか」（Google/Meta で頻出）
「3つの技術の組み合わせです。
①TrueTime——GPS と原子時計を使い、『真の時刻はこの区間の中にある』という不確実性の上限（通常数ms）を API で返す。時刻を正確にするのではなく、誤差の上限を保証するのが要点です。
②commit-wait——Tx に付けたタイムスタンプが確実に過去になるまで、commit の完了を数ms 意図的に遅らせる。これにより『commit が完了した後に始まった Tx は、必ず大きいタイムスタンプを持つ』ことが保証され、Serializable より強い External Consistency が得られます。
③Paxos + 2PC——データ範囲ごとに Paxos グループを作り、グループ跨ぎのTxは 2PC。重要なのは、2PC のコーディネータ自体も Paxos グループであること。これによりコーディネータ障害でブロックするという 2PC 最大の弱点が実用上解消されます。
代償は commit のレイテンシ（数ms の待ち + Paxos の往復）と、専用ハードウェアへの依存です」
Q. 「Spanner のような分散DBがあるなら、Saga は不要では？」
「DB内部の整合性は不要になりますが、Saga が必要な場面は残ります。
理由は、外部システム（決済API、メール送信、物理的な出荷）は Spanner のTxに参加できないからです。Stripe に課金した後で rollback することはできず、返金という補償操作しかありません。
また、組織的な理由もあります。マイクロサービスが別チームで運用され、それぞれ別のDBを持つ場合、Spanner を共有すると『疎結合』というマイクロサービスの目的が損なわれます。
整理すると: DB内部の整合 → 分散DBで解決。外部システムや組織境界を跨ぐ整合 → Saga + 冪等性。両者は競合せず、レイヤが違います」

29 ドメイン設計①: 銀行送金 — 複式簿記とべき等性

結論: 残高を UPDATE してはいけない。「取引を追記し、残高は導出する」（複式簿記）のが金融システムの標準設計。これにより Lost Update が原理的に消え、監査可能性が得られ、分散にも耐える。

🏦 実際の銀行の帳簿。 銀行は「残高」という数字を書き換えていない。取引を1行ずつ追記し、残高はその合計として計算される。
なぜか。「なぜこの残高になったか」を後から証明できなければならないから（監査）。そして追記は上書きより安全だから——追記は失われた更新を生まない。
500年前にヴェネツィアの商人が発明した複式簿記が、現代の分散システムでも最適解であり続けている。

30 ドメイン設計②: EC在庫 — 確保と確定を分ける

結論: 「在庫を減らす」を1つの操作にしない。①仮確保（reserve）②確定（commit）③解放（release）の3状態に分けることで、Saga とタイムアウトに耐える設計になる。さらに人気商品のホットスポットという別種の問題を解く必要がある。

🛒 物流倉庫の例え。 現実の倉庫では、注文が入ると商品を棚から「出荷準備エリア」に移す。まだ出荷はしていないが、他の注文には割り当てられない。在庫は「棚にある」でも「出荷済み」でもない第3の状態にある。
決済が失敗したら棚に戻す。決済が成功したら出荷する。この「準備エリア」に相当するのが reserved（引当済み）。
「在庫を減らす」という1つの数字の操作にしてしまうと、この現実のプロセスを表現できない。

個別に読む — 特に学ぶ価値のある3つの設計

1. Airbnb「二重支払いの回避」（2019年の公開記事）

決済APIのタイムアウト時にリトライすると二重課金になる問題を、冪等キーをライブラリ化して全サービスに強制することで解決した事例。要点は「冪等キーをシャードキーに含める」ことで、リトライが必ず同じシャードに届くようにした点。技術記事として最も実用的。

2. YouTube / Vitess の「単一シャードへの寄せ」

Vitess は 2PC を実装しているが、公式ドキュメントは「性能上のコストが大きいので、可能な限り単一シャードで完結させよ」と明記している。「機能があること」と「使うべきこと」は別という好例。

3. Instagram のシャード内ID生成

PostgreSQL のシャードごとに、シャードID + タイムスタンプ + 連番を組み合わせたIDを生成する関数をDB内に持つ。中央の採番サービスが不要になり、「一意性のための分散調整」そのものを消した。分散Txを避ける最良の方法は、そもそも調整が要らないキー設計をすること。

4. Uber / Cadence（現 Temporal）

Saga の状態管理・リトライ・タイムアウトを毎回書くのが限界だったため、「ワークフローをコードとして書けば、クラッシュしても続きから再開する」実行基盤を自社で作った。大規模組織では、パターンを「共通基盤」に落とすのが最終的な答えになる。

面接での使い方

Q. 「大規模サービスでも ACID トランザクションは使われていますか」
「使われていますが、範囲が非常に限定されています。共通するパターンは3つです。
①強整合を使うのは、金銭・在庫・一意性の3領域だけ。注文確定、決済、ユーザー名の重複防止など。
②カウンタ（いいね数、再生回数）と配信（タイムライン）は必ず非同期。YouTube の再生回数が即座に反映されないのは、技術的な妥協ではなく意図的な設計です。
③シャードキーの設計で、分散Txが必要になる状況そのものを減らす。Instagram はIDをシャード内で生成し、YouTube の Vitess は単一シャードへの寄せを推奨しています。
つまり『強整合を諦める』のではなく『強整合が必要な範囲を、設計で小さくする』のが大規模サービスの答えです」

33 理解度チェック — 25問

各問、まず自分で答えてから開いてください。「なんとなく分かる」と「説明できる」の間には大きな差があります。7割を自力で説明できなければ、該当章に戻ることを推奨。

Part 1: 基礎（1〜5）

Q1. Atomicity と Isolation の違いを1文ずつで説明してください
Atomicity: 途中で失敗しても、その Tx の変更が全部取り消される（＝アボート可能性）。守る相手はクラッシュや障害。
Isolation: 同時に実行されている他の Tx から、自分の途中状態が見えない/影響を受けない。守る相手は並行する他の Tx。
よくある誤解: 「atomic だから同時に見える」は誤り。同時性は Isolation の役割。（1章・2章）
Q2. ACID の C（Consistency）はなぜ「DBの機能ではない」と言われるのですか
C は「アプリ固有の不変条件が Tx の前後で保たれること」で、何が『一貫している』かはアプリのビジネスルールが決めるため。DB は UNIQUE や CHECK といった強制する手段を提供するだけで、「借方＝貸方」のようなルールを知る術がない。
DDIA でも「C は頭文字を ACID にするために足された」という指摘が引用されている。CAP の C（線形化可能性）とは全く別物。（2章）
Q3. WAL の「先に書く」とは何を先に書くのですか。なぜそれで速くなるのですか
データページを変更する前に、変更内容をログに書いて fsync する。
速くなる理由: データページの更新は複数箇所へのランダム書き込みだが、WAL は1本のファイルへのシーケンシャル追記なので、commit に必要なディスクI/Oが「末尾への1回の書き込み」に圧縮される。データページの反映は後回しでよい（クラッシュしてもログから再現できるため）。安全性と性能を同時に得る珍しい設計。（3章）
Q4. undo ログは rollback 以外に何に使われますか
MVCC の「過去のバージョン」の再構築。MySQL InnoDB では、テーブルには最新版だけを置き、古い版が必要なときは DB_ROLL_PTR で undo チェーンを辿って再構築する。
この性質から、長時間トランザクションがあると undo が回収できず肥大し、読み取りが遅くなるという運用上の問題が生じる。（3章・14章）
Q5. 「COMMIT が成功した」と言えるのはどの瞬間ですか
単一ノードなら「WAL の COMMIT レコードが fsync された瞬間」。分散なら「合意グループの過半数に複製された瞬間」。
注意点: ①設定次第で fsync を省略できる（速いが失う可能性がある）②非同期レプリケーションでは、フェイルオーバー時に消え得る ③クライアントが応答を受け取れなかった場合は「成功か失敗か不明」という第3の状態で、これが冪等性が必要な理由。（1章・3章）

Part 2: 異常（6〜11）

Q6. Lost Update と Write Skew の違いは何ですか
読んだ行と書いた行が同じか違うか。
Lost Update: 同じ行を読んで同じ行に書く → その行をロックすれば防げる（FOR UPDATE、原子的UPDATE）。
Write Skew: 読んだ行と書く行が違う（他の当直医を読んで、自分の行を更新） → 書く行をロックしても防げない。読んだ範囲全体を守る必要があり、Serializable か制約か明示ロックが要る。（6章・8章）
Q7. なぜ Phantom Read は行ロックで防げないのですか
まだ存在しない行にはロックを掛けられないから。「10/1に予約が無いこと」を守りたいが、無いものにはロック対象が存在しない。
対策は①ギャップロック / next-key lock（インデックス上の隙間をロック。MySQL）②SSI（読んだ範囲を記録し、commit 時に検証。PostgreSQL）③制約に落とす（UNIQUE / EXCLUDE。実務での最良解）。（8章・15章）
Q8. Snapshot Isolation で防げない異常は何ですか。それはなぜですか
Write Skew。SI は「読み取りはスナップショットから」「書き込みが衝突したら片方を中断」の2ルールで動くが、Write Skew では2つの Tx が別々の行に書くので、書き込みの衝突が発生しない。
破れているのは「読んだ結果に基づく前提」であり、SI は読み取りと書き込みの間の依存（rw依存）を追跡していない。PostgreSQL の SSI はこの rw 依存を追跡することで SI を Serializable に拡張している。（11章・12章）
Q9. MySQL の REPEATABLE READ で Lost Update は防げますか
防げません（PostgreSQL の RR は検出してエラーにする）。
さらに MySQL RR には独特の挙動があり、SELECT はスナップショットから読むが、UPDATE は最新のcommit済みバージョンに適用される。そのため「同じ Tx 内で、SELECT した値と UPDATE が使う値が違う」ことが起こる。
対策は①原子的UPDATE ②FOR UPDATE ③version 列。（6章・11章・13章）
Q10. Non Repeatable Read が実害になる具体的な場面を挙げてください
①バックアップ——数時間かかるダンプの途中で更新が入ると、「送金の片側だけ入ったバックアップ」ができる（mysqldump --single-transaction を付け忘れる事故）②複数テーブルを跨ぐ集計・レポート——数字が合わない ③整合性チェックバッチ——検査自体が誤検知する。
対策は Repeatable Read の読み取り専用Txにするか、1つのクエリにまとめる。（7章）
Q11. Dirty Read を防ぐために Read Uncommitted を避ける以外の対策は必要ですか
基本的に不要。Read Committed 以上なら防がれ、PostgreSQL では Read Uncommitted を指定しても RC として動くため原理的に起きない。
ただし「Tx 内で外部システムを呼ぶ」という設計は、Dirty Read でなくても同じ問題（自分が rollback したのに副作用が残る）を起こすので、そちらの方が実務では重要。（5章・20章）

Part 3-4: Isolation Level と実装（12〜18）

Q12. MVCC の可視性判定はどう行われますか
各行バージョンが「作成した Tx ID（xmin）」と「削除した Tx ID（xmax）」を持ち、Tx 開始時に取得したスナップショット（＝その時点で実行中だった Tx ID の集合）と比較する。
「xmin が commit 済みかつ自分より前」かつ「xmax が無いか、未commit/自分より後」なら見える。判定に必要な情報が全て手元にあるので、読み取りがロックを必要としない。（14章）
Q13. 長時間トランザクションが1本あるだけで、なぜDB全体が劣化するのですか
MVCC の古いバージョンを回収できなくなるから。最も古い実行中の Tx が見る可能性のあるバージョンは削除できないため、1本の放置Txが、無関係なテーブルの回収まで止める。
PG ではテーブル肥大（bloat）と xid wraparound、MySQL では undo 肥大と History list の伸長として現れる。対策は idle_in_transaction_session_timeout、Tx の短縮、分析クエリのレプリカ隔離。（14章）
Q14. InnoDB の行ロックは何に対して掛かりますか。それがなぜ重要ですか
インデックスエントリに対して掛かる。したがってWHERE 句にインデックスが使えないと、走査した全行（RR ではギャップも含む）にロックが掛かり、実質テーブルロックになる。
「1行だけ更新するはずのクエリで本番が止まった」の典型的な原因。更新・削除の WHERE 句にインデックスがあることの確認は、コードレビューの必須項目。（15章）
Q15. 楽観ロックと悲観ロックはどう使い分けますか
競合率と、ロックを保持できる時間で決める。
楽観: 競合が稀（数%以下）/ 人間の思考時間や複数リクエストを跨ぐ / 分散環境でロックを保持できない。
悲観: 競合が頻繁 / やり直しのコストが高い / 短いTxで完結する。
損益分岐点は競合率10〜20%程度。競合率が50%を超えるならデータモデル自体を疑う（分割、キューによる直列化）。（17章・18章）
Q16. デッドロックを減らす最も効果的な方法は何ですか
ロックの取得順序をシステム全体で統一する（ID昇順など）。循環待機が構造的に作れなくなるため。
次点で①Tx を短くする ②インデックスを確認する（範囲ロックの縮小）③S ロックからの昇格を避け最初から X を取る。
「デッドロックをゼロにする」は目標として誤り。起きる前提でリトライを実装し、発生率を監視する。（19章）
Q17. PostgreSQL の Serializable でアボートが多発するとき、まず何を確認しますか
インデックス。SSI は「読んだ範囲」を SIREAD で追跡するので、フルスキャンすると『全行を読んだ』ことになり、偽陽性のアボートが激増する。適切なインデックスで読み取り範囲を狭めるだけで劇的に改善することが多い。
次に Tx の短縮、READ ONLY の明示、ホットな行の分割。（12章）
Q18. Go で Tx を扱うときの典型的なバグを3つ挙げてください
①Rollback を忘れる（defer tx.Rollback() を書かず、途中 return で接続が返らない）②Tx 内で db を直接使う（別接続＝別Txになり原子性が壊れる）③Tx 内で外部API を呼ぶ（接続プール枯渇で全断）。
他に、Context を渡し忘れる、Rows を Close しない、Tx をゴルーチンで共有する、など。（20章）

Part 5-6: 分散とドメイン（19〜25）

Q19. 2PC のブロッキング問題とは何ですか
コーディネータが「commit する」と決定した後、通知の前にクラッシュすると、参加者は prepared 状態から動けなくなる問題。参加者は commit も abort も自分では決められず、ロックを保持したまま固まるため、そのデータに触る他の処理も止まる。
2PC は「安全性（全員が同じ結論に至る）は守るが、進行性（いつ結論が出るか）は保証しない」。（22章）
Q20. Spanner はどうやってブロッキング問題を緩和していますか
コーディネータ自体を Paxos グループにする。決定ログが過半数のレプリカに複製されるため、コーディネータのマシンが1台死んでも、別のレプリカが決定を知っていて続行できる。
「2PC の弱点は 2PC そのものではなく、単一のコーディネータだった」という洞察が要点。（22章・28章）
Q21. 3PC が実用されない理由は何ですか
「同期ネットワーク（遅延に既知の上限がある）」「完全な故障検出」という前提が、現実のネットワークで成り立たないから。前提が崩れると、ネットワーク分断時に一部 commit・一部 abort という原子性の破壊が起こり得る。
2PC は「止まる」が、3PC は「壊れる」。安全性を優先する価値観では受け入れられない。（23章）
Q22. Outbox パターンは何を解決しますか。単独で完成しますか
二重書き込み問題（DBとメッセージキューの両方に書く必要があるが原子的にできない）を解決する。業務データとイベントを同じDBの同じTxで書き、別プロセスが配信する。
単独では完成しない。配信は at-least-once なので、受け手側の冪等性（Inbox パターン）が必須。この2つでようやく「実質 exactly-once」になる。（26章）
Q23. Saga で得られないものは何ですか
Isolation（分離性）。各ステップが即座に commit されるため、中間状態が他のTxから見える。「在庫は減っているが注文は未確定」という状態が観測できてしまう。
対策は①意味的ロック（status = pending を立てて他の処理に無視させる）②可換な操作にする ③値の再読み込みによる検証。（25章）
Q24. 送金システムで残高を UPDATE しない理由を3つ挙げてください
①監査可能性——「なぜこの残高か」を証明できる。金融規制の要件 ②Lost Update の排除——追記は上書きしないので、失われた更新が原理的に起きない ③補償が自然に書ける——Saga の補償を「逆仕訳の追記」として表現でき、履歴が正しく残る。
残高はスナップショット行として持ち、日次で ledger の集計と突合する。（29章）
Q25. 「在庫1個に10万リクエスト」への対処を、効果の大きい順に挙げてください
①手前で削る——レート制限、待機列、抽選。在庫100個に10万リクエストなら、99.9%はDBに到達させる必要が無い ②Redis の前段カウンタ——DECR で弾く（ただしDB側の制約が最後の防壁）③キューで直列化——SKU ごとに1コンシューマ。競合が原理的にゼロ ④在庫の分割（sharded counter）。
「DBの1行を守る」より「DBに到達させない」方が本質的。（30章）

34 システム設計面接 12問 — 想定問答

Google / Meta / Amazon のシステム設計面接で実際に問われる形式。「正解の暗記」ではなく「トレードオフを言語化する構造」を身につけるための12問。各問、①要件確認 ②素朴な案 ③問題点 ④改善 ⑤限界の順で答えるのが基本形。

Q1. チケット販売システムを設計してください。人気公演では発売開始1秒間に10万リクエストが来ます
① 要件確認（必ず最初にする）: 「座席指定はありますか？」「オーバーセルは絶対に許されませんか？」「先着順ですか抽選ですか？」この3つで設計が全く変わります。

② 全体構成: 「10万 req/s をDBで受けるのは不可能なので、3段構えにします。第1段: 手前で削る——CDN と API Gateway でレート制限、待機列（バーチャルウェイティングルーム）で流入を制御。第2段: Redis の在庫カウンタ——DECR で座席数を超えたら即座に売り切れ応答。DBには到達させない。第3段: DBでの確定——Redis を通過したリクエストだけがDBに届く。ここは秒間数千で済む」

③ 正しさの担保: 「Redis はフィルタであり真実の源ではないので、DB側に CHECK (sold <= capacity) と UNIQUE(event_id, seat_id) を必ず置きます。Redis がズレても、DBが最後の防壁になる。座席指定なら『座席×公演』の一意制約が効きます」

④ 予約の状態遷移: 「held（仮押さえ、TTL 10分）→ paid → issued。決済に時間がかかるので、確保と確定を分ける。期限切れの held を回収するバッチが止まると『在庫はあるのに買えない』障害になるので、監視必須です」

⑤ 限界と代替案: 「先着順である限り、瞬間的な集中は避けられません。ビジネス側と『抽選にする』選択肢を議論すべきです。技術的にも、抽選なら受付を非同期にでき、10万リクエストをキューに入れて後で処理できます。最も効果的な解決策が技術ではないこともある、と言えるのは強い」
Q2. マイクロサービス構成で、注文・在庫・決済の整合性をどう保ちますか
① まず分割を疑う: 「なぜ分かれているのかを確認させてください。『注文と在庫が常に同時に更新される』なら、それらは同じ集約であり、同じサービス・同じDBに置くべきかもしれません。マイクロサービスの分割線の誤りを、分散トランザクションで補うのは悪手です」

② 分割が正当なら Saga: 「オーケストレーション型を選びます。ステップは 注文作成(pending) → 在庫引当 → 決済 → 配送手配 → 注文確定。失敗したら逆順に補償（引当解除、返金）。補償が困難なステップ（出荷、メール送信）はできるだけ後ろに置きます」

③ 各サービス間の通信は Outbox: 「サービスAがDBを更新してイベントを送る部分は、outbox テーブルへの INSERT を同一Txで行い、CDC または Relay が配信します。これで二重書き込み問題が消えます。受け手は event_id で冪等に処理」

④ Isolation が無いことへの対処: 「Saga には分離性が無いので、注文は pending という『意味的ロック』の状態を持ち、確定するまで他の処理から『まだ有効でない』と扱われるようにします」

⑤ 運用: 「Saga は必ず詰まります。『N分以上進んでいない Saga』のアラートと、手動で補償を起動できる管理画面を最初から作ります。実装は Temporal のようなワークフロー基盤に乗せると、状態管理とリトライを自前で書かずに済みます」
Q3. DBに保存してKafkaにイベントを送る処理で、両方の成功をどう保証しますか
「これは二重書き込み問題です。XA / 2PC で束ねるのは推奨しません（Kafka は実質サポートせず、prepared Tx の滞留とコーディネータの単一障害点が運用を殺す）。
Outbox パターンを使います。①業務データとイベントを同じDB・同じTxで書く ②Relay（ポーリングまたは Debezium による CDC）が outbox を読んで Kafka へ配信 ③消費側は event_id で重複排除（Inbox）。
代償は2つ: 配信が数百ms〜数秒遅れること、重複配信があること。ほとんどの業務でこれは許容できます。
補足として、exactly-once 配信は分散システムでは原理的に不可能で、実現できるのは『at-least-once + 冪等処理 = effectively-once』だけです」
Q4. 会議室予約システムで二重予約を防いでください
「これは Write Skew / Phantom Read です。『空きを確認してから予約』は、確認時点で相手の予約がまだ存在しないため、Snapshot Isolation でも防げません。
第一選択は制約に落とすこと: PostgreSQL なら EXCLUDE USING gist (room_id WITH =, period WITH &&)。アプリは『INSERT して例外が出たら埋まっていた』と書く。確認しないので隙間が存在しません。
MySQL なら離散化: 時間枠を15分刻みにして UNIQUE(room_id, slot_start)。1時間予約なら4行 INSERT し、1つでも重複すれば Tx の原子性で全体が失敗します。
代替案の比較: SERIALIZABLE + リトライ、アドバイザリロックもありますが、制約は『どの経路からも、10年後の誰のコードからも破れない』点で最強なので優先します。制約で表現できない複雑な条件（『1人月10時間まで』）だけ、Serializable かアプリロックで守ります」
Q5. Isolation Level を Serializable に上げると何が起きますか
「実装によって払う場所が違います。
PostgreSQL（SSI・楽観型）: 読み取りはブロックしませんが、競合時に 40001 でアボートするのでリトライ実装が必須。高競合ではアボートの無駄が積み上がります。
MySQL（2PL・悲観型）: 読み取りにも共有ロックが必要になり、読み手が書き手をブロックします。デッドロックが増え、P99 レイテンシが悪化します。
共通の注意: Serializable にしてもTx の外は守られません。Tx 内で読んだ値をキャッシュに書いたり外部APIを呼んだりすれば、そこは穴として残ります。
実務の判断: 全体を上げるのではなく『金銭や在庫に触るユースケースだけ Serializable、他は Read Committed + 明示的な守り』という部分適用にします」
Q6. 決済APIの遅延で、無関係なAPIまで応答しなくなりました。原因と対策は
「Tx 内で外部APIを呼んでいて、接続プールが枯渇したと考えます。DB接続は有限なので、遅い外部API待ちのTxが全接続を占有すると、DBを使う全処理が止まります。
対策は3段階。①Tx を分割——『注文を pending で作成して commit』『外部API呼び出し（Tx外）』『結果を反映して commit』。これは Saga の考え方そのもの。②全経路にタイムアウト——context の締切、HTTP クライアント、DB の statement_timeout / lock_timeout。③バルクヘッド——参照用と更新用でプールを分け、重い処理が軽い処理を巻き込まないようにする。
原則は『ロックや接続という有限資源を、自分が制御できない待ち時間に晒さない』ことです」
Q7. シャーディングされたDBで、シャードを跨ぐトランザクションが必要です。どうしますか
「順に4つ検討します。
①シャードキーを変えて同居させられないか——注文と明細なら order_id、ユーザーの全データなら user_id でシャード。これが最良の解で、Spanner の INTERLEAVE や Vitess の keyspace もこの思想です。
②そもそも同時である必要があるか——数秒遅れてよいなら Saga + Outbox。
③2PC を使う——Vitess は 2PC を持ちますが、公式にも『性能コストが大きいので単一シャードに寄せよ』と書かれています。使うなら prepared Tx の監視が必須。
④分散DBに移行する——Spanner / CockroachDB。アプリの複雑さをインフラのコストで買う判断。グローバル展開や強整合が本質的に必要なら合理的です。
面接では『まず①を試す』と言うこと自体が評価されます」
Q8. 「いいね数」を正確かつ高速に表示するには
「まず『正確』の定義を確認します。『最終的に合っていればよい』なら答えが大きく変わります。実際、X も YouTube もリアルタイムには正確でない設計を採用しています。
設計: ①いいねは追記——likes(user_id, post_id) に INSERT（UNIQUE 制約で二重いいねを防ぐ。これは強整合が必要）②カウントは非同期集計——Kafka や CDC で流し、集計結果をキャッシュに書く ③表示はキャッシュから——数秒〜数分の遅延を許容。
なぜカウンタを UPDATE しないか: 人気投稿では1行に書き込みが集中し、その1行がシステム全体のボトルネックになるからです。どうしてもDBで持つなら sharded counter（N行に分割してSUM）。
UX の工夫: 「自分の『いいね』は即座に反映して見せる（楽観的UI）。他人のいいね数は遅れてよい」——一貫性の要求はユーザーの視点によって違うという指摘は評価されます」
Q9. 二重課金を防ぐ設計を説明してください
「冪等キー（idempotency key）が中核です。
①クライアントが一意なキーを生成してリクエストに含める（UUID）。サーバが生成してはいけません——リトライ時に同じキーである必要があるため。
②サーバは冪等キーを主キーとするテーブルに INSERT。ON CONFLICT DO NOTHING で0行なら既に処理済みとして、1回目の結果を返します（エラーにしない）。
③外部決済APIにも冪等キーを渡す（Stripe の Idempotency-Key ヘッダ）。自社の防御だけでは不十分で、外部への呼び出しも二重にならないようにする。
④『不明』状態を持つ——タイムアウトは失敗ではないので、status に unknown を用意し、照会APIで後から確定させる。
⑤日次の突合——決済事業者の明細と自社の記録を照合。金銭系では突合は『設計の一部』です。
Airbnb が『Avoiding Double Payments in a Distributed Payments System』という記事でこの設計を公開しており、冪等キーをシャードキーに含める工夫が参考になります」
Q10. Spanner のような分散DBを使えば、全ての整合性問題は解決しますか
「DB内部の整合性は解決しますが、2つの問題が残ります。
①外部システムは参加できない——決済API、メール送信、物理的な出荷。Stripe に課金した後で rollback はできず、返金という補償しかありません。ここは Saga + 冪等性が必要です。
②組織の境界——マイクロサービスが別チームで運用されている場合、DBを共有すると独立性が失われます。技術的に可能でも組織的に選べないことがある。
さらにコストの問題: Spanner は高価で、commit に数ms の待ち（commit-wait）が入ります。『単一リージョンで済むなら PostgreSQL の方が安くて速い』という判断も正当です。
整理: DB内部の整合 → 分散DBで解決可能。外部システムや組織境界 → Saga。この2つはレイヤが違う」
Q11. あるテーブルへの UPDATE が遅くなりました。調査手順を説明してください
「4つの層で切り分けます。
①ロック待ちか——PG なら pg_stat_activity.wait_event と pg_locks、MySQL なら performance_schema.data_locks と SHOW ENGINE INNODB STATUS。長時間ロックを保持しているTxを特定する。
②ロック範囲が広すぎないか——EXPLAIN でインデックスが使われているか確認。インデックスが無いと走査した全行にロックが掛かる。
③MVCC の GC が滞っていないか——PG なら dead tuple 数と autovacuum の状態、MySQL なら History list length。長時間Txが原因のことが非常に多い。
④I/O やリソースの問題か——バッファプールのヒット率、ディスクの latency、チェックポイントの頻度。
実務では①か③が大半です。そして両方とも根本原因は『どこかに長いトランザクションがある』ことが多い」
Q12. あなたが設計したシステムで、並行性のバグが起きたときどう発見しますか
「並行性のバグは再現しないので、『発見の仕組み』を最初から設計に入れます。
①突合バッチ——「在庫テーブルの合計 = 入出庫履歴の合計」「複式簿記の全エントリの合計 = 0」のような不変条件を定期的に検証し、ズレたら即アラート。これが最も効果的です。
②DB制約を最後の防壁にする——CHECK (stock >= 0) があれば、バグが起きた瞬間にエラーとして顕在化します。制約が無いと静かにデータが壊れる。
③メトリクス——デッドロック数、シリアライゼーション失敗数、リトライ率、ロック待ち時間。急増は設計の問題を示すシグナル。
④負荷試験で並行性を再現する——同一リソースへの並行アクセスを意図的に作り、不変条件が壊れないか検証する。通常のE2Eテストでは絶対に見つかりません。
『バグを防ぐ』だけでなく『バグが起きたことに気づける』設計を選ぶ、という姿勢が本質です」

設計ミスの「型」に還元すると6つしかない

  1. 読んでから書くまでの隙間を守っていない（#1, #5, #6）→ 最頻出。原子的UPDATE か FOR UPDATE か version 列。コードレビューで「SELECT した値で判断して書いている箇所」を探すのが最も効率的
  2. 「無いことの確認」をアプリでやっている（#2, #3, #4）→ 制約に落とす。確認せず書いて、弾かれたら埋まっていた、と反転する
  3. 有限資源を、制御できない待ち時間に晒した（#7, #8, #21）→ Tx 内で外部通信をしない、タイムアウトを全経路に、インデックスで範囲を絞る
  4. Tx を長くした（#11, #12, #13, #24）→ MVCC のGCを止め、ロックを長く持ち、失敗時のコストを上げる。「Tx は短く」が最も効く原則
  5. 分散を「無かったこと」にした（#16, #17, #18, #20）→ 二重書き込み、冪等性の欠如、Saga の滞留。Outbox + 冪等キー + 滞留監視の3点セット
  6. 壊れたことに気づく仕組みが無い（全て）→ 並行性のバグは再現しない。突合バッチ、DB制約、メトリクスという「発見の仕組み」を設計に含める

付録 チートシート

1. Tx を使う判断

「守るべき不変条件」を言語化できるかを先に問う。言えないTxは、ただ遅くしているだけ。境界はUseCase 単位に引き、Repository の中で commit しない。

2. ACID の非対称性

A/D はクラッシュ対策（DBの機能）、I は同時実行対策（強度を選ぶダイヤル）、C はアプリが定義する不変条件。「ACID準拠だから安全」は無意味な発言。

3. 異常の6分類

Dirty Write / Dirty Read（相手が未commit）、Non Repeatable / Phantom（相手がcommit済み・行 or 範囲）、Lost Update / Write Skew（読んで判断して書いた）。実務の事故は後者2つが9割。

4. 既定設定は安全ではない

PG の RC も MySQL の RR も、Lost Update と Write Skew を防いでいない。「トランザクションで囲んだから安全」は誤り。危険な箇所は明示的に守る。

5. Lost Update の対策（上から検討）

①原子的UPDATE（SET x = x - 1 WHERE x >= 1、影響行数で判定）②FOR UPDATE ③version 列 ④Serializable + リトライ ⑤競合しない設計（分割・キュー）。

6. Phantom / Write Skew の対策

①制約に落とす（UNIQUE / EXCLUDE）②実体化衝突（スロット行を作って FOR UPDATE）③Serializable ④アドバイザリロック。「確認して書く」を「書いて弾かれる」に反転。

7. Isolation Level の実装差

PG RR = SI（Lost Update を検出しエラー）、MySQL RR = SI + next-key lock（Lost Update は静かに起きる）、Oracle の SERIALIZABLE = 実は SI。名前でなく挙動で会話する。

8. MVCC の代償

読み取りはロックしないが、古いバージョンを回収できないと全体が劣化する。長時間Txは1本でDB全体を止める。idle_in_transaction_session_timeout を必ず設定。

9. ロックの最重要事実

InnoDB の行ロックはインデックスエントリに掛かる。WHERE 句にインデックスが無いと走査した全行がロックされる。更新系の EXPLAIN 確認はレビュー必須項目。

10. 楽観 vs 悲観

競合率10〜20%が損益分岐点。低競合・思考時間を跨ぐ → 楽観、高競合・短いTx → 悲観。競合率50%超えはデータモデルを疑うシグナル。

11. デッドロック対策

①ロック順序の統一（ID昇順）——これで9割消える ②Tx を短く ③インデックス ④リトライ（40001/40P01/1213/1205 を指数バックオフで）。ゼロにするのは目標として誤り。

12. Go の Tx 三大バグ

①defer tx.Rollback() を書かない ②Tx 内で db を直接使う ③Tx 内で外部APIを呼ぶ。③は接続プール枯渇による全断に直結。

13. 分散の前に問う5つ

①分けずに済むか ②同じシャードに置けるか ③同時でなくてよいか ④補償できるか ⑤本当に原子性が必要か。面接ではこの順で潰してから道具を選ぶ。

14. 2PC の要点

prepare = 取り消せない約束。弱点はコーディネータ障害時のブロッキング（ロックを持ったまま固まる）。Spanner はコーディネータを Paxos で冗長化して解決。

15. Saga の要点

ACD であって ACID ではない（Isolation が無い）。補償可能なステップを前に、不可能なものを後ろに。状態の永続化・全ステップの冪等性・滞留の監視が必須3点。

16. Outbox の要点

業務データとイベントを同一DB・同一Txで書き、Relay/CDC が配信。単独では不完全で、受け手の冪等性（Inbox）とセット。exactly-once 配信は存在しない。

17. 冪等キーの作法

クライアントが生成（サーバ生成ではリトライで別キーになる）。主キーにして ON CONFLICT DO NOTHING。2回目はエラーではなく1回目の結果を返す。外部APIにも渡す。

18. 金銭系の設計

残高を UPDATE せず、仕訳を追記する（複式簿記）。残高はスナップショット + 日次突合。保留勘定で中間状態を表現。突合は「設計の一部」。

19. 在庫の設計

on_hand と reserved の2つの数字。確保と確定を分け、held には必ず TTL と回収バッチ。ホットスポットは「DBに到達させない」（レート制限・待機列・前段カウンタ・キュー）順に対処。

20. 予約の設計

連続的な期間を離散的なスロットに変換して一意制約に落とす。照会は弱整合でよく、確保だけ強整合。航空券ではオーバーブッキングが意図的な仕様である点に注意。

21. 大規模サービスの共通解

①強整合は金銭・在庫・一意性だけ ②カウンタと配信は非同期 ③シャードキー設計で分散Txが必要な状況そのものを減らす。

22. 監視すべき指標

デッドロック数 / シリアライゼーション失敗数 / ロック待ち時間 / 最古のトランザクション経過時間 / dead tuple・History list / Outbox 未送信の最古 created_at / 滞留 Saga 件数。

23. 発見の仕組み

並行性のバグは再現しない。だから①突合バッチ（不変条件の定期検証）②DB制約（バグを即エラーに変える）③メトリクスを設計に含める。これが最も費用対効果が高い。

24. レビューで探すもの

「SELECT した値を IF で判定して、その後 UPDATE/INSERT している箇所」。ここが全ての候補。加えて「Tx 内の外部通信」「WHERE 句のインデックス」「ロック順序」。

この本を1文にまとめると

トランザクションとは「原子性と分離性という2つの嘘を、必要な強度だけ買う取引」である。
だから設計とは「どのデータに、どこまでの嘘を払うか」を決めることであり、実装とは「払っていない箇所を、明示的に守ること」（原子的UPDATE・制約・ロック）であり、運用とは「守れているかを検証し続けること」（突合・監視・負荷試験）である。

面接でも実務でも、「トランザクションで囲みます」より「ここは Lost Update が起きるので原子的UPDATEにします、理由はこうです」と言える人のほうが信頼される。そして「壊れたことにどう気づきますか」に答えられる人は、さらに信頼される。
