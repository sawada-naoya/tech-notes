DB機能やSQL構文の解説はしない。B-Tree・レプリケーション・パーティショニングといったDB内部は別ノート（database-system-design-ddia / replication / partitioning）で扱う。

主張1

モデリングは「現実の写経」ではなく「目的に対する切り取り」。同じECでも、会計が要件に入った瞬間に正解のテーブルが変わる。

主張2

設計の良し悪しは「時間」で決まる。今日のデータが正しく入るかではなく、値が変わった後も過去が壊れないかで決まる。

主張3

「Applicationで守るからDB制約は不要」は成立しない。アプリは複数・並行・使い捨て、データは1つで永続。守る側はデータに近いほど強い。

Part 1

基礎概念 — 何を「もの」として扱うか

モデリングの9割は、用語ではなく「切り分け」で決まる。何をEntityとし、何を属性とし、何を関連とするか。ここを間違えると、以降のすべての章の技法が効かなくなる。

01 モデリングとは何か

結論: モデリングとは「現実を写すこと」ではなく、「目的のために現実を捨てること」。何を捨てたかを説明できる状態が良いモデル。

地図の比喩。 1/1スケールの完全な地図は地図として使えない。路線図は距離も形も正確ではないが、「乗り換え」という目的には最適。モデルの正しさは現実との一致度ではなく、目的への適合度で決まる。「ユーザーとは何か」に唯一の正解がないのは、目的が違えば切り取りが変わるため。

1-1. 現実世界とデータモデルの距離

△ ありがちな出発点

「現実にある通りにテーブルを作る」。人がいるから users、商品があるから products。ここまでは正しい。問題はこの先で、現実に存在しないものが必要になった瞬間に手が止まる。

  • 「注文明細」は現実には紙の1行にすぎない。なぜ独立したテーブルが要るのか
  • 「カート」は現実には籠。DBに保存すべきか、セッションで十分か
  • 「支払い」は現実には一度きりの行為。なぜレコードとして残すのか

▸ 判断の軸は3つだけ

  1. 後から参照する必要があるか — 参照されないものは保存しなくていい
  2. 個別に識別する必要があるか — 「あの注文のあの1行」を指す必要があるならEntity
  3. 独立に変化するか — 別々のタイミングで変わるものは、別の入れ物に分ける

この3つは以降の全章で使う。迷ったら戻ってくる場所。

▲ なぜ一致しないのか

  • Domain Modelは振る舞いで分割したい。Data Modelはアクセスパターンと整合性で分割したい。動機が違う以上、常に一致はしない。
  • 一致を強制すると、どちらかが歪む。DBに合わせてDomainを歪めると業務ルールが散らばり、Domainに合わせてDBを歪めるとN+1と全件スキャンが生まれる。
  • 小〜中規模では「ほぼ一致させて、ズレた箇所だけ明示的に変換する」が現実解。全面的に分離するのは、変換コードの量に見合う複雑さがある場合だけ（→ 12章）。

1-3. Conceptual / Logical / Physical

図1.1 — 3層。上ほど寿命が長く、下ほど変更が容易。Conceptualの誤りだけは下層で救えない

◎ 実務での使い分け

  • 3つの成果物を毎回作る必要はない。重要なのは「今どの層の話をしているか」を混ぜないこと。
  • 設計レビューが紛糾する典型は、Conceptualの議論（そもそも注文とは何か）にPhysicalの反論（INDEXが効かない）をぶつけること。層を宣言してから話すと収束する。
  • 寿命の目安 — Conceptual: 事業が変わるまで / Logical: 年単位 / Physical: 負荷が変わるたび。下の層の都合で上の層を曲げるときは、必ず記録を残す（なぜ非正規化したのか）。

1-4. Entity / Value Object / Identity

▸ 唯一の判定基準

「属性がすべて同じでも、別物として区別する必要があるか」。必要ならEntity、不要ならValue Object。

Entity — 同一性で識別

1万円札が2枚。記番号が違えば別の札として追跡する必要があるならEntity。
属性が変わっても同じものであり続ける（住所が変わっても同じ顧客）。

Value Object — 値で識別

1万円という金額。どの1万円でも同じ。
属性が変わったら別の値になる（10000円と10001円は別物）。不変（immutable）として扱えるのが利点。

候補判定理由
CustomerEntity同姓同名同住所でも別人。改名しても同じ人
OrderEntity同じ内容の注文を2回してもそれは2つの注文
Money(amount, currency)Value Object1000円は1000円。追跡する意味がない
Address場合による下記参照。ECで最も判断が割れるところ
EmailValue Objectただし「送信履歴を持つ」要件が出た瞬間にEntity化圧力がかかる
OrderItemEntity数量変更・部分キャンセル・部分返品で個別に指す必要がある

▲ Address がなぜ割れるのか

  • 住所録として管理する（ユーザーが複数登録して選ぶ、編集する、削除する）→ 個別に指す必要がある → Entity（addressesテーブル）
  • 注文時の配送先（その時点の宛先、後から変えてはいけない）→ 値そのもの → Value Object（ordersに埋め込む / order_shipping_addressに凍結コピー）
  • つまり同じ「住所」でも、文脈が違えば別の扱いになる。ここを1つにまとめようとすると、次章の「価格が変わると過去が壊れる」と同じ事故が起きる。

1-5. Identityとは何か

△ 素朴な理解

「Identity = 主キー」。半分正しく、半分間違い。主キーはIdentityの実装手段の1つにすぎない。

✓ 正確な理解

  • Identityとは「時間が経ち属性が変わっても、同じものだと言えること」。
  • 実務で問うべきは「主キーは何か」ではなく 「このEntityの同一性を、業務上は何で判断しているか」。
  • 例: 社員の同一性は社員番号か、マイナンバーか、メールアドレスか。メールは変わるので同一性の根拠にはできない（ログインIDとしては使えるが別の話）。
  • この「業務上の同一性」をNatural Key、DBが振る通し番号をSurrogate Keyと呼ぶ。両立させるのが定石（→ 6章）。

1-6. 属性 / Relationship / Aggregate

属性（Attribute）

Entityに従属し、単独では存在意義がないもの。
判定: 「これだけを一覧したい」「これ自体に履歴が要る」なら属性ではなく別Entityの候補。

Relationship

Entity間の結びつき。多重度（1:1 / 1:N / N:N）と必須性を必ずセットで決める。
「関連自体が属性を持つか」が次の分岐（→ 3章）。

Aggregate

まとめて整合性を保つ単位。1トランザクションで一貫させる範囲。
外部からは代表（Aggregate Root）経由でのみ触る（→ 10章）。

Aggregateとテーブルの関係

Aggregate = テーブルではない。Order Aggregate = orders + order_items の2テーブルのように、複数テーブルが1つの整合性単位になる。

1-8. Business Ruleをどこまでスキーマで表現するか

▸ 3層で考える

  1. 構造で表現できるもの — 「注文には必ず顧客が要る」→ customer_id NOT NULL + FK。最強。破れない
  2. 制約で表現できるもの — 「数量は1以上」「メールは一意」→ CHECK / UNIQUE。強い。並行実行でも守られる
  3. コードでしか表現できないもの — 「発送済みの注文はキャンセル不可」「3万円以上で送料無料」→ アプリの責務

判断基準: 時間とともに変わるルールはコードへ、変わらない性質はスキーマへ。送料無料の閾値は来月変わるが、「注文に顧客が要る」は変わらない。

⇄ スキーマに寄せすぎた場合

  • キャンペーンのたびにマイグレーションが必要になる。デプロイの単位が業務変更の単位より重くなる
  • 複雑なCHECK制約はエラーメッセージが不親切で、ユーザーに何が悪いか伝えられない
  • → 「入れてはいけないデータ」を防ぐのがDB、「どう案内するか」がアプリ。両方でチェックしてよい（二重実装は冗長ではなく多層防御、→ 5章）

1-9. ApplicationとDBの責務境界

責務DBApplication根拠
存在の保証（FK）主補助どんな経路の書き込みでも守る必要がある
一意性（UNIQUE）主補助並行実行ではアプリの事前チェックは必ず破れる
値域（CHECK / 型）主補助不正値が1件でも入ると全コードが防御的になる
入力バリデーション–主ユーザーへの説明が必要。DBは理由を返せない
状態遷移の正当性補助主遷移表は業務知識。ただし到達不能な状態はCHECKで塞ぐ
認可（誰が見てよいか）補助主文脈依存。DBのRLSは有効だが、業務ロジックは持てない
集計・派生値補助主計算式が変わる。持つなら再計算可能にしておく（→ 13章）

▸ 覚え方

DBは「あり得ない状態を作らせない」係、Applicationは「正しい状態遷移を選ぶ」係。
DBは理由を説明できない代わりに絶対に破られない。Applicationは親切な代わりに、経路が増えると抜ける。

✓ これだけ覚える

  • モデリングは現実の模写ではなく、目的に対する取捨選択
  • Entity / Value Objectの判定は「属性が同じでも区別が要るか」の一点
  • 別Entityにする理由は「変化のタイミングが違う」「個別に参照する」のどちらか
  • Conceptual / Logical / Physical を混ぜて議論しない
  • DB = あり得ない状態を作らせない / App = 正しい遷移を選ぶ

⇄ Trade-off

  • Domain ModelとData Modelを一致させる → 実装が速い / ORMの都合が業務ルールに侵入する
  • 分離する → 業務ルールが守られる / 変換コードとテストが倍増する
  • ルールをスキーマに寄せる → 破れない / 変更にマイグレーションが要る
  • ルールをコードに寄せる → 柔軟 / 書き込み経路が増えると漏れる

✕ よくある失敗

  • 画面をそのままテーブルにする — 画面変更のたびにスキーマ変更が発生する
  • Value ObjectをEntity化 — 意味のないIDとJOINが増え、金額の比較すらJOINになる
  • EntityをValue Object化 — Paymentをカラムにして、分割決済が来た時点で破綻
  • 「将来必要かも」で先にEntityを分ける — 使われないテーブルは腐り、整合性だけ増える

? 設計時に自問する質問

  • このデータは誰が・いつ変更するか。他のデータと変更タイミングは同じか
  • 属性が全部同じ2件を、業務は別物として扱う必要があるか
  • 「これ1件だけを指し示したい」場面はあるか
  • このルールは来年も同じか。同じならスキーマ、変わるならコード
  • 今の議論は Conceptual / Logical / Physical のどれの話か

02 Entityをどう見つけるか

結論: 名詞を拾うだけでは見つからない。要件文に書かれていないEntityこそが重要で、それは「時間が経つと何が起きるか」を問うことでしか現れない。

● 題材の要件

ユーザーは商品を複数購入できる。 注文時の価格を保持する。 商品価格は後から変更できる。 注文には配送先住所が必要。

2-2. Step2: 素朴な設計を一度書く

2-3. Step3: 「時間が経つと何が起きるか」を問う

■ 問題1 — 複数商品が入らない

要件の1行目「商品を複数購入できる」を満たしていない。orders.product_id は1つしか持てない。

  • 回避案A: product_id をカンマ区切りで持つ → JOINできない、数量が持てない、FKが効かない。第1正規形違反（→ 4章）
  • 回避案B: 商品ごとに別注文にする → 1回の買い物が3注文になり、送料・支払い・配送がバラバラになる
  • 正解: 1:Nを表現する子テーブル order_items を作る

■ 問題2 — 価格改定で過去が書き換わる（最重要）

1/10 商品A の価格 1,000円 1/15 ユーザーが注文 → 請求 1,000円 / メールも 1,000円 2/01 値上げ UPDATE products SET price = 1,200 WHERE id = A 2/02 ユーザーが注文履歴を開く 画面表示 = products.price * quantity = 1,200円 実際の請求 = 1,000円
  • 発生すること: 注文履歴・請求書PDF・売上集計・返金額が全部ずれる。会計監査で落ちる
  • 検知の遅さ: バグではないのでテストが通る。エラーも出ない。気づくのは月次締めか顧客からの問い合わせ
  • 根本原因: 「注文時の価格」と「現在の販売価格」という意味の違う2つの値を、1つのカラムで兼用したこと

▲ なぜこれが「属性の見落とし」なのか

要件文の2行目「注文時の価格を保持する」は、実は「OrderItemという入れ物が要る」と書いてある。

2-5. 要件文からEntityを見つける定型手順

✓ 5つの問いを順に当てる

  1. 名詞を全部拾う — まず機械的に
  2. 動詞を拾う — 「購入する」「承認する」「発送する」。記録が必要な行為は Entity になる
  3. 各名詞に「複数ありうるか」 — 「N個」ならその時点で1:Nかコレクション
  4. 各属性に「後から変わるか」 — 変わるなら「変わったとき過去はどうあるべきか」を続けて問う
  5. 各関連に「その関連自体が情報を持つか」 — 持つならEntityへ昇格（→ 3章）
要件文の表現示唆されるモデル
「〜を複数持てる」1:N。子テーブル
「〜時点の〜を保持する」凍結カラム。マスタ参照では満たせない
「〜は後から変更できる」その値に依存する過去データの扱いを必ず確認する
「〜の履歴を見たい」履歴テーブル or イベントテーブル（→ 9章）
「誰がいつ〜したか」関連にactor/timestamp属性 → 中間テーブルのEntity昇格
「〜の状態は A → B → C と進む」状態列 + 遷移ルール（→ 8章）。booleanではない
「承認されるまで公開されない」状態 + 権限。boolean 2本にしない
「〜または〜を指定する」排他的な選択肢。CHECK制約 or サブタイプ

2-6. 逆方向 — Entityを作りすぎない

⇄ 分けすぎの害

  • よくある過剰分割: user_profiles user_settings user_details を最初から分ける。常に1:1で常に一緒に読むなら、それはJOINが1本増えただけ
  • 分ける正当な理由: ①ライフサイクルが違う ②アクセス頻度が極端に違う ③NULL率が高い ④権限が違う（機微情報の分離） ⑤行サイズが巨大（TEXT/BLOB）
  • 分けない判断も設計。「同時に作られ、同時に読まれ、同時に消される」なら1テーブル

✓ これだけ覚える

  • 要件の動詞がEntityを、「〜時点の」が凍結カラムを告げている
  • マスタの値を過去レコードから参照し続けると、マスタ更新で過去が書き換わる
  • 凍結の基準は「これが変わったとき、過去の領収書は書き換わるべきか」
  • Entityは足りなくても事故るが、増やしすぎても腐る。分ける理由を言えるときだけ分ける

⇄ Trade-off

  • 凍結する → 過去が守られる / データ重複・マスタ修正が過去に反映されない（誤登録の訂正が面倒）
  • 参照する → 単一の真実 / 参照先の変更・削除が過去を破壊する
  • 住所を注文に埋め込む → 高速・安全 / 住所の正規化された検索ができない
  • 住所を別テーブルでFK → 再利用可能 / 「配送先の凍結」を別途やる必要がある

✕ よくある失敗

  • unit_price を持たない — 最頻出。値上げの日まで誰も気づかない
  • 配送先をFKだけで持つ — ユーザーが住所を編集/削除すると過去の伝票が変わる
  • 商品を物理削除する — order_itemsのFKが折れるか、CASCADEで注文明細ごと消える
  • 名詞だけ拾って動詞を無視 — 「承認する」「返金する」の記録が残らない

? 設計時に自問する質問

  • この値はマスタの現在値か、取引時点の事実か
  • 参照先を編集・削除したとき、この行の意味は変わるか
  • 要件文に「〜時点の」「〜の履歴」「誰がいつ」が含まれていないか
  • このテーブルを分ける理由を、性能以外の言葉で言えるか

03 Relationship — 関連の設計

結論: 多重度（1:1 / 1:N / N:N）は結論ではなく出発点。本当に問うべきは「この関連自体が情報を持つか」「関連はいつ生まれ、いつ消えるか」。

3-1. 関連を決めるときに必ず決める4項目

① 多重度

両方向から数える。「1注文は何個の明細を持つか」「1明細は何個の注文に属するか」。片方向だけ数えると必ず間違える

② 必須性（オプショナリティ）

「明細のない注文は存在するか」「注文のない明細は存在するか」。→ NOT NULL / NULL許容の根拠

③ ライフサイクル

親が消えたら子はどうなるか。CASCADE / RESTRICT / SET NULL のどれが業務的に正しいか

④ 関連自体の属性

「いつ結ばれたか」「誰が結んだか」「どういう条件で結ばれたか」を持つ必要があるか

3-2. 1:1 — 本当に1:1か疑う

△ 1:1が出てきたら、まず統合を検討する

1:1は「2つに分ける積極的な理由」がなければ、1テーブルにまとめるのが基本。分けた瞬間にJOINと整合性の心配が増える。

実装形使いどころ注意
同一テーブルusers にカラム追加常に一緒に読む / NULLが少ないデフォルト。まずこれ
別テーブル + FK + UNIQUEuser_profiles.user_id UNIQUE任意入力が多い / 巨大なTEXT / アクセス頻度が違うUNIQUEを忘れると静かに1:Nになる
共有主キーuser_profiles.user_id が PK かつ FK上と同じ用途。より厳密PKがそのままUNIQUEなので崩れない
サブタイプ分割users + individual_users / corporate_users種別ごとに属性が大きく違うどちらか一方のみ存在をDBで強制するのは難しい

3-3. 1:N — FKは必ず「多」の側が持つ

▸ 理由

  • 1側に持たせようとすると、1行に複数の子IDを入れることになる。配列・カンマ区切り・item1_id/item2_id... どれも破綻する
  • N側に parent_id を置けば、子が何個増えても行が増えるだけ。スキーマ変更なしでスケールする
  • 必須性は NOT NULL で表す。「親のない子」を許すなら NULL 許容（例: 下書きコメント）

■ カンマ区切りが破壊するもの

orders.product_ids = "12,345,6" 検索: WHERE product_ids LIKE '%12%' → 12 だけでなく 123, 512 もヒット JOIN: 不可能（関数で分解すればINDEXが効かない） FK : 貼れない。存在しない商品IDを入れても誰も止めない 数量: 持てない。"12:2,345:1" と独自フォーマットに進化し始める 集計: 商品別売上が出せない

1つのカラムに複数の値を入れた瞬間、RDBのほぼ全機能が無効になる。これが第1正規形の実務的な意味（→ 4章）。

3-4. N:N — なぜ中間テーブルが要るのか

▲ 構造的な理由

N:Nは「どちらの側にもFKを置けない」関係。Post が複数Tagを持ち、Tag が複数Postに付くとき、posts に tag_id を1つ置いても、tags に post_id を1つ置いても足りない。
→ 「関連そのもの」を行として表す第3のテーブルが必要。これが中間テーブル（結合テーブル / 関連テーブル）。

  • title
1 ──< N

  • FK post_id

N >── 1

図3.1 — N:N は「2本の 1:N」に分解される。中間テーブルは関連そのものを表す実体

▸ ON DELETE の非対称性に注目

  • post削除 → CASCADE: 記事が消えたらタグ付けも消えるのが自然
  • tag削除 → RESTRICT: 使われているタグを消させない。誤操作で大量の記事からタグが剥がれる事故を防ぐ
  • CASCADEは「業務的に一緒に消えるべきか」で決める。実装の都合で決めない

3-5. RelationshipがEntityへ昇格する瞬間

最重要。中間テーブルにカラムを1本足したくなった瞬間、それはもう「関連」ではなく「事実（Entity）」になっている。

図3.2 — 「いつ」「誰が」が要求された時点で、関連は出来事の記録に変わっている

✓ 昇格の判定質問

  1. 同じペアが2回以上成立しうるか — YESなら複合PKは使えない。代理キーが必要
  2. 関連に始まりと終わりがあるか — 「いつから有効」があるなら期間を持つEntity（→ 7章）
  3. 関連自体を他から参照するか — 「この権限付与について承認を得る」など。参照されるならIDが要る
  4. 関連が消えた事実を残す必要があるか — 「いつ剥奪されたか」が要るなら物理削除できない

  • さらに悪いのは、「1商品1カテゴリ」という現在のルールがDBで守られないこと。バグで2行入っても検知できず、画面によって表示が変わる

3-7. 多態関連（Polymorphic）の扱い

△ ありがちな設計

代替案形長所短所
対象ごとにテーブル分割post_comments / product_commentsFKが貼れる。型安全共通処理が重複。全コメント横断検索が UNION

▸ 実務の判断

対象が2〜3種類で固定なら Nullable FK + CHECK が扱いやすい。
種類が増え続けるなら多態も選択肢だが、その場合は「孤児レコードを検出するバッチ」を同時に用意するのが条件。DBが守らない以上、監視で補う。

✓ これだけ覚える

  • FKは常に「多」の側が持つ。1側に複数値を詰めない
  • N:Nは「2本の1:N」。中間テーブルは関連そのものの実体
  • 中間テーブルに属性を足したくなったら、それはEntityになっている
  • 同じペアが2回成立しうるなら複合PKは使えない。代理キー + 期間
  • 「将来のためのN:N」は、現在のルールをDBが守れなくする

⇄ Trade-off

  • 複合PKの中間テーブル → 重複が構造的に不可能 / 属性追加・履歴化に弱い
  • 代理キー + UNIQUE → 拡張しやすい / UNIQUE忘れで重複が入る
  • 1:1を分割 → 機微情報の権限分離・行の軽量化 / JOIN増・存在保証の手間
  • 多態関連 → 拡張が速い / 参照整合性を放棄し、監視コストに振り替える

✕ よくある失敗

  • 1:1にUNIQUEを付け忘れる — 静かに1:Nになり、どの行が正なのか分からなくなる
  • 中間テーブルに代理キーだけ — 重複行が入り、集計が二重計上される
  • ON DELETE CASCADEを深く連鎖させる — 1件の削除で数万行が消える
  • カンマ区切り / JSON配列でN:Nを表現 — FK・JOIN・集計を全部失う

  • この関連は両方向から数えたか
  • 同じ組み合わせが時間をおいて再び成立することはあるか
  • この関連が「いつ・誰によって」結ばれたかを、後から聞かれる可能性はあるか
  • 親を削除したとき、業務的に子はどうなるべきか
  • 一意性は今どこで守られているか（PK / UNIQUE / アプリ / どこにもない）

Part 2

構造の品質 — 矛盾が入り込む隙をなくす

正規化は「きれいにすること」ではなく「同じ事実を2箇所に書かないこと」。制約は「面倒な縛り」ではなく「あり得ない状態を構造的に不可能にする仕組み」。どちらも目的は同じで、矛盾したデータが物理的に入らない状態を作ること。

04 正規化と非正規化

結論: 正規化の目的は美しさではなく「1つの事実を1箇所にだけ書くこと」。2箇所に書いた瞬間、ズレる可能性が生まれ、どちらが正しいか誰にも分からなくなる。

4-1. 素朴な設計 — 1枚の表に全部入れる

■ この表が抱える3つのAnomaly

  • Update Anomaly（更新異常）
    田中のメールを変更するには、全注文行を更新する必要がある。1行でも漏れると2種類のメールが並存する（上表の行2と3）。どちらが正しいかDBには判断できない
  • Insert Anomaly（挿入異常）
    まだ注文していない顧客を登録できない。注文がないと行が作れないため。商品も同様で、売れていない商品はカタログに存在できない
  • Delete Anomaly（削除異常）
    注文3を削除すると、鈴木という顧客が世界から消える。消したかったのは注文であって顧客ではない

3つとも原因は同じ — 「顧客という事実」と「注文という事実」が1つの行に同居しているため、片方だけを操作できない。

4-2. 1NF / 2NF / 3NF を「何を防ぐか」で理解する

正規形形式的定義実務的な意味違反例
1NF各列が単一の値（繰り返しグループがない）1セルに複数値を入れないproduct_ids = "1,2,3" / tel1, tel2, tel3
2NF1NF かつ、非キー列が主キー全体に関数従属複合キーの一部にしか依存しない列を分離するPK(order_id, product_id) の表に customer_name（order_idにしか依存しない）
3NF2NF かつ、非キー列同士に従属がない（推移的従属の排除）「キー以外の列から決まる列」を分離するorders に customer_id, customer_name（nameはidから決まる）
BCNFすべての決定項が候補キー3NFで取り切れない稀なケースを潰す実務では3NFで十分なことが多い

▸ 覚え方（Codd の要約）

「すべての非キー列は、キーに依存し、キー全体に依存し、キーだけに依存する」

  • キーに依存し → 1NF/2NFの前提（キーで行が決まる）
  • キー全体に → 2NF（複合キーの一部だけに依存させない）
  • キーだけに → 3NF（他の列から決まる列を置かない）

4-3. 正規化の実行

▲ なぜ unit_price は「非正規化」ではないのか（重要）

  • 一見 products.price の重複コピーに見える。しかし意味が違う。
  • products.price = 「現在いくらで売っているか」（将来変わる）
    order_items.unit_price = 「2026-01-15にいくらで売れたか」（未来永劫変わらない）
  • たまたま注文時点で値が一致しているだけで、これは2つの異なる事実。したがって別々に保存するのは3NF違反ではない。
  • 見分け方: 片方を更新したときもう片方も更新すべきなら重複（=正規化対象）。更新すべきでないなら別の事実（=正しい設計）。

4-4. 「では正規化すればするほど良いのか」

■ 正規化のコスト

  • JOIN数の増加 — 結合順序の最適化が難しくなり、プランが不安定になる
  • 集計のコスト — AVG(r.score) は毎回レビュー全件を走査する
  • ソートが効かない — 集計結果でのORDER BYはINDEXが使えず、全件ソートになる
  • クエリの複雑化 — 読めない・テストしづらい・変更が怖い、という人的コスト

4-5. 非正規化の4つの型

型例復元可能性崩れ方推奨度
① 集計キャッシュproducts.review_count, orders.total_amount元データから再計算できる更新漏れでズレる。定期的な再計算バッチで復旧可能条件付きで可
② 参照値のコピーorder_items.product_name（表示用のみ）元が消えると復元不能マスタ更新が反映されない目的次第（凍結なら正しい）
③ Read Model / 事前結合product_search_view, timeline テーブル元データから再構築できる反映遅延。結果整合推奨（責務が分離される）
④ 構造の埋め込みJSONカラムに子要素を全部入れる部分更新・検索が困難肥大化。スキーマが読めない限定的（→13章）

✓ 非正規化を入れるときの3つのルール

  1. 正規化された「真実」を必ず残す — 派生値は消しても復元できる状態を保つ。復元できない非正規化は非正規化ではなく、単なるデータ喪失
  2. 更新経路を1つに絞る — 集計値を10箇所から更新すると必ずズレる。更新はドメインサービス or トリガ or 非同期ワーカーの1経路に集約
  3. ズレを検出する仕組みを同時に作る — 日次で再計算して差分を検知するバッチ。「ズレたら困る」ものは、ズレたことに気づける必要がある

? Thinking Point

「注文合計 total_amount は、毎回SUMで計算すればいいのでは？ なぜカラムに持つのか」 — 持つ理由・持たない理由の両方を挙げてから開く。

考えてから開く

持たない理由（まずこちらを検討する）

  • 明細は数件〜数十件。SUMのコストは実質ゼロ。1注文の表示なら常にこれで足りる
  • ズレる可能性がそもそも存在しない

持つ理由

  • 注文一覧で1000件表示するとき、毎行SUMすると1000回の集計になる
  • 合計金額でソート・絞り込みしたいとき、集計値ではINDEXが使えない
  • 決定的な理由 —送料・クーポン・端数処理・税計算が入ると、total は明細のSUMと一致しなくなる。「その時点の計算ルールで確定した請求額」という独立した事実になる。この瞬間、total_amount は非正規化ではなくなる

つまり判断は性能ではなく意味で決まる。計算式が将来変わりうるなら、確定額は必ず保存する。

✓ これだけ覚える

  • 正規化の目的は「1つの事実を1箇所に」。Anomalyはすべてこの違反から出る
  • 「非キー列は、キーに、キー全体に、キーだけに依存する」
  • 凍結（unit_price）は重複ではなく別の事実。更新すべきかどうかで見分ける
  • 非正規化は「真実を残す」「更新経路を1つに」「ズレを検出する」の3点セットで導入する

⇄ Trade-off

  • 正規化を進める → 矛盾が入らない・更新が安全 / JOIN増・クエリ複雑化・読み性能
  • 非正規化する → 読みが速い・クエリが単純 / 更新箇所が増え、ズレが必ず発生する
  • 集計値をカラムに持つ → ソート・絞り込みが可能 / 同期コストと監視コスト
  • Read Modelを別に作る → 書きと読みの要求を両立 / 実装量・反映遅延・運用対象の増加

✕ よくある失敗

  • 性能問題が出る前に非正規化 — 測定していないので、効果も不明なまま複雑さだけ残る
  • 集計値の更新をアプリの複数箇所に散らす — 必ずどこかが漏れる
  • 「正規化しすぎた」を理由に元テーブルを消す — 復元不能になり、後戻りできない
  • 凍結を非正規化と誤認して「正規化」してしまう — 過去の金額が変わる事故に戻る

? 設計時に自問する質問

  • この値が2箇所にある。片方を更新したら、もう片方も更新すべきか
  • この集計値がズレたとき、誰がいつ気づくか
  • 非正規化した列を全部消しても、元データから再構築できるか
  • この計算式は将来変わるか。変わるなら確定値を保存すべきではないか

05 制約とInvariant

結論: 「Applicationでチェックしているから制約は不要」は、単一プロセス・単一スレッド・単一経路という成立しない前提の上にしか立たない。制約は縛りではなく、あり得ない状態を物理的に作れなくする装置。

5-1. 制約の種類と守備範囲

制約防ぐもの並行実行下設計上の意味
PRIMARY KEY同一性の重複・欠落安全「この行を一意に指す方法がある」の宣言
FOREIGN KEY存在しないものへの参照安全「この関連は必ず相手が居る」の宣言
UNIQUE業務上の重複安全「業務上これは1つしかない」の宣言
NOT NULL値の欠落安全「この情報は必ず存在する」の宣言
CHECK不正な値域・行内の矛盾安全「この値が取りうる範囲」の宣言
型・長さ形式の不一致安全最も基本的な制約。VARCHAR(255)乱用を避ける
App Validation入力ミス・業務ルール違反破れるユーザーへの説明責任を持つ。DBの代替ではない

5-2. なぜアプリだけでは破れるのか

■ 破れる経路は4つある

  1. 並行実行（最も多い） — 事前チェックと書き込みの間に他のリクエストが割り込む（TOCTOU）
  2. 別経路の書き込み — バッチ、管理画面、データ移行スクリプト、障害対応の手動SQL、別チームのサービス
  3. コードの分岐漏れ — 新しいユースケースを追加したとき、チェックのコピーを忘れる
  4. リトライ・重複実行 — メッセージの再配送、ユーザーの二度押し、タイムアウト後の再送

図5.1 — アプリの事前チェックは「見た時点では正しい」。書き込む時点では正しいと限らない

▸ 事前チェックを消す必要はない

UXのために事前チェックは残してよい（「このメールは使用済みです」をフォームで即時表示）。
重要なのは「事前チェックはUXのため、制約は正しさのため」と役割を分けること。事前チェックを正しさの担保だと思っている状態が危険。

5-3. 在庫 stock >= 0 — 制約だけでは足りない例

▸ 3層の防御が噛み合っている状態

  1. CHECK制約 — 負の在庫は「存在できない」。どんな経路でも破れない最終防衛線
  2. 条件付きUPDATE — 並行実行でも1つのSQLで判定と更新が原子的に行われる
  3. アプリの事前確認 — カート画面で「在庫切れ」を親切に伝える。正しさの担保ではない

3つは冗長ではない。それぞれ守る対象が違う（構造 / 並行性 / UX）。

5-4. Domain Invariant と DB Constraint

観点Domain InvariantDB Constraint
定義業務上、常に成り立っていなければならない条件DBが物理的に強制する条件
表現力任意（複数Entity・外部状態・時間依存も可）行内・テーブル内に限られることが多い
強制力コードを通った場合のみすべての書き込み経路で有効
説明力エラー理由を業務の言葉で返せる「制約違反」としか言えない
変更容易性デプロイのみマイグレーション + 既存データの適合

DBで表現できるInvariant

・email は一意
・quantity > 0
・total_amount >= 0
・valid_to > valid_from
・status は列挙値のいずれか
・キャンセル日時は注文日時以降

DBでは表現しにくいInvariant

・発送済みの注文はキャンセルできない（遷移のルール）
・同一ユーザーの未払い注文は3件まで（複数行集約）
・合計金額は明細の合計 + 送料 − 割引（計算式）
・営業時間内のみ予約可（外部状態）

✓ 表現しにくいものへの対処

  • Aggregateに閉じ込める — 「同一ユーザーの未払い3件まで」は、ユーザー行をロックしてから数える（→ 10章）
  • 生成列 + UNIQUE で表現に持ち込む — 「有効な行は1つだけ」は3章の active_key パターンで表現できる
  • 到達不能な状態だけでもCHECKで塞ぐ — 遷移全体は無理でも「cancelled かつ shipped_at IS NOT NULL」は禁止できる（→ 8章）
  • 検出に切り替える — 完全な防止が高コストなら、違反を日次で検出してアラートする方が現実的な場合がある

5-5. NULL の設計

▲ NULLは「値がない」ではなく「意味が3つある」

  • まだ分からない（未入力の生年月日）
  • 該当しない（法人顧客の性別）
  • まだ起きていない（cancelled_at / shipped_at）
  • 3つを同じNULLで表すと、クエリで区別できない。③は状態と併せて設計すれば意味が明確になる（→ 8章）

⇄ NOT NULL + デフォルト値 vs NULL許容

  • 空文字をデフォルトにする → クエリが単純（NULL考慮不要） / 「未入力」と「空と入力した」が区別できない
  • 0をデフォルトにする → 集計が楽 / 数値では致命的。「未測定」と「0だった」の混同は事故になる
  • 原則: 存在が保証できる列はNOT NULL。区別が必要ならNULLを恐れずに使う。「NULLを減らす」ことが目的化すると意味が壊れる
  • ただしNULL許容列が過半数を超えたら、テーブル分割かサブタイプ化を検討する合図（→ 13章）

✓ これだけ覚える

  • 事前チェックはUXのため、制約は正しさのため。役割が違うので両方置く
  • アプリのチェックは、並行実行・別経路・分岐漏れ・再実行の4経路で破れる
  • 「確認してから書く」ではなく「条件付きで書いて、結果を見る」
  • DBで表現できないInvariantは、Aggregate + ロック か 検出バッチで補う
  • NULLを機械的に排除しない。意味の区別が消える方が有害

⇄ Trade-off

  • 制約を厚くする → 不正データが物理的に入らない / マイグレーションが重く、既存データの是正が必要
  • 制約を薄くする → 変更が速い / 一度混入した不正データは永久に残り、全コードが防御的になる
  • FKを張る → 孤児が出ない / 削除順序の制約、大量データ操作の遅延、シャーディングとの相性
  • CHECKで業務ルールを表現 → 破れない / ルール変更時にDDLが必要でエラーメッセージが不親切

✕ よくある失敗

  • 「アプリで見てるから制約不要」 — 二重登録・孤児・負の在庫が本番で発生する
  • 後からUNIQUEを張ろうとして既存重複で張れない — 是正作業が先に必要になり、放置される
  • 全部VARCHAR(255) NULL許容 — スキーマから業務ルールが一切読み取れない
  • 制約違反エラーをそのままユーザーに見せる — 業務エラーへの翻訳層を作る

? 設計時に自問する質問

  • このチェックは2つのリクエストが同時に来ても成立するか
  • 管理画面・バッチ・手動SQLから書かれても、このルールは守られるか
  • このNULLは「未入力」「該当なし」「未発生」のどれか
  • この制約を今張れるか。張れないなら既に不正データが入っているのではないか

06 ID設計

結論: IDは「内部で行を指すための値」と「外部に見せる識別子」の2つの役割を持つ。この2つを同じ値で兼ねると、性能・機密・移行のどこかで必ず困る。

6-1. 候補の比較

方式形サイズ採番場所順序性推測可能性主な用途
AUTO_INCREMENT1, 2, 3...8BDB（INSERT時）完全に単調増加容易内部PK
UUID v4f47ac10b-...16B(36文字)アプリランダム不可能分散採番・外部公開
UUID v7018f3c...（時刻先頭）16Bアプリ時刻順生成時刻が漏れる現代の第一候補
ULID01HQ3F...（26文字）16Bアプリ時刻順生成時刻が漏れるUUIDv7とほぼ同等。文字列が短い
Snowflake時刻+ノード+連番8Bアプリ/専用概ね時刻順ノード数が漏れる大規模分散

Composite Key(order_id, product_id)可変–––関連テーブル

6-2. UUIDv4 の Index Locality 問題

図6.1 — 二次索引にもPK値が含まれるため、PKが大きいとすべての索引が太る点にも注意

▸ 誤解しやすい点

  • 「UUIDは遅い」は雑な理解。遅いのはランダム性であって、UUIDという形式ではない。UUIDv7/ULIDなら局所性は連番と同等
  • 文字列で保存するのが最悪。CHAR(36) は16Bの2倍以上。MySQLなら BINARY(16) に格納する
  • 逆に連番は末尾に書き込みが集中するため、極端な高スループットではホットスポットになる。ここでSnowflakeなどが出てくる

6-3. 内部IDと外部公開IDを分ける

■ 連番をURLに出したときに起きること

  • IDOR — /orders/1234 を 1235 に書き換えて他人の注文が見える（認可の不備が即座に悪用される）
  • 事業情報の漏洩 — 月初と月末に注文を1件ずつ作れば、月間注文数が外部から計測できる（German Tank Problem）。競合・投資家に筒抜け
  • スクレイピング容易性 — 1から順に叩くだけで全件取得できる
  • 移行時の衝突 — 他システムと統合する際、両方に id=1 が存在する

⇄ 分ける / 分けない

  • 分ける → 索引が小さく保て、推測も防げる / 2種類のIDが存在することで、どちらを渡すかの混乱・変換漏れが起きる
  • ULID単体をPKにする → シンプル・分散採番可能 / PKが16Bになり、全二次索引が太る。JOINもわずかに重い
  • 判断: 外部にIDを晒すシステム（公開Web / 外部API / メール内リンク）なら分ける価値がある。社内管理システムだけなら連番PK単体で十分
  • 避けるべき中間案: 連番をハッシュ化して隠す（Hashids等）。可逆なので機密性の担保にならず、認可の代わりにはならない

6-4. Natural Key と Surrogate Key

△ Natural Key を主キーにしたときの崩れ方

  • 「メールアドレスをPKにする」 → メール変更のたびに、参照している全テーブルのFKを更新する必要がある
  • 「国コードをPKにする」 → 国名変更・国の統合・分裂が起きる（実際に起きる）
  • 「ISBNをPKにする」 → ISBN-10からISBN-13への移行、ISBNを持たない同人誌の登録で破綻
  • 共通する問題: 業務的に意味のある値は、業務が変われば変わる。主キーは変わってはいけない

✓ 定石 — 両立させる

  • PK は Surrogate Key（意味のない通し番号/ULID）。永久に変わらないことを保証できる
  • Natural Key は UNIQUE 制約で表現する。業務上の同一性はここで守る
  • これで「変更に強い参照」と「業務上の一意性」が両立する。Natural Keyを捨てるのではなく、主キーの座から降ろす

6-5. Composite Key を使う場面

場面複合PKにする理由
属性のない中間テーブル（post_tags）推奨重複が構造的に不可能。余計なIDを増やさない
子テーブルで親の中でのみ意味を持つ（order_items）どちらでも(order_id, line_no) は自然だが、外部から個別参照するならidが便利
時系列データ（metrics）推奨(device_id, measured_at) で範囲スキャンが効く形になる
履歴テーブル非推奨同じキーが複数回現れる。代理キー + 期間で持つ
ORMが絡む主要Entity非推奨多くのORMが複合PKを苦手とし、実装コストが跳ね上がる

▸ 複合PKの列順は性能に直結する

InnoDBではPKがそのまま行の物理順序になる。PRIMARY KEY (device_id, measured_at) なら「あるデバイスの期間指定」が連続読み出しになる。逆順だと全デバイスを跨いで散る。
「最も多いクエリの絞り込み条件」を先頭に置く。

6-6. 分散環境でのID生成

▲ なぜAUTO_INCREMENTでは足りなくなるか

  • 採番にDBアクセスが必要 — INSERTするまでIDが決まらない。アプリ側で「IDを先に決めてイベントを発行する」ことができない
  • シャーディングで衝突 — 複数DBが同じ番号を採番する。offset/increment で回避できるが、シャード追加時に破綻する
  • マルチマスタ・オフライン生成ができない — モバイルアプリが圏外でレコードを作れない

? Thinking Point

「MySQL 1台のWebサービス。IDはどうする？」 — 自分の答えを決めてから開く。

考えてから開く

唯一解はないが、判断の分岐はこうなる。

  • 社内システム・管理画面のみ → BIGINT AUTO_INCREMENT 単体。最小・最速。悩む価値がない
  • 一般公開のWebサービス → 内部 BIGINT + 外部 ULID/UUIDv7（BINARY(16)）。注文数が外部から数えられる問題は、事業上の実害になりうる
  • 将来の分割やイベント駆動が見えている → 最初から ULID を PK に。後から付け替えるのは全FKの書き換えになり、実質不可能
  • 最も重要なのは「どちらを選ぶか」より「途中で変えられない」こと。IDはスキーマの中で最も移行コストが高い要素。ここだけは先に決める

✓ これだけ覚える

  • PKは意味を持たない不変値（Surrogate）、業務上の一意性はUNIQUEで表す
  • 遅いのはUUIDではなくランダム性。時刻順ID（ULID/UUIDv7）なら局所性は保てる
  • 連番を外部に晒すと、他人のIDが推測でき、事業規模まで漏れる
  • IDは後から変更できない唯一に近い設計要素。最初に決める

⇄ Trade-off

  • BIGINT連番 → 最小・最速・索引に優しい / 推測可能、分散採番不可、事前採番不可
  • ULID/UUIDv7 → 事前採番・分散可・推測困難 / 16Bで全索引が太る、生成時刻が漏れる
  • 内部/外部の二重ID → 双方の利点 / 変換層が要る。渡し間違いのリスク
  • 複合PK → 重複が構造的に不可能 / ORM対応が重く、参照側のFKが太る

✕ よくある失敗

  • UUIDをCHAR(36)で保存 — 索引サイズが2倍以上になり、性能劣化の主因になる
  • メールアドレスをPKにする — 変更のたびに全参照の更新が必要になる
  • 外部システムのIDをそのままPKに使う — 相手の仕様変更で自分のDBが壊れる（→ 13章）
  • 推測防止のためにIDをハッシュ化 — 認可の代替にならない。認可は別途必要

? 設計時に自問する質問

  • このIDはURL・メール・APIレスポンスに載るか
  • IDを連番で公開して、件数が外部に知られて困らないか
  • 永続化する前にIDが必要な場面はあるか（イベント発行・テスト・オフライン作成）
  • このNatural Keyは10年後も同じ値か

Part 3

時間と状態 — 設計が壊れる主戦場

データモデルが本当に壊れるのは、値が変わったときと、状態が進んだとき。この2つを扱えるかどうかで、3年後にそのスキーマが使えるかが決まる。

07 時間をどうモデル化するか

結論: 時間には「いつDBに書いたか」「いつ現実で起きたか」「いつからいつまで有効か」の3種類がある。created_at は1種類目しか表していない。

7-1. 3種類の時間

種類カラム例意味これがないと困る場面
記録時間
(Transaction Time)		created_at / updated_atDBに書かれた時刻。システムの都合「いつデータが入ったか」の調査。監査
発生時間
(Valid / Event Time)		occurred_at / ordered_at / paid_at現実世界でその出来事が起きた時刻非同期処理・バッチ取込・オフライン入力で記録時間とズレる
有効期間
(Effective Period)		valid_from / valid_to / effective_atその値が正である期間予約された料金改定・将来の異動・過去に遡る訂正

▲ なぜ created_at だけでは足りないのか

ケース1: 決済Webhookが3時間遅れて届いた 実際の決済: 10:00 ← 顧客にとっての事実 DBへの記録: 13:00 ← created_at 「10:00〜11:00の売上」を集計すると、この決済が漏れる ケース2: 来月からの新料金を今日登録したい created_at = 今日 → 今日から新料金が適用されてしまう effective_at = 来月1日 が必要 ケース3: 先月の入力ミスを今日訂正した 「先月時点で正しかった値」と「今の訂正後の値」の両方が必要 → 記録時間と有効期間の2軸（bitemporal）

7-2. 期間の表し方

▸ 半開区間 [from, to) にする理由

  • 境界の重複が起きない — 閉区間 [from, to] だと、前の期間の終わりと次の始まりが同じ瞬間を指してしまう
  • 隙間が生まれない — 「23:59:59まで」方式は、ミリ秒精度が入った瞬間に穴が空く
  • 連結が単純 — 前行の valid_to = 次行の valid_from をそのまま代入できる

⇄ 「現在」を NULL で表すか、9999-12-31 で表すか

  • NULL → 意味が明確（終わりが未定） / クエリ条件が (valid_to IS NULL OR valid_to > ?) と長くなり、INDEXも効きにくい
  • 9999-12-31 → 条件が valid_from <= ? AND ? < valid_to と単純になり、範囲INDEXが効く / 番兵値であり、意味を知らないと誤読される
  • 履歴テーブルを頻繁に時点検索するなら 9999 方式が扱いやすい。どちらでもよいが、チーム内で統一すること

■ 期間の重なりをDBで防ぐ

同じ商品に対して有効期間が重なる行が2つ入ると、「その時点の価格」が2件返る。クエリは成功し、金額だけが間違うため発見が遅れる。

  • PostgreSQL: EXCLUDE USING gist (product_id WITH =, tstzrange(valid_from, valid_to) WITH &&) で完全に防げる
  • MySQL: 排他制約がないため、①「現在有効な行は1つ」を生成列+UNIQUEで保証 ②更新は必ずドメインサービス経由 ③重なり検出バッチ、の3点で担保する

7-3. 履歴テーブルの3つの典型

例持つもの設計上の要点
ProductPriceHistory価格の有効期間「その時点の価格」が引ける必要がある。将来日付の予約登録も同じ構造で扱える
SubscriptionPlanHistory契約プランの変遷日割り計算のために期間が必須。アップグレード/ダウングレードの理由も持つと分析できる
ReservationStatusHistory状態遷移の記録期間ではなく時点の列（occurred_at）。誰が変えたか（actor）が監査上ほぼ必須

▸ 「期間型」と「時点型」を混ぜない

  • 期間型（valid_from/valid_to）— 「いつからいつまでこの値だったか」を問うもの。価格・プラン・住所・担当者
  • 時点型（occurred_at）— 「何がいつ起きたか」を問うもの。状態遷移・支払い・通知送信
  • 時点型から期間型は導出できる（次のイベントまでが期間）が、クエリが重くなる。よく「その時点の値」を聞かれるなら期間型で持つ

7-4. deleted_at（論理削除）の扱い

■ 論理削除が全体に染み出す

  • 全クエリに条件が必要 — WHERE deleted_at IS NULL を1箇所忘れると削除済みが表示される。JOIN先にも必要
  • UNIQUE制約が機能しなくなる — 削除したメールアドレスで再登録できない。UNIQUE(email) が削除済み行にも効くため
  • 「削除」の意味が曖昧 — 退会したのか、管理者が消したのか、間違えて消したのか。deleted_at だけでは分からない

✓ 対処

  • 状態として扱う — status = 'withdrawn' + withdrawn_at + withdrawn_reason。何が起きたのかが読める（→ 8章）
  • UNIQUEは生成列で回避 — UNIQUE(email, IFNULL(deleted_at,'1970-01-01')) のように「有効な行だけ一意」を表現する
  • 本当に消すものは別テーブルへ退避 — 削除ではなくアーカイブ。本体テーブルは常に「生きている行」だけにする
  • 個人情報は物理削除が必要な場合がある — 削除要求への対応。論理削除だけでは要件を満たさないことがある

7-5. 型とタイムゾーン

保存は UTC

アプリ境界で変換し、DBにはUTCで入れる。MySQLの DATETIME はタイムゾーン情報を持たないので、運用ルールで統一するしかない。TIMESTAMP は暗黙変換が入るため、混在させない

「日付」は日付として持つ

誕生日・営業日・締め日は DATE。DATETIMEにすると 00:00:00 の解釈がタイムゾーンでズレて1日ずれる事故が起きる

精度を決める

DATETIME(3) / (6) を明示する。秒精度だと同一秒内の順序が決まらず、履歴の並び順が不定になる

現地時刻が意味を持つ場合

宿泊のチェックイン日、イベント開催時刻などは「現地の何時か」が本質。UTCに加えてタイムゾーン識別子も保存する（サマータイム・時差変更に耐えるため）

✓ これだけ覚える

  • 時間は記録時間・発生時間・有効期間の3種類。created_at は1つ目だけ
  • 期間は半開区間 [from, to)。境界の重複と隙間を同時に防げる
  • 「現在有効な行は1つ」は生成列 + UNIQUEで構造的に守れる
  • deleted_at は全クエリとUNIQUE制約に染み出す。状態として設計する

⇄ Trade-off

  • 履歴テーブルを持つ → 時点の再現・監査・分析が可能 / 全クエリに時点条件が必要になり、書き込みも2文になる
  • 現在値だけ持つ → 単純・高速 / 過去が再現できず、後から履歴化するのは実質不可能
  • valid_to に NULL → 意味が明確 / 条件が複雑でINDEXが効きにくい
  • valid_to に 9999-12-31 → クエリが単純・範囲索引が効く / 番兵値の意味を共有する必要がある

✕ よくある失敗

  • updated_at だけで履歴を再現しようとする — 直前の値は分からない。更新の回数も分からない
  • 期間の重なりを許す — 「その時点の価格」が2件返り、集計が静かに狂う
  • 発生時間を持たず記録時間で集計 — 遅延したWebhookやバッチ取込で日付がずれる
  • DATEで足りるものをDATETIMEにする — タイムゾーン変換で1日ずれる

? 設計時に自問する質問

  • この時刻は「記録した時刻」か「起きた時刻」か。ズレる可能性はあるか
  • 「先月15日時点の状態」を聞かれたら答えられるか
  • 将来日付での登録（予約された変更）が要件に含まれていないか
  • 期間が重なる行が入ったとき、誰がどう気づくか

08 状態をどうモデル化するか

結論: booleanをn本並べると 2n 通りの状態が表現可能になり、その大半は業務的にあり得ない。あり得ない状態を表現できてしまうスキーマは、いずれ必ずその状態になる。

8-1. 素朴な設計 — boolean を増やす

図8.1 — boolean n本 = 2^n 状態。statusは「取りうる状態の集合」そのものを表現する

8-2. 改善 — State として持つ

▸ ENUM型を使うか、VARCHAR + CHECK か

  • MySQLのENUM — 値の追加に ALTER TABLE が必要。順序の扱いに癖がある。アプリ側の定数と二重管理になる
  • VARCHAR + CHECK — 追加は同じくDDLだが、扱いが素直。多くの現場でこちら
  • 参照テーブル（order_statuses） — 値の追加がINSERTで済み、表示名も持てる。ただしFKとJOINが増え、コード側のswitchは結局必要
  • 状態の集合は業務ルールそのもの。頻繁に増えるなら設計を疑う（軸が混ざっている可能性が高い → 8-4）

8-4. status を1本にすべきか、軸を分けるべきか

▲ 「状態が増え続ける」ときは軸が混ざっている

次のような状態一覧が出てきたら赤信号。

pending / paid / paid_and_partially_shipped / paid_and_shipped / partially_refunded / refunded_and_shipped / ...
  • これは「支払い」と「出荷」という直交する2軸を1本のstatusに押し込んだ結果。組み合わせ爆発する
  • 独立に進む2つの進行は、2つの列に分ける

⇄ 1本 vs 複数軸

  • status 1本 → 状態が一目で分かる・遷移表が単純 / 直交する進行があると組み合わせ爆発する
  • 軸を分ける → 各軸の遷移が単純・部分出荷や分割返金を表現できる / 軸をまたいだ禁止組み合わせを別途守る必要がある（例: cancelled なのに shipped）
  • 判定: 「AとBは独立に進むか？」を問う。独立なら分ける。順番が決まっているなら1本

8-5. 遷移の履歴を持つ

✓ 履歴があると答えられるようになる質問

  • 「この注文はなぜキャンセルされたのか、誰が操作したのか」— 問い合わせ対応で毎回必要になる
  • 「注文から発送までの平均日数」— 現在の状態だけでは絶対に出せない
  • 「キャンセル率が先月から上がった原因」— reason 別に集計できる
  • 状態列は「今」しか答えられない。履歴は「なぜ」に答えられる

? Thinking Point

「paid_at などの日時カラムがあれば、遷移履歴テーブルは要らないのでは？」

考えてから開く

日時カラムで足りる範囲と、足りない範囲がはっきりある。

  • 日時カラムで足りる: 各状態に1回しか到達しない、かつ「誰が・なぜ」が不要な場合。多くの小規模サービスはここで十分
  • 足りなくなる瞬間: ①同じ状態に2回到達する（決済失敗→再決済でpaidが2回） ②操作者を記録する必要が出た ③取り消し・巻き戻しが発生する ④状態が増えてカラムも増え続ける
  • 実務的な順序: まず日時カラム。監査要件や問い合わせ対応で「誰が」が必要になった時点で遷移履歴テーブルを追加する。ただし後から追加しても過去は復元できないので、記録が重い業務（決済・医療・人事）なら最初から持つ

✓ これだけ覚える

  • boolean n本 = 2^n 状態。大半はあり得ない状態で、DBはそれを止めない
  • 状態モデリングの成果物は状態一覧ではなく遷移表
  • 状態変更の入口は1つの関数に集約し、直接代入させない
  • 状態が増え続けるなら、直交する軸が混ざっている疑い
  • 状態列は「今」、履歴は「なぜ」に答える

⇄ Trade-off

  • status列 + CHECK → 不正状態が入らない / 値の追加にDDLが必要
  • 参照テーブル → 値の追加が容易・表示名を持てる / JOIN増、コード側の分岐は結局必要
  • 遷移履歴を持つ → 原因分析・監査・リードタイム計測が可能 / 書き込みが増え、テーブルが肥大する
  • 日時カラムのみ → 単純・クエリが速い / 再遷移・操作者・理由を表現できない

✕ よくある失敗

  • is_xxx を足し続ける — 矛盾状態が本番に実在し、画面ごとに表示が食い違う
  • statusを文字列で直接代入 — typoが検出されず、'shiped' が本番データに残る
  • 遷移チェックを呼び出し側に散らす — 新しい経路を追加したときに必ず漏れる
  • statusと日時カラムの整合を取らない — status=shipped なのに shipped_at がNULLの行が生まれる

? 設計時に自問する質問

  • このbooleanの組み合わせで、あり得ない組み合わせはいくつあるか
  • 状態遷移図を描けるか。描けないなら仕様が決まっていないのでは
  • この2つの状態は独立に進むか、順序が決まっているか
  • 「なぜこの注文はこうなったのか」と聞かれて答えられるか

  • 「必要になったら履歴を足そう」 — 必要になる時は既に過去が失われている
  • 全テーブルに機械的な監査ログ — 容量と書き込みコストだけ増え、誰も読まない
  • 現在値と履歴を別トランザクションで更新 — 障害時にどちらが正か分からなくなる

  • 金額・在庫・権限・契約に関わる値か（→ 履歴が要る可能性が高い）

  • 履歴を持つとして、書き込み経路はすべてそこを通るか

10-3. 在庫をどう扱うか — 3つの選択

方式やり方得られるもの代償
A. 同一トランザクション注文作成と在庫減算を1つのTxで売り越しが絶対に起きない人気商品の行にロックが集中。セール時にスループットが落ちる
B. 引当（予約）モデル先に在庫を確保（reserved）し、後で確定確保と確定を分離でき、失効も扱える引当テーブルと失効処理が必要。設計が増える
C. 事後整合注文を受けてから非同期で在庫確認最速。大量注文を捌ける売り越しが発生しうる。キャンセル運用が前提

▸ 選択は業務が決める

  • 一点物（中古品・チケットの座席） → A か B。売り越しは即クレームであり、謝罪では済まない
  • 在庫潤沢な量産品 → C でも成立する。「まれに在庫切れでキャンセル連絡」が業務として許容されるため
  • 技術的な正しさだけでは決まらない。「売り越したらどうなるか」を業務側に聞く

10-4. 外部システム（決済）を跨ぐ場合

■ 外部API呼び出しをトランザクション内に入れると

  • トランザクションが外部の応答時間だけ開き続ける — 決済APIが3秒かかれば、3秒間ロックを保持する
  • ロールバックしても外部は戻らない — DBはロールバックできるが、課金は取り消されない
  • タイムアウト時に状態が不明 — 課金されたのかどうか分からないまま、DBだけロールバックされる

✓ ここでのデータモデル上の要求

  • 中間状態を表現できるスキーマ — 「注文はあるが未払い」という状態が正当に存在できること。boolean設計ではこれが表現できない（→ 8章）
  • 冪等キーを保存する — payments.idempotency_key UNIQUE。リトライで二重課金しない
  • 外部のIDを保存する — external_transaction_id。突合と返金に必須
  • 失効・回収の経路を持つ — 引当の expires_at、未払い注文の自動キャンセル。結果整合は「後で辻褄を合わせる仕組み」とセットで初めて成立する

10-5. 楽観ロックと version カラム

⇄ 楽観 vs 悲観

  • 楽観（version） → ロックを持たないので同時実行性が高い / 衝突時のリトライをアプリで書く必要がある。衝突が多いと無駄が増える
  • 悲観（SELECT ... FOR UPDATE） → 確実。リトライ不要 / ロック保持中は他が待つ。デッドロックの設計が必要
  • 使い分け: 画面で開いて長時間編集するもの（管理画面の商品編集）は楽観。短時間で完結し衝突が頻繁なもの（在庫減算）は悲観 or 条件付きUPDATE

✓ これだけ覚える

  • Aggregate = 1トランザクションで整合させる範囲。不変条件が閉じる単位で切る
  • Aggregate間はIDで参照し、別トランザクションで扱う
  • 外部API呼び出しはトランザクションの外。中間状態を表現できるスキーマが前提
  • 結果整合を選ぶなら、失効・再送・突合の仕組みをセットで設計する

⇄ Trade-off

  • Aggregateを大きく → 強い整合性が簡単に得られる / ロック競合と同時実行性の低下
  • Aggregateを小さく → スケールする / 跨る整合性を自前で設計する必要がある
  • 在庫を同一Tx → 売り越しゼロ / 人気商品でロック集中
  • 引当モデル → 分離と失効が扱える / テーブルとバッチが増える

✕ よくある失敗

  • 外部API呼び出しをトランザクション内に置く — ロック長時間保持、ロールバック不能な副作用
  • 「全部1つのトランザクションにすれば安全」 — 負荷が上がった瞬間にデッドロックとタイムアウトが多発する
  • 結果整合にしたが回収処理がない — 引当が残り続け、在庫が徐々に減っていく
  • 冪等キーを持たない — リトライやWebhook再送で二重課金・二重登録が起きる

? 設計時に自問する質問

  • この2つは同時に失敗しなければ矛盾するか。それとも片方だけ成功しても業務は回るか
  • このトランザクションはどのくらいの時間、どの行をロックするか
  • 途中で落ちたとき、その中間状態はスキーマ上で表現できるか
  • 同じ処理が2回実行されたらどうなるか

11 Queryから逆算するモデリング

結論: 書き込み側だけで設計すると、正しいが誰も引けないスキーマができる。「このデータをどう取り出すのか」を並行して設計する。

11-1. Write Model と Read Model は要求が逆

▸ 設計時にクエリを先に書く

  • スキーマを引く前に、主要画面で実際に投げるSQLを書いてみる。書けないなら、そのスキーマは未完成
  • 各クエリに 想定件数・レイテンシ要求・実行頻度を書く。「商品一覧: 100万件から20件、100ms以内、秒間200回」
  • ここから逆算してINDEXが決まり、時にはテーブル自体が変わる

11-2. EC — 一覧・検索・集計で必要なものが変わる

クエリ素朴な実装の限界必要になるモデル
注文履歴（自分の注文20件）問題なしINDEX(customer_id, ordered_at DESC) だけで足りる

複数条件の絞り込み + ソート条件の組み合わせ分だけ複合索引が必要になり破綻検索専用のフラットなテーブル or 検索エンジン
売れ筋ランキング注文明細を毎回集計 → 数千万行の走査集計テーブル（日次/時間次バッチ）

在庫のある商品だけ表示inventoriesとJOIN + フィルタ商品行に販売可能フラグを持ち、在庫変動時に更新（非正規化）

▸ 「集計テーブルを作る」の判断ライン

  • リアルタイム性の要求 — 「今日の売上」に5分の遅れが許されるなら集計テーブルでよい
  • 走査量 — 毎回1万行未満ならオンデマンド集計で十分。100万行を超えるなら事前集計
  • 実行頻度 — 管理者が月1回見るレポートのために集計テーブルを作るのは過剰

11-3. SNS — 書き込み時に作るか、読み込み時に作るか

▲ ここでの学び

「posts というテーブルが必要」まではどちらも同じ。そこから先はクエリが決める。
データの構造だけを見て設計を完了したと思うと、この分岐に気づけない。読み方が違えば、正しいスキーマも違う。

11-4. 予約サービス — 空き検索が形を決める

✓ 逆算の型

  1. 主要クエリを列挙する（一覧 / 検索 / 集計 / ランキング / 履歴 / 詳細）
  2. 各クエリの絞り込み条件・ソート条件・件数を書く
  3. Write Modelのままで引けるか確認。引けるなら索引を設計して終わり
  4. 引けないものだけ、Read Model（集計テーブル・展開テーブル・検索エンジン）を追加する
  5. Read Modelは常に再構築可能にする。Write Modelが唯一の真実であることを崩さない

11-5. CQRSに踏み込む前に

⇄ 読み書きを分離するコスト

  • 得るもの: 読みと書きを独立に最適化できる。読み側のスキーマ変更が書き側に影響しない
  • 失うもの: 同期の仕組み（バッチ or イベント）が必要。遅延が発生し、「保存したのに一覧に出ない」をUIで扱う必要がある。運用対象が増える
  • 段階を踏む: ①索引追加 → ②集計カラム → ③同一DB内の集計テーブル → ④別ストア（検索エンジン等）。①②で解決するものを④で解こうとしない

✓ これだけ覚える

  • スキーマを引く前に主要クエリを書く。書けないスキーマは未完成
  • Write Modelは整合性、Read Modelは取得速度。要求が逆なので1つの形で両立しないことがある
  • 同じデータでも、読み方が違えば正しいテーブルが違う
  • Read Modelは常にWrite Modelから再構築可能に保つ

⇄ Trade-off

  • 読み専用モデルを作る → 読みが速い・書き側を汚さない / 同期の仕組みと遅延、運用対象増
  • 1つのモデルで通す → 単純・常に最新 / 複雑なクエリで性能が頭打ちになる
  • Fan-out on Write → 読みが最速 / 書き込み増幅、データ量爆発
  • Fan-out on Read → データが単一・常に正確 / フォロー数が増えると読みが重い

✕ よくある失敗

  • 正規化だけ完璧で、一覧画面が5テーブルJOIN — リリース直後に性能問題になる
  • 索引で解決できる問題に検索エンジンを導入 — 運用対象が増えただけになる
  • Read Modelを手で直して真実にしてしまう — 再構築すると直した内容が消える
  • 本番DBで重い分析クエリを回す — 業務処理のレイテンシを巻き込む

? 設計時に自問する質問

  • この画面を出すSQLを今すぐ書けるか。何テーブルJOINになるか
  • そのクエリは3年後のデータ量でも同じ速度か
  • この絞り込み条件の組み合わせは何通りあるか。索引で賄えるか
  • Read Modelを全部消しても、元データから作り直せるか

12 ORMとの関係

結論: ORMの構造体は「テーブルの形」であって「業務の形」ではない。同一視すると、DBの都合が業務ルールに侵入し、業務ルールが表現できなくなる。

12-1. 3つのモデルと、統合/分離

Domain Model

業務ルールと不変条件を持つ。不正な状態を作れないコンストラクタとメソッドを持つ。DBもJSONも知らない

DB Model（ORM struct）

テーブルと1:1。タグ・NULL許容型・リレーション定義を持つ。ゼロ値で構築できてしまう

DTO（API/リクエスト・レスポンス）

外部との契約。JSONタグ・バリデーションタグを持つ。後方互換のために自由に変えられない

3つを1つにすると

structがgorm:"..."json:"..."validate:"..."で埋まる。DBのカラム名変更がAPIレスポンスを壊す

12-2. Trade-off を正直に見る

観点統合（1 struct）分離（3層）
初期実装速度速い変換コードが必要
業務ルールの守られ方構造上、迂回できる不正な状態を構築できない
DBスキーマ変更の影響APIまで波及変換関数の中で吸収される
テストDBが要るDomainは純粋関数としてテストできる
コード量少ない1.5〜2倍
読みやすさ追いやすい層をまたぐので追跡が面倒
向いている規模管理画面・小規模・CRUD中心業務ルールが多い・長期運用・複数人開発

▸ 中間解（実務で最も多い）

  • DTOだけは必ず分ける — API契約とDBスキーマを直結させない。ここは分離のコストが最も低く、効果が最も高い
  • Domain と DB Model は、業務ルールが厚いAggregateだけ分ける — Order は分離、マスタ系のCRUDは統合、という混在は合理的
  • 全部分離 or 全部統合という二択にしない。「どこにルールが集中しているか」で決める

12-3. ORMに引っ張られたモデリングの典型

ORMの都合引っ張られた結果本来あるべき姿
複合PKが扱いづらい全テーブルに id を付け、UNIQUEを忘れる代理キーを使うならUNIQUE制約を必ずセットで
リレーションの自動ロードPreload("Items.Product.Category") が増殖し、1画面で数十クエリAggregate境界を越える参照はIDのみ。必要なものを明示的に取る
自動マイグレーション制約・索引がコードから抜け落ちる。本番と差分が出るDDLはマイグレーションファイルで管理し、レビュー対象にする
Soft Delete が標準機能全テーブルに deleted_at。意味が曖昧なまま増殖削除の意味を業務で定義する（→ 7章）
NULL許容が面倒すべて非ポインタ型 → ゼロ値とNULLが区別できないNULLに意味があるならポインタ / sql.Null型を使う
structタグで完結させたいCHECK制約を書かず、バリデーションタグだけで済ませるDBの制約はDBに書く（→ 5章）
1テーブル1structの発想Aggregateという概念が消え、トランザクション境界が曖昧にRepositoryの単位をAggregateに合わせる（→ 10章）

✓ Repositoryの単位はAggregate

  • テーブルごとにRepositoryを作らない。OrderRepository.Save(order) が orders と order_items を一括で保存する
  • これにより「明細だけ保存して注文ヘッダを保存し忘れる」という状態が呼び出し側から不可能になる
  • OrderItemRepository を作った時点で、Aggregateの境界は壊れている

✓ これだけ覚える

  • ORM structはテーブルの形であって業務の形ではない
  • 分離の効果が最も高いのはDTO（API契約）。ここだけは常に分ける
  • Repositoryの単位はテーブルではなくAggregate
  • DDL（制約・索引）はORMの自動生成に任せず、マイグレーションでレビューする

⇄ Trade-off

  • 1 struct で統合 → 実装が速く読みやすい / 業務ルールを迂回でき、DB変更がAPIまで波及
  • 完全分離 → ルールが守られテストしやすい / コード量1.5〜2倍、層をまたぐ追跡コスト
  • 部分分離 → コストと効果のバランスが良い / どこを分けるかの判断基準をチームで共有する必要がある

✕ よくある失敗

  • 金額を float で持つ — 丸め誤差で合計が1円合わなくなる。整数（最小単位）かDECIMALで持つ
  • statusを裸のstringで持つ — typoがコンパイルを通り、本番データに残る
  • Preloadの連鎖 — 1画面で不要なデータを大量にロードし、メモリとレイテンシを消費
  • AutoMigrateを本番で使う — 意図しないカラム削除・索引欠落が起きる

? 設計時に自問する質問

  • このstructはゼロ値で構築できてしまうか。できるなら不正な状態が作れる
  • DBのカラム名を変えたら、APIレスポンスのキーも変わるか
  • Repositoryの単位はAggregateと一致しているか
  • この制約はコードにしか存在しないのではないか

実践 — アンチパターンと通し設計

最後に、現場で繰り返し現れる10の失敗形と、ECを題材にした要件からコードまでの通し設計を置く。ここまでの章で扱った判断が、どう組み合わさるかを確認する。

13 アンチパターン10

共通する構造は1つ。短期的に書くのが楽な形を選ぶと、スキーマから業務の意味が読めなくなり、その状態が数年残る。

① God Table — 1つのテーブルが全部を知っている

■ 症状と具体例

users テーブル（カラム 68本） id, email, password_hash, name, kana, tel, postal, pref, city, addr1, addr2, company_name, company_tel, invoice_no, bank_name, branch, account_no, plan, plan_started_at, trial_ends_at, card_last4, card_brand, card_exp, notify_email, notify_sms, notify_push, notify_marketing, ... is_admin, is_staff, is_verified, is_locked, is_deleted, ... last_login_at, login_count, failed_login_count, ...
  • 起きること: 1行の更新で行ロックが広範囲の機能に波及。SELECT * が常に重い。「userを触る」変更が常に全機能のレビュー対象になる
  • 原因: 「ユーザーに関係するから users に足す」という判断。関係の有無ではなくライフサイクルで分けるべき

✓ 直し方

  • 認証（email/password/2FA）/ プロフィール / 請求情報 / 通知設定 / 権限 / ログイン履歴 に分割する
  • 判断軸: 更新頻度・権限・NULL率・ライフサイクルが違うものは別テーブル（→ 2章）
  • 既存の巨大テーブルは一度に直せない。新機能のカラムを追加しないところから始め、段階的に切り出す

② JSON Columnへの詰め込みすぎ

✓ JSONを使ってよい条件

  • 検索も集計もしない — 表示するだけ、ログとして残すだけ
  • 部分更新しない — 常に丸ごと置き換える
  • 構造が本質的に不定 — 外部APIの生レスポンス、アンケートの自由回答、機能フラグ
  • 適例: webhook_events.raw_payload / audit_logs.changes / products.spec_attributes（商品カテゴリごとに異なる仕様）
  • 不適例: 金額・数量・状態・関連ID。業務が依存する値は必ずカラムにする

③ Nullableだらけ

■ 症状

  • 30カラム中25カラムがNULL許容。どの組み合わせが正しい行なのか、スキーマからは一切読めない
  • アプリ側が全カラムでnilチェックをする羽目になり、コードが防御的になる
  • 典型的な原因: 1つのテーブルに複数の種類（サブタイプ）を同居させている
payments テーブル id, order_id, method, card_brand, card_last4, card_token, ← method='card' のときだけ bank_name, branch_code, account_no, ← method='bank' のときだけ conveni_code, conveni_receipt_no, due_date, ← method='conveni' のときだけ point_amount, point_account_id ← method='point' のときだけ

✓ 直し方 — 共通部分とサブタイプに分ける

判断: サブタイプが2〜3個で属性が少数なら、NULL許容 + CHECK のまま1テーブルでも実務的。種類が増え続けるなら分割。

④ Boolean乱立

■ 8章の再掲 + 見分け方

  • 危険信号: 同じテーブルに is_ で始まるカラムが3本以上ある
  • 確認方法: 全組み合わせを表にして、「業務的に意味のある行」が何%か数える。50%を切ったらstatusに置き換える
  • 例外: 本当に独立した設定フラグ（notify_email, notify_sms）は並べてよい。進行状態を表すbooleanだけが問題

⑤ EAV（Entity-Attribute-Value）

✓ 代替

  • 検索・絞り込みに使う属性はカラムにする — 「色」「サイズ」で検索するなら、それはEAVに置くべきではない
  • 表示専用の可変属性はJSONカラム — EAVより圧倒的に扱いやすい（1行で済む、部分検索はJSON索引で可）
  • カテゴリごとにテーブルを分ける — 書籍/家電/衣類で属性が違うなら、それぞれのテーブルを持つ
  • EAVが正当化される数少ない場面: ユーザーが実行時に定義するカスタムフィールド（CRMのカスタム項目など）。その場合も「検索対象になった項目はカラムに昇格させる」運用を持つ

⑥ 意味のないN:N

■ 3章の再掲 + 判定

  • 症状: 中間テーブルの行数が、片方のテーブルの行数とほぼ同じ（= 実質1:N）
  • 確認SQL: SELECT product_id, COUNT(*) FROM product_categories GROUP BY 1 HAVING COUNT(*) > 1; が0件なら、N:Nである必要がない
  • 害: 全クエリにJOINが1本増え、「1商品1カテゴリ」というルールがDBで守られていない

⑦ 履歴を上書きする

▸ 原則

履歴テーブルへのUPDATE / DELETE は、原則として権限ごと禁止する。訂正も「訂正イベント」として追記する。
上書きを許した時点で、その履歴は「調査に使えるかどうか分からないデータ」になり、監査にも耐えない。

⑧ Derived Data（派生データ）の無管理な重複保持

■ 症状

users.full_name = last_name + first_name ← 片方だけ更新して不一致 orders.item_count = COUNT(order_items) ← 明細追加時に更新漏れ products.review_count = COUNT(reviews) ← レビュー削除時に減らし忘れ customers.total_spent = SUM(orders.total) ← 返金を引き忘れ users.age = 生年月日から計算 ← 誕生日が来ても更新されない
  • 共通点: どれも「計算できるもの」を保存している。保存自体は悪くないが、更新経路と検出手段がないまま保存しているのが問題
  • users.age は特に悪質 — 時間経過だけで勝手に間違いになる。生年月日を持ち、必要なときに計算する

✓ 判断表

派生値持つべきか理由
age（年齢）持たない時間で自動的に狂う。birth_dateから計算
full_name持たない表示時に結合すればよい。検索用途なら生成列
order.total_amount持つ計算式（税・送料・割引）が時期で変わる確定値（→ 4章）
product.review_count条件付きで持つソートに使うなら必要。更新経路の集約 + 日次再計算とセット
inventory.quantity持つ制約（>=0）を張るために必要。movementsとの照合を定期実行

⑨ Business Ruleがスキーマから読み取れない

■ 症状 — 新メンバーがDDLを見て何も分からない状態

CREATE TABLE reservations ( id BIGINT, user_id BIGINT, room_id BIGINT, start_date VARCHAR(255), ← なぜ文字列？日付ではないのか end_date VARCHAR(255), status VARCHAR(255), ← 取りうる値は？ flag1 TINYINT, ← 何のフラグ？ memo TEXT, ← 何が入る？ type INT ← 1と2と3の意味は？ ); -- FKなし。CHECKなし。UNIQUEなし。コメントなし。
  • 起きること: 仕様が「コードを読むか、古参メンバーに聞く」でしか分からない。その人が辞めた時点で仕様が失われる
  • 本質: スキーマはドキュメントでもある。制約は実行される仕様書（コメントと違い、嘘をつけない）

✓ スキーマに意味を載せる方法

  • 型を正しく使う — 日付はDATE、金額はDECIMAL/BIGINT、真偽値はBOOLEAN。VARCHAR(255)一択をやめる
  • 列挙値はCHECKで宣言 — 取りうる値がDDLに書いてある状態にする
  • FKを張る — 関連がDDLから読める。ER図を自動生成できるようになる
  • カラム名で意味を伝える — flag1 ではなく is_smoking_allowed。type ではなく reservation_source
  • COMMENT を書く — 特に「なぜこうなっているか」。単位（円/銭、秒/ミリ秒）は必ず書く

⑩ 外部システムIDと内部IDの混同

▸ 原則

自分のシステムの同一性は、自分で決める。外部のIDは「その外部システムにおける識別子」という属性にすぎない。
外部IDをPKにするのは、自社データの構造を他社の都合に委ねること。連携先が増えた瞬間に破綻する。

✓ これだけ覚える

  • 10個すべての本質は「スキーマから業務の意味が読めなくなること」
  • 制約・型・カラム名は実行される仕様書。コメントと違い嘘をつけない
  • 柔軟性（JSON / EAV / 汎用カラム）を得るたびに、検証可能性を失っている
  • 外部システムのIDは属性。同一性は自分で決める

⇄ Trade-off

  • JSON採用 → スキーマ変更なしで追加できる / 検索・集計・制約・FKをすべて失う
  • EAV採用 → 実行時に属性を増やせる / 型も制約も索引も失い、JOINが条件数だけ増える
  • 派生値を保持 → ソート・絞り込みが可能 / 更新漏れによる不整合が必ず発生する
  • テーブル分割（サブタイプ） → NOT NULLを張れる / 「どちらか一方が存在する」の強制が難しい

✕ よくある失敗

  • 「とりあえずJSONに入れておけば後で何とかなる」 — 形式が混在してから直すのは非常に高い
  • 全カラムをVARCHAR(255) NULL — 型による検証を丸ごと放棄している
  • 履歴テーブルをUPDATE — 履歴の価値そのものが消える
  • 外部サービスのIDをPKに使う — 乗り換え・複数連携で詰む

? 設計時に自問する質問

  • このDDLを初見の人が読んで、業務ルールをいくつ読み取れるか
  • このJSONの中身を、検索・集計・ソートに使う日は来ないか
  • この派生値がズレたとき、誰がいつ気づくか
  • このテーブルのNULL許容カラムは何割か。サブタイプが混ざっていないか

Step 4. Physical Schema

? Thinking Point 2

order_items に UNIQUE(order_id, product_id) を張った。これは正しいか？

考えてから開く

業務によって変わる。判断を分けるのは「同じ商品を1注文に2行で持ちたい場面があるか」。

  • 張ってよい場合: カートで同じ商品を追加したら数量が増える仕様。一般的なEC
  • 張ってはいけない場合: ①ギフト設定が明細ごとに違う（同じ商品を別の相手に）②明細ごとに異なるクーポンが適用される ③同じ商品を異なる価格で（一部だけセール適用）
  • 教訓: UNIQUE制約は「業務上の一意性の宣言」。技術的に張れるから張るのではなく、業務に確認して張る。後から外すのは簡単だが、外した理由が記録に残らない

Step 6. 主要Query

? Thinking Point 3

daily_product_sales を作った。では「今日の売上」もこのテーブルから取るべきか？

考えてから開く
  • 日次バッチの集計テーブルから「今日」を取ると、当日分が存在しない（バッチは翌日実行のため）。よくある事故
  • 対処1: 当日分は orders から直接集計、過去分は集計テーブル、とクエリを分ける。「境界日の扱い」を間違えると二重計上になる
  • 対処2: 集計を時間次に上げ、当日も含める。バッチの頻度と鮮度のトレードオフ
  • 設計上の学び: 集計テーブルを作ったら「いつからいつまでが入っているか」を必ずメタデータで持つ（last_aggregated_at）。持たないと、欠損と「売上ゼロ」が区別できない

Step 7. 将来の変更に耐えるか

将来の要求このモデルでの対応難易度
クーポン・割引を導入したいorder_discounts を追加。total_amount は既に確定値なので過去は影響なし低
定期購入（サブスク）を始めたいsubscriptions を追加し、注文を自動生成。orders 側は変更不要低
複数通貨に対応したいcurrency は既にある。unit_price と合わせてMoneyとして扱う。レートの時点記録が別途必要中
分割払いを導入したいpayments は既に1注文N行。スキーマ変更不要低
マーケットプレイス化（複数出品者）products に seller_id、orders を出品者ごとに分割するか検討。注文の単位そのものが変わる高
「注文時点の在庫数」を後から知りたいinventory_movements があるので再構築できる低
3年前の注文の消費税率で再発行税率を凍結していないと不可能。今のうちに tax_rate を order_items に足す高（後からでは不可）

▲ 最後の行が最も重要

ここまで丁寧に設計しても、凍結し忘れた属性は後から取り戻せない。
「請求書・領収書に印字される値はすべて凍結する」という基準を持つと、税率・送料・割引額・事業者情報の取りこぼしが減る。
設計レビューでは「この注文の領収書を5年後に再発行できるか」を1問だけ必ず聞く。
