図解DDD実践
update処理の設計と、MVCからの移行コスト

DDDの理論書ではなく、実務で最初に必要になる2つの具体的な問いだけを扱う。
①「更新処理をどう書くか」（get → domain → save / トランザクション境界 / ロック戦略）
②「MVCから移行すると何が増え、いくらかかるか」（構造物の数 / 判断基準 / 段階的移行）

理論の全体像（Entity・VO・Aggregate・Bounded Context・ifの置き場）は software-design-micro.html の Part 3〜5 にある。この教材はその実践編・移行編として、コードと判断基準に絞る。

主張1

クライアントが送るのは「命令」であって「新しい状態」ではない。この1点を守るだけで、更新処理の設計はほぼ決まる。

主張2

トランザクション境界はusecase（application service）。ドメインはトランザクションを知らない。Repositoryも自分でcommitしない。

主張3

DDDは「構造物の増殖」という明確なコストを伴う。1リソースで構造体5〜6個。払う価値があるかを機能単位で判断する。

00 はじめに — DDDの1つの問い

DDDの本は分厚いが、実務で最初に効くのは「ビジネスルールをどこに書くか」という1つの問いだけ。そして更新処理（update）は、この問いが最も鋭く現れる場所である。なぜなら「何を変えてよいか」の判断が、必ずどこかに書かれなければならないから。

図0-1 同じ「名前変更」でも、ルールの置き場所で設計が根本的に変わる。

00.5 全体地図

この教材は2部構成。Part 1 は「正しい書き方」、Part 2 は「そのコストを払うべきかの判断」。順序が重要 — 正しい書き方を知らずにコストを議論することはできない。

図0-2 2部構成。Part 1で「正しさ」を、Part 2で「経済性」を扱う。

Part 1

update処理の設計

結論を先に: usecase内で「get → ドメインロジック → save」の順に処理し、その全体をトランザクションで囲み、ロックは楽観ロックをデフォルトにする。この3行が Part 1 のすべてである。以下はその根拠と実装。

01 アンチパターン: 全フィールド送信 → 直接update

最も多く見る形。動くし、コードも短い。だから疑われない。しかしこれは「DDDの構造だけ借用したトランザクションスクリプト」である。

③ なぜ問題なのか — 4つの具体的な損失

図1-1 4つの損失。特に損失4（送られなかったフィールドが消える）は実際のデータ破壊につながる。

⑩ このアンチパターンを見つける質問

  • 「このリクエストで、送られなかったフィールドはどうなりますか？」 — 答えられないなら設計が曖昧
  • 「role を勝手に変えられませんか？」 — 認可がどこにあるかを確認する
  • 「同じ処理をバッチから呼びたくなったらどうしますか？」 — handlerにルールがあると呼べない
  • 「Entityにメソッドが1つもないのはなぜですか？」 — 貧血モデルの確認

02 正しい形: get → domain → save

結論。usecaseは「取得して、Entityに依頼して、保存する」だけ。判定も計算もEntityが行う。usecaseにif文が並び始めたら、それはEntityに移すべきロジックである。

図2-1 3ステップ。②が「Entityへの依頼」であることが本質。

⑥ Before / After — 「文字数上限を100→50に変える」要求

観点アンチパターン（全フィールド送信）get→domain→save
変更箇所handlerのバリデーション + フロントの検証 + バッチ + 管理画面 = 4箇所domain/user.go の定数1箇所
テストDBを立てて統合テストを4本修正単体テストに1ケース追加（1ms）
漏れのリスク高（1箇所忘れると不整合なデータが入る）構造的にゼロ
実装時間半日（4箇所の調査 + 修正 + 動作確認）10分

03 「命令」と「状態」の違い

結論。クライアントが送るべきは「命令（コマンド）」であり、「エンティティの新しい状態」ではない。この区別を最初に決めないと、APIの形がドメイン設計を歪めてしまう。

図3-1 状態型と命令型。状態遷移を含む操作は命令型でなければルールを守れない。

⑨ 過剰になる境界 — 命令型にしすぎる害

  • 属性1つごとにエンドポイントを作る — /users/1/change-phone /change-address /change-birthday… 10個のエンドポイントと10個のUseCaseが生まれる。設定画面で全部同時に編集するなら、まとめて1つのPUTでよい
  • 判定基準: 「その項目が、他と違う権限・検証・副作用を持つか」。Noなら同じエンドポイントでまとめる
  • 現実的な形: PUT /users/1/profile（名前・電話・住所をまとめて）+ POST /users/1/change-role（権限が違う）+ POST /users/1/withdraw（状態遷移）

04 トランザクション境界はどこか

結論。usecase（application service）。理由は「1つの業務操作 = 全部成功か全部失敗」という単位が、usecaseと一致するから。domainに置くとインフラを知ることになり、repositoryに置くと複数操作をまとめられない。

図4-1 Lost Update。トランザクションと楽観ロックは別の道具で、両方必要。

③ なぜ domain / repository ではないのか

置き場所問題判定
domain（Entity）Entityがトランザクション（インフラの概念）を知ることになる。func (u *User) ChangeName(name string, tx *gorm.DB) のようなシグネチャはドメイン層の汚染。単体テストにもDBが必要になる不可
repository の内部1メソッド = 1トランザクションになるので、「ユーザー更新 + 監査ログ記録」を1つのTxにできない。片方だけ成功する状態が生まれる複数操作があると不可
handler / middleware「1リクエスト = 1Tx」になる。読み取りAPIでも無駄にTxが張られ、外部API呼び出しがTx内に入ってしまう（最悪）推奨しない
usecase「1つの業務操作」の単位と一致する。複数Repositoryをまとめられる。domainは無関係でいられる★ これ

context に値を入れることへの批判: Goのガイドラインでは「contextは必須の依存を運ぶべきではない」とされる。反論としては「Txがない場合は通常接続にデグレードするので壊れない」「代替案（Reposを引数で渡す）は保守コストが高い」。弱点を潰す方法として、Tx必須のメソッドで if _, ok := From(ctx); !ok { return ErrNoTransaction } と検査するのが実務的。詳細は software-design-micro.html ch32（5方式の比較）。

⑩ トランザクションのレビュー観点

  • Txの中に外部通信（HTTP・メール・S3・Queue publish）が入っていないか — 例外なしのルール。ロック時間が外部の応答時間になる
  • Txが何ms続くか（100ms超は要注意）
  • 複数テーブルを更新する順序が、他の箇所と一致しているか（デッドロック）
  • ロールバックされたとき、メモリ上のEntityはどうなるか — Goではロールバックしてもメモリ上のEntityは変更されたまま。そのEntityを再利用すると不整合になる（リトライ時に注意）

05 楽観ロックと悲観ロック

結論。DDDでは楽観ロックをデフォルトにする。理由は「ロックを取らないのでスループットが落ちない」「デッドロックしない」「Aggregateの境界と一致する」の3つ。悲観ロックが必要なのは「必ず成功させたい」処理だけ。

図5-1 3方式。DDDのデフォルトは①、性能が要求されるカウンタ系は③。

④ 選択の判断表

対象方式リトライ理由
ユーザー・予約などのEntity更新楽観ロックWorkerなら自動 / 人間なら409競合が稀。Aggregate単位と一致する
在庫の減算原子的UPDATE不要WHERE remain >= 1 で原子的に判定。Entityを通すと並行実行で破れる
ポイント・残高の加算原子的UPDATE + 台帳不要履歴から再計算できる形にする（監査要件）
連番の発行SEQUENCE / AUTO_INCREMENT不要「最大値+1」は競合する。DBの機能を使う
バッチのジョブ取得FOR UPDATE SKIP LOCKED不要他のWorkerが処理中の行を飛ばす
複雑な読み書き（複数テーブル参照後に判定）悲観ロック不要原子的UPDATEに落とせない場合のみ

重要な認識: 「Entityの中でチェックしているから安全」は並行実行下では成り立たない。if u.balance >= amount をEntityに書いても、2つのgoroutineが同じ残高を読めば両方通る。アプリの不変条件とDBの制約は二重化する（詳細: software-design-micro.html ch20, ch46 / transaction-system-design.html）。

06 対比表と「DBアクセス2回」の是非

Part 1 の総括。get→変更→save は DBアクセスが2回になる。これが唯一の実質的なコストなので、正面から評価する。

⑥ 総合対比表

観点全フィールド送信 → 直接updateget → 変更 → save
ドメイン知識の場所散逸（handler / フロントエンドに漏れる）Entityに集約
不変条件の保護できない（任意の値が入る）Entityのメソッドで保護
状態遷移の制御できない（statusを直接書ける）遷移表で制御できる
DBアクセス数1回（UPDATE のみ）2回（SELECT + UPDATE）
競合検知難しい（読んでいないのでversionが分からない）楽観ロックで対応可
「送られなかったフィールド」の扱い空文字で上書きされる危険触らないフィールドはそのまま
監査ログ何が変わったか分からない変更前後を比較できる
単体テストDBが必要Entityだけで書ける（1ms）
別の入り口からの再利用ルールを再実装する同じEntityメソッドを呼ぶ
実装の初期コスト低（3行）中（Entity + メソッド + テスト）

⑧ 「DBアクセスが2回になる」を正面から評価する

実際のコスト

同一AZ内のRDSで 1クエリのRTTは 0.5〜2ms。主キー検索のSELECTは1ms未満。つまり増分は約1ms。HTTPリクエスト全体が50〜200msなら、1〜2%の増加。

気にすべき場合

①ループの中で更新する（N件 → 2N クエリ）②毎秒数千件の更新 ③RTTが大きい構成（クロスAZ・クロスリージョン）。この3つに該当しないなら、測る前に最適化する理由はない。

ループの場合の対処

「1件ずつget→save」をやめて、バルク処理にする。FindByIDs で一括取得 → メモリ上で全Entityを変更 → SaveAll で一括更新。Entityを通す形は維持できる。

高スループットの場合の対処

Entityを通さない高速パスを、意図的に用意する（原子的UPDATE一発）。ただし①どのルールを捨てたか ②どう検出するか（突合バッチ）をADRに書く。これは「妥協」ではなく「担保の場所を移す」設計判断。

Part 1 のまとめ

  1. クライアントは「命令」を送る。Entityの新しい状態を送らせない
  2. usecaseは get → Entityに依頼 → save の3ステップだけ。if文が並んだらEntityに移す
  3. トランザクション境界はusecase。TransactionManagerをinterfaceで注入する
  4. 楽観ロックをデフォルトにする。version は Entity が持ち、WHERE句は repository が書く
  5. 在庫・カウンタは原子的UPDATE。Entityのチェックは並行実行で破れる
  6. DBアクセス2回は約1ms。ループと高スループット以外では問題にならない

Part 2

MVC → DDD の移行コスト

DDDは堅実だが、MVCからの移行は「構造物の増殖」という明確なコストを伴う。メリットとコストを正確に把握した上で、機能単位で採用を判断するのが正しい態度。「DDDが正しいから全部DDDにする」は判断の放棄である。

07 生まれる構造物の一覧

MVCでは db.Model 1つを全レイヤーで使い回していた。DDDでは同じデータが4〜5種類の構造体 + mapper に分解される。まずこれを正確に数える。

図7-1 1リソースで型5個 + mapper 4個。これがDDDの実質的なコストの正体。

08 なぜ増えるのか — 「変更の局所化」を買っている

構造物が増える理由は「各レイヤーは自分の関心事だけを持つべき」という原則の帰結。抽象論ではなく、具体的な変更シナリオで効果を測る。

⑦ 5つの変更シナリオで比較する

変更要求MVC の影響範囲DDD の影響範囲
DBのカラム名を name → display_name に変える structのタグを変える → APIのJSONキーも変わる → フロントエンドが壊れる
（両方のタグを併記している構造体なので、片方だけ変えられない）		 repository/user_record.go + mapper の2ファイル。APIは1文字も変わらない
APIレスポンスに「登録日からの経過日数」を追加 DBに列を足すか、structに gorm:"-" のフィールドを足す（DBモデルが表示用の項目を持ち始める） handler/dto.go の1ファイル。Response DTOで計算する
「退会済みユーザーは名前を変更できない」ルールを追加 handlerに if u.Status == "withdrawn" を追加 → バッチ・管理画面・CSV取込にも同じifを追加（4箇所） domain/user.go の ChangeName() に3行。全入り口に自動反映
内部管理用のフラグ is_test_account を追加 JSONに勝手に出る（json:"-" を書き忘れると外部に漏洩） record に足すだけ。Response DTOに書かなければ出ない（デフォルトで安全）
MySQL → PostgreSQL に移行 全レイヤーのタグとクエリを確認（実際には移行しないことが多い） repository/ 配下のみ

最も価値が出るのは3行目と4行目。「ルールの追加」と「内部項目の隠蔽」は実務で頻繁に発生し、MVCでは必ず事故る。逆に1行目・5行目（DB移行）は稀なので、これを理由にDDDを推すのは説得力が弱い。

09 コストを数字で見る

「認知負荷が高い」のような主観ではなく、測れる数字で見積もる。移行を提案するときも、断るときも、数字がなければ議論にならない。

図9-1 コストの実測感覚。初回は3〜4倍、2回目以降の変更で逆転する。

⑧ 損益分岐点はどこか

ざっくりした試算

初回の追加コストが約8時間、1回の変更で節約できる時間が約2時間とすると、4回変更が来れば元が取れる。実務では「1つの機能に年3〜5回の変更」は普通なので、1〜1.5年で回収される計算になる。

回収されないケース

①半年後にサービスが終わる ②その機能に誰も変更を要求しない（マスタCRUD・お知らせ管理）③チームが1人で、全部頭に入っている（他人が読む便益が発生しない）

回収が速いケース

①状態遷移がある（予約・注文・承認フロー）②お金・在庫を扱う（事故のコストが高い）③外部システムと連携する（相手の仕様変更が来る）④入り口が複数ある

この試算の使い方

「DDDにすべきか」の議論を、感情論から数字の議論に変えるためのもの。数字自体はチームの習熟度で大きく変わるので、自分のチームで最初の1機能を実装して実測するのが最も確実。

10 採用判断のフレーム

結論。プロジェクト単位ではなく、機能単位で判断する。同じシステムの中に「DDDの機能」と「MVCの機能」が共存するのが正しい状態。

図10-1 3分類（DDDの Distillation）。投資はCoreに集中させ、Genericには払わない。

④ 分類のためのスコアシート（実務で使う）

質問Yes の点数
1. 不変条件（常に真であるべきルール）が3つ以上あるか+2
2. 状態遷移があり、遷移の可否にルールがあるか+2
3. 入り口が2つ以上あるか（API / Worker / バッチ / 管理画面 / CSV）+2
4. 並行実行・重複リクエストがあり得るか+2
5. お金・在庫・法的義務が関わるか+2
6. 外部システムと連携するか+1
7. 過去1年で仕様変更が3回以上あった（または今後見込まれる）か+1
8. 複数人・複数チームが同じコードを触るか+1
9. 内部情報（原価・仕入値・内部メモ）を含むか+1

0〜2点 → Generic

handler + GORM 直結。Entity も UseCase も作らない。ADRに理由を残す。

3〜5点 → Supporting

Entity + Repository + 必要なVOだけ。record と Entity は分けない（gormタグ併用でよい）。

6〜9点 → 準Core

Entity + VO + Repository + UseCase + mapper。トランザクション境界を明示する。

10点以上 → Core

全部 + 楽観ロック + 冪等性 + 統合テスト + 突合バッチ。予約Webhookは12点。

⑨ 「統一しないこと」のコストと対処

統一しないコスト

「なぜここは層があって、ここはないのか」を毎回説明する必要がある。新メンバーは混乱し、レビュー基準がファイルごとに変わる。

対処1: ディレクトリで物理的に分ける

internal/reservation/（Clean）と internal/master/（CRUD）を分ける。「どこにあるか」で「どう書くか」が分かる状態にする。

対処2: ADRに書く

docs/adr/0012-crud-without-ddd.md「マスタ系CRUDは不変条件が単一かつ入り口が管理画面のみであるため、handler + GORM の2層とする。ルールが2つ以上になった時点で通常の層構成に移行する」

対処3: パターンを2〜3種類に集約する

毎ファイル違うのは規律がない。「Core形」「CRUD形」の2種類だけにして、それ以外を作らない。Supporting は「Core形の一部を省いたもの」として扱う。

11 段階的移行の実務手順

結論。全面書き換え（Big Rewrite）はしない。境界を決めて共存させ、新規機能から適用する。既存コードは「変更要求が来た機能」だけを移行する。

図11-1 5フェーズ。「移行完了」を目標にしないのが重要。Genericは永久にMVCのままでよい。

④ 移行の7つの実務ルール

  1. 全面書き換えをしない — Big Rewrite は歴史的にほぼ失敗する。動いているコードには価値がある
  2. Characterization Test を先に書く — 現在の挙動を固定してからリファクタする（詳細: software-design-micro.html ch59）
  3. リファクタと機能追加を同じPRに混ぜない — 壊れたとき原因が特定できない
  4. 「触らない」判断も設計判断 — 1年間PRが来ていないコードの移行は投資回収されない
  5. mapperは生成する — 手書きのmapperが移行の最大の不満要因。goverter / copygen などのコード生成、または簡単な自作テンプレートで解決する
  6. 移行の完了を目標にしない — Generic は永久にMVCでよい。「全部移行する」を目標にすると必ず途中で力尽きる
  7. CIで方向を強制する — 人の意識では守れない。depguard で「新方式から旧方式へのimport」を禁止する

Part 2 のまとめ

  1. DDDは1リソースで型5個 + mapper 4個。これが正確なコスト
  2. 買っているのは「変更の局所化」と「デフォルト非公開（fail-safe）」
  3. 初回は3〜4倍、変更4回目で逆転する。数字で議論する
  4. プロジェクト単位ではなく機能単位で判断する（Core / Supporting / Generic）
  5. 共存が正しい最終形。ディレクトリで物理的に分け、ADRに書き、CIで強制する
  6. 移行は「変更要求が来た機能」から。全面書き換えはしない

update処理のレビューチェックリスト

#確認することNGのサイン
1クライアントは「命令」を送っているか全フィールドを含むPUT / statusを直接送れる
2Entityにメソッドがあるかフィールドだけのstruct（貧血モデル）
3usecaseに業務判定のifがないかif文が3つ以上 / 四則演算がある
4トランザクション境界がusecaseにあるかrepositoryの中でcommit / handlerでTxを張る
5Txの中に外部通信がないかHTTP / メール / Queue publish が含まれる
6楽観ロックが効いているかversion条件なしのUPDATE / RowsAffectedを見ていない
7競合時のリトライに上限があるか無限リトライ / リトライ回数の記録がない
8「送られなかったフィールド」の扱いが明確かdb.Save(struct) で全カラム更新している
9Entityの単体テストがあるかDBを立てないと1つもテストが通らない
10Response DTOで出す項目を選んでいるかEntityやDBモデルを直接JSONにしている
11Mapperのround-tripテストがあるかカラム追加でmapperの片方だけ直せる状態
12この機能の分類（Core/Supporting/Generic）が決まっているか「なんとなくDDD」「なんとなくMVC」
