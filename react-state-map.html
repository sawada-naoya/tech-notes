状態はどこに棲み、コードはどこで動くか

React（状態→画面）と Next.js（サーバー/ブラウザの境界）を、実画面と裏側の配管で1枚に。まず全体像、次に各論。PART 1 React / PART 2 Next.js / PART 3 Virtual DOM（何が書き換わるか）/ PART 4 イベントループ（いつ動くか）。

UI = f(状態) 画面 = 状態から描かれる関数の出力。「状態がどこに住むか（React）」と「関数がどこで動くか（Next.js）」の2つを押さえれば全体が見える。
PART 1 React 基礎 — 状態はどこに棲むか

Reactとは — 「状態 → 画面」を書くライブラリ

  • UI = f(状態)。状態が変わるとコンポーネント（関数）が再実行され、画面が描き直される。
  • 宣言的: 「どう操作して変えるか」でなく「どう見えるか」を書く。手でDOM操作しない。
  • コンポーネント指向: 画面を小さな部品に分割して組み合わせる。
  • 本体は「描画」だけ。ルーティング・データ取得・フォームは別ライブラリで補う（router / React Query / React Hook Form）。だから土台として Next.js が要る。
  • 学ぶ順: ①状態を分類（7バケツ）→ ②どこに置くか → ③非同期（サーバ）と繋ぐ。これが PART 1 の流れ。

R6 非同期の基礎 — await / axios は「Reactの外」の話

配管の fetch 部分はReactの機能ではない。JS/ブラウザの非同期の仕組み。React Query はその上に「キャッシュ＆状態化」を乗せているだけ。層を分けて理解する。

🟫 JSの世界（ブラウザ / Node）

Promiseasync/awaitfetchaxios

「時間のかかる処理の結果を待つ」仕組み。ネットワーク・タイマー・ファイルなど。Reactは一切関係ない。

JSが待って得た結果を「状態」に変えてUIを描き直す。useQueryは「awaitの結果をcacheに入れて再描画する」係。

R9 さらに知っておくと一段上（React / RQ）

状態分類を掴んだ次に効く「実務で刺さる」知識。

staleTime と gcTime RQ

staleTime=「新鮮」とみなす時間。この間は再fetchしない（デフォ0＝即stale）。gcTime=誰も見なくなったcacheを捨てるまでの時間。この2つで「いつ取り直すか」が決まる。

isPending / isError は必須 RQ

データだけ使って loading/error を書かないのは初心者の典型。if(isPending) スケルトン、if(isError) リトライUI。3状態を毎回ハンドリング。

race condition は解決済み RQ

「古いリクエストが後から返って新しい結果を上書き」問題。自前useEffect+fetchだと自分で防ぐ羽目。React QueryはqueryKey単位で管理し自動で無効化する。

queryKeyに依存を全部入れる RQ

['reservations', status, page]。絞り込みに使う値をkeyに入れ忘れると、条件を変えても古いcacheを表示してバグる。keyが変われば別データ扱い＆自動再取得。

optimistic update RQ

保存を待たずに先にUIを更新し、失敗したら戻す。体感速度が上がる。いいね/トグル系で有効。

派生stateを持たず key でリセット React

propsで初期化するuseStateは同期バグの温床。「別データになったら作り直す」は <Comp key={id} /> でReactに再マウントさせるのが定石。

Contextの再描画 React

Contextは値が変わると配下を全部再描画する。頻繁に変わる値を大きなContextに入れない。分割するか Zustand/Jotai を使う。

R10 キャッシュの箱 — 中身とkeyはいつ変わり、いつ消え、いつ使われるか

invalidateQueries(key)残る変わらない（staleの印だけ付く）消えない → 裏で更新
refetchQueries(key)残る取り直して上書き消えない → 更新
resetQueries(key)残る（初期化）undefinedに戻る＋購読中なら再取得一瞬スケルトン
removeQueries(key)削除消滅空になる（ログアウト時など）
gcTime経過（observers=0のまま）自動削除消滅次回mountでスケルトン
リロード / タブを閉じるcache丸ごと消滅消滅全部やり直し（persist設定時を除く）
key変更（条件切替）別の箱を見る元の箱の中身はそのまま生存新keyがmissならスケルトン

一番混同するのは invalidate と remove。 invalidate＝「古い印を付けるだけ・中身は見せ続ける」＝mutation後の定番。remove＝「箱を捨てる」＝画面が一瞬空になるのでログアウトなど破棄したい時だけ。「更新したいから remove」は誤り。

⑤ 箱の中身が「使われる」3つの瞬間

同keyの別コンポーネントがmount→fresh ならそのまま返して通信0 / stale ならまず古い中身を返し裏でrefetch
条件を元に戻した / 前の画面に戻った→gc前なら箱が生きている＝即表示（体感が速い正体）
hydration（PART 2 の Pattern 2）→サーバーで prefetchQuery して詰めた箱を初期値に →初回fetchなしで即表示

まとめ: 箱ができるのはmount時のmiss、中身が書かれるのはfetch成功 / setQueryData、中身が使われるのは同keyのmount・戻り・hydration、箱が消えるのはgcTime経過 / removeQueries / リロード。invalidate は中身を消さず印を付けるだけ — この1点を押さえると React Query の挙動はほぼ説明できる。

R12 Mutationの箱 — 失敗した時、エラーはどこに入るのか

✅ 正しいmutation自体の箱ができ、その中に data / error が入る→MutationCache に status / data / error / variables / failureCount を持つエントリが作られる
✅ 正しい成功なら invalidate、失敗ならエラーを返す→onSuccess / onError / onSettled のコールバックで分岐する

② 発火順序 — 成功ルートと失敗ルート

✅ 成功ルート（onSuccess）
  1. mutate(値) を呼ぶ → mutationの箱が作られ status: 'pending'
  2. onMutate … 送信前。optimistic updateとロールバック用の退避はここ（戻り値が context になる）
  3. mutationFn 実行 → PUT/POST → 2xx
  4. 箱に data = レスポンスbody が入り status: 'success'
  5. onSuccess(data, variables, context) … ここで invalidateQueries・モーダルを閉じる・成功トースト
  6. onSettled … 成功/失敗どちらでも最後に走る（後片付け・共通のinvalidate）
❌ 失敗ルート（onError）

  2. 箱に error = 投げられた例外 が入り status: 'error'。data は入らない

  4. onSettled … 共通処理
  5. invalidateQueries は呼ばない（サーバーは変わっていないので取り直す必要がない）
  6. UIは const { error, isError } = useMutation() で箱の中身を読んで表示

④ 失敗系で踏みやすい罠 3つ

fetch は 4xx/5xx で throw しない 最頻

fetch は 422 が返っても reject しない（R6の表の通り）。すると mutationFn が正常終了し onSuccess が走ってしまう——「エラーなのに成功トーストが出て、invalidateまで走る」最悪の挙動。
対策: if (!res.ok) throw await res.json() を必ず書く。axios（orval生成）なら自動でrejectするのでこの罠はない。

mutateAsync の未処理rejection 落ちる

mutate() はthrowしない（エラーは箱に入るだけ）。一方 mutateAsync() はPromiseがrejectするので、await するなら try/catch が必須。忘れると unhandled rejection になる。
使い分け: 基本は mutate。「保存の完了を待って次の処理をしたい」時だけ mutateAsync + try/catch。

optimistic update のロールバック漏れ 画面が嘘をつく

R11⑨の続き。onMutate で setQueryData して先に画面を変えた場合、onErrorで退避した値に戻さないと嘘の表示が残る。
型: onMutateで cancelQueries → 現在値を退避して return → onErrorで setQueryData(prev) → onSettledで invalidate（成功でも失敗でも最後にサーバーと同期を取る）。

PART 2 Next.js 基礎 — コードはどこで動くか

Next.jsとは — Reactに「サーバー」を足したフレームワーク

  • Reactは描画だけ。実アプリに要るルーティング・サーバー実行・ビルド最適化を足したのが Next.js。
  • 核心は「どこで動くか」: Server Component（サーバーで1回）と Client Component（ブラウザで動く）を選べる。
  • 提供物: ファイルベースrouting（app/）/ Server Components / Route Handler（APIエンドポイント=軽量BFF）/ SSR・SSG / middleware / 画像最適化。

N6 認証 — NextAuth は token をどう受け取り、どこで判定するか

「tokenを受け取って判定」が具体的に誰の仕事か。NextAuth（session管理）と Goバックエンド（tokenの真偽判定）で役割が分かれているのが要点。

PART 3 画面はどう書き換わるか — Virtual DOM と差分

結論 — Virtual DOMは「速くする道具」ではなく「宣言的に書ける道具」

  • Reactは実DOMを直接いじらない。まずただのJSオブジェクトの木を作り、前回の木と比べ、違った所だけ実DOMへ書き込む。
  • 目的は速度そのものではない。「UI = f(状態)」を毎回まるごと書き直す書き方でも実用速度が出るようにすること。手書きDOM操作（命令的）だと「今の画面がどうなっているか」を人間が全部覚える必要があり、状態が増えると破綻する。
  • 更新は必ず2段階。Render phase（関数を再実行して差分を計算・画面は1pxも変わらない）→ Commit phase（差分だけ実DOMへ書き込む・同期・中断不可）。
  • 頭の中の持ち方: 状態を変える＝新しい設計図を出すだけ。何をどう書き換えるかはReactが決める。自分は差分を考えない。ただし key だけは例外で、Reactが推測できない唯一の情報なので自分が正しく渡す。

V3 差分の取り方 — Reactが使う3つのルールだけ

2つの木の完全な差分は理論上 O(n³) で使い物にならない。Reactは2つの仮定を置いて O(n) に落としている。①型が違う要素は違う木を作る ②開発者がkeyで「どれとどれが同じか」を教える。この2つが崩れると事故る。

ルール1: typeが違う 捨てる

同じ位置で div→span、<UserCard>→<AdminCard> になったら、そのDOMノードも子孫も丸ごと破棄して作り直す。

巻き添え: 子孫のstate・入力中の値・scroll位置が全部消える

ルール2: typeが同じ 使い回す

DOMノードはそのまま。propsを比べて変わった属性だけ書き換える。className だけ変わったなら className だけ。

stateは維持される。DOMノードの同一性も保たれる

ルール3: 子リスト keyで対応

兄弟の配列は key で新旧をマッチング。keyが無ければ「位置（index）」で比較する。

keyが正しければ「移動」で済む／間違えば「全書き換え」になる

大事な前提: Reactは「同じ位置にあるか」で同一性を判断する。DOMツリー上の位置＋type＋key の3点セット。だから {cond ? <Input/> : <Input/>} のように書き方を変えただけで位置が変わると、見た目は同じでもstateがリセットされる。逆にわざと key を変えてstateを捨てるのは正しいテクニック（<Form key={userId} />）。

V4 keyの実験 — 予約一覧の先頭に1件挿入する

状況: 予約3件を表示中。2行目「佐藤」を展開している（#4 ローカルUI の open=true がその行に住んでいる）。ここに新規予約「田中」が先頭に入ってきた。key の付け方だけで結果が変わる。

線の形が答え: index key は線が水平＝「0番目は0番目と比べる」ので、中身が別人でも同じDOMノードを使い回し、state だけ元の位置に取り残される。id key は線が斜め＝「r-102 は下に1つ動いただけ」と分かるので、ノードもstateも一緒に移動する。

「表示が壊れる」の実害index key で崩れるのは見た目だけではない。行内の入力欄に打ちかけの文字・チェックボックスの選択・フォーカス位置が全部1行ズレる。しかもエラーにならず静かにズレるので、レビューでもテストでも見つけにくい。

indexが許されるケース①リストが並び替え・挿入・削除されない ②各行がstateを持たない ③フィルタもされない。この3つ全部を満たす時だけ。1つでも将来崩れるなら最初からidにする。

PART 4 JavaScript イベントループ — いつコードが動くか

結論 — スレッドは1本。「並行」は全部キューの順番の話

  • JSを実行するスレッドは1本だけ。同時には1つの関数しか動かない。描画（paint）も同じ1本のスレッドを使う。
  • だから「非同期」は並列実行ではない。いま実行を中断して、続きをキューに預け、後で取り出すだけ。await はスレッドを止めない。
  • キューは2種類。Microtask（Promise / await の続き）は空になるまで全部消化する。Macrotask（setTimeout / click）は1周に1つだけ取り出す。
  • paint が入れるのは macrotask と macrotask の間だけ。長い同期処理・microtask の連鎖は、この隙間を潰す＝画面が固まる。
  • 頭の中の持ち方: 「この行はどのターンで動くか」を 同期 / micro / macro の3つにラベル付けするだけ。順番はそのラベルで決まる。

E1 登場人物 — 箱は5つだけ

「非同期処理がどこかへ消えて戻ってくる」感覚を無くす。消えていない。ブラウザ側（別スレッド）に預けられ、終わったらキューに積み直されているだけ。

E2 1周（tick）の順番 — これだけ覚えれば全部説明できる

ループはこの4ステップの繰り返し。ステップ2と3の「全部 / 1つ」の非対称が、実行順のほぼ全てを決めている。

1
Call Stack が空になるまで同期コードを実行
macrotask を1つ取り出して実行する。その中の同期コードは最後まで一気に走る。途中で割り込めない。
2
Microtask Queue を「空になるまで」全部実行
1つではなく全部。実行中に新しく積まれた microtask も同じターンで消化する。Promise.then の中でさらに then を積めば、それも今回中に走る。
3
必要なら描画（rAF → style → layout → paint）
毎ターン必ず走るわけではない。ディスプレイのリフレッシュに合わせて（通常60fps＝約16.7ms間隔）ブラウザが判断して挟む。2 が終わらないと絶対に来ない。
4
Macrotask Queue から「1つだけ」取り出して 1 に戻る
キューに10件溜まっていても、1ターンで処理するのは1件。だから macrotask 同士の間には必ず「描画と他のイベント処理のチャンス」がある。

1 tick の中身 — 「全部」と「1つ」の非対称

重い処理を分割する時に setTimeout(fn, 0) を使い Promise.resolve().then(fn) を使わない理由がこれ。後者は②の中で連鎖するので、③に一度も到達しない。

「必要なら」の中身ステップ3は毎tick走らない。ブラウザはディスプレイのリフレッシュ間隔（通常60fps）に合わせて挟むかを決める。だから setTimeout(fn, 0) を連打しても描画は60回/秒が上限で、それ以上細かく刻んでも見た目は変わらず、分割のオーバーヘッドだけ増える。
Node.jsは少し違うNode には process.nextTick（microtaskより更に先）と phase 分け（timers / poll / check）がある。setImmediate はブラウザに無い。ここではブラウザの話に限定している。

E3 実行順を追う — コードとキューを並べる

「読んだ順」ではなく「どのキューに入るか」で並ぶ。1行ずつラベルを付けて読む練習。

console.log('1') // 同期 setTimeout(() => console.log('2'), 0) // macrotask へ予約 Promise.resolve().then(() => console.log('3')) // microtask へ予約 queueMicrotask(() => console.log('4')) // microtask へ予約 console.log('5') // 同期

setTimeout(…, 0) が最後になるのは「0msが遅いから」ではなく、microtaskを全部消化してからでないと次のmacrotaskに進めないルールだから。

読み取るポイント2つ: ①async関数の中身は await に当たるまで同期実行される（Eが先）。②microtask消化中に積まれたDも、同じターンで、しかもFの後ろに並ぶ。

E4 await の正体 — 「待つ」ではなく「続きを予約して帰る」

R6 の「await / axios は Reactの外」を、イベントループの言葉で言い直す。await はスレッドを1ミリ秒も止めていない。

誤ったイメージ（同期的な「待ち」）

実行 await で止まっている（他は何もできない） 続き

これは間違い。もしこうなら、通信中はクリックもアニメーションも一切効かなくなる。

実際（関数を中断してキューに預ける）

実行 他のtask（click / paint / 別の処理） micro: 続き

await の瞬間に関数から抜けて呼び出し元へ戻る。Promiseが解決したら残りの行がmicrotaskとして再開される。その間スレッドは他の仕事をしている。

async function save() { console.log('①') // 同期。呼んだ瞬間ここまで一気に走る const res = await axios.put(…) // ← ここで関数を中断して呼び出し元に return console.log('②') // 通信完了後、microtask として再開 return res.data } save() // ①だけ出て、すぐ次の行へ進む console.log('③') // ②より先に出る // 出力: ① → ③ → ②
React Queryとの接続queryFn が返すのはPromise。Reactはそれを待たない。「まだ無い」で1回描画し、解決したら setState 相当が走ってもう1回描画する。isLoading の存在理由がこれ。
直列awaitの罠for (const id of ids) { await fetchOne(id) } は1件ずつ順番に待つので合計時間になる。await Promise.all(ids.map(fetchOne)) なら同時に投げて最も遅い1件分で済む。並列化はここでしか起きない。

E5 なぜUIが固まるのか — paintの隙間が消える

「重い処理を書いたら固まる」の正確な理由。paint は Call Stack が空 かつ microtask が空 の時にしか入れない。この条件を満たさない時間が長いほど、画面は死ぬ。

フレーム境界で見る — 描画されなかったフレームの数がそのまま「固まった時間」

数え方: 「固まった」の体感は描画されなかったフレームの数。200msの同期処理は約12フレーム分を飛ばす。1フレーム（16.7ms）を超える同期処理は全部この×を1つ以上作っていると考えると、どこを削るべきか判断しやすい。

チャンク分割 手軽

配列を数百件ずつに割って setTimeout(…, 0) で継続。実装が軽い。ただし全体の所要時間は伸びる。

Web Worker 本命

本当に別スレッドで動かす。メインスレッドを1msも使わない。DOMは触れないので「重い計算」向け（CSVパース、集計、暗号処理）。

startTransition React

重い再レンダーを「低優先度」に落とす。入力欄の反応を優先し、リストの更新は後回しにできる。計算そのものは軽くならない点に注意。

そもそもやらない 設計

1万件のソート・集計はサーバー側でやる。仮想スクロールで描画対象を減らす。分割やWorkerより効くことが多い。

E6 React とイベントループ — バッチングと並行レンダリング

「なぜ setState を3回呼んでも再レンダーが1回なのか」「なぜ setState 直後に state を読むと古いのか」は、全部スケジューリングの話。

自動バッチング（React 18〜）

function onClick() { setCount(c => c + 1) setName('田中') setOpen(true) console.log(count) // ← 古い値！ } // 再レンダーは 3回ではなく 1回

setState はキューに積むだけで即renderしない。ハンドラを最後まで走らせてからまとめて1回render する。だから同じ関数内では count は古いまま（更新後の値が要るなら関数形 c => c + 1）。
React 18の変更点: 17まではReactのイベントハンドラ内でしか束ねなかった。18の createRoot 以降は setTimeout / Promise.then / ネイティブイベントの中でも自動で束ねる。

並行レンダリング（Concurrent）

render 一部 入力処理（割り込み） paint render 続き commit

Reactは重いrenderを複数のmacrotaskに分割して積む（内部的に MessageChannel を使う）。だからrenderの途中でブラウザがpaintと入力処理を挟める。
Render phase が「中断・破棄できる」設計になっている理由がこれ（V2）。commit だけは分割不可・同期。

useTransition 優先度を下げる

startTransition(() => setQuery(v)) で「この更新は遅れてよい」と宣言。入力欄の文字は即反映、重いリストは後から追いつく。isPending で薄く表示できる。

useDeferredValue 値を遅らせる

値そのものの「遅れて追従するコピー」を作る。R10の debounce と目的は似るが、タイマーではなくスケジューラが判断する点が違う。

flushSync バッチを破る

その場で同期的にrender+commitさせる。「DOMを更新してから即座にscroll位置を測る」など本当に必要な時だけ。多用するとバッチングの利点を全部捨てる。

useEffect は paint後 タイミング

effect内の setState はもう1周させる＝画面が一瞬ちらつく可能性がある。ちらつかせたくない測定・補正だけ useLayoutEffect。
