図解Go言語の基礎
値・ポインタ・ゼロ値・nil・出力

Goで最初につまずく3つの領域を、全部「メモリの絵」で説明する。
①値とポインタ（コピーされるのか、共有されるのか）②ゼロ値・nil・空（存在するのか、しないのか、サイズ0なのか）③fmt の出力（どこへ、どんな形で出るのか）。

主張1

Goのポインタは「難しい機能」ではなく「コピーするかしないかの選択」。C言語のようなポインタ演算はできないので、覚えることは & と * の2つだけ。

主張2

「存在するが空」と「存在しない」は別物。この区別が付くと、nil panic・JSONの null vs []・nil interfaceの罠が全部同じ原理で説明できる。

主張3

fmt の関数名は3つの軸の掛け算（出力先 × 改行 × フォーマット）。暗記対象は9個ではなく3文字の規則だけ。

00 はじめに — メモリの3つの絵

Goの入門でつまずく質問はほぼ全部、「そのとき、メモリはどうなっているか」を絵にすれば解決する。まずこの3枚を頭に入れる。以降の全章はこの3枚の変奏である。

図0-1 値・ポインタ・nil。Goの質問の9割は、この3枚のどれかを描けば答えが出る。

この本で使うサンプル型（全章共通）

フィールドが2つだけの単純な型だが、値/ポインタ・ゼロ値/nil・出力形式の全ての論点を説明できる。実務の型はフィールドが20個あるが、原理は同じ。

00.5 全体地図 — 3つの問いに分解する

Goの「よく分からない」は、次の3つの問いに分類できる。どの問いなのかを言い当てられれば、答えは本書のどこかにある。

図0-2 3つの問い。詰まったら「これはどの問いか？」を先に決める。

Part 1

値とポインタ

Goには「参照型」という概念がない。代入・関数渡しは常に値のコピーである。ポインタを使うと「コピーされるのが住所になる」だけ。この一貫したルールを理解すると、slice/map/chan が「参照っぽく」振る舞う理由も、値レシーバで変更が反映されない理由も、同じ原理で説明できる。

01 値（struct）— 実体そのもの

結論。u := User{...} の u は実体そのもの。箱の中に中身が直接入っている。だから代入も関数渡しも「中身の複製」になる。

図1-1 値の代入はコピー。ただし「浅いコピー」なので、内部のポインタ・slice・mapは共有される。

① よくある事故 — 「浅いコピー」を「完全なコピー」と思い込む

⑩ レビュー観点

  • slice / map / ポインタを持つ struct を「コピーして変更」しているコード — 元も変わる
  • Entity（Part 3のDDD参照）を値でコピーして返す関数 — 内部のsliceが共有されていないか
  • append をコピー後の slice に対して行っている — cap に余裕があると元の配列を書き換え、余裕がないと新配列になる（挙動が不定に見える）。ch6で詳述

02 ポインタとアドレス — & と *

Goのポインタで覚えることは2つの演算子だけ。& = 住所を取る、* = 住所から実体を取る。C言語のようなポインタ演算（p+1 で次の要素へ）はできないので、危険な使い方が言語レベルで封じられている。

図2-1 & と * は逆向きの操作。* が「型の一部」でもあることが混乱の原因。

④ 演算子まとめ

書き方意味例結果の型
&uu のアドレスを取るp := &u*User
*p（式）p の指す先の値を取るv := *pUser
*User（型）User へのポインタ型var p *User—
&User{...}生成と同時にアドレスを取る（複合リテラル）p := &User{ID: 1}*User
new(User)ゼロ値のUserを作り、そのアドレスを返すp := new(User)*User

&User{} と new(User) の使い分け: 実務ではほぼ常に &User{...} を使う（初期値を同時に書けるため）。new が便利なのは new(int) のようにリテラルが書けない型のポインタが欲しいときだけ。

② よくある落とし穴 — アドレスが取れないもの

なぜ map の要素はアドレスが取れないのか: mapは内部でリハッシュ（再配置）が起きるため、要素の住所が動く。動く住所を渡すと危険なので、言語仕様で禁止されている。ch6でこの制約の実務的な影響を扱う。

03 フィールドアクセスと自動デリファレンス

結論。p.ID と書けば、Goが自動で (*p).ID に変換する。だから実務でポインタを扱っていても * を書く機会はほとんどない。これがGoのポインタが「他言語より簡単」に感じる最大の理由。

図3-1 フィールド単位のアドレス。実務での主な用途は「未設定を表現する」ためのポインタフィールド。

⑤ 実務で最も使うポインタの用途 — 「未設定」の表現

⑨ 過剰になる境界 — ポインタフィールドを使いすぎる害

  • 全フィールドをポインタにする → 使う側が全部 nil チェックすることになる。コードが2倍になり、nil panicのリスクも増える
  • スライスをポインタにする（*[]string） → ほぼ常に不要。slice自体が nil になれるので、ポインタで包む意味がない
  • 判定基準: 「ゼロ値が有効な値として意味を持つか？」がYesのときだけポインタにする。「0円の割引」と「割引なし」を区別する必要があるならポインタ、なければ int で十分

04 値レシーバ vs ポインタレシーバ

実務で最も事故が多いのがここ。値レシーバのメソッドで状態を変更しても、呼び出し元には反映されない。しかもコンパイルは通り、エラーも出ない。静かにバグる。

図4-1 値レシーバはコピーに対する操作。「変更したのに反映されない」の原因はほぼこれ。

結論。迷ったら値。ポインタは「理由があるときだけ」使う。「ポインタの方が速いから」は多くの場合誤り（後述）。

図5-1 判断フロー。Q1〜Q4がNoなら値を使う。「速いから」は計測してから言う。

⑧ トレードオフ — ポインタのコスト

コスト1: nilチェックの伝染

ポインタを返す関数は、呼び出し側に nil チェックを強制する。これが10箇所に増えると、コードの半分がnilチェックになる。

コスト2: 意図が不明になる

func Process(u *User) を見た人は「この関数はuを変更するのか？」と考える必要がある。値で受けていれば「変更しない」ことが型で保証される。

コスト3: 並行安全性が失われる

ポインタを複数のgoroutineに渡すと、同じ実体を共有する。値ならコピーなので競合しない。go test -race で検出される事故の多くがこれ。

コスト4: GC負荷

ポインタはエスケープ解析でヒープに逃げやすい。スタック割り当てなら実質ゼロコストだが、ヒープならGCの対象になる。

06 slice / map / chan の「参照的」な性質

結論。slice / map / chan は「内部にポインタを持つ構造体」。だから値としてコピーされるのに、中身は共有される。「参照型」ではなく「ポインタを含む値型」と理解するのが正確で、そう理解するとappendの謎の挙動も説明できる。

図6-1 sliceの正体とappendの挙動。「capの状態で挙動が変わる」ことがGoで最も混乱を招く仕様。

⑩ レビュー観点（Part 1 まとめ）

  • 状態を変えるメソッドが値レシーバになっていないか（最頻出の事故）
  • 1つの型でレシーバが混在していないか（Goの慣習違反）
  • sync.Mutex を含む型を値でコピーしていないか（go vet が検出してくれる）
  • append の戻り値を捨てていないか
  • slice を関数に渡して「中身を書き換える」設計になっていないか（意図が伝わらない）
  • ポインタフィールドが多すぎないか（nilチェック地獄）
  • go vet と go test -race をCIに入れているか — Part 1の事故の半分は機械的に検出できる

Part 2

ゼロ値・nil・空

結論を先に: 「存在するが空」と「存在しない」と「サイズ0の型」は全部別物。この3つを区別できると、nil panic・JSONの null vs []・err != nil なのに中身がない罠が、全部同じ原理で説明できる。Goの「ゼロ値が使える」という設計は強力だが、「ゼロ値と未設定を区別できない」という代償を伴う。

07 ゼロ値 struct — nilにならない

結論。var u User は nil にならない。実体が存在し、各フィールドが型のゼロ値で埋まっている。これがGoの「zero value is useful」という設計思想で、他言語（Javaのnull）との最大の違い。

図7-1 型ごとのゼロ値。左（nilにならない群）と右（nilになる群）を分けて覚える。

⑤ ゼロ値を活かす設計（Goらしい書き方）

⑧ トレードオフ — 「ゼロ値で使える」vs「コンストラクタ必須」

ゼロ値で使える設計

向く型: バッファ・カウンタ・Mutex・オプション構造体。「空の状態」に意味がある型。使う側が楽。

コンストラクタ必須の設計

向く型: 不変条件を持つ型（Money・StayPeriod・Email）。「ゼロ値が不正な状態」である型。Money{} が通ってしまうと不変条件が破れる。

判定

「その型のゼロ値は、業務的に正しい状態か？」 Yesならゼロ値で使える設計、Noならコンストラクタ必須（+ フィールドをunexportedにして外から作れなくする）。

Goの弱点として認識すべき点

Goには「コンストラクタを強制する」言語機能がない。同じパッケージ内なら Money{} と書けてしまう。パッケージ境界とレビューで守るしかない。

10 スライス: nil / 空 / 値あり

結論。コード上ではnilスライスと空スライスを区別する必要はほぼない（len / range / append が全部安全に動く）。唯一の例外がJSONシリアライズで、ここは実務で必ず事故る。

⑩ レビュー観点

  • 配列フィールドに omitempty が付いていないか
  • 内部処理で if s != nil という不要なチェックをしていないか（len(s) == 0 で足りる）

出力とフォーマット

fmt の関数は9個あるように見えるが、実際は3つの軸（出力先 × 改行 × フォーマット）の掛け算にすぎない。規則を覚えれば暗記は不要。さらに「デバッグ出力」と「本番のログ」は別の道具である、という区別を付ける。

結論。関数名は「接頭辞（出力先）+ Print + 接尾辞（形式）」という機械的な組み合わせ。実務で使うのは Printf / Sprintf / Println / Fprintf の4つ。

図13-1 fmt の直交マトリクス。9関数を暗記するのではなく、3文字の規則（S / F / ln / f）を覚える。

14 フォーマット指定子と %v/%+v/%#v

結論。デバッグでは %+v を使う（フィールド名が付く）。%v は値だけ、%#v はGoの構文そのまま。この3つの違いを実際の出力で見る。

① 実務で必ず困ること — ポインタの中身が見えない

図16-1 fmt と slog の役割分担。「fmtの出力は人が読む、slogの出力は機械が読む」。

Part 3 のまとめ

  1. fmt の関数名は3軸の掛け算。覚えるのは Printf / Sprintf / Println / Errorf の4つ
  2. デバッグは %+v、ネストは json.MarshalIndent、テストの期待値は %#v
  3. 外部入力を含むエラーメッセージは %q（空文字が見える）
  4. エラーのラップは %w。%v にすると型情報が失われる
  5. 組み込み println は使わない。go vet と forbidigo で機械的に防ぐ
  6. 本番のログは slog（構造化）。値は文に埋めず、フィールドに置く
