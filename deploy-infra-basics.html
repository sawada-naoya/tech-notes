ローカルから本番DBまで、何がどこに乗っているのか

目的: 「コードがどう運ばれるか」と「リクエストがどう届くか」の2つを、図で頭に入れること。
前提スタック: AWS + Docker + GitHub Actions + RDS。ECS / EC2 / Kubernetes の違いは6章と6B章で、サービス規模ごとの構成の違い（QPS の数字つき）は「規模」章で扱います。GCP・Azure でも登場人物の名前が変わるだけで構造は同じです。

最初に掴む1

流れは2種類しかない。①コードが運ばれる流れ（デプロイ）②リクエストが往復する流れ（実行時）。この2つを混ぜないこと。

最初に掴む2

環境の違いは「中身」ではなく「外側」。同じイメージを配り、環境変数と権限だけを変える。これが Docker 時代の原則。

最初に掴む3

認証は「誰が何に」で3種類。人間→クラウド / CI→クラウド / アプリ→DB。全部を一時的な資格情報にするのが今の正解。

MAP 全体地図 — 2つの流れを分けて見る

インフラが分かりにくい最大の理由は、「デプロイの流れ」と「リクエストの流れ」を1枚の図に描いてしまうから。この2つは登場人物も方向も別物なので、最初から分けて覚える。

図0-1 3つの流れ。①はデプロイ時だけ動く一方通行、②は常時動く往復、③は人間が調査する時だけの経路。この3つを分けて考えるのが理解の第一歩。

最初に区別すべき3つの言葉

言葉正体よくある誤解
GitHubコードの置き場所（+ レビュー・CI の実行場所）「GitHub にデプロイする」は誤り。GitHub はアプリが動く場所ではない
レジストリ（ECR / Docker Hub）ビルド済みイメージの置き場所GitHub と混同されがち。コードではなく「実行可能な塊」が入る

1文でまとめると: コードは GitHub に、イメージはレジストリに、動いているものは実行環境にある。

01 4つの環境の違い

local / CI / staging / production。「何が同じで、何が違うのか」を明示できるかが重要。違いを減らせば減らすほど「本番だけ動かない」が減る。

🍳 料理の例え。 local = 自宅のキッチンで試作（材料は代用品でよい）。CI = 衛生検査（毎回まっさらな検査室で、レシピ通りに作れるか確認）。staging = 本番と同じ厨房で、本番と同じ器具を使うリハーサル（客には出さない）。production = 実際に客に出す営業。
staging の価値は「本番と同じ構成であること」。構成が違えば、リハーサルの意味がない。

図1-1 4環境の比較。「イメージは同じ、設定は違う」が原則。逆に「staging だけ別ビルド」にすると staging の意味が消える。

「ローカルでは動くのに本番で動かない」の原因トップ5

  1. 環境変数の設定漏れ — ローカルの .env にあるキーが本番の Secrets に無い。起動時に必須環境変数を検証して即死させるのが対策
  2. ネットワークで到達できない — ローカルは全部同じPC内なので繋がるが、本番はセキュリティグループで拒否されている（7章）
  3. ファイルシステムへの書き込み — ローカルでは書けたが、本番のコンテナは読み取り専用 / 再起動で消える
  4. データ量の違い — ローカルは100件、本番は1000万件。インデックスが無いクエリが本番だけタイムアウトする
  5. 複数台であることの前提漏れ — ローカルは1プロセスなので「メモリ上のキャッシュ」「ローカルファイルにセッション」が動くが、本番は N 台なので壊れる

04 GitHub と CI/CD

GitHub は「コードの置き場所」+「使い捨てのビルドマシンを貸してくれる場所」。この2つの役割を分けて理解する。GitHub 上でアプリが動いているわけではない。

図4-1 CI/CD の全体。「CI = 確認」「CD = 配布」と分けて覚える。DBマイグレーションの実行場所は最初に必ず詰まるポイント。

GitHub Actions が AWS に認証する仕組み（OIDC）

ここが「CI がどうやって本番環境を触れるのか」という核心。アクセスキーをGitHubに保存する方式は古く、今は OIDC が標準。

図4-2 OIDC の仕組み。「保存された鍵」を「その場で発行される短命な鍵」に置き換えるのが現代の認証設計の共通パターン。9章でも同じ考え方が出てくる。

実際の workflow（要点だけ）

05 Docker で何が変わるのか

Docker の価値は「環境差をなくす」ことだと説明されるが、より正確には「環境差を、コードの外側の一箇所（環境変数と権限）に押し込める」こと。

📦 引っ越しの例え。 Docker が無い時代のデプロイは「引っ越し先で家具を組み立て直す」方式だった（サーバに Go をインストールし、ライブラリを入れ、ビルドする）。組み立て手順書が古かったり、現地で部品が足りなかったりして失敗する。
Docker は「部屋ごと持っていく」方式。中身を組み立てた状態のまま運ぶので、現地で組み立てミスが起きない。違うのはコンセントの形（環境変数）だけ。

図5-1 Build once, deploy many。「イメージは不変、設定は外から」が守れているかが、Docker を正しく使えているかの判定基準。

Docker を使った時の「ローカル vs 本番」の差分

項目local（compose）本番（ECS など）なぜ違うのか
イメージの取得元その場で buildECR から pull本番でビルドするとビルド環境が必要になり、時間もかかる

ローリング更新 — 「無停止でデプロイする」の中身

図6-2 ローリング更新。「無停止デプロイ」は「新旧が共存する時間を許容する」ことで実現している。この事実がマイグレーション設計を縛る。

6B EC2 と ECS の違い — そもそも同じ階層の選択肢ではない

結論を先に。「EC2 と ECS のどちらを使うか」という問いは、そもそも設定が間違っている。EC2 は「サーバーそのもの」、ECS は「コンテナをどこにどう置くかを決める管理役」で、レイヤが違う。ECS を選んでも、その下でコンテナが動く場所として EC2 か Fargate を選ぶことになる。

🚚 運送会社の例え。 EC2 = トラック1台を借りること。ECS = 配車センター（何台必要か、どの荷物をどの車に載せるか、故障したら代車を出すかを決める）。
配車センターだけでは荷物は運べないので、必ず車が必要。その車を「自分で買って停めておく（EC2）」か「必要な時だけ呼ぶ（Fargate）」かが本当の選択。
だから正しい比較は 「EC2 vs ECS」ではなく「EC2 vs Fargate」、そして 「ECS vs Kubernetes」。

図6B-1 責任分界点。①→②で「プロセスの世話」が消え、②→③で「サーバの世話」が消える。減るのは仕事、増えるのは単価。

コストと起動時間 — 「EC2 の方が安い」が成立する条件

単価だけを比べれば EC2 が安い。しかし課金の単位が違う（EC2 = 起動している時間 / Fargate = タスクが動いている時間）ため、使用率（bin-packing 率）が損益分岐点になる。

図6B-2 コストと反応速度。Fargate の高い単価は「余剰を持たない」ことで相殺される。EC2 が有利になるのは高使用率・Spot・GPU に限られる。

選び方 — 迷ったら順に判定する

  1. GPU が必要 / Spot 前提の大量バッチ / 特殊なカーネル機能が必要 → ECS on EC2（または EKS）。ここだけは Fargate では代替できない。
  2. 常時 100 タスク以上を動かし、コスト最適化が仕事として成立する規模 → ECS on EC2 ＋ Savings Plan / Spot。専任の人がいる前提。
  3. 上の2つに当てはまらない → ECS on Fargate。これが 9 割のケース。
  4. リクエストが疎ら（1日数百回・夜間ゼロ） → Lambda の方が安く速い。常時稼働なら逆転する。

なお EC2 に直接 docker run は、本番の選択肢としては勧めない。「自動復旧しない」「無停止デプロイが自作になる」という2点が、節約できる金額に対して割に合わない。検証・学習・使い捨て環境では最良の選択。

誤解しやすい点（正面から）

  • 「ECS は AWS 独自だからロックインが怖い」 — ロックインの実体は ECS ではなく、RDS・SQS・IAM・ALB。ECS 部分は Dockerfile が残るので移行コストは小さい。ここを心配して Kubernetes を選ぶのは、コストの見積もりを間違えている。
  • 「Fargate は中に入れないから困る」 — ECS Exec で入れる（13章）。本当に困るのは「入って直す」運用そのもの。コンテナは直さず作り直す。
  • 「EC2 なら安いから最初は EC2」 — 月 $10〜30 の差のために、OS パッチと ASG 設計とデプロイ自作を引き受けることになる。時給換算すれば1ヶ月で赤字。

Go 同じ Go API を、3つの実行基盤に載せ比べる

お題を固定する。「HTTP リクエストを受けて DB に CRUD するだけの Go API」を1つ用意し、コードは一切変えずに実行基盤だけを EC2 / ECS on EC2 / ECS + Fargate に差し替える。何が変わって、何が変わらないのかを確定させるのがこの章の目的。
6B 章では「責任分界点とコスト」を見た。ここでは「負荷が増えた時に、自分が何を増やす操作をするのか」という運用の視点で見る。

🍱 弁当屋の例え。 EC2 = 厨房（コンロとスペースを提供する）。Task = 調理担当者1人（実際に弁当を作る）。ALB = 注文を担当者に割り振る店長。
厨房を3つに増やしても、担当者が1人なら作れる弁当の数は増えない。逆に担当者を3人にすれば作れる数は3倍になるが、置く場所（厨房）が必要になる。
Fargate = 厨房を借りずに「担当者を1人追加」と言うだけで済むサービス。厨房の手配は業者がやる。

最初に潰しておく誤解

  • 「EC2 を増やせば速くなる」 — ECS では成り立たない。EC2 は置き場所で、処理するのは Task。
  • 「Task = Go サーバー」 — 厳密には違う。Task はコンテナの集まりを起動する単位で、1 Task に複数コンテナ（sidecar）も入る。ただし1 Task = 1 Container = 1 Go API という素直な構成なら、実務上「Task 数 ≒ Go API サーバー数」と考えて差し支えない。この章はその前提で進める。
  • 「CPU 60% を超えたら Task が1個増える」 — Target Tracking はそういう仕掛けではない（後述の図G-6）。

★ 最重要図 — 「EC2 を増やす」と「Task を増やす」は別の操作

この章で1枚だけ覚えるならこの図。EC2 は計算機（容れ物）、Task はアプリの実行単位（中身）。増やす対象を間違えると、金は増えるのに処理能力が増えない。

7. 選択基準 — 「常に Fargate が正解」ではない

ECS ＋ Fargate が向いているケース

  • 一般的な Web API（今回のお題そのもの）
  • マイクロサービス構成で、サービスごとに独立してスケールさせたい
  • EC2 / OS の管理を減らしたい
  • Task 単位で細かくスケールしたい
  • 小〜中規模チーム（インフラ専任がいない）
  • インフラ運用よりアプリ開発に人手を使いたい

ECS on EC2 が向いているケース

  • 大規模かつ常時高負荷（使用率を高く保てる）
  • EC2 の利用率を上げてコストを最適化したい
  • GPU・特殊インスタンスを細かく制御したい
  • ホストレベルの制御が必要（DAEMON 型の常駐エージェント・特定カーネル機能）
  • Reserved Instances / Savings Plans / Spot を含めて基盤を最適化したい
  • ローカルディスクへの大量 I/O が必要

EC2 直接配置が向いているケース

  • レガシーアプリでコンテナ化が難しい
  • 特殊な常駐プロセス・ライセンスがホストに紐づく
  • OS やホスト構成への強い依存がある
  • 単純な小規模構成で、オーケストレーションが不要
  • 検証環境・使い捨て環境（速く作って捨てる）

判断の順序（一般的な新規 Web API）

  1. コンテナ化できるなら、まず ECS ＋ Fargate を有力候補にする
  2. コスト・特殊要件・規模の3つで実際に問題が出てから ECS on EC2 を検討する
  3. コンテナ化できない事情があるなら EC2 直配置

重要なのは、この3つは後から移れるということ。Dockerfile とステートレス設計を維持していれば、移行は「起動方法の差し替え」で済む。だから最初の選択に時間をかけすぎる必要はない。

率直な指摘

  • 「ECS を学ぶ」より先に「Task と EC2 の違い」を掴む方が効く。用語（Cluster / Service / Task Definition）の暗記は、図G-1 が理解できていれば後から自然に入る。逆は入らない。
  • 構成選びに1週間かける価値はない。3構成の移行コストは Dockerfile があれば小さい。その1週間は「1 Task が何 QPS 捌けるか」の実測に使った方がリターンが大きい。台数・コスト・スケール設定の全部がその数字から決まる。
  • Go の CPU 使用率だけを見てオートスケールを組むのは危ない。goroutine は DB 待ちで CPU を使わないため、遅くなっているのに CPU が上がらずスケールしないという状態が起きる。Web API では ALBRequestCountPerTarget を第一候補にする。
  • Fargate を選んだ理由が「新しいから」なら、選定になっていない。理由は「管理する数字を1つに減らせるから」であるべき。この言い方ができないと、コストを詰める段階で判断を誤る。

07 ブラウザ → DB の全経路

この章が本書の中心。ユーザーがボタンを押してから、DBのデータが返ってくるまでに何を通るのか。「なぜ踏み台が必要になるのか」もこの図から自然に出てくる。

🏢 オフィスビルの例え。 public subnet = 1階のロビー（誰でも入れる）。private subnet = 上層階の執務室（ロビーからしか行けない・外の道路から直接入る扉が無い）。ALB = 受付。セキュリティグループ = 各扉のカードリーダー（「誰からの通信を許すか」の設定）。
DBは最上階の金庫室。外から直接行く道が存在しないので、開発者が中を見たい時は「一度ロビーから入る」必要がある。これが踏み台（8章）。

疑問答え
TLS（https）はどこで終わるのか？通常は CDN または ALB で終端する。そこから先（ALB → コンテナ、コンテナ → RDS）は VPC 内なので http でも成立する。ただし RDS への接続は TLS を有効にするのが望ましい
フロントエンド（React 等）はどこで動くのか？ユーザーのブラウザ。S3/CDN から配られた JS がブラウザ上で実行される。サーバ側では動いていない（SSR を使う場合はサーバでも動く）

アプリから外部API（Stripe 等）はどう出るのか？NAT Gateway 経由。private subnet から「出る」のは許されている（入るのが不可）。この非対称性が肝
ECR からイメージを pull するのも外向き通信？そう。だから NAT Gateway か VPC エンドポイントが必要。これが無いとタスクが起動できない（初期構築でよく詰まる）
SG と「サブネット」はどう違うのか？サブネットは「住所（経路があるか）」、SG は「扉の鍵（誰の通信を許すか）」。両方通らないと通信できない

率直な指摘 — 規模の議論で最も多い失敗

  • 実測せずに構成を決める。「たぶん重いから」でインスタンスを2段上げるのは、根拠のない出費。ピーク QPS と 1req の CPU 時間、この2つを測るだけで議論が終わることが多い。
  • 「将来のスケール」を今日の複雑さで買う。マイクロサービス分割・シャーディング・K8s は、規模が来なければ純損失。来た時に移れる形（コンテナ化・ステートレス・設定の外部化）だけ守っておけば、移行は間に合う。

  • 構成図を暗記して満足する。図は結論で、価値は「なぜその層があるか」を数字で言えることにある。DAU から必要タスク数を口頭で出せるかが本当の到達点。

08 踏み台サーバーの仕組み

7章の図から自然に出てくる要求：「private subnet の中にある DB を、開発者のPCから見たい」。そのための「VPC の中に置いた足がかり」が踏み台（Bastion / Jump Server）。

🏢 ビルの例え。 最上階の金庫室（RDS）に、道路から直接入る扉は無い。だから1階ロビーの受付（踏み台）で入館証をもらい、そこから内部の階段で上がる。
重要なのは、踏み台自体は「何もしないサーバ」だということ。アプリも動いていない。ただ「VPC の中に居る」ことだけが価値。だから最小構成でよく、逆に言えば侵入されたら全部見られるので厳重に守る必要がある。

図8-1 3方式の比較。新規構築なら SSM 一択。「鍵の管理」という人間依存の作業が消えるのが最大の利点。

実際のコマンド（3方式）

# ============ ① SSH 踏み台（従来型） ============ # -L で「自分の15432 を、踏み台の先の RDS:5432 に転送」 ssh -i ~/.ssh/bastion.pem -L 15432:prod-rds.xxxxx.rds.amazonaws.com:5432 \ ec2-user@bastion.example.com -N # 別ターミナルで psql -h localhost -p 15432 -U app_readonly -d appdb # ============ ② SSM Session Manager（推奨） ============ # 踏み台にシェルで入る（SSH鍵もポート開放も不要） aws ssm start-session --target i-0123456789abcdef0 # ポートフォワード（踏み台経由で RDS へ） aws ssm start-session \ --target i-0123456789abcdef0 \ --document-name AWS-StartPortForwardingSessionToRemoteHost \ --parameters '{"host":["prod-rds.xxxxx.rds.amazonaws.com"],"portNumber":["5432"],"localPortNumber":["15432"]}' # → localhost:15432 が本番RDSに繋がる # ============ ③ ECS タスクの中に入る（踏み台なしでデバッグ） ============ # アプリコンテナ自体にシェルで入れる。踏み台EC2を用意しなくてよい aws ecs execute-command --cluster prod --task <task-id> \ --container app --interactive --command "/bin/sh" # 前提: サービスに enableExecuteCommand を有効化し、タスクロールに SSM 権限を付ける

③が便利な理由: 踏み台EC2 を1台も置かずに済む。アプリコンテナ自体が private subnet に居るので、そこに入れれば DB にも届く。ただし本番コンテナ内で作業するリスクはあるので、調査専用のタスクを別に起動する運用のほうが安全。

起動時に必須の環境変数を検証する（強く推奨）

// 「本番でだけ設定漏れが発覚する」を防ぐ最も安価な対策 type Config struct { DatabaseURL string RedisURL string StripeKey string AppEnv string } func Load() (*Config, error) { c := &Config{ DatabaseURL: os.Getenv("DATABASE_URL"), RedisURL: os.Getenv("REDIS_URL"), StripeKey: os.Getenv("STRIPE_KEY"), AppEnv: os.Getenv("APP_ENV"), } // 必須項目が欠けていたら起動を止める（= デプロイが失敗する） var missing []string for k, v := range map[string]string{ "DATABASE_URL": c.DatabaseURL, "REDIS_URL": c.RedisURL, "STRIPE_KEY": c.StripeKey, "APP_ENV": c.AppEnv, } { if v == "" { missing = append(missing, k) } } if len(missing) > 0 { return nil, fmt.Errorf("missing env: %v", missing) } return c, nil }

効果: 設定漏れがあるとタスクがヘルスチェックに失敗し、ローリング更新が中止されて旧版が残る。つまりユーザーに影響が出ない。逆にこれが無いと「起動はするが特定機能だけ壊れている」状態になり、発見が遅れる。

12 いつ「バイナリ」になるのか

先に結論を書きます。「デプロイするとコードがバイナリになる」は、多くの場合そうなっていません。言語によって「機械語になる瞬間」が全く違い、Node/TypeScript の場合は最後まで機械語のファイルが作られません。ここを正確にすると、コールドスタートやウォームアップの話が全部繋がります。

よくある誤解を先に3つ潰す

誤解実際
「デプロイするとコードがコンパイルされてバイナリになる」言語による。Go / Rust は ビルド時に機械語の実行ファイルになる。Node / Python / Ruby は機械語のファイルにならない（実行中にメモリ上で機械語が作られる）
「next build は Next.js をコンパイルしている」コンパイル（機械語化）ではない。やっているのは「変換・結合・圧縮・事前レンダリング」。出力は依然として JavaScript のテキストと HTML
「docker build がコンパイル」違う。docker build は「ファイルシステムを詰めた箱を作る」だけ。ただし Dockerfile の中で go build を書けば、その行でコンパイルが起きる（＝ 詰める前の作業として）
🍳 料理の例え。 Go = 工場で完成品の缶詰を作って出荷する（現地は温めるだけ）。Java = 半調理のキットを送り、現地の厨房が「よく出る料理から順に」本格調理していく。Node/Python = レシピを送り、現地のシェフが毎回その場で読んで作る。よく作る料理だけ手が覚えて速くなる。
だから Node のサーバは「起動直後が一番遅く、しばらく動かすと速くなる」。缶詰（Go）にはこの現象が無い。

図12-1 機械語になる瞬間。この1枚で「なぜ Go はサーバーレス向き」「なぜ Node は温まると速い」「なぜ Java は起動が重い」が全部説明できる。

では next build は何をしているのか（成果物の分解）

Next.js のビルドは「コンパイル」と呼ばれることが多いが、実際にやっているのは5種類の別作業。出力物を見ると分かる。

ビルドは「デプロイのたびに1回」だけ。リクエストごとにビルドは起きない。だからビルドが3分かかってもユーザー体験には無関係 ② 環境変数の扱いが2種類に分かれる — NEXT_PUBLIC_ 付きはビルド時にコードへ埋め込まれるので、後から変えられず、ブラウザから見える。 サーバー側だけで使う変数は実行時に読まれる。→ NEXT_PUBLIC_ に秘密情報を入れる事故が非常に多い ③ バンドルサイズがコールドスタートに直結する — 関数モデルでは起動ごとにパースするので、重い依存を1つ入れると全リクエストが遅くなる ④ 「事前生成できるページ」を増やすほど速く安くなる — サーバが動かないので、CDNから返して終わり（キャッシュの章と同じ発想） ⑤ ソースマップを本番に置くとソースが読める — 出力が JS のテキストである以上、難読化しても復元されうる。クライアントに秘密は置けない

図12-2 next build の分解。「1回のビルドで、CDN行き・関数行き・Isolate行きの3種類に分裂する」のが Vercel 型プラットフォームの本質（図11-2 と対応）。

Docker イメージの正体（「コンパイルされた塊」ではない）

コンパイル = ソースを機械語（or 中間表現）に変換すること。Dockerfile の中の go build がこれ ・docker build = 上の結果を含むファイル群を、層に分けて固めること。これ自体はコンパイルではない ・docker run = 固めた層を展開し、隔離した環境で中の実行ファイルを起動すること

図12-3 イメージの正体。「イメージはコンパイル結果ではなく、ファイルシステムの詰め合わせ」。だから中に Go のバイナリを入れることも、JS のテキストを入れることもできる。

付録 チートシート

1. 3つの流れを分ける

①デプロイ（ローカル→GitHub→ECR→環境。一方通行・時々）②リクエスト（ブラウザ→ALB→アプリ→DB。往復・常時）③調査（開発者→踏み台→DB）。GitHub は②に登場しない。

2. 登場人物の役割

GitHub = コードの置き場 / ECR = イメージの置き場 / ECS = コンテナが動く場所。「GitHub にデプロイ」という言い方は存在しない。

3. 環境の違いは「外側」だけ

同じイメージを配り、変えるのは①環境変数 ②秘密情報の値 ③台数 ④権限 ⑤接続先。イメージを環境ごとにビルドし直さない（build once, deploy many）。

4. 同じにすべきもの

アプリのイメージ / DBのメジャーバージョン / OS・ミドルウェアの版 / マイグレーション手順 / タイムゾーン・文字コード。ここが違うと staging の意味が消える。

5. public / private の違い

IGW への経路を持つかどうか、だけ。private は外から到達不可（＝ 踏み台が必要）。ただし NAT 経由で「出る」のは可能。

6. サブネットと SG の違い

サブネット = 住所（経路があるか） / SG = 扉の鍵（誰の通信を許すか）。両方通らないと繋がらない。SG はIPではなく「送信元SG」で指定する。

7. ブラウザ→DBの経路

ブラウザ → DNS → CDN → ALB(TLS終端) → アプリコンテナ → (Redis) → RDS。ブラウザから DB への直通経路は存在しないし、作ってはいけない。

8. 踏み台の選択

新規なら SSM Session Manager（ポート開放ゼロ・SSH鍵なし・IAMで制御・ログが残る）。ECS Exec ならアプリコンテナに直接入れるので踏み台EC2すら不要。

9. なぜ SSM はポートを開けずに繋がるか

サーバ側のエージェントが自分から AWS API へ常時接続（アウトバウンド）を張り、開発者はその通路に相乗りする。「入る穴」を作らない発想。

10. 認証は3主体で別々

人間→SSO+MFA / CI→OIDC / アプリ→タスクロール。加えてアプリ↔ユーザーのセッション認証は完全に別の話。

11. 認証の方向性

「秘密を保存して使い回す」→「身元を証明して短命な権限をもらう」。長期アクセスキー・SSH鍵は減らす方向。漏れても短時間で無効になる。

12. 秘密情報の置き場所

local = .env（gitignore・弱い値） / CI = GitHub Secrets（OIDCなら鍵は不要） / 本番 = Secrets Manager / Parameter Store。環境間で値を共有しない。

13. 絶対にやらないこと

Git にコミット / Dockerfile に焼く / ログに出す / Slack で共有 / stg と prod で同じ値。漏れたら「まず鍵の無効化」が最優先（履歴削除より先）。

14. ローリング更新の制約

新旧が同時に動く時間がある。だから①マイグレーションは後方互換（追加→使う→削除の3段階）②SIGTERM で graceful shutdown。

15. 「1台前提」を疑う

メモリ上のキャッシュ / ローカルファイルにセッション・アップロード / プロセス内 cron。状態は必ず外（DB・Redis・S3）に置く。ローカル1台では気づけない。

16. デプロイ先の選択

迷ったら ECS on Fargate。学ぶ概念が少なく必要なことは全部できる。「K8s を使いたい」が理由なら選ばない。どれでもイメージを作る部分は同じなので後から移れる。

17. マイグレーションの実行場所

GitHub Actions から DB へは直接繋がらない（private subnet）。VPC 内の ECS タスクとして1回実行するのが定石。

18. 最初に整えると効くもの

①起動時の環境変数チェック ②イメージタグ = コミットSHA ③graceful shutdown ④人間用の読み取り専用DBユーザー。どれも1日で入れられて、事故を構造的に防ぐ。

19. プラットフォームの4分類

①常駐系（ECS/Render/App Runner）②関数系（Lambda/Vercel/Amplify SSR）③Isolate系（Cloudflare Workers）④BaaS（Supabase/Firebase）。縦（実行モデル）の移動はアプリの設計変更。

20. 「バイナリになる」のは言語次第

Go/Rust = ビルド時に機械語 / Java = bytecode→実行時JIT / Node・Python = 機械語のファイルは作られない（V8 が実行中にメモリ上で生成）。これが起動速度の差の正体。

21. next build は何をしているか

コンパイルではない。①TS→JS変換 ②バンドル ③圧縮 ④事前レンダリング ⑤ルート表生成。出力は JS のテキストと HTML。NEXT_PUBLIC_ はここでコードに埋め込まれる（＝ブラウザから見える）。

22. docker build はコンパイルではない

イメージ = ファイルシステムの層（tar）+ 起動方法のメモ。docker run は層を展開して隔離環境で実行ファイルを起動するだけ。Dockerfile 内の go build がコンパイル。

23. 関数モデル × RDBMS の必須対策

同時100リクエスト = 実行環境100個 = 接続100本。接続プーラーは最適化ではなく必須（Supabase pooler / RDS Proxy / PgBouncer / Hyperdrive）。常駐モデルなら不要。

24. エッジの正しい使い方

状態を見ない処理はエッジ、状態を触る処理はDBの隣。DBが遠いのにエッジで複数回SQLを投げると、中央より遅くなる。

25. ロールバックできるもの / できないもの

アプリのバージョンは戻せる（Vercel は数秒、ECS は数分）。DBスキーマは戻せない。だからマイグレーションは常に追加のみ（後方互換）にする。

26. ロックインの本当の所在

「ビルドの仕方」ではなく「実行モデル」と「データの置き場所」に縛られる。イメージを渡すだけの ECS/Render/App Runner は相互に移りやすい。RLS に認可を寄せた・DynamoDB のアクセスパターンに合わせた設計は書き直しになる。

27. 層は「作るリスト」ではない

図14-1 のうち MVP で必要なのは CDN・ALB・アプリ・DB の4段だけ。リバプロ(Nginx)・共有FS は多くの場合不要、BFF・NoSQL・キューは痛みが出てから。足すのは簡単、消すのは難しい。

デプロイとは「同じイメージを、違う設定と違う権限で、違う場所に置くこと」であり、インフラとは「どこからどこへ通信できるかを決めること」である。

そして人間が本番に触る回数を減らすことが、最も効果の高い安全対策である。
