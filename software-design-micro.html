重要な概念は ①問題 → ②初心者コード → ③なぜ問題か → ④設計原則 → ⑤改善後 → ⑥Before/After → ⑦変更範囲 → ⑧トレードオフ → ⑨過剰設計の境界 → ⑩レビュー観点 の10ステップで進む。

この本の主張1

SOLID・DDD・Clean Architecture・GoFパターン・TDD はそれぞれ独立した正解ではなく、全部「変更容易性・理解容易性・正しさ」を守るための道具。宗教として教えない。道具は目的から選ぶ。

この本の主張2

設計とは「変更の理由が違うものを、別の場所に置くこと」。分割の単位は行数でもファイル数でもなく「誰の要求で書き換わるか」。これが Cohesion / SRP / Bounded Context の共通の核。

この本の主張3

L6 は抽象化が多い人ではない。「将来の変更コスト」と「今の複雑性」を天秤にかけて、抽象化を足す/足さないを説明できる人。過剰設計も設計ミスである。

00 はじめに — ズームの体系

この本は最初から最後まで、たった1つの題材を使う。「OTA（楽天トラベル・じゃらん・Booking.com などの予約サイト）から予約Webhookを受け取り、自社の宿泊管理システムに反映する」。地味な題材だが、ここには設計のほぼ全論点が詰まっている。重複リクエスト、順序逆転、並列実行、複数の外部フォーマット、トランザクション、在庫同期、外部API失敗、スケール。
そして本書のクライマックスは、次のたった1行のifを9つのレイヤーから説明することである。

この1行に、何が同時に含まれているのか

この if は、見る解像度によって名前が変わる。同じコードなのに、である。

  • Idempotency（冪等性）の実装 — 同じWebhookが2回来ても2回目は何もしない
  • Out-of-order 対策 — 古いrevisionが後から来ても上書きしない
  • Domain Invariant（不変条件）の防衛 — 「予約は時間を巻き戻らない」というビジネスルール
  • State Transition Guard — 状態遷移の可否判定
  • UseCase Orchestration の早期リターン — 以降の処理（DB更新・在庫同期・イベント発行）を全部スキップする分岐
  • そしてこれだけでは Race Condition を防げていないという欠陥の証拠

「この行は何？」と聞かれて「revisionの比較です」と答えるのが L4。「冪等性の実装です」が L5。「アプリ層の冪等性ガードです。ただし並列Workerでは効かないので、DBのversion条件付きUPDATEと二重化しています。この行はfast pathで、正しさの最終防衛線はDBにあります」と答えるのが L6。

本書のもう1つの軸は「解像度の上下移動」である。ソフトウェア設計が難しいのは、9つの異なる解像度が同時に存在し、それぞれに別の言葉と別の判断基準があるからだ。まずその地図を持つ。

Part 1

良いコードとは何か

「動くコード」と「良いコード」の差を、感覚ではなく4つの品質（変更容易性・理解容易性・正しさ・テスト容易性）に分解する。そして Cohesion / Coupling / SOLID を「暗記する原則」ではなく「どんな変更要求が来たときに困るか」から導く。最後に神関数 CreateReservation を7段階で解体し、同時に「関数を小さくすれば良い」「interfaceを作れば良い」という2大誤解を潰す。

01 Software Design とは — 設計と実装の違い

結論から。設計とは「決定を、どこに、いつ、誰が変えられる形で置くか」を決める行為である。実装は「決めた場所に、動く手続きを書く行為」。だから「設計フェーズが終わったので実装します」という言い方は、ほとんどの場合ウソになる。コードを書いている間も、人は毎行で設計している。

図1-1 要求 → 設計 → 実装。設計の本質は「未来の変更を、どこに閉じ込めるか」の賭けである。

① どんな問題があるのか — 「動くコード」で止まると何が起きるか

「動くコード」は、書いた瞬間はコストゼロで最速だ。問題は2回目以降に起きる。

  • 読む回数 >> 書く回数 — コードは1回書かれ、10回読まれ、5回変更される。書く速度を最適化して読む速度を犠牲にするのは、1回のために15回を捨てる取引
  • 変更のたびに「全部読まないと安全に変えられない」状態になる — 1関数800行のコードを1行変えるために800行を読む。これが「変更コストが線形に増えない（指数的に増える）」原因
  • 壊れたことに気づけない — テストが書けない構造だと、変更の副作用は本番で発見される

② 初心者が書きがちなコード — 本書を通じて解体していく「神関数」

これは実在のコードを圧縮した形。動く。テストも通る（手動で）。リリースもできる。だから最初の1回は誰も困らない。

③ なぜそのコードが問題なのか — 「汚い」ではなく「変更コストが測れる」形で言う

「読みにくい」は主観だが、「変更コスト」は客観的に測れる。レビューでは後者で語る。この関数の問題を、変更要求ベースで数える。

来るはずの変更要求この関数だと何が起きるか本来の変更範囲
OTAが5社に増え、JSON形式が違うこの関数を5回コピーする（あるいは巨大なif分岐が生える）gateway パッケージに5つの実装を追加するだけ
「4泊目以降10%引き」を「5泊目以降15%引き」に変えるHTTPハンドラを開いてビジネスルールを探す。テストがないので手動確認domain の料金計算1箇所 + 単体テスト

重要: この表が「設計の言語」である。「ダメなコードです」ではなく「この形だと、5社対応のときに5コピーになります」と言えるかどうかが、L4とL5の差。

④ 設計原則 — 設計の目的は「変更コストを一定に保つこと」

ソフトウェアは Hardware ではなく Soft-ware、つまり「変わることが前提の製品」である。よって設計の評価関数は「美しさ」ではない。

設計の評価関数

要求の変更量に対して、コードの変更量が比例以下であること。「1つの要求変更 → 1箇所の変更」に近づけるのが良い設計。「1つの要求変更 → 12ファイル変更」は設計の失敗（Shotgun Surgery）。

設計が不要なケースも存在する

使い捨てスクリプト、1回のデータ移行、実験用コード。「二度と変更しない」と確信できるなら、神関数が最適解。設計はコストなので、変更が来ないところに払ってはいけない。

⑨ 過剰設計になる境界 — この章の時点で言っておくべきこと

これから本書は上のコードを解体していくが、最終形はいきなり目指すものではない。以下の状況では、解体の途中で止めるのが正解。

  • 1画面のCRUD、要求変更の見込みが年1回未満 → handler + repository の2層で十分。usecase も domain も要らない
  • プロトタイプで、3ヶ月後に捨てる予定 → 神関数のままでよい。ただし「捨てる予定」は8割ウソになることを知っておく
  • チームが1人で、コードの全体像が頭に入っている → 抽象化の便益（他人が読める）が発生しないので、投資回収できない

逆に「外部システムと繋がる」「お金・在庫・状態を持つ」「複数人で触る」のどれか1つでも当てはまれば、設計投資はほぼ確実に回収できる。予約Webhookは3つ全部に当たる。

02 4つの品質 — Maintainability / Understandability / Changeability / Testability

「良いコード」を分解すると4つになる。この4つは独立ではなく、Testability が他の3つの先行指標になっているのが重要な構造。「テストしにくい」は、設計が壊れていることの最も早い警報である。

図2-1 Testability は原因側、Maintainability は結果側。結果指標だけを見ていると手遅れになる。

② 「テストできない」を体感する

テストを書くには MySQLを起動し、外部APIをモックするプロキシを立て、システム時刻を偽装する必要がある。つまり「単体テストが書けない」のではなく「この関数が3つの外部世界と直結している」のが問題。テストの困難は症状であって病気ではない。

④ 設計原則 — テスト容易性の3条件

  1. 依存を「作らない」で「受け取る」（Dependency Injection） — gorm.Open を関数内で呼ばない
  2. 副作用を境界に押し出す — 判断（純粋な計算）と実行（DB書き込み・通信）を分ける。判断部分は引数と戻り値だけでテストできる
  3. 暗黙の入力を明示する — 時刻・乱数・UUID・環境変数は全部「入力」。time.Now() は隠れた引数である

⑤ 改善後 — 依存を引数化しただけで4つの品質が同時に上がる

⑥ Before / After

観点Before（自分で依存を作る）After（依存を受け取る）
単体テスト不可能（MySQL・SMTP・外部APIが必要）可能・1ms・並列実行可

正直に言うべきこと: After は確実にコードが増える。20行が60行になる。これが設計のコストであり、「変更が来る前提なら安い、来ないなら高い」という賭けの本質。

⑨ 過剰設計になる境界

  • Clock を全部の関数に注入する → 過剰。時刻が「判定に使われる」場合だけ注入する。ログのタイムスタンプ用に注入するのは無駄
  • 依存が1つもない純粋関数にDIを持ち込む → 無意味。func CalcNights(in, out time.Time) int は引数だけでテストできる。最良のテスト容易性は「そもそも依存がないこと」
  • interfaceを「将来差し替えるかも」で作る → Part 2 ch16 で潰す。実装が1つで差し替え予定がないなら、structを直接使ってよい（テストのためだけなら妥当な場合もある）

⑩ コードレビューで見るポイント

  • 関数内に gorm.Open / http.Post / time.Now() / os.Getenv / uuid.New() が直接書かれていないか
  • 「この関数のテストはどう書きますか」を聞く — 答えに「まずDBを立てて」が出たら設計の問題
  • PRの差分が「1つの要求」に対して不自然に広くないか（Shotgun Surgery の兆候）
  • 逆に、テストのためだけに5つのinterfaceが増えていないか（過剰の兆候。ch16で判定基準を示す）

03 Cohesion / Coupling — 設計の最も基本的な2軸

結論。High Cohesion = 「同じ理由で変わるものが同じ場所にある」／Low Coupling = 「違う理由で変わるものが互いを知らない」。この2つは独立ではなく、Cohesion を上げると自然に Coupling が下がる関係にある。逆に「Coupling を下げよう」と先に手を付けると、interfaceだけ増えて中身がバラバラ（低凝集・低結合）になる典型的な失敗をする。

図3-1 4象限。改善の順序は「凝集を上げる → 結合を下げる」。逆順は左上の罠に落ちる。

① どんな問題があるのか

「機能ごとにファイルを分けました」と言うが、変更のたびに5ファイル開く。あるいは「共通処理をutilsにまとめました」と言うが、utilsを1行変えると誰が壊れるか誰も分からない。これは分け方の軸が間違っている。

② 初心者が書きがちなコード — 「技術的な種類」で分けてしまう（低凝集）

③ なぜ問題なのか — Cohesion の定義を「変更理由」で言い直す

教科書的な凝集度の分類（機能的凝集 > 逐次的 > 通信的 > 手続き的 > 時間的 > 論理的 > 偶発的）を覚える必要はない。実務で使える判定基準は1つ。

判定基準

「このファイルの中身は、同じ人の、同じ要求で、同時に書き換わるか？」

上の utils は、キャンセルポリシー担当者（営業）と、経理（税率）と、SRE（Slack通知）の3者の要求で書き換わる。だから低凝集。逆に domain/reservation に「泊数計算・キャンセル料・料金計算」が集まっているのは、全部「予約の商売ルール」という同じ理由で変わるので高凝集。

Conway の法則との接続: 「同じ人の要求で変わる」＝「同じチームが所有する」。凝集度の正しい単位は、組織の要求の単位である。これが Part 3 の Bounded Context に直結する。

⑤ 改善後 — 「変更理由」で切り直す（High Cohesion）

「1箇所を読めば全部わかる」という利点。処理の全体像を追うのに複数ファイルを開くことになる。最初に最も苦しむのはこの点で、「Clean Architectureは読みにくい」という不満の正体。

イベント化のコスト

メッセージ結合（イベント）は結合度が最も低いが、処理の順序と失敗時の挙動が追跡困難になる。「メールが来ない」の原因調査が10倍難しくなる。同期呼び出しのほうが良い場面は多い。

判断の目安

「失敗しても業務が続くもの（通知・分析・検索インデックス）」はイベント、「失敗したら業務が壊れるもの（在庫・課金）」は同期呼び出し。結合度を下げる代償に一貫性を捨ててよいかで決める。

⑨ 過剰設計になる境界

  • 2〜3個の関数のために package を切る → Goでは package が増えると import 地獄と循環依存の危険が増える。まず同じpackage内でファイルを分けるだけで十分
  • 全ての別Aggregate操作をイベント化する → 在庫の同期をイベントにすると「予約は取れたが在庫が減っていない」時間が生まれる。それをビジネスが許容するかを確認せずにやると事故
  • 凝集を求めて1ドメインに全部詰める → 逆方向の失敗。「予約」に請求・清掃・鍵の発行まで入れると、それは新しい God Package

⑩ コードレビューで見るポイント

  • package名に utils / common / helpers / manager / base が出てきたら必ず質問する — 「これは何の変更理由で変わりますか？」
  • bool引数（特に2つ以上）— 制御結合のサイン。関数を分けられないか
  • a.B.C.D = x のようなドット3連 — Law of Demeter 違反 = 内容結合（ch8）
  • グローバル変数・パッケージレベルの可変状態
  • 「この1要求で何ファイル変わったか」を数える — PRの差分ファイル数が要求の複雑さに見合っているか

04 Separation of Concerns — 「関心」とは何か

結論。Concern（関心）＝「変更を要求する人（ステークホルダー）」。SoC は「機能を分けろ」ではなく「異なる人の要求が同じコードに乗らないようにしろ」という原則。これが SRP の元ネタでもある。

図4-1 SoC の実体は「1ファイルに何人の要求者がいるか」。5人いたら、そのファイルは5回書き換わる。

④ 設計原則 — Concern の見つけ方（実務手順）

  1. この処理の変更を依頼してくるのは誰かを書き出す（営業・経理・CS・SRE・外部企業・法規制）
  2. 変更の頻度と予測不能性で並べる。外部企業の仕様（OTA）と法規制（税率・インボイス）は最も予測不能 → 最も強く隔離する
  3. 同じ要求者・同じ頻度のものを1ファイルに集める（＝凝集）
  4. 要求者が違うものの間に変換層（Mapper / Gateway / DTO）を置く

ここが Clean Architecture の Dependency Rule の根拠: 「変わりにくいもの（ドメインルール）が、変わりやすいもの（HTTP・DB・外部API）に依存してはいけない」。依存の向きは「変更頻度の低い方向」へ流す。

⑨ 過剰設計になる境界

  • 1人しか要求者がいないのに層を分ける — 社内管理画面のマスタCRUDは「開発者だけが要求者」。handler + repository で十分
  • 「関心」を細かく取りすぎる — 「バリデーションの関心」「ログの関心」「型変換の関心」で3ファイルに分けると、読む側は3ファイル追う。関心の粒度は「要求者の粒度」まで。それ以上細かくしない

05 Abstraction / Encapsulation / Information Hiding — 似て非なる3つ

この3つは混同されがちだが、目的が違う。Abstraction は「何を無視できるか」、Encapsulation は「状態を誰が変えられるか」、Information Hiding は「決定を誰に見せないか」。Goでは3つ目が特に重要で、package の小文字（unexported）は設計の主要武器である。

図5-1 Abstraction は読む人のため、Encapsulation は正しさのため、Information Hiding は将来の自分のため。

② 初心者が書きがちなコード — 全部publicの構造体（Anemic Model）

③ なぜ問題なのか

  • 不正な状態が「作れてしまう」 — バグの探索範囲が「この構造体を触る全コード」に広がる。50箇所あれば50箇所を疑う
  • ルールの置き場所がなくなる — 「チェックアウトはチェックイン後」というルールを書く場所がないので、各handlerにコピーされる（Shotgun Surgery）
  • 文字列のstatus — 取りうる値がコードから読めない。grep "confirmed" が唯一の仕様書になる
  • DBスキーマがドメインの形を支配する — gorm タグが付いた構造体をドメインで使うと、テーブル設計を変えるとビジネスルールのコードが壊れる。依存の向きが逆になっている

⑤ 改善後 — 「不正な状態を作れなくする」

⑥ Before / After — バグの「探索範囲」が変わる

バグBefore の調査After の調査
チェックアウトがチェックインより前の予約がDBにいるCheckOut = を書いている全箇所（50箇所）を調べるNewStayPeriod の1箇所だけ。そこを通らずに作る方法がない
status に "cofirmed" が入っているgrepして目で探す。テストでも発見されないコンパイルエラーで発生自体が不可能
キャンセル済みが確定に戻っている状態遷移を書いている全箇所を読むConfirm() の中だけ。単体テストで固定できる
合計金額が負計算箇所を全部追うMoney のコンストラクタだけ

これがカプセル化の本当の価値: コードが綺麗になることではなく、バグの調査範囲がO(n)からO(1)になること。

⑧ トレードオフ — 正直に言う

コスト1: コード量

1つのフィールドに対して「VO定義 + コンストラクタ + getter + テスト」が生える。3フィールドの構造体が、200行のパッケージになる。

コスト2: ORMとの摩擦

GORMはunexportedフィールドに値を入れられない。よって「DB用の構造体（record）」と「ドメインの構造体（entity）」の2つが必要になり、Mapperが必要になる。これは Part 5 で扱う実務上の最大の面倒。

コスト3: JSONとの摩擦

encoding/json も同様にunexportedを扱えない。よって Response DTO が必要になる（これは Part 6 で「むしろ利点」だと示す）。

回収できる条件

不変条件が2つ以上ある / 状態遷移がある / お金か在庫を扱う / 複数箇所から生成される。1つも当てはまらないなら、公開フィールドのstructで十分。

⑨ 過剰設計になる境界 — VOを作ってはいけないもの

  • 制約のないただの文字列に type Memo string を作る → 型安全の便益はあるが、ルールがないなら効果は薄い。ID型（type ReservationID string）は引数の入れ替え事故を防ぐので例外的に価値が高い
  • 全フィールドをVO化する → 5つのVOで50行、10フィールドで500行。「不正な値が入ると業務が壊れるもの」だけVO化する（金額・期間・人数・メールアドレス）。表示用の名前や備考は素の string でよい
  • getterを機械的に全部生やす → それは public フィールドと等価。getterを書く前に「これは外から読む必要があるか？」を毎回問う

⑩ コードレビューで見るポイント

  • Set* メソッドがあるか（あるなら、それは業務操作の名前で置き換えられないか）
  • ドメイン構造体に gorm: / json: タグが付いていないか（＝外部の関心が漏れている）
  • status が string / int の生値になっていないか
  • コンストラクタを通らずに &Reservation{...} で作れる場所がないか（同package内では作れてしまう点に注意）
  • 逆に、getterが20個並んでいないか（カプセル化した気になっているだけ）

06 Composition と Dependency — Goに継承がない理由

結論。Goには継承がなく、それは欠陥ではなく設計上の選択である。継承は「実装の再利用」と「型の階層」と「振る舞いの差し替え」という3つの別物を1つの機能に押し込んでいた。Goはそれを埋め込み（実装の再利用）とinterface（型と差し替え）に分離した。

図6-1 継承は「1本の木」、Compositionは「部品の組み合わせ」。要求が2軸以上になると継承は必ず破綻する。

② Goで継承を再現しようとする失敗（埋め込みの誤用）

⑤ 改善後 — 必要なものだけを、名前を付けて持つ

⑨ 過剰設計の境界 — 引数7個は多すぎないか？

「多い」と感じたら、それは正しい感覚。ただし対処法は「BaseUseCaseにまとめる」ではない。選択肢は3つ。

  1. UseCaseを分割する — 依存が多いのは責務が多い証拠。ProcessWebhook が「予約更新」と「在庫同期」の2つをやっているなら、後者を別UseCase＋イベント駆動にすれば依存は4つに減る（ch29で検討）
  2. 横断的関心（logger, clock, metrics）を1つにまとめる — deps struct や context 経由。ドメイン依存とインフラ横断依存は別物なので、後者だけまとめるのは妥当
  3. そのまま受け入れる — 7個でも、それが本当に必要な依存なら正直な設計。隠すより見えている方が良い。Wire を使えば配線の手間は消える（ch15）

④ 埋め込みを使ってよい場面 — Decoratorとして使う

埋め込みが正しく効くのは「同じinterfaceを実装しつつ、振る舞いを1点だけ足す」とき（Decorator / Part 10）。

⑩ コードレビューで見るポイント

  • Base* / Abstract* という名前の構造体（継承の再現＝ほぼ設計ミス）
  • 埋め込みが「共通処理の再利用」目的になっていないか（＝ has-a でないものを has-a している）
  • 構造体を見て「この型が何に依存しているか」が読めるか
  • 使わない依存を持たされていないか（ISP違反）

07 SOLID — 定義ではなく「困る変更要求」から導く

SOLIDの定義を暗記しても設計はできない。5つとも「ある特定の変更要求が来たときに困る」という具体的な痛みへの処方箋である。だから各原則を「この原則を守っていないと、どの要求で死ぬか」から入る。そして最後に「守らない方が良い場合」も必ず書く。

図7-1 SOLIDの本体は「痛み」の側。処方だけ覚えると、痛みがない場所にも処方してしまう（＝過剰設計）。

S Single Responsibility Principle

① 困る変更要求

「消費税率が変わったので請求書の計算を直してください」と経理から言われて修正した。翌日、営業から「予約のキャンセル料が全部0円になっている」と報告が来る。原因は utils/calc.go の共通関数を触ったこと。

④ 原則の正しい定義

Robert C. Martin の定義は「1つのことだけをする」ではない。正確には "A module should have one, and only one, reason to change" ＝ 「モジュールの変更を要求するアクター（人・部門）は1つであるべき」。
つまりSRPは技術的な原則ではなく、組織的な原則である。行数は無関係。500行あっても、変更を要求する人が1人なら SRP を満たしている。

⑥ Before / After

⑨ 過剰設計の境界 — SRPを守らない方が良い場合

  • アクターが実質1人（開発チームだけ） — 社内ツールでは「予約構造体にToJSONを付ける」で全く問題ない。分割コストが回収できない
  • 1メソッドのために1パッケージを作る — domain/cancel_policy パッケージを作るのは行き過ぎ。同じpackage内のファイル分割で十分。Goではpackageを増やすほど循環依存リスクが上がる
  • SRPを「関数は10行以内」と誤解して分割する — 最悪の適用。ch11で詳述

O Open-Closed Principle

① 困る変更要求 — 「OTAが5社になりました」

これは本書の中心的な変更要求（Drill #4, #5）。OCPが効いているかどうかで、1社追加のコストが「新ファイル1つ」か「既存全体の再テスト」かに分かれる。

② 初心者コード — switchが増殖する

⑤ 改善後 — interface + registry で「追加のみ」にする

⑦ 変更範囲の比較（OTA 1社追加）

レベルswitch版Provider版
File既存の巨大関数を編集（+80行）新規4ファイル追加、既存1行追加
Test全社分のテストを再実行・レビュー新社のテストのみ。既存テストは触らない
Review全OTAの知識を持つ人でないとレビュー不能新社担当だけでレビュー可

障害の影響1社のパース失敗が全社に波及するリスク1社の実装バグは1社に閉じる

⑨ 過剰設計の境界 — OCPは「2回目」に適用する

OTAが1社しかない時点でProvider interfaceを作るのは、多くの場合過剰設計。理由は「どこが変わる軸なのか、1例では分からない」から。1社目だけで抽象化すると、2社目で必ず抽象が合わずに作り直す。

  • Rule of Three: 1つ目は素直に書く。2つ目で共通点が見えるので抽象化する。3つ目で抽象の正しさを検証する
  • 例外: 「増えることが要求として確定している」なら1社目から抽象化してよい。予約Webhookで「今はじゃらんだけだが半年後に楽天を繋ぐ」が経営計画に載っているなら、それは投機ではなく既知の要求
  • switchが悪いわけではない: 分岐が2〜3個で、増える見込みがなく、同じファイルに閉じているなら switch のほうが読みやすい。「switch を見たら interface」は思考停止

L Liskov Substitution Principle

① 困る変更要求 — 「Booking.comだけ挙動が違う」

Goに継承はないので「LSPは関係ない」と思われがちだが、interfaceを使う瞬間からLSPは全面的に関係する。UseCaseは ota.Provider の全実装が「同じ約束」を守ると信じてコードを書いている。1実装だけ約束を破ると、UseCaseを触っていないのに壊れる。

② LSP違反のGoコード — 4つの典型

④ 設計原則 — interfaceは「シグネチャ」ではなく「契約」

LSPの正体は「事前条件を強めてはいけない / 事後条件を弱めてはいけない / 不変条件を破ってはいけない」。Goでは型システムがこれを守ってくれないので、契約をコメントで明文化し、Contract Test で機械的に検証するのが唯一の実務解。

⑩ レビュー観点

  • interfaceのメソッドに契約コメントがあるか。「実装を読まないと使えないinterface」は抽象化に失敗している
  • 実装の中に panic / log.Fatal / os.Exit がないか
  • ctx を受け取っているのに使っていない実装がないか（_ context.Context は要注意）
  • 1つの実装だけが持つ特殊な制約・特殊なエラー型がないか

I Interface Segregation Principle

① 困る変更要求 — 「予約一覧のテストを書きたい」

Repositoryが20メソッドあると、2メソッドしか使わないUseCaseのテストでも20メソッドのモックを作る羽目になる。さらに悪いのは、Repositoryに1メソッド増やすと、全てのモックがコンパイルエラーになること。

② Fat Interface

⑤ 改善後 — Consumer-owned Interface（Goの定石）

Goでは「interfaceは使う側のパッケージが宣言する」のが慣習。これによりinterfaceは自然に小さくなる。io.Reader が1メソッドである理由と同じ。

⑧ トレードオフ

利点

モックが小さい / 依存が正確に読める / Repositoryの拡張がテストを壊さない / 「このUseCaseはDBの何を使うか」が宣言で分かる

欠点

同じメソッドのinterface宣言が複数箇所に散る。FindByOTAID の宣言が3つのUseCaseファイルに書かれる。Goの慣習では許容されるが、初見では「重複」に見える。

実務での落ち着きどころ

ドメイン層に「Aggregate単位の中核Repository interface」を1つ置き（3〜6メソッド）、それ以外の検索系はUseCase側で個別に宣言するハイブリッドが現実的。読みやすさと小ささのバランスが取れる。

mockgenを使う場合

生成ツールを使うなら小さいinterfaceでも手間は同じなので、ISPの動機は「モック作成コスト」より「変更耐性」に移る。それでもISPの価値は消えない。

D Dependency Inversion Principle

① 困る変更要求 — 「MySQLからPostgreSQLに移行します」「GORM v1からv2に上げます」

実務では「DB移行」は稀だが、ORMのバージョンアップ、キャッシュ層の追加、リードレプリカへの振り分け、テスト用のインメモリ実装は頻繁に起きる。これら全てが同じ形の問題。

② 依存の向きが「外向き」になっているコード

③ なぜ問題なのか — 「変更頻度の向き」で考える

図7-2 DIPは「呼ぶ向き」と「importの向き」を分離する技術。この2つが同じだと思っている限り理解できない。

⑤ 改善後

⑨ 過剰設計の境界 — DIPを適用しない方が良い場合

  • 標準ライブラリへの依存は逆転しなくてよい — time / fmt / errors は「変わらないもの」。time.Time をラップするのは無駄（ただし time.Now() は別問題＝隠れた入力）
  • 管理画面のCRUDにDIPを敷く — handler から *gorm.DB を直接使うのは、CRUDに限れば合理的。レイヤーを跨いだ変換コードのほうがバグの温床になる
  • 「テストのため」だけが理由の場合は、まず本当にテストが必要か問う — SQLの正しさを検証したいなら、interfaceで抽象化してモックするのは無意味（SQLがテストされない）。testcontainers で実DBを使う統合テストのほうが価値が高い

L6視点 — SOLIDを「使わない判断」ができるか

  • L4: SOLIDを知らない、あるいは名前だけ知っている。コードは動く
  • L5: SOLIDを適用できる。ただし「常に適用した方が良い」と思っている。結果として小さなCRUDにも5層を敷く
  • L6: 「ここはOCPを効かせる（OTAは増えるから）。ここは効かせない（管理画面のマスタは増えない）」を、根拠を持って言い分けられる。さらに「今はswitchで書き、3社目が来たらこう抽象化する」という移行計画をコメントかADRに残す

08 DRY / KISS / YAGNI / Law of Demeter / Tell, Don't Ask

この5つは互いに衝突する。DRYを突き詰めるとKISSが壊れ、YAGNIを守るとOCPが効かない。重要なのは、衝突したときにどちらを優先するかの判断基準を持つこと。

DRY — 「コードの重複」ではなく「知識の重複」を消す

① よくある誤解が生む問題

DRYを「同じコードを書くな」と理解すると、偶然似ているだけの2つを共通化して、後で地獄を見る。これは実務で最も高頻度の設計事故。

② 誤ったDRY — 偶然の一致を共通化する

④ 原則 — DRYの正しい対象は「知識（Single Source of Truth）」

消すべき重複（真のDRY違反）

同じ意思決定が2箇所にある状態。
例: 「キャンセル無料は7日前まで」という数字が、domain と handler の両方に書かれている。片方だけ直すと不整合になる。これは必ず1箇所にする。

消してはいけない重複（偶然の一致）

今は同じだが、変更理由が違うもの。
例: 予約の期間制限と見積の期間制限。変更を依頼する人が違うなら、別のコードであるべき。

判定質問

「片方だけ変わる未来はあり得るか？」
あり得る → 分けておく（重複を許容）
あり得ない（あったらバグ） → 共通化する

コストの非対称性

誤って共通化したものを分離するコスト >> 重複を後から共通化するコスト。だから迷ったら重複させておくのが期待値的に正しい。

⑤ 改善後 — 知識の重複だけを消す

KISS と YAGNI — 「今」を最適化する原則

⑧ 原則同士の衝突と、優先順位の決め方

状況YAGNI が言うことOCP が言うこと判断

OTAが1社。半年後に2社目が経営計画に載っているまだ要らない抽象化せよOCP優先。「確定した将来要求」はYAGNIの対象外

Code Smell は「必ず直すべき欠陥」ではなく「調べる価値がある兆候」。医者が発熱を見て検査を始めるのと同じ。臭いを見つけたら、まず「どの変更要求で困るか」を確認し、困らないなら放置するのが正しい。

① God Object / ② Long Method

症状

1つの型/関数が数百行。「〜Manager」「〜Service」「〜Util」「〜Helper」という名前はほぼ確定サイン。

本当の問題

行数ではなく「変更理由の数」。50行でも3人のアクターが要求するなら God。500行でも1つの状態機械なら健全なことがある。

①この型/関数を過去1年で変更したPRの「変更理由」を数える ②git log で「同じファイルが違う機能のPRに何回現れたか」を数えるのが最も客観的

放置してよい場合

⑨ 過剰の境界

図9-2 Shotgun Surgery は「層の代償」でもある。ゼロにはできないので、漏れても壊れない仕組みで対処する。

誤解1: 関数を小さくすれば良い

④ 正しい判断基準 — 「行数」ではなく「抽象度」と「名前」

13 Dependency Rule — 「呼ぶ向き」と「importの向き」は別物

Clean Architecture の中身は、実質この1つのルールだけである。「ソースコードの依存（import）は、必ず外側から内側へ向かう」。これを理解する鍵は、「制御の流れ」と「依存の向き」が逆になる箇所があると気づくこと。

図13-1 実行時は上から下へ流れるが、importは常に内向き。この「ねじれ」を作るのがinterfaceの唯一の役割。

④ 原則 — Dependency Rule の正確な定義と3つの帰結

"Source code dependencies must point only inward, toward higher-level policies."（Robert C. Martin）

  1. 内側の層は、外側の層の名前を1つも知らない — domain パッケージの import 文に gorm / echo / aws-sdk が出てきたら違反。これは機械的に検査できる（ch17でCI設定を示す）
  2. 境界を越えるデータは、内側で定義された型である — repository が返すのは *domain.Reservation。*gorm.Model や *sql.Rows を境界の外に出さない
  3. 依存を逆転させる箇所は「外部世界へ出るところ」だけ — handler→usecase→domain は素直な依存。逆転が必要なのは domain→(DB/外部API) の部分のみ。全ての層の間にinterfaceを置く必要はない

ZOOM interface・DI・Wire は「別々の3つの仕事」— Animal で分解する

Dependency Rule を守る道具は3つあり、混同すると「DIって結局Wireのこと？」になる。役割は完全に別物。interface = 「できること」の契約、DI = 「誰を使うか」を外に出す設計、Wire = 「渡す作業」の自動生成。以下、予約・GORMを忘れて Animal で見る。

interface は「メソッド名と型だけを書いた契約」である。Goでは implements 宣言がないので、Speak() string を持つ型は全部、勝手に Animal になる（構造的型付け）。Greeter はフィールドの型を Animal にすることで「Speak できる何か」だけを要求し、それが犬か猫かを知らないまま呼べる。

② 何もしないと「ここからこれを使えてしまう」— Go のコンパイラは Dependency Rule を知らない

Go は import が書けるものは何でも呼べる。Greeter の中で pets.NewDog() を書いても、コンパイラは1文字も文句を言わない。interface も DI も使わない「素直な」コードがどう壊れるかを見る。

③ DI とは「Greeter は Animal を必要とする」と宣言し、「Dog を渡す」を外に追い出すこと

DI はライブラリではない。NewGreeter(a Animal) のシグネチャそのものが「Greeter が依存する interface の一覧」であり、これが「usecase はどの interface を持っているか」を明確にする正体。渡す側（main）だけが zoo と pets の両方を知る。

④ Wire がやっていること — コンストラクタの「引数の型」を読んで、手書きの main.go を生成する

Wire は DI の「考え方」ではなく「③の手書きコードを、型シグネチャから機械的に書く道具」。NewGreeter(a zoo.Animal) を見て「Animal を返す provider はどれだ？」と探し、wire.Bind で「Animal には *Dog を使え」と教えられて、生成順序まで解決した Go コードを吐く。実行時リフレクションはゼロ。

コスト2: 「なぜ2つあるのか」の説明コスト

⑩ レビュー観点

  • interfaceの定義位置。実装と同じパッケージにあるなら、依存が逆流している可能性
  • 境界を越える型。*gorm.DB / echo.Context / *http.Request が usecase や domain のシグネチャに現れていないか
  • 逆に、Query系で層を貫通しているコードに「違反だ」と言っていないか（意図的な設計判断ならOK。ただしコメントで宣言されているべき）

⑤ 解決の3択 — 強さとコストの順に

  • ドメインが1つしかないのに feature-first にする — internal/reservation/domain だけが存在する構成は無駄な階層。2つ目のドメインが生まれた時に分ければよい

② 「作らない方が良い」の実例 — モックで自己満足するテスト

④ 原則 — Goのinterfaceに関する4つの慣習

  1. "Accept interfaces, return structs" — 引数はinterfaceで受け、戻り値は具体型を返す（柔軟に受け、明確に返す）。ただしRepositoryのコンストラクタのように「実装型を隠したい」場合はinterfaceを返してよい
  2. "The bigger the interface, the weaker the abstraction"（Rob Pike）— 1メソッドのinterfaceが最強。io.Reader が全Goコードで再利用される理由
  3. interfaceは使う側が宣言する — 実装側が「これがAPIです」と宣言するのではなく、使う側が「これだけ必要です」と宣言する。これによりinterfaceは必要最小になる
  4. 抽象化は「発見」するもので「予測」するものではない — 2つ目の実装が現れたときに、共通点を抽出する。1つ目で予測した抽象は外れる

定義の二重管理メソッド追加時にinterfaceと実装の両方を編集中

モックによる偽の安心モックだけのテストで「テストがある」と思ってしまう大（品質が下がる）

⑩ レビューでの決め台詞（この章の実用的な成果物）

「実装は今いくつありますか？ テストで差し替える必要はありますか？ 両方Noなら、structを直接使いませんか」

Goは構造的型付けなので、後からinterfaceを追加しても既存の実装は1行も変更しなくてよい。だから「先に作っておく」動機が他言語より弱い。これは設計判断を後回しにできる貴重な性質。

Domain Modeling & DDD

DDDを「巨大な設計手法」として教えない。DDDが答えようとしている問いはたった1つ「ビジネスルールをコードのどこに置くか」である。Entity / VO / Aggregate / Domain Service は、その置き場所の候補につけられた名前にすぎない。予約システム（Reservation / Room / Plan / Guest / StayPeriod / ReservationStatus / RevisionID）を題材に、「このif文はHandler / UseCase / Domain のどこに置くべきか」を10例で比較する。最後に単純CRUDにDDDを持ち込む過剰設計を扱う。

18 DDDの出発点 — 「ルールの置き場所」問題

DDDの本（Evans本 / IDDD）は分厚いが、実務でまず必要なのは「あるビジネスルールを書くとき、5つの置き場所のどれを選ぶか」という判断だけである。用語を覚える前に、この判断を練習する。

図18-1 5つの置き場所。DDDの用語はこの表を説明するための語彙にすぎない。用語より判定基準を覚える。

① どんな問題があるのか — 「貧血モデル（Anemic Domain Model）」

ルールの置き場所を決めていないと、必ず「データだけのstruct」＋「巨大なService」という形になる。これが貧血モデル。DDDは、この形から抜け出すための道具立てである。

④ 設計原則 — 「ルールはデータの隣に置く」

状態を変えるルールは、その状態を持つ型の中に置く。これだけで Entity / VO / Aggregate の8割が導ける。残り2割（複数Entityにまたがる場合）が Domain Service。

19 Entity と Value Object — 「同一性」があるか、ないか

区別の基準は1つ。Entity = 「IDで同一と判断するもの」（値が変わっても同じもの）／Value Object = 「値そのものが同一性」（値が変わったら別のもの）。予約は Entity（金額が変わっても同じ予約）、金額は VO（1000円と2000円は別の値）。

図19-1 予約ドメインのモデル図。VOを多用し、他Aggregateへの参照はIDのみに留めるのが基本形。

⑧ トレードオフ — VOの3つの実務的な痛み

痛み1: ORMがunexportedを扱えない

GORMは reflect で非公開フィールドに書けない。→ DB用のrecord構造体 + Mapperが必須になる（Part 5 ch30）。これがClean+DDDの最大の定型作業。

痛み2: JSONシリアライズ

VOをそのまま json.Marshal すると {} になる。→ Response DTOが必要（Part 6）。結果的にAPI表現とドメインが分離されるので、これは利点に転じる。

痛み3: 比較とゼロ値

VOに slice や map を持たせると == で比較できない。VOは比較可能な型（数値・文字列・time.Time）だけで構成すると、テストが劇的に楽になる。

それでもVOを使う理由

「不正な値がシステムに存在しない」という保証は、他のどの手段でも得られない。バリデーションを各所に書く方式では、必ずどこかが漏れる。

⑨ 過剰設計になる境界

  • 全フィールドをVO化する — type RoomName string に不変条件がなければ、変換コストだけが残る。目安: 不変条件があるか、引数の入れ替え事故が起きるものだけ
  • Entityにgetterを全部生やす — 「Repositoryで保存するために全部必要」という理由でgetterを20個作るのは、Mapperを同一パッケージに置くことで回避できる（domain パッケージ内に ToRecord/FromRecord の変換関数を置く方式）。どちらを選ぶかはチームの好みだが、「getter地獄」は設計の失敗の兆候として認識する
  • 状態遷移表を作るほど状態がない — 状態が2つ（有効/無効）なら bool で十分。表が価値を持つのは3状態以上

20 Aggregate と Invariant — 「トランザクション境界」の別名

結論。Aggregate とは「1つのトランザクションで整合させる範囲」であり、それ以上でもそれ以下でもない。DDDの用語で最も実務的な意味を持つのがこれ。Aggregate の設計を間違えると、ロック競合とスケーラビリティの問題が直接発生する。

図20-1 Aggregate設計は「整合性 vs スループット」のトレードオフ判断。大きくすれば正しくなるが遅くなる。

① 実務の判断 — 予約と在庫を同一トランザクションにするか

本書のケースでは「予約Aggregateと在庫Aggregateは別だが、同一トランザクションで更新する」という判断を採る。これは原則「1Tx = 1Aggregate」の意図的な違反であり、理由を明示できることが重要。

なぜ同一トランザクションにするか

「予約はあるが在庫が減っていない」状態を業務が許容しない（オーバーブッキングが発生し、現場が対応不能になる）。結果整合の窓（数百ms〜数秒）でも、繁忙期には実害が出る。

なぜAggregateは分けるか

①在庫は「部屋×日付」単位でロックしたい（予約単位ではない）②在庫は他の経路（手動調整・OTAへの在庫配信・清掃による閉栓）からも更新される ③将来の在庫サービス分離に備える

この判断のコスト

2つのAggregateを1Txで更新するため、ロック順序を統一しないとデッドロックする（Part 5 ch33）。「常に予約→在庫の順、在庫内は日付昇順」というルールを明文化する必要がある。

将来分割するときの移行

Saga または「在庫の仮確保（hold）+ TTL」に移行する。この移行が来ることを前提に、在庫操作を Reserve/Release という語彙で書いておく（後で非同期にしやすい形にする）。これはYAGNI違反ではなく「命名の選択」なのでコストゼロ。

③ なぜ「アプリの不変条件」だけでは足りないのか — ch46への伏線

④ 原則 — 不変条件の「二重防御」

不変条件の種類アプリ（Entity/VO）DB両方書くべきか
1インスタンス内の整合（checkout > checkin）ここで守るCHECK制約（任意）アプリで十分。DBは保険
値域（金額 ≥ 0、人数 ≥ 1）VOで守るCHECK / UNSIGNED両方（アプリはエラーメッセージ、DBは最終防衛）
一意性（同じOTA予約番号は1件）守れない（TOCTOU）UNIQUE制約DB必須。アプリ側は「事前チェックで親切なエラー」用
集計値（在庫残 ≥ 0）守れない（並行更新）条件付きUPDATE + CHECKDB必須
状態遷移（canceled → confirmedは不可）ここで守る難しい（トリガーは避ける）アプリ + 楽観ロックで「読んだ状態が有効」を保証
順序（revisionは巻き戻らない）Entityで判定version条件付きUPDATE両方必須（Part 7 ch46の核心）

覚えるべき一文: 「1つのインスタンスを見れば判断できる条件」はアプリ、「複数レコードや他トランザクションを見ないと判断できない条件」はDB。

⑨ 過剰設計になる境界 — Aggregateを作らない方がよい場合

  • マスタデータ（部屋タイプ・プラン・設備） — 不変条件がほぼなく、更新も管理画面からだけ。Aggregateとして設計するより、素朴なCRUD + テーブルで十分
  • ログ・監査記録・イベント履歴 — 追記のみで状態遷移がない。Aggregateにする意味がゼロ
  • 集計・レポート — 読み取り専用。Aggregateを経由すると必ずN+1になる。Query側は専用のSQLで直接読む（ch27 CQRS）
  • Aggregate Rootを介した強制アクセス — 「在庫を更新するには必ず予約Aggregate経由で」というルールを作ると、清掃による閉栓や手動調整ができなくなる。現実の業務は複数の経路からデータを変える

⑩ レビュー観点

  • 1つのAggregateが何件のレコードをロードするか（数千件超なら設計を疑う）
  • 他Aggregateをオブジェクト参照で持っていないか（roomID RoomID ではなく room *Room になっていないか）
  • 1トランザクションで更新するAggregateの数（2つ以上なら理由を聞く）
  • 「この不変条件は並行実行下でも守られますか？」 — この質問1つで、ほとんどのAggregate設計のバグが見つかる
  • UNIQUE制約・CHECK制約がマイグレーションに入っているか（アプリのバリデーションだけを信じていないか）

21 Domain Service と Application Service — 混同されやすい2つ

結論。Domain Service は「計算・判定」、Application Service（UseCase）は「段取り」。前者は業務知識を持ち、後者は業務知識を持たない。「Serviceという名前がついているから同じ」と思っているうちは、ルールがUseCaseに流出し続ける。

図21-1 判定基準: 「その処理はDBを触るか？」触るならApplication Service、触らないならDomain Service（かEntity）。

① Domain Service が必要になる瞬間 — ダブルブッキング判定

⑨ 過剰設計になる境界 — Domain Service を作りすぎる害

  • Entityに置けるものをDomain Serviceにする — これが最も多い誤り。ReservationService.Confirm(r) のような形は、単に貧血モデルの言い換え。「引数が1つのEntityだけ」ならEntityのメソッドにできる
  • 「〜Service」という名前で思考停止する — Domain Service には業務的な名前を付ける（BookingConflictChecker, PricingPolicy, RoomAssigner）。「Service」で終わる名前は責務が曖昧になる兆候
  • 状態を持たせる — Domain Serviceがフィールドに可変状態を持つと、並行実行で壊れる。設定（ポリシー）を持つのは可（immutable）

22 Repository / Factory / Domain Event

この3つは「Aggregateのライフサイクル」を扱う道具。生成（Factory）、永続化と再構成（Repository）、変化の通知（Domain Event）。詳細は Part 5・Part 8 に譲り、ここでは「ドメインの視点から何であるか」を確定させる。

④ Repository の定義 — 「Aggregateのコレクションに見えるもの」

Repositoryとは

「Aggregateを、あたかもメモリ上のコレクションのように扱えるインターフェース」。SQLもキャッシュもコネクションも隠す。1 Aggregate に対して 1 Repositoryが原則。

DAOとの違い

DAOは「テーブル1つに対する操作」（reservation_guests テーブル用のDAO）。Repositoryは「Aggregate1つに対する操作」で、内部で複数テーブルを扱ってよい。粒度と語彙が違う（詳細はPart 5 ch30）。

戻す型

必ずドメイン型（*domain.Reservation）。*gorm.DB や record 型を返した瞬間に抽象が漏れる。

置き場所

interfaceは domain、実装は repository（ch13）。これがDIPの実体。

④ Factory — 「生成が複雑なとき」だけ作る

④ Domain Event — 「起きた事実」を型にする

⑧ トレードオフ — Domain Event を導入する判断

統一しないコスト

統一するコスト

全部CleanにするとCRUDのコードが5倍になり、開発速度が落ちる。全部CRUDにするとCoreがバグの巣になる。

解決策

L6の視点

統一の便益（認知負荷の低減）と、最適化の便益（速度と正しさ）を天秤にかける。「全部同じにするのは、判断を放棄している」が「毎ファイル違うのは、規律がない」。2〜3種類のパターンに集約するのが現実解。

段階内容コスト推奨
0. 分けないRepositoryが読みも書きも担当低CRUDならこれでよい

案C（完全非同期）既存のWorkerに購読を追加するだけ在庫の反映が遅れる分だけ、OTA側の在庫が古くなる

重要な原則: トランザクションの中に外部通信を入れてはいけない。理由は①外部の遅延がDBのロック時間になる ②外部呼び出しが成功してDBがロールバックすると不整合になる ③リトライすると外部呼び出しが重複する。Outbox パターンがこの3つを同時に解決する。

Part 4 のまとめ

  1. UseCaseの責務は「順序・境界・翻訳」の3つだけ。計算と判定は持たない
  2. 読みと書きの経路を分ける（CQRS段階1）。これだけで一覧の性能とAggregateの肥大を同時に解決
  3. Validationは3層で多層防御。重複はDRY違反ではない
  4. UseCaseの分割基準はトランザクション境界。行数ではない
  5. UseCaseからUseCaseを呼ばない。共有するのは能力（interface）とドメインの操作

批判の内容

33 Optimistic Lock / Pessimistic Lock / MVCC との関係

結論。「読んで、考えて、書く」の間に他人が書き換える可能性があるなら、必ずどちらかのロックが必要。予約Webhookは並列Workerで動くので、これは必須の話題。MVCCがあるから安全、という理解は誤りである。

図33-1 3つの対策。予約は①（楽観ロック）、在庫は③（原子的UPDATE）を選ぶのが本書の設計。

③ なぜ「MVCCがあるから安全」は誤りなのか

MVCCがしていること

「読み取りが書き込みをブロックしない」を実現する仕組み。トランザクション開始時点のスナップショットを読ませる。これは読み取りの一貫性の話。

MVCCがしていないこと

「読んだ値が、書き込む時点でも有効である」ことの保証。REPEATABLE READ でも、UPDATE時には最新の行が対象になる（MySQLの場合）。「読んだ値をもとに計算して書く」パターンは、MVCCでは守られない。

PostgreSQL の場合

REPEATABLE READ で書き込み競合が起きると could not serialize access エラーになる（＝アプリでリトライが必要）。つまりMVCCは「安全にする」のではなく「エラーで教える」だけ。

結論

SELECT → if → UPDATE のパターンを書いたら、必ず「並行実行でどうなるか」を考える。これは分離レベルに関係なく必要な思考。→ 詳細は transaction-system-design.html の Lost Update / Write Skew の章。

⑧ ロック方式の選択表（実務判断）

対象方式理由

③ 特に判断が難しい3つのケース

400 vs 422

400 = 「構文的に解釈できない」（壊れたJSON・型不一致）／422 = 「解釈できたが、意味的に受け付けられない」（期間が逆・定員超過）。厳密に守ると、クライアントが「自分のバグか、業務ルール違反か」を区別できる。区別しない選択（全部400）も実務的にはあり。

404 vs 403

他人のリソースIDを指定されたとき。403を返すと「そのIDは存在する」という情報を与える（列挙攻撃の材料）。機密性が重要なら404に統一。社内APIなら403で親切にする方がデバッグしやすい。

「同じ通知の2回目」は409ではなく200/204を返す。理由: 冪等な操作の再実行は「成功」である。409を返すとOTA側がエラーとして扱い、アラートを上げてしまう。409は「あなたが持っている情報が古いので、取得し直して再送してください」という意味に限定する。

④ 冪等性の定義を正確にする — 3つの異なる「冪等」

種類定義予約Webhookでの例

④ 順序非依存にするための3つの道具

道具仕組み適用条件注意点
単調増加するバージョン
（revision / version / seq）		「より大きいものだけを適用する」送信側が単調増加する番号を付ける（OTAはこれを提供する）番号がリセットされる場合がある（相手のシステム移行時）→ 監視が必要
タイムスタンプ
（updated_at / LWW）		「より新しいものだけを適用する」バージョンがない場合の代替時計のズレで壊れる。相手のサーバ間で数秒ズレると順序が狂う。可能なら使わない
状態の全量送信
（Full State Transfer）		差分ではなく「現在の完全な状態」を送るpayloadに全項目が含まれる（OTAのWebhookは通常こう）差分だけを送る相手には使えない。全量なら「最新だけ適用すれば正しい」が成立する

外部APIの同時呼び出し数を制限するプロセス内: semaphore / 全体: 分散レート制限制限なし（相手をDoSする）
同じ予約を同じWorkerに寄せるQueueのパーティションキー（otaIDでハッシュ）—

最後の行が最も設計として強い: 「同じ予約IDのメッセージは、必ず同じパーティションに入れる」ことで、そもそも並行実行が起きない。KafkaやSQS FIFO（MessageGroupId）で実現できる。ロックで守るより、競合が発生しない構造にするのが上位の解。ただしパーティション内は直列になるのでスループットが制限される（Drill #9で再検討する）。

⑩ 並行性のレビュー観点 — 「go test -race」だけでは足りない

  • go test -race が検出するのは「メモリのデータ競合」だけ。DBを介した競合（Lost Update）は検出しない。これを混同している人が多い
  • DBを介した競合を検出するには、「同じ処理を並列で実行して結果を検証する」統合テストを書く（下記）
  • グローバル変数・パッケージ変数への書き込みがないか
  • Mutexで守っている状態が、プロセスをまたいで共有される必要がないか
  • goroutineがリークしないか（ctx の受け取り、defer wg.Done()、チャネルのクローズ）

Part 7 のまとめ — 本書で最も重要な6点

  1. 状態が3つ以上なら遷移表にする。全組み合わせをテストする
  2. 重複は必ず起きる。「1回だけ送る」は実現不可能なので、受信側を冪等にする
  3. 順序は保証しない。順序に依存しない設計にする。全量 + 単調増加バージョンが鍵
  4. 1つのifを5つの視点で見る。役割ごとに domain / usecase / DB の3層に分解する
  5. アプリのifは並行実行に無力。「SELECT → 判定 → UPDATE」を見たら必ず疑う
  6. Mutexはプロセス内でしか効かない。正しさはDBに書く。分散ロックは最後の手段

52 Context / Timeout / Retry / Exponential Backoff

結論。タイムアウトのない外部呼び出しは、いつか必ずシステム全体を止める。そしてリトライは「間違って使うと障害を増幅する」危険な道具である。

③ リトライが障害を悪化させる3つのパターン

1. リトライストーム

相手が過負荷で500を返している状態で、全クライアントが3回リトライする → トラフィックが3倍になり、相手が完全に落ちる。対策: Circuit Breaker（ch53）+ ジッター + リトライ予算。

2. 多層リトライの掛け算

handler が3回、UseCase が3回、gateway が3回リトライすると 27回。リトライは「1箇所だけ」に置く。原則として最も外側（Worker）または最も内側（HTTPクライアント）のどちらか一方。

3. 冪等でない操作のリトライ

「予約を作成する」をリトライすると2件できる。リトライを実装する前に「この操作は冪等か」を確認する。冪等でないなら、リトライではなく冪等キーを先に実装する。

リトライ予算（advanced）

Googleの実践: 「全リクエストの10%までしかリトライに使わない」という予算を設ける。予算を超えたらリトライを止める。これにより、障害時にリトライがトラフィックを増幅しない。

53 Circuit Breaker / Fallback / Partial Failure / Compensation

結論。「相手が落ちているときは、呼ぶのをやめる」のが最も効果的な障害対策。落ちている相手を呼び続けると、自分のリソース（接続・goroutine・スレッド）が枯渇し、相手の障害が自分の障害になる（障害の連鎖）。

図53-1 Circuit Breaker。「失敗が確実な呼び出しを、即座に失敗させる」ことでリソースを守る。

④ Partial Failure — 「一部だけ成功した」をどう扱うか

予約Webhookでは、次の失敗パターンが実際に起きる。それぞれに方針を決めておく必要がある。

状況方針実装

DBは成功、OTAへのack送信が失敗DBはcommitし、ackはリトライOutbox + Worker。ackが数分遅れても業務は成立する

54 どのレイヤーでログを出すか

結論。ログは「エラーを処理し終える場所」で1回だけ出す。各層で出すと同じエラーが3回ログに現れ、件数が数えられなくなり、アラートの閾値が意味を失う。

図54-1 ログの二重報告。「返すならログを出さない、ログを出すなら返さない」が原則。

④ ログの原則 — 5つのルール

  1. 「エラーを返す」か「ログを出す」のどちらか一方。両方やると二重報告になる。終着点（handler / worker / main）だけがログを出す
  2. 例外: 「握りつぶす」場合は必ずログを出す。エラーを無視して処理を続けるなら、その事実を記録する必要がある（defer resp.Body.Close() のような無視は例外）
  3. 構造化ログを使う（slog）。メッセージに値を埋め込まず、フィールドにする。「provider=rakuten のエラーを集計する」ができるかどうかで、障害調査の速度が10倍違う
  4. ctxを渡す（ErrorContext）。trace_id / request_id が自動で入り、分散トレースと紐づく
  5. 機微情報を出さない。氏名・メール・電話番号・カード番号・トークン。payload全体をログに出すのは最も多い漏洩経路（マスキングか、ID参照だけにする）

Part 8 のまとめ

  1. エラーは層をまたぐごとに翻訳する。境界（repository / gateway）でドメインの語彙に変える
  2. %w でラップし、errors.Is/As で判定。文字列比較は禁止
  3. 8分類 → Status/Retry/Log/Alert のマッピング表を作る。これがない現場はアラート疲れになる
  4. ERRORは「人間が今やることがある」ものだけ。業務ルール違反はWARN/INFO
  5. リトライは1箇所だけ、ジッター付き、冪等性を確認してから
  6. ログは終着点で1回、構造化して、機微情報を抜いて

59 レガシーコードの安全な解体 — 5段階の手順

現実の仕事の大半は、これである。テストがなく、誰も仕様を知らず、動いている180行の関数。ここに手を入れる正しい順序を示す。最初にやるのはリファクタではなく「現在の挙動を固定すること」。

図59-1 5段階。Step 1（現状固定）を飛ばして Step 2 に進むのが最も多い失敗。

④ レガシー解体の原則 — 7つの実務ルール

  1. 動いているコードには価値がある — 「汚い」だけで書き換えない。変更要求が来ている箇所だけを直す（Boy Scout Rule）
  2. リファクタとバグ修正と機能追加を、同じPRに混ぜない — 混ぜると「どの変更が原因で壊れたか」が分からなくなる
  3. Strangler Fig パターン — 全面書き換えではなく、新しい実装を横に作り、少しずつ切り替える。「Big Rewrite」は歴史的にほぼ失敗する
  4. Feature Flag で切り替える — 新旧の実装を両方動かし、結果を比較する期間を作る（シャドーラン）。予約のような重要処理では、これが最も安全
  5. 「触らない」判断も設計判断 — 1年間PRが来ていないコードは、リファクタの投資が回収されない
  6. 計測してから直す — 「遅い」と思ってリファクタしたら、ボトルネックは別の場所だった、が最も多い無駄
  7. 解体の記録を残す — ADRに「なぜこの構造にしたか」「何を意図的に残したか」を書く。次の人が同じ調査を繰り返さないようにする

Part 9 のまとめ

  1. テストは設計の診断器具。書きにくいなら設計を直す（テストを諦めない）
  2. Unitはdomainに、Integrationはrepositoryと並行制御に。SQLはモックでは検証できない
  3. Fakeを第一選択。Mockは実装の詳細に結合し、リファクタを妨げる
  4. Golden Testで外部payloadを固定。実物をtestdataに置くこと自体が価値
  5. TDDはdomainだけ徹底する。全部やろうとして挫折するより効果が出る
  6. レガシーはCharacterization Testから。リファクタとバグ修正を混ぜない

Part 10 のまとめ — パターンとの正しい付き合い方

  1. パターンは「変更要求から自然に現れる形」。先に適用するものではない
  2. Goで実務的に価値があるのは6つ: Strategy / Adapter / Decorator / Facade / Observer / Command
  3. interface・関数型・compositionで、GoFの半分は不要になる
  4. Singletonとグローバル状態は使わない。DIで渡す

64 要求から始める（マクロ: System / Service）

出発点は1文の要求。「OTAから予約Webhookを受信し、予約をStayFlowへ反映する」。この1文から、まず箱の配置（マクロなSystem Design）を決める。ここは別教材の範囲だが、ミクロ設計の前提として必要なので確認する。

図64-1 マクロな設計判断が、ミクロ設計の制約を決める。「Workerが並列実行される」の一言が、Part 7 の全内容を必須にしている。

重要な認識 — マクロとミクロは独立ではない

「別教材でSystem Designを学んだ」ことと、この教材の内容は因果関係で繋がっている。

  • Queueを入れた → at-least-once配信 → 冪等性が必須（ch43）
  • Workerを並列にした → 同じ予約が同時に処理される → 楽観ロックが必須（ch46）
  • OTAを5社にした → payload形式が違う → 腐敗防止層が必須（ch23）
  • 外部通信を非同期にした → 結果整合になる → Outboxと補償処理が必須（ch53）
  • DBを1つに保った → 強整合が可能 → Sagaを避けられた（最大の設計判断）

逆に言えば: マクロな設計を変えると、ミクロな設計も変わる。「Queueをやめて同期処理にする」と決めれば、冪等性の要求は弱まる（ただしOTAの再送は残るのでゼロにはならない）。「アーキテクチャを決めた人」と「コードを書く人」が別だと、この因果が伝わらない — これが設計ドキュメント（ADR）が必要な理由。

Drill #9 — 1秒に10,000件届くようになった

変更箇所（7レベル）— 設計判断が「規模で変わる」実例

レベル変更内容
System①APIは受信のみ（署名検証 → Queue → 202）②Queueをパーティション分割（otaID のハッシュ）③Workerを水平スケール ④DBを書き込み分散（シャーディング or 予約テーブルのパーティショニング）⑤在庫のホットスポット対策
Package変更は小さい。UseCaseとdomainは無変更（★ 層を分けた最大の見返り）
Interfaceバッチ処理用のメソッドを追加: UpsertManyIfNewer(ctx, []*Reservation)（1件ずつではなく100件まとめて書く）
Struct変更なし
Function①Reconcileのサブクエリを廃止（重い）→ 差分更新 + 日次突合に変更 ②Entityの検証を通さない高速パス（条件付きUPSERT一発）を選択 ③受信記録を非同期化（別テーブル・バッチINSERT）
Database①予約テーブルのパーティショニング（check_in の月別）②在庫の更新競合対策（部屋×日付でシャード分散）③Outboxのバッチ読み取り ④Read Replicaへの読み取り分離 ⑤古いwebhook_receiptsのアーカイブ
Test負荷試験（k6 / vegeta）が必須。「1万件/秒でp99 < 100ms」をCIまたは定期実行で検証する。単体テストでは絶対に検出できない領域

最も重要な洞察: この規模では「Part 3〜5で作った綺麗な設計」の一部を意図的に捨てる。具体的には:

  • Entityの検証を通さない（SELECT → 検証 → UPDATE をやめ、条件付きUPSERT一発にする）→ 状態遷移の異常は日次突合で検出する
  • 在庫の完全な整合性を諦める（Reconcileの再計算をやめ、差分更新にする）→ ズレは突合バッチで修正する
  • 受信記録を非同期化する（Tx内でINSERTしない）→ 一部の記録が失われる可能性を受け入れる

これがL6の判断: 「正しさを担保する場所を、同期的な検証から非同期的な検出に移す」。捨てているのは「正しさ」ではなく「正しさを保証するタイミング」である。そして「何を捨てたか」「どう検出するか」「いつ気づけるか」を明文化する。これができないと、単に品質を落としただけになる。

Drill の使い方（実務での訓練法）

  • 自分のプロジェクトで同じ表を作る。実際に来た変更要求10件について、7レベルの影響を書き出す
  • ● が多いレベルを見る。そこが設計の弱点。特に「Package/Interfaceが毎回変わる」なら境界の引き方が間違っている
  • PRの差分ファイル数を記録する。1つの要求に対して10ファイル以上変わるなら、Shotgun Surgery（ch9）
  • 新機能の設計レビューでこの表を書く。「この機能に後から〜という要求が来たら、どこが変わりますか？」を必ず聞く

L6を目指す上での5つの誤解

誤解1: 抽象化が多いほど上位

逆。L6は「必要な抽象だけを持つ」。過剰な抽象化は、L5が陥りやすい罠として認識されている。

誤解2: 新しい技術を使うほど上位

無関係。L6は「なぜMySQLで十分か」を説明できる。技術選定は制約とコストの判断であり、新しさは基準ではない。

誤解3: コードを書かない

逆。最も難しい部分（並行制御・移行・境界）を自分で書く。設計だけして実装を任せると、設計の誤りに気づけない。

誤解4: 完璧な設計を最初に作る

不可能。L6は「今は簡単に作り、この条件になったらこう変える」という時間軸を持つ。段階的な移行計画こそが成果物。

誤解5: 1人で判断する

逆。判断をADR・コメント・レビューを通じて共有し、他の人が同じ判断を再現できるようにするのがL6の仕事。属人化させたら失敗。

本当の差

「何をやらないか」を根拠付きで言えるかどうか。L4は選択肢を知らない、L5は全部やろうとする、L6は選んで捨てる。

最後に — 本書のゴールの再確認

コードを見たときに「これは何をしているか」ではなく「なぜこのコードがこの場所に存在するのか」を説明できる状態が本書のゴールだった。

その説明は、常に次の形をとる:
「〜という要求があり、〜という制約（並行実行・外部の再送・変更頻度・チーム境界）があるので、〜という判断をした。その代償として〜を受け入れており、〜という条件になったら設計を変える予定である。壊れたときは〜で検出する。」

この文が言えるなら、SOLIDもDDDもClean Architectureもパターンも、全部その説明を支える道具として正しく使えている。逆にこの文が言えないなら、どれだけ層を分けても設計をしたことにはならない。

付 チートシート / レビュー観点まとめ

本書の要点を1画面に圧縮した。迷ったらここに戻る。

1. 設計の評価関数

要求の変更量に対して、コードの変更量が比例以下であること。美しさではない。「1要求 → 1箇所」に近づける。

2. 分割の軸

「変更を要求する人」で分ける。行数でも技術種別でもない。同じ理由で変わるものを集め、違う理由で変わるものを離す。

3. Testabilityは原因側の指標

テストが書きにくいのは症状。原因は「依存を自分で作っている」「判断と実行が混ざっている」「隠れた入力がある」。

4. Dependency Rule

importは常に内向き。interfaceを内側のパッケージが所有することで、制御の流れと依存の向きを逆にする。

5. interfaceを作る理由は2つだけ

複数実装 / 外部世界。「疎結合のため」「将来のため」は理由にならない。Goは後から足せる。

6. Aggregate = トランザクション境界

小さく保つ。大きくすると直列化してスループットが死ぬ。他AggregateはIDで参照する。

7. 不変条件は二重防御

1インスタンスで判断できる → アプリ / 全レコードを見る必要がある → DB。並行実行はアプリのifを無効化する。

8. UseCaseの責務は3つ

順序・境界・翻訳。計算と判定は持たない。if文が6個以上あったら、ルールが漏れている。

9. Txに外部通信を入れない

例外なし。DB更新とイベント記録を同一Txに入れ、配信はOutbox Workerが行う。

10. 「SELECT → 判定 → UPDATE」を見たら疑う

並行実行で必ず壊れる（TOCTOU）。条件をWHERE句に入れるか、楽観ロックにする。

11. 重複と順序逆転は同じ仕組みで解く

単調増加のバージョン + 全量payload + 「より新しければ上書き」。これで収束性が保証される。

12. エラーは8分類

分類 → Status / Retry / Log / Alert / ユーザー表示 のマッピング表を作る。ERRORは「人間が今やることがある」ものだけ。

13. ログは終着点で1回

「エラーを返す」か「ログを出す」のどちらか一方。構造化して、ctxを渡して、機微情報を抜く。

14. Fakeを第一選択

Mockは実装の詳細に結合し、リファクタを妨げる。SQLと並行制御は実DBでしか検証できない。

15. パターンは発見される

「変更要求から自然に現れる形」。Goで実務的に価値があるのは Strategy / Adapter / Decorator / Facade / Observer / Command の6つ。

16. CRUDにDDDを持ち込まない

Core / Supporting / Generic を分けて投資する。「全部同じにする」は判断の放棄。

17. 過剰設計も設計ミス

「将来のため」だけの抽象化は、外れたときにマイナスになる。今日のコードを読みやすく/テストしやすくするかで判断する。

18. L6の条件

「何をやらないか」を根拠付きで言える。何を捨て、どう検出し、いつ設計を変えるかを明文化している。

この本を1文にまとめると

ミクロなソフトウェア設計とは「決定を、変更の理由ごとに、適切な解像度の場所に配置する行為」である。

だから設計とは「この決定は誰の要求で変わるか」を問い続けることであり、実装とは「その場所に、その決定だけを書くこと」であり、レビューとは「決定が正しい場所にあるかを確認すること」であり、運用とは「配置が間違っていたことに気づく仕組みを持つこと」である。

そして最も重要なのは、「配置しない」という選択も配置の1つであるということ。全ての決定に専用の場所を用意する設計は、設計ではなく儀式である。
