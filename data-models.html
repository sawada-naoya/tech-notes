この教材のゴールは1つ。「なぜそのストレージを選んだか」を説明できるようになること。
システムデザイン面接で「Twitterを設計してください」と言われたとき、「全部PostgreSQLでいいです」は説明になっていない回答。「ツイートはアクセスパターンがこうなのでドキュメントDB、タイムラインはこうなのでRedisでキャッシュ…」が説明できている回答。DDIA Ch2 は、この差を埋めるための語彙を作る章である。

主張1

リレーショナルは万能ではない。ただし「万能に近い」ので、まず疑うべきは自分の設計。9割のケースでRDBが正解である。

主張2

選択の基準は「データの形」ではなく「アクセスパターン」。同じデータでも、どう読み書きするかでモデルが変わる。

主張3

「ドキュメントDBはread専用」は誤解。read/write両対応。read用途が多く見えるのは、キャッシュ的に使うアーキテクチャが多いから。

Part 1

リレーショナルの得意・苦手

他のモデルを理解するには、まずリレーショナルが何を得意とし、どこで苦しくなるかを正確に知る必要がある。「苦しくなる」の中身が、他のモデルが存在する理由そのものだから。

01 得意なこと・苦手なこと

④ 得意 / 苦手の整理

得意1: 構造が決まっていて正規化できるデータ

スキーマで型・NOT NULL・一意制約・外部キーを強制できる。「不正なデータが入らない」ことをDBが保証する。アプリのバグに対する最後の防衛線になる。

得意2: 複雑なJOINや集計

「今月の施設別・プラン別の売上を、キャンセル分を除いて集計」がSQL 1本で書ける。これを他のモデルでやると、アプリ側で全件走査するかETLが必要になる。

得意3: トランザクション・整合性

「予約を作り、在庫を減らす」を全部か無かで実行できる。これがある/ないで、アプリの複雑性が桁違いに変わる（補償トランザクションが不要になる）。

苦手1: 行ごとに構造が異なるデータ

カラムが可変。「商品タイプごとに属性が全然違う」場合、①全属性を nullable カラムで持つ ②EAV（属性テーブル）③JSON型 のいずれかになり、どれも綺麗ではない。

苦手2: 入れ子構造・ツリー構造の読み書き

「1注文 = 明細 + 配送先 + クーポン + 決済」を1画面に出すのに4〜6テーブルJOIN。読めるが、モデルとコードの距離が遠い。

苦手3: 「繋がり」自体が重要なデータ

「友達の友達の友達」を辿るのに再帰JOIN。3段階で SQL が爆発的に複雑になり、性能も予測不能になる。

補足 — 現代のPostgreSQLは「苦手」の多くを埋めている

苦手PostgreSQLの機能どこまで代替できるか
可変構造JSONB カラム + GINインデックスかなり代替できる。スキーマがある部分は列、可変部分はJSONBに置くハイブリッドが実用的
入れ子構造JSONB / 配列型 / json_agg読み取りは json_agg で1クエリにまとめられる。「4テーブルJOINして1つのJSONを返す」が可能
ツリー・グラフWITH RECURSIVE（再帰CTE）/ ltree数段の階層なら実用的。ただし「6ホップ先を最短経路で」のような探索は厳しい
全文検索tsvector / pg_trgm日本語は形態素解析が必要（pgroonga など）。大規模ならElasticsearchに分離
時系列パーティショニング / TimescaleDB拡張パーティショニングで十分な場合が多い
KVS的な高速readUNLOGGED TABLE / index-only scanRedisには及ばない（メモリ vs ディスク）

実務的な結論: 「PostgreSQL + 必要になったらRedis/Elasticsearch」でほとんどのサービスが成立する。MongoDBやNeo4jを最初から選ぶのは、明確な理由があるときだけ。ただし「知らないから選ばない」と「知っていて選ばない」は違う — 以降の章はその区別のためにある。

Part 2

ドキュメントモデル

本質は1つ。「一緒に読み書きされるデータを1塊にする」モデル。JOINをしない代わりに、関連データをネストして持つ。これはDDDの Aggregate と同じ発想であり、だからこそドキュメントDBは「Aggregateをそのまま保存できる」という利点を持つ。

03 本質 — 一緒に読み書きするものを1塊に

結論。ドキュメントモデルの判断基準は「データの形」ではなく「アクセスの単位」。常に一緒に読み、常に一緒に書くなら、1塊にする価値がある。

図3-1 埋め込む/参照するの判断。ドキュメントDBの設計の8割はこの判断である。

DDDの Aggregate との対応（重要な洞察）

同じ発想

Aggregate =「1トランザクションで整合させる範囲」／ドキュメント =「1回の読み書きの単位」。どちらも「一緒に扱うものを1塊にする」という同じ問いに答えている。

だから相性が良い

Aggregateをそのままドキュメントとして保存できる。RDBだと Aggregate → 複数テーブル への分解（mapper）が必要だが、ドキュメントDBならそれが不要になる。これがドキュメントDBの最大の設計上の魅力。

Aggregateの原則がそのまま使える

「Aggregateは小さく保つ」「他AggregateはIDで参照する」— この原則はドキュメント設計にそのまま適用できる。ddd-practice.html / software-design-micro.html ch20 を参照。

ただし失われるもの

複数Aggregateにまたがるトランザクション。「予約を作り、在庫を減らす」を原子的にできない（MongoDBは4.0+でマルチドキュメントTxを持つが、性能とスケールの制約がある）。→ Saga・補償トランザクションが必要になる。

具体例で比較する。EC サイトの注文履歴は、ドキュメントモデルが最も分かりやすく効く例。

⑥ Before / After — 操作別の比較

操作リレーショナルドキュメント
1注文を表示する4テーブルJOIN（または json_agg）1回の読み取り（findOne）
注文を作成する4回のINSERT（Txで囲む）1回の insertOne（原子的）
「明細に商品Xを含む注文」を検索JOIN order_items WHERE product_name = ?配列内検索（インデックスを張れる）
「今月の商品別売上」を集計GROUP BY で1クエリAggregation Pipeline（$unwind + $group）。書けるが重い
配送先だけを更新1テーブルのUPDATEドキュメント全体を読んで書く（または $set で部分更新）
「同じ住所の注文」を検索index付きで高速ネストしたフィールドのindexが必要
商品名が変わったとき履歴を残すなら非正規化が必要（結局コピー）コピーが自然（注文時点の情報として残る）
スキーマ変更（項目追加）ALTER TABLE（大テーブルではロック・時間がかかる）不要（新しい項目を持つ文書を書くだけ）

読み取り時のポイント: 「注文時点の商品名・価格を残す」という業務要件がある場合、RDBでも結果的に非正規化（コピー）することになる。この場合、ドキュメントモデルの方が「意図が素直にコードに現れる」。

05 実際に使われる場面

ドキュメントDBが選ばれる典型例

サービス例なぜドキュメントかキーとなる性質
ECサイトの注文履歴注文ごとに商品数・配送先・クーポンがバラバラ。注文時点の情報を凍結したい可変構造 + 一括読み書き + 履歴の凍結
ブログ・CMS記事ごとにタグ数・カスタムフィールドが異なる可変構造 + 記事単位のアクセス
チャットのメッセージ1メッセージに添付・リアクション・スレッドがネスト入れ子 + 追記中心
ゲームのユーザーデータキャラクター・アイテム・ステータスが柔軟に変わる。スキーマ変更が頻繁可変構造 + スキーマ変更の速度
IoTのセンサーログデバイスごとにカラム構造が違う。追記のみ可変構造 + 追記（ただし時系列DBの方が適する場合が多い）

予約システムへの当てはめ: 「1予約に紐づく全情報（ゲスト・部屋・オプション・鍵情報）をまとめて取得する」場面にフィットする。ただし在庫の整合性（トランザクション）が必要なので、予約本体はRDBに置くのが妥当。OTAから受信した生ペイロード（社ごとに形が違う・追記のみ・監査用）はドキュメント的な保存が向く — 実際にはPostgreSQLのJSONBカラムで足りることが多い。

06 トレードオフ（正直な評価）

ドキュメントDBの「スキーマレス」は、スキーマがなくなるのではなく、スキーマの管理責任がアプリに移るだけである。これを理解せずに採用すると、数年後に苦しむ。

⑧ 失うもの（採用前に必ず認識する）

1. 横断集計が重い

「全注文の商品別売上」は $unwind + $group のAggregation Pipelineになり、RDBのGROUP BYより遅く、書きにくい。分析要件があるなら、別途データウェアハウス（BigQuery等）へのETLが必要になる。

2. 多対多が扱いにくい

「記事↔タグ」の双方向参照。ドキュメントでは「両方に持たせる（重複）」か「中間コレクション（=RDBと同じ）」になる。JOINがないので、アプリ側で2回読む = N+1のリスク。

3. スキーマの責任がアプリに移る

「古い形式の文書」と「新しい形式の文書」が混在する。読み取り時に両方を扱うコードが必要（doc.newField ?? doc.oldField）。マイグレーションを「やらなくてよい」のではなく「やらないと技術的負債が溜まる」。

4. トランザクションの制約

複数ドキュメント間の整合性。MongoDB 4.0+ はマルチドキュメントTxを持つが、性能ペナルティがあり、シャード横断では制約が大きい。設計として「1ドキュメント = 1トランザクション」に収める必要がある。

5. ドキュメントサイズの上限

MongoDBは16MB。「無制限に増える配列を埋め込む」設計は必ず破綻する（コメント・ログ・履歴）。設計時に「この配列は最大何件か」を見積もる必要がある。

6. 運用の知見

RDBは20年分のノウハウ・ツール・人材がある。障害時の調査・チューニング・バックアップ戦略で、経験者の有無が大きく効く。これは技術的な優劣ではなく、組織のリスク。

⑨ 「ドキュメントDBを選ばない方がよい」ケース

  • トランザクション整合性が業務要件 — 予約と在庫、注文と決済、送金。RDBを選ぶ
  • 分析・レポートが主要な機能 — 横断集計が重い。RDB + DWH の方が素直
  • スキーマが実は安定している — 「将来変わるかも」は理由にならない（YAGNI）。実際に変わっている実績があるかで判断する
  • チームにRDBの経験しかない — 学習コスト + 運用リスクを、得られる利点が上回るか
  • PostgreSQLのJSONBで足りる — 最も多いケース。「一部のカラムだけ可変」ならJSONBが最適解（トランザクションもJOINも維持できる）

Part 3

グラフモデル

本質は1つ。「繋がり自体がデータ」になる場合に使うモデル。ノード（実体）とエッジ（関係）で構成し、エッジにも属性を持てるのが決定的な違い。「AとBが友達」だけでなく「いつから友達か」「どれくらい親密か」を関係そのものに持たせられる。

07 本質 — 繋がり自体がデータ

結論。「関係を何段階も辿るか」がグラフDBの唯一の判断基準。1〜2段ならRDBで十分（それはただのJOIN）。3段以上、かつ段数が動的に変わるなら、グラフDBを検討する。

図7-1 index-free adjacency がグラフDBの技術的な本質。「深く辿る」ときだけ効く。

08 再帰JOINの爆発 vs Cypher

具体例で見る。SNSの「友達の友達の友達」を辿る。

⑥ 比較まとめ

やりたいことRDBグラフDB
1ホップ（友達一覧）JOIN 1回。速い同等
2ホップ（共通の友達）JOIN 2回。実用的同等
3〜5ホップ再帰CTE。書けるが遅い / 中間結果が爆発自然に書ける・速い
可変長（1〜Nホップ）再帰CTE + 深さ制限を自作*1..N で1行
最短経路非常に困難（ダイクストラを自作）shortestPath() 組み込み
経路の重み合計で最適化実質不可能reduce() で書ける
大量の集計（月間売上）GROUP BY で高速苦手（そもそも用途外）
単純なCRUD最適できるが、わざわざ使う理由がない
トランザクション成熟Neo4jはACID対応だが、分散時の制約あり
運用・人材・ツール豊富限定的

09 実際に使われる場面 / トレードオフ

グラフDBが選ばれる典型例

サービス例なぜグラフか辿る対象
SNS（フォロー・推薦）「友達の友達」を辿って「知り合いかも」を出すUser → FRIEND → User → FRIEND → User
地図の経路探索交差点=ノード、道路=エッジ、距離/所要時間=エッジ属性最短経路 + 重み最小化
レコメンド（Netflix / Amazon）「この作品を見た人が見た別の作品」User → 視聴 → 作品 → ジャンル → 別作品
不正検知「同じ端末・同じ住所で繋がる複数アカウント」を発見送金・デバイス・住所の異常な繋がり
組織図・権限管理部署 → チーム → ユーザーの階層と権限の継承階層の上下 + 継承ルール
知識グラフ / マスタデータ管理概念間の関係（同義語・上位下位・関連）意味的な繋がり
依存関係の解析パッケージの依存ツリー・マイクロサービスの呼び出し関係循環検出・影響範囲の特定
競合施設分析「A施設はB・Cと競合、B施設はC・Dと競合」という複雑な関係網類似度・同エリア・同カテゴリの関係

⑧ グラフDBを採用するコスト

コスト1: 学習コスト

Cypher / Gremlin という新しいクエリ言語。チーム全員が書けるようになる必要がある（あるいは書ける人がボトルネックになる）。

コスト2: 運用の知見が薄い

バックアップ・監視・チューニング・障害対応。RDBの20年分のノウハウが使えない。マネージドサービス（Neptune / AuraDB）を使っても、内部の理解は必要。

コスト3: 集計・レポートが苦手

「月間の売上集計」のような処理は苦手。結果的にRDBやDWHとの併用になり、データの二重管理が発生する。

コスト4: 「本当に3段以上辿るのか」

実際の要件は1〜2段のことが多い。「友達の友達」（2段）はRDBのJOIN 2回で十分。3段以上を、実際のユースケースとして持っているかを確認する。

⑨ 「グラフDBを選ばない」判断のための3つの質問

  1. 実際に3段以上辿るユースケースがあるか？ — 「将来推薦機能を作るかも」は理由にならない。今ある要件で判断する
  2. PostgreSQLの再帰CTEで足りないか？ — 数千ノード・4段程度なら実用的。まずこれを試して、性能を測る
  3. その用途だけを分離できるか？ — 「全部Neo4jに移行」ではなく「推薦機能だけグラフDB、本体はRDB」にできるか。できるなら、リスクが局所化される

実務的な現実: グラフDBを本番で採用する判断は、多くのチームにとって重い。「関係の探索」が主要な機能でない限り、RDB + 再帰CTE、あるいは「関係をアプリのメモリに載せて計算する」（数千ノードなら十分可能）という選択の方が現実的なことが多い。

12 ポリグロット・パーシステンス

1つのサービスの中で複数のDBを目的別に使い分ける設計。「全部PostgreSQLでいい」は小規模なら正しいが、スケールすると限界が来る。

図12-1 ポリグロットの実例。「用途ごとに最適なストレージ」+「事前計算でreadを速くする」の2つが要点。

⑧ ポリグロットのコスト（採用前に認識する）

コスト1: 整合性の担保が自前になる

「RDBに書いたが、Elasticsearchへの同期が失敗した」が必ず起きる。Outbox パターン / CDC（Debezium）/ 定期的な突合バッチが必要になる。

コスト2: 運用対象が増える

監視・バックアップ・アップグレード・障害対応が N倍。DBを1つ増やすたびに、オンコールの負荷が増える。

コスト3: 開発者の認知負荷

「このデータはどこにあるか」を全員が把握する必要がある。データの所在を示すドキュメントが必須。

だから順序が重要

①1つのRDBで始める ②計測する ③ボトルネックを特定する ④その用途だけを分離する。この順序を飛ばして最初からポリグロットにするのは、ほぼ常に過剰設計。

13 read/write の誤解

「ドキュメントDBはread専用」は誤解。read/write 両対応である。read用途が多く見えるのは、ドキュメントDBをキャッシュ的な役割で使うアーキテクチャが多いからで、それはDBの特性ではなく設計の選択。

④ 正しい理解

ストレージread/write選ぶ理由正本になれるか
リレーショナル両対応整合性の都合で選ぶなれる（最も一般的な正本）
ドキュメント両対応データ構造の都合で選ぶなれる
グラフ両対応関係の探索のためなれる（ただし正本にする例は少ない）
KVS（Redis）主にread高速化速度のため基本的にならない（失っても再構築できる形で使う）
列指向（BigQuery）read中心（追記）集計性能のためならない（本番DBのコピー）
全文検索（ES）read中心（追記）検索機能のためならない（同期が必要）

整理: 「read/writeの向き」と「正本になれるか」は別の軸。ドキュメントDBは正本になれる（read/write両対応）。RedisやESは正本になれない（正本の派生）。「正本はどこか」を1つに決めるのが、ポリグロット設計の最初の一歩。

14 面接での答え方 / 予約システムへの当てはめ

システムデザイン面接での答え方（3ステップ）

Step 1: アクセスパターンを先に整理する

「まず読み書きのパターンを整理させてください」と言ってから始める。「書き込み: 秒間N件、1件あたりのサイズ」「読み取り: 主キー引きか検索か、read:write比」を明示する。これを飛ばしてDBを選ぶと、根拠のない選定になる。

Step 2: 用途ごとに分ける

「1つのDBに全部載せるか、用途で分けるかを検討します」。そして「まず全部RDBに置き、ここがボトルネックになったらここを分離します」という段階的な計画を示す。

Step 3: トレードオフを言う

「この構成で失うものは〜です」を必ず自分から言う。「Elasticsearchに分離すると、検索結果に数秒の遅延が出ます。それが許容できるかを確認したいです」 — これが評価される。

避けるべき答え方

×「全部PostgreSQLでいいです」（検討していない）
×「MongoDBを使います」（理由がない）
×「Cassandraを使います」（知識の披露で、要件と繋がっていない）
△「スケールするのでNoSQLを」（NoSQLは分類ではない）

予約システム（StayFlow）への当てはめ

データ選択理由
予約・在庫MySQL（リレーショナル）トランザクション整合性が業務要件（「予約は取れたが在庫が減っていない」を許容できない）。一意制約（同じOTA予約番号は1件）も必要
OTAから受信した生ペイロードMySQL の JSON カラム / S3社ごとに形が違う・追記のみ・監査と再処理のため保持。「1予約に紐づく全情報をまとめて取得」する用途にはドキュメント的な保存がフィット。ただし別DBを立てるほどではない
予約の検索（施設名・ゲスト名の部分一致）まず MySQL の index / 全文検索インデックス数十万件までなら十分。それを超えたら Elasticsearch を検討
在庫の照会（読み取り）Redis キャッシュ（必要になったら）「空室検索」は read が圧倒的に多い。ただし「確保」は必ずMySQLで（整合性）
稼働率・売上の分析リードレプリカ → 必要ならBigQuery本番DBで重い集計を回すとサービスに影響する
競合施設の関係網（Lighthouse）まず MySQL + 再帰CTE「A施設はB・Cと競合、B施設はC・Dと競合」という関係網。2〜3段なら再帰CTEで十分。多段の類似度探索が主要機能になったらグラフDBを検討
セッションRedis または cookie（JWT）揮発してよい / 失っても再ログインで復旧できる

結論: StayFlow の規模では「MySQL 1つ + 必要になったらRedis」で十分。重要なのは「他のモデルを知っていて、選ばなかった」という状態を作ること — そしてその判断をADRに残すこと。

DDIA Ch2 との接続（この教材のまとめ）

DDIA Ch2 が言いたいことは3つ:
① リレーショナルは万能ではない
② データの「形」と「アクセスパターン」によって最適なモデルが変わる
③ どのモデルを選ぶかは設計判断であり、トレードオフがある

設計面接で「なぜPostgresを選んだか」と聞かれたとき、「他のモデルでは解決できない理由」あるいは「他のモデルを選ばなかった理由」を言えると深さが出る。

そして実務では、①〜③を知った上で「それでもRDBで十分」と判断できることが、最も価値のある結論であることが多い。
